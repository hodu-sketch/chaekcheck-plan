지금 쓰는 PostgreSQL 안에 기록용 칸(새 schema)을 하나 더 만드는 것을 추천합니다.

1같은 PostgreSQL에 기록 칸을 새로 만듦 [안]

이렇게 되면: 새로 설치하는 프로그램이 없습니다. 나중에 "어느 지역 도서관이 많이 눌렸나"를 볼 때 기록과 도서관 정보를 한 번에 맞춰 볼 수 있습니다. 지금 모듈마다 칸(schema)을 따로 두는 방식 그대로입니다.

커지면: 기록을 달마다 나눠 두면 오래된 달을 통째로 지울 수 있습니다. 공식 문서는 이 나누기가 표가 서버 메모리(4GB)보다 커질 때쯤 의미가 있다고 해서, 처음에는 나누지 않고 시작해도 됩니다 (PostgreSQL 공식 문서, 확인 2026-10-12).

크기 어림: 한 줄 0.3~0.5KB. 하루 1만 건이면 1년에 1~2GB입니다. 이용자 수를 몰라 어림한 값이고, 운영 뒤에 잽니다.

지금 예상하는 양(하루 수만 줄)이면 DB에 남겨도 검색이 느려지거나 RAM이 눈에 띄게 늘지 않습니다. 단, 검색 요청 안에서 바로 쓰지 말고 모아서 몇 초마다 한 번에 넣어야 합니다. 파일(JSONL)은 DB 부담이 아예 없는 대신, 통계를 낼 때 파일을 읽어 들이는 일이 따로 생깁니다.

JSONL이란: 기록 한 건을 JSON 한 줄로 파일 끝에 덧붙이는 형식입니다. 예: {"t":"2026-10-20T21:03","title":"채식주의자","results":12}

2) DB 부담: 트랜잭션·잠금·RAM

걱정공식 문서로 확인한 것
검색을 막을까 (잠금)기록을 넣을 때 걸리는 잠금과 검색이 거는 잠금은 서로 부딪치지 않습니다. 같은 칸을 읽고 쓰더라도 서로 기다리지 않습니다 (PostgreSQL 잠금 문서). 기록은 새 칸이라 책·도서관 칸과 아예 다릅니다
트랜잭션이 무거울까한 줄씩 따로 넣으면 넣을 때마다 디스크 쓰기를 기다립니다. 공식 문서는 여러 줄을 한 트랜잭션으로 묶어 넣으라고 권합니다 (Populating a Database). 기록용 트랜잭션만 "비동기 커밋"으로 하면 디스크 쓰기를 기다리지 않고, 공식 문서도 이벤트 기록을 이 방식에 맞는 예로 듭니다 (비동기 커밋 문서)
DB 연결이 모자랄까서비스는 DB 연결을 10개까지 씁니다(설정 없음, 기본값) (HikariCP). 몇 초마다 한 번 묶어 넣으면 연결 하나를 아주 잠깐 씁니다. 한 줄씩 검색 요청 안에서 넣으면 사람이 몰릴 때 검색과 연결을 다툽니다
RAM (DB)기록은 표 끝에 붙기만 해서, DB 메모리(공유 버퍼)에는 마지막 몇 쪽만 올라옵니다. 넣기에는 정렬용 메모리(work_mem)가 쓰이지 않는 것으로 보이지만 문서에 직접 적혀 있지는 않아 확인 못 함입니다 (메모리 설정 문서)
RAM (서비스)모아 두는 동안 서비스 메모리에 둡니다. 1,000줄 × 0.5KB = 약 0.5MB로, 힙 512MB에 비해 작습니다 (어림)
청소(autovacuum)넣기만 하는 칸도 1,000줄 + 20%쯤 쌓일 때마다 DB가 알아서 한 번 정리합니다. 이 정리는 뒤의 정리를 가볍게 만드는 일입니다 (autovacuum 문서)

3) 지금 서비스에 맞는가

  • 서버 한 대(4GB) 안에 DB가 같이 돕니다. 하루 수만 줄이면 1년에 1~2GB(어림)로, 지금 DB 약 8.5GB에 비해 작습니다.
  • 다음 일인 통계는 "어느 지역·도서관이 많이 눌렸나"처럼 도서관 정보와 맞춰 보는 것이라 DB 쪽이 쉽습니다.
  • 서비스의 기존 이벤트 기능(Spring Modulith 이벤트)으로 기록하면 이벤트마다 이벤트 기록 칸에 넣고 지우는 일이 한 번씩 더 생겨, 기록 한 줄에 DB 쓰기가 세 번이 됩니다 (Spring Modulith 문서). 그래서 이 기능은 쓰지 않는 쪽을 권합니다.

질문: Spring Modulith 이벤트가 뭐고, 지금 그걸로 기록하는 게 있나

지금 검색이나 클릭을 기록하는 데 쓰는 곳은 없습니다. 이 기능은 회원 탈퇴 한 곳에서만 씁니다.

무엇인지: 서버 안의 한 부분(모듈)이 "이런 일이 있었다"고 알리면, 다른 부분이 그 알림을 받아 자기 일을 하게 하는 기능입니다. 알림을 놓치지 않도록 DB의 이벤트 기록 칸(event_publication)에 먼저 적어 두고, 받는 쪽이 일을 마치면 그 줄을 지웁니다.

지금 쓰는 곳 (dev 코드 2026-10-12 확인): 회원 탈퇴 하나뿐입니다.

순서하는 일
1로그인 부분(auth)이 회원을 지우고 "회원 탈퇴됨" 알림을 냄
2이벤트 기록 칸에 받을 곳마다 한 줄씩 적음
3내 도서관 부분(mylibrary)이 그 회원의 지역·도서관을 지움, 탈퇴 기록을 서버 로그에 남김
4일이 끝나면 이벤트 기록 칸의 줄을 지움

왜 이번 기록에 안 쓰는지: 검색 기록을 이 방식으로 하면 "검색 부분이 알림 → 기록 부분이 받아서 저장"이 됩니다. 검색 한 번마다 이벤트 기록 칸에 적고 지우는 일이 더 생겨, 기록 한 줄을 남기려고 DB에 세 번 쓰게 됩니다. 탈퇴처럼 드물고 꼭 처리돼야 하는 일에는 맞지만, 잦고 몇 줄 빠져도 되는 기록에는 무겁습니다 (Spring Modulith 문서, 확인 2026-10-12).

  • 기록이 한 번이라도 빠지면 안 되는 일은 아니라서, 서버가 갑자기 꺼질 때 마지막 몇 초가 빠지는 것은 받아들일 수 있다고 봅니다.

정리: 추천은 그대로 DB 기록 칸입니다. 조건은 셋입니다: 검색 응답과 떨어져서 쓰기, 모아서 몇 초마다 한 트랜잭션으로 넣기, 기록용 트랜잭션만 비동기 커밋. DB를 전혀 건드리고 싶지 않으시면 JSONL 파일이 맞고, 그때는 "통계를 낼 때 파일을 DB로 옮겨 넣기"가 사이클 범위에 들어옵니다. 1번 칩에서 고르시면 됩니다. JSONL로 가시려면 기타에 적어 주세요.

확인 못 한 것: 넣기가 정렬용 메모리를 쓰지 않는지, 파일이 서버가 꺼질 때 얼마나 빠지는지, 칸에 색인이 하나 늘 때 넣기 비용. 사이클에서 시험으로 잽니다. 자세한 근거는 docs/research/usage-log/storage.md 2.6·2.7절.

질문: 이런 서비스들은 보통 어디에 저장하나 (유명한 곳들)

작게 시작한 분석 서비스들은 PostgreSQL 하나에 남기다가, 느려지면 분석 전용 DB(ClickHouse)로 옮겼습니다. 하루 수천억 건을 다루는 큰 회사들은 대기열(Kafka 등) → 파일 저장소(S3 등) → 분석 창고(BigQuery 등)로 보냅니다. 지금 우리 규모는 앞쪽에 가깝습니다.

질문: 서버 메모리를 4GB로 할 건데, 기록 때문에 모자라지 않을까

기록을 DB에 남겨도 4GB 안에서 정해 둔 몫은 그대로입니다. DB도 서비스도 상한이 고정이라 기록 때문에 메모리 몫이 늘지 않습니다. 기록이 쓰는 것은 메모리보다 디스크(1년 1~2GB 어림)입니다.
어디기록 때문에 달라지는 것
서비스 (Java)몇 초 모으는 동안 약 0.5MB(어림). 힙 상한 512MB는 그대로
DB 컨테이너상한 1GB, 공유 버퍼 64MB, 연결 10개 모두 그대로. 기록 넣기는 이미 있는 연결 하나를 잠깐 씀. DB가 알아서 하는 정리(autovacuum)가 기록 칸에도 가끔 돌지만, 이미 다른 칸에도 도는 것과 같은 몫 안에서 돎
파일 캐시기록은 칸 끝에만 붙어서 최근 몇 쪽만 캐시에 올라옴. 책·소장 파일이 캐시에서 밀려나는 양은 작다고 봄(어림, 사이클에서 잼)
디스크 (gp3 40GB)1년 1~2GB(어림). 반영할 때 책 표가 두 벌(약 16GB)이 되는 순간이 디스크에서 가장 빡빡하므로, 기록 크기를 그 계산에 더해 봄

JSONL 파일이면: DB 쪽은 아예 0이지만, 파일에 쓸 때도 운영체제가 파일 캐시를 씁니다. 메모리 면에서는 두 방식 차이가 거의 없습니다(어림).

조심할 것: 메모리가 문제가 되는 것은 기록을 남길 때가 아니라 나중에 통계를 낼 때입니다. 1년 치 기록을 한 번에 훑는 집계는 정렬·묶음용 메모리를 씁니다. 그래서 통계 사이클에서 "하루치씩 미리 합쳐 두기" 같은 방법을 같이 정합니다.

근거: 메모리 몫 docs/research/deploy/aws-layout.md 6절(서비스 측정은 로컬 PC 기준), PostgreSQL 메모리 설정 (공식 문서, 확인 2026-10-12). 조회 서버와 OS 몫은 재지 않음. 실제 영향은 사이클에서 기록 켜기 전·후로 docker stats로 잽니다.

2무엇을 "검색 한 번"으로 셀까

사용자가 검색 버튼을 누른 그 처음 요청만 한 번으로 세는 것을 추천합니다.

2처음 검색 요청만 한 줄로 남김 [안]

이렇게 되면: "김영하"로 검색하면 한 줄이 남습니다. 그 뒤에 화면이 알아서 부르는 "다음 묶음", "대출 수 채우기", "다음 쪽"은 남기지 않습니다. 사람이 한 검색 수와 기록 수가 같아집니다.

검색 입구는 둘입니다: 수집한 책 목록에서 찾기, 도서관에서 직접 찾기. 둘 다 같은 방식으로 셉니다.

다른 선택: 다음 쪽·책 상세 보기까지 따로 남김 → 사람이 어디까지 봤는지 알 수 있지만 줄 수가 몇 배로 늘고, 나중에 "검색 한 번"을 다시 골라 세야 합니다.

승인하며 덧붙이신 것: 검색한 사람의 지역·도서관도 남기기

검색할 때마다 화면이 거주 지역, 직장 지역, 고른 도서관, 범위를 이미 서버로 보냅니다. 그래서 회원 번호 없이도 같은 줄에 남길 수 있고, 4번(회원 번호·IP 없이)과 부딪치지 않습니다. 원본 문서에 사용자 말 그대로 적었습니다. 다만 이 셋을 합치면 사람마다 꽤 다를 수 있어, 다른 정보와 합쳐 특정인을 알아볼 수 있게 되는지는 전문가에게 확인할 것으로 남겼습니다.

3도서관 클릭은 어떻게 알까

링크는 지금처럼 바로 열고, 브라우저가 따로 "이 도서관 눌렀음"을 우리 서버에 보내는 것을 추천합니다.

3링크는 그대로, 클릭 알림만 따로 보냄 [안]

이렇게 되면: 사용자가 결과 카드를 누르면 새 탭은 지금처럼 바로 열립니다. 동시에 브라우저가 우리 서버에 짧은 알림을 보냅니다. 브라우저에 있는 sendBeacon 기능을 쓰는데, 이 기능은 화면 이동을 늦추지 않고 페이지가 닫혀도 보냅니다 (MDN, 확인 2026-10-12).

광고 차단 프로그램을 쓰는 사람의 클릭은 일부 빠질 수 있습니다 (얼마나 빠지는지는 확인 못 함, 시험 필요).

다른 선택: 링크를 우리 서버 주소로 바꿔, 우리 서버를 거쳐 전자도서관으로 보냄 → 빠지는 클릭이 없지만 넘어갈 때 한 번 더 왔다 갔다 하고, 링크에 마우스를 올리면 우리 주소가 보입니다.

4무엇을 남길까

사람을 알아볼 수 있는 값(회원 번호, IP, 브라우저 식별값)은 빼고, 무엇을 찾았고 어디를 눌렀는지만 남기는 것을 추천합니다.

4회원 번호·IP·브라우저 식별값 없이 남김 [안]

남기는 것예
시각2026-10-20 21:03
검색 조건제목 "채식주의자", 지역, 고른 도서관, 정렬
결과 수책 12권
누른 도서관과 누른 곳강남구 전자도서관, 결과 카드

왜 빼는지: 개인정보 보호법은 그것만으로 사람을 알 수 없어도 "다른 정보와 쉽게 합쳐 알 수 있으면" 개인정보로 봅니다(제2조). 사람을 알아볼 수 없는 정보에는 이 법을 적용하지 않습니다(제58조의2) (국가법령정보센터, 확인 2026-10-12). 세 값을 빼면 동의·처리방침 부담이 가장 작습니다.

검색어 자체에 이름이 들어갈 수는 있습니다(저자 칸에 자기 이름). 동의 창이 필요한지, 처리방침에 적는 것으로 충분한지는 법 조문만으로 정할 수 없어 확인 못 함입니다.

5얼마나 둘까

원본 기록은 1년 뒤에 지우는 것을 추천합니다.

5원본 기록은 1년 보관 [안]

이렇게 되면: 2026년 10월 기록은 2027년 10월에 지웁니다. 1년이면 계절·학기에 따른 변화를 한 바퀴 볼 수 있습니다. 회원 정보도 마지막 로그인 1년 뒤에 지우게 되어 있어 기준이 같아집니다.

법은 보관 기간이 지나면 바로 지우라고 하고(제21조), 처리방침에 보관 기간을 적게 합니다(제30조).
