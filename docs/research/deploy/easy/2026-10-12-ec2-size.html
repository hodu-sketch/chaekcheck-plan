가져오기를 따로 하면 EC2는 이렇게

이미 정한 모양(EC2 한 대에 nginx·서비스·조회 서버·DB, 2026-10-04)에, 사이클 11의 "가져오기는 내 PC, 운영은 파일만 받아 넣기"를 더해 크기를 잡았습니다. 운영 서버에는 가져오기용 힙 6GB도, 사본·국가서지 파일도 필요 없습니다. (2026-10-12)

추천: t4g.medium(2 vCPU, 메모리 4GiB) 한 대 + gp3 디스크 40GiB. 내 PC에서 가져온 파일을 올려 반영합니다.

반영 명령은 EC2에서 돌고, 하는 일은 파일 넣기 → 색인 → 바꿔 끼우기뿐입니다.

2메모리: 왜 4GiB인가

서비스와 DB가 쓰는 양을 더하면 2GiB 안팎이라 2GiB 서버는 여유가 없습니다. 4GiB면 남는 만큼을 DB 파일 캐시로 써서 검색이 빨라집니다.

숫자는 내 PC에서 잰 값입니다(사이클 08). 운영 서버에서 다시 잽니다(백로그 "배포 사이클: 메모리 값").

1EC2는 t4g.medium(2 vCPU, 4GiB) 한 대로 시작한다 [안]

t4g는 CPU를 평소 기준(vCPU당 20%)까지 쓰고, 그보다 많이 쓸 때는 모아 둔 크레딧을 씁니다. 반영할 때 색인을 1~2분 만드는 정도는 크레딧(최대 576)으로 충분하다고 봅니다. 기본 모드(Unlimited)에서는 하루 평균이 기준을 넘으면 넘은 만큼 요금이 더 붙습니다.

다른 선택: t4g.small(2GiB) — 메모리 여유 없음. t4g.large(8GiB) — 캐시가 넉넉하지만 더 비쌈. m7g.large(8GiB, 크레딧 없는 일반형) — CPU를 늘 많이 쓸 때.

근거: 사양 EC2 instance types (general purpose), 크레딧 burstable credits (확인 2026-10-12). 금액은 5번 카드.

추천: t4g.medium.

3디스크: 왜 40GiB인가

반영할 때는 옛 책 표와 새 책 표가 잠깐 함께 있어 DB가 두 배 가까이 됩니다. 덤프 파일과 OS·이미지 자리까지 더해 40GiB를 제안합니다.

2디스크는 gp3 40GiB로 시작한다 [안]

사이클 11에서 덤프 파일 크기와 반영 때 최대 크기를 재면 다시 맞춥니다. 늘리는 것은 서버를 멈추지 않고 할 수 있어서, 처음에 크게 잡을 필요는 없습니다.

다른 선택: 30GiB — 반영 때 빠듯할 수 있음. 60GiB 이상 — 여유는 크지만 당장 필요 없음.

근거: EBS gp3 "baseline IOPS performance of 3,000 IOPS", "125 MiB/s", Elastic Volumes로 멈추지 않고 바꿈 (확인 2026-10-12)

추천: 40GiB.

4확인하고 넘어갈 것

t4g는 ARM 칩(Graviton)이라, 지금 쓰는 Docker 이미지가 ARM에서 도는지 먼저 봐야 합니다. 안 되면 같은 크기의 Intel(t3.medium)로 갑니다.

3t4g(ARM)로 가되, 배포 전에 DB 이미지(PostgreSQL 18 + pg_bigm)와 서비스가 ARM에서 도는지 시험하고, 안 되면 t3.medium(Intel, 4GiB)으로 바꾼다 [안]

공식 postgres 이미지가 ARM을 지원하는지, pg_bigm을 ARM에서 빌드할 수 있는지는 확인하지 못했습니다. 배포 사이클에서 서버를 하나 띄워 빌드해 봅니다.

다른 선택: 처음부터 t3.medium(Intel). 이미지 걱정은 없지만 한 달 약 $7.6 더 듭니다(서울, 5번 카드).

조회 서버가 쓰는 메모리

재 본 값은 없습니다. 대신 코드와 문서에서 이렇게 알 수 있습니다.

  • 조회 서버(fetch-service)에는 힙 상한 설정이 없습니다(build.gradle, application.yml). 이러면 Java가 실메모리의 1/4을 힙 상한으로 잡아서, 4GiB 서버라면 1GiB까지 커질 수 있습니다.
  • dev가 적어 둔 최악의 경우: 동시 32건 × 응답 최대 4MB × 1.33(base64) ≈ 170MB(application.yml 주석).

제안: 조회 서버 힙 상한을 256MB로 정하고(최악 170MB + 여유), 배포 전에 재서 맞춥니다. 상한을 두지 않으면 서비스·DB와 메모리를 다툽니다.

근거: "Maximum heap size of 1/4 of physical memory" — Java 25 GC tuning, Ergonomics (확인 2026-10-12)

반영할 때 DB 메모리 (maintenance_work_mem)

  • maintenance_work_mem은 CREATE INDEX, VACUUM 등이 쓰는 메모리 상한이고 기본값은 64MB입니다. 반영 단계의 색인 만들기가 이 값을 씁니다.
  • 사이클 08 가져오기는 이 값을 세션에서 1GB, 병렬 작업자 4로 돌렸습니다(색인 1분 39초). 운영 DB 컨테이너 상한 1GB(권장)와 같은 크기라 운영에서 그대로 쓰면 안 됩니다. 또 dev 로컬 compose에는 컨테이너 메모리 상한이 실제로 걸려 있지 않아, 지금까지 측정은 상한 없이 한 것입니다.
  • 병렬 작업자 수는 메모리를 늘리지 않습니다. 문서에 따르면 병렬 유지보수 명령은 maintenance_work_mem을 명령 전체에 대한 한도로 씁니다. 대신 CPU·디스크를 더 씁니다.

제안: 운영 반영 명령은 maintenance_work_mem=256MB로 돌리고, 사이클 11 시험 때 운영 역할 DB(포트 5434) 컨테이너에 메모리 상한 1GB를 실제로 걸고 색인 시간을 잽니다. 값은 사이클 11 설계에서 정합니다.

근거: "maximum amount of memory to be used by maintenance operations, such as VACUUM, CREATE INDEX … defaults to 64 megabytes", "treat the resource limit maintenance_work_mem as a limit to be applied to the entire utility command" — PostgreSQL 18, Resource Consumption (확인 2026-10-12). 사이클 08 값은 dev plan-feedback.md 8단계.
