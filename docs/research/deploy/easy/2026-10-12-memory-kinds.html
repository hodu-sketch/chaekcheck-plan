1한눈에: 누가 얼마를 쓰나

Java 프로그램은 저마다 "힙" 상한 하나를 정합니다. PostgreSQL은 쓰임새마다 따로 정합니다. 둘 다 쓰고 남은 메모리는 운영체제(Linux)가 디스크 파일을 담아 두는 데 씁니다.

값은 사이클 08 확정(서비스 512MB, DB 설정)과 사이클 11·배포 제안(조회 서버 256MB, 반영 512MB, DB 컨테이너 1GB, 승인 2026-10-12)입니다. 힙 밖 메모리와 Linux 자체가 쓰는 양은 운영 서버에서 재 봐야 합니다.

3PostgreSQL의 메모리: 다 같이 쓰는 것과 연결마다 쓰는 것

PostgreSQL은 연결(서비스·반영 명령이 DB에 붙은 줄 하나) 하나마다 프로세스를 따로 띄웁니다. 모든 연결이 함께 쓰는 "공유 버퍼"가 하나 있고, 정렬·색인 만들기 같은 작업은 그 연결이 따로 메모리를 잡습니다.

표의 temp_file_limit·temp_tablespaces가 말하는 "임시 파일"

4번 카드의 ① 임시 파일입니다. 정렬·해시가 메모리(work_mem, 색인 만들기는 maintenance_work_mem)를 넘칠 때 PostgreSQL이 스스로 만들었다가 작업이 끝나면 지우는 파일입니다. 우리가 만드는 표(임시 표, catalog_next)와는 다릅니다.

  • temp_tablespaces = 어디에 쓰나. 비워 두면(기본) 그 DB의 기본 자리, 곧 데이터 폴더 안 base/pgsql_tmp/에 씁니다. 우리 DB는 데이터 폴더가 Docker 볼륨 db-data(/var/lib/postgresql) 안이라 결국 서버 디스크를 씁니다. 다른 디스크를 따로 붙여 이름(tablespace)을 주면 그쪽으로 보낼 수 있지만, 우리는 디스크 하나라 기본 그대로입니다.
  • temp_file_limit = 얼마까지 쓰나. 연결 하나(프로세스 하나)가 동시에 들고 있을 수 있는 임시 파일 크기의 상한입니다. 문서가 꼽는 대상은 정렬·해시 임시 파일과 보류 커서 저장 파일입니다. 넘으면 그 트랜잭션이 취소됩니다. 기본은 -1(상한 없음)이라, 큰 정렬 하나가 디스크를 다 채울 수도 있습니다.
  • 우리에게 닿는 곳: 운영 반영의 색인 만들기(256MB를 넘는 정렬이 임시 파일로 감)와 sql 방식 묶기(내 PC). 운영 디스크 40GiB 안에서 "평소 DB + 반영 때 두 벌 + 덤프 파일 + 이 임시 파일"이 다 들어가야 합니다. 그래서 이번 사이클에 temp_bytes로 임시 파일 양을 같이 잽니다. 운영에 temp_file_limit을 걸지(예: 디스크가 꽉 차기 전에 작업만 취소되게)는 그 측정을 보고 정하면 됩니다(지금은 기본).

근거(확인 2026-10-12): temp_file_limit "the maximum amount of disk space that a process can use for temporary files, such as sort and hash temporary files, or the storage file for a held cursor. A transaction attempting to exceed this limit will be canceled … -1 (the default) means no limit" — Resource Consumption; temp_tablespaces "Temporary files for purposes such as sorting large data sets are also created in these tablespaces … The default value is an empty string, which results in all temporary objects being created in the default tablespace of the current database" — Client Connection Defaults; 위치 "PGDATA/base/pgsql_tmp" — Database File Layout.

근거(확인 2026-10-12): Resource Consumption — work_mem "the total memory used could be many times the value of work_mem", autovacuum_work_mem "-1, indicating that the value of maintenance_work_mem should be used", temp_buffers "session-local buffers used only for access to temporary tables … default is eight megabytes", 병렬 유지보수 명령은 maintenance_work_mem을 "a limit to be applied to the entire utility command"로 씀; Query Planning — effective_cache_size "used only for estimation purposes"; Compose — mem_limit. 자동 청소 작업자 최대 3은 autovacuum_max_workers 기본값으로 알고 있으나 이번에 문서로 다시 확인하지 못했습니다.

근거(확인 2026-10-12): PostgreSQL 18 문서 Resource Consumption(shared_buffers "typically 128 megabytes", work_mem 4MB, hash_mem_multiplier 2.0, maintenance_work_mem 64MB, autovacuum_work_mem -1, temp_buffers 8MB, temp_file_limit -1), Query Planning(effective_cache_size 4GB), Autovacuum(autovacuum_max_workers 3), Connections(max_connections "typically 100"), Client(temp_tablespaces 빈 값); Java Ergonomics(1/4, 1/64), Other Considerations(Metaspace 상한 없음), JEP 192·JEP 519. shared_buffers를 바꾸려면 재시작이 필요하다는 것은 이번에 문서로 다시 확인하지 못했습니다(compose command로 주므로 컨테이너를 다시 띄울 때 적용).

4"임시"라는 말이 붙는 것 셋: 어디에 생기고 어떻게 움직이나

PostgreSQL에서 "임시"는 서로 다른 셋입니다. ① 정렬·해시가 메모리를 넘칠 때 쓰는 임시 파일, ② CREATE TEMPORARY TABLE로 만든 임시 표, ③ 우리 가져오기의 catalog_next(이건 이름만 준비용이고 PostgreSQL이 말하는 임시는 아님). ①·②는 연결이 끝나면 사라지고, 셋 다 DB 디스크(db-data 볼륨)를 씁니다.

① 임시 파일② 임시 표③ catalog_next

어디에DB 데이터 폴더 base/pgsql_tmp/, 이름 pgsql_tmp<프로세스번호>.<번호>그 DB 폴더 안, 이름 t<프로세스번호>_<번호>그 DB 폴더 안, 보통 표와 같음

① 임시 파일이 생기는 모습: 정렬이 4MB를 넘을 때

그래서 반영 때 색인 메모리를 1GB에서 256MB로 낮추면, 메모리는 아끼지만 정렬이 임시 파일로 더 많이 넘쳐 디스크를 더 쓰고 느려질 수 있습니다. 이번 사이클에서 temp_bytes와 디스크 최대, 색인 시간을 같이 재는 이유입니다(AC-14).

근거(확인 2026-10-12): 임시 파일 위치·이름 "created within PGDATA/base/pgsql_tmp", 임시 표 파일 이름 "tBBB_FFF" — Database File Layout; temp_tablespaces 기본 빈 값 = DB 기본 자리 — Client Connection Defaults; temp_file_limit "-1 (the default) means no limit", hash_mem_multiplier 기본 2.0, 정렬은 ORDER BY·DISTINCT·병합 조인, 해시는 해시 조인·해시 집계 — Resource Consumption; 죽은 뒤 정리 remove_temp_files_after_crash 기본 on — Developer Options; log_temp_files는 파일을 "when it is deleted" 기록 — Logging. dev compose의 DB 볼륨은 db-data:/var/lib/postgresql(dev compose.yaml 38행). 정렬을 조각으로 나눠 합치는 방식은 이해를 돕는 요약이며 문서 문장 그대로는 아닙니다.

5DB가 책 한 권을 읽을 때 메모리를 거치는 순서

PostgreSQL은 먼저 공유 버퍼를 보고, 없으면 Linux에 파일을 달라고 합니다. Linux는 파일 캐시에 있으면 바로 주고, 없을 때만 디스크를 읽습니다. 그래서 서버에 남는 메모리가 많을수록 디스크를 덜 읽습니다.

사이클 08에서 이 효과를 잰 예: 소장을 책 순서로 붙여 쓴 뒤, 책 3권의 소장을 읽는 데 1,169조각·78ms 걸리던 것이 77조각·1.4ms가 됐습니다(dev 측정). 읽을 조각 수가 줄면 ①·② 메모리에 담기기도 쉬워집니다.

6반영하는 동안만 늘어나는 것

반영 명령을 돌리는 몇 분 동안만 Java 반영 명령(힙 512MB)이 하나 더 뜨고, DB 안에서는 그 연결이 색인을 만들며 256MB를 씁니다. 끝나면 둘 다 돌려놓습니다.

가로 길이는 시간 비율이 아니라 순서만 나타냅니다. 실제 시간(파일 넣기, 색인)은 사이클 11 시험에서 운영 역할 DB(5434)에 컨테이너 상한 1GB를 걸고 잽니다.

질문 "maintenance_work_mem은 유동적으로 바꿀 수 있는 값이야?" (2026-10-12)

네, 실행할 때마다 바꿀 수 있습니다. 서버를 다시 켤 필요도, 코드를 고칠 필요도 없습니다. 다만 저절로 바뀌는 값은 아니고, 돌릴 때 사람이 정해 주는 값입니다.

어디서 바꾸나언제 적용누구에게
가져오기·반영 명령의 설정 chaekcheck.catalog.load.maintenance-work-mem (예: --chaekcheck.catalog.load.maintenance-work-mem=512MB)그 명령을 돌릴 때 바로그 명령의 DB 연결 하나만. 검색·자동 청소는 그대로
DB 서버 설정 파일(postgresql.conf) 또는 compose command설정을 다시 읽히면(재시작 없이) 이후 연결부터모든 연결, 자동 청소 포함

지금 dev 코드가 이미 그렇게 합니다: 가져오기 연결에서 SET maintenance_work_mem = …을 실행하고(JdbcCatalogLoad.java 110행), 사이클 08은 이 값을 1GB로 주고 돌렸습니다. 이번 반영 명령도 같은 설정 칸으로 256MB를 줍니다.

지킬 것: 이 값은 DB 컨테이너 상한(1GB)보다 넉넉히 작아야 합니다. 사이클 08에서 상한 512MB에 1GB를 주었다가 DB가 메모리 부족으로 죽었습니다. 256MB로 재 보고 색인이 너무 느리면 올리고, 그때 공유 버퍼·검색 연결 몫을 빼고 남는 만큼만 올립니다.

근거: PostgreSQL에서 이런 종류(context user) 설정은 "within a session via the SET command" 바꿀 수 있고 "Any user is allowed to change their session-local value" — pg_settings (확인 2026-10-12). maintenance_work_mem이 세션에서 바뀌는 것은 dev 코드와 사이클 08 실행으로 확인.
