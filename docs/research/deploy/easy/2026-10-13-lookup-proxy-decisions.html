대출 조회에 프록시 쓰기:
무엇을 쓰고, 어떻게 나눠 보낼지

사용자 말씀(2026-10-13): "조회하는데 프록시를 쓸까 하는데 쓰려면 어떻게 써야 하는지도 좀 알려줘.. 이거 원칙 바꾸는 거고 우리가 여러 사람의 조회를 대신 하는 만큼 프록시를 쓰는게 합당하다고 봐. 어짜피 우리가 안 했으면 다른 사람들도 다 각각요청보냈을건데 대신해주는거자나". 쓰는 방법을 먼저 설명하고, 정할 것을 네 가지로 나눴습니다.

1우리 구조에서 프록시가 들어가는 자리

이미 있는 조회 서버(fetch-service)가 바로 그 자리입니다. 조회 서버는 본 서비스 대신 도서관 사이트에 요청을 보내고 응답을 돌려주는, 우리가 운영하는 프록시입니다. 조회 서버를 여러 대 두거나, 조회 서버가 업체 프록시를 거쳐 나가게 하면 됩니다.

실선은 우리 서버의 고정 IP로 바로 나가는 길, 점선은 업체 프록시를 한 번 더 거치는 길입니다.

실제로 쓰는 방법

  • 우리 조회 서버를 늘림: Lightsail $5 묶음(고정 IP 무료)이나 iwinv 1GB(월 5,600원)에 조회 서버를 하나 더 띄웁니다. 본 서비스 설정의 조회 서버 목록(fetch-1, fetch-2 …)에 주소를 더합니다. 조회 서버와 본 서비스 사이에는 지금처럼 비밀 값으로 인증합니다.
  • 업체 프록시를 거침: 업체에서 프록시 주소와 아이디·비밀번호를 받습니다. 조회 서버가 도서관에 보내는 요청에 그 프록시를 지정합니다(Java HTTP 클라이언트의 프록시 설정). 비밀번호는 코드가 아니라 서버의 비밀 값으로 둡니다.
  • 공통: 어떤 IP로 나갔는지를 조회 기록에 남겨야, 어느 IP가 막혔는지 알 수 있습니다. 지금 코드에는 프록시 설정이 없으므로 dev가 만들어야 합니다.

질문: 프록시는 실제로 어떻게 쓰나요? 프록시 쪽에도 서버를 구성해야 하나요?

어떤 프록시냐에 따라 다릅니다. 우리 조회 서버를 늘리는 방식이면 작은 서버를 하나 더 만들어 조회 서버 프로그램을 띄워야 합니다. 업체 프록시를 쓰면 서버는 필요 없고, 받은 주소와 비밀번호를 설정에 넣기만 합니다.

가. 우리 조회 서버를 하나 더 둘 때 (서버 구성 필요)

  • ③에서 넣는 값: 본 서비스와 같은 비밀 토큰(FETCH_SERVICE_TOKEN)과 우리 User-Agent. 조회 서버는 이 토큰이 붙은 요청만 받습니다(dev 설정 X-Fetch-Token).
  • ④가 필요한 이유: 바깥에 열린 조회 서버는 남이 우리 IP로 도서관을 부르는 데 쓸 수 있습니다. 토큰에 더해 본 서비스 서버의 IP에서만 들어오게 방화벽을 좁힙니다. 둘 사이를 암호화할지(HTTPS나 같은 사설망)는 아직 정하지 않았습니다 [확인 필요: dev 설정의 TODO].
  • ⑤: 본 서비스 설정의 조회 서버 목록(fetch-1, fetch-2)에 새 서버 주소를 넣고, 조회 방식을 조회 서버 사용(FETCH_MODE=fetch-service)으로 바꿉니다.
  • 노트북으로 옮긴 뒤에도 이 작은 서버들은 그대로 둘 수 있습니다. 그러면 노트북 집 IP와 조회 서버 IP가 따로 됩니다.

나. 업체 프록시를 쓸 때 (서버 구성 없음)

  • 업체 가입 → 한국 IP 상품을 고르고 결제 → 업체가 프록시 주소(예: 호스트:포트)와 아이디·비밀번호를 줍니다.
  • 우리 조회 서버(또는 본 서비스)가 도서관에 요청을 보낼 때 "이 프록시를 거쳐라"고 설정합니다. 지금 코드에는 이 설정이 없어서 dev가 더해야 합니다(Java HTTP 클라이언트의 프록시 지정).
  • 아이디·비밀번호는 서버의 비밀 값으로 둡니다.
  • 업체 약관(크롤링·자동 요청 허용 여부)은 따로 확인해야 합니다 [확인 필요].

다. 수집용으로 조사했던 Squid·tinyproxy와의 차이

Squid·tinyproxy는 아무 요청이나 전달하는 일반 프록시입니다. 수집기(파이썬)가 클라우드에서 돌 때 나가는 IP만 바꾸려고 조사했습니다. 서비스의 대출 조회는 이미 우리 조회 서버라는 전용 프로그램이 있으므로, 서비스 쪽에는 가(조회 서버)를 쓰는 것이 자연스럽습니다.

근거: dev fetch-service/src/main/resources/application.yml(토큰 헤더, 동시 32건, UA), 본 서비스 application.yml availability.fetch(조회 서버 목록, FETCH_MODE), ADR-0011, ADR-0015. 2026-10-13 읽음.

2무엇을 프록시로 쓸지

세 종류가 있습니다. 어느 쪽이든 수집 쪽 원칙(우리 고정 IP만)과 서비스 조회 쪽 원칙이 달라지는지도 함께 정해집니다.

사용자 말씀(2026-10-13): "아니 다 가능하도록 개발했으면 해 조회 서버를 두는 것도 방법이고 각각의 조회 서버 내에서 업체 프록시 여러개 쓸 수 있고 우리 본 서버에서 조회기능도 있되 업체 프록시 여러개 쓸 수 있는 걸로다가". 바로 앞의 "서버 하나 + 업체 프록시"안을 이 말씀대로 넓혔습니다. 칩을 승인하시면 이 내용으로 적습니다.

길 1은 지금 있는 것, 길 3의 조회 서버도 지금 있는 것입니다. 새로 만드는 것은 "업체 프록시를 거쳐 보내기"를 본 서비스와 조회 서버 양쪽에 넣는 일입니다.

설정으로 고르는 것예
본 서비스가 직접 부를지, 조회 서버를 거칠지지금 있는 FETCH_MODE(direct / fetch-service)
직접 부를 때 업체 프록시 목록없음(자기 IP로) 또는 업체 A·B의 주소·아이디·비밀번호
조회 서버마다 업체 프록시 목록조회 서버 1은 없음, 조회 서버 2는 업체 A·C
프록시를 고르는 방식돌아가며, 멈춘 업체는 잠시 빼기 [안: dev가 정함]
어떤 IP로 나갔는지 기록조회 기록에 길과 업체 이름을 남김
  • 몇 건 보낼지는 언제나 본 서비스에서 셈: 어느 길로 나가든 도서관 한 곳이 받는 양은 본 서비스가 정합니다. 그래서 길을 늘려도 도서관 쪽 양이 저절로 늘지 않습니다(2번 제안). 교보 서버는 ADR-0094대로 조회 서버를 쓸 때 조회 서버마다 3건, 평소 한 대만입니다.
  • 바뀌는 이전 결정: 나가는 IP 원칙의 "우리 국내 서버 고정 IP만"이 서비스 대출 조회에 한해 "우리가 빌린 업체 고정 IP까지"로 넓어집니다. ADR-0011(조회 서버 분리)은 그대로 살아 있고, 고를 수 있는 길 하나가 됩니다.
  • 상품: 업체 프록시는 IP가 바뀌지 않는 고정 IP 상품으로 합니다. 예: Oxylabs 한국 전용 데이터센터 월 $8.25부터, ISP 고정 IP당 $1.10~1.50 (업체 표기, 2026-10-12). 최소 구매 수량과 자동 요청 허용 약관은 확인 못 함.
  • 개발 범위: 업체 프록시를 거쳐 보내기(Java HTTP 클라이언트 프록시 설정과 인증)를 본 서비스와 조회 서버에 각각 넣고, 설정 목록과 나간 길 기록을 더합니다. 배포 사이클에서 dev에 넘깁니다.

한 가지 길만 만듦(서버 하나 + 업체 프록시): 만들 것이 적습니다. 대신 나중에 조회 서버를 쓰고 싶어지면 그때 다시 만들어야 합니다.
업체 주거용·IP 바꿔 가는 프록시도 길로 넣음: 설정에 넣을 수는 있게 됩니다. 2026-10-12의 금지와 정반대이고 법 관련 배경 자료(카드 4)의 위험이 가장 크므로, 이 안에서는 고정 IP 상품만 넣습니다.

추천: 말씀대로 세 길 모두 + 설정으로 고름, 업체 프록시는 고정 IP 상품만.

3여러 IP로 나눠 보낼 때 도서관 한 곳이 받는 양

IP를 나눌 때 "도서관 한 곳이 받는 양을 그대로 두고 IP만 나눌지", "IP마다 따로 세어 더 많이 보낼지"를 정해야 합니다. 앞의 것은 막힐 위험을 나누고, 뒤의 것은 빨라지지만 도서관 부담이 늘어납니다.

IP 두 개로 그린 예입니다. 사용자 말씀대로 사람들이 각자 요청했다면 도서관은 그만큼을 받았을 것입니다. 다만 우리가 모아서 보내면 같은 몫이 짧은 시간에 몰려 갈 수 있습니다.

2도서관 한 곳이 받는 양은 지금 규칙(합계 1초 1건, 교보 서버는 3건)대로 두고, IP만 나눠 보냄 [안]

서비스 서버가 도서관마다 몇 건을 보낼지 지금처럼 한 곳에서 세고, 보낼 때 프록시를 돌아가며 고릅니다. 도서관이 받는 양은 그대로라 빨라지지는 않습니다. 대신 IP 하나가 막혀도 나머지로 계속 조회합니다(막힌 IP를 어떻게 다룰지는 3번).

IP마다 따로 셈: 프록시마다 각자 1초 1건씩 보내므로, IP 수만큼 빨라지고 몰릴 때 덜 기다립니다. 대신 도서관은 IP 수만큼 더 받습니다. 2026-09-28에 "조회 서버마다 따로 제어하면 도서관 한 곳에 서버 수만큼 동시에 요청이 간다"고 해서 고르지 않았던 방식(ADR-0011 B안)입니다. 교보 서버는 어제 "조회 서버마다 3건, 평소 한 대만"으로 정했는데, 이 방식이면 "평소 한 대만"이 풀려 교보 서버도 IP 수 × 3건을 받게 됩니다.

추천: 합계는 그대로, IP만 나눔.

4한 IP가 막혔을 때와 우리 이름

IP가 여러 개가 되면, 하나가 막혔을 때 나머지로 그 사이트에 계속 보낼지를 정해야 합니다. 어제 저장한 ADR-0094는 "그 IP도 막히면 멈추고 묻는다, 세 번째 IP를 찾지 않는다"입니다(아직 제안됨 상태라 고칠 수 있습니다).

3한 IP가 어느 사이트에서 막히면, 그 사이트로 가는 조회를 모든 IP에서 멈추고 사용자에게 물음 [안]

예: IP A가 교보 서버에서 막히면 IP B로 옮겨 계속 보내지 않습니다. 교보 서버 도서관은 화면에 "확인 불가"로 나오고, 기록과 알림이 남습니다. 다른 사이트는 두 IP 모두 계속 씁니다.

막힌 IP만 빼고 나머지 IP로 계속: 대출 현황이 끊기지 않습니다. 대신 사이트가 우리를 막은 뜻을 다른 IP로 피해 가는 모양이 됩니다. ADR-0094의 "세 번째 IP를 찾지 않는다"와 ADR-0011의 "도서관이 거부할 때는 다른 조회 서버로 넘기지 않는다"를 바꿔야 합니다.

추천: 모든 IP에서 멈추고 물음.

4어느 IP로 나가든 User-Agent에 우리 서비스 이름을 그대로 둠 [안]

지금처럼 chaekcheck/…로 우리를 밝힙니다(2026-09-28 결정, 서비스 주소가 생기면 함께 적음). 도서관은 IP가 달라도 우리라는 것을 알 수 있고, 원하면 이름으로 우리를 막을 수 있습니다.

IP마다 다른 이름이나 일반 브라우저 이름: 막히기 어려워집니다. 대신 우리를 숨기는 것이 되어, 사이클 01부터 지킨 "우리를 밝힌다"는 원칙을 버리게 됩니다.

추천: 우리 이름 그대로.

알고 정하실 것 (법적 판단이 아닌 배경 자료)

  • 2022년 대법원 판결(2021도1533, 숙박 앱 크롤링, 무죄)은 접근이 막혔는지를 "보호조치나 이용약관 등 객관적으로 드러난 여러 사정"으로 판단했습니다. 별도 보호조치가 없었다는 점이 무죄 이유 중 하나였습니다.
  • IP 차단은 그 보호조치로 읽힐 수 있습니다. 막힌 뒤 다른 IP로 다시 들어간 경우를 직접 다룬 한국 판례는 찾지 못했습니다.
  • "여러 사람의 조회를 대신 한다"는 말씀은 서비스의 목적으로 이해합니다. 다만 법원이 이 사정을 어떻게 보는지는 확인하지 못했습니다. 전문가 확인 항목(backlog)에 함께 넣어 두는 것을 제안합니다.
