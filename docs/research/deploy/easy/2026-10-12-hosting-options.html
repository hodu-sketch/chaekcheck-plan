업체·화면 호스팅·수집 프록시 비교

국내외 업체 요금과 무료 혜택, GitHub로 화면을 무료로 올리는 서비스, 수집 프록시, 과한 요청 막기와 모니터링, 대출 현황 조회의 1초 간격을 공식 문서와 dev 코드로 확인했습니다. 사이클이 아니라 조사이며, 아래 7가지에 방향을 골라 주시면 문서에 적어 둡니다. (확인일 2026-10-12)

1한 장으로 보면

2주는 AWS 서울 EC2(약 $17), 무료로 하려면 KT Cloud 신규 쿠폰. 화면은 지금처럼 서버의 nginx가 내려 주고, 프록시는 속도용으로는 쓰지 않습니다.

질문: 사용량이 적으면 EC2가 이득일까요?

사용자가 적어도 서버를 계속 켜 두면 EC2가 더 싸지지는 않습니다. 두 업체 모두 서버가 켜져 있는 시간으로 요금을 받고, 방문자 수로 받지 않습니다. EC2가 이득이 되는 것은 서버를 하루에 반 넘게 꺼 둘 때입니다.

2주(336시간) 기준 계산값입니다. EC2 = 서버 시간당 $0.0416 × 켜 둔 시간 + 디스크 약 $1.7 + 고정 IP $1.7. Lightsail = 월 $24의 336시간 몫 약 $11.

  • EC2가 싸지는 지점: 2주 중 약 185시간, 하루 평균 13시간쯤 넘게 꺼 둘 때입니다. EC2는 꺼 두면 서버 요금이 안 나가고, 디스크와 고정 IP 요금만 나갑니다.
  • Lightsail은 꺼 둬도 같은 값입니다. 공식 FAQ에 "켜져 있거나 멈춰 있는 동안" 요금을 받는다고 적혀 있습니다.
  • 사용량이 영향을 주는 곳은 두 군데뿐입니다. 나가는 데이터와 CPU 사용입니다.
    • 나가는 데이터: EC2는 계정 전체 월 100GB까지 무료입니다. Lightsail은 4TB가 묶음에 들어 있습니다. 사용자가 적으면 둘 다 추가 요금이 없을 것으로 봅니다.
    • CPU: 평소 몫(vCPU당 20%)을 넘겨 오래 쓰면 EC2는 추가 요금이 나갑니다. 사용자가 적으면 넘지 않을 것으로 봅니다.
  • 사용자가 적다고 더 작은 서버로 줄이기는 어렵습니다. 4GiB가 필요한 이유는 사용자 수가 아니라 책 데이터 크기(DB 약 8.5GiB)이기 때문입니다(2026-10-12 크기 검토).

그래서 2주 동안 서비스를 계속 켜 두고 시험할 계획이면 Lightsail이 쌉니다.

근거: EC2 서울 요금(AWS 공식 가격 데이터, 2026-10-12 확인), Lightsail FAQ https://aws.amazon.com/lightsail/faq/ (2026-10-13 확인). 185시간은 위 값으로 계산한 것입니다.

질문: Lightsail 4GB의 CPU는 어떤가요?

질문: EC2는 IP를 그때그때 바꿀 수 있지 않나요?

네, 바꿀 수 있습니다. 하지만 우리 원칙으로는 IP를 바꿔 가며 쓰지 않습니다. 그래서 EC2에는 바뀌지 않는 고정 IP(Elastic IP)를 붙이는 것을 추천합니다. 요금은 어느 쪽이든 같습니다.

기본 공인 IPElastic IP (고정 IP)
언제 바뀌나서버를 멈췄다 켜면 새 IP가 붙음. 한 번 놓은 IP는 다시 못 씀내 계정에 묶여 있어 멈췄다 켜도 그대로. 다른 서버로 옮겨 붙일 수도 있음
요금시간당 $0.005시간당 $0.005
  • 도서관 사이트 쪽에서 보는 IP: 우리 서버가 도서관에 묻는 요청은 이 공인 IP로 나갑니다. 기본 공인 IP를 쓰면, 2주 동안 서버를 멈췄다 켤 때마다 도서관이 보는 IP가 달라집니다.
  • 원칙과의 관계: 나가는 IP는 "우리 국내 서버의 고정 IP"로만 정했습니다(2026-10-12). 어제 정한 ADR-0094도 "그 IP도 막히면 멈추고 묻는다, 세 번째 IP를 찾지 않는다"입니다. IP를 바꿀 수 있다는 것을 막힘을 피하는 데 쓰면 이 두 결정과 부딪힙니다.
  • 사용자가 들어오는 길에는 영향 없음: Cloudflare Tunnel로 연결하면 사용자는 도메인으로 들어오므로, 서버 IP가 바뀌어도 접속에는 문제가 없습니다.
  • Lightsail도 고정 IP를 붙일 수 있고, 서버에 붙어 있는 동안은 무료입니다.

3노트북으로 옮길 때

클라우드 서버도 Cloudflare Tunnel로 연결해 두면, 노트북으로 옮길 때 도메인과 카카오 설정을 바꾸지 않아도 됩니다.

2클라우드 서버도 Cloudflare Tunnel로 연결 [안]

클라우드 서버에서 cloudflared를 켜 둡니다. 2주 뒤에는 노트북에서 같은 터널을 켜고 클라우드 서버의 터널을 끕니다. 데이터베이스는 덤프 파일로 노트북에 옮깁니다.

다른 선택, 도메인을 서버 IP에 바로 연결: 서버에서 80·443 포트를 열고 인증서를 따로 설정해야 합니다. 옮길 때 DNS도 다시 바꿔야 합니다.

추천: 터널. 집 PC에서 이미 써 본 방식입니다.

질문: Cloudflare Tunnel은 정확히 무슨 일을 하나요?

바깥 사람이 내 도메인으로 들어오면, Cloudflare가 그 요청을 받아 우리 서버로 넘겨 줍니다. 이때 우리 서버는 바깥에 문을 열지 않습니다. 서버 쪽 프로그램 cloudflared가 먼저 Cloudflare로 연결을 걸어 두고, 요청은 그 연결을 타고 들어옵니다.

서버에서 밖으로 나가는 연결 하나만 있으면 됩니다. 집처럼 공유기 뒤에 있는 기계도 같은 방식으로 연결됩니다.

누가하는 일
우리 서버의 cloudflared켜질 때 Cloudflare로 연결을 걸어 둡니다. 들어온 요청을 서버 안의 nginx(localhost:8088)에 넘기고, 응답을 다시 돌려보냅니다.
Cloudflare내 도메인의 HTTPS 인증서를 붙여 사용자와 암호화 연결을 맺습니다. 화면 파일을 캐시하고, 알려진 공격을 걸러 냅니다. 사용자의 진짜 IP를 헤더에 적어 넘깁니다.
nginx와 우리 서비스지금과 같습니다. Cloudflare가 넘긴 요청을 받아 화면과 API를 돌려줍니다.
  • 좋아지는 것: 서버에 포트를 열지 않아도 됩니다. 인증서를 서버에서 관리하지 않아도 됩니다. 서버를 Lightsail에서 노트북으로 바꿔도 도메인과 카카오 설정은 그대로입니다.
  • 대신 생기는 것: 모든 요청이 Cloudflare를 거칩니다. 그래서 Cloudflare 제한을 받습니다. 예를 들어 서버 응답을 125초까지만 기다립니다. 또 nginx가 진짜 사용자 IP를 보게 하는 설정이 필요합니다(아래 5번 제안).
  • 나가는 요청은 상관없습니다: 우리 서버가 도서관 사이트에 묻는 요청은 터널을 거치지 않고, 서버의 고정 IP로 바로 나갑니다.

출처: Cloudflare Tunnel 설명 https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/ (cloudflared가 밖으로 연결을 맺고 들어오는 포트가 필요 없음, 2026-10-05 확인), 연결 제한 https://developers.cloudflare.com/fundamentals/reference/connection-limits/

질문: Cloudflare는 어떻게 이걸 무료로 해 주나요?

Cloudflare가 직접 밝힌 이유는 넷입니다. 무료 사이트가 많을수록 Cloudflare의 비용이 줄고, 공격을 더 많이 보고, 새 기능을 먼저 시험받을 수 있다는 것입니다. 돈은 유료 요금제와 유료 추가 기능에서 법니다. 아래는 Cloudflare 공식 블로그의 설명이고, 우리가 확인한 사실이 아니라 Cloudflare의 주장입니다.

Cloudflare가 밝힌 이유내용
비용이 줄어듦무료 사이트까지 Cloudflare를 거치니, 많은 통신사가 Cloudflare와 무료로 직접 연결하고 서버를 자기 쪽에 둡니다. 그래서 Cloudflare가 내는 전송 비용이 줄어든다고 합니다
공격을 더 많이 봄무료 사용자가 많으면 다양한 요청과 공격이 들어와, 보안·안정성 문제를 일찍 찾는다고 합니다
새 기능 시험무료 사용자가 새 기능을 먼저 써 보고 빠르게 의견을 준다고 합니다
회사 목표웹 대부분을 더 빠르고 안전하게 만든다는 목표에 무료 요금제가 맞는다고 합니다
  • Tunnel이 무료가 된 때: 2021-04-15 Cloudflare 발표입니다. 그전에는 전송량에 따라 돈을 받았습니다. 지금은 "서버에서 밖으로만 연결하는 기능"은 누구나 무료이고, 트래픽을 더 빠른 경로로 보내는 Argo Smart Routing만 유료입니다.
  • 무료 요금제의 제한 하나: 동영상이나 큰 파일을 많이 내보내는 용도는 유료 서비스를 쓰라고 약관에 적혀 있습니다. 우리 서비스는 화면 파일과 검색 결과라 해당하지 않을 것으로 봅니다(추정).
  • 계정 없이 쓰는 빠른 터널(trycloudflare)은 시험용입니다. 주소가 매번 바뀌고, 가동을 보장하지 않습니다. 이번 2주와 노트북에서는 계정과 도메인으로 만드는 정식 터널을 씁니다.

질문: Cloudflare 대신 쓸 수 있는 서비스는 없나요?

있습니다. 다만 무료로 "내 도메인"을 붙여 계속 서비스할 수 있는 곳은 Cloudflare Tunnel뿐이었습니다. 나머지는 무료 한도가 작거나, 그 업체가 정해 준 주소만 씁니다. 터널 없이 서버 문을 직접 여는 방법도 있습니다.

질문: Cloudflare Tunnel 같은 서비스를 뭐라고 부르나요?

정해진 공식 이름은 없습니다. 흔히 "터널링 서비스", "리버스 터널(reverse tunnel)"이라고 부릅니다. 검색할 때는 reverse tunnel, localhost tunneling, ingress tunnel을 쓰면 비슷한 서비스가 나옵니다.

  • "리버스"인 이유: 보통은 바깥에서 서버로 연결을 엽니다. 이 서비스들은 반대로 서버 쪽 프로그램이 먼저 바깥(업체)으로 연결을 열고, 요청이 그 연결을 거꾸로 타고 들어옵니다.
  • 업체마다 부르는 이름이 다릅니다.
    • Cloudflare: Tunnel. 서버에서 도는 프로그램 이름이 cloudflared입니다.
    • ngrok: 스스로를 리버스 프록시, 로드 밸런서, API 게이트웨이 같은 역할을 하나로 합친 플랫폼이라고 설명합니다. 서버에서 도는 프로그램을 "agent"라고 부릅니다.
    • Tailscale: Funnel
  • 비슷한 일을 하는 공개 소스 프로그램도 있습니다. 이 경우 바깥에 둘 서버를 직접 준비해야 합니다. 이번에는 조사하지 않았습니다.

질문: 내 IP가 바뀌어도 Cloudflare는 어떻게 그대로 찾아오나요? 직접 연결이면 DNS를 바꿔야 하잖아요

터널을 쓰면 도메인이 우리 IP가 아니라 "터널 번호"를 가리키기 때문입니다. 우리 서버가 어디에 있든 cloudflared가 그 터널 번호로 Cloudflare에 연결을 걸면, Cloudflare는 그 연결로 요청을 보냅니다. IP는 연결을 거는 쪽에서 쓰일 뿐, DNS에는 적히지 않습니다.

DNS가 가리키는 대상이 IP가 아니라 터널이라서, 기계나 IP가 바뀌어도 DNS를 고칠 일이 없습니다.

  • 터널을 만들면 Cloudflare가 터널마다 고유 번호(UUID)를 붙입니다. 내 도메인의 DNS 기록은 (그 번호).cfargotunnel.com을 가리키는 CNAME 하나입니다.
  • cloudflared는 그 터널의 인증 정보(설치할 때 넣은 토큰)로 Cloudflare에 연결합니다. Cloudflare는 IP가 아니라 이 인증 정보로 어느 터널의 연결인지 압니다.
  • 그래서 집 IP가 바뀌거나 기계를 바꿔도, cloudflared가 다시 연결을 걸기만 하면 됩니다. 반대로 이 토큰이 새면 다른 기계가 우리 터널을 받을 수 있으니 비밀번호처럼 다뤄야 합니다.

출처: Cloudflare Tunnel DNS 기록 https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/routing-to-tunnel/dns/ (확인 2026-10-13), 원격 관리 터널 만들기(토큰 설치) https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/ (확인 2026-10-05)

노트북의 CPU 종류(Intel·AMD인지 Arm인지), 메모리, 디스크 크기를 알려 주시면 그에 맞춰 적겠습니다.

5수집 프록시: 속도는 빨라지지 않습니다

수집 속도는 "서버마다 동시에 1건, 앞 응답이 끝난 뒤 1초"라는 규칙에서 정해집니다. 프록시는 요청이 나가는 IP만 바꾸고, 중간에 한 번 더 거치므로 오히려 조금 느려집니다.

이 규칙은 서버마다 따로 셉니다. 서로 다른 서버끼리는 동시에 받습니다. 지금 수집기는 40곳을 동시에 받습니다.

업체에서 빌리는 데이터센터 IP업체 IP로 내보냅니다. 예: Oxylabs 한국 월 $8.25부터원칙 밖
주거용, IP를 바꿔 가는 프록시요청마다 남의 가정용 IP로 바꿉니다. 예: GB당 $2~8쓰지 않기로 정함 (2026-10-12)

원칙의 배경 자료로, 2022년 대법원 판결(2021도1533, 숙박 앱 크롤링)이 있습니다. 이 판결은 접근이 막혔는지를 "보호조치나 이용약관 등"으로 판단했습니다. 별도의 보호조치가 없었다는 점이 무죄 이유 중 하나였습니다. 막힌 뒤 IP를 바꿔 다시 들어간 경우를 직접 다룬 한국 판례는 찾지 못했습니다. 법적 판단이 아니라 배경 자료입니다.

4속도 때문에 프록시를 쓰지 않음. 빠르게 하는 방법은 수집 개선 후보로 적어 둠 [안]

후보는 셋입니다.

  • 바뀐 것만 다시 받기: 갱신 기능과 같은 주제입니다.
  • 연결을 재사용하기: 요청마다 연결을 새로 맺는 시간을 없앱니다. 지금 수집기는 요청마다 새로 연결하는 것으로 보이는데, 확인이 필요합니다.
  • 압축해서 받기: 사이트가 압축을 지원하는지 확인이 필요합니다.

프록시는 지금 정해 둔 대로, 수집기를 해외(Claude 클라우드)에서 돌릴 때 나가는 IP를 국내로 맞추는 데만 씁니다.

다른 선택, 업체 데이터센터 IP 빌리기: "우리 서버 IP만"이라는 원칙을 바꾸는 것이라 따로 결정해야 합니다. 속도는 마찬가지로 빨라지지 않습니다.

추천: 프록시는 쓰지 않고, 후보 셋을 backlog에 적습니다.

질문: 조회에 프록시를 쓰고 싶습니다. 어떻게 써야 하나요?

여러 사람의 조회를 대신 하니 프록시가 합당하다는 말씀은 원칙을 바꾸는 일이라, 방법과 고를 것을 새 페이지 "대출 조회에 프록시 쓰기"에 따로 정리했습니다. 이 4번 칩은 수집 속도에 관한 것이라 그대로 두었습니다.

6과한 요청 막기와 모니터링

IP별 요청 한도는 이미 있습니다. 하지만 Cloudflare Tunnel 뒤에서는 모든 사용자가 한 주소로 보여서, 한도를 다 같이 나눠 쓰게 됩니다.

  • 있는 것: 도서관을 부르는 API에 IP별로 평균 2초에 1번, 한 번에 몰아서 20번, 동시 6개 한도가 있습니다. 넘으면 "잠시 뒤 다시"(429) 응답을 보냅니다. 서버 전체로는 동시 검색이 20개까지입니다.
  • 빈 곳: 책 검색 목록, 도서관 목록, 로그인에는 IP별 한도가 없습니다.
  • Cloudflare 무료 요금제로 한도 규칙 1개를 더 둘 수 있습니다. IP 기준이고 10초 단위로 셉니다.
  • 지금 dev에는 서버 상태를 숫자로 내보내는 기능이 없습니다. Spring에 의존성 하나와 설정을 더하면 Prometheus가 읽을 수 있습니다.

5배포 때 nginx가 Cloudflare가 알려 주는 진짜 사용자 IP를 읽게 설정 [안]

Cloudflare가 붙여 주는 CF-Connecting-IP 헤더를 nginx가 사용자 주소로 씁니다. 그러면 IP별 한도가 사람마다 따로 걸립니다. 터널을 거칠 때도 이 헤더가 붙는지는 공식 문서에서 확인하지 못해서, 배포할 때 시험합니다.

다른 선택, 한도를 Cloudflare 규칙 하나에만 맡기기: 설정은 쉽습니다. 대신 10초 단위 규칙 하나뿐이라, 지금처럼 동시 연결 수까지 막을 수는 없습니다.

추천: nginx 설정. 여기에 Cloudflare 규칙 하나를 더할지는 운영해 보고 정합니다.

6모니터링: 2주는 Grafana Cloud 무료, 노트북에서는 Prometheus·Grafana를 직접 [안]

Grafana Cloud 무료는 숫자 종류 1만 개, 14일 보관, 사용자 3명까지입니다. 2주 체험에는 충분합니다. 서버에는 숫자를 보내는 프로그램만 올라가서 4GiB 서버의 메모리를 덜 씁니다. 노트북에서는 원하신 대로 Prometheus, Grafana, node_exporter를 직접 띄웁니다.

다른 선택, 처음부터 클라우드 서버에 직접 띄우기: 노트북과 같은 구성을 미리 써 볼 수 있습니다. 대신 4GiB 서버에서 메모리를 나눠 써야 하는데, 얼마나 쓰는지는 재 보지 않았습니다.

추천: 2주는 Grafana Cloud.

질문: Prometheus·Grafana를 직접 띄우는 것과 Grafana Cloud는 뭐가 다른가요? (2주 동안 Lightsail)

숫자를 모으는 방식은 같고, "모은 숫자를 어디에 쌓고 그래프를 어디서 보느냐"가 다릅니다. 직접 띄우면 Lightsail 서버 안에 쌓이고, Grafana Cloud면 Grafana 회사 서버에 쌓입니다.

7대출 현황 조회의 1초 간격

혼자 쓸 때는 거의 영향이 없습니다. 몇 초 안에 여러 사람이 같은 도서관을 찾으면 줄을 서서 늦어질 수 있습니다.

  • 도서관 사이트 주소마다 동시에 1건만 보내고, 앞 요청이 끝난 뒤 1초를 쉽니다. 이 간격은 모든 사용자를 합쳐서 셉니다.
  • 검색 페이지는 8초, 상세 페이지는 30초 안에 차례가 오지 않으면 그 도서관은 화면에 "확인 못 함"으로 나옵니다.
  • 예: 응답이 1초 걸리는 도서관을 몇 초 사이에 5명이 서로 다른 검색어로 찾으면, 8초 안에 3~4명까지만 결과를 받습니다. 계산값이며 재 보지는 않았습니다.
  • 같은 검색은 3분 동안 캐시에서 바로 답합니다.
  • 교보 구독형 사이트는 한 서버에 하위 주소가 수백 개입니다. 서비스는 주소별로 세기 때문에, 이 서버에 동시에 최대 5건이 갈 수 있습니다. 이 서버는 예전에 우리 IP를 막은 적이 있습니다.

7처음에는 그대로 두고, "차례를 못 받아 포기한 횟수"를 모니터링에 넣어 봄 [안]

이 횟수는 지금도 로그에 남습니다. 숫자가 늘면 그때 검토합니다.

  • 캐시 시간 늘리기 (지금 3분)
  • 도서관별로 간격 다르게 두기
  • 교보 구독형을 IP 기준으로 묶기

다른 선택, 배포 전에 교보 구독형을 IP 기준으로 묶기: 교보 서버가 우리를 다시 막을 위험이 줄어듭니다. 대신 교보 구독형 도서관이 여러 곳 든 검색은 더 느려집니다.

추천: 처음에는 그대로 두고 숫자를 봅니다.

질문: 교보 구독형은 지금 막혀 있는 것 아닌가요?

네. 교보 구독형 서버는 2026-10-07부터 집 IP를 막고 있습니다. 마지막으로 확인한 것은 10-07이고, 지금도 막혀 있는지는 그 뒤로 확인하지 않았습니다. 위 7번 설명의 "예전에 막은 적이 있다"는 "지금도 막혀 있다"로 읽어 주세요.

  • 그래서 2주 체험이나 노트북 서버를 시작하기 전에 정해야 할 것이 하나 생겼습니다. 서비스가 새 IP로 이 교보 서버에 조회를 보낼지, 아니면 이 1,203곳의 대출 현황은 "확인 못 함"으로 둘지입니다. 이 페이지가 끝난 뒤 따로 여쭙겠습니다.
