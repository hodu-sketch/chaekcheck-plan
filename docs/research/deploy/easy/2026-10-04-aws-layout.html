AWS에 올릴 때 S3 등으로 나눌지에 대해:
지금은 나누지 않고 서버 한 대로 올리는 것을 권합니다.

나누는 것 자체는 좋은 방향이고 나중에 앱 코드를 바꾸지 않고 옮길 수 있습니다. 다만 10월 6일 새벽이 목표라면, dev가 이미 시험해 둔 구성(nginx 한 곳에서 화면과 API를 함께 줌)을 그대로 올리는 쪽이 새로 확인할 것이 가장 적습니다. 고르실 것은 하나입니다.

1용어 넷

AWS는 역할마다 서비스가 따로 있습니다. 이 프로젝트에 쓰일 수 있는 것은 넷입니다.
이름하는 일이 프로젝트에서 맡을 수 있는 것
EC2빌려 쓰는 서버 한 대. 무엇이든 설치할 수 있음Spring 서버, 조회 서버, nginx, (원하면) DB까지

3공식 문서에서 확인한 것

DB를 RDS로 옮기는 길은 열려 있습니다. CloudFront는 조용한 연결을 30초에 끊습니다.
궁금한 것확인한 사실
RDS가 pg_bigm을 지원하나지원합니다. PostgreSQL 18.1~18.6에 1.2_20250903이 들어 있고, dev가 쓰는 것과 같은 판입니다
RDS에서 pg_bigm을 미리 불러오는 설정(shared_preload_libraries)을 넣을 수 있나확인 못 함. 문서에 문장이 없어, RDS 설정 화면에서 직접 봐야 합니다
CloudFront가 서버 응답을 얼마나 기다리나기본 30초. 응답 조각 하나를 받은 뒤 다음 조각까지도 30초입니다. 넘기면 연결을 끊습니다
AWS 문서 "PostgreSQL extensions supported on Amazon RDS"(docs.aws.amazon.com/AmazonRDS/latest/PostgreSQLReleaseNotes/postgresql-extensions.html), "Origin settings"(docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesOrigin.html), 2026-10-04 확인. 자세한 것은 docs/research/deploy/aws-layout.md 2절

4고르실 것

먼저 한 대로 올리고, 회원 데이터가 쌓이기 전에 DB를 RDS로 옮기는 순서를 권합니다.

110월 6일에는 EC2 한 대에 nginx·Spring·조회 서버·PostgreSQL을 모두 올림. S3와 CloudFront는 쓰지 않음 [확정]

개발 환경에서 쓰는 PostgreSQL 이미지와 dev가 시험한 nginx 설정을 그대로 씁니다. DB는 하루 한 번 파일로 떠서 S3에 두는 백업만 붙입니다(S3는 여기에만 씁니다). 공개 뒤 첫 작업으로 DB를 RDS로 옮깁니다. 옮길 때 앱 코드는 바뀌지 않고 접속 주소만 바뀝니다.

감수하는 점: 그 서버가 죽으면 서비스가 전부 멈춥니다. 백업 사이에 가입한 회원 정보는 잃을 수 있습니다.

다른 선택: 처음부터 DB를 RDS로(B. 데이터가 안전하지만 설정 하나를 먼저 확인해야 하고 값이 더 듦). 처음부터 화면도 S3와 CloudFront로(C. 가장 튼튼하지만 dev가 시험한 구성을 다시 만들고 시험해야 해서 10월 6일에는 권하지 않음. 고르시면 ADR-0042에 덧붙여야 함). 고르시려면 기타에 "B" 또는 "C"라고 적어 주세요.

질문: 한 대(A)로 올린 뒤 DB만 따로(B)나 화면도 따로(C)로 옮기는 것은 어렵지 않나

앱 코드를 고칠 일은 없고, 옮기는 작업은 정해진 순서대로 하면 됩니다. 다만 옮기는 동안 서비스를 잠깐 멈춰야 하고, 처음부터 그 모양으로 올릴 때 필요한 확인은 옮길 때도 똑같이 필요합니다. 미룬다고 일이 없어지지는 않습니다.

한 대(A) → DB만 따로(B)DB만 따로(B) → 화면도 따로(C)
하는 일RDS에 빈 DB를 만듦 → 서버의 DB를 파일로 떠서 RDS에 넣음 → 서버가 볼 DB 주소를 RDS로 바꾸고 다시 켬 → 서버 안의 DB를 끔화면 파일을 S3에 올림 → CloudFront에 "그 밖의 주소는 S3, /api는 서버" 규칙을 만듦 → 도메인이 CloudFront를 가리키게 바꿈
앱 코드바뀌지 않음. DB 주소는 서버를 켤 때 주는 설정 값바뀌지 않음. 화면과 API가 계속 같은 주소
서비스가 멈추는 때DB를 떠서 넣는 동안. 그 사이 가입·탈퇴가 생기면 안 되므로 잠깐 닫아야 함없게 할 수 있음. 도메인을 돌리기 전에 CloudFront 주소로 먼저 시험
어려운 곳RDS에서 pg_bigm을 미리 불러오는 설정이 되는지(확인 못 함). 안 되면 검색 방식을 다시 봐야 해서 이것만은 일찍 확인하는 것이 좋음dev가 nginx로 시험한 것 셋을 CloudFront에서 다시 맞추고 시험: 보안 헤더, /books/1 같은 화면 주소, 대출 현황 연결이 30초에 끊기지 않는지
되돌리기서버 안의 DB를 지우지 않고 꺼 두기만 하면 주소를 되돌려 돌아갈 수 있음도메인을 다시 서버로 돌리면 됨

그래서 제안은 이렇습니다. 한 대로 올리되, RDS의 그 설정 하나는 이번 주 안에 설정 화면에서 미리 확인합니다(RDS를 만들기 전에도 파라미터 그룹 화면에서 볼 수 있는지는 확인 못 함. 안 보이면 가장 작은 RDS를 잠깐 만들어 확인). 걸리는 시간은 근거가 없어 적지 않았습니다.
