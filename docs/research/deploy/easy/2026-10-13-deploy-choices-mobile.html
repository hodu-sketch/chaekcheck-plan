2노트북으로 옮길 때 연결 방법

클라우드 서버도 Cloudflare Tunnel로 연결하면, 2주 뒤 노트북으로 옮길 때 도메인과 카카오 설정을 그대로 둡니다. 바뀌는 것은 터널을 켜는 기계 하나뿐입니다.

Cloudflare Tunnel은 서버에서 cloudflared 프로그램을 켜 두면, 그 프로그램이 Cloudflare 쪽으로 먼저 연결을 맺는 방식입니다. 사용자가 내 도메인으로 들어오면 Cloudflare가 그 연결을 통해 서버로 넘깁니다. 서버는 바깥에서 들어오는 포트를 열지 않아도 됩니다. 집 PC에서 이미 써 본 방식입니다.

사용자와 Cloudflare 쪽은 그대로이고, 오른쪽 기계만 바뀝니다. 카카오에 등록한 돌아올 주소도 도메인 기준이라 바꿀 필요가 없습니다.

질문 2클라우드 서버도 Cloudflare Tunnel로 연결할까요?

추천터널로 연결

옮길 때 DNS, 인증서, 카카오 설정을 건드리지 않습니다. 서버에 80·443 포트를 열지 않아도 됩니다.

도메인을 서버 IP에 바로 연결

서버에서 80·443 포트를 열고 인증서를 따로 설정해야 합니다. 노트북으로 옮길 때 DNS를 다시 바꿔야 하고, 집 인터넷은 IP가 바뀔 수 있습니다.

노트북의 CPU 종류(Intel·AMD인지 Arm인지), 메모리, 디스크 크기를 알려 주시면 옮기는 순서에 반영합니다.

3화면을 GitHub 연동 무료 호스팅으로 옮길지

지금 구성에서는 얻는 것이 거의 없습니다. Cloudflare가 앞에 있으면 화면 파일은 이미 Cloudflare가 캐시해서 빠르게 내려 줍니다.

화면과 API가 같은 주소여야 하는 이유

2026-10-04에 정한 규칙입니다. 브라우저는 로그인 쿠키를 그 쿠키를 준 주소로만 보냅니다. 카카오 로그인이 끝나면 카카오가 브라우저를 /api/v1/auth/login/oauth2/code/kakao로 돌려보내는데, 이 주소에서 우리 서버가 받아야 로그인이 끝납니다.

화면만 다른 곳에 올리면, 그곳이 /api 요청을 우리 서버로 넘겨 주는 설정을 따로 만들어야 같은 주소가 유지됩니다.

서비스별로 걸리는 점

Cloudflare Pages / Workers
/api를 넘기는 함수를 만들어야 하고, 그 요청은 하루 10만 건 무료 한도에서 빠집니다. 설정을 잘못하면 카카오가 돌려보낸 주소에 우리 서버 대신 화면 파일이 나가 로그인이 안 끝납니다.
Vercel 무료(Hobby)
비상업 개인용만 됩니다. 광고, 결제, 판매가 붙으면 약관 위반입니다.

우리 서버로 넘긴 요청은 26초 뒤 끊깁니다. 무료 한도를 다 쓰면 사이트 전체가 멈춥니다.
GitHub Pages
/api를 넘기는 기능이 없습니다. 온라인 사업용 무료 호스팅으로 쓰지 말라는 정책이 있습니다.

Cloudflare가 앞에 있으면 이미 캐시됨

Cloudflare는 파일 확장자를 보고 JS, CSS, 글꼴, 그림을 기본으로 캐시합니다. 지금 nginx는 빌드한 화면 파일에 "1년 동안 바뀌지 않음" 표시를 붙여 보내고, 무료 요금제의 Cloudflare는 이 표시를 따릅니다. 그래서 첫 방문자 이후로는 화면 파일이 Cloudflare에서 바로 나갑니다.

질문 3화면을 어디서 내려 줄까요?

4과한 요청 막기와 모니터링

사람마다 요청 한도를 거는 설정은 이미 있습니다. 하지만 터널 뒤에서는 모든 사용자가 같은 주소로 보여서, 한도 하나를 다 같이 쓰게 됩니다. 배포할 때 이것을 고쳐야 합니다.

IP별 한도는 서버가 도서관 사이트를 대신 불러야 하는 요청에만 걸려 있습니다. 검색 결과의 대출 현황, 도서관별 "더 보기"가 해당합니다. dev가 2026-10-05에 연달아 24번 보내 22번째부터 막히는 것을 확인했습니다.

터널 뒤에서 생기는 문제

Cloudflare는 요청마다 CF-Connecting-IP라는 헤더에 진짜 사용자 IP를 적어 보냅니다. 터널을 거칠 때도 이 헤더가 붙는지는 공식 문서에서 확인하지 못해, 배포할 때 시험합니다.

질문 4배포할 때 nginx가 진짜 사용자 IP를 읽게 설정할까요?

추천nginx에서 CF-Connecting-IP를 사용자 주소로 씀

지금 있는 IP별 한도가 사람마다 따로 걸립니다. Cloudflare 무료 규칙을 하나 더할지는 운영해 보고 정합니다.

Cloudflare 무료 한도 규칙 하나에만 맡김

설정은 쉽습니다. 무료 규칙은 1개, IP 기준, 10초 단위뿐이라 동시 연결 수는 막지 못합니다.

모니터링: 서버 상태를 숫자로 보기

모니터링은 CPU, 메모리, 응답 시간, 오류 수 같은 서버 상태를 시간 순서로 모아 그래프로 보는 것입니다. 사이클 15의 이용 기록(무엇을 검색했나)과는 다른 것입니다. 지금 우리 서비스에는 상태 숫자를 내보내는 기능이 없습니다. Spring에 의존성 하나와 설정을 더하면 /actuator/prometheus 주소에서 숫자가 나옵니다. 이 주소는 바깥에 보이면 안 됩니다.

4GiB 서버에서는 Prometheus와 Grafana가 서비스와 메모리를 나눠 씁니다. 얼마나 쓰는지는 재 보지 않았습니다.

5대출 조회의 1초 간격

혼자 쓸 때는 거의 영향이 없습니다. 몇 초 안에 여러 사람이 같은 도서관을 찾으면 줄을 서서 늦어집니다. 교보 구독형 서버는 따로 다룹니다(카드 6).

지금 규칙

우리 서비스는 도서관 사이트 주소마다 한 번에 1건만 보냅니다. 앞 요청의 응답이 끝나면 1초를 쉬고 다음 요청을 보냅니다. 이 줄은 모든 사용자를 합쳐서 하나입니다. 검색 결과는 묶음이 시작되고 8초 안에, 상세 화면은 30초 안에 답이 와야 합니다. 그때까지 차례가 오지 않으면 그 도서관은 화면에 "확인 못 함"으로 나옵니다. 같은 검색은 3분 동안 저장해 둔 답을 그대로 씁니다.

한 사람마다 약 2초씩 밀립니다. 5번째 사람부터는 8초 안에 차례가 오지 않아 "확인 못 함"이 됩니다. 계산값이며 실제로 재 보지는 않았습니다.

혼자 쓸 때 괜찮은 이유: 검색 한 번에 도서관마다 1번씩만 보내고, 도서관마다 주소가 달라서 서로 기다리지 않습니다. 한 번에 5곳씩 동시에 보냅니다.

지금도 확인할 수 있는 것: 차례를 못 받아 포기하면 서비스 로그에 throttle timeout이 남습니다. 모니터링에 이 횟수를 넣으면 얼마나 자주 생기는지 보입니다.

질문 6일반 도서관의 1초 간격은 어떻게 할까요?

추천처음에는 그대로 두고 포기 횟수를 지켜봄

숫자가 늘면 그때 저장 시간 늘리기(지금 3분)나 도서관별 간격 조정을 검토합니다.

배포 전에 간격을 줄이거나 없앰

몰릴 때 덜 기다립니다. 도서관 사이트에 가는 요청이 그만큼 촘촘해집니다. 이 간격은 사이클 01에서 정한 예절 규칙입니다.

6교보 구독형 서버에 서비스 조회를 다시 보낼지

교보 구독형 서버는 2026-10-07부터 집 IP를 막고 있습니다. 클라우드나 노트북의 다른 IP에서 조회를 보내려면 원칙을 바꿔야 합니다. 보낸다면 1초 간격 대신 "이 서버 전체에 동시 5건까지"로 묶자는 제안입니다.

교보 소장형1,182곳, 서비스에 있음
공공도서관 구독21곳, 서비스에 있음

세 종류의 차이는 사이트 화면에 권수가 나오는지입니다.

2026-10-07 폰으로 확인하신 화면(한국국제교류재단 "대출 0/2", LG인화원은 버튼만)과 dev 시험(2026-10-05)이 근거입니다.

왜 1초 간격으로는 안 되나

말씀하신 대로입니다. 이 서버는 평소에도 한 번 답하는 데 4~6초가 걸렸습니다(2026-10-06 기록). 검색 결과는 8초 안에 와야 합니다.

응답 5초로 그린 예입니다. 동시 1건이면 8초 안에 1곳만 답이 오고, 동시 5건이면 5곳이 같이 옵니다.

이 서버를 쓰면서 가입 조건을 조사한 도서관은 22곳입니다(로컬 데이터베이스, 2026-10-12). 소장형 1,206곳은 대부분 학교·기관 구성원용이라, 사용자가 직접 추가하지 않으면 검색 대상에서 빠집니다.

지금 코드의 문제: 서비스는 도서관 주소별로 셉니다. 교보 구독형은 도서관마다 하위 주소가 달라서, 이 서버 하나에 여러 사람 몫이 쌓이면 동시에 최대 100건(검색 하나에 5건 × 동시 검색 20개)까지 갈 수 있습니다. 막혔을 때 우리가 보내던 양은 동시 4건이었습니다.

질문 7교보 서버에 서비스 조회를 다른 우리 IP에서 다시 보낼까요?

추천보냄. 간격 없이, 모든 사용자 합쳐 이 서버에 동시 5건까지

소장형과 공공도서관 구독의 대출 현황이 다시 나옵니다. 5건은 지금 검색 하나가 한꺼번에 보내는 수와 같습니다. 상한을 두는 일은 dev에 넘깁니다.

보냄. 상한 없이 지금 코드 그대로

가장 빠릅니다. 사용자가 몰리면 막혔을 때보다 훨씬 많이 갈 수 있습니다.

보냄. 상한 2~3건

서버 부담이 더 적습니다. "전체 도서관" 검색에서 확인 못 함이 늘어납니다.

보내지 않음

원칙이 그대로 남습니다. 이 서버의 도서관은 대출 현황이 늘 "확인 못 함"입니다.

북큐브와 YES24도 공용 서버에 도서관이 여럿 모여 있습니다. 같은 방식을 쓸지는 dev가 서버별로 어떻게 묶이는지 확인한 뒤 정합니다.

7수집: 교보 서버, 원칙 문장, 빠르게 하는 방법

수집은 1초 간격을 지켜도 됩니다(사용자 말씀). 프록시를 써도 수집은 빨라지지 않습니다. 빠르게 하려면 받는 양을 줄이는 쪽이 맞습니다.

수집기의 간격 규칙

수집기는 서버(IP)마다 줄을 하나씩 세웁니다. 한 줄 안에서는 한 번에 1건, 앞 응답이 끝나고 1초 뒤에 다음 요청을 보냅니다. 서로 다른 서버의 줄은 동시에 움직이고, 지금은 40줄을 함께 돌립니다.

한 서버에서 받는 속도는 "1 ÷ (응답 시간 + 1초)"로 정해집니다. 프록시는 이 식을 바꾸지 못하고 중간 단계가 하나 늘어 조금 느려집니다.

프록시 종류

우리 국내 서버에 직접 올린 프록시

우리 서버 한 대의 고정 IP로 내보냅니다. 국내 1GB 서버는 월 5,600원부터입니다. 수집기를 Claude 클라우드(미국)에서 돌릴 때 나가는 IP를 한국으로 맞추는 용도입니다. 원칙에 맞습니다.

업체에서 빌리는 데이터센터 IP

예: Oxylabs 한국 전용 월 $8.25부터. "우리 서버 IP만"이라는 원칙 밖입니다.

주거용, IP를 바꿔 가는 프록시

요청마다 남의 가정용 IP로 바꿉니다. 예: GB당 $2~8. 쓰지 않기로 정했습니다(2026-10-12).

질문 8교보 소장형·공공도서관 구독을 다른 우리 IP에서 다시 받을까요?

추천받음. 이 서버에는 동시 1건, 1초 간격

막혔을 때처럼 동시 4건으로 올리지 않습니다. 대여·혼합 230곳은 그대로 받지 않습니다. 지금 수집기는 이 서버로 가는 요청을 일부러 걸러 내므로(사이클 13 인계), 그 부분을 바꾸는 일이 dev에 넘어갑니다.

서비스 조회만 풀고 수집은 그대로 막음

교보 서버에 가는 양이 가장 적습니다. 이 도서관들의 책 목록은 10-07 이전에 받은 것에 머뭅니다.

법적 판단이 아니라 배경 자료입니다. 2022년 대법원 판결(2021도1533, 숙박 앱 크롤링, 무죄)은 접근이 막혔는지를 "보호조치나 이용약관 등"으로 판단했고, 별도 보호조치가 없었다는 점이 무죄 이유 중 하나였습니다. IP 차단은 그 보호조치로 읽힐 수 있습니다. 막힌 뒤 다른 IP로 다시 들어간 경우를 직접 다룬 한국 판례는 찾지 못했습니다. 저작권법 제93조와 부정경쟁방지법의 전문가 확인은 backlog에 남아 있습니다.

수집을 실제로 빠르게 하는 방법

바뀐 것만 다시 받기
매번 전체를 받지 않고 새로 들어온 책만 받습니다. 받는 쪽수가 줄어 효과가 가장 큽니다. "갱신 기능" 계획과 같은 주제입니다.

압축해서 받기
사이트가 압축을 지원하면 주고받는 양이 줄어듭니다. 사이트마다 지원하는지 시험이 필요합니다.
