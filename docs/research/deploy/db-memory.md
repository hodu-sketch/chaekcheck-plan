# DB 메모리 줄이기 안 (사이클 밖 조사)

- 작성: 2026-10-05. 사용자 질문: "db크기를 줄일 수 있지 않을까?", "메모리를 효율적으로 관리하는게 문제 아닌가"
- 조사와 방법만 적습니다. 모듈·표·API 설계는 없습니다. 이 안을 쓰는 사이클이 이 문서를 링크합니다.
- 측정: 로컬 개발 DB(`chaekcheck-db-1`)를 읽기만 하여 2026-10-05에 잼. 서버 메모리 설정은 재지 않음.

## 1. 결론

메모리를 많이 쓰는 것은 DB 전체 크기가 아니라 **인기 책의 `holding` 줄이 표 전체에 흩어져 있는 것**입니다. 줄을 작게 만들기보다 **같은 책의 줄을 붙여 저장**하는 것이 메모리에 훨씬 효과가 큽니다.

## 2. 측정값 [확정: 측정]

| 항목 | 값 |
|---|---|
| DB 전체 | 9,902MB |
| `catalog.holding` | 20,383,882줄, 8,408MB (표 5,983MB + 인덱스 2,423MB), 페이지당 평균 26.6줄 |
| 서로 다른 (platform, item_key) | 3,358,587개 (평균 6.1배 반복) |
| 책 한 권의 줄 흩어짐 | 무작위 책 200권의 11,234줄이 10,732페이지에 있음. `book_id` 상관도 0.01 |
| 도서관 목록이 통째로 같은 경우 | 거의 없음 (같은 목록끼리 묶어도 20,190,571줄) |

소장 도서관이 많은 책부터 셌을 때 그 책들의 `holding` 줄이 차지하는 페이지:

| 상위 책 | 줄 수 | 지금 | `book_id` 순으로 붙이면 [안: 계산값] |
|---|---|---|---|
| 100권 | 59,489 | 364MB | 약 17MB |
| 1,000권 | 432,382 | 1,727MB | 약 127MB |
| 10,000권 | 2,334,745 | 4,189MB | 약 686MB |

읽는 곳(dev 코드, 2026-10-05):
- 검색 목록은 `catalog.book`만 읽음 (`PgBigmBookSearch`, `book.library_ids`로 거름)
- 대출 현황 스트림은 `JdbcCatalogHoldings.holdingsOf`로 결과 책의 **모든 도서관** `holding` 줄을 읽음 (계획 도서관으로 거르지 않음)
- 도서관 응답은 앱 안 Caffeine 캐시에 둠

## 3. 안 (순서대로)

| # | 안 | 효과 | 바뀌는 것 | 시기 [안] |
|---|---|---|---|---|
| 1 | **`holding`을 `book_id` 순으로 저장** (가져오기에서 정렬해 쓰기, 또는 가져온 뒤 `CLUSTER`) | 메모리: 큼 (위 표) | 가져오기 순서만. 표·API·화면 그대로 | 배포 전 |
| 2 | **PostgreSQL 메모리 설정** (`shared_buffers`, `effective_cache_size` 등)을 서버 크기에 맞춤 | 메모리를 실제로 쓰게 함 | 운영 DB 설정 | 배포 때 |
| 3 | `holdingsOf`가 계획 도서관 줄만 읽기 | 1을 하면 추가 효과 작음 | 조회 코드 | 나중에 |
| 4 | `detail_url` 저장하지 않고 `base_url` + `item_key`로 만들기 (포털·알라딘 293,443줄은 저장) | 디스크: 약 8.4GB → 6.3GB [안: 추정] | 표·가져오기·스트림 | 디스크·백업이 부담될 때 |
| 5 | 책 코드 표 + 도서관–코드 짝 표로 나누기 | 디스크: 약 3GB [안: 추정] | 표·가져오기·스트림 번호(`holdingId`) | 4와 같음 |
| - | Redis 등 별도 캐시 | 필요 없음 (서버 한 대) | - | - |
