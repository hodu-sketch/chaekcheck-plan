주기적으로 하는 세 작업의 절차를
dev의 운영 안내서 한 곳에 모읍니다.

이 페이지는 결정 기록 초안(ADR-0047)을 풀어 쓴 것입니다. 맨 아래 한 가지만 고르시면 됩니다. 원본은 대화에 링크한 ADR 초안입니다.

1지금은 세 곳에 흩어져 있습니다

세 작업 모두 dev 코드를 실행하는데, 절차는 dev 안내서, plan 연구 문서, dev 회고 문서에 나뉘어 있습니다. 수집기 코드는 어느 저장소에도 없습니다.

이 때문에 생긴 일: plan의 flows.md는 책 검색 화면이 dev에 만들어진 뒤에도 "미구현"으로 남아 있었습니다. 첫 실제 가져오기(2026-10-03)도 plan 문서에는 "아직 안 함"으로 적혀 있었습니다.

2바뀐 뒤: dev docs/maintenance/ 한 곳

운영할 때는 dev의 docs/maintenance/README.md 한 장에서 시작합니다. plan에는 왜 그렇게 하는지만 남습니다.
dev에 생기는 것내용지금 있는 곳
docs/maintenance/README.md① → ② → ③ 순서, 주기, 체크리스트 한 장plan docs/research/maintenance/periodic-tasks.md (초안)
1-libraries.md도서관 목록 확인dev library-maintenance.md

3-import.md서비스 DB로 가져오기: 명령, 먼저 세기, 확인할 숫자dev plan-feedback.md "가져오기 실행 방법"
scripts/crawl/수집기 코드git 밖 chaekcheck-data/scripts

수집 DB(ebook-catalog.sqlite), 로그, 국립중앙도서관 인증키는 지금처럼 git 밖 chaekcheck-data에 둡니다.

질문: plan에 있는 수집 문서를 전부 dev로 옮기나요?

아닙니다. 돌리는 방법(실행 절차)과 수집기 코드만 옮기고, 원칙·조사·결정은 plan에 남깁니다. 두 쪽은 서로 링크합니다.

plan 문서옮기나이유
crawl-runbook.md실행 부분만 dev 2-crawl.md로 (이어 받기, 명령, 병렬·IP 줄 설정법, 받지 않는 도서관 표시법, 문제별 대처, 새 사이트 붙이는 순서). 진행 상태 표와 결정 기록은 plan에 남김수집기를 돌리는 사람이 코드 옆에서 볼 내용
platforms.mddev로 (제안, plan에 두어도 됨)플랫폼 타입별 목록 주소·쪽 크기·읽는 위치. 사이트가 바뀌면 코드와 함께 고침
crawl-method.mdplan에 남김한 서버 1건·1초, 수집 범위, 저장 항목 등 사용자가 정한 원칙
research.mdplan에 남김직접 수집하는 이유, 법적 검토 등 조사 기록
catalog-refresh.md, same-book-isbn.md, search-and-normalization.mdplan에 남김앞으로 정할 것과 정리 규칙의 근거. 규칙의 코드는 이미 dev에 있음
periodic-tasks.md내용은 dev README.md로, plan 파일은 안내만dev 운영 안내서의 초안

3다른 선택과 비용

dev에 모으는 안을 추천합니다. 실행하는 코드 옆에 절차가 있어야 코드가 바뀔 때 절차도 같이 고쳐지기 때문입니다.
안좋은 점드는 비용
dev에 운영 안내서 + 수집기도 dev로 (추천)절차와 코드가 한곳. 2026-10-01 원칙과 맞음. 수집기 수정이 커밋으로 남음한 번 옮겨야 함. plan은 dev에 쓸 수 없어 요청서로 넘김. Python 수집기가 Java 저장소에 들어가 실행 환경(bs4, lxml)을 적어야 함
plan에 운영 안내서plan 세션에서 바로 고칠 수 있음plan은 dev 코드 변화를 바로 알지 못함. 2026-10-01 원칙을 뒤집어야 함
지금처럼 흩어 두고 색인으로 연결할 일 없음상태 표시가 계속 어긋남. 매번 reference-index.md부터 찾아야 함

4정할 것

1ADR-0047 초안대로 씀: 정기 유지보수 절차는 dev docs/maintenance/에, 수집기는 dev scripts/crawl/로 [안]

승인하시면 이렇게 됩니다.

1) docs/adr/0047-maintenance-procedures-in-dev.md를 씁니다. 사이클 칸은 "사이클 밖 (2026-10-04, 사이클 05 개발 중)"입니다. 끝난 사이클 05 문서와 인계서는 건드리지 않습니다. dev는 plan의 docs/current/handoff.md만 읽으므로 지금 개발에 끼어들지 않습니다.

2) 요청서 docs/research/maintenance/dev-move-request.md를 만듭니다. 사용자가 사이클 05 개발과 겹치지 않을 때 dev 세션에 그대로 전달합니다(사용자 선택, 2026-10-04: "ADR 추가 + 요청서를 내가 dev에 전달").

3) 수집기는 지금 진행 중인 수집이 끝난 뒤(10월 6일 0시 무렵 예상) 옮깁니다. 옮긴 뒤 plan의 crawl-runbook.md·periodic-tasks.md 머리말에 "절차 원본은 dev docs/maintenance/"를 적고 실행 절차는 지웁니다.

이유: 사용자 "근데 지금 주기적으로 필요한 작업들이 dev랑 plan에 흩어진 게 좀 그런데...". 형태는 Claude 제안 → 승인("이렇게 하도록 해줘"). 다른 두 안을 고르지 않은 이유는 [이유 미확인]으로 적습니다.

다른 선택: 3번 카드의 두 안. 또는 ADR 없이 backlog.md에 한 줄만 남기고 다음 사이클 시작 때 정함(기록이 늦어짐).
