AI 도서 추천을 어떤 모델로, 어떤 순서로 만들지
11가지를 골라 주세요.

"로깅으로 추천도서 + 글 설명으로 추천도서에 적합한 AI 모델들을 알려주고 어떻게 구성하면 좋은지"라고 물으셨습니다. 결론은 모델은 운영 서버 밖(PC나 잠깐 빌린 GPU)에서 미리 돌리고, 서버는 결과 표만 읽는 구성입니다. 글(서지)로 비슷한 책을 찾는 모델, 기록으로 같이 본 책을 세는 계산, 소개 문구를 쓰는 모델이 각각 다릅니다. 법 확인 결과(동의·표시)도 같이 넣었습니다. 바탕: docs/research/ai-recommend/overview.md와 industry·infra-cost·law 세 조사 문서(2026-10-17). 여기 수치는 모두 공식 페이지에서 2026-10-17에 확인한 값이고, 확인 못 한 것은 그렇게 적었습니다.

1단계에서는 이 두 칸(소개 문구, 비슷한 책)만 생깁니다. "같이 본 책"·"나에게 맞는 책" 칸은 2·3단계.

가. 구성과 범위

1세 단계로 나누고,
모델은 운영 서버 밖에서

[안] 추천을 ① 후보 뽑기(비슷한 책·같이 본 책) ② 순위(규칙 계산) ③ 소개 문구(LLM) 세 단계로 나누고, ①③은 PC에서 미리 계산해 표만 운영 DB에 넣습니다. 서버는 조회와 가벼운 계산만 합니다.

어디서 생기는 값인지: 서버 메모리 4GB에 Spring Boot와 PostgreSQL이 같이 삽니다(사이클 17). 68만 권 임베딩은 원본만 약 2.79GB이고 검색 색인은 그만큼 더 필요해 서버에 둘 수 없습니다(pgvector 공식 README의 크기 산식으로 계산, infra-cost.md 4절). 책당 이웃 20권만 표로 두면 약 130MB입니다.

예: 사용자가 책 창을 열면 서버는 book_similar에서 그 책의 이웃 20권을 한 번 읽고, 내 도서관에 있는 책을 앞으로 보냅니다. AI를 부르지 않습니다.

다른 선택: 서버가 요청마다 AI(API나 vast.ai)를 부르기 — 응답이 느려지고 요청 수만큼 돈이 들며, 빌린 GPU가 내려가면 추천도 멈춥니다. 권하지 않습니다.

21단계는 "비슷한 책 + AI 소개 문구"만,
기록은 바꾸지 않음

[안] 첫 사이클은 서지 임베딩으로 만든 "비슷한 책"과 AI 소개 문구를 책 창·추천도서 화면에 넣습니다. 비로그인도 똑같이 보입니다. 이용 기록·약관은 손대지 않습니다. 같이 본 책(2단계)과 로그인 맞춤(3단계)은 뒤에 합니다.

왜 이 순서인지: 기록이 적을 때 기록 기반 추천은 결과가 나쁩니다. Amazon은 "아는 게 없으면 가장 인기 있는 것", Netflix는 신규 회원에게 인기작과 설문, Goodreads는 20권 평가를 요구합니다(industry.md 4절, 각 회사 공식 자료). 책첵은 추천목록 세 개(사서·이동진·서울대)와 서지가 이미 있어 1단계를 바로 할 수 있습니다.

다른 선택: 처음부터 3단계까지 한 사이클에 — 표 3개, 설정 화면, 약관·처리방침 새 판이 한꺼번에 들어가 사이클이 커집니다.

3vast.ai는 "빌려서 돌리고 바로 반납",
서버가 실시간으로 부르지 않음

[안] GPU가 필요하면 vast.ai를 on-demand(중단 없음)로 몇 시간 빌려 임베딩·문구를 만들고 파일로 받은 뒤 바로 destroy합니다. 책 서지만 올리고 API 키·DB 덤프·이용 기록은 올리지 않습니다. 책첵 서버가 vast.ai REST를 부르는 구성은 하지 않습니다.

근거 (vast.ai 공식 문서, 2026-10-17 확인): 가격은 장비 주인이 정하는 시세(RTX 3090 최저 $0.16/시간, 4090 $0.40, 조회 당시), 입찰형은 더 높은 입찰에 밀리면 "프로세스가 죽은 채 멈춤", 삭제하면 "컨테이너 디스크 데이터는 영구 삭제", 보안 FAQ는 "제공자마다 보안 수준이 크게 다름"·"올리기 전에 암호화 권장"이라고 적고 장비 주인이 데이터를 볼 수 없다는 문장은 없습니다. docs.vast.ai 보안 FAQ, 저장소.

비용 예: 임베딩 68만 권 + 문구 10만 권을 4090으로 3~15시간 → 약 1,300~11,000원(환율 1,334.89원 가정, infra-cost.md 5절).

다른 선택: 서버리스(vast.ai·RunPod)로 실시간 호출 — 요청마다 켜지는 시간이 있고 켜 둔 만큼 과금, 주소가 바뀝니다. 개인 서비스 규모에 맞지 않습니다.

나. 모델 고르기

4비슷한 책 찾기는
한국어 임베딩 모델 KURE-v1, PC에서

[안] "글(서지)로 추천"은 nlpai-lab/KURE-v1(bge-m3를 한국어로 조정한 임베딩 모델, 1024차원, MIT 무료)을 PC에서 돌려 책마다 가까운 20권을 뽑습니다. 입력은 제목·저자·출판사(·출판일)만.

근거: 모델 카드에 한국어 검색 성능 top-1 recall 0.5264로 bge-m3 계열 중 가장 높게 보고됨, 라이선스 MIT (huggingface.co/nlpai-lab/KURE-v1, 2026-10-17 확인). PC CPU 처리량은 공식 수치가 없어 1,000권으로 시험해야 합니다(확인 못 함).

5같이 본 책은 모델 없이 SQL,
기록이 쌓이면 implicit

[안] "기록으로 추천"은 AI 모델이 아니라 SQL로 셉니다: 같은 방문에서 함께 연 책 쌍을 세고, 인기 책이 어디에나 나오지 않게 평균 대비 비율로 보정합니다(Amazon 2003 논문 방식). 기록이 몇 달 쌓이면 Python 라이브러리 implicit(ALS)으로 바꿀 수 있습니다.

근거: Amazon item-to-item 협업 필터링 논문 (PDF), GRU4Rec 논문은 "긴 이력이 없는 사이트는 실무가 item-to-item으로 회귀"한다고 적음 (arxiv 1511.06939). 둘 다 2026-10-17 확인.

다른 선택: 세션 추천 신경망(GRU4Rec·SR-GNN) — 학습 데이터가 수백만 세션일 때 뜻이 있습니다. 지금 규모에는 과합니다.

6소개 문구는 Claude Haiku 5.5 배치로,
입력은 서지만

[안] 문구는 Claude Haiku 5.5를 Message Batches로 불러 책마다 1~2문장을 미리 만들어 DB에 저장합니다. 입력은 제목·저자·출판사·분야(있으면)만 주고, "주어진 정보에 없는 줄거리·수상 경력을 쓰지 말 것"을 규칙으로 둡니다. 책 소개 원문(출판사 글)은 넣지 않습니다.

비용 (platform.claude.com 요금 페이지, 2026-10-17 확인): Haiku 5.5 입력 $0.10·출력 $0.50/100만 토큰, 배치는 둘 다 절반. 10만 권 × (입력 300 + 출력 80 토큰) = 약 $3.5, 한국어 토큰이 2배면 $7. 결과는 "대부분 1시간 안"에 옵니다.

7Jev(제브)는 순위 점수용으로
나중에 검토

[안] Jev는 글을 만들지 않으므로 소개 문구에는 쓸 수 없고, "이 후보가 이 독자의 최근 본 책과 맞는가"를 점수로 돌려받는 ② 순위 단계에 맞습니다. 다만 지금은 early access이고 개인정보 처리 문구를 홈페이지에서 찾지 못해, 1단계에서는 규칙 계산으로 가고 가입·약관을 확인한 뒤 검토합니다.

확인한 것 (TypeSafe AI 공식 문서, 2026-10-17): "returns typed decisions and probabilities rather than generated text", 입력은 글만, 질문 종류는 Choice(선택)·Score(점수)·Noul(예/아니오 확률), "답장 쓰기·코드·설명 생성에는 쓰지 말 것" (docs.typesafe.ai). 요금 "입력 10억 토큰당 $42", 출력 비용 표기 없음, 가입 절차 설명 없음, 개인정보 처리 설명 없음 (typesafe.ai). 1.14판(2026-10-14)은 다국어가 좋아졌다고 하나 "실험 단계라 실서비스 적용 비권장"(AI타임스 보도, 공식 원문 확인 못 함).

쓴다면 이렇게: 서버가 아니라 PC에서, (기준 책, 후보 책) 쌍마다 "같은 독자가 좋아할 확률"을 Noul로 받아 표에 점수로 저장. 쌍이 68만 × 20 = 1,360만 개라 토큰이 많으니 추천목록·많이 찾는 책부터.

다른 선택: 처음부터 Jev로 순위 — 가입이 되는지, 올린 책·기록 데이터를 어떻게 다루는지 모른 채 설계하게 됩니다.

다. 기록(로깅)과 약관

8같이 본 책을 세려면
방문 번호 칸 하나 (2단계)

[안] 브라우저 탭을 열 때 무작위 번호를 만들어(탭을 닫으면 사라짐, 쿠키 아님) 책 상세 열기·도서관 클릭 알림에 함께 보내고, 기록 표에 visit_key 칸을 더합니다. 회원 번호와 잇지 않고, 같이 본 책 계산은 IP를 읽지 않습니다.

지금과 달라지는 것: 사이클 15에서 "기록끼리 잇는 칸 없음"으로 정했습니다(ADR-0096). 이것을 바꾸는 일이라 새 ADR이 필요합니다.

법 (law.go.kr·개인정보위 작성지침, 2026-10-17 확인): 개인정보는 "다른 정보와 쉽게 결합하여 알아볼 수 있는 정보"까지입니다(제2조1호 나목). 쿠키도 회원 번호도 없는 탭 번호는 결합 키가 없어 개인정보가 아니라고 볼 여지가 큽니다(추론). 같은 줄에 IP(30일)가 있어 결합 가능성이 남으니 계산 때 IP를 읽지 않습니다. 개인을 식별하지 않는 행태정보 처리는 처리방침에 "안내 권장"(작성지침 p.58) → 1절에 한 구절 더합니다(11번).

다른 선택: 쿠키(기기 단위, 며칠 이어 봄) — 처리방침에 "자동 수집 장치 설치·운영·거부" 절이 필수(제30조①7호)가 되고 광고 차단기가 막습니다. 이번엔 쓰지 않습니다.

9로그인 맞춤 추천은 별도 표에,
기본 켬 + 설정에서 끄기 (3단계)

[안] 익명 통계 기록(usagelog)은 그대로 두고, 추천용 표를 따로 만듭니다: 회원 번호·책 번호·종류(연 책·누른 도서관·관심도서)·시각. 탈퇴하면 함께 지우고, 보관은 탈퇴 또는 마지막 로그인 뒤 1년. 회원 설정에 "맞춤 추천 끄기"를 두고, 끄면 저장을 멈추고 있던 줄도 지웁니다.

동의가 꼭 필요한가 (law.md 1절, 2026-10-17 확인): 개인정보위 통합 안내서 FAQ(p.129): "맞춤형 콘텐츠 추천이 계약의 본질적인 내용이며 해당 내용을 이용계약·약관 등에 명확히 규정하고 있고 정보주체가 충분히 알 수 있도록 조치하였다면, 계약 이행을 위해 별도의 동의 없이도 수집·이용할 수 있음"(제15조①4호). 다만 작성지침은 "식별하여 행태정보를 처리하는 경우" 처리방침에 근거·항목·방법·목적·기간·거부 방법을 적으라고 합니다(p.55) → 끄기 설정이 거부 방법이 됩니다. "자동화된 결정" 절은 필요 없습니다(안내서가 상품·콘텐츠 추천을 명시적으로 제외, p.10).

10AI가 쓴 문구에는 "AI가 쓴 소개" 표시,
서비스 안내에 사전 고지

[안] 문구 옆에 "AI가 쓴 소개"(또는 AI 표시)를 붙이고, 서비스 안내·약관에 "책 소개 문구 일부는 생성형 AI(Claude)가 씁니다"를 적습니다. 비슷한 책 목록 자체는 글을 만들지 않으므로 표시하지 않습니다.

법 (law.go.kr, 2026-10-17 확인): 인공지능 기본법 제31조① "생성형 인공지능을 이용한 제품 또는 서비스를 제공하려는 경우 … 사실을 이용자에게 사전에 고지", ② "결과물이 생성형 인공지능에 의하여 생성되었다는 사실을 표시". 시행령 제23조: 고지는 "이용약관 등에 기재" 또는 화면 표시, 표시는 "사람이 인식할 수 있는 방법". 규모 면제 없음(매출·이용자 기준은 국내대리인 조항에만). 과기정통부: "1년 이상 계도기간", 서비스 안에서만 보일 때는 "UI나 로고 표출 등으로 유연하게" (보도자료 2026-01-21). 국내 서점(교보·YES24·밀리)은 "AI와 대화" 같은 진입점 이름으로만 드러내고 문구별 표시는 확인되지 않았습니다(industry.md 2절).

다른 선택: 표시 없이 — 계도기간이라 당장 과태료는 없지만 표시를 넣는 비용이 거의 없습니다.
