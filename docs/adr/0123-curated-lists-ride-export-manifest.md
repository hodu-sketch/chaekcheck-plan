# ADR-0123: 이동진·서울대 목록은 수집기가 만든 목록 파일을 가져오기 파일 목차(`notes.listPart`, 판 3)에 실어 운영 반영 때 넣고, 표지도 수집기가 줄여 함께 실음

Status: Accepted (사용자 승인, 2026-10-16, 설계 정리 페이지)
Date: 2026-10-16
Cycle: 21-recommended-books
Supersedes: 없음

## 배경
이동진 추천도서·서울대 100선은 수집기(내 PC)가 목록 파일을 만들고(scope #2, 명세 R4), 전자책 목록 가져오기에 실어 운영 DB로 보내기로 했다(명세 결정 #10). 가져오기는 내 PC에서 파일 하나를 만들어 운영에 반영한다(ADR-0078), 도서관 정보는 목차 칸으로 실어 보낸다(ADR-0086).

## 결정
- export 때 `collection`이 `picks` 공개 API `CuratedListTransfer.read(listsDir)`를 불러 검사된 목록을 받아 `load_manifest`의 `notes.listPart`에 싣는다. 반영 파일 판을 2 → 3으로 올린다
- apply는 책 표를 바꿔 끼운 **뒤** 작은 트랜잭션 하나로 `replace(listPart)`를 부른다(**고침, 2026-10-16**: 처음 "도서관 부분과 같은 첫 트랜잭션"). 지문 비교가 다르거나 바꿔 끼우기가 실패하면 목록은 그대로, 목록 넣기만 실패하면 옛 목록이 남는다. `finish`·`in-place`도 바꿔 끼운 뒤 같은 `replace`
- 표지: 수집기가 ISBN 서지 API 표지를 받아 폭 200px JPEG로 줄여 목록과 함께 `listPart`에 싣고, `replace`가 `cover` 표에 넣는다. 운영 서버는 새 목록 표지를 바깥에서 받지 않는다

## 이유 (사용자 발언)
- 넣는 때 고침: 설계 검토 3 #3 "(B) 바꿔 끼운 뒤 작은 트랜잭션" 승인, 바꿔 끼우기 트랜잭션 안은 "나는 시간이 늘어나는게 싫어"로 미승인 (2026-10-16). 첫 트랜잭션에 두면 복원·색인 동안 목록이 새 책 번호를 가리키는 틈이 생김 (설계 검토 #8)
- "② 전자책 목록 가져오기에 실어 보내기 이걸로 하자" (2026-10-15, 명세 결정 #10)
- 설계 결정 #3 제안 → 승인, 메모 "표지 그림도 가져오기 파일에 함께 실려 간다 … 이거 이렇게 해" (2026-10-16)
- 설계 결정 #6: 추천안(서버가 표지 받기)을 미승인하고 "수집기가 표지를 받아 줄여서 가져오기 파일에 싣기"를 고름 (2026-10-16)

## 검토한 대안
### A안: 목차 칸 `listPart` + 판 3, 표지도 함께 (채택)
- 장점: 파일 하나(ADR-0078), 모듈 경계 지킴, 사이클 13에서 실데이터로 통과한 방식, 새 책 표지가 바로 보임. 단점: `collection → picks` 의존이 생김, 판 3 배포 때 기다리는 판 2 내보내기가 있으면 `finish` 거절(ADR-0086과 같은 감수), 파일이 약 1~3MB 커짐, 줄이는 코드가 수집기에 생김
### B안: 가져오기 파일 속 표로
- 단점: `catalog` 덤프 코드가 `picks` 표를 알게 됨. 채택하지 않은 이유: [이유 미확인] (추천하지 않은 안)
### C안: 옆에 작은 파일 하나 더
- 단점: 옮길 파일이 둘, 짝 맞추기 검사 필요. 채택하지 않은 이유: [이유 미확인] (추천하지 않은 안)
### D안: 표지는 운영 서버가 받기 (ADR-0091 방식)
- 채택하지 않은 이유: 사용자가 미승인하고 다른 선택을 고름 (2026-10-16, 설계 결정 #6)
