# ADR-0093: 넣기 명령은 `library`의 읽기 기능으로 서비스 도서관 전체를 보고, 운영 반영은 넣기 실행 기록 줄도 옮긴다

Status: Accepted
Date: 2026-10-12
Cycle: 13-crawler-to-dev
Supersedes: 없음 (ADR-0083·0084·0086·0087을 보완)

> **미리 정함**: 사이클 13은 사이클 12(책 묶기 기준)가 끝나기 전에 나란히 진행해 정한 결정이다. dev에는 사이클 12 handoff 뒤에 넘긴다.

## 배경
사이클 13 cycle-close 설계 검토(2026-10-12)에서 두 빈 곳이 나왔다. ① 넣기 명령(ADR-0084)은 서비스 도서관 전체(꺼진 곳 포함)의 주소·이름·업체·대출 방식·순번·꺼짐 여부와 비교해야 하는데, `library`가 내주는 읽기 기능(`LibraryCatalog.enabledLibraryRefs()`, `LibraryEligibility`)에는 이름·업체·꺼진 곳이 없다. `collection`이 `library.library`를 직접 읽으면 모듈 규칙(다른 모듈 표를 읽지 않음)을 어긴다. ② `/about`의 가입 조사 기준일은 넣기 실행 기록에서 읽는데(ADR-0087), 운영 반영(ADR-0086)이 그 줄을 운영 DB에 만든다는 규칙이 없어 운영에서 공지 줄이 비게 된다.

## 결정
- `LibraryRegistry`(ADR-0083)에 읽기 기능 `listAll()`을 더한다 [안: 이름]. 모든 도서관(꺼진 곳 포함)을 번호·이름·`base_url`·업체·대출 방식·순번·꺼짐 여부로 돌려준다. 넣기 명령은 이것만 부르고 `library` 표를 읽지 않는다
- 운영 반영(apply)은 `notes.libraryPart`의 도서관·가입 규칙·짝 줄과 함께 **성공한 넣기 실행 기록 줄**도 운영 `collection.library_insert_run`에 넣는다. 같은 `report_id`의 성공 줄이 이미 있으면 건너뛴다. 운영 `GET /api/v1/join-surveys/latest`가 값을 돌려주는 것을 AC-7에서 확인한다
- 기준일 API 경로는 복수형 규칙(dev api-design)에 맞춰 `GET /api/v1/join-surveys/latest` [확정] (ADR-0087의 [안] 경로 `/api/v1/join-survey`를 바꿈)

## 이유 (사용자 발언)
- 1번 읽기 기능, 운영 반영 때 실행 기록 옮기기: 설명을 들은 뒤 "설명대로"를 고름 (2026-10-12, cycle-close 검토). 이유는 [이유 미확인]
- 경로: "API로 읽음 (/join-surveys/latest)"를 고름 (2026-10-12). API 없이 화면 글로 고정하는 안은 고르지 않음 [이유 미확인]

## 검토한 대안
### A안: `library`에 읽기 기능 + 운영 반영이 실행 기록도 옮김 (채택)
- 장점: 모듈 규칙을 지킴, 운영에서도 공지 줄이 보임
- 단점: `library` 공개 기능이 하나 늘고, 반영 코드가 표 하나를 더 다룸
### B안: `collection`이 `library.library`를 직접 읽음
- 단점: 모듈 경계 위반(Spring Modulith 시험이 잡지 못하는 SQL 의존)
- 채택하지 않은 이유: [이유 미확인] (추천하지 않은 안)
### C안: API 없이 `/about`에 날짜를 글로 고정
- 장점: 새 API·실행 기록 옮기기가 필요 없음
- 단점: 다시 조사할 때 화면 글을 손으로 고쳐야 함
- 채택하지 않은 이유: [이유 미확인] (사용자가 API를 고름)

## 결과
- 좋아지는 점: 넣기 비교가 공개 기능만으로 됨, 내 PC와 운영의 공지가 같음
- 감수하는 점: 운영 반영이 실행 기록 표도 다룸(도서관 부분과 같은 트랜잭션)
- 나중에 되돌리거나 서비스로 분리할 때의 비용: 낮음. 나중에 분리할 때 `listAll`은 `library` 서비스의 읽기 API 하나가 됨
