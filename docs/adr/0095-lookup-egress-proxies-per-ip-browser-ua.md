# ADR-0095: 서비스 대출 조회는 세 가지 나가는 길(직접·업체 고정 IP 프록시·조회 서버)을 설정으로 고르고, 나가는 IP마다 따로 세며, 막힌 IP만 멈추고, 일반 브라우저 User-Agent로 보낸다

Status: Proposed
Date: 2026-10-13
Cycle: 사이클 밖 (배포 조사, `docs/research/deploy/`)
Supersedes: 없음 (ADR-0011 일부 바꿈: 호출 간격 제어 위치, 다른 서버로 넘기는 기준. ADR-0094의 서비스 조회 부분을 바꿈. 사이클 01 User-Agent 식별 원칙을 서비스 대출 조회에 한해 바꿈)

## 배경
서비스는 사용자가 검색할 때마다 도서관 사이트에 대출 현황을 그 자리에서 묻는다. 지금은 본 서비스가 서버 자기 IP로 직접 묻거나(ADR-0015 `direct`), 조회 서버(fetch-service)를 거친다(ADR-0011). 호출 간격은 본 서비스 한 곳에서 도서관 호스트 이름마다 동시 1건·1초로 세고(ADR-0010), User-Agent는 우리 서비스를 밝힌다(사이클 01). 교보 구독형 서버가 집 IP를 막은 뒤(2026-10-07), 사용자는 서비스 조회가 여러 사람의 조회를 대신 하는 것이므로 프록시를 쓰는 것이 합당하다고 보았다.

## 결정
- 나가는 길 세 가지를 모두 만들어 두고 설정으로 고른다: ① 본 서비스 직접(서버 자기 IP) ② 본 서비스 직접 + 업체 프록시 여러 곳 ③ 조회 서버(조회 서버마다 업체 프록시 여러 곳을 쓸 수 있음). 업체 프록시는 IP가 바뀌지 않는 고정 IP 상품만, 주소·인증은 비밀 값. 나간 길과 업체를 조회 기록에 남긴다.
- 도서관 한 곳에 보내는 양(동시 건수·간격)은 나가는 IP(업체 프록시·조회 서버)마다 따로 센다. 교보 구독형 서버는 나가는 IP마다 동시 3건(설정으로 조절), 그 밖의 사이트는 IP마다 동시 1건·1초.
- 한 IP가 어느 사이트에서 막히면 그 IP만 그 사이트에서 멈추고, 다른 IP로는 계속 조회한다.
- 서비스 대출 조회 요청의 User-Agent는 일반 브라우저와 같은 값으로 하고 우리 서비스 이름을 넣지 않는다.
- 수집(수집기)은 이 결정의 대상이 아니다. 수집은 `crawl-method.md` 1절과 ADR-0094 그대로(우리 고정 IP만, IP마다 1건·1초, 우리 이름을 밝힘).

## 이유 (사용자 발언)
- "조회하는데 프록시를 쓸까 하는데 … 이거 원칙 바꾸는 거고 우리가 여러 사람의 조회를 대신 하는 만큼 프록시를 쓰는게 합당하다고 봐. 어짜피 우리가 안 했으면 다른 사람들도 다 각각요청보냈을건데 대신해주는거자나" (2026-10-13)
- "아니 다 가능하도록 개발했으면 해 조회 서버를 두는 것도 방법이고 각각의 조회 서버 내에서 업체 프록시 여러개 쓸 수 있고 우리 본 서버에서 조회기능도 있되 업체 프록시 여러개 쓸 수 있는 걸로다가" (2026-10-13)
- "각 프록시 ip마다 따로 세는 걸로 해줘" (2026-10-13)
- "ㄴㄴ 특정 프록시/조회서버ip만 하지 말아" (2026-10-13, 막힌 IP만 멈춤)
- "그냥 사용자로 하면 안 될가? 그냥 사용자를 대신할 뿐이잖아", "ㄴㄴㄴㄴ 그냥 일반 사용자들 대신하는거니 일반 사용자들처럼" (2026-10-13)
- 업체 프록시는 고정 IP 상품만: 제안 → 승인 (2026-10-13)

## 검토한 대안
### A안: 세 길 모두, IP마다 따로 셈, 막힌 IP만 멈춤, 일반 브라우저 User-Agent (채택)
- 장점: 나가는 길을 상황에 맞게 고름. 업체 하나나 IP 하나가 막혀도 대출 현황이 계속 나옴. IP 수만큼 빨라짐
- 단점: 도서관 한 곳이 받는 양이 IP 수만큼 늘어남. 사이트가 우리를 알아보거나 막을 방법이 거의 없어짐. 업체 프록시 비용과 약관 확인
### B안: 우리 조회 서버 여러 대만 (업체 프록시 없음)
- 채택하지 않은 이유: "아니 다 가능하도록 개발했으면 해 …" (2026-10-13)
### C안: 서비스 서버 하나 + 업체 프록시만 (조회 서버 없음)
- 채택하지 않은 이유: 같은 말씀으로 세 길 모두를 고름 (2026-10-13)
### D안: 도서관 한 곳이 받는 양은 합계로 유지하고 IP만 나눔 (ADR-0011 그대로)
- 채택하지 않은 이유: "각 프록시 ip마다 따로 세는 걸로 해줘" (2026-10-13)
### E안: 한 IP가 막히면 그 사이트로 가는 조회를 모든 IP에서 멈추고 물음
- 채택하지 않은 이유: "ㄴㄴ 특정 프록시/조회서버ip만 하지 말아" (2026-10-13)
### F안: User-Agent에 우리 이름을 남기고 필요한 곳에만 브라우저 표시를 앞에 붙임
- 채택하지 않은 이유: "ㄴㄴㄴㄴ 그냥 일반 사용자들 대신하는거니 일반 사용자들처럼" (2026-10-13)
### G안: 업체 주거용·IP 바꿔 가는 프록시도 길로 넣음
- 채택하지 않은 이유: 고정 IP 상품만 넣는 제안을 승인 (2026-10-13)

## 결과
- 좋아지는 점: 교보 서버를 포함해 대출 현황이 막힘에 덜 끊김. 나가는 길을 설정으로 바꿈
- 감수하는 점: 사이트가 IP를 막아도 다른 IP와 브라우저 User-Agent로 계속 들어가는 모양이 되어, 대법원 2021도1533(접근 제한을 보호조치·약관 등으로 판단)의 기준에서 불리하게 읽힐 수 있음. 막힌 뒤 다른 IP로 들어간 경우를 다룬 한국 판례는 찾지 못함. 전문가 확인 항목(backlog "운영에 올리기")에 이 조합을 더함. 도서관 한 곳이 받는 양이 IP 수만큼 늘어나므로, 사이클 15가 기대는 "봇이 몰려도 도서관 사이트 하나는 1초에 한 번"이 "IP 수만큼"으로 바뀜. 업체 프록시 월 비용(예: Oxylabs 한국 전용 데이터센터 월 $8.25부터, 2026-10-12 업체 표기)과 약관 확인 [확인 필요]
- dev에 넘길 것(배포 사이클): 본 서비스와 조회 서버의 업체 프록시 거쳐 보내기와 인증, 프록시·길 설정 목록, 호출 간격을 나가는 IP마다 세기, 막힌 IP만 그 사이트에서 멈추기, 나간 길·업체 기록, User-Agent 값 바꾸기
- 나중에 되돌릴 때: 설정으로 길 ①만 쓰고 User-Agent를 되돌리면 지금과 같아짐. 간격 세는 위치는 코드 변경이 필요함
