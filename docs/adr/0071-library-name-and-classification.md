# ADR-0071: 도서관 이름에는 기관 이름만, 업체·대출 방식은 분류로

Status: Proposed
Date: 2026-10-11
Cycle: 09-library-naming
Supersedes: 없음 (ADR-0017의 "같은 기관의 두 번째 사이트에는 '(구독)' 등을 붙여 이름을 구분"과 사이클 07 design-delta seed 규칙의 "이름" 줄을 바꿈)

## 배경
같은 기관이 사이트를 둘 이상 운영하면 두 번째 사이트 이름에만 괄호가 붙었다. 서비스 seed 2,663곳 중 277곳에 업체(YES24 95, 교보 81, 북큐브 72, 알라딘 8)나 대출 방식(구독 15 등) 괄호가 있고, 사이클 07에서는 "(교보, 호스트)"까지 붙었다(2026-10-11 dev seed 셈, `docs/cycles/09-library-naming/research.md` 3절). 괄호 없는 쪽이 어느 업체인지는 화면에서 알 수 없었고, "(구독)"이 붙은 교보 구독형 9곳은 실제 대출 방식이 대여·혼합이었다. 서비스 DB에는 이미 화면 종류(`platform_type`)와 대출 방식(`lending_model`) 칸이 있다.

## 결정
- 이름에는 기관 정식 이름만 둔다. 이름 끝의 업체·대출 방식 괄호는 떼고, 기관 이름의 일부인 괄호((주), (임직원) 등)는 남긴다. 수집 DB의 이름도 같게 바꾼다.
- 모든 도서관에 업체(교보·YES24·북큐브·알라딘·통합 포털·자체)와 대출 방식(소장·구독·대여·혼합)을 둔다. 교보 일반과 교보 구독형은 같은 "교보"다. 업체는 대출 방식처럼 도서관 수집이 알아낸 사실로 보고 seed 생성 스크립트가 칸에 쓴다(지금은 화면 종류 대응표로 정함). DB는 허용 값만 확인한다. 통합 포털은 여러 업체가 섞여 대출 방식을 비워 둔다.
- 겹치면 안 되는 것은 (이름, 업체, 대출 방식, 순번) 조합이다. 순번은 이름과 따로 된 칸으로 보통 1이고, 이름·업체·대출 방식이 같은 곳이 또 들어오면 seed 생성 스크립트가 2, 3을 붙인다. 비어 있는 대출 방식끼리도 같은 값으로 보고, 꺼진 도서관도 센다.
- 다른 기관이 겹치면 정식 이름으로 나누고, 같은 사이트는 받지 않음으로 표시한다. 순번이 붙은 곳은 사이트 이름을 확인해 고치고 순번을 1로 되돌린다.
- 화면에서는 이름 옆(결과 카드는 모든 폭에서 이름 다음 줄)에 "교보 · 소장"처럼 분류를 작게 붙이고, 순번 2 이상은 "· 2번째 사이트"를 더한다.
- 이번 괄호 떼기는 한 번만 하는 예외이고, 그 뒤에는 "한 번 정한 이름은 바꾸지 않음"(예외: 공식 개명·틀린 이름)을 지킨다.

## 이유 (사용자 발언)
- "이름을 ( ) 하지 말고 따로 분류 칸을 만들어서 이름 + 분류 조합으로 unique하게 하는게 어떨까 해" (2026-10-11)
- "각 전자도서관마다 분류를 꼭 했으면 해 어떤 것만 따로 분류 ( ) 안에 붙는게 이상해서" (2026-10-11)
- 순번: "겹치면 1, 2, 3 이렇게 순서 따로 붙이는 거 안 되나" (2026-10-11), 따로 된 칸은 제안 → 승인
- 수집 DB 이름도 바꿈: 다른 선택으로 낸 것을 사용자가 고름 ("이렇게 가자", 2026-10-11)
- 업체를 도서관 수집이 정함(DB가 화면 종류에서 계산하는 안은 미승인): "이게 나은 것 같으데 수집 스크립트가 하는게... 역할 분리를 잘 따져봐야 할 것 같아", 미승인 이유 "역할 분리" (2026-10-11)
- 결과 카드는 이름 다음 줄: "검색 결과 카드에서는 공통으로 도서관 이름 있고 개행 하고 교보 소장 이런거 보이도록 하는 걸 어떻가 해" (2026-10-11)
- 통합 포털 대출 방식 비워 둠, 이름 유지 규칙, 업체 묶기, 대출 방식 채우는 규칙: 제안 → 승인 (2026-10-11)

## 검토한 대안
### A안: 이름 + 업체·대출 방식 분류, 조합 UNIQUE (채택)
- 장점: 모든 도서관이 같은 방식으로 분류됨, 화면에서 업체·방식이 늘 보임, 이미 있는 칸을 씀
- 단점: 이름 277곳을 고침, 대출 방식이 없는 도서관을 채워야 함, seed 생성 스크립트의 이름 규칙과 테스트를 고침
### B안: 글로 적는 "분류" 칸 하나 (예 "교보 구독")
- 장점: 단순함
- 단점: 적는 방식이 다시 제각각이 될 수 있음
- 채택하지 않은 이유: [이유 미확인] (사용자가 A안을 승인)
### C안: 지금 괄호 규칙 유지, 앞으로만 새 규칙
- 장점: 이미 넣은 이름을 고치지 않음
- 단점: 화면에 두 방식이 섞임
- 채택하지 않은 이유: [이유 미확인]
### F안: 업체는 DB가 화면 종류에서 계산 (생성 칸)
- 장점: 화면 종류와 업체가 어긋날 수 없음
- 단점: 새 업체·새 화면마다 DB 계산식을 고침, 한 화면 종류를 두 업체가 쓰면 나눌 수 없음
- 채택하지 않은 이유: "역할 분리" (사용자, 2026-10-11)
### D안: 겹치면 이름 뒤에 숫자 ("부여대왕초등학교 2")
- 장점: 새 칸이 없음
- 단점: 이름에 기관 이름이 아닌 것이 다시 들어감
- 채택하지 않은 이유: [이유 미확인] (사용자가 미승인, 2026-10-11)
### E안: 겹치면 seed 생성 스크립트가 멈추고 알림
- 장점: 사람이 매번 확인함
- 단점: 스크립트가 멈춤
- 채택하지 않은 이유: 사용자가 미승인하고 순번을 제안 ("겹치면 1, 2, 3 이렇게 순서 따로 붙이는 거 안 되나", 2026-10-11)

## 결과
- 좋아지는 점: 같은 이름의 사이트를 화면에서 구분할 수 있음. 도서관 번호는 그대로라 내 도서관·로그인 계정에 영향 없음(dev 코드 확인, 2026-10-11)
- 감수하는 점: S10 이름 찾기가 분류 글자도 찾게 바뀜. 지금 "(구독)"으로 보이던 교보 8곳은 "대여"로 보임. 순번만으로는 이용자가 어느 사이트인지 알 수 없어 이름 확인을 다음 할 일로 남김
- 검색·소장 판정 동작은 바뀌지 않음(대출 방식으로 동작이 갈리는 곳은 교보 구독형의 "소장" 하나이고, 이번에 소장으로 바꾸는 교보 구독형은 없음)
- 나중에 분리할 때: 해당 없음
