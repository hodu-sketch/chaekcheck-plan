# ADR-0014: 묶음 단위 검색 API, 도서관 순서 목록은 브라우저가 가짐

Status: Accepted
Date: 2026-09-28
Cycle: 02-library-expansion
Supersedes: 0005

## 배경
ADR-0005의 스트림은 대상 도서관 전부를 한 번에 조회한다. 사이클 02는 수백 곳 중 순위대로 약 20줄이 찰 때까지만 조회하고, 목록 맨 아래 "더 보기"로 다음 도서관을 이어서 조회하며(라운드 로빈), 이미 본 결과의 위치는 바꾸지 않는다 (spec.md 5.3). 어디까지 조회했는지를 둘 곳이 필요하다. 경북·전북 포털은 대출 중인 책의 판정을 상세 페이지에서만 얻을 수 있고(research.md 12절 근거 5), 같은 호스트라 1초 간격이 걸린다.

## 결정
- 첫 검색은 SSE 스트림 하나다. 서버가 정렬된 **전체 조회 계획**(사이트 순서와 우선순위 그룹)을 먼저 보내고, 첫 묶음을 실행한다.
- 브라우저가 계획과 사이트별 진행 상태(다음 쪽, 더 있음, 실패)를 가진다. 목록 맨 아래 "더 보기" 때 브라우저가 다음 후보 `siteId:page` 목록을 보내고, 서버는 그 순서로 한 묶음만 실행한다. 서버는 검색 상태를 저장하지 않는다.
- 도서관별 "더 보기"는 사이트 한 곳의 다음 쪽 GET API로 하고, 결과는 목록 맨 아래 새 묶음으로 붙인다.
- 한 묶음 안에서 조회에 실패한 사이트는 같은 검색의 이후 "더 보기"에서 다시 조회하지 않는다.
- 경북·전북처럼 판정을 상세 페이지에서 읽어야 하는 줄은 먼저 "대출 정보 조회 중"으로 보내고, 판정을 읽으면(최대 30초) 그 줄의 판정을 다시 보낸다. 브라우저는 그 줄을 **같은 묶음 안에서만** 알맞은 칸으로 옮긴다. 30초 안에 못 읽으면 "대출 가능 여부 확인 필요".
- 줄마다 대출 가능 여부 판정은 서버가 계산한다. 칸 안의 정렬은 프론트가 한다 (ADR-0005와 같음).

## 이유 (사용자 발언)
- 브라우저가 계획을 가짐: [이유 미확인] (추천안 선택, 2026-09-28)
- 실패한 사이트를 다시 조회하지 않음: [이유 미확인] (추천안 선택, 2026-09-28)
- 경북·전북 상세 판정: "2로 하되 묶음에서 먼저 보여줄 건 보여주고 해당 도서관의 책들 대출 정보만 조회 중으로 했다가 완료가 되면 위치 바꾸는 건?" (2026-09-28). 최대 30초는 사용자 선택, 이유 [이유 미확인]

## 검토한 대안
### A안: 브라우저가 계획을 가짐 (채택)
- 장점: 서버 재시작에도 "더 보기"가 끊기지 않음. 계획이 첫 응답의 스냅숏이라 위치가 밀리지 않음. 서버를 상태 없이 늘릴 수 있음
- 단점: 라운드 로빈 계산이 프론트에 있음. 첫 응답에 수백 곳의 계획이 실림
### B안: 서버 메모리에 검색 세션
- 장점: 브라우저가 단순함
- 단점: 재시작·만료 때 "더 보기" 실패. 본 서비스 1대 전제가 늘어남
- 채택하지 않은 이유: [이유 미확인]
### C안: 위치를 담은 토큰을 주고받음
- 장점: 서버 상태 없음
- 단점: 요청 사이에 계획이 바뀌면 결과가 빠지거나 겹침. 도서관별 더 보기와 얽힘
- 채택하지 않은 이유: [이유 미확인]
### 경북·전북 상세 판정의 다른 안
- 8초 안에 못 읽은 줄은 "확인 필요"로 둠 / 상세 없이 대출 중이면 예약 칸
- 채택하지 않은 이유: 사용자가 위 방식을 제안함

## 결과
- 좋아지는 점: 도서관 수와 상관없이 첫 결과가 빨리 나옴. 조회는 필요한 만큼만
- 감수하는 점: "이미 본 줄 위치 유지"(spec 5.3)의 예외가 생김 (상세 판정 줄은 같은 묶음 안에서 옮김). 스트림이 묶음 8초 뒤에도 상세 판정 때문에 최대 30초 열려 있음
- 되돌리는 비용: 낮음 (묶음 실행기는 다른 안에서도 그대로 씀)
