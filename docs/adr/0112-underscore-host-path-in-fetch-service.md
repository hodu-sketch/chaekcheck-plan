# ADR-0112: 밑줄 호스트 요청 길을 조회 서버 앱에도 넣는다

Status: Accepted
Date: 2026-10-14
Cycle: 18-empty-library-holdings
Supersedes: 없음

## 배경
ADR-0111은 호스트에 밑줄이 있는 도서관 주소를 `collection`은 따로 읽고, `availability`(대출 조회·직접 찾기)는 따로 만든 요청 길로 보내기로 했다. 대출 조회는 본 서비스가 직접 할 수도 있고, 따로 도는 조회 서버 앱(`fetch-service`, ADR-0011·0015)을 거칠 수도 있다. 조회 서버 앱의 주소 검사 `UrlGuard`는 `getHost()`가 없으면 거절하고, 요청은 Java 기본 요청 기능으로 보낸다. 사이클 17 첫 배포에서는 조회 서버를 꺼 둔다.

## 결정
조회 서버 앱에도 같은 밑줄 길을 넣는다. `UrlGuard`는 밑줄 호스트를 읽되, `LibraryClient`가 실제로 연결할 이름과 같은 이름으로 DNS를 풀어 사설·내부 주소면 거부하고, 사용자 정보가 든 주소 거부도 그대로 둔다. `LibraryClient`는 밑줄 호스트를 본 서비스와 같은 요청 라이브러리·같은 조건(SNI 없이, 인증서 이름 검사 켬, 같은 제한)으로 보낸다. 의존성은 앱마다 하나.

## 이유 (사용자 발언)
- "같이 해 굳이 왜 나눠서 해 조회 서버도 같이 해" (2026-10-14, "직접 조회에만" 안 미승인)
- 내부망 막기 유지는 지금 보호를 그대로 두는 것 (설계 검토 2차)

## 검토한 대안
### A안: 직접 조회에만 넣고, 조회 서버 모드에서는 그 줄만 실패
- 장점: 따로 도는 앱을 고치지 않음
- 단점: 조회 서버를 켜면 밑줄 주소 도서관은 조회가 안 됨
- 채택하지 않은 이유: 위 사용자 발언
### B안: 조회 서버 앱에도 같은 길 (채택)
- 장점: 어느 방식으로 조회해도 같게 동작
- 단점: 앱이 하나 더 바뀌고 의존성이 앱마다 하나, `UrlGuard` 보안 검사를 고침(시험으로 내부망 막기 확인)

## 결과
- dev `fetch-service/`의 `UrlGuard`·`LibraryClient`, 별도 Gradle 빌드·시험
- ADR-0111을 보완 (대체 아님)

## 나중에 분리할 때
- 조회 서버는 이미 따로 도는 앱이라 그대로 따라감
