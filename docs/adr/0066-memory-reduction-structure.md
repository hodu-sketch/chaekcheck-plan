# ADR-0066: 메모리를 줄이는 구조 — 먼저 재고, 읽지 않을 것은 읽지 않는다

Status: Accepted
Date: 2026-10-11
Cycle: 08-polish-swap-memory
Supersedes: 없음 (ADR-0004·ADR-0006 그대로, ADR-0006의 상한 값은 측정 뒤 바뀌면 새 기록)

## 배경
DB는 9.8GB이고 소장 표의 같은 책 줄이 흩어져 있다(`docs/research/deploy/db-memory.md`). 서비스는 검색 계획을 만들 때마다 도서관 2,674곳을 다 읽고 약 385곳만 남기며, 책 화면 소장도 모든 도서관 줄을 읽은 뒤 앱에서 거른다. 캐시 둘은 개수(1,000건)로만 막혀 실제 크기·적중률을 모른다. Java 힙·DB 메모리 설정이 없고, 재는 도구(Actuator)도 없다(`research.md` 9절).

## 결정
- 검색 계획은 들어갈 수 있는 도서관(가입 조사됨·안내 못 찾음 + 직접 추가)만 DB에서 읽는다. 켜짐 여부는 요청마다 읽는다(ADR-0004 그대로)
- 책 화면 소장 읽기는 계획에 든 도서관 줄만 DB에서 읽는다(`CatalogHoldings`에 도서관 번호를 받는 읽기를 더함). 가져오기용 색인과 원문 칸은 남긴다
- 두 캐시는 통계를 켜고 캐시마다 상한 설정을 나눈 뒤, 잰 값으로 상한을 정한다
- 재는 도구는 더하지 않는다: `jcmd`, 캐시 통계 로그, PostgreSQL 통계·`EXPLAIN (ANALYZE, BUFFERS)`
- DB 메모리 값은 Docker 실행 설정(`compose.yaml`)에 두고, 가져오는 동안에만 정렬·색인 메모리를 올린다. Java 힙 상한은 실행 설정에 둔다
- 도서관 응답 본문 복사를 이번에 줄인다
- 최적점: 검색 첫 쪽 1초 안, 줄이기 전보다 20% 넘게 느려지기 직전 단계

## 이유 (사용자 발언)
- "DB메모리도 어떻게 해야 최적인가(너무 메모리에 맞춰서 줄였다가 느려지면 또 그건 별로니까) 찾아보자", "물론 DB메모리도 줄이고 캐시 메모리도 줄이고" (2026-10-05)
- 응답 복사: "비효율적이고 고칠 수 있으면 지금 고치는게 나아" (2026-10-11)
- 나머지: 제안 → 승인 (2026-10-10~11, 설계 결정 #5~9)

## 검토한 대안
### A안: 위 결정 (채택)
- 장점: 예전 결정을 바꾸지 않고 읽는 양·메모리가 함께 줄어듦, 새 의존성 없음
- 단점: 캐시 상한 값은 측정 뒤에야 정해짐
### B안: 도서관 목록을 30초 메모리에 기억
- 장점: DB 읽기가 거의 없어짐
- 단점: 끈 도서관이 최대 30초 늦게 반영, ADR-0004를 바꿔야 함
- 채택하지 않은 이유: [이유 미확인]
### C안: 캐시를 크기(무게)로 상한
- 단점: 비동기 캐시에서 무게 계산 방식 확인 못 함, 크기가 들쭉날쭉하다는 근거 없음
- 채택하지 않은 이유: [이유 미확인]
### D안: 측정 때만 Actuator
- 단점: 의존성·관리 포트가 생김
- 채택하지 않은 이유: [이유 미확인]
### E안: 응답 복사는 측정에서 보일 때만
- 채택하지 않은 이유: "비효율적이고 고칠 수 있으면 지금 고치는게 나아" (2026-10-11)

## 결과
- 운영 서버가 정해지면 같은 방법으로 다시 잰다
- 서버가 여러 대가 되면 캐시는 ADR-0006대로 Redis를 다시 본다
