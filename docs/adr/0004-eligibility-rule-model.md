# ADR-0004: 자격 규칙 모델과 도서관 사용 여부

Status: Superseded by 0013
Date: 2026-09-27
Cycle: 01-ebook-availability-search
Supersedes: 없음

## 배경
도서관마다 가입 자격이 다르다 (강서구: 서울 거주·재직·재학, 고흥군: 누구나 가입). 다음 사이클에는 재학(학교 지역)과 소속(대학·회사 전자도서관) 자격이 들어와야 하는데, 이번 사이클에는 그 입력과 도서관이 없다. 모듈 간 FK는 두지 않는다.

## 결정
- 자격 규칙 한 행 = 근거(`RESIDENCE | WORK | SCHOOL | AFFILIATION`) × 범위(`REGION | INSTITUTION`).
- 범위 참조는 `scope_region_id`, `scope_institution_id` 두 nullable 컬럼이고, CHECK로 둘 중 하나만 값이 있게 한다. `institution` 테이블은 만들지 않는다.
- 가입 조건 종류(누구나 가입 / 자격 필요)는 저장하지 않고 규칙 유무로 계산한다.
- 도서관 사용 여부는 `library.enabled` 컬럼이고 요청마다 DB에서 읽는다. 운영자가 SQL로 바꾼다.

## 이유 (사용자 발언)
- 구조 확장: "직장, 학교별 도서관도 가능해야 해 이걸 염두하고 만들어 줘"
- 사용 여부를 운영용으로 유지: 사용자가 "운영용으로 유지"를 선택 (2026-09-27)
- 기관을 nullable 참조로만 두는 것, 규칙 유무로 계산, SQL로 변경: [이유 미확인] (추천안 채택. 설명을 들은 뒤 "초안대로 가줘")

## 검토한 대안
### A안: 규칙 여러 행 + nullable 기관 참조 (채택)
- 장점: 다음 사이클에 규칙 테이블을 바꾸지 않고 행만 추가
- 단점: FK가 없어 없는 ID가 들어갈 수 있음 → 공개 API로 확인
### B안: 도서관 테이블에 종류·자격 지역 칸만
- 단점: 여러 근거나 여러 지역을 담기 어려움
- 채택하지 않은 이유: [이유 미확인]
### C안: 빈 institution 테이블을 지금 생성
- 단점: 쓰지 않는 테이블, 소유 모듈을 미리 정해야 함
- 채택하지 않은 이유: [이유 미확인]
### D안: scope_ref_id 한 컬럼 (다형 참조)
- 단점: 컬럼 뜻이 행마다 달라 검증이 약함
- 채택하지 않은 이유: [이유 미확인]
### E안: join_policy 컬럼 명시
- 장점: 규칙을 실수로 지워도 종류가 바뀌지 않음
- 단점: 같은 사실이 두 곳에 저장됨
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 재학·소속 자격을 스키마 변경 없이 추가
- 감수하는 점: 이번 사이클에는 INSTITUTION 행을 넣지 않음. 사용 여부 변경은 DB 접근 권한이 있는 사람만 가능
- 나중에 서비스로 분리할 때: 기관을 가진 모듈이 정해지면 그 공개 API로 ID를 확인
