# ADR-0105: 책 묶는 방식 셋(compact·objects·sql)을 모두 남기고 기본은 compact로 한다

Status: Accepted
Date: 2026-10-14
Cycle: 11-separate-import (최종 회고), 12-grouping-rules
Supersedes: 없음 (ADR-0079 덧붙임(2026-10-12)의 "current는 사이클 12에서 지우고 compact·sql만 남긴다"와 "측정 뒤 기본값을 다음 사이클에서 바꾼다"를 바꿈. ADR-0079 본문(세 방식의 결과가 번호까지 같아야 쓴다)은 그대로)

## 배경
사이클 11 측정(2026-10-12, 같은 새 사본, 실행 23번)에서 세 방식 모두 결과가 번호까지 같았고, 끝까지 된 가장 작은 힙은 sql 1GB(약 34분, 실행마다 DB 임시 쓰기 약 61GB) < compact 2GB(약 21분) < current+Java 옵션 4GB < current 6GB였다(dev `docs/plan-feedback.md` 3022~3081행). R-B7 기준을 그대로 적용한 dev 추천은 sql. ADR-0079 덧붙임은 사이클 12에서 current를 지우기로 했다. 이 결정은 2026-10-12에 dev 세션에서 사용자가 정했고, 2026-10-14 회고에서 ADR로 기록했다.

## 결정
- 설정 `chaekcheck.collection.import.grouping`의 기본값을 `compact`로 한다 (사이클 11에서 바꿈)
- 세 방식을 모두 남겨 설정으로 고른다. 옛 방식 이름 `current`를 `objects`로 바꾼다(클래스 `BookGrouping`은 그대로, 설정 값 `current`는 시작 전에 거절)
- 묶기 규칙을 바꿀 때는 세 방식 모두에 넣고, 세 방식의 결과가 번호까지 같은지 비교한다 (사이클 12에서 그렇게 함, AC-6 세 방식 차이 0)
- `objects`를 쓸 때는 `-PbootRunXmx=8g` (사이클 12 규칙 뒤 살아 있는 데이터 약 5,751MB)

## 이유 (사용자 발언)
- "기본 방식은 compact로 해줘 그리고 sql이나 다른 방법들도 구현에 남겨둬 선택해서 할 수 있게 해줘" (2026-10-12)
- "옛 방식 이름을 current가 아니라 다른 걸로 해야 할 것 같은데 normal이라던가 아니면 날짜를 붙이던가" → 선택지 objects / normal / v2026-10 / classic 중 objects (2026-10-12)
- R-B7 기준의 결과(sql) 대신 compact를 고른 까닭은 [이유 미확인] (결정 전에 dev가 보인 맞바꿈: compact 힙 2GB·약 21분·DB 부담은 옛 방식과 같음, sql 힙 1GB·약 34분·실행마다 DB 임시 쓰기 약 61GB)
- ADR로 기록·확정: 초안 승인 (2026-10-14, 회고 결정 #8)

## 검토한 대안
### A안: 기본 compact, 셋 모두 남김 (채택)
- 장점: 가장 빠름, DB 부담 그대로, 다른 방식으로 바로 돌아갈 수 있음
- 단점: 규칙을 바꿀 때 세 곳을 고치고 비교해야 함
### B안: R-B7 그대로 기본 sql
- 장점: 힙 1GB
- 단점: DB 임시 쓰기 약 61GB·DB 최대 약 27GB, 가장 느림, 규칙 고칠 곳이 가장 많음
- 채택하지 않은 이유: [이유 미확인]
### C안: ADR-0079 덧붙임대로 current 지움
- 장점: 묶기 코드가 둘로 줄어듦
- 단점: 옛 방식으로 돌아갈 수 없음
- 채택하지 않은 이유: "sql이나 다른 방법들도 구현에 남겨둬 선택해서 할 수 있게 해줘" (2026-10-12)

## 결과
- 좋아지는 점: 가져오기 힙 6GB → 2GB, 시간 약 5분 줄어듦
- 감수하는 점: 묶기 코드 셋 유지, 시험(계약·무작위 대조) 셋 유지
- 나중에 서비스로 분리할 때: 가져오기는 `collection` 안이라 그대로 함께 감
