# ADR-0134: 이용 기록에 회원 번호(로그인한 경우)와 방문 번호(탭 단위 난수)를 남긴다 — AI 추천용, ADR-0096의 "회원 번호 안 남김·기록끼리 잇는 칸 없음"을 바꿈

Status: Accepted (2026-10-18, 사용자 승인 — 방향: AI 추천 결정 페이지 1차 #8·2차 #2; 세부(표·칸·흐름·바꿀 곳·문구·시점): `docs/research/ai-recommend/easy/2026-10-18-logging-change-decisions.html` #1~#7 모두 승인)
Date: 2026-10-18
Cycle: 없음 (사이클 밖 조사 `docs/research/ai-recommend/`, dev 전달은 사이클 20 인계서에 덧붙임)
Supersedes: [ADR-0096](0096-usage-log-storage-and-fields.md)의 두 문장 — "회원 번호·쿠키·User-Agent는 남기지 않는다", "기록끼리 잇는 칸 없음"(spec R2-6). 나머지(저장 장소, IP 30일, 1년, 04:30 정리)는 그대로.

## 배경
AI 도서 추천을 하려면 (가) "이 책을 본 방문에서 같이 본 책"을 세려고 기록끼리 이을 칸이, (나) 로그인한 회원에게 맞춘 추천을 하려고 회원이 연 책·누른 도서관이 필요하다. 사이클 15 기록은 둘 다 없다(ADR-0096). 처음에는 회원 기록을 별도 표에 두는 안을 냈으나 사용자가 "아직 외부 배포 전이라서 괜찮지 않나 / 기록 표에 회원번호 넣기"(2026-10-17)라고 해 기록 표에 넣는 안으로 바꿔 승인받았다(2026-10-18). 공개 배포 전이라 바꾸는 비용이 지금 가장 작다.

## 결정
- `usagelog.book_view`·`library_click`·`screen_event`에 두 칸을 더한다: `account_id bigint NULL CHECK (> 0)`(로그인한 회원만, 아니면 NULL, FK 없음), `visit_key text NULL CHECK (길이 16~64, 영숫자)`(브라우저 탭을 열 때 `sessionStorage`에 만든 32자 난수, 탭을 닫으면 사라짐, 쿠키 아님; 책 상세 GET은 헤더 `X-Visit-Key`, 사용 알림 POST는 본문 `visitKey`; 형식이 틀리면 NULL, 거절하지 않음). 색인 없음. 회원 번호는 `auth`의 `LoginStatusReader`가 로그인함일 때 함께 돌려준다(쿠키 서명이 맞으면 만료돼도). Liquibase `usagelog/005`, 사이클 20 1단계(사이클 17 배포 앞)에 같이. `search_event`에는 둘 다 넣지 않는다(검색어는 민감할 수 있고 추천에 필요 없음).
- 회원 번호는 회원 번호와 방문 번호를 서로 잇는 데만 쓰고, 통계 SQL은 `account_id`를 읽지 않는다. 같이 본 책 계산은 `client_ip`를 읽지 않는다.
- 탈퇴(`AccountDeleted`)하면 `usagelog`가 그 회원의 `account_id`를 NULL로 비운다(줄은 남겨 익명 통계 유지). 회원 설정 "맞춤 추천 끄기"(AI 추천 3단계 사이클에서 만듦)를 끄면 그 뒤로 NULL로 저장하고 있던 줄도 NULL로 비운다. 설정이 생기기 전에는 로그인한 회원 모두 저장한다.
- 보관은 ADR-0096 그대로(IP 30일, 나머지 1년). 회원 번호는 탈퇴·끄기 때 바로 비움.
- 처리방침 1절 "자동으로 수집되는 정보"를 "IP 주소, 브라우저 종류, 접속 기록, 서비스 이용 기록(로그인한 경우 회원 번호 포함), 부정 이용 기록", 목적 "이용 통계, 운영과 보안, 책 추천", 보유 기간 줄에 "회원 번호는 탈퇴하면 바로 지움"으로 한다(사용자: 짧은 판 승인, 2026-10-18; 방문 묶음 설명은 적지 않음 — 식별하지 않는 처리는 권장 사항). 교보·카카오·알라딘 처리방침의 자동 수집 항목은 이보다 길다(2026-10-18 확인, 결정 페이지 5번 답).

## 이유 (사용자 발언)
- 기록 표에 넣기: "아직 외부 배포 전이라서 괜찮지 않나", "기록 표에 회원번호 넣기" (2026-10-17)
- 방문 번호·쿠키 안 씀·검색 기록 제외·탈퇴 때 비움: 제안 → 승인 (2026-10-18) [이유 미확인]
- 지금 바로 dev에 전하기: "지금 별개로 배포 전이니가 20 dev에게 ai활용을 위한 로깅 정책을 바뀐다고 전해줬으면 해 저장하는 것이랑 다 바꾸고 수정하자고" (2026-10-18)

## 검토한 대안
### A안: 별도 추천 표 (회원 번호·책·종류·시각), 기록 표는 그대로
- 장점: 익명 통계 표에 식별자가 안 들어감, 탈퇴 때 줄 삭제로 끝
- 단점: 표 하나 더, 같이 본 책 계산에 두 표를 맞춰야 함
- 채택하지 않은 이유: "기록 표에 회원번호 넣기" (사용자, 2026-10-17)
### B안: 기록 표에 회원 번호·방문 번호 (채택)
### C안: 쿠키로 방문 번호
- 장점: 며칠에 걸친 방문을 이음
- 단점: 처리방침에 자동 수집 장치 절 필수(개인정보 보호법 제30조①7호 [확정], `docs/research/ai-recommend/law.md` 3절), 광고 차단기가 막음
- 채택하지 않은 이유: 제안(안 씀) → 승인 [이유 미확인]

## 결과
- 좋아지는 점: 같이 본 책·회원 맞춤 추천의 재료가 공개 첫날부터 쌓임
- 감수하는 점: 익명 통계 표에 회원 번호가 들어가 통계 SQL이 그 칸을 읽지 않도록 지켜야 함. 처리방침 문구 변경. 탭 난수는 같은 사람이 탭을 새로 열면 다른 방문으로 셈
- 법 (law.md, 2026-10-17 확인): 회원 맞춤 추천은 약관에 서비스 내용으로 적고 처리방침에 공개하면 별도 동의 없이 가능(개인정보위 통합 안내서 FAQ p.129, 제15조①4호) [확정]; 작성지침은 식별하여 행태정보를 처리하면 근거·항목·방법·목적·기간·거부 방법을 적으라 함 [확정] → 거부 방법 = 끄기 설정(3단계). 자동화된 결정 절은 불필요(안내서가 상품·콘텐츠 추천을 제외) [확정]
- 나중에 분리할 때: 추천 계산은 PC 배치이므로 기록 표만 읽음. 식별자를 다시 빼려면 두 칸을 NULL로 비우는 작업 하나
