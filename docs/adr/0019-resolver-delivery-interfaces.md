# ADR-0019: 판정 방식과 SSE 전달을 인터페이스로 분리

Status: Accepted
Date: 2026-09-28
Cycle: 02-library-expansion
Supersedes: 없음

## 배경
ADR-0014는 경북·전북처럼 검색 목록에 판정이 비어 있는 포털에서 대출 중인 책의 판정을 상세 페이지로 읽고(최대 30초), 먼저 "대출 정보 조회 중"으로 보낸 뒤 판정을 나중에 보내기로 했다. 이 처리를 묶음 실행기나 화면 코드에 특정 도서관 종류의 분기로 넣으면, 대기 시간 규칙이 여러 곳에 흩어진다. 또한 ADR-0014·0015 본문은 ADR-0017 이전에 쓰여 도서관 식별자를 `siteId`로 적고 있다.

## 결정
- 줄의 대출 가능 여부를 정하는 일을 인터페이스(이름 [안] `AvailabilityResolver`)로 두고 플랫폼 유형마다 구현을 고른다: 수량 계산, 포털 목록 판정, 상세 조회(추가 요청·30초 마감·실패 시 `UNKNOWN`을 구현이 가짐), 구독형.
- SSE로 언제 무엇을 보낼지를 인터페이스(이름 [안] `SiteResultDelivery`)로 두고 구현 둘을 둔다: 한 번에 전달(`library-result` 한 번), 나눠서 전달(`library-result` 뒤 `row-verdict`). 판정이 나중에 정해지는 줄이 있으면 나눠서 전달을 쓴다.
- 묶음 실행기는 "이 도서관의 전달이 끝났는가"만 기다리고, 도서관 종류나 대기 시간을 알지 못한다.
- 웹은 도서관 종류를 보지 않고 줄 상태(`PENDING`)와 이벤트 종류만 본다. 조회 중 줄의 자리와 판정 뒤 칸 이동은 목록 코드와 떨어진 한곳에서 처리한다.
- 식별자: ADR-0014·0015 본문의 `siteId`는 ADR-0017 이후 `libraryId`로 읽는다 (`candidates=libraryId:page`, 이벤트 `library-*`). 기준 문서는 사이클 02 `design-delta.md`다.

## 이유 (사용자 발언)
- "특정 종류의 도서관을 대기시간 로직을 다르게한게 좀 걸리긴 해 이것도 좀 인터페이스인데 구현을 다르게 하는 식으로 분리되게 개발하도록" (2026-09-28)
- "나는 프론트에 sse로 정보주고 보여주는거말했는뎅" (2026-09-28) → 서버 전달과 프론트 처리를 둘 다 분리하는 안을 선택
- 식별자 정리: 설계 검토(design-reviewer)에서 지적, 사용자가 "전부 반영" 선택 (2026-09-28)

## 검토한 대안
### A안: 서버 전달 + 프론트 처리 둘 다 분리, 판정 방식은 별도 (채택)
- 장점: 새 화면 종류가 추가 조회를 필요로 해도 구현만 더함. 묶음 실행기와 화면은 고치지 않음
- 단점: 인터페이스가 둘로 늘어남
### B안: 서버 전달만 분리
- 단점: 프론트 목록 코드에 PENDING 줄 처리가 섞임
- 채택하지 않은 이유: [이유 미확인]
### C안: 판정 방식과 전달을 한 인터페이스로
- 단점: 한 인터페이스가 판정과 전달 두 가지 일을 함
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 경북·전북 특수 처리가 두 구현(상세 조회 판정, 나눠서 전달) 안에만 있음
- 감수하는 점: 구현을 고르는 규칙(플랫폼 유형 → 판정 방식, PENDING 유무 → 전달 방식)을 테스트로 지켜야 함
- 나중에 분리할 때: 조회 쪽을 서비스로 떼어도 두 인터페이스는 본 서비스에 남음
