# ADR-0044: 앱 전체의 보안 설정은 auth 모듈이 가지고, 보호하는 주소는 /api/v1/me 아래뿐

Status: Accepted
Date: 2026-10-04
Cycle: 05-login-account
Supersedes: 없음

## 배경
Spring Security를 넣으면 앱 전체 요청이 보안 필터를 거친다. 어느 주소가 로그인이 필요한지, 401·403을 어떤 모양으로 답할지를 어느 모듈이 가질지 정해야 했다. 다른 모듈은 `auth`에 의존하지 않기로 했다(ADR-0036, AC-18).

## 결정
`auth` 모듈이 앱 전체의 `SecurityFilterChain`을 가진다. 보호하는 주소는 `/api/v1/me/**`뿐이고 나머지는 모두 열어 둔다(`permitAll`). 다른 모듈의 주소는 문자열 규칙으로만 다뤄 모듈 의존을 만들지 않는다. 보안 필터 단계의 401·403은 `auth`의 `AuthenticationEntryPoint`·`AccessDeniedHandler`가 ProblemDetail(`code`)로 직접 쓴다. form login, HTTP Basic, 자동 생성 사용자는 끈다.

## 검토한 대안
### A안: 앱 전체의 보안 설정은 auth 모듈이 가지고, 보호하는 주소는 /api/v1/me 아래뿐 (채택)
- 장점 / 단점: "결과" 절 참고
### B안: 공용(루트) 패키지에 보안 설정을 둠
- 장점: `auth`가 다른 모듈의 주소를 몰라도 됨
- 채택하지 않은 이유: [이유 미확인]
### C안: 모듈마다 자기 주소의 보안 규칙을 가짐
- 장점: 모듈이 자기 주소를 스스로 지킴
- 채택하지 않은 이유: [이유 미확인] (모듈이 `auth`나 보안 설정에 의존하게 됨)

## 결과
- 좋아지는 점: 기존 모듈은 보안을 모르고 바뀌지 않음. 사이클 06의 `member`는 주소를 `/api/v1/me/...` 아래에 두기만 하면 보호됨
- 감수하는 점: 로그인이 필요한 주소를 `/api/v1/me` 밖에 만들면 보호되지 않으므로, 그런 주소가 필요해지면 이 결정을 다시 봐야 함. Spring Security가 모든 응답에 보안 헤더를 붙여 기존 API 응답의 헤더가 늘어남
- 되돌리는 비용: 규칙을 옮기는 정도. 나중에 분리할 때 보호 규칙은 그 서비스나 앞단으로 감
