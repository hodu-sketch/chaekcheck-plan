# ADR-0086: 반영 파일 판 2 — 새 도서관을 `load_manifest` 설명 줄에 싣고, 운영은 도서관 → 비교 → 책 순서로

Status: Accepted
Date: 2026-10-12
Cycle: 13-crawler-to-dev
Supersedes: 없음 (ADR-0078을 이어서: 파일 하나·비교·바꿔 끼우기는 그대로)

> **미리 정함**: 사이클 13은 사이클 12(책 묶기 기준)가 끝나기 전에 나란히 진행해 정한 결정이다. dev에는 사이클 12 handoff 뒤에 넘긴다.

## 배경
사이클 11(ADR-0078)은 내 PC에서 가져와 파일 하나로 운영에 옮기고, 운영에서 도서관 목록·`collection_link` 해시가 같을 때만 바꿔 끼운다. 사이클 13은 도서관을 내 PC에서 넣으므로(ADR-0084), 운영에도 같은 도서관이 먼저 들어가야 해시가 맞는다. dev 확인으로 `load_manifest` 줄은 이미 표 COMMENT에 `row_to_json`으로 들어가고(`Manifests.create`), 판이 다르면 거절한다(`FORMAT_VERSION = 1`) (`research.md` 4-1). COMMENT는 text라 약 1GB까지 들어간다(`research.md` 7-2).

## 결정
- 반영 파일 판을 2로 올린다. 판 1 앱은 판 2 파일을 반영하지 않는다
- export는 성공한 넣기 실행 기록을 모두 `load_manifest.notes.libraryPart`에 싣는다(도서관·가입 규칙·짝 줄) [안: 키 이름]
- apply는 한 트랜잭션에서 도서관 부분 넣기(이미 있는 줄은 건너뜀) → 지문 비교 → 다르면 되돌리고 `mismatch`, 같으면 커밋 → 복원·색인·바꿔 끼우기(ADR-0078 그대로)
- 도서관 부분 넣기가 실패하면 반영을 시작하지 않는다
- 새 표를 만들지 않으므로 "바꿔 끼우기 전에 지움"은 `load_manifest` 지우기로 끝난다

## 이유 (사용자 발언)
- 운영에 반영 파일로 함께 싣고 "도서관 → 짝 표 → 책" 순서: 사전 결정 6 승인 (2026-10-12)
- 표 COMMENT에 싣기, 도서관 부분이 실패하면 반영하지 않음: 사용자 승인 (2026-10-12, spec R3-4·flow I2)
- `notes`에 싣는 A안: 추천안을 고름 (2026-10-12, 설계 결정 3). 고른 이유는 [이유 미확인]

## 검토한 대안
### A안: 기존 `load_manifest.notes`에 `libraryPart` (채택)
- 장점: 새 표가 없음, `catalog`는 판 번호만 바꿈, 목차만 읽어 빠름
- 단점: COMMENT 한 줄이 길어짐(`Manifests.parse`가 맞게 읽는지 시험 필요)
### B안: `catalog_next.library_part` 표 + COMMENT
- 장점: 줄 단위로 다루기 쉬움
- 단점: `collection`이 `catalog` 스키마에 표를 만들어 모듈 경계를 어김
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 운영에서도 앱 재시작 없이 내 PC와 같은 번호로 도서관이 들어가고, 사이클 11 비교가 그대로 지켜 줌
- 감수하는 점: 판 2를 배포할 때 내 PC에 판 1 내보내기가 기다리고 있으면 `finish`가 거절됨(배포 전에 끝내야 함)
- 나중에 되돌리거나 서비스로 분리할 때의 비용: 중간. 나중에 분리할 때 도서관 반영은 `library` 쪽 API 호출로 따로 떼야 함
