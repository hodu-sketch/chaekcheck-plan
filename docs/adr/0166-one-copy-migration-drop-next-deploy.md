# ADR-0166: 책 설명 옮기기는 한 번의 배포에서 복사하고, 옛 표는 다음 배포에서 지움

Status: Accepted
Date: 2026-10-28
Cycle: 26-book-descriptions
Supersedes: 없음

## 배경
사이클 26은 `foryou.book_blurb`·`book_cover`, `picks.book_tag`·`tag_dictionary`·`cover`, `aisearch.search_book`의 내용을 `catalog`의 새 표로 옮긴다(ADR-0161·0163·0165). 옮기는 동안 화면의 요약·표지가 빠지지 않아야 하고, 잘못되면 되돌릴 수 있어야 한다. dev 제안(2026-10-27)은 "새 표 → 양쪽에서 읽기 → 옛 표 지우기" 세 단계였다.

## 결정
- 배포 1: Liquibase `catalog/002-book-descriptions.yaml`이 새 표를 만들고 옛 표 내용을 그대로 한 번 복사하며, 같은 배포에서 읽는 곳을 모두 새 표로 바꾼다. 줄 수를 옛 표와 비교한다(AC-4)
- 배포 2: 배포 1이 문제없음을 확인한 뒤 `foryou/002-drop-book-blurb-cover.yaml`, `picks/007-drop-moved-tables.yaml`, `aisearch/005-drop-search-book.yaml`로 옛 표를 지운다. 추천목록 요약 파일은 복사하지 않고 배포 1에서 지운다(ADR-0161)
- 표지 그림과 프로필이 들어가는 차례는 design-delta "배포 순서"를 따른다

## 검토한 대안
### A안: 한 번 복사 + 옛 표는 다음 배포에서 지움 (채택)
- 장점: 양쪽을 읽는 임시 코드가 없음, 배포 1이 잘못되면 옛 표가 남아 되돌릴 수 있음
- 단점: 배포 1~2 사이 옛 표·새 표가 함께 있어 디스크 약 +110~150MB [추론]
### B안: 세 단계(새 표 → 한동안 양쪽에서 읽기 → 옛 표 지우기, dev 제안)
- 장점: 가장 조심스러움
- 단점: 양쪽을 읽는 코드를 만들었다가 다시 지움
- 채택하지 않은 이유: [이유 미확인]
### C안: 배포 1에서 옛 표까지 지움
- 장점: 배포 한 번
- 단점: 잘못되면 되돌릴 옛 표가 없음
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 옮기는 코드가 단순하고 되돌릴 길이 남음
- 감수하는 점: 23·24 dev가 배포 2 전에 옛 표·API를 쓰지 않게 맞춰야 함(`to-dev23-24.md` 3절)
