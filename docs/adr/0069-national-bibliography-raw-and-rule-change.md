# ADR-0069: 국가서지는 원문을 남기고, 정리 규칙을 바꿀 때는 상황별로 다시 가져온다

Status: Accepted
Date: 2026-10-11
Cycle: 08-polish-swap-memory
Supersedes: 없음 (ADR-0065의 국가서지 결과 부분을 바꿈)

## 배경
ADR-0065는 국가서지 TTL을 푼 결과(다듬은 키 → ISBN)를 파일 지문·정리 규칙 판과 함께 남기고 같으면 다시 쓰기로 했다. 다듬은 키는 정리 규칙이 바뀌면 틀려지므로 판 번호와 그것을 잊지 않게 하는 장치가 필요했다. 사용자가 "규칙을 DB에 남겨야 하나", "표를 통째로 바꿔 끼우면 판 번호가 필요 없지 않나"를 물었고, 정리 규칙을 바꿨을 때의 순서도 정해져 있지 않았다(`docs/cycles/08-polish-swap-memory/easy/2026-10-11-normalize-rule-change.html`).

## 결정
- 국가서지 TTL에서 뽑은 원문(ISBN·제목·저자·출판사)과 파일 지문만 `collection`에 남긴다. 지문이 같으면 원문을 다시 쓰고, 가져올 때마다 지금 정리 규칙으로 다듬어 키를 만든다. 정리 규칙 판 번호는 두지 않는다
- 새 사본으로 갱신하거나 묶기·대표값·날짜 규칙만 고쳤으면: 가져오기 → 바꿔 끼우기. 서비스는 다시 켜지 않는다
- 검색어 다듬기 규칙을 고쳤으면: 옛 서비스를 켜 둔 채 새 코드로 가져오기 → 바꿔 끼우자마자 서비스를 새 코드로 다시 켠다
- 표 교체는 한 트랜잭션에서 이름 자리만 바꾸므로, 켜진 서비스는 다음 검색부터 새 표를 읽는다
- 이 순서를 dev 가져오기 절차(`docs/maintenance/3-import.md`)에 적는다

## 이유 (사용자 발언)
- "규칙을 db에 남겨야 하나? 어짜피 새 규칙으로 db가 새로 만들어 져야 하는 거 아니야?" (2026-10-11)
- "테이블만 바꿔끼우는 거면 굳이 \"규칙을 고치고 VERSION 3→4\"이것을 할 필요가 없지 않나?" (2026-10-11)
- "그냥 트랜잭션 걸려 있어서 테이블만 교체하면 알아서 되는 거 아니야? 검색어를 다듬는 규칙이 달라지는 경우에만 서비스 다시 키면 되는 거 아니야?" (2026-10-11)
- 상황별 할 일 표: "이렇게 해줘" (2026-10-11)

## 검토한 대안
### A안: 원문을 남기고 매번 다듬음, 판 번호 없음 (채택)
- 장점: 규칙이 바뀌어도 남긴 것이 틀려지지 않음, 손으로 올릴 번호와 잊지 않게 하는 테스트가 필요 없음
- 단점: 남기는 양이 조금 커지고 가져올 때마다 다듬는 시간이 듦(7.7GB 풀기보다 작을 것으로 봄, 재지 않음)
### B안: 다듬은 키 + 손으로 올리는 판 번호 + 테스트 (처음 제안)
- 단점: 판 번호 관리가 필요
- 채택하지 않은 이유: 위 사용자 발언
### C안: 테스트 벡터 결과로 자동 지문
- 단점: 판 값이 읽기 어려움, 장치가 하나 더
- 채택하지 않은 이유: [이유 미확인]
### D안: 배포 번호를 판으로
- 단점: 규칙과 상관없는 배포에도 국가서지를 다시 풂
- 채택하지 않은 이유: [이유 미확인]
