# ADR-0021: 운영은 본 서비스 1대, 설계는 여러 대 대비

Status: Accepted
Date: 2026-09-28
Cycle: 02-library-expansion
Supersedes: 없음

## 배경
사이클 02 개발 중 dev에서 사용자가 정한 결정을 사이클 03 시작 때(2026-09-29) 기록한다. ADR-0011(조회 서비스 분리)을 보완한다.
사이클 02 scope는 "서버 여러 대"를 제외했고, 사용자는 인계서 질문에 이것이 "본 서비스 1대"라고 확인했다. 그런데 호스트 간격 제어는 상태를 메모리에 가진 구체 클래스여서, 본 서비스가 N대가 되면 도서관 한 곳에 N건이 동시에 갈 수 있다(도서관 호출 예절 위반).

## 결정
- 이번 운영은 본 서비스 1대다.
- 여러 대가 되면 틀려지는 부분은 인터페이스 뒤에 둔다: `HostThrottle`(구현 `InMemoryHostThrottle`), `SearchPageCache`, `DetailVerdictCache`(구현은 Caffeine). 공유 저장소(Redis 등)는 구현하지 않는다.
- 묶음 검색(ADR-0014)과 상세 판정 스트림은 서버 밖에 상태를 남기지 않게 유지한다.
- 조회 서버의 "쉼" 표시는 서버마다 따로 둔다(늦게 알아챌 뿐 틀리지 않음).

## 이유 (사용자 발언)
- "근데 MSA 고려니까 나중에 본 서버도 여러 대 댈 수 있어. 이거 고려해야 해." (2026-09-28, dev plan-feedback C2-U-1)

## 검토한 대안
### A안: 교체 지점(인터페이스)만 두고 구현은 메모리 (채택)
- 장점: 이번 범위를 넘지 않고, 나중에 구현만 바꿔 끼움
- 단점: 여러 대로 늘리기 전에는 공유 구현이 없음
### B안: 지금 공유 저장소(Redis)로 간격 제어·캐시
- 장점: 바로 여러 대 운영 가능
- 단점: 운영할 저장소가 늘어남
- 채택하지 않은 이유: [이유 미확인] (사이클 02 scope 제외 항목)
### C안: 간격 제어를 조회 서버로 옮기고 호스트마다 조회 서버를 고정 배정
- 장점: 본 서비스가 상태를 덜 가짐
- 단점: ADR-0011("캐시·간격 제어는 본 서비스 한곳")과 어긋남
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 여러 대로 늘릴 때 바꿀 곳이 인터페이스 구현으로 좁혀짐
- 감수하는 점: 여러 대로 늘리면 공유 저장소 구현과 ADR-0011 재검토가 필요함. 느리거나 실패하는 도서관 기억하기(backlog)도 같은 방식이 필요함
- 나중에 서비스로 분리할 때: 간격 제어·캐시가 이미 인터페이스 뒤에 있어 공유 구현으로 바꾸는 비용이 작음
