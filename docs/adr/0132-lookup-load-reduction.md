# ADR-0132: 조회 부하 줄이기 — 결과 10, 책 화면 이어 부르기 3묶음, 도서관 요청 gzip + 풀었을 때 1MB(4MB → 1MB) + 1MB 넘음 기록, 1분 운영 요약 로그

Status: Accepted (2026-10-17, 사용자 승인 — 사이클 20 설계 검토 #2)
Date: 2026-10-17
Cycle: 20-lookup-status-and-extension
Supersedes: 없음

## 배경
운영 서버는 2GB(사이클 17, 시드니 t4g.small, 앱 전 이미 약 0.97GiB 사용)이고, 사용자는 "이 서비스는 메모리 점유가 더 문제"라고 했다(2026-10-15). 지금 dev는 검색 한 번이 결과 줄 20까지 도서관을 부르고(`batch.row-limit` 20), 책 기준 검색은 기본 20권(`BookParams.MAX_PAGE_SIZE` 20), 도서관 응답 본문 상한은 4MB이며 압축을 받지 않는다. 책 화면 대출 상태는 보이는 10권을 다 채울 때까지 화면이 묶음을 이어 부르도록 정했었다(세 관점 검토 #26). 서버가 지금 얼마나 바쁜지 한 줄로 보는 기록도 없다.

이 ADR은 이미 승인한 결정을 한곳에 모은 기록이다. 새 결정은 없다. 원문: `docs/cycles/20-lookup-status-and-extension/spec.md` R15·R15-1·R16, `design-delta.md` "전반 점검으로 바뀐 것" #5·#6·#7, 세 관점 검토 #7(4MB → 1MB).

## 결정
- **결과 10** [확정] (세 관점 검토 #23 승인 2026-10-16, 명세 R15): 바로 검색은 결과 줄이 10줄 넘게 모이면 새 도서관 요청을 멈춘다(`batch.row-limit` 20 → 10, 서버·확장 모드 같음). 책 기준 검색 `GET /api/v1/books`는 기본 `pageSize` 10(최대 20 그대로), 값은 서버 설정 속성 하나(검토 #30). 1단계.
- **책 화면 이어 부르기 최대 3묶음** [확정] (세 관점 검토 #26 승인 2026-10-16, 전반 점검 #7 승인 2026-10-17, 명세 R15-1): 책 화면 대출 상태 조회는 줄 상한 없이 보이는 10권을 대상으로 하되, 화면이 자동으로 이어 부르는 것은 첫 묶음 포함 **최대 3묶음**(약 24초, 설정)까지, 그 뒤 남은 상태는 「더 보기」. 서버·확장 모드 같음. 사이클 21 책 창 조회 넓히기(`holdingLimit` 3 → 6 → 10 → 20)는 별개 단계. 1단계. (같은 규칙이 ADR-0131에도 적혀 있음)
- **도서관 응답 본문 상한 4MB → 1MB** [확정] (세 관점 검토 #7 승인 2026-10-16): 서버 모드·확장 모드·nginx가 같은 값 `LOOKUP_MAX_BODY_MB` 하나를 씀(`docs/settings-index.md` 2절·8절). 1단계.
- **도서관 요청 gzip + 풀었을 때도 1MB** [확정] (전반 점검 #6 승인 2026-10-17, 명세 R16 ③): 서버 모드 도서관 요청(직접·조회 서버 경유)에 `Accept-Encoding: gzip`을 보내고, 풀면서 세어 풀린 크기도 1MB를 넘으면 그 자리에서 끊고 그 도서관만 실패(압축 폭탄 막기). 확장 모드는 브라우저가 풀고 확장이 스트림으로 세어 끊으므로 바뀌지 않음. 1단계.
- **1MB 넘음 기록** [확정] (전반 점검 #6; 칸은 마무리 확인 #6 승인 2026-10-17): 1MB를 넘어 실패하면 ① 서버 로그 한 줄(도서관 번호·주소·받은 크기·시각) ② 사용 기록 `usagelog.library_response_daily`의 `failed_count`에 더하고 새 칸 `body_too_large_count`(integer, 0 이상, 기본 0, `usagelog/004`)에도 셈 ③ 1분 요약 로그에 "1MB 넘음 n건". 1단계.
- **1분 운영 요약 로그 (앱 쪽)** [확정] (전반 점검 #5 승인 2026-10-17, 명세 R16 ②): 앱이 1분마다 한 줄 — 검색 자리 사용(최대·지금), 503 수, 힙, 멈춘 길 수, 1MB 넘음 수, 최근 DB 오류 수, 확장/서버 도서관 요청 수, 계획 무게 합(2단계부터), 장부 크기(3단계부터). 필드 이름·모양 [안: dev, CloudWatch 지표 필터로 읽기 쉬운 `key=value`]. 경보는 사이클 17 몫(`docs/cycles/17-first-deploy/from-cycle-20-observability.md`). 1단계.

## 이유 (사용자 발언)
- 결과 10: "별개로 지금 도서 검색 정보 바로 검색이든 도서책 기준 검색이든 검색 결과 수를 줄여야겠다 10개로" (2026-10-16, 세 관점 검토 #23)
- 책 화면 10권: "책 기준 검색 말이야 이거 5개 고대로 안 가져가고 그냥 한 번에 보여지는 10개대로 하는 게 맞지 않아?" (2026-10-16, 세 관점 검토 #26)
- 이어 부르기 3묶음: 제안 → 승인 (2026-10-17, 전반 점검 #7) [이유 미확인]
- 4MB → 1MB: 제안 → 승인 (2026-10-16, 세 관점 검토 #7) [이유 미확인]
- gzip·1MB 넘음 기록: "1MB 넘는 거 잘 기록하고" (2026-10-17, 전반 점검 #6). gzip 자체는 제안 → 승인 [이유 미확인]
- 1분 요약 로그: 제안 → 승인 (2026-10-17, 전반 점검 #5) [이유 미확인]
- 하나의 ADR로 모음: 제안 → 승인 (2026-10-17, 설계 검토 #2) [이유 미확인]

## 검토한 대안
### A안: 다섯 가지를 함께 (채택)
- 장점: 검색 한 번이 쓰는 도서관 요청이 대략 반(결과 10, 어림), 책 화면 한 번이 자리를 잡는 시간이 약 24초 안, 큰 응답 하나가 잡는 메모리가 4분의 1, 넘는 일이 생기면 기록으로 보고 기준을 다시 정함
- 단점: 결과가 10줄에서 멈춰 「다음 쪽」·「더 보기」를 누르는 일이 늘 수 있음, 1MB를 넘는 도서관 페이지는 실패(지금까지 잰 최대 약 322KB, 2026-10-05)
### B안: 지금 값 그대로 (결과 20, 이어 부르기 제한 없음, 4MB, 압축 없음)
- 장점: 코드 변경 없음
- 단점: 2GB 서버에서 동시 해석 메모리 최악이 커짐(`docs/settings-index.md` 3절·6-1절 어림), 서버가 바쁜지 볼 기록 없음
- 채택하지 않은 이유: [이유 미확인] (제안 → 승인)

## 결과
- 좋아지는 점: 같은 서버로 받을 수 있는 검색이 약 2배(어림), 동시 해석 메모리 상한이 줄고, 1MB 넘음·503·힙을 1분마다 볼 수 있음
- 감수하는 점: 1MB를 넘는 도서관은 그 도서관만 실패(기록으로 지켜봄). gzip 압축률은 dev가 몇 곳에서 재서 기록 [확인 필요: dev 측정]. 상세 페이지 기다림 등 다른 값은 그대로
- 나중에 되돌리거나 서비스로 분리할 때: 모두 설정 값(`batch.row-limit`, `pageSize` 기본값, 이어 부르기 묶음 수 `VITE_*`, `LOOKUP_MAX_BODY_MB`, 요약 로그 간격)이라 값만 바꾸면 됨. 나중에 분리할 때 조회를 맡는 쪽을 따라감
