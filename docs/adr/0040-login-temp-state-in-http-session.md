# ADR-0040: 로그인 도중의 임시 값은 HttpSession에 두고, 서버 수에 따라 저장소를 설정으로 고름

Status: Accepted
Date: 2026-10-04
Cycle: 05-login-account
Supersedes: 없음

## 배경
로그인 도중에는 몇 분 동안 들고 있어야 하는 값이 있다: 제공자에 보낸 확인 값(`state`), 가입 동의 전의 제공자 번호, 탈퇴 재인증 증명과 네이버 접근 토큰. "가입 전에는 DB에 아무것도 저장하지 않는다"는 결정 때문에 DB에는 둘 수 없다.

## 결정
임시 값은 `HttpSession`으로만 다룬다(수명 10분). 이번 사이클은 서버 메모리 구현만 만든다. 서버가 여러 대가 되면 Spring Session(Redis)을 설정으로 켜서 같은 코드가 Redis에 저장하게 한다. 동의 화면을 그냥 떠난 사람은 임시 값이 만료될 때 제공자 연결을 끊는다. 로그인 유지(JWT)는 이 세션과 무관하다.

## 이유 (사용자 발언)
- "일단 (가)로 가되 여러 백엔드 서버가 동시에 존재하더라도 잘 되도록 redis가 차후 도입되었을 때를 대비해서 설계되었으면 해" (2026-10-04)
- "선택으로 멀티서버/원 서버 환경에서 각각 돌아가도록 했으면 해" (2026-10-04)

## 검토한 대안
### A안: 로그인 도중의 임시 값은 HttpSession에 두고, 서버 수에 따라 저장소를 설정으로 고름 (채택)
- 장점 / 단점: "결과" 절 참고
### B안: 암호화한 쿠키에 둠
- 장점: 서버가 상태를 갖지 않아 여러 대에서 그대로 동작
- 채택하지 않은 이유: [이유 미확인] (서버 메모리 안을 고르고 Redis 대비를 조건으로 둠)
### C안: DB 표에 수명을 두고 저장
- 장점: 여러 대에서 동작
- 채택하지 않은 이유: "가입 전에는 DB에 아무것도 없음" 결정과 충돌

## 결과
- 좋아지는 점: Spring 기본 기능 그대로라 만들 것이 적음. 버려진 가입 대기의 제공자 연결을 끊을 수 있음
- 감수하는 점: 서버를 다시 켜면 그 순간 로그인하던 사람은 처음부터 다시 함. 여러 대가 되면 Redis(또는 같은 서버로 보내는 설정)가 필요함
- 되돌리는 비용: 몇 분짜리 값이라 옮길 자료가 없음. Redis로 바꿀 때 민감한 값(네이버 접근 토큰)은 암호화해 넣고, 세션 만료 알림 설정을 확인해야 함
