# ADR-0038: 로그인 유지는 JWT (짧은 액세스 토큰 + DB의 리프레시 토큰)

Status: Accepted
Date: 2026-10-04
Cycle: 05-login-account
Supersedes: 없음

## 배경
로그인한 상태를 유지하는 방법을 정해야 했다. 2026-10-01에는 세션을 DB에 두는 방식(Spring Session JDBC)으로 정했으나, 사용자가 서버가 여러 대가 될 때 늘어나는 것을 줄이고 싶어 했고 나중에 폰 앱도 같은 로그인으로 쓰려 한다.

## 결정
액세스 토큰은 계정 번호와 만료 시각만 담은 JWT(HS256, 15분). 리프레시 토큰은 무작위 값으로 DB에 SHA-256 해시로 저장하고 쓸 때마다 교체하며, 이미 쓴 값이 다시 오면 그 로그인을 끊는다. 로그인한 때부터 30일이면 만료(미사용 기한은 따로 없음). 두 토큰은 `Secure`·`HttpOnly`·`SameSite=Lax` 쿠키. 로그인이 필요한 API는 요청마다 그 계정이 아직 있는지만 확인한다. 여러 탭의 동시 갱신은 웹이 Web Locks로 한 번에 한 탭만 하게 한다.

## 이유 (사용자 발언)
- "가능하면 jwt로 했으면 좋겠어 세션을 쓰더라도 나중에 확장될 멀티 서버 환경에서 redis등이 필요해지는데 음 가능하면 줄이고 싶어" (2026-10-03)
- "jwt로 가려고 해" (2026-10-03)
- 서명 방식: "우리 서비스만 토큰을 확인하면 되니까 '가'로 가자" (2026-10-04)
- 계정 확인: "'나'로 하되 이렇다는 걸 명시하고" (2026-10-04)
- 30일 하나로, `SameSite=Lax`, 탭 갱신 방식: 승인만 함 [이유 미확인]

## 검토한 대안
### A안: 로그인 유지는 JWT (짧은 액세스 토큰 + DB의 리프레시 토큰) (채택)
- 장점 / 단점: "결과" 절 참고
### B안: 세션을 DB에 (Spring Session JDBC)
- 장점: 요청마다 DB를 읽음. 로그아웃이 바로 끊김. 만들 것이 적음
- 채택하지 않은 이유: 위 사용자 발언(2026-10-03)
### C안: 요청마다 로그인 기록(리프레시 토큰 줄)까지 확인
- 장점: 로그아웃한 토큰도 바로 끊김
- 채택하지 않은 이유: "리프레시 토큰을 db에 두면 세션이랑 다를 바가 없어 보여서" (2026-10-04)
### D안: 키 한 쌍으로 서명 (ES256·RS256)
- 장점: 다른 서비스가 토큰을 확인할 때 필요
- 채택하지 않은 이유: "우리 서비스만 토큰을 확인하면 되니까" (2026-10-04)
### E안: 서버가 바로 앞 리프레시 토큰을 몇 초 받아 줌
- 장점: 갱신 응답이 유실돼도 로그아웃되지 않음
- 채택하지 않은 이유: [이유 미확인] (화면 쪽에서 막는 안을 승인)

## 결과
- 좋아지는 점: 15분 동안은 DB를 읽지 않고, 서버가 여러 대여도 Redis 없이 로그인이 유지됨. 폰 앱이 같은 토큰을 헤더로 쓸 수 있음
- 감수하는 점: 로그아웃 전에 누가 미리 빼낸 액세스 토큰은 만료까지 최대 15분(시계 오차 포함 약 16분) 통과함. OWASP ASVS 5.0 7.4.1에 그만큼 못 미침. 갱신 응답이 유실되면 그 브라우저는 다음 갱신 때 로그아웃됨
- 되돌리는 비용: 서명 방식·키는 15분이면 바뀜. 세션 방식으로 돌아가려면 발급·갱신 부분을 다시 만들어야 함. 나중에 분리할 때 다른 서비스가 토큰을 확인하게 되면 키 한 쌍 방식으로 바꿈
