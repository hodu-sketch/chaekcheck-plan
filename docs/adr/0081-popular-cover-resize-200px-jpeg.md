# ADR-0081: 표지는 미리 받아 폭 200px JPEG로 줄여 저장하고 우리 서버가 넘겨준다

Status: Accepted
Date: 2026-10-12
Cycle: 10-popular-books
Supersedes: 0075 (미리 받기·우리 주소로 넘겨주기·두 달 보관은 그대로, "작은 표지를 받은 그대로 저장"을 바꿈. 결정은 사이클 10 개발 중 2026-10-12)

## 배경
ADR-0075는 사이트의 작은 표지(`s_<id>.jpg`, 약 51KB)를 받은 그대로 저장하는 것이었다. 개발 중 받기 시험(2026-10-12)에서 `s_` 그림도 폭 458~600px, 2KB~505KB로 제각각이었고 PNG·GIF가 섞였으며, PNG 두 장은 1MB 본문 상한을 넘어 실패했다. 작은 표지가 `/files/isbn/` 말고 `onix`·`old`·`trans` 폴더에도 있어(2026-09 "전체" 50권 중 13권), 처음 규칙대로면 약 1/4이 제목 글자로 보였다(dev `docs/plan-feedback.md` 사이클 10).

## 결정
- 매달 순위를 받은 뒤 그달 작은 표지를 2초 간격으로 미리 받아 `popular.cover`에 저장하고, 화면은 우리 주소(`/api/v1/popular-books/covers/{coverId}`)로 받는다. 최근 두 달 순위에 쓰인 표지만 남긴다. 몇 장이 실패해도 순위는 성공(ADR-0075 그대로)
- **저장 전에 폭 200px로 줄여 JPEG로 저장·게시**한다. 더 좁은 그림은 크기 그대로 JPEG로만, 세로는 비율대로, 투명 부분은 흰 바탕. JDK `javax.imageio`만 씀(새 의존성 없음)
- 표지 응답 본문 상한은 **50MB**(화면·POST 응답은 1MB 그대로)
- 받는 경로는 `/files/<영문 소문자 폴더>/…/s_<이름>`(`..`·`//`·스킴·호스트·`?` 없음)
- 풀었을 때 1,600만 화소를 넘는 그림은 풀지 않고 실패로 셈 (dev 제안 → 사용자 승인, 2026-10-12)

## 이유 (사용자 발언)
- "출판유통통합전산망 화면의 표지를 그대로", "다른 선택 우리 서버가 그림을 받아 넘겨주기 이걸로 해줘" (2026-10-11, ADR-0075)
- 크기를 하나로: "나는 표지 크기를 일원화했으면 하는데 받는 크기가 여러개여도", "좀 작아도 괜찮아 오히려 최대한 작은게 좋아 서비스되는 표지의 크기가 그렇게 안 크자나" (2026-10-12)
- 본문 상한: "상한 없애고 받아줘", 이어서 "상한 여유롭게 50MB로 하던가" (2026-10-12)
- 경로 규칙: 넓힌 규칙을 "넓힌 규칙 그대로"로 고름 (2026-10-12)
- 폭 200px: 화면 표지 칸(PC 약 180~200px, 폰 약 115px)과 줄여 본 크기(200px 중간 13KB)를 보고 정함. 사용자 말은 위 "최대한 작은게 좋아" [200이라는 값을 고른 말은 이유 미확인]
- 화소 상한: dev 제안 → 승인 (2026-10-12, 사이클 10 회고 결정 #3), 까닭 [이유 미확인]

## 검토한 대안
### A안: 줄여서 JPEG 하나로 (채택)
- 장점: 표지 크기·형식이 같아짐, 저장이 줄어듦(808장 약 11MB, 한 장 중간 14KB)
- 단점: 받을 때 그림을 풀고 다시 씀(힙에 원본이 한 장씩 올라옴)
### B안: 받은 그대로 저장 (ADR-0075)
- 단점: 크기·형식이 제각각, 큰 PNG가 상한에 걸림
- 채택하지 않은 이유: "표지 크기를 일원화했으면 하는데" (2026-10-12)
### C안: 표지 본문 상한을 없앰
- 채택하지 않은 이유: 사용자가 이어서 "상한 여유롭게 50MB로 하던가"를 고름 (2026-10-12)

## 결과
- 좋아지는 점: 저장 두 달 약 90MB 계산 → 실제 한 달 약 11MB, 화면에 같은 크기 그림
- 감수하는 점: 표지 하나를 받는 동안 원본(최대 50MB)이 서비스 힙(512MB)에 올라옴(한 번에 한 장) → 배포 때 힙 다시 재기에 포함(backlog)
- 나중에 되돌릴 때: 폭 설정(`cover.width`)만 바꾸고 다음 달부터 다시 받음
