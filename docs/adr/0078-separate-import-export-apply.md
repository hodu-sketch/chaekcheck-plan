# ADR-0078: 가져오기는 내 PC에서 하고, 운영 DB에는 파일 하나로 옮겨 바꿔 끼운다

Status: Accepted
Date: 2026-10-12
Cycle: 11-separate-import
Supersedes: 없음 (ADR-0065를 이어서: 바꿔 끼우기는 그대로 쓰고, ADR-0065에서 고르지 않은 E안 "다른 DB에서 가져와 옮기기"를 이번에 고름. ADR-0062·0070 번호 잇기는 그대로)

## 배경
가져오기는 힙 6GB(살아 있는 데이터 최대 약 4.8GB), 수집 사본·국가서지 파일, 약 33분이 든다(사이클 08 #3c). 운영 서버에서 돌리면 서버를 가져오기에 맞춰 키워야 하고, 운영 DB 컨테이너 상한 안에서 색인 메모리를 크게 잡으면 DB가 죽는다(사이클 08 #3b, 상한 512MB에서 `maintenance_work_mem` 1GB로 `OOMKilled`). 사이클 08에서 dev는 "가져오기 서버에서 가져와 네 표를 `pg_dump` → 운영에서 `catalog_next`에 복원 → 색인·ANALYZE → 바꿔 끼우기"를 의견으로 냈다. 책·소장 번호 잇기는 가져오는 DB의 지금 `catalog` 표를 읽으므로(`JdbcCatalogLoad` `Ids.decide`), 두 DB가 같은 상태여야 번호가 이어진다.

## 결정
- 가져오기 명령에 모드를 더한다: `in-place`(지금 동작, 기본) · `export` · `apply` · `finish` · `discard`
- **내 PC (`export`)**: 지금처럼 읽기·묶기·번호 잇기·`catalog_next` 쓰기까지 하고, `catalog_next` 스키마(네 표 + 작은 표 `load_manifest`)를 `pg_dump -Fc` 파일 하나로 내보낸다. 새 표는 남겨 둔다
- **운영 (`apply`)**: 파일 속 `load_manifest`만 먼저 읽어 두 DB를 비교(도서관 목록 해시, `collection_link` 해시, 책·소장 줄 수·가장 큰 번호·시퀀스, 네 표 칸 구조 해시). 다르면 아무것도 하지 않고 `mismatch` 기록. 같으면 남은 `catalog_next` 지우기 → 복원 → 색인·제약(운영 정의, 세션 `maintenance_work_mem` 256MB) → `VACUUM (ANALYZE)` → 바꿔 끼우기(ADR-0065 그대로)
- **내 PC (`finish` / `discard`)**: 운영이 성공하면 남겨 둔 새 표로 바꿔 끼우고, 실패하면 지운다. 기다리는 새 표가 있으면 다음 `export`·`in-place`는 시작하지 않는다. `discard`는 어느 DB에서든 남은 `catalog_next`를 지우는 명령을 겸한다
- `pg_dump`·`pg_restore`는 Java가 DB 컨테이너 이미지 안의 18판 프로그램을 불러 돌리고, 기록은 운영 반영마다 한 줄·내 PC `finish` 뒤 한 줄을 `export_id`로 잇는다
- 공개 API는 `catalog`의 `CatalogLoad`에 기능 7개를 더한다. 모듈 방향(`collection → catalog, library`)은 그대로
- 이 사이클의 운영 쪽 시험은 같은 PC의 두 번째 DB(포트 5434, `mem_limit` 1GB, 처음엔 `db` 통째 복사)

## 이유 (사용자 발언)
- "가져오기를 이 서버에서 하고 그것을 따로 운영중인 서버에 따로 반영하도록 하는 건?" (2026-10-11, 사이클 08 중 질문)
- "사이클 11은 가져오기 따로 하기로 잡아줘" (2026-10-11)
- 번호 잇기는 내 PC, 내 PC 바꿔 끼우기는 운영 성공 뒤, 비교 항목, `-Fc`, 반영 순서, 기록 한 줄, 운영 역할 DB: 제안 → 승인 (2026-10-12, 스펙 결정 #1~#7)
- 파일 속 작은 표, 표 구조 비교, 모드 설정, 컨테이너 안 도구, `CatalogLoad`에 더함, 기다리는 새 표 보호, 기록 줄, 반영 메모리: 제안 → 승인 (2026-10-12, 설계 결정 #1~#7·#12)
- 남은 빈 표를 지우는 명령: "남은 빈 표를 지우는 명령을 따로 만듦"을 고름 (2026-10-11, 사이클 08 회고) → 사이클 11에 넣음, 제안 → 승인 (2026-10-12, 점검 #1)

## 검토한 대안
### A안: 내 PC에서 가져와 파일로 옮기기 (채택)
- 장점: 운영 서버에 힙 6GB·사본·국가서지 파일이 필요 없음, 내 PC 가져오기가 실패해도 운영 무관, 바꿔 끼우기 코드 재사용
- 단점: 두 DB가 같은 상태여야 함(비교로 지킴), 명령이 하나에서 셋(`export`·`apply`·`finish`)으로, 바꿔 끼우는 동안 운영 디스크 두 벌
### B안: 운영 서버에서 직접 가져오기 (지금 방식)
- 장점: 명령 하나, 두 DB를 맞출 필요 없음
- 단점: 운영 서버가 가져오기용 8GB급 힙·파일을 감당해야 함
- 채택하지 않은 이유: [이유 미확인] (사용자가 따로 하기를 사이클 주제로 고름)
### C안: 번호 잇기를 운영에서 (내 PC는 번호 없이 보냄)
- 장점: 내 PC 책 표가 운영과 달라도 됨
- 단점: 운영에서 번호 잇기·쓰기(약 5분)를 하고 가져오기 코드를 둘로 쪼갬
- 채택하지 않은 이유: [이유 미확인] (추천하지 않은 안, 사용자는 A를 승인)
### D안: 비교 값을 덤프 옆 JSON 파일로
- 단점: 파일이 둘이 되어 "파일 하나"와 어긋남
- 채택하지 않은 이유: [이유 미확인]
### E안: `pg_dump` 없이 Java가 COPY로 자체 파일
- 장점: 외부 프로그램 판 걱정 없음
- 단점: `pg_dump -Fc` 결정을 다시 열어야 하고, 파일 형식·시퀀스를 직접 만들어야 함
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 운영 서버 크기를 검색 서비스에 맞춰 정할 수 있음(EC2 t4g.medium 4GiB, `docs/research/deploy/aws-layout.md` 6절)
- 감수하는 점: 운영에서 책 표를 직접 고치면 다음 반영이 `mismatch`로 막힘, 두 DB의 앱 판을 같게 돌려야 함, 내 PC가 꺼져 있으면 갱신 못 함(자동 갱신은 이 사이클 밖)
- 나중에 서비스로 분리할 때: 파일 형식(`load_manifest.format_version`)이 두 쪽의 약속이 되고, 운영 쪽은 `readManifest`·`baseline`·`apply`만 있으면 된다
