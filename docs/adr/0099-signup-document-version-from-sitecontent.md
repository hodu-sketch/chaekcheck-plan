# ADR-0099: 가입 문서 버전의 원본을 서버 설정에서 `sitecontent`로 옮기고, 동의 기록에는 판 순번을 남긴다

Status: Accepted (사용자: "회고 15 플랜 세션이 주면 그거 반영해서 /cycle-close하고 dev가 할 수 있게 해줘", 2026-10-14 — 설계 확정, dev main 대조 뒤)
Date: 2026-10-13
Cycle: 16-notices-and-policies
Supersedes: 없음

## 배경
지금 이용약관·동의문 버전은 서버 설정 `chaekcheck.auth.documents`의 날짜(`2026-10-04`)이고, 웹 `documentVersions.json`과 같은지 테스트로 확인한다(사이클 05 제약 27). 동의 기록(`auth.account_consent.document_version`)도 그 날짜를 남긴다. 글을 `sitecontent` 판으로 옮기면(ADR-0098) 버전의 원본도 DB여야 하고, 판을 순번으로 부르기로 했다. `auth`는 지금 어떤 모듈에도 의존하지 않는다(`auth/package-info.java` AC-18).

## 결정
가입 화면(`GET/POST /api/v1/auth/signup`)이 쓰는 지금 판 번호를 `auth`가 `sitecontent`의 Java 공개 창구(`SiteDocuments.currentVersion`)로 묻는다. 동의 기록에는 판 순번 글자(`"1"`)를 남기고, 테스트 계정 기록 `'2026-10-04'`를 `'1'`로 바꾸며 형식 CHECK를 더한다(`auth/002`). 서버 설정의 문서 버전과 `documentVersions.json` 비교 테스트는 지운다(제약 27 폐기). 새 의존 `auth → sitecontent` 하나가 생긴다(AC-18 변경). 409 `document_version_mismatch` 동작은 그대로. 다시 동의 표시 칸은 다시 동의 화면을 만들 때 더한다.

## 이유 (사용자 발언)
- 지금 버전을 DB로: 제안 → 승인 (2026-10-12) [이유 미확인]
- 판 순번: "하루에 여러 공지가 날 수 있는데 이상한데 그냥 그 자체의 순번으로 하면 안돼?" (2026-10-13)
- 동의 기록 = 판 순번: 제안 → 승인 (2026-10-13) [이유 미확인]. 지금 가입자는 테스트 한 명: "아직 실제로 테스트 인원 이외에 뭐 된 거 없어서 괜찮아 나만 가입했어" (2026-10-12)
- 다시 동의 칸을 지금 만들지 않음: "아직 기능이 다시 동의 필요가 없지 않나?" (2026-10-13)

## 검토한 대안
### A안: 판 순번을 글자로 저장 (채택)
- 장점: 같은 날 여러 판도 정확히 가리킴, 주소 `?version=`과 같은 값, UNIQUE·CHECK 구조 그대로
- 단점: 기록만 보고는 날짜를 모름
### B안: 시행일 그대로 저장
- 단점: 같은 날 두 판이면 어느 글인지 모름
- 채택하지 않은 이유: [이유 미확인]
### C안: 표 내부 번호 저장
- 단점: 주소·화면과 다른 값, 환경마다 다를 수 있음
- 채택하지 않은 이유: [이유 미확인]
### D안: 이벤트로 버전 전달
- 단점: 가입은 동기 읽기가 필요함
- 채택하지 않은 이유: [이유 미확인]

## 결과
- `sitecontent`가 `auth`(또는 그 설정)를 알면 서로 의존하므로, 이용약관 REST는 로그인 기능이 꺼져도 열어 두고 웹 경로 `/terms`만 숨긴다(제안 → 승인 [이유 미확인])
- dev 시험 `ModularityTests`의 "auth 의존 없음" 줄을 "auth → sitecontent만"으로 바꾼다(2026-10-14 dev main 확인)
- 나중에 분리할 때: 판 순번은 환경과 상관없는 값이라 서비스 사이 HTTP로 주고받아도 의미가 같다
