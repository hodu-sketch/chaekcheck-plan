# ADR-0114: 같은 책 묶기에서 같은 공급사의 상품 코드로 잇고, 제목 앞 괄호(관제)를 떼고 견준다

Status: Accepted
Date: 2026-10-15
Cycle: 19-author-angle-brackets
Supersedes: 없음 (ADR-0106 ④ 규칙에 덧붙임)

## 배경
「백만장자 마인드」(율리시즈)는 저자 칸에 다른 책 저자 이름(「김근아 저자」)이 잘못 든 줄과 「(부를 끌어 당기는) 백만장자 마인드」 줄 때문에 한 권으로 모이지 않았다(사이클 12 AC-3 미통과). 김근아 줄의 공급사 코드(1210492004114)가 다른 도서관 교보 줄의 상품 번호와 같았고, 공급사 번호 체계는 공급사마다 다르며 9자리 번호를 북큐브와 YES24가 함께 쓴다(수집 DB 2026-10-12). 목록 규칙(KORMARC 245)은 제목 앞 꾸밈말(관제)을 원괄호로 묶고 정렬에서 뺄 수 있다고 정한다.

## 결정
묶기 ② 단계를 넓혀 ISBN과 함께 (공급사 묶음, 코드)가 같으면 저자를 보지 않고 잇는다. 공급사 이름은 다듬은 이름을 묶음으로 쓰고 다른 이름끼리 같은 공급사는 dev 규칙 파일 `supplier_families.tsv`에 적는다. 같은 책 견줄 제목(④)에서만 맨 앞 `( … )`를 떼되, 판·원서·형태·뒷권 낱말과 "…판"·EDITION은 남긴다(코드 상수). 화면 제목·검색은 그대로.

## 이유 (사용자 발언)
- "그러면 각각의 서비스들에 대해서 코드를 다르게 취급하도록 하면 되는 거 아니야?" → "같은 공급사의 코드끼리만 견주고, 제목 조건은 두지 않습니다. 이걸로 해줘" (2026-10-15)
- 제목 앞 괄호: 승인 (세 원인 #2, 2026-10-14), 남길 낱말 목록·"…판" 일반화: 승인 (확인 결과 결정 #3, 명세 결정 #5, 2026-10-15)
- ② 단계에 넣기, 목록 밖 공급사 이름 처리, 남길 낱말을 코드 상수로: 제안 → 승인 (설계 결정 #1·#2·#7, 2026-10-15)
- 규칙 목록: "이거 다른 세션에서 수집기 md로 검증할 때 규칙에 포함되었으면 하는데... 수집기 규칙대로하되 규칙이 변동이 가능해야 하는데 그 구조로 가야 해... python 코드에 있되 그것을 ai가 파악하기 쉽도록 되어 있어? 안 되면 그렇게 가야 해" → "규칙 목록 문서 하나를 두는 것을 이 결정에 더하기로 해줘" (2026-10-15)

## 검토한 대안
### A안: ② 단계에서 ISBN과 공급사 코드로 함께 잇기 (채택)
- 장점: 세 묶는 방식(compact·objects·sql)이 같은 "값마다 잇기" 길을 그대로 씀, 코드 계산이 한 곳
- 단점: ISBN이 다른 두 묶음이 코드로 이어지면 가장 많은 ISBN만 남음 → 미리 돌려 볼 때 그런 묶음 수를 세어 0이 아니면 plan에 물음
### B안: ②와 ③ 사이 새 단계, ISBN이 다른 묶음은 잇지 않음
- 단점: 세 방식을 크게 고쳐야 해 공개일 일정에 부담
- 채택하지 않은 이유: [이유 미확인] (추천하지 않은 안)
### C안: 코드만 같으면 공급사를 보지 않고 잇기 (+ 제목 조건)
- 단점: 9자리 번호가 공급사끼리 겹쳐 다른 책이 합쳐질 수 있음
- 채택하지 않은 이유: 사용자 "각각의 서비스들에 대해서 코드를 다르게 취급"
### D안: 남길 낱말 목록을 DB 또는 규칙 파일에
- 단점: 가져오기는 내 PC에서만 돌고 바꿔도 다시 가져와야 효과, 묶기 규칙 원본이 둘로 나뉨
- 채택하지 않은 이유: [이유 미확인] (질문 "이거 db에 정보 두는 건 이상하나"에 답한 뒤 코드 상수 승인)

## 결과
- 「백만장자 마인드」의 김근아 줄은 「Y2Books 전자책」 = 「와이투북스」 묶음이 있어야 모임 → 공급사 묶음 목록은 dev가 수집 DB로 만들어 보고
- 잘못 합친 책이 표본에서 1권이라도 나오면 반영 전에 plan에 알림(명세 결정 #8)
- 괄호 없이 수식어를 붙인 제목은 여전히 따로(backlog)
- 사람이 정한 규칙(`supplier_families.tsv`, `SameTextKey`의 남길 낱말·판 낱말)은 dev 규칙 목록 문서(`docs/maintenance/rules-index.md` [안: 이름])에 한 줄씩 적는다: 어디에(파일·상수) / 뜻 / 데이터로 확인하는 법 / 바꾸는 법과 그 뒤 할 일. 코드 상수마다 그 줄을 가리키는 주석, 수집·가져오기 문서의 시작 점검이 확인 칸을 돌림 (방향 지침은 ADR-0117)

### 경위 (dev 측정, `plan-feedback.md` "# 사이클 19")
- 첫 dry run: 제목이 다른 합쳐짐 12,293건, 표본 40건 중 다른 책 약 13건. 원인은 703번 도서관 「우리전자책 전자책」 줄이 같은 `alt_code`를 다른 책에 붙인 것 → 제목 조건을 더함
- 두 번째: 같은 제목·다른 저자·다른 출판사 책이 이어짐 → 출판사 조건을 더함
- 세 번째: 표본 「귀가」(출판사 둘 다 「기타」) → 자리 채움 출판사를 뺌
- 네 번째: 원인별 표본 120권 중 잘못 합친 책 0 → 운영 역할 DB에 반영(기록 12번, 2026-10-16)
- 코드로 이었는데 ISBN이 둘 이상인 묶음 셈(`codeJoinedIsbnConflicts`)은 네 번 모두 0이었다. 잘못 이어진 줄에 ISBN이 없어 이 셈으로는 못 잡으므로, 반영 전 표본 판단이 실제로 막는 장치다
