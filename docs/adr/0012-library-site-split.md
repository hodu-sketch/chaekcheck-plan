# ADR-0012: 도서관과 전자도서관 사이트를 나눔

Status: Superseded by 0017
Date: 2026-09-28
Cycle: 02-library-expansion
Supersedes: 없음

## 배경
사이클 01의 `library.library`는 도서관 1곳 = 사이트 1개(`platform`, `base_url`)다. 사이클 02 조사에서 한 도서관이 일반·구독형 사이트를 함께 쓰거나, 교보·YES24를 함께 쓰는 경우를 확인했다 (research.md 10절). 가입 자격은 도서관 단위이고, 조회는 사이트 단위다.

## 결정
- `library.library`(이름, 자격, 가입 방법, 사용 여부)와 `library.library_site`(플랫폼 유형, 사이트 루트 URL, 사용 여부, 보유 전자책 수와 조사일, 후순위 표시)로 나눈다. 도서관 1 : 사이트 1..N.
- 조회, 캐시 키, 도서관별 "더 보기"는 `siteId`를 쓴다.
- 통합 포털은 가입 단위가 하나이므로 도서관 1곳 + 사이트 1개로 등록한다.

## 이유 (사용자 발언)
- [이유 미확인] (architect 추천안을 사용자가 선택, 2026-09-28)

## 검토한 대안
### A안: 도서관 + 사이트 테이블 분리 (채택)
- 장점: 자격이 한 곳에만 있어 수백 곳 seed에서 어긋날 위험이 적음. 여러 사이트를 쓰는 실제 구조와 맞음
- 단점: 테이블 하나 추가, 기존 `platform`·`base_url`을 옮기는 마이그레이션, API 경로가 `siteId`로 바뀜
### B안: 사이트마다 도서관 한 행
- 장점: 스키마 변경이 가장 적음
- 단점: 자격 규칙을 사이트 수만큼 똑같이 넣어야 함. `name` UNIQUE 때문에 이름을 꾸며야 함
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 사이트 단위로 켜고 끌 수 있음 (robots 차단, 주소 없어짐)
- 감수하는 점: 마이그레이션과 공개 타입 변경. 사이클 01 API `libraries/{libraryId}/ebooks`가 `sites/{siteId}/ebooks`로 바뀜
- 나중에 서비스로 분리할 때: `library_site`는 도서관 쪽이 가지고, 조회 쪽은 `siteId`와 주소만 받음
