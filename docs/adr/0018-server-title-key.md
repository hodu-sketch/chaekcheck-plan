# ADR-0018: 같은 제목 판단 키를 서버가 만들어 응답에 넣음

Status: Accepted
Date: 2026-09-28
Cycle: 02-library-expansion
Supersedes: 없음

## 배경
사용자는 각 묶음의 칸 안에서 같은 책 제목끼리 모아 정렬하기를 원했다 (spec 5.6). 도서관 화면마다 제목 표기가 다를 수 있어(띄어쓰기, 문장부호, 괄호 부제, "큰글자책", 권차) 같은 제목인지 판단하는 규칙이 필요하다. 이 규칙을 서버와 프론트 중 어디에 둘지 정해야 했다. 사용자는 프론트에 두면 서버 부담이 줄지 않는지 물었고, Claude는 한 묶음이 20~50줄이라 정리 비용은 HTML 해석에 비해 무시할 만하다고 답했다.

## 결정
- 서버(`availability`)가 결과 줄마다 **제목 비교 키** `titleKey`를 만들어 응답에 넣는다. 정리 규칙은 한 컴포넌트(이름 [안] `BookKeyNormalizer`)에 둔다.
- 프론트는 `titleKey`가 같은지만 비교해 칸 안에서 같은 제목끼리 모으고, 제목 안에서는 기존 순서를 쓴다. 키의 모양은 해석하지 않는다.
- 이번에는 제목만 키에 넣는다. 저자·출판사는 화면 종류마다 있는지와 표기를 조사한 뒤 더한다 (backlog).
- 줄을 합치지 않는다. 같은 책 묶기(ISBN)는 별도 사이클이다.

## 이유 (사용자 발언)
- 제목끼리 모으는 정렬: "조회 결과를 받고 나서 … 정렬을 같은 책제목 순으로 하고 싶거든?", "기존 정렬 순서는 새 정렬 순서의 후순위로 가게 해줘" (2026-09-28)
- 저자·출판사 고려: "나중에 책제목말고도 저자, 출판사 정보가 왔을 때도 좀 처리가 필요한 것 같아" (2026-09-28)
- 서버에 둠: 사용자가 프론트 안과 비교한 설명을 듣고 "서버"를 선택. 이유 [이유 미확인]
- 이번엔 제목만: [이유 미확인] (추천안 선택)

## 검토한 대안
### A안: 서버가 키를 만들고 프론트가 정렬 (채택)
- 장점: 화면 종류별 표기 차이를 아는 adapter 가까이에서 정리하고 HTML 고정 파일로 테스트함. 나중에 같은 책 묶기·인기 도서 사전 수집·통계(모두 서버)에서 같은 기준을 씀. 다른 클라이언트가 생겨도 규칙을 다시 만들지 않음
- 단점: API 응답에 필드가 늘고, 규칙을 고치면 서버 배포가 필요함
### B안: 프론트가 제목을 정리해 비교
- 장점: API 변경 없음, 웹 배포만으로 규칙 수정
- 단점: 나중에 서버에서도 같은 책 판단이 필요해지면 규칙이 두 벌이 되어 결과가 어긋날 수 있음
- 채택하지 않은 이유: [이유 미확인]
### C안: 이번엔 프론트, 같은 책 묶기 사이클에서 서버로 옮김
- 채택하지 않은 이유: [이유 미확인]
### 키에 넣을 값
- 제목만 (채택) / 제목 + 저자 / 제목 + 저자 + 출판사. 저자·출판사는 표기 정리 규칙과 화면별 유무를 먼저 알아야 함. 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 같은 제목 판단 기준이 서버 한곳에 있어 나중에 저자·출판사를 더해도 프론트는 그대로
- 감수하는 점: 정리 규칙의 세부(괄호 부제·"큰글자책"·권차)는 실제 표기를 모은 뒤 정함 [확인 필요]. 규칙이 너무 느슨하면 다른 책이 붙고, 너무 엄격하면 같은 책이 떨어짐
- 나중에 되돌릴 때: 프론트가 키 값을 해석하지 않으므로, 서버의 키 계산만 바꾸면 됨
