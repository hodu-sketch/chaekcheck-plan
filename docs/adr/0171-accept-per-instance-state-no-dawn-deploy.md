# ADR-0171: 바뀌는 순간 서버마다 따로 갖는 상태는 그대로 받아들이고, 새벽 정해진 일 시간에는 배포하지 않음

Status: Accepted
Date: 2026-10-29
Cycle: 27-zero-downtime-deploy
Supersedes: 없음

## 배경
백엔드 둘이 겹치는 약 1분 동안 메모리에만 있는 상태가 서버마다 따로 논다: Webshare 길·도서관별 "한 번에 1개, 1초 간격", 막힌 길 쉬게 하기, AI 검색 IP별 한도, 검색 캐시, 카카오 로그인 진행 중 세션(dev 코드 읽기 2026-10-29, `research.md` 4-2). 대부분은 지금 재시작 배포에서도 똑같이 사라진다. 또 정해진 일(04:00 계정·토큰 정리, 04:30 이용 기록 정리, 03:30·05:00 꺼진 일)은 잠금이 없어 두 판이 같이 돌면 두 번 돈다.

## 결정
겹치는 동안의 서버별 상태 차이는 고치지 않고 받아들인다(같이 쓰는 저장소를 두지 않음). 정해진 일이 두 번 돌지 않게 `release.sh`와 `switch.sh`는 서울 시각 03:25~05:10에 배포를 거절하고 이유를 알린다(잠금을 넣지 않음).

## 이유 (사용자 발언)
- 명세 결정 #1·#4 승인 (2026-10-29). 이유는 말하지 않음 [이유 미확인]

## 검토한 대안
### A안: 받아들임 + 새벽 시간 배포 거절 (채택)
- 장점: 코드 변경 없음, 지금 재시작 배포와 거의 같은 성질
- 단점: 길 간격이 최대 약 35초 동안 2배가 될 수 있음, 새벽엔 배포 못 함
### B안: 같이 쓰는 저장소(Redis 등)
- 단점: 메모리·관리할 것이 늘어남, 겹침이 짧아 얻는 게 적음
- 채택하지 않은 이유: [이유 미확인]
### C안: 정해진 일에 DB 잠금(ShedLock 등)
- 장점: 새벽에도 배포 가능
- 단점: 서비스 코드를 고칠 곳이 늘어남
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 백엔드 코드 변경 없이 무중단 배포
- 감수하는 점: 전환 직후 캐시·한도·막힌 길 기억이 처음부터, 로그인 중이던 사람은 드물게 다시 로그인, 03:25~05:10 배포 불가
- 나중에 되돌리거나 서비스로 분리할 때의 비용: 서버를 여러 대로 늘릴 때(나중에 분리할 때)는 B·C안이 필요해짐 (`application.yml`의 "Redis comes when the service runs on several instances" 주석과 같은 방향)
