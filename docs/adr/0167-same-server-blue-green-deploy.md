# ADR-0167: 같은 서버에서 백엔드 두 자리를 번갈아 쓰는 무중단 배포

Status: Accepted
Date: 2026-10-29
Cycle: 27-zero-downtime-deploy
Supersedes: 없음

## 배경
지금 배포는 `docker compose up -d`가 백엔드·nginx 컨테이너를 멈추고 새로 만들어, 새 백엔드가 뜨는 약 20초(실측 19.4초) 동안 Cloudflare 502가 나고 열려 있던 대출 조회·AI 찾기 스트림이 끊긴다. 운영 서버는 EC2 한 대(1,834MB, 2코어, 스왑 2GB)이고, 사용자는 "이거 나 무중단 배포로 바꾸고 싶은데 어떻게 하면 좋지?"(2026-10-29)라고 물었다.

## 결정
같은 서버에 백엔드 서비스를 `backend-blue`·`backend-green` 두 자리로 두고 번갈아 쓴다. 새 판을 쉬는 자리에 띄워 준비 확인이 통과하면 nginx가 가리키는 곳을 reload로 바꾸고, 옛 자리는 정상 종료(최대 40초, Docker 60초)로 내린다. 일하는 자리와 판 번호는 서버 `/srv/chaekcheck/slots.env`에 적고, 전환은 서버의 새 스크립트 `bin/switch.sh`가 맡으며, 되돌리기도 `release.sh --switch-only`로 같은 전환을 쓴다. 준비가 60초 안에 안 되면 nginx를 건드리지 않고 새 자리를 내린다.

## 이유 (사용자 발언)
- 범위·명세·설계 결정 페이지에서 모두 승인 (2026-10-29). 이유는 말하지 않음 [이유 미확인]
- 준비 기다림 60초: 사용자 "60초로 줄이고 4번 승인" (2026-10-29, 실측 시작 19.4초를 본 뒤)

## 검토한 대안
### A안: 같은 서버 블루·그린, 서비스 두 개 (채택)
- 장점: 서버·비용 그대로, 이름으로 한 자리만 가리킴
- 단점: 바꾸는 약 1분 동안 메모리 약 713MB 더 씀 → 약 250MB가 스왑으로
### B안: 서버 두 대 + 로드밸런서
- 장점: 가장 확실, 서버 하나가 죽어도 버팀
- 단점: 서버·로드밸런서 값과 관리할 것이 늘어남
- 채택하지 않은 이유: [이유 미확인]
### C안: 끊김은 두고 "업데이트 중" 안내·자동 다시 시도
- 장점: 가장 간단
- 단점: 몇십 초 검색 멈춤은 그대로
- 채택하지 않은 이유: [이유 미확인]
### D안: 서비스 하나를 둘로 늘리기(`--scale`) / 자리마다 compose 프로젝트
- 단점: 같은 별칭이라 nginx가 둘에 나눠 보냄 / 비밀값·네트워크가 두 벌
- 채택하지 않은 이유: [이유 미확인]
### 기록 방법 B안: nginx 설정 파일을 기록으로, 판 번호는 `docker inspect`
- 단점: compose 이미지 변수 때문에 결국 env 파일이 생김
- 채택하지 않은 이유: [이유 미확인]
### 스크립트 A안: `up.sh`에 덧붙이기
- 단점: 비밀값 읽기와 전환이 한 파일에 섞임
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 낮에도 배포·되돌리기 중 502 없음, 새 판이 안 뜨면 사이트는 옛 판 그대로
- 감수하는 점: 전환 약 1분 동안 메모리를 스왑까지 씀, 서버마다 따로 갖는 상태는 새 판에서 처음부터(ADR-0171), 처음 옮길 때 한 번은 점검 배포, db·cloudflared·nginx 이미지 판 올리기는 점검 배포
- 나중에 되돌리거나 서비스로 분리할 때의 비용: 배포 파일만 바뀌어 되돌리기 쉬움. 나중에 분리할 때 서버 두 대 + 로드밸런서로 가도 "준비 확인 뒤 전환" 순서는 그대로 쓸 수 있음
