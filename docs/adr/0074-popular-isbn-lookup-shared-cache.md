# ADR-0074: 순위 책과 우리 책은 저장하지 않고 볼 때 ISBN으로 맞추며, 책 정보는 공용 캐시

Status: Superseded by 0090
Date: 2026-10-11
Cycle: 10-popular-books
Supersedes: 없음 (사이클 10 spec R3-2 처음 글을 바꿈)

## 배경
spec 처음 글은 "짝을 받을 때 저장하고 가져오기 뒤 다시 맞춘다"였다. 그러나 있음/없음은 이용자마다 계획 도서관이 달라 화면을 열 때마다 책 목록에 한 번 물어야 하고, 목록 가져오기는 따로 켜졌다 끝나면 `System.exit`하는 프로세스라 "가져오기 끝남"을 알리는 길이 까다롭다(dev `CatalogImportRunner`, 2026-10-11 읽음).

## 결정
- 짝을 저장하지 않는다. `catalog`에 공개 API `BookLookup.byIsbn13`(ISBN → 책 번호·그 책을 가진 도서관 목록)를 더한다
- 그달 순위와 ISBN별 책 정보를 서버 메모리에 모두가 함께 쓰는 한 벌로 둔다. 10분마다, 새 달을 받으면 바로 새로 고친다
- 이용자별 값(계획 도서관과 겹치는지)은 요청마다 계산하고 캐시하지 않는다
- 제목으로는 맞추지 않는다

## 이유 (사용자 발언)
- "응 그리고 캐싱 활용할 수 있으면 활용하려고 해 사용자별로가 아니라 그냥 도서 정보" (2026-10-11)
- 제목 맞추기 안 함: 표본 30권 중 약 20권이 틀림(`docs/research/popular-books/kpipa.md` 4절) → ISBN만 승인 (2026-10-11). 이유 발언은 [이유 미확인]

## 검토한 대안
### A안: 볼 때 ISBN으로 찾기 + 공용 캐시 (채택)
- 장점: 짝 표·다시 맞추기·이벤트 없음, 가져오기 뒤 늦어도 10분 안에 반영
- 단점: 캐시를 새로 고칠 때 약 1,050권을 한 번에 찾음(시간 재지 않음)
### B안: 저장 + 가져오기 끝 알림(이벤트)
- 단점: 가져오기 프로세스가 바로 꺼져 비동기 알림이 끊길 수 있고, 남은 이벤트는 운영 서버 재시작 때만 다시 처리됨
- 채택하지 않은 이유: [이유 미확인]
### C안: 저장 + 하루 한 번 다시 맞춤
- 단점: 가져오기 뒤 최대 하루 옛 값, 예약 작업 하나 더
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 구조가 가장 단순하고 늘 최신에 가까움
- 감수하는 점: 공용 캐시 메모리(수 MB 안쪽 추정, 재지 않음)
- 나중에 서비스로 분리할 때: 짝 저장(B·C안)으로 옮기는 것을 다시 검토
