# ADR-0005: 검색 조회 API: SSE 스트림 + 더 보기 API

Status: Superseded by 0014
Date: 2026-09-27
Cycle: 01-ebook-availability-search
Supersedes: 없음

## 배경
도서관마다 응답 속도가 달라 먼저 응답한 도서관의 결과부터 보여 줘야 한다 (spec 5.2, AC-13). 도서관별 전체 건수, 캐시 시각, 실패를 함께 전달해야 하고, 도서관별 "더 보기"가 필요하다.

## 결정
- 검색은 SSE 스트림 하나로 한다. 이벤트 순서: 대상 도서관 목록 → 도서관마다 결과 또는 실패 → 끝. 서버가 동시 호출과 검색 전체 8초 제한을 관리한다.
- "더 보기"는 도서관 하나의 다음 페이지를 돌려주는 일반 GET API로 한다.
- 별도의 대상 도서관 API는 두지 않는다.
- 여러 도서관 결과의 정렬은 프론트가 하고, 백엔드는 정렬에 쓰는 값(재고, 원래 순서, 페이지 대출률)을 계산해 준다.

## 이유 (사용자 발언)
- SSE 선택: [이유 미확인] (사용자가 검토 화면에서 "결정 3: B안"으로 선택)
- 스트림 하나 + 더 보기 API: [이유 미확인] (추천안 채택)

## 검토한 대안
### A안: SSE 스트림 + 더 보기 API (채택)
- 장점: 검색 요청이 하나이고 서버가 동시 호출과 8초를 한곳에서 관리. 도서관이 많아져도 브라우저 연결 수 제한에 걸리지 않음
- 단점: API가 두 형태. 비동기 처리, 프록시 버퍼링, 자동 재연결 방지를 챙겨야 하고 테스트가 더 복잡함
### B안: 대상 도서관 API + 도서관별 검색 호출 (architect 추천안)
- 장점: 단순하고 더 보기와 같은 API 하나로 끝남
- 단점: 도서관 수만큼 브라우저 요청, HTTP/1.1 연결 수 제한
- 채택하지 않은 이유: [이유 미확인]
### C안: 모두 기다렸다 한 번에 응답
- 단점: AC-13을 만족하지 못함
- 채택하지 않은 이유: [이유 미확인]
### D안: 스트림 + 대상 도서관 API 따로
- 단점: API가 하나 더 늘어남
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 도서관이 늘어도 검색 요청 구조가 그대로
- 감수하는 점: 스트림이 끊기면 다시 연결되며 도서관 요청이 반복되지 않게 막아야 함. SSE 오류 이벤트의 모양을 정해야 함
- 나중에 서비스로 분리할 때: 조회 서비스가 도서관 서비스를 호출하는 서비스 간 동기 호출이 생김
