# ADR-0118: 조회 상태 신호는 화면이 10초마다 묻고, 서버는 자리·줄 선 호스트를 메모리에서 길마다 센다

Status: Accepted (2026-10-17, 사용자 승인 — 사이클 20 마무리 확인)
Date: 2026-10-16
Cycle: 20-lookup-status-and-extension
Supersedes: 없음

## 배경
지금은 동시 검색 자리(`SearchSlots`, 20개; 전반 점검 #13으로 40)가 차면 503 `server_busy`로 거절할 뿐 미리 알릴 길이 없고, 한 도서관 호스트에 요청이 몰려 자리를 8초 기다리다 실패해도 사용자는 이유를 모른다(dev `InMemoryHostThrottle`). 운영은 시드니 EC2 t4g.small 메모리 2GB 한 대(사이클 17이 무료 플랜 제약으로 설계의 서울 4GB 대신 만듦, `docs/cycles/17-first-deploy/research.md` 17절)이고, 사이클 17이 나가는 길(조회 서버·프록시·직접)마다 호스트 자리를 따로 세고 막힌 길을 기록한다(ADR-0095). 사용자는 머리말에 신호(초록/노랑/빨강)를 두고 특정 도서관에 몰리는 경우도 보이게 해 달라고 했다.

## 결정
- 머리말 신호는 화면이 `GET /api/v1/lookup-status`를 **10초마다** 묻는 방식(SSE 아님). 탭이 숨으면 멈추고, 503을 받으면 즉시 빨강, 30초 넘게 답이 없으면 회색. 확장 모드에서는 묻지 않는다.
- 상태 주소는 nginx 도서관 호출 구역(`/api/v1/availability/`, 30r/m) 밖, 일반 `/api/` 구역 안에 둔다.
- 서버는 동시 검색 자리 사용 수, 최근 503 시각(`SearchSlots.lastRefusedAt`), 그리고 **길(나가는 IP)마다** 줄이 선 호스트(기다리는 요청 1건 이상 또는 최근 60초 안 시간 초과; 그 호스트에서 막힌 길은 자리로 세지 않음)를 throttle 옆의 작은 부품 `HostQueueBoard`에서 세어 1초 캐시로 돌려준다. 단계는 서버가 판정한다(초록 / 노랑 = 자리 절반 이상 / 빨강 = 모두 참 또는 최근 10초 안 503).
- 업체(Webshare) 길이 한꺼번에 멈춘 동안(업체 오류 또는 데이터 90%, 사이클 22) 단계는 **최소 노랑**, 둘째 줄 「지금은 조회가 평소보다 느려요」. 빨강 규칙은 그대로, 다시 켜지면 원래 규칙 (사이클 20 세 관점 검토 #21, 사용자 승인 2026-10-16).
- 나가는 길 설정이 `프록시만`이고 업체 길이 모두 멈춘 동안은 서버 모드로 갈 길이 없으므로 **빨강**, 둘째 줄 「지금은 도서관 조회를 할 수 없어요」(확장 모드는 그대로) (세 관점 검토 #24, 사용자 승인 2026-10-16).
- 위 두 값은 사이클 17/22의 나가는 길 코드가 주는 읽기 전용 포트로 읽고, 상태 응답에 `reason`(`NONE`·`VENDOR_PAUSED`·`NO_LANE`)을 더해 화면이 둘째 줄을 고른다. 포트가 없으면 `NONE`과 기본 규칙 — 이 방법은 [확정] (검토 #28 승인 2026-10-16).
- (전반 점검 2026-10-17, 결정 페이지 `docs/cycles/20-lookup-status-and-extension/easy/2026-10-17-overall-review.html`; ADR이 Proposed라 본문에 더함)
  - 이 ADR의 모든 것(상태 묻기·`HostQueueBoard`·도서관별 「밀려요」 포함)은 사이클 20 **1단계**에 만든다 (전반 점검 #1·#3).
  - `HostQueueBoard`는 **스스로 낫는 구조**: 기다림 시작(+1)·끝(−1)을 한 곳의 try/finally로 짝 맞추고, 기다림마다 시작 시각을 적어 시작한 지 10초(묶음 마감 8초 + 2초)가 지난 기다림은 세지 않는다 → 짝이 어긋나도 최대 10초 뒤 「밀려요」가 사라진다. dev 단위 시험 둘(기다리는 중 오류 뒤 0으로 돌아옴, 10초 지난 항목 빠짐) (전반 점검 #3).
  - 최근 **30초** 안에 DB 오류가 있었으면 단계는 회색(`level=GRAY`, `reason=DB_ERROR`, 값 이름 [안]), 화면은 짧은 글 「상태 모름」, 말풍선 둘째 줄 「상태를 확인할 수 없어요」 [확정] (사용자 승인, 2026-10-17, 마무리 확인 #7) — 상태 응답이 DB를 보지 않아 DB 장애에도 초록이던 문제를 막음 (전반 점검 #9).
  - 동시 검색 자리는 20 → **40**(설정)으로 올리고, 단계 기준은 그대로 "절반·전부"라 20 노랑·40 빨강 (전반 점검 #13). 해석 메모리는 서버·확장 모드가 함께 쓰는 해석 자리 8로 따로 묶는다(ADR-0119, 전반 점검 #4).

## 이유 (사용자 발언)
- 10초 묻기(SSE 아님): "자원 비교해서 이 서비스는 메모리 점유가 더 문제라고 판단했다" (2026-10-15)
- 도서관별: "특정 도서관에 몰리는 경우도 좀 생각해야 할 것 같아", "계산할 때 조회 서버 여러대이면 그 여러대만큼으로 분류되는 거 생각해서 하고", "조회 서버마다 접근이 안 되는 곳들 따로 관리할건데 그곳은 또 빼야 해", "조회 서버마다 1초 카운팅 다르게 하는거 잊지 마" (2026-10-15)
- 세 단계: 다른 선택 ① 세 단계를 고름 (2026-10-15)
- 업체 길 멈춤 → 최소 노랑: 제안 → 승인 (2026-10-16, 검토 #21) [이유 미확인]
- `프록시만` → 빨강: "프록시만 하면 프록시만 하고 자체 서버 IP에서 … 안 하도록" (2026-10-16, 검토 #24에서 사용자 요청), 빨강 표시는 제안 → 승인
- `HostQueueBoard` 1단계·스스로 낫는 구조: "지금 가자" (2026-10-17, 전반 점검 #3, 처음 제안 "3단계로 미룸"을 바꾼 제안을 승인)
- DB 오류 회색: 제안 → 승인 (2026-10-17, 전반 점검 #9) [이유 미확인]
- 자리 40: "이걸 올리는 게 나을 것 같은데 사이클 20에게 알려줘" (2026-10-17, 전반 점검 #13), 40이라는 값은 제안 → 승인

## 검토한 대안
### A안: 10초마다 묻기 + `HostQueueBoard` + `/api/v1/lookup-status` (채택)
- 장점: 요청 뒤 서버에 남는 것이 없고 재연결이 없음. 보드는 사이클 17이 고치는 throttle 파일과 겹치지 않고 따로 시험 가능. 주소는 nginx 설정을 바꾸지 않아도 한도 밖
- 단점: 최대 10초 지연, CPU를 조금 더 씀(100명에 1% 안쪽 추정). 보드가 호스트→도서관을 요청을 보면서 배우므로 재시작 뒤 아직 불리지 않은 포털 소속 도서관은 목록에서 빠질 수 있음
### B안: SSE로 밀어 주기
- 장점: CPU·데이터가 적음
- 단점: 보는 사람 수만큼 연결·메모리를 유지, nginx `worker_connections` 기본 512(프록시 연결 포함, 1명 = 2개)라 약 250명에서 한도, 살아 있음 신호(nginx 120초·Cloudflare 125초)·재연결·바뀜 알림 코드
- 채택하지 않은 이유: "메모리 점유가 더 문제"
### C안: 줄 선 호스트를 `InMemoryHostThrottle` 안에서 셈
- 장점: 클래스가 늘지 않음
- 단점: 사이클 17이 같은 파일을 길마다 세도록 고치므로 두 사이클의 변경이 한 파일에서 겹침
- 채택하지 않은 이유: [이유 미확인] (제안 → 승인)
### D안: 상태 주소를 `/api/v1/availability/status`로
- 장점: 범위 문서의 예시 이름 그대로
- 단점: nginx 정확 일치 예외 블록이 필요하고, 운영 conf에서 빠지면 상태 묻기가 429
- 채택하지 않은 이유: [이유 미확인] (제안 → 승인)

## 결과
- 좋아지는 점: 혼잡을 검색 전에 보고, 몰린 도서관은 그 결과 줄에서 알 수 있음. 서버 메모리 사용은 요청 중에만
- 감수하는 점: 10초 지연. 값이 서버 한 대 메모리 기준이라 서비스를 여러 대로 늘리면 합치는 설계가 필요함. 길·막힌 길 기록은 사이클 17이 먼저 들어가야 함
- 나중에 되돌리거나 서비스로 분리할 때: 주소 하나와 부품 하나라 비용이 작음. 나중에 분리할 때 `HostQueueBoard`는 조회를 하는 쪽(availability 또는 조회 서비스)에 따라감
- 감수하는 점 (전반 점검 #3): 상세 페이지(마감 30초) 기다림도 10초 뒤에는 세지 않아 「밀려요」가 일찍 사라질 수 있음
