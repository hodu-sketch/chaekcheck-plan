# ADR-0039: 로그인 수단 표를 소셜 전용으로 만들지 않고, 제공자 번호는 프로필 API로 받음

Status: Accepted
Date: 2026-10-04
Cycle: 05-login-account
Supersedes: 없음

## 배경
이번 사이클은 네이버·카카오 로그인만 만든다. 사용자는 나중에 이메일·비밀번호 가입을 더할 수 있게 해 두기를 원했다. 또 제공자에게서 회원번호를 받는 길이 둘(프로필 API, OIDC 신분 토큰)인데, 네이버는 두 길의 번호가 같은지 문서에 없다.

## 결정
계정 표(`auth.account`)와 로그인 수단 표(`auth.login_method`)를 나누고, 로그인 수단 표의 칸을 `method`(NAVER, KAKAO, 나중에 PASSWORD)와 `subject`(그 수단 안의 식별자)로 짓는다. 두 제공자 모두 OAuth 2.0 + 프로필 API로 식별자를 받는다. 이메일·이름·제공자 토큰은 저장하지 않는다.

## 이유 (사용자 발언)
- "사이클 05 설계에서 로그인 수단 표를 '소셜 전용'으로 좁게 만들지 않는 것 이거 꼭 지키고" (2026-10-03)
- 표를 둘로: "표는 둘로, 연결 기능은 나중" (2026-10-01)
- 프로필 API: 승인만 함 [이유 미확인]

## 검토한 대안
### A안: 로그인 수단 표를 소셜 전용으로 만들지 않고, 제공자 번호는 프로필 API로 받음 (채택)
- 장점 / 단점: "결과" 절 참고
### B안: `provider`·`provider_user_id` 같은 소셜 전용 칸 이름
- 장점: 지금은 더 직관적
- 채택하지 않은 이유: 위 사용자 발언(2026-10-03)
### C안: OIDC 신분 토큰의 `sub` 사용
- 장점: 카카오는 다시 로그인한 시각을 받을 수 있음
- 채택하지 않은 이유: [이유 미확인] (네이버 `sub`가 프로필 `id`와 같은지 확인 못 함)

## 결과
- 좋아지는 점: 직접 가입을 더할 때 값 하나와 비밀번호 표 하나만 더하면 됨. 저장하는 식별자가 공식 문서로 확인된 값
- 감수하는 점: 탈퇴 재인증이 실제로 일어났는지는 제공자에 보낸 요청(`prompt=login`, `auth_type=reauthenticate`)을 믿는 수준
- 되돌리는 비용: OIDC로 바꾸려면 네이버 `sub`와 `id`가 같은지 먼저 확인. 다르면 기존 계정과 연결이 끊김
