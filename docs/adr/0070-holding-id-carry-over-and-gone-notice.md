# ADR-0070: 같은 소장은 옛 소장 번호를 잇고, 빠진 책·소장은 따로 알린다

Status: Accepted
Date: 2026-10-11
Cycle: 08-polish-swap-memory
Supersedes: 없음 (ADR-0065의 소장 번호 부분을 바꿈)

## 배경
ADR-0065는 바꿔 끼울 때 소장 번호를 옛 최대 번호 다음부터 새로 매기기로 했다. 그러면 바꿔 끼우기 직전에 열린 책 화면이 옛 소장 번호로 대출 현황을 물을 때 "찾을 수 없음"이 된다. 설계 검토(2026-10-11, 7번)에서 이를 "실패 0건" 기준과 어떻게 맞출지 다뤘고, 사용자가 중간 단계(번호 맞춤 표)를 제안했다. 가져오기는 이미 옛 소장 줄과 (도서관, `item_key`)로 맞대어 책 번호를 잇고 있어(ADR-0062), 같은 결과로 소장 번호도 이을 수 있다(`docs/cycles/08-polish-swap-memory/easy/2026-10-11-holding-id-followup.html`).

## 결정
- 가져오기에서 (도서관, `item_key`)가 같은 소장은 옛 소장 번호(`catalog.holding.id`)를 그대로 쓴다. 새로 생긴 소장만 옛 최대 번호 다음부터 매긴다. 책 번호 잇기(ADR-0062)와 같은 맞대기 결과를 쓴다
- 바꿔 끼운 뒤 옛 화면의 요청: 남아 있는 소장은 정상으로 답한다
- 빠진 소장은 대출 현황 스트림에서 새 코드 `holding_not_found`로 알리고(도서관이 없거나 꺼진 `library_not_found`와 나눔), 책 화면 그 도서관 줄에 "이 도서관 목록에서 빠졌어요"를 보인다
- 빠진 책은 지금의 `book_not_found`로 답하고, "책을 찾을 수 없어요" 아래에 "도서관 목록을 새로 받으면서 빠진 책일 수 있어요. 다시 검색해 주세요."를 보인다
- ADR-0065의 "소장 번호는 지난번 최대 번호 다음부터 매긴다"는 이 기록으로 바뀐다

## 이유 (사용자 발언)
- "이건 중간 단계를 좀 넣어두는게 어떨까... 매핑 db이런걸로 그럴려면 요청에 버전 번호를 넣어야 할 것 같은데" (2026-10-11) → 이어 쓰기 안에 승인
- "승인인데 '책'정보가 사라진 경우에 맞는 메세지 나와야 해" (2026-10-11)
- 보일 말 두 가지와 이 초안: 승인 (2026-10-11)

## 검토한 대안
### A안: 같은 소장은 옛 번호를 이어 씀 (채택)
- 장점: 맞춤 표·버전 번호가 필요 없음, 열린 화면이 바꿔 끼운 뒤에도 그대로 동작
- 단점: 맞대기 결과를 소장 번호에도 써야 함(시간은 거의 같을 것으로 봄, 재지 않음)
### B안: 번호 맞춤 표(옛 → 새)
- 단점: 표 약 2천만 줄과 지울 규칙·찾는 코드가 더 생김. 새 번호가 옛 최대 다음부터라 버전 번호는 필요 없음
- 채택하지 않은 이유: 사용자가 A안을 승인 (2026-10-11)
### C안: 그대로 "찾을 수 없음"
- 단점: 바꿔 끼울 때마다 열린 화면이 실패
- 채택하지 않은 이유: 사용자가 A안을 승인 (2026-10-11)
