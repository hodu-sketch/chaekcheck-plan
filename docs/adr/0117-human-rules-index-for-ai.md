# ADR-0117: 사람이 정한 수집·가져오기·도서관 규칙은 코드·표 파일에 두고, 규칙 목록 문서로 찾고 검증하게 한다

Status: Accepted
Date: 2026-10-15
Cycle: 19-author-angle-brackets
Supersedes: 없음 (ADR-0085를 넓힘)

## 배경
수집·가져오기·도서관 넣기는 Claude 세션이 dev 운영 문서를 읽고 돌린다(dev `docs/maintenance/1-libraries.md` 114행). 도서관 규칙은 `scripts/library/rules/*.tsv`와 README 표로 찾기 쉽지만(ADR-0085), 수집기 Python 상수(`crawl_catalog.py` 맨 위)와 가져오기 Java 상수(`SameTextKey`의 판 낱말, `Contributors`의 역할 낱말 등)는 코드 안에 흩어져 있고 모아 둔 문서가 없다. 사이클 19가 규칙을 더 늘린다(공급사 묶음, 뒤바뀐 포털, 남길 낱말, 기호 떼기).

## 결정
사람이 정한 규칙의 내용은 지금처럼 코드 상수나 규칙 표 파일에 두되, dev에 규칙 목록 문서 하나(`docs/maintenance/rules-index.md` [안: 이름])를 두고 규칙마다 한 줄씩 적는다: 어디에 있나(파일·상수 이름) / 뜻 / 데이터로 맞는지 확인하는 법(가능하면 스크립트) / 바꾸는 법과 그 뒤 할 일(다시 수집 또는 다시 가져오기). 코드 상수마다 그 줄을 가리키는 주석을 달고, 수집기는 사람이 정한 값을 파일 맨 위 "규칙" 묶음에 모은다. 수집·가져오기 문서의 시작 점검 목록이 규칙 목록의 "확인하는 법"을 돌린다. 목록이 길어진 수집기 상수는 표 파일로 옮긴다.

## 이유 (사용자 발언)
- "이것도 수집기가 하는거고 ai가 md를 보고 잘 할 수 있도록 문서랑 python코드랑 잘 구조화 되어 있도록 방향 지침을 했으면 해" (2026-10-15)
- "이거 다른 세션에서 수집기 md로 검증할 때 규칙에 포함되었으면 하는데... 수집기 규칙대로하되 규칙이 변동이 가능해야 하는데 그 구조로 가야 해... python 코드에 있되 그것을 ai가 파악하기 쉽도록 되어 있어? 안 되면 그렇게 가야 해" (2026-10-15)
- 규칙 목록 문서 하나: 승인 (ADR 초안 확인 #1·#2, 2026-10-15), 이 초안: 승인 (설계 이어서 #1, 2026-10-15)

## 검토한 대안
### A안: 내용은 코드·표 파일, 찾기·검증은 규칙 목록 문서 (채택)
- 장점: 지금 코드를 크게 옮기지 않음, 바꾼 이력은 git에 남음, AI가 문서 ↔ 상수를 오감
- 단점: 규칙을 바꿀 때 목록 줄도 함께 고쳐야 함 → 시작 점검이 어긋남을 찾음
### B안: 모든 규칙을 표 파일로 옮김
- 장점: 한 곳에 모임, 빌드 없이 고침
- 단점: 수집기·가져오기 코드를 크게 고쳐야 하고 묶기 규칙의 시험이 파일에 기대게 됨
- 채택하지 않은 이유: [이유 미확인] (제안하지 않음)
### C안: 그대로 둠 (코드 주석만)
- 단점: 다른 세션이 수집·가져오기 할 때 이 규칙을 검증할 길이 없음
- 채택하지 않은 이유: 사용자 "안 되면 그렇게 가야 해"

## 결과
- 사이클 19 인계서에 규칙 목록 문서 만들기, 상수 주석, 시작 점검 한 줄을 넣음. 사이클 19의 규칙(ADR-0113·0114·0115)부터 적고, 이미 있는 규칙(도서관 규칙 README, 수집기·가져오기 상수)도 한 번 옮겨 적음
- plan `docs/reference-index.md`가 이 문서를 가리킴

## 나중에 분리할 때
- 수집·가져오기를 따로 떼면 규칙 목록도 그 서비스의 문서로 함께 감
