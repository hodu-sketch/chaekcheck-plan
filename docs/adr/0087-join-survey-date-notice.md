# ADR-0087: 가입 조건 조사 기준일은 하나만 기록하고, 서비스 안내 페이지 공지 한 줄로 보인다

Status: Accepted
Date: 2026-10-12
Cycle: 13-crawler-to-dev
Supersedes: 없음

> **미리 정함**: 사이클 13은 사이클 12(책 묶기 기준)가 끝나기 전에 나란히 진행해 정한 결정이다. dev에는 사이클 12 handoff 뒤에 넘긴다.

## 배경
사이클 12 세션이 "도서관 표에 날짜가 없다"는 질문을 넘겼다(backlog 206행). 확인해 보니 `created_at`·`updated_at`과 수집 사본 시각은 이미 있고, 없는 것은 가입 조건을 언제 조사했는지였다. 가입 조건 조사는 도서관을 한꺼번에 새로 세팅할 때 같이 하므로 날짜가 거의 하나다(지금 최신 2026-10-05).

## 결정
- 도서관 줄마다 날짜 칸을 더하지 않는다
- 기준일은 규칙 폴더의 한 줄 파일 `join_surveyed_on.txt`(ADR-0085)에 적고, 넣기 실행 기록 `library_insert_run.join_surveyed_on`에 남긴다 [안: 칸 이름]
- `GET /api/v1/join-survey` → `{"surveyedOn":"2026-10-05"}`(없으면 `null`) [안: 경로]. `/libraries` 응답에는 싣지 않는다
- 서비스 안내 페이지(`/about`) 첫 문단 아래에 "가입 조건은 2026년 10월에 조사한 내용입니다." 한 줄. 로딩 중에는 비워 두고, 기준일이 없거나 오류면 그 줄을 보이지 않는다
- 도서관마다 화면에 날짜를 보이지 않는다

## 이유 (사용자 발언)
- "공지 문구 용으로 하고 모든 전자도서관마다 데이터를 더하는 건 흠... 어짜피 새로 다 한꺼번에 세팅할건데 의미가 있나 싶어 최신 조사 날짜는 따로 기록해둬야지" (2026-10-12)
- "굳이 보여줄 필요는 없어. 어디 공지로 하자.." (2026-10-12)
- 날짜 한 줄 파일, 실행 기록에 남김, 공지 자리·문구: 사용자 승인 (2026-10-12)

## 검토한 대안
### A안: 기준일 하나 + 공지 한 줄 (채택)
- 장점: 표 변경이 작고, 한꺼번에 세팅하는 실제 방식과 맞음
- 단점: 도서관마다 조사일이 다를 때는 가장 최근 날짜만 보임
### B안: 도서관마다 날짜 칸 하나
- 장점: 도서관별 조사일을 알 수 있음
- 단점: 줄마다 같은 값이 반복됨
- 채택하지 않은 이유: "모든 전자도서관마다 데이터를 더하는 건 흠... 어짜피 새로 다 한꺼번에 세팅할건데 의미가 있나 싶어"
### C안: 가입 정보 창에 작게 보이기
- 채택하지 않은 이유: "굳이 보여줄 필요는 없어. 어디 공지로 하자.."
### D안: `/libraries` 응답에 기준일을 실음
- 단점: 큰 목록(약 874KB)에 실리고 `library → collection` 의존 고리가 생김
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 사용자가 가입 조건이 언제 기준인지 앎, 데이터 변경이 작음
- 감수하는 점: 도서관 일부만 다시 조사하면 공지 날짜가 그 일부를 기준으로 보임
- 나중에 되돌리거나 서비스로 분리할 때의 비용: 낮음
