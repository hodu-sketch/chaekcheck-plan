# ADR-0124: 이동진·서울대의 판은 수집기가 내 PC DB를 읽어 고르고(고정 판), 가져오기 파일을 만들 때 같은 파일의 책 표에 대고 맞춰 책 번호를 저장함. 서버는 읽기만

Status: Accepted (사용자 승인, 2026-10-16, 설계 정리 페이지)
Date: 2026-10-16
Cycle: 21-recommended-books
Supersedes: 없음

## 배경
서울대 100선처럼 판이 정해지지 않은 책은 "같은 책" 가운데 보유량이 가장 많은 판을 쓰고(scope #1), 판 고르기는 수집기가 한다(명세 결정 #5 "수집기가"). 사서추천도서는 서버가 따로 받기 때문에 서버 캐시 때 맞춘다(ADR-0090).

## 결정
- 수집기(Python)가 내 PC 서비스 DB(`catalog.book`·`book_contributor`·`library.lending_model`)를 읽기만 해서 판을 고르고 목록 파일 "고정 판" 칸에 적는다. 같은 입력으로 Java·Python 보유량 결과를 비교하는 시험을 둔다
- 사람이 적은 고정 판(`pinned_by = manual`)은 수집기가 덮어쓰지 않고, 수집기가 고른 판은 실행할 때마다 다시 고른다
- 가져오기 파일을 만들 때(내 PC) 같은 파일의 책 표(`catalog_next`)에 대고 고정 판을 맞춰 `list_book.book_id`에 저장한다. 운영 서버는 DB를 읽기만 한다(10분 메모리 캐시는 응답 속도용 그대로). 사서 줄은 지금처럼 서버 캐시 때 맞춘다

- "수집기가" (2026-10-15, 명세 결정 #5)
- "너무 이상한데 DB에서 서버가 값을 읽어서 보여주는게일반적인거 아니야? 왜 10분마다 맞춰줘야 해? 같이 맞춰주면 되는 거 아니야?" → 새 제안 선택 "추천을 바꿉니다: 가져오기 파일을 만들 때 같이 맞춰 책 번호를 저장하고, 서버는 DB를 읽어 보여 주기만 합니다." (2026-10-16, 설계 결정 #4)

## 검토한 대안
### A안: 가져오기 때 맞춰 책 번호 저장 (채택)
- 장점: 서버는 읽기만, 맞춘 결과를 반영 전에 기록으로 봄, 책 번호는 내 PC에서 정해지고(ADR-0078) 같은 책이면 이어 씀(ADR-0062). 단점: 한 표 안에 맞추는 방식이 둘(사서는 캐시 때)
### B안: 서버가 10분마다 고정 판 글자로 맞춤 (처음 추천)
- 채택하지 않은 이유: 사용자 "왜 10분마다 맞춰줘야 해? 같이 맞춰주면 되는 거 아니야?" (2026-10-16)
### C안: 판 고르기를 서버 명령(Java)이
- 채택하지 않은 이유: [이유 미확인] (추천하지 않은 안, "수집기가"를 그대로 따름)
