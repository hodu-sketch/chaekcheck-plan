# ADR-0011: 도서관 조회 전용 서비스를 분리하고 여러 대로 운영

Status: Accepted
Date: 2026-09-28
Cycle: 02-library-expansion
Supersedes: 없음

## 배경
사이클 02는 전국 도서관 수백 곳을 조회 대상에 넣고, robots.txt가 막은 도서관도 조회하기로 했다 (scope.md, research.md 9절). 도서관이 우리를 차단하면 조회만 멈추고 서비스는 계속 돌아야 하고, 도서관이 허용 목록에 넣을 수 있는 고정 주소가 있으면 좋다. 지금은 `availability` 모듈이 도서관 사이트를 직접 호출한다 (ADR-0001). dev 규칙상 서비스 분리는 사용자가 요청할 때만 하는데, 사용자가 요청했다.

## 결정
- 도서관 사이트 호출만 하는 **조회 서비스**를 본 서비스와 따로 두고, **여러 대**를 운영한다. 조회 서버마다 고정 IP를 쓴다.
- 조회 서버는 본 서비스가 보낸 요청을 도서관에 보내고 응답을 돌려주기만 한다. **캐시(ADR-0006)와 호출 간격 제어(ADR-0010)는 본 서비스 한곳에서 한다.** 조회 서버마다 따로 제어하면 도서관 한 곳에 서버 수만큼 동시에 요청이 가기 때문이다.
- 본 서비스는 조회 서버 한 대에 요청하고, 응답이 없으면 다른 조회 서버에 보낸다.
- 다른 조회 서버로 넘기는 기준: **조회 서버 자체가 죽었거나 본 서비스가 조회 서버에 연결하지 못할 때만** 넘긴다. 도서관이 거부(403 등)하거나 도서관 응답이 늦을 때는 넘기지 않고 그대로 실패로 처리한다. 넘기면 차단된 IP를 다른 IP로 피하는 것과 같아지기 때문이다.
- 모든 조회 서버는 같은 User-Agent로 우리를 밝힌다.

## 이유 (사용자 발언)
- "별도 서비스로 하고.. 안정성을 위해서 조회 전용 서버를 여러대 두고 그 중 한대에게 요청하고 응답이 없으면 다른 곳에 하는 식으로 안정성을 높이려고 해" (2026-09-28)
- "크롤링용 프록시 서버를 따로 두는 것을 고려하도록 해줘 접근용으로" (2026-09-28)
- 캐시·간격 제어를 본 서비스에 두는 것과 다른 서버로 넘기는 기준은 Claude 제안 → 사용자 승인 (2026-09-28)

## 검토한 대안
### A안: 조회 서비스 분리 + 여러 대, 간격 제어·캐시는 본 서비스 (채택)
- 장점: 조회 서버가 하나 죽어도 계속 조회함. 간격 규칙이 서버 수와 상관없이 지켜짐. 조회 서버는 상태가 없어 늘리기 쉬움
- 단점: 서버, 배포, 서비스 사이 통신이 늘어남. 본 서비스가 한 대라는 전제가 남음
### B안: 조회 서버마다 간격 제어·캐시
- 장점: 본 서비스가 단순함
- 단점: 도서관 한 곳에 서버 수만큼 동시에 요청이 감
- 채택하지 않은 이유: [이유 미확인]
### C안: 분리하지 않고 본 서비스 안에서 나가는 경로(고정 IP)만 둠
- 장점: 서비스가 하나로 유지됨
- 단점: 조회 쪽 장애나 차단이 본 서비스와 같은 서버에서 일어남
- 채택하지 않은 이유: "별도 서비스로 하고" (사용자)

## 결과
- 좋아지는 점: 조회 서버 장애에 강해짐. 도서관 호출이 한곳(조회 서버들)으로 모여 기록과 고정 주소 관리가 쉬움
- 감수하는 점: 운영할 서버가 늘어남. 조회 서버와 본 서비스 사이 요청·응답 형식, 인증, 상태 확인 방법을 정해야 함 [확인 필요]. 요청당 8초 제한에 조회 서버를 거치는 시간과 다른 서버로 넘기는 시간이 포함됨
- 조회 서버 대수, 배치 위치, IP는 정하지 않음 [확인 필요]
- 모듈 경계(ADR-0001): 조회 서비스가 맡는 것은 `availability` 안의 "도서관 사이트 호출" 부분뿐이다. adapter(HTML 해석)를 조회 서버와 본 서비스 중 어디에 둘지는 design-delta에서 정한다 [확인 필요]
- 설계에 넣지 않는 것: IP를 계속 바꿔 가며 차단을 피하는 방식, 다른 봇으로 위장하는 방식 (research.md 9절)
