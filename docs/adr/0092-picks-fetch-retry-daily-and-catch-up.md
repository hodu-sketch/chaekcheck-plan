# ADR-0092: 사서추천 받기는 실패하면 성공할 때까지 매일 다시, 놓친 주는 따라잡음

Status: Accepted
Date: 2026-10-12
Cycle: 14-librarian-picks
Supersedes: 없음 (ADR-0089 "받기"의 "다음 날 한 번 더"를 바꿈)

## 배경
ADR-0089는 받기를 매주 월요일 05:00에 하고, 실패하면 다음 날 한 번 더 받는다고 정했다. 설계 검토(2026-10-12)에서 월요일 05:00에 서버가 꺼져 있으면 그 주를 통째로 건너뛰는 빈틈이 나왔고, 이를 메우는 "따라잡기"(마지막 성공이 7일보다 오래됐으면 받음)를 더하자 "실패하면 다음 주까지 기다림"과 부딪혔다(월·화가 모두 실패하면 수요일부터 따라잡기가 걸림).

## 결정
- 05:00(Asia/Seoul)과 서버 시작 때 판단해, 하나라도 맞으면 요청 1건으로 받는다: ① 저장된 목록 없음 ② 월요일(05:00) ③ 마지막 받기가 실패이고 그 뒤 성공 없음(05:00) ④ 마지막 성공이 7일보다 오래됨(따라잡기, 시작 또는 05:00)
- 그래서 실패하면 성공할 때까지 하루 1건씩 다시 받는다. 같은 날 이미 성공했으면 받지 않는다
- `fetch_run.trigger`는 `STARTUP`·`SCHEDULED`·`RETRY`·`CATCH_UP`

## 이유 (사용자 발언)
- 따라잡기: "켜질 때 따라잡기 (추천)" (2026-10-12)
- 실패 뒤: "성공할 때까지 매일" (2026-10-12)

## 검토한 대안
### A안: 실패하면 성공할 때까지 매일 + 놓친 주 따라잡기 (채택)
- 장점: 규칙끼리 부딪히지 않음, 새 추천이 늦게 보이는 일이 적음
- 단점: 키가 막히거나 API가 바뀌면 매일 실패 기록이 한 줄씩 쌓임(요청은 하루 1건)
### B안: 실패는 화요일 한 번까지, 따라잡기는 아예 못 돈 주에만
- 장점: 요청이 가장 적음
- 단점: 규칙이 복잡함(못 돈 주와 실패한 주를 나눔), 최대 일주일 늦음
- 채택하지 않은 이유: [이유 미확인] (사용자가 A안을 고름)
### C안: 따라잡기 없음 (다음 월요일까지 기다림)
- 채택하지 않은 이유: [이유 미확인] (사용자가 따라잡기를 고름)

## 결과
- 좋아지는 점: 서버가 꺼져 있었거나 실패해도 다음 날 바로 회복
- 감수하는 점: 계속 실패하는 동안 실패 기록이 매일 쌓임. 알림은 없음(backlog)
- 나중에 서비스로 분리할 때: 영향 없음
