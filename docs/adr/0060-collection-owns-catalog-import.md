# ADR-0060: 가져오기는 `collection`이 맡고, 제목 다듬기 규칙은 `catalog`에 한 벌만 둔다

Status: Accepted
Date: 2026-10-05
Cycle: 07-candidate-libraries
Supersedes: 없음

## 배경
ADR-0052로 새 모듈 `collection`을 만들고 짝 표를 맡겼지만, 설계 초안은 가져오기 코드(수집 DB 읽기 → 정리 → 같은 책 묶기 → 표 채우기)를 사이클 04 그대로 `catalog`에 두었다(ADR-0031). 사용자는 `collection`을 "새로 수집된 것을 DB에 추가할 때 용"으로 만든 것이라고 했다. 한편 제목·저자·출판사를 다듬는 규칙(띄어쓰기 없애기, 본제목 떼기, 출판사 다듬기, 저자 나누기)은 같은 책 묶기와 책 검색이 둘 다 쓴다. 모듈끼리 서로 부르는 고리는 만들 수 없다.

## 결정
가져오기 일 — 수집 DB 사본 읽기(나눠 읽기), 짝 표로 서비스 번호 바꾸기, 빼는 줄 거르기, 같은 책 묶기, 대표값·날짜 규칙, 책마다 가진 도서관 번호 계산, 가져오기 기록 — 은 `collection`이 맡는다. `catalog`는 책·사람·소장 표와 책 검색을 가지고, 공개 기능 "받은 책·사람·소장으로 표를 통째로 바꾸기"를 내준다(쓰기·정리 작업은 `catalog` 안에서). 제목 다듬기 규칙은 `catalog`에 한 벌만 두고 공개하며, `collection`은 묶기에 이것을 빌려 쓴다. 모듈 방향: `collection → catalog`, `collection → library`, `catalog → library`. ADR-0052의 범위를 넓히고, ADR-0031의 "가져오기는 `catalog` 안" 부분을 바꾼다(정리 코드 한 벌 원칙은 유지).

## 이유 (사용자 발언)
- "나는 새로 수집 된 것으 DB에 추가할 때 용으로도 collection했는데 뭔가 다르게 된 건가...?????" (2026-10-05)
- "가져오기(수집 DB 읽기 → 정리 → 같은 책 묶기 → 표 채우기)도 나는 이걸 컬렉션이 하는게 맞다고 보는데......" (2026-10-05)
- 규칙 자리: "(가) catalog에 두고 collection이 빌려 씀 … 이걸로 해줘" (2026-10-05)

## 검토한 대안
### A안: 가져오기는 `collection`, 규칙은 `catalog`에 두고 빌려 씀 (채택)
- 장점: 수집 쪽 일이 한 모듈에 모임(앞으로 갱신도 여기서), 규칙 한 벌, 고리 없음, 규칙 파일을 옮기지 않음
- 단점: `catalog`에 "표 통째로 바꾸기" 공개 기능이 새로 생기고, 가져오기 코드를 옮기는 일
### B안: 규칙도 `collection`에 둠
- 장점: 수집 쪽이 규칙까지 가짐
- 단점: 검색이 `collection`을 부르고 `collection`이 `catalog`에 책을 넘겨 고리가 생김. 피하려면 가져오기 흐름을 뒤집어야 함
- 채택하지 않은 이유: [이유 미확인] (사용자가 A를 고름)
### C안: 작은 공용 모듈("제목 다듬기")에 규칙을 두고 둘 다 빌려 씀
- 장점: 규칙이 어느 한쪽 것이 아님이 드러남, 고리 없음
- 단점: 모듈 하나가 더 늘고 규칙 파일을 옮김
- 채택하지 않은 이유: [이유 미확인]
### D안: `collection`은 짝 표만, 가져오기는 `catalog`에 그대로
- 장점: 바뀌는 것이 가장 적음
- 단점: 수집 연결 일이 두 모듈에 흩어짐
- 채택하지 않은 이유: "새로 수집 된 것으 DB에 추가할 때 용으로도 collection했는데"

## 결과
- 좋아지는 점: "수집 → 서비스로 가져오기"가 `collection` 한 곳에서 보임. 갱신 기능을 만들 자리가 정해짐
- 감수하는 점: `collection`이 `catalog`의 책 표 모양(넘기는 데이터)과 규칙을 알아야 함. 이번 사이클에 가져오기 코드를 옮기는 일이 더해짐
- 나중에 분리할 때: `collection`은 "수집 연결" 서비스, `catalog`의 "표 바꾸기"는 그 서비스가 부르는 쓰기 API가 됨
