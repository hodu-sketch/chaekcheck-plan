# ADR-0048: 둘째 회원 모듈은 "내 도서관" 전용 `mylibrary`

Status: Accepted
Date: 2026-10-04
Cycle: 06-my-libraries
Supersedes: 0036

## 배경

ADR-0036(2026-10-01)은 로그인(`auth`)과 회원 자료(`member`: 지역, 직접 고른 도서관, 나중에 관심 책)를 다른 모듈로 나눴습니다. 사이클 06 명세를 정하면서 사용자가 `member` 대신 "도서관과 사용자를 잇는 일"만 맡는 모듈을 물었고, 그렇게 정했습니다(`docs/cycles/06-my-libraries/spec.md` R8-1). 제약: 모듈끼리는 공개 API나 이벤트로만 통하고 서로의 표를 건드리지 않습니다(ADR-0001). 검색 모듈은 회원을 모릅니다(ADR-0037).

## 결정

로그인(`auth`)과 내 도서관(`mylibrary`, 패키지 `com.chaekcheck.mylibrary`, 스키마 `mylibrary`)을 다른 모듈로 둡니다. `mylibrary`는 계정의 거주·직장 지역과 직접 추가한 도서관만 맡고, 알림의 관심 책은 넣지 않습니다. `auth`에는 계정 번호 `AccountId`, 탈퇴 이벤트 `AccountDeleted`, 계정 줄 잠금(ADR-0051)으로만 기댑니다.

## 이유 (사용자 발언)

- "member말고 도서관-사용자 매핑용 모듈은?" → "매핑 전용 모듈로" (2026-10-04)
- 이름 `mylibrary`는 제안 → 승인(2026-10-04). 그 밖의 이유 [이유 미확인]

## 검토한 대안

### A안: `mylibrary` (채택)
- 장점: 화면 이름 "내 도서관", 주소 `/my-libraries`와 같은 말. 맡은 일이 이름에 드러나 다른 회원 자료가 들어오기 어려움
- 단점: 지역 저장도 있어 이름보다 조금 넓음(지역은 도서관을 고르는 입력이라 범위 안으로 봄)

### B안: `member` 그대로 (ADR-0036)
- 장점: 기존 문서를 덜 고침
- 단점: 관심 책 등 회원 자료가 모두 들어올 자리가 됨
- 채택하지 않은 이유: 사용자가 매핑 전용 모듈을 고름 ("매핑 전용 모듈로")

### C안: `patron`
- 장점: 도서관 용어
- 단점: 사람에 관한 자료가 모두 들어올 자리처럼 보임
- 채택하지 않은 이유: [이유 미확인]

### D안: 도서관 모듈(`library`) 안에 둠
- 장점: 모듈 수가 늘지 않음
- 단점: 여러 검색이 함께 쓰는 도서관 모듈이 계정을 알게 되어 ADR-0037과 섞임
- 채택하지 않은 이유: [이유 미확인] (결정 페이지에서 권하지 않은 안)

## 결과

- 좋아지는 점: `auth`는 여전히 다른 모듈을 모름. 알림 사이클의 관심 책은 새 모듈(예: `notification`)에 두므로 `mylibrary`를 건드리지 않음
- 감수하는 점: 회원 자료 모듈이 알림 때 하나 더 생김
- 나중에 분리할 때: `auth` 서비스와 "내 도서관" 서비스. 탈퇴 이벤트는 그때 외부 브로커로 내보냄. 계정 줄 잠금은 쓸 수 없으므로 ADR-0051의 "나중에 나눌 때"를 따름
