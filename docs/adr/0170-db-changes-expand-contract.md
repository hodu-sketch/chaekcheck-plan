# ADR-0170: DB 변경은 옛 판·새 판이 같이 돌아도 되는 것만, 아니면 두 번에 나누거나 점검 배포

Status: Accepted
Date: 2026-10-29
Cycle: 27-zero-downtime-deploy
Supersedes: 없음

## 배경
블루·그린(ADR-0167)에서는 새 판이 시작할 때 Liquibase를 돌리고, 옛 판은 바뀐 DB에서 최대 약 1분 더 돈다. 옛 판은 `ddl-auto: validate`로 시작 때만 표를 검사하므로 그 뒤 바뀐 구조를 모른다. `runOnChange`로 함수·트리거 본문을 바꾸는 changeset도 있어 옛 판이 즉시 새 함수를 쓴다. 새 판이 준비에 실패해도 이미 돈 변경은 남는다.

## 결정
무중단 배포에는 옛 판이 그대로 돌 수 있는 DB 변경만 싣는다(추가, 옛 판이 안 쓰는 것 지우기, 옛 판과 같은 결과의 함수 본문). 칸 이름 바꾸기·지우기·타입 바꾸기는 두 번의 배포로 나눈다(1차 새 칸 추가·둘 다 씀, 2차 옛 칸 지움). 나눌 수 없으면 짧은 중단을 알리는 점검 배포(지금 방식)로 하고, 인계서에 그렇다고 적는다. 이 규칙은 사이클 27 이후 모든 사이클의 설계·인계에 적용한다.

## 이유 (사용자 발언)
- 범위 결정 #4 승인 (2026-10-29). 이유는 말하지 않음 [이유 미확인]

## 검토한 대안
### A안: 같이 돌아도 되는 변경만 + 두 번 나누기 + 점검 배포 (채택)
- 장점: 대부분의 배포가 무중단, 예외는 명시
- 단점: 큰 변경은 배포가 두 번
### B안: 모든 배포를 무중단으로 (나누지 않고 강행)
- 단점: 바뀐 표에서 옛 판이 오류를 낼 수 있음
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 옛 판이 도는 동안 DB 오류 없음, 새 판 실패 때도 사이트 유지
- 감수하는 점: 설계(design-delta)마다 변경이 어느 쪽인지 적어야 함, 큰 변경은 배포 두 번
- 나중에 되돌리거나 서비스로 분리할 때의 비용: 없음. 서비스를 나눠도 같은 규칙이 필요함
