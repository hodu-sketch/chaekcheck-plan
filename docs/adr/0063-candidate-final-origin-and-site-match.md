# ADR-0063: 후보 도서관은 최종 주소를 쓰고, 가져오기는 호스트·경로로 같은 사이트를 확인한다

Status: Accepted
Date: 2026-10-05
Cycle: 07-candidate-libraries
Supersedes: 없음 (ADR-0052 보완)

## 배경
수집 DB에는 도서관 목록에서 찾은 주소(대개 http)가 있다. 우리 서버는 다른 주소로 넘기는 응답(리다이렉트)을 따라가지 않아서, https로 넘기는 후보 도서관 사이트는 늘 실패했다(강동대학교 북큐브). 책 상세 주소도 http라 책 화면의 대출 확인이 실패했다. 인계서는 가져오기가 수집 주소와 서비스 주소의 `base_url`이 같은지 보게 했다(C10). 결정은 사이클 07 개발 중에 했고(dev `docs/plan-feedback.md` "handoff 밖 추가 작업 A"), 기록은 회고에서 남긴다.

## 결정
- 후보 도서관의 서비스 주소는 리다이렉트를 따라간 최종 주소로 둔다(248곳이 https로 바뀜, `scripts/library/CheckFinalOrigins.java`). 등록 도서관에 하던 최종 주소 확인(dev `library-maintenance.md` 4-7)을 후보에도 한다.
- 가져오기는 수집 주소와 서비스 주소를 호스트·경로·쿼리로 비교한다. http/https와 포트 차이는 같은 사이트로 본다(`CollectedCatalog.sameSite`).
- 책 상세 주소는 서비스 도서관 주소의 http/https·포트로 옮겨 쓴다(`CollectedCatalog.onOrigin`).

## 이유 (사용자 발언)
- 사용자 보고: 강동대학교 북큐브가 "검색해도 안나오고" (2026-10-05, dev 기록)
- 바꾸는 방법 자체에 대한 사용자 말은 없음 [이유 미확인]
- 기록: 사이클 07 회고 결정 기록 초안 승인 (2026-10-05)

## 검토한 대안
### A안: seed에 최종 주소, 가져오기는 호스트·경로 비교 (채택)
- 장점: 요청이 늘지 않음, 다른 호스트로 넘어가는 것을 막는 안전장치(`UrlGuard`)와 부딪히지 않음
- 단점: 리다이렉트로 호스트까지 바뀐 곳은 여전히 걸림(도서관 411, 소장 64,461줄 빠짐)
### B안: 서비스가 요청할 때마다 리다이렉트를 따라감
- 장점: 주소가 바뀌어도 자동으로 따라감
- 단점: 요청이 한 번씩 늘고, 다른 호스트로 넘어가는 것을 막는 안전장치와 부딪힘
- 채택하지 않은 이유: [이유 미확인]
### C안: 수집 DB 주소를 고침
- 장점: 두 DB 주소가 같아짐
- 단점: 돌고 있는 수집기가 쓰는 주소가 바뀜
- 채택하지 않은 이유: [이유 미확인]
