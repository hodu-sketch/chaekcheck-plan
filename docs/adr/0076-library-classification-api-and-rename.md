# ADR-0076: 도서관 분류 값은 API로 보내고 화면이 글자를 만듦, 이름은 번호로 고치는 changeset, 이름 찾기는 화면에서

Status: Accepted
Date: 2026-10-11
Cycle: 09-library-naming
Supersedes: 없음 (ADR-0071을 이어서 구현 방식을 정함. `docs/current/api.md`의 "`lendingModel`은 웹에 보내지 않음" 기록을 바꿈. ADR-0019 "화면은 화면 종류로 갈리지 않음"은 그대로 지킴)

## 배경
ADR-0071로 이름에서 괄호를 떼고 업체·대출 방식·순번을 분류로 두기로 했다. 그 값을 화면에 어떻게 보낼지, 이미 넣은 이름 약 293곳(겹침 빼기 전)을 어떻게 고칠지, 직접 추가 이름 찾기를 어디서 바꿀지 정해야 했다. 사이클 08은 이름 8곳을 seed를 다시 만들지 않고 번호로 UPDATE하는 changeset(013)으로 고쳤다.

## 결정
- 도서관 목록(`GET /api/v1/libraries`)과 검색·대출 현황 스트림의 `targets.libraries[]`에 `vendor`, `lendingModel`(통합 포털은 null), `orderNo`를 보낸다. 우리말 글자("교보 · 소장", "· 2번째 사이트")는 웹이 만든다. 값이 없으면 이름만 보인다.
- 이미 있는 이름은 새 changeset(`library/014`)에서 번호와 옛 이름이 맞을 때만 UPDATE한다. 적용된 seed는 고치지 않는다. 목록은 `name_overrides.tsv`에 이어 적는다.
- S10 직접 추가 이름 찾기는 웹에서만 바꾼다(목록을 한 번 받아 브라우저에서 찾는 ADR-0058 그대로). 낱말마다 이름 또는 분류 글자에 있으면 맞는다.

## 이유 (사용자 발언)
- 세 결정 모두 제안 → 승인 (2026-10-11, `docs/cycles/09-library-naming/easy/2026-10-11-design-decisions.html`). 이름 찾기는 맥락 설명을 읽은 뒤 승인

## 검토한 대안
### A안: 값을 보내고 웹이 글자를 만듦 (채택)
- 장점: `eligibility`·`joinSurvey`처럼 지금 방식과 같음, 글자를 바꿀 때 웹만 고침
- 단점: 목록 응답이 압축 전 약 130KB 늘 것으로 추정(확인 필요)
### B안: 서버가 "교보 · 소장" 글자를 보냄
- 단점: 화면 문구가 서버에, 같은 이름끼리 업체순 정렬에 값이 따로 필요
- 채택하지 않은 이유: [이유 미확인]
### C안: `platformType`만 보내고 웹이 업체를 계산
- 단점: 대응표가 웹에도 생김, ADR-0019와 맞지 않음
- 채택하지 않은 이유: [이유 미확인]
### D안: 이미 넣은 seed 파일을 직접 고침
- 단점: 로컬 DB를 다시 만들고 책 목록을 다시 가져와야 함, 사이클 08 방식과 갈림
- 채택하지 않은 이유: [이유 미확인]
### E안: 서버에 도서관 찾기 API를 만듦
- 단점: ADR-0058 방식을 바꾸고 서버와 웹을 함께 고침
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: DB를 다시 만들지 않음, 화면 문구가 웹 한 곳에
- 감수하는 점: 목록 응답이 커짐, `name_overrides.tsv`가 길어짐(첫 배포 직전 seed 정리 때 합침, backlog)
- 나중에 분리할 때: `library` 서비스 응답의 칸이 됨. 영향 없음
