# ADR-0119: 크롬 확장은 "사용자 쪽 조회 서버"다 — 화면이 원본을 올리고 서버가 해석·검사한다

Status: Proposed
Date: 2026-10-16
Cycle: 20-lookup-status-and-extension
Supersedes: 없음

## 배경
조회 부담을 사용자 쪽으로 옮기되(사이클 20 범위 #5), 도서관 페이지 해석 코드(adapter 9종)는 한 곳에 두고, 가짜 결과가 3분 공유 캐시를 더럽히지 않아야 한다. 조회 서버(ADR-0015)는 "URL을 받아 상태 코드와 원본 바이트만 돌려주는" 약속이며, 확장에도 같은 약속을 쓸 수 있다. dev 코드 확인(2026-10-15): 통합 포털 줄은 판정이 비면 서버가 책 상세 페이지를 한 번 더 부르고, 소장 묶음은 처음부터 상세 페이지를 부른다. 확장 ↔ 화면 메시지는 JSON(base64)만 오간다(크롬 공식 문서).

## 결정
- 확장은 도서관 페이지를 GET만 해서 화면(port)에 돌려주고 **우리 API를 모른다**. 화면이 서버의 계획 입구 셋으로 원본 바이트를 올린다: `POST /api/v1/ebook-searches/plans`(책 화면은 `/api/v1/book-availabilities/plans`) → `POST /api/v1/lookup-plans/{planId}/items/{itemId}`(원본 그대로, 응답에 결과 이벤트와 포털용 상세 주소) → `POST /api/v1/lookup-plans/{planId}/close`. **확장 모드는 서버 캐시를 읽지 않는다**: 계획 응답은 모든 도서관 주소를 주고, 사용자는 자기 브라우저가 받은 결과만 본다. 서버는 올라온 결과를 해석해 캐시에 넣기만 하여 다른 사용자가 3분 재사용한다(빈 칸이면 넣고, 확장 출처 값은 갱신, 서버 출처 값은 덮지 않음). 「더 보기」도 같은 입구로.
- 서버는 `LibraryPageFetcher`·`DetailPageFetcher`에 **받은 응답을 넣는 입구(`accept`)**를 달아 해석 → 캐시 → 결과 줄 → 판정을 서버 모드와 같은 코드로 하고(포털 상세 조회는 "상세 주소 뽑기"와 "받은 상세로 판정" 2단계로 나눔), `SearchSlots`와 호스트 throttle은 쓰지 않는다.
- 올라온 바이트는 본문을 읽기 전에 ⑥ `Origin`(설정의 허용 origin과 대조) → ⑨ IP 잠금 → ①⑤ 계획 있음·쪽 번호·처음·만든 IP(`X-Real-IP`, IPv6는 /64)와 같음 → ② `Content-Length` 상한·`Content-Encoding` 없음 → 동시 해석 자리 순으로 거르고, 그 뒤 상한까지만 읽어 ② status 200 → ③ adapter 해석(⑩ adapter는 계획 URL로만) → ⑪ `detailUrl`·상세 주소는 도서관과 같은 호스트만(서버 모드 `DetailLookupResolver`에도 같은 검사) → ④ 캐시 넣기(빈 칸이면 넣음, 서버 출처·진행 중인 서버 로드는 덮지 않음). 400 `invalid_plan`은 계획 문제(없음·만료·지워짐·쪽 번호·중복·IP·Origin)에만 쓰고, 해석 실패·status≠200·TIMEOUT·ERROR는 그 도서관만 200 `library-failed`(캐시 안 넣음). ⑦ IP별 계획 한도(nginx 계획 구역) ⑧ 캐시 값에 출처 `via=extension`·시각(비우기는 서비스 재시작) ⑨ 계획 문제로 인한 실패를 IP별로 세어 `rejected_event`(새 공개 `UsageLog.recordRejected`, IP·이유마다 1분 1줄, 원본 없음)에 남기고 한도를 넘으면 잠시 막음. 세 POST는 CSRF 머리(`csrf.spa()`). 확장은 `sender.origin` 대조, http(s)·GET·공개 호스트·기본 포트만, 전역 호스트 큐, 스트림으로 읽어 상한에서 중단. (2026-10-16 세 관점 검토로 고침, ADR이 Proposed라 본문을 고침)
- 바이트 상한은 상수가 아니라 설정 하나(`chaekcheck.availability.max-body-size`, 지금 4MB)로, nginx `client_max_body_size`도 배포 변수 하나(`LOOKUP_MAX_BODY_MB`)에서 템플릿으로 같은 값. 올리기 경로는 nginx 별도 요청 수 구역.
- 사용 기록은 `library_response_daily.source=extension`(CHECK를 새 changeset으로 다시 걺).

## 이유 (사용자 발언)
- "그런데 조작되지 않도록 보안에 신경써줘", "이것말고도 보안적으로 막을 수 있는 방법 있으면 넣어줘" (2026-10-15~16)
- "이거 상수인데 옵션으로 빼서 옵션으로도 가능하게 해주라" (2026-10-16)
- "확장에서 가져온 해당 도서관의 대출 정보를 캐시로 사용할 수 있었으면 해" (2026-10-15)
- 서버 해석 유지: "(가) 서버가 해석 (지금 결정)" (2026-10-16, 설계 #13)
- 확장 모드는 캐시를 읽지 않음: "확장은 어짜피 사용자로 접근하는거니 사용자걸로 보여주고 그 결과만 우리 서버가 캐시로 가져가면 되는 거 아닐까?" (2026-10-16; 처음 설계 #4의 "캐시에 있으면 결과를 바로 줌"을 바꿈)
- 나머지(화면이 올림, JSON 입구 셋, accept 입구, 빈 칸만, 더 보기): 제안 → 승인 [이유 미확인]

## 검토한 대안
### A안: 화면이 올림 + 서버 해석(accept) + JSON 입구 셋 + 검사·보안 장치 (채택)
- 장점: 확장이 API를 몰라 API를 바꿔도 재심사 불필요, 해석 코드 한 벌, 가짜 검사 가능, 연결을 붙들지 않음
- 단점: 바이트가 base64 메시지를 거침(최대 약 322KB), 서버가 해석 메모리를 잠깐 씀, 포털 2단계로 왕복이 늘어남
### B안: 확장이 서버에 직접 올림
- 장점: 메시지를 거치지 않음
- 단점: 확장이 API 경로·판에 묶여 바꿀 때마다 재심사, CSRF 예외·확장 origin CORS 확인
- 채택하지 않은 이유: [이유 미확인] (제안 → 승인)
### C안: 확장이 해석해 결과만 올림
- 장점: 서버 메모리 거의 0
- 단점: adapter를 자바·자바스크립트 두 벌로 유지, 가짜 검사 불가(보낸 숫자를 믿어야 함), 판정 규칙까지 확장에
- 채택하지 않은 이유: 사용자가 (가) 서버 해석을 고름
### D안: 지금 SSE 스트림에 확장 모드 끼우기
- 장점: 화면 이벤트 처리 그대로
- 단점: 검색마다 연결·`SseEmitter`를 최대 35초 유지, 두 통로를 짝지어야 함, nginx 도서관 호출 구역에 걸림
- 채택하지 않은 이유: [이유 미확인] (제안 → 승인)
### E안: 업로드를 기다리는 가짜 SiteFetcher
- 장점: 검색 코드가 글자 그대로
- 단점: 서버 throttle 줄에 사용자 IP가 섞이고, 기다리는 스레드와 밀어주기 통로가 필요
- 채택하지 않은 이유: [이유 미확인] (제안 → 승인)
### 캐시 오염: (가) 그대로 / (나) 빈 칸만 / (다) 그 사람에게만
- (나)에 검사를 더한 안을 채택. (다)는 "확장도 캐싱"과 어긋남 [이유 미확인] (제안 → 승인)

## 결과
- 좋아지는 점: 확장 사용자는 서버 자리와 무관하게 검색(빨강이어도), 결과는 서버 캐시로 다른 사용자와 공유, 해석·판정이 서버 모드와 같음
- 감수하는 점: 페이지 모양을 흉내 낸 가짜는 3분 노출될 수 있음(⑧로 치움). 계획 번호·IP 묶기 등 검사 코드가 늘어남. 사이클 17 nginx 파일에 올리기 경로 조각(템플릿)을 더해야 함
- 나중에 되돌리거나 서비스로 분리할 때: 확장 해석(C)으로 가려면 adapter를 JS로 옮기는 큰 일. 나중에 분리할 때 계획 입구는 조회를 맡는 쪽을 따라감
