# ADR-0119: 크롬 확장은 "사용자 쪽 조회 서버"다 — 화면이 원본을 올리고 서버가 해석·검사한다

Status: Accepted (2026-10-17, 사용자 승인 — 사이클 20 마무리 확인)
Date: 2026-10-16
Cycle: 20-lookup-status-and-extension
Supersedes: 없음

## 배경
조회 부담을 사용자 쪽으로 옮기되(사이클 20 범위 #5), 도서관 페이지 해석 코드(adapter 9종)는 한 곳에 두고, 가짜 결과가 3분 공유 캐시를 더럽히지 않아야 한다. 조회 서버(ADR-0015)는 "URL을 받아 상태 코드와 원본 바이트만 돌려주는" 약속이며, 확장에도 같은 약속을 쓸 수 있다. dev 코드 확인(2026-10-15): 통합 포털 줄은 판정이 비면 서버가 책 상세 페이지를 한 번 더 부르고, 소장 묶음은 처음부터 상세 페이지를 부른다. 확장 ↔ 화면 메시지는 JSON(base64)만 오간다(크롬 공식 문서).

## 결정
- 확장은 도서관 페이지를 GET만 해서 화면(port)에 돌려주고 **우리 API를 모른다**. 화면이 서버의 계획 입구 셋으로 원본 바이트를 올린다: `POST /api/v1/lookup-plans/searches`(책 화면은 `/api/v1/lookup-plans/holdings`, 「더 보기」는 `/api/v1/lookup-plans/more`; 끝 이름 [안: dev가 맞춤]) → `POST /api/v1/lookup-plans/{planId}/items/{itemId}`(원본 그대로, 응답에 결과 이벤트와 포털용 상세 주소) → `POST /api/v1/lookup-plans/{planId}/close`. **계획·올리기·닫기 주소는 모두 `/api/v1/lookup-plans` 밑**: 번호 쿠키 `Path`가 하나로 되고 nginx `location ^~ /api/v1/lookup-plans/` 블록 하나로 한도를 건다 (사이클 20 전반 점검 #11, 사용자 승인 2026-10-17; 설계 결정 #6의 `/api/v1/ebook-searches/plans`·`/api/v1/book-availabilities/plans`·`/api/v1/availability/libraries/{libraryId}/ebooks/plans`를 바꿈 — 넷째 주소는 쿠키가 서버 모드 「더 보기」 GET에도 붙고, dev nginx `location ^~ /api/v1/availability/`에 걸려 계획 한도 대신 도서관 호출 한도(1분 30)를 받았음). **확장 모드는 서버 캐시를 읽지 않는다**: 계획 응답은 모든 도서관 주소를 주고, 사용자는 자기 브라우저가 받은 결과만 본다. 서버는 올라온 결과를 해석해 캐시에 넣기만 하여 다른 사용자가 3분 재사용한다(빈 칸이면 넣고, 확장 출처 값은 갱신, 서버 출처 값은 덮지 않음). 「더 보기」도 같은 입구로.
- 서버는 `LibraryPageFetcher`·`DetailPageFetcher`에 **받은 응답을 넣는 입구(`accept`)**를 달아 해석 → 캐시 → 결과 줄 → 판정을 서버 모드와 같은 코드로 하고(포털 상세 조회는 "상세 주소 뽑기"와 "받은 상세로 판정" 2단계로 나눔), `SearchSlots`와 호스트 throttle은 쓰지 않는다.
- 올라온 바이트는 본문을 읽기 전에 ⑥ `Origin`(설정의 허용 origin과 대조) → 브라우저 번호 쿠키가 장부에 있음 → 장부의 받은 IP(`X-Real-IP`, IPv6는 /64) = 지금 IP → ⑨ 번호 잠금 → ①⑤ 계획 있음·쪽 번호·처음·계획을 만든 번호와 같음 → ② `Content-Length` 상한·`Content-Encoding` 없음 → 해석 자리(서버 모드와 함께 쓰는 하나, 8, 전반 점검 #4) 순으로 거르고, 그 뒤 상한까지만 읽어 ② status 200 → ③ adapter 해석(⑩ adapter는 계획 URL로만) → ⑪ `detailUrl`·상세 주소는 도서관과 같은 호스트만(서버 모드 `DetailLookupResolver`에도 같은 검사) → ④ 캐시 넣기(빈 칸이면 넣음, 서버 출처·진행 중인 서버 로드는 덮지 않음). 400 `invalid_plan`은 계획 문제(없음·만료·지워짐·쪽 번호·중복·번호 다름·Origin)에만 쓰고, 번호 쿠키 없음·장부에 없음은 400 `invalid_client_key`, 받은 IP와 다름은 400 `client_ip_changed`(두 이름 [안]), 해석 실패·status≠200·TIMEOUT·ERROR는 그 도서관만 200 `library-failed`(캐시 안 넣음). ⑦ 공인 IP별 계획 한도(nginx 계획 구역, 큰 울타리) ⑧ 캐시 값에 출처 `via=extension`·시각(비우기는 서비스 재시작) ⑨ 계획 문제로 인한 실패를 브라우저 번호별로 세어(IP 단위 거절은 없음, 전반 점검 #12) `rejected_event`(새 공개 `UsageLog.recordRejected`, IP·이유마다 1분 1줄, 원본 없음)에 남기고 한도를 넘으면 잠시 막음. 세 POST는 CSRF 머리(`csrf.spa()`). 확장은 `sender.origin` 대조, http(s)·GET·공개 호스트·기본 포트만, 전역 호스트 큐, 스트림으로 읽어 상한에서 중단. (2026-10-16 세 관점 검토로 고침, Accepted 전에 본문을 고침)
- 바이트 상한은 상수가 아니라 설정 하나(`chaekcheck.availability.max-body-size`, 지금 4MB → 1MB, 세 관점 검토 #7)로, nginx `client_max_body_size`도 배포 변수 하나(`LOOKUP_MAX_BODY_MB`)에서 템플릿으로 같은 값. 올리기 경로는 nginx 별도 요청 수 구역.
- 사용 기록은 `library_response_daily.source=extension`(CHECK를 새 changeset으로 다시 걺). 서버 대행 목록 도서관은 `server_for_extension`(검토 #16).
- **사람(브라우저)마다 세기** (세 관점 검토 #22, 사용자 승인 2026-10-16): 계획은 만든 브라우저 번호로만 올리기·닫기·지우기, 열린 계획 20과 10분 잠금은 번호별, 공인 IP는 울타리로만.
- **브라우저 번호는 서버가 주고 서버 장부로 관리** (검토 #27·#32, 사용자 승인 2026-10-16): 서버가 무작위 번호(16바이트)를 만들어 메모리의 브라우저 번호 장부(번호 → 받은 공인 IP(/64)·받은 시각·열린 계획 수·계획 무게 합·최근 실패)에 적는다. 서명(HMAC)은 쓰지 않는다 — 장부에 없는 번호는 거절. 요청마다 "장부에 있나 + 받은 IP = 지금 IP"를 보고, IP가 다르면 400(이름 [안] `client_ip_changed`) → 화면이 조용히 새 번호를 받아 남은 도서관만 다시 계획(잠금에 안 셈). 장부 상한 5만 줄·받은 지 1일, 값은 설정. **장부가 차면 가장 오래 안 쓴 줄을 밀어내고**(503 아님) 밀려난 사람은 다음 올리기·닫기에서 400 `invalid_client_key` → 화면이 조용히 새 번호를 받아 남은 도서관만 다시 계획 (전반 점검 #10, 사용자 승인 2026-10-17). 서버를 다시 켜면 장부가 비고 화면은 자동으로 새 번호를 받는다. 화면이 번호를 만드는 처음 안(#22의 "탭마다 무작위 열쇠")과 "계획을 만든 IP와 같음" 검사(처음 설계)는 이것으로 바뀐다.
- **번호는 HttpOnly 쿠키로** (검토 #33, 사용자 승인 2026-10-16): `HttpOnly`·`Secure`·`SameSite=Strict`, `Path=/api/v1/lookup-plans` 하나(전반 점검 #11), 수명 1일(설정). 자바스크립트는 번호를 보지 못하고, 머리글 `X-Lookup-Client`는 없앤다. CORS는 열지 않음(기본 거절). POST의 CSRF 머리(`X-XSRF-TOKEN`)는 그대로. 근거: MDN Set-Cookie (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie , 2026-10-16 확인).
- **공인 IP 울타리 둘** (검토 #31, 사용자 승인 2026-10-16, 장부로 셈; 전반 점검 #12로 셋째를 뺌, 사용자 승인 2026-10-17): ① 그 IP에 준 번호들의 계획 무게 합 > 보관함의 20%(25,000 중 5,000) ② 한 IP에 새 번호 1분 30개 초과. (처음의 ③ "그 IP의 잠긴 번호 5개 이상 → IP 10분 거절"은 ①·②·번호 잠금과 겹치고 같은 IP의 정상 사용자까지 막을 수 있어 뺌. 남용은 ①·②·번호 잠금과 거절 기록으로 봄.) 둘 다 그 IP의 새 계획 요청만 거절(429, 코드 이름 [안])하고 화면은 「잠시 후 다시」 — 서버 모드로 넘기지 않음, 다음 검색은 다시 확장 모드. #22의 "공인 IP당 열린 계획 200"은 ①로 바뀜. 숫자는 바깥 표준이 없어 우리 설계 숫자에서 계산(근거·계산은 `docs/settings-index.md` 6절).
- **남의 계획을 밀어내지 않음** (검토 #8, 사용자 승인 2026-10-16): 계획 보관함 전체가 가득 차면 새 계획 요청을 503으로 거절하고, 화면은 그 한 번의 검색을 서버 모드로 한다(한 곳 탓이 아니라 사람이 많은 경우라 결과를 줌).
- **확장이 못 여는 도서관만 서버가 대신** (검토 #16, 사용자 승인 2026-10-16): 설정 목록(`server-fetched-libraries`, 이름 [안])에 넣은 도서관은 계획에서 확장 주소로 주지 않고 서버가 불러(그때만 서버 자리 1개) 같은 응답에 돌려주며 `server_for_extension`으로 기록. 목록이 비면 쓰지 않음. 그 자리가 찼을 때는 그 도서관만 「확인하지 못한 도서관」, 나머지는 확장으로 계속(검토 #29, 사용자 승인 2026-10-16).
- **만드는 순서는 세 단계** (사이클 20 전반 점검 #1, 사용자 승인 2026-10-17; 결정·설계는 그대로, dev 순서만): **2단계(확장 최소판)** = 확장·계획 입구·`accept`·올리기 검사·확장 결과 공유 캐시·사용 기록 `extension`·거절 기록 `invalid_plan`, 그리고 사람을 가리키는 것은 **계획 번호 + 계획을 만든 IP(/64)**(올리기·닫기·`replaces`는 같은 IP일 때만, 다르면 400 `client_ip_changed` → 화면이 남은 도서관만 다시 계획). 2단계에는 같은 공인 IP에 nginx 계획 구역(1분 300)과 보관함 전체 상한(25,000)만 걸고 IP마다 임시 상한은 두지 않으며, 사용 기록에 남용이 보이면 3단계를 앞당김 [확정] (사용자 승인, 2026-10-17, 마무리 확인 #9). **3단계(웹스토어에 올릴 때 또는 거절 기록에 남용이 보일 때)** = 브라우저 번호 장부·HttpOnly 쿠키·번호마다 열린 계획 20·번호 잠금·IP 울타리 둘·서버 대행 목록. 3단계가 들어오면 "만든 IP" 검사는 "장부의 받은 IP" 검사로 바뀜. 단계 표는 `docs/cycles/20-lookup-status-and-extension/design-delta.md` "개발 단계"
- **확장 결과는 2단계부터 나눔** (전반 점검 #2, 사용자: "나눔 (#9·#10 그대로) 이걸로 해", 2026-10-17): 확장 결과를 공유 캐시에 넣지 않는 제안은 미승인 → 따로 둔 캐시(500칸, 처음 넣은 시각 + 3분 고정)에 넣고 서버 모드 사용자도 씀
- **해석 자리는 서버 모드·확장 모드가 함께 쓰는 하나(8, 설정)** (전반 점검 #4, 사용자 승인 2026-10-17): 처음의 "확장 올리기 동시 해석 4"를 바꿈. 자리가 없으면 최대 2초 기다린 뒤 그 도서관만 실패(확장 모드 올리기는 503 `server_busy`). 서버 모드가 상한 없이 최대 100건(자리 20 × 묶음 5, 자리 40이면 200건)을 동시에 해석하면 1MB 쪽에서 힙 512MB를 넘을 수 있어서(실측 1MB 쪽 해석 7.4MB). 메모리가 바닥나면 JVM `-XX:+ExitOnOutOfMemoryError` + 컨테이너 재시작(사이클 17 몫)
- **확장 약속 판 번호** (전반 점검 #8, 사용자 승인 2026-10-17): 인사 답에 약속 판 번호(이름 [안] `protocol`)를 싣고, 웹이 요구하는 최소 판보다 낮으면 확장 모드로 가지 않고 서버 모드 + 「확장을 새로 깔아 주세요」(머리말 상태 점 말풍선 둘째 줄, 점은 파란색 대신 서버 모드 색, [확정] (사용자 승인, 2026-10-17, 마무리 확인 #8)). 개발자 모드 확장은 자동 갱신이 없어 웹만 새로 배포되면 메시지 모양이 어긋나 모든 줄이 조용히 「확인하지 못한 도서관」이 될 수 있어서

## 검토한 대안
### A안: 화면이 올림 + 서버 해석(accept) + JSON 입구 셋 + 검사·보안 장치 (채택)
- 장점: 확장이 API를 몰라 API를 바꿔도 재심사 불필요, 해석 코드 한 벌, 가짜 검사 가능, 연결을 붙들지 않음
- 단점: 바이트가 base64 메시지를 거침(최대 약 322KB), 서버가 해석 메모리를 잠깐 씀, 포털 2단계로 왕복이 늘어남
### B안: 확장이 서버에 직접 올림
- 장점: 메시지를 거치지 않음
- 단점: 확장이 API 경로·판에 묶여 바꿀 때마다 재심사, CSRF 예외·확장 origin CORS 확인
- 채택하지 않은 이유: [이유 미확인] (제안 → 승인)
### C안: 확장이 해석해 결과만 올림
- 장점: 서버 메모리 거의 0
- 단점: adapter를 자바·자바스크립트 두 벌로 유지, 가짜 검사 불가(보낸 숫자를 믿어야 함), 판정 규칙까지 확장에
- 채택하지 않은 이유: 사용자가 (가) 서버 해석을 고름
### D안: 지금 SSE 스트림에 확장 모드 끼우기
- 장점: 화면 이벤트 처리 그대로
- 단점: 검색마다 연결·`SseEmitter`를 최대 35초 유지, 두 통로를 짝지어야 함, nginx 도서관 호출 구역에 걸림
- 채택하지 않은 이유: [이유 미확인] (제안 → 승인)
### E안: 업로드를 기다리는 가짜 SiteFetcher
- 장점: 검색 코드가 글자 그대로
- 단점: 서버 throttle 줄에 사용자 IP가 섞이고, 기다리는 스레드와 밀어주기 통로가 필요
- 채택하지 않은 이유: [이유 미확인] (제안 → 승인)
### 캐시 오염: (가) 그대로 / (나) 빈 칸만 / (다) 그 사람에게만
- (나)에 검사를 더한 안을 채택. (다)는 "확장도 캐싱"과 어긋남 [이유 미확인] (제안 → 승인)

## 결과
- 좋아지는 점: 확장 사용자는 서버 자리와 무관하게 검색(빨강이어도), 결과는 서버 캐시로 다른 사용자와 공유, 해석·판정이 서버 모드와 같음
- 감수하는 점: 페이지 모양을 흉내 낸 가짜는 최대 3분 노출될 수 있음(⑧로 치움). 확장 값은 서버 캐시와 따로 둔 캐시(500칸)에만 넣고 만료는 처음 넣은 시각 + 3분 고정이라, 서버가 받은 값과 섞이지 않고 다시 올려도 늘지 않음 (사이클 20 세 관점 검토 #9·#10, 사용자 승인 2026-10-16). 같은 공인 IP를 쓰는 사람끼리 한도·잠금으로 묶이지 않음(#22). 번호는 서버가 준 것만 통하고 받은 IP에서만 통하며 자바스크립트가 읽지 못해, XSS가 생겨도 번호를 훔쳐 다른 곳에서 쓸 수 없음(#32·#33). 대신 서버 메모리에 장부(최대 5만 줄, 어림 약 5MB)와 IP별 합계가 더해지고, 서버를 다시 켜면 모든 번호가 새로 나감. 폰 회선이 바뀌면 남은 도서관을 한 번 더 계획함(왕복 1번). 같은 IP 뒤에서 많이 쓰는 곳(큰 회사·학교)은 울타리에 걸려 「잠시 후 다시」를 볼 수 있음(#31) — 배포 뒤 거절 기록으로 숫자를 맞춤. 보관함 전체가 차면 다른 사람 계획을 지우지 않고 새 검색이 서버 모드로 감(#8) — 503이 나면 그 검색은 서버 자리를 씀. XSS 스크립트가 그 화면 안에서 보내는 요청은 막지 못하고 번호 하나·IP 하나의 한도 안으로 묶을 뿐이며, XSS 자체는 CSP·외부 HTML을 화면에 넣지 않기로 막아야 함. 처리방침의 쿠키 설명에 한 줄이 필요함 [확인 필요: 사이클 16 처리방침 문구와 맞춤]. 서버 대행 목록이 비어 있지 않으면 확장 모드도 그 도서관만큼 서버 자리·나가는 길을 씀(#16). 계획 번호·브라우저 번호 묶기 등 검사 코드가 늘어남. 사이클 17 nginx 파일에 올리기 경로 조각(템플릿)을 더해야 함
- 나중에 되돌리거나 서비스로 분리할 때: 확장 해석(C)으로 가려면 adapter를 JS로 옮기는 큰 일. 나중에 분리할 때 계획 입구는 조회를 맡는 쪽을 따라감
