# ADR-0160: AI 찾기 표의 "가진 도서관 목록"은 중복 저장 금지의 예외로 둠

Status: Accepted
Date: 2026-10-28
Cycle: 26-book-descriptions
Supersedes: 없음

## 배경
사이클 26에서 사용자는 "지금 더 군데 중복저장되는거는 없었으면해"(2026-10-27, 명세 결정 #3)라고 정했고, AI 검색이 `catalog`에서 복사해 두던 사본 표(`aisearch.search_book`)를 없애기로 했다(명세 결정 #6). 그런데 AI 검색 후보 질의는 낱말 색인으로 찾은 책을 그 책을 가진 도서관 번호 목록(`library_ids`)으로 거른다. 이 목록을 새 찾기 표(`catalog.book_search`)에 두면 같은 모듈의 `catalog.book.library_ids`와 같은 값이 두 번 있게 되고, 두지 않으면 찾을 때마다 `catalog.book`(868MB)과 이어 읽어야 한다. 사용자는 "나는 속도가 우선이긴 한데 그렇게 차이가 많이나나? 조사해서 알려줘"라고 물었다.

## 결정
`catalog.book_search`에 `library_ids integer[]`를 둔다. 이 칸은 사이클 26의 "중복 저장 없음" 원칙의 **예외**이며, 같은 `catalog` 모듈 안의 찾기 전용 칸으로만 쓴다. 다른 모듈로 복사하는 일은 없다.

## 이유 (사용자 발언)
- "나는 속도가 우선이긴 한데" (2026-10-28)
- "승인하고 예외라고 기록해 줘." (2026-10-28, 측정 결과를 본 뒤)

측정 (dev 24 세션, 2026-10-28, dev `docs/plan-feedback.md` "# 사이클 26 질의 속도", 원본 `docs/reports/ai-search-eval/candidate-join-2026-10-28.json`): 운영과 같은 DB 설정 사본, 실제 질문 24개, 계획 도서관 25곳, LIMIT 50. 두 방식이 돌려준 책은 같음.

| | 찾기 표에 둠 (채택) | `catalog.book`과 이어 읽음 |
|---|---|---|
| 캐시 찬 상태 중간값 | 16.1ms | 17.9ms |
| 캐시 빈 상태 중간값 | 106ms | 230ms |
| 캐시 빈 상태 최대 | 234ms | 1,054ms |
| 읽은 블록 | — | 대개 2~5배 |

운영 서버는 메모리 2GB에 백엔드가 약 650MB를 써서 `catalog.book`이 캐시에 남기 어려움 [추론, dev 24].

## 검토한 대안
### A안: 찾기 표에 `library_ids`를 둠 (채택)
- 장점: 지금 AI 검색 질의를 표 이름만 바꿔 그대로 씀, 빠르기 그대로
- 단점: 같은 모듈 안에 같은 값이 두 번. 다시 가져오기 뒤 다음 설명 넣기 때까지 찾기 표는 옛 소장 정보(지금과 같음)
### B안: 찾을 때 `catalog.book`과 이어 읽음
- 장점: 중복 없음
- 단점: 캐시가 빈 상태에서 약 2배, 최대 1초 넘게 느림
- 채택하지 않은 이유: "나는 속도가 우선이긴 한데" (2026-10-28)

## 결과
- 좋아지는 점: AI 검색 첫 글 시간이 늘지 않음
- 감수하는 점: 한 칸의 중복. 값은 `book-texts` 넣기 때 `catalog.book.library_ids`에서 다시 채움. 다시 가져오기 직후 새로 고치는 일은 backlog
- 나중에 서비스로 분리할 때: 찾기 표는 `catalog`(책 설명) 쪽에 함께 감
