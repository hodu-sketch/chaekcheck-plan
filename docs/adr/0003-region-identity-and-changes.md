# ADR-0003: 지역 식별과 행정구역 변경 처리

Status: Accepted
Date: 2026-09-27
Cycle: 01-ebook-availability-search
Supersedes: 없음

## 배경
2026-07-01 전남광주통합특별시 출범으로 광주·전남의 법정동 코드가 새로 적용됐고, 같은 날 인천·안양 변경분도 공지됐다 (행정안전부 변경내역 2026.7.1. 시행, https://www.mois.go.kr/frt/bbs/type001/commonSelectBoardArticle.do?bbsId=BBSMSTR_000000000052&nttId=127039, 2026-09-27 확인). 도서관 자격 규칙과 브라우저에 저장하는 사용자 선택이 지역을 가리키므로, 코드가 바뀌어도 깨지지 않아야 한다.

## 결정
- 지역마다 우리 내부 ID를 둔다. seed에서 직접 부여해 모든 환경에서 같게 한다. 법정동 코드는 속성으로만 둔다.
- 시도 → 시군구 2단계. 일반구가 있는 시는 시까지만 넣는다.
- 폐지된 지역은 지우지 않고 `ABOLISHED`로 표시하고, 연결 테이블 `region_replacement`로 대체 지역을 가리킨다 (나뉨 표현 가능).
- 저장된 옛 ID는 해석 전용 API가 `ACTIVE | REPLACED | SPLIT | UNKNOWN`으로 알려 준다.
- 목록은 행정안전부 공지가 나오면 법정동 코드 파일로 수동 갱신한다 (Liquibase 변경분).

## 이유 (사용자 발언)
- "시군구에 전자도서관이 종속되는 구조라면, 시군구 코드랑 전자도서관 연결 코드랑 별개로 두면 되는 거 아니야?"

- 일반구 제외: [이유 미확인]

## 검토한 대안
### A안: 내부 ID + 연결 테이블 + 해석 API (채택)
- 장점: 코드 변경이 속성 수정으로 끝나고, 합쳐짐과 나뉨을 모두 표현
- 단점: 테이블 하나와 API 하나가 늘어남
### B안: 법정동 코드를 키로 사용
- 단점: 코드가 바뀌면 자격 규칙과 브라우저 저장값이 모두 깨짐
- 채택하지 않은 이유: 위 사용자 발언
### C안: `replaced_by_id` 컬럼 하나
- 단점: 한 지역이 여럿으로 나뉘는 경우를 표현하지 못함
- 채택하지 않은 이유: [이유 미확인]
### D안: 목록 API가 폐지 이력까지 주고 프론트가 해석 / 도서관 API가 자동 교체
- 단점: 해석 규칙이 프론트에 생기거나, 도서관 API에 지역 이력 책임이 섞임
- 채택하지 않은 이유: [이유 미확인]
### E안: 행정표준코드 API로 자동 동기화 / 이력 없이 최신 목록만
- 단점: 배치와 키가 필요하고 통합·분리 연결은 결국 사람이 확인 / 저장된 선택이 사라짐
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 행정구역이 바뀌어도 자격 규칙과 사용자 선택이 유지되고, 사용자에게 변경을 안내할 수 있음
- 감수하는 점: 반년마다 사람이 파일을 보고 갱신해야 함. ID를 직접 관리해야 함
- 나중에 서비스로 분리할 때: 지역 서비스가 ID 체계를 그대로 가져감
