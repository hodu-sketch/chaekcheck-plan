# ADR-0022: 도서관 사이트 TLS 호환: 중간 인증서 보충, RSA 키 교환 허용, 연결 5초

Status: Accepted
Date: 2026-09-29
Cycle: 02-library-expansion
Supersedes: 없음

## 배경
사이클 02 개발 중 dev에서 사용자가 정한 결정을 사이클 03 시작 때(2026-09-29) 기록한다.
- 교보 공식 목록 중 24곳이 인증서의 중간 인증서를 보내지 않아 JDK 25에서 PKIX 오류가 난다.
- 대구전자도서관은 TLS 1.2 + `TLS_RSA_WITH_AES_256_GCM_SHA384`만 받는데, JDK 24부터 `TLS_RSA_*`가 기본으로 막혀 `handshake_failure`가 난다.
- 경기도교육청 전자도서관은 연결에 1~3초가 걸려 연결 제한 3초를 가끔 넘긴다.
- 사이클 02 인계서는 인증서 검증을 끄는 것을 금지했다 `[확정]`.

## 결정
- 본 서비스와 조회 서비스의 **도서관 호출에만**, JDK 최상위 기관만 믿는 TLS 설정을 쓴다. 사이트가 빠뜨린 중간 인증서 6개(`tls/library-intermediates/*.pem`)는 체인을 만드는 재료로만 주고 신뢰 대상으로 두지 않는다.
- 두 앱 시작 때 `jdk.tls.disabledAlgorithms`에서 `TLS_RSA_*` 한 항목만 뺀다. 이 설정은 JVM 전체에 적용된다.
- 도서관 연결 제한을 3초에서 5초로 늘린다(직접 호출과 조회 서버 모두). 읽기 5초, 묶음 8초는 그대로다.
- 인증서 검증과 호스트 이름 검증은 그대로 켠다.

## 이유 (사용자 발언)
- 인증서 불완전 사이트: "넣되 내가 확인할 수 있게 나중에 문서로 좀" (2026-09-29, dev plan-feedback C2-U-14)
- RSA 키 교환: "허용" (2026-09-29, C2-U-5)
- 연결 제한: "5초로 늘림" (2026-09-29, C2-U-5)

## 검토한 대안
### A안: 중간 인증서 보충 + RSA 허용 + 연결 5초 (채택)
- 장점: 검증을 유지하면서 해당 도서관을 검색 대상에 넣음
- 단점: 중간 인증서 만료를 관리해야 함. RSA 허용이 JVM 전체에 적용됨
### B안: 해당 사이트를 검색 대상에서 빼기
- 장점: 설정이 단순함
- 단점: 24곳 + 대구가 빠짐
- 채택하지 않은 이유: [이유 미확인]
### C안: 인증서 검증 끄기
- 채택하지 않은 이유: 사이클 02 인계서 "하지 않는 것" `[확정]`

## 결과
- 좋아지는 점: 24곳과 대구를 검색함. 인증서 검증은 유지됨
- 감수하는 점: 중간 인증서 만료 전 교체 필요(2027-05-21 GlobalSign GCC R6 AlphaSSL CA 2025, 2027-11-02 Thawte TLS RSA CA G1). 운영에서 DB 등 다른 연결을 TLS로 붙이면 RSA 허용이 거기에도 적용됨 — 처리 방법 [확인 필요]
