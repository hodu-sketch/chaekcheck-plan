# ADR-0046: 로그인 기능은 서버 설정으로 켜고 끔 (저장소는 나누지 않음)

Status: Accepted
Date: 2026-10-04
Cycle: 05-login-account
Supersedes: 없음

## 배경
사용자는 로그인 기능을 설정으로 고를 수 있기를 원했다. 같은 때 `auth` 코드를 다른 저장소에 두는 것도 요청했으나(오픈소스로 공개할 때 인증 코드까지 공개하는 것을 걱정함), 코드 공개 자체보다 비밀 값 공개가 위험하다는 설명을 듣고 저장소 분리는 취소했다.

## 결정
서버 설정 값 하나(`chaekcheck.auth.enabled`, 기본 꺼짐)로 로그인 기능 전체를 켜고 끈다. 꺼져 있으면 사이클 04와 같은 검색 서비스로 동작한다(로그인 주소 없음, 보안 필터 없음, 웹에 로그인 관련 요소 없음, 네이버·카카오 키 없이 서버가 켜짐). `auth`는 지금 저장소 안의 모듈로 둔다. 비밀 값은 저장소에 넣지 않는다.

## 이유 (사용자 발언)
- "application파일에 넣든 뭐든 선택해서 할 수 있게" (2026-10-04)
- 저장소 분리 취소: "아니다 취소해줘 너 설명 들으니까 저장소 분리 안 하는 것이 나은 것 같아" (2026-10-04)

## 검토한 대안
### A안: 설정으로 켜고 끔, 저장소는 하나 (채택)
- 장점 / 단점: "결과" 절 참고
### B안: auth 서버 코드를 별도(비공개) 저장소에 둠
- 장점: 공개 저장소에 인증 서버 코드가 없음
- 채택하지 않은 이유: "너 설명 들으니까 저장소 분리 안 하는 것이 나은 것 같아" (2026-10-04)
### C안: 켜고 끄는 설정을 두지 않음
- 장점: 만들 것이 적음
- 채택하지 않은 이유: 위 사용자 발언(설정으로 고를 수 있게)

## 결과
- 좋아지는 점: 키가 준비되기 전이나 네이버 검수 전에 꺼 둔 채로 배포할 수 있음. 저장소가 하나라 버전을 맞출 일이 없음
- 감수하는 점: 켜짐·꺼짐 두 경우를 모두 테스트해야 함. 저장소를 공개하면 인증 코드도 공개됨(비밀 값은 저장소에 없음)
- 되돌리는 비용: 설정을 없애는 것은 쉬움. 나중에 분리할 때 영향 없음

## 덧붙임 (2026-10-04): 제공자별 설정
- 결정: 네이버와 카카오를 둘 다 만들고, 로그인 창에 보일 제공자를 설정으로 고른다(설정 이름 `chaekcheck.auth.providers`는 [안], dev가 정함). 뺀 제공자는 버튼이 보이지 않고 그 주소가 동작하지 않는다.
- 이유 (사용자 발언): "일단 카카오만 되게 하고 네이버는 나중에 되도록 하는게 어떨까 하는데" (2026-10-04). 네이버는 검수를 통과해야 누구나 로그인할 수 있고 카카오는 검수가 없다는 설명을 들은 뒤, 캔버스에서 이 안을 승인.
- 채택하지 않은 안: 카카오만 만들고 네이버는 다음 사이클로 미룸 [이유 미확인], 지금 설계 그대로 둠 [이유 미확인].
- 감수하는 점: 제공자 조합마다 테스트가 늘어남.
