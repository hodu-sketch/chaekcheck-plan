# ADR-0150: AI 책 찾기 — 새 모듈 `aisearch`, Haiku 5.5 실시간 두 번 호출, LLM 부르는 곳 하나

Status: Accepted
Date: 2026-10-24
Cycle: 24-ai-book-search
Supersedes: 없음

## 배경
사용자가 원하는 책을 문장으로 쓰면 우리 DB의 책을 골라 질문에 맞춘 글과 함께 보여 주는 기능을 만든다(사이클 24). 서버가 외부 LLM을 실시간으로 부르는 것은 처음이다. 사이클 23이 같은 때 `picks`를 크게 고치고 있어 같은 코드를 함께 고치면 합칠 때 부딪힌다. 2026-10-17 결정 3번("vast.ai는 일괄로만, 서버가 실시간으로 부르지 않음")은 vast.ai에 대한 것이라 Haiku API 실시간 호출은 그 결정을 바꾸지 않는다.

## 결정
새 모듈 `aisearch`를 두고 `picks`에는 목록 책을 읽는 공개 API `ListedBooks` 하나만 더한다. 질문마다 Claude Haiku 5.5를 두 번 부른다(1차 질문 → 낱말, 2차 후보 → 고르기·글). LLM 호출은 `aisearch` 안 `LlmClient` 한 곳에서 JDK `HttpClient`로 Anthropic Messages API를 직접 부르고, 이번에는 Anthropic 구현만 둔다.

## 이유 (사용자 발언)
- "하이쿠로 일단 먼저 만들어 로컬 llm은 별개야" (2026-10-24)
- "일단 둘 다 되도록 해주고, haiku로 먼저 하고" (2026-10-23) — 부르는 곳 하나로 모으기
- 모듈·직접 요청 선택: "(가) 새 구역 aisearch", "(가) 직접 요청"을 고름 (2026-10-24, 설계 결정 #1·#5) — 이유는 말하지 않음 [이유 미확인]
- 두 번 호출: "(가) 낱말로 30권 (지금 안)" 선택 (2026-10-24, 명세 규칙 2차 #2), 질문 "우리서버에 낮말에 맞게 있어야 하는거네?"

## 검토한 대안
### A안: 새 모듈 `aisearch` (채택)
- 장점: 사이클 23과 겹치는 곳이 새 파일 둘. 찾는 범위를 넓힐 때 책 출처만 바꿈. 나중에 서비스로 나누기 쉬움
- 단점: 모듈 하나, `picks` 공개 API 하나
### B안: `picks` 안에
- 장점: 새 공개 API 없음
- 단점: 23과 같은 패키지를 동시에 고침, `picks`가 외부 LLM·요금까지 맡음
- 채택하지 않은 이유: [이유 미확인]
### C안: Anthropic 공식 Java SDK
- 장점: 스트림·재시도가 있음
- 단점: 의존이 늘고 새 매개변수를 따라오는지 확인 필요, 로컬 LLM은 다른 클라이언트
- 채택하지 않은 이유: [이유 미확인]
### D안: 목록 전체를 Haiku에 한 번에 (한 번 호출)
- 장점: 낱말이 달라도 놓치지 않음
- 단점: 한 번에 약 10배 비용, 목록이 커지면 안 됨
- 채택하지 않은 이유: [이유 미확인] (사용자는 "(가) 낱말로 30권"을 고름)

## 결과
- 좋아지는 점: 23과 따로 개발 가능. Ollama·vLLM(OpenAI 호환)을 나중에 `LlmClient` 구현 하나로 붙임
- 감수하는 점: Anthropic 스트림 해석을 직접 만들고 시험. 질문마다 Haiku 두 번(시간·비용)
- 나중에 되돌리거나 분리할 때: 모듈을 지우고 `aisearch` 스키마를 DROP. 나중에 분리할 때 `ListedBooks`를 REST 읽기로 바꾸고 표 둘을 들고 나감
