# ADR-0017: 도서관 한 줄 = 이용 단위 하나, 종류 칸으로 전자·실물 구분

Status: Accepted
Date: 2026-09-28
Cycle: 02-library-expansion
Supersedes: 0012

## 배경
ADR-0012는 도서관(`library`)과 전자도서관 사이트(`library_site`)를 나누고 자격을 도서관에만 두었다. 조사 기록에 같은 도서관이라도 사이트마다 조건이 다른 사례가 있다 (광산구 "준회원도 구독형 이용", 시흥 구독형 "분기 200명 선착순", 광주 서구 구독형. 대부분 검색 요약이라 원문 미확인). 나중에 실물 도서관도 다룰 예정이다. 개발 초기라 기존 구조를 지킬 필요가 없다.

## 결정
- 전자도서관 사이트 하나를 `library.library` 한 줄로 둔다. 자격 규칙(`eligibility_rule.library_id`)은 그 줄에 건다. 같은 운영 기관의 일반·구독형은 두 줄이고, 자격이 같으면 규칙을 두 번 적는다.
- `library_type` 칸으로 종류를 나눈다. 지금은 `EBOOK`만 쓰고, 실물 도서관은 나중 사이클에 `PHYSICAL`과 실물 전용 칸을 더해 같은 테이블에 넣는다. 자격 규칙 테이블과 판정 코드는 종류와 상관없이 함께 쓴다.
- 전자도서관 전용 칸(`platform_type`, `base_url`, `holdings_count`, `holdings_counted_on`, `deferred`)은 같은 테이블에 두고, `EBOOK`이면 `platform_type`과 `base_url`이 필수라는 조건을 CHECK로 막는다.
- `library_site` 테이블은 만들지 않는다. 조회·캐시·도서관별 "더 보기"는 `libraryId`를 쓴다.
- 운영 기관으로 묶는 테이블은 두지 않는다 (backlog, 실물 도서관 사이클에서 다시 검토).

## 이유 (사용자 발언)
- "기존 구조를 우선시할 필요가 전혀 없어 나는 되려 사이트별로 관리하도록 하는게 어떨까해" (2026-09-28)
- "실물도서관도 따로 다룰건데 각 도서관 타입 다르게하는거지" (2026-09-28)
- "C안이 나아보여", "실물 도서관이라고 자격 규칙이 다를 것 같지 않은데" (2026-09-28)

## 검토한 대안
### C안: 한 테이블 + 종류 칸 (채택)
- 장점: 테이블이 가장 적고 지금 dev 구조에 칸을 더하는 모양. 자격 규칙·판정 코드 하나
- 단점: 종류마다 안 쓰는 빈 칸. 종류별 필수 칸을 CHECK로 막아야 함
### ADR-0012: 도서관 + 사이트, 자격은 도서관
- 단점: 사이트마다 자격이 다른 곳을 담지 못함
- 채택하지 않은 이유: "사이트별로 관리하도록 하는게 어떨까해"
### A안: 공통 부모(`library_unit`) + 종류별 상세 테이블
- 장점: 빈 칸 없음, 규칙·판정 하나
- 단점: 테이블이 늘고 읽을 때 합쳐야 함
- 채택하지 않은 이유: [이유 미확인]
### B안: 종류별 완전 분리 (테이블과 자격 규칙 각각)
- 단점: 실물 도서관 때 규칙 테이블·판정 코드가 두 벌
- 채택하지 않은 이유: "실물 도서관이라고 자격 규칙이 다를 것 같지 않은데"

## 결과
- 좋아지는 점: 사이트마다 다른 자격을 그대로 적음. 실물 도서관도 같은 판정을 씀
- 감수하는 점: 같은 기관의 여러 사이트는 자격 규칙을 반복해 적음. 이름이 겹치지 않게 "(구독)" 등을 붙임 (`name` UNIQUE 유지 여부는 seed 때 확인)
- 나중에 A안으로 옮기려면: 종류별 칸을 상세 테이블로 떼는 마이그레이션. 규칙 테이블은 그대로 쓸 수 있음
