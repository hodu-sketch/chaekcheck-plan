# ADR-0036: 계정(`auth`)과 회원 자료(`member`)를 다른 모듈로 둠

Status: Accepted
Date: 2026-10-01
Cycle: 05-login-account
Supersedes: 없음

## 배경

회원 기능은 두 가지 일로 이뤄집니다. 하나는 네이버·카카오 로그인, 세션, 동의, 탈퇴, 연결 끊기처럼 외부 로그인 제공자와 맞닿은 일이고, 다른 하나는 거주지·직장 지역과 직접 고른 도서관(나중에 관심 책)을 저장하는 일입니다. 이 둘을 한 모듈에 둘지 나눌지 정해야 했습니다 (`docs/research/member-and-alerts/integration-plan.md` 3.1). 제약: 모듈끼리는 공개 API나 이벤트로만 통하고 서로의 표를 건드리지 않습니다 (dev `CLAUDE.md`, ADR-0001).

## 결정

`auth`와 `member` 두 모듈로 둡니다. `auth`는 계정(provider + provider_user_id), 세션, 동의 기록, 탈퇴, 카카오 연결 해제 웹훅을 갖고 다른 모듈에 의존하지 않습니다. `member`는 지역 자격과 직접 추가 도서관을 갖고, `auth`에는 현재 계정을 주는 `AccountId`와 계정 삭제 이벤트 `AccountDeleted`로만 기댑니다.

## 검토한 대안

### A안: `member` 하나 (안에서 `internal/auth`, `internal/profile` 패키지로만 나눔)
- 장점: 표 4개짜리 작은 모듈. 지킬 경계가 하나
- 단점: 나중에 인증을 분리하려면 패키지를 모듈로 올려야 함
- 채택하지 않은 이유: [이유 미확인]

### B안: `auth` + `member` 둘 (채택)
- 장점: 인증(외부 IdP·세션)과 회원 자료를 처음부터 나눔. 나중에 서비스로 나눌 때 그대로 둘
- 단점: 사이클 05에서는 `auth`를 쓰는 모듈이 없어 경계의 반대쪽이 비어 있음. 두 모듈 사이 계약(`AccountId`, `AccountDeleted`)을 지금 정해야 함

## 결과

- 좋아지는 점: `auth`가 다른 모듈을 모르므로 로그인·탈퇴를 따로 시험하고 따로 뗄 수 있음. 회원 자료 모듈이 늘어도(`member`, 나중에 `notification`) 계정 삭제는 이벤트 하나로 전달됨
- 감수하는 점: 사이클 05에서 `AccountDeleted` 이벤트와 영속 발행 저장소를 소비자 없이 먼저 넣음(사용자 선택 "공통 + 웹훅 + 이벤트·저장소", 2026-10-01). 모듈 간 FK가 없어 `member`의 `account_id`는 이벤트로만 정리됨
- 나중에 분리할 때: `auth` 서비스와 `member` 서비스. 이벤트는 그때 외부 브로커로 내보냄. 되돌려 하나로 합치려면 패키지 이동과 이벤트 제거
