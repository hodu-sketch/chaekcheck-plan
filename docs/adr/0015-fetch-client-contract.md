# ADR-0015: 도서관 호출 인터페이스와 조회 서비스 계약

Status: Accepted
Date: 2026-09-28
Cycle: 02-library-expansion
Supersedes: 없음

## 배경
ADR-0011은 조회 전용 서비스를 따로 두고 여러 대로 운영하기로 했고, adapter 위치와 본 서비스–조회 서비스 사이 계약은 design-delta에서 정하기로 남겼다. 사용자는 조회 서버를 따로 두되 본 서버에서도 바로 조회할 수 있기를 원했다.

## 결정
- 본 서비스 `availability`의 "도서관 사이트 부르기"를 인터페이스로 두고, 구현을 둘 둔다: **직접 호출**(본 서버가 도서관을 바로 부름)과 **조회 서버 경유**. 설정으로 고른다.
- 조회 서버가 모두 죽어도 직접 호출로 자동 전환하지 않는다. 그때는 "조회 실패"이고, 바꾸려면 설정을 고친다.
- adapter(URL 만들기, HTML 해석)는 본 서비스에 둔다. 조회 서버는 받은 URL을 GET으로 가져와 상태 코드와 원본 바이트를 돌려주기만 한다.
- 평소에는 설정 목록의 첫 번째 살아 있는 조회 서버에 보낸다 (우선순위 순).
- 다음 조회 서버로 넘기는 경우는 조회 서버에 **연결하지 못했거나 조회 서버가 503**을 줄 때뿐이다. 조회 서버의 응답이 늦을 때(읽기 시간 초과)와 도서관 쪽 실패(403, 시간 초과)는 넘기지 않는다.
- 조회 서비스는 dev 저장소 안의 새 폴더에 작은 Spring Boot 앱으로 둔다.
- 설계에 넣지 않는 것: Kafka, 서비스 디스커버리, API 게이트웨이, Kubernetes. 조회 서버 목록은 본 서비스 설정의 고정 목록이다.

## 이유 (사용자 발언)
- 인터페이스 + 직접 호출: "조회용 서버는 따로두되 원 서버에서도 바로 가능하도록 인터페이스로 해줘" (2026-09-28)
- 자동 전환 안 함, adapter 위치, 우선순위 순, 넘기는 기준, 저장소 위치: [이유 미확인] (추천안 선택, 2026-09-28)

## 검토한 대안
### adapter 위치
- A안 본 서비스 (채택): adapter를 고쳐도 본 서비스만 배포. ADR-0011의 "요청을 보내고 응답을 돌려주기만"과 같음. 원본 HTML이 서비스 사이를 오감
- B안 조회 서버: 응답이 작음. 파서 수정 때 조회 서버 전부 배포, 포털 상세 조회 흐름이 두 서비스를 넘나듦. 채택하지 않은 이유: [이유 미확인]
### 조회 서버 고르기
- A안 우선순위 순 (채택): 도서관이 평소 IP 하나만 봐서 차단 원인을 가리기 쉬움. 평소엔 한 대만 일함
- B안 차례로 돌려 보냄: 부하를 나눔. 한 IP만 차단되면 절반만 실패해 원인을 가리기 어려움. 채택하지 않은 이유: [이유 미확인]
### 넘기는 기준
- A안 연결 실패·503만 (채택): 도서관에 중복 요청이 가지 않음
- B안 응답이 없어도 넘김: 같은 요청이 도서관에 두 번 갈 수 있음. 채택하지 않은 이유: [이유 미확인]
### 조회 서버가 모두 죽었을 때
- A안 설정으로만 직접 호출 (채택): 도서관이 보는 IP가 고정 IP로만 유지됨
- B안 자동 전환: 서비스는 계속되지만 본 서버 IP가 드러나고 차단될 수 있음. 채택하지 않은 이유: [이유 미확인]
### 저장소 위치
- A안 같은 저장소 새 폴더 (채택) / B안 별도 저장소 / C안 이번엔 직접 호출만. 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 개발·테스트는 직접 호출로 간단히 하고, 운영은 조회 서버로. 바꿔 끼우기 쉬움
- 감수하는 점: dev `CLAUDE.md`의 "backend/는 Spring Boot 앱 하나" 규칙을 바꿔야 함 (handoff). 조회 서버 대수, 배치 위치, 고정 IP, 인증 토큰 보관, "쉼" 표시 시간은 정하지 않음 [확인 필요]
- 나중에 되돌릴 때: 직접 호출 구현이 남아 있어 비용이 낮음
