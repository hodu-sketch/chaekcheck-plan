# ADR-0174: AI 검색 책 목록은 손님 요청 안에서 다시 확인하지 않는다

Status: Accepted
Date: 2026-11-09
Cycle: 29-ai-first-text-latency
Supersedes: 없음

## 배경
운영 AI 책 찾기에서 첫 글이 가끔 3~7초 걸렸다. 2026-11-08 측정(`docs/cycles/29-ai-first-text-latency/measurements.md`): 직전 확인에서 1분이 지난 요청 9건 모두 `nearest`→`neighbours` 사이 1.3~1.4초 멈춤(오래 쉰 첫 요청 2.6초), 1분 안의 요청 14건은 0. 원인은 dev `SearchBooks.fresh()`가 1분마다 손님 요청 안에서 `SELECT count(*), max(imported_at) FROM catalog.book_search`(242MB 전체 읽기)를 부르는 것. 또 AI 검색 한 줄 넣기(`book-texts`)는 표를 `DELETE`로 비우고 다시 넣은 뒤 `VACUUM (FULL, ANALYZE)`로 표를 잠가 AI 검색이 약 10초 기다린다(dev `docs/maintenance/6-aisearch.md` 238행). 카탈로그 전체 가져오기는 이미 새 표에 넣고 바꿔 끼운다(ADR-0065).

## 결정
1. AI 검색 책 목록은 서비스 서버가 켜질 때 한 번 읽는다. 1분마다 확인하는 일은 없앤다
2. 가져오기(`book-texts`, 카탈로그)가 끝나면 백엔드의 내부 「책 목록 다시 읽기」 REST 요청을 한 번 보낸다. 서버는 뒤에서 새 목록을 읽고 다 읽으면 한 번에 바꿔 끼운다. 그동안 옛 목록으로 답한다. 이 주소는 바깥(nginx·Cloudflare 터널)에 열지 않는다
3. `book-texts` 넣기도 「새 표에 넣고 이름 바꿔 끼우기」로 바꾸고 `VACUUM FULL`을 없앤다
4. 바꾼 뒤 DB 미리 데우기(`pg_prewarm`)를 시험해서 효과가 있으면 적용한다
5. Haiku·임베딩 서버 연결 유지 설정은 넣지 않는다

## 이유 (사용자 발언)
- 1분 세기 대신: 이벤트 방식을 고름("그렇게 하도록 해줘", 2026-11-08), LISTEN/NOTIFY는 "연결 하나가 너무 아깝지 않아?", 백엔드 다시 띄우기는 "졸라 낭비 아니야?" → "그냥 백엔드에 rest api받는거 하나 주고 그거 응답 받으면 새 버전을 적용하는 거 하면 되는 거 아니야?"
- 미리 데우기: "가져오기를 표 교체로 바꾼 다음에 db 미리 데우기도 테스트 해서 해" (2026-11-08)
- 3·5번: [이유 미확인] (결정 페이지에서 말 없이 승인, 2026-11-08)

## 검토한 대안
- 확인 간격 늘리기(10분): 10분마다 한 사람이 여전히 기다림
- 작은 판 번호 표 한 줄을 1분마다 읽기: 싸지만 확인 자체는 남음. REST 요청이 채택됨
- PostgreSQL LISTEN/NOTIFY: 연결 하나를 계속 붙잡음 (사용자 반대)
- 켜질 때만 읽고 가져오기 뒤 백엔드 다시 띄우기: 한 줄 넣기마다 자바를 하나 더 띄움 (사용자 반대)
- 보통 `VACUUM`(잠그지 않음): 빈자리가 남아 표가 커진 채 있음

## 결과
- 1분 넘긴 요청의 1.3초 멈춤과 가져오기 직후 10초 기다림이 없어질 것으로 본다. 배포 뒤 같은 측정으로 확인(사이클 29 결정 5)
- 가져오기 절차에 「다시 읽기 요청」 단계가 생긴다. 잊으면 다음 재시작까지 옛 목록
- 나중에 분리할 때: 가져오기와 검색이 다른 서비스가 되면 같은 요청을 서비스 사이 호출로 바꾸면 된다
