# ADR-0006: 검색 캐시: Caffeine 메모리 캐시, 나중에 Redis

Status: Accepted
Date: 2026-09-27
Cycle: 01-ebook-availability-search
Supersedes: 없음

## 배경
같은 도서관·검색어·페이지 결과를 3분 캐시해야 한다 (spec 5.6). 검색 결과를 DB에 쌓지 않기로 했다 (spec 10장). 운영 서버는 1대다.

## 결정
Caffeine 메모리 캐시를 쓴다. 쓰기 후 3분 만료, 최대 1,000건, 같은 키 동시 요청은 한 번만 조회, 실패는 캐시하지 않는다. 캐시 키의 검색어는 앞뒤 공백 제거 + 연속 공백 하나로 정규화한다. **운영 서버가 여러 대가 되면 Redis로 옮긴다.**

## 이유 (사용자 발언)
- "4-1 A안으로 가되 나중에 Redis 갈 것을 명시"
- 서버 1대, 세부 값: 사용자가 추천안 선택 (2026-09-27)

## 검토한 대안
### A안: Caffeine (채택)
- 장점: 인프라 추가 없음, 원본을 디스크에 쌓지 않음
- 단점: 재시작하면 비워지고 서버가 여러 대면 따로 돎
### B안: PostgreSQL 캐시 테이블
- 단점: 검색 결과를 DB에 쌓게 되어 spec 10장과 부딪힘. 청소 작업 필요
- 채택하지 않은 이유: [이유 미확인]
### C안: 처음부터 Redis
- 단점: 새 인프라, 이번에는 필요 없음
- 채택하지 않은 이유: "나중에 Redis 갈 것을 명시" (지금이 아니라 나중에)

## 결과
- 좋아지는 점: 단순하고 빠름
- 감수하는 점: 재시작 직후 캐시가 비어 도서관 요청이 늘 수 있음
- 나중에 서버를 늘리거나 서비스로 분리할 때: Redis로 옮김. 캐시 접근을 한 인터페이스 뒤에 두어 교체 비용을 줄임
