# ADR-0079: 책 묶기는 세 방식(current·compact·sql)을 설정으로 고르고, 결과가 번호까지 같아야 쓴다

Status: Accepted
Date: 2026-10-12
Cycle: 11-separate-import
Supersedes: 없음 (묶기 규칙 `same-book-isbn.md` 5절과 ADR-0062 번호 잇기는 그대로)

## 배경
가져오기의 첫 읽기가 묶음 약 760만 개를 묶음마다 개수표 6개(제목·저자·출판사·종류·ISBN·출판일)와 도서관 목록째 힙에 들고 있어 6GB가 필요하다(dev `BookGrouping.java`, 4GB는 멈춤). dev는 줄이는 안 셋을 냈다: 같은 글자 합치기(30~40%), 개수표를 칸으로·묶음 열쇠를 숫자로(3GB 안팎), 묶기를 SQL로(몇백 MB, 큰 일). 묶는 결과가 달라지면 책 번호가 바뀐다(새 책 번호와 동점일 때 옛 번호를 받는 책이 "책을 만든 순서"를 따름, `JdbcCatalogLoad` 546·554행).

## 결정
- 묶는 방식을 설정 `chaekcheck.collection.import.grouping`으로 고른다: `current`(지금, 비교 기준) · `compact`(같은 글자 합치기 + 개수표를 묶음 안의 칸으로 + 묶음 열쇠를 128비트 숫자로) · `sql`(글자 정리는 Java가 줄마다 해 임시(TEMPORARY) 표에 넣고, 묶기·사슬 잇기·대표값 고르기만 SQL. 동점이면 개수 큰 순 + `COLLATE "C"` 순, `mode()` 쓰지 않음)
- 세 방식 모두 "그 책의 첫 줄을 사본에서 읽은 순서"로 책을 만든다
- 같은 사본으로 세 방식을 돌려 책마다 비교하고(dry run 책 목록·줄 목록 파일 + 비교 스크립트, 번호는 export → 번호 뽑기 → discard), 다른 책이 한 권이라도 있거나 번호가 다르면 그 방식은 쓰지 않는다
- 여섯 관점(메모리, 시간, DB 디스크, CPU, 가져오는 동안 검색, 결과)으로 방식마다 두 번 잰다. `current`에는 Java 옵션 `-XX:+UseStringDeduplication`·`-XX:+UseCompactObjectHeaders`를 붙인 경우도 잰다. GC 기록을 켠다
- 측정 뒤 기본값: 결과 비교를 통과하고 전체 시간이 지금(약 33분)보다 10분 넘게 늘지 않는 것 중 힙이 가장 작은 것. 그때까지 기본값은 `current`
- 묶는 규칙 자체(책 묶기 기준 다시 보기)는 바꾸지 않는다. 기본 방식이 정해진 뒤 사이클 12에서

## 이유 (사용자 발언)
- "힙 메모리도 줄일 수 있으면 줄이고 싶어" (2026-10-11)
- "안 2 · 안 1 + 개수표를 칸으로, 열쇠를 숫자로 · 일 중간 / 이거 하고 / 안 3 · 책 묶기를 Java가 아니라 DB(SQL)에서 하기 · 일 큼 / 이것도 하고 / 따로 설정으로서 골라서 하게 해줘 / 이거 다 만들고 / 각각 성능/기능을 다양한 관점에서 측정해 줘" (2026-10-11)
- 첫 줄 순서·번호까지 비교: 사용자가 바꾼 제안을 고름 "세 방식 모두 \"첫 줄을 읽은 순서\"로 책을 만들고, 결과 비교에서 번호까지 같아야 통과로 봅니다" (2026-10-12, 스펙 결정 #10)
- 설정 값 셋·기본 `current`, 책마다 비교, 측정 관점·두 번, 기본값 기준, `sql`은 정리 Java·묶기 SQL, 동점 처리, Java 옵션 측정, 설정 자리, 128비트 열쇠, 임시 표, 비교 도구: 제안 → 승인 (2026-10-11~12)
- 묶기 기준은 사이클 12로: 제안 → 승인 (2026-10-12)

## 검토한 대안
### A안: 세 방식 모두 만들고 설정으로 고르기 (채택)
- 장점: 결과가 같은지와 성능을 같은 사본으로 나란히 잼, 문제가 생기면 `current`로 되돌아감
- 단점: 묶기 코드가 셋, `sql`은 규칙을 SQL로 다시 써야 함
### B안: 힙 줄이기를 넣지 않음 (내 PC 32GB라 6GB면 됨)
- 채택하지 않은 이유: "힙 메모리도 줄일 수 있으면 줄이고 싶어" (2026-10-11)
### C안: 한 방식만 골라 만들기
- 채택하지 않은 이유: "이거 하고 … 이것도 하고 따로 설정으로서 골라서 하게 해줘" (2026-10-11)
### D안: `sql`에서 글자 정리까지 SQL로
- 단점: 저자 나누기(155줄)를 SQL로 다시 쓰고, Java와 PostgreSQL 정규식 차이로 결과가 달라질 위험
- 채택하지 않은 이유: [이유 미확인] (추천하지 않은 안)
### E안: `compact` 열쇠를 숫자 코드만 정확한 숫자로
- 장점: 겹침이 아예 없음
- 단점: 두 갈래 코드, 효과를 미리 모름
- 채택하지 않은 이유: [이유 미확인]
### F안: 묶기 기준도 이 사이클에 같이 바꾸기
- 단점: 바꾼 규칙을 세 곳에 넣고, 결과 비교 기준이 움직임
- 채택하지 않은 이유: [이유 미확인] (사용자는 사이클 12 안을 승인)

## 결과
- 좋아지는 점: 가져오기 힙이 줄면 내 PC 말고 작은 서버에서도 가져올 수 있음
- 감수하는 점: 측정 때까지 묶기 코드 셋을 함께 유지, `sql`은 가져오는 동안 DB 디스크를 수 GB 더 씀(재 봄)
- 나중에: 기본값이 정해지면 쓰지 않는 방식을 남길지 지울지 정한다. 묶기 규칙을 바꿀 때(사이클 12)는 기본 방식에만 넣는다 → 아래 덧붙임으로 바뀜

## 덧붙임 (2026-10-12): 사이클 12에서는 compact와 sql 둘 다 남긴다

- 결정: `compact`와 `sql`을 둘 다 쓸 수 있게 남기고, 사이클 12의 새 묶기 규칙(`same-book-isbn.md` 5.5절)을 둘 다에 넣는다. 기본값은 사이클 11 측정 결과로 바꾼다 [확정] (사용자: "compact와 sql 둘 다 가능하게 하고 기본값을 바꾸느 걸로 해", 2026-10-12, `docs/easy/2026-10-12-remaining-decisions.html` #1 "기본이 되지 않은 방식은 지움" 미승인)
- 바뀌는 것: 위 "나중에"의 "기본 방식에만 넣는다"
- `current`(지금 방식)를 남길지는 이 말에 없음 → `docs/easy/2026-10-12-remaining-followup-decisions.html`에서 질문
- 감수하는 점: 새 규칙을 두 곳에 넣고, 두 방식의 결과가 같은지 사이클 12에서도 비교해야 함(R-B5와 같은 비교)
