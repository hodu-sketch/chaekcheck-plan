# ADR-0094: 우리를 막은 서버에는 막힌 IP에서만 보내지 않고, 교보 구독형 서버 서비스 조회는 조회 서버마다 동시 3건

Status: Proposed
Date: 2026-10-13
Cycle: 사이클 밖 (배포 조사, `docs/research/deploy/`)
Supersedes: 없음 (ADR-0011 보완: 교보 구독형 서버에 한해 "호출 간격 제어는 본 서비스 한곳"을 바꿈. 서비스 조회 부분은 ADR-0095와 함께 읽음)

## 배경
교보 구독형 서버(`*.dkyobobook.co.kr`)가 2026-10-07부터 집 IP를 막았다(`docs/research/ebook-catalog/crawl-runbook.md` 8-2-1절). 이틀 동안 약 8만 건, 이 서버에만 동시 4건으로 보내던 때였다. 2026-10-12에 정한 나가는 IP 원칙은 "우리 IP를 막은 곳에 새 IP로 다시 가지 않음"이라, 이 서버를 쓰는 교보 소장형 1,182곳과 공공도서관 구독 21곳의 대출 조회와 다시 받기가 막혀 있었다. 사이클 13에서 dev 수집기는 `*.dkyobobook.co.kr`을 요청 직전에도 막게 되어(`BlockedHost`), 서비스에 있는 이 서버의 도서관 책 목록도 다시 수집되지 않는다(dev `plan-feedback.md` 3610·3616행, 2026-10-12. 수집 DB에서 이 서버의 도서관은 1,480곳). 한편 이 서버는 평소 응답이 4~6초여서, 서비스 조회에 1초 간격을 두면 8초 마감 안에 1곳 정도만 답이 온다. 지금 서비스는 도서관 주소별로 세서 이 서버 하나에 동시 상한이 없다(검색 하나 5건 × 동시 검색 20 = 최대 100건).

## 결정
- 우리를 막은 서버: 막힌 그 IP에서는 그 서버로 더 보내지 않는다. 다른 우리 고정 IP에서는 수집은 동시 1건·1초, 서비스 조회는 그 서버 전체 동시 상한 안에서 보낸다. 그 IP도 막히면 그 서버로 가는 요청을 멈추고 사용자에게 묻는다(세 번째 IP를 찾지 않음). IP를 바꿔 가는 프록시·주거용 프록시는 쓰지 않는다(그대로). (2026-10-13 고침) 이 줄은 수집에 적용한다. 서비스 대출 조회는 ADR-0095(나가는 IP마다 따로 셈, 막힌 IP만 그 사이트에서 멈추고 다른 IP로 계속).
- 교보 구독형 서버: 수집은 다른 우리 IP에서 소장형·공공도서관 구독만 동시 1건·1초(대여·혼합은 ADR-0067대로 받지 않음). 서비스 조회는 1초 간격 없이 동시 3건, 이 3건은 나가는 IP(업체 프록시·조회 서버)마다 각자 센다(2026-10-13 고침, ADR-0095. 처음 초안은 "조회 서버마다 각자 세고 평소에는 조회 서버 한 대만"). 동시 건수(3)는 코드에 박지 않고 설정으로 바꿀 수 있게 한다.
- 교보 서버가 느려지거나 연달아 실패하면 동시 1건으로 내리고, 연결이 대답 없이 끊기는 일이 이어지면 그 서버로 가는 조회를 멈추고 기록한다. 멈춰서 조회하지 못한 도서관은 따로 알리는 응답을 주고 화면에 "확인 불가"처럼 보인다. 기준 숫자는 dev가 수집기 값(평균 응답 12초, 5번 연달아 실패)을 참고해 정한다.
- (2026-10-14 더함) 교보 구독형 서버의 다시 받기는 첫 배포(사이클 17) 뒤 AWS에 수집용 서버를 잠깐 따로 띄워(서비스 서버 4GB와 따로, 같은 AWS 계정) 이 서버만 위 수집 한도(동시 1건·1초)로 받는다. 결과 파일은 집 PC로 가져와 지금처럼 가져오기 → 운영 반영으로 넣는다. 사이클 17 뒤 따로 사이클로 한다. 수집 시간·서버 비용은 [확인 필요: 1,480곳 기준 측정]

## 이유 (사용자 발언)
- "원칙을 바꿀 때가 되었어", "서버 규모에 비해서 무리가 되게끔 요청을 보내고 있지도 않아" (2026-10-12)
- "수집은 1초간격 가능한데 서비스 실시간 조회 1초는 서비스가 불가능해" (2026-10-12)
- "동시 3건으로 하고... 따로 도서관 검색하는 모듈을 둘 생각인데(이미 구현은 되어 있을 듯) 이것마다 따로 개수 카운팅하자" (2026-10-13)
- 스스로 줄이기·멈추기: 제안 → 승인, 조건 "못 보면 봇 본다고 따로 응답 주고 그걸 화면에 '확인 불가 '이런 식으로 보이게끔.." (2026-10-13)
- 막은 서버 규칙 문장, 교보 수집 동시 1건: 제안 → 승인 (2026-10-13)
- 동시 건수를 설정으로: "추가로 동시 건수는 설정으로 조절 가능하게 해줘" (2026-10-13, 초안 승인 때)
- AWS 수집용 서버: "aws에서 배포하게 될 건데 aws에서 수집을 돌릴 수도 있어" (2026-10-14, 회고 결정 #17), 이어서 "첫 배포 뒤 AWS에 수집용 서버를 잠깐 따로" 제안 → 승인 (2026-10-14, 회고 이어서 정할 것 #2)

## 검토한 대안
### A안: 다른 우리 IP에서 다시 보냄, 교보 서비스 조회 동시 3건을 조회 서버마다 셈, 평소 한 대 (채택)
- 장점: 1,203곳의 대출 현황과 책 목록이 다시 새로워짐. 조회 서버가 각자 자기 IP 몫을 지킴
- 단점: 막은 서버에 다른 IP로 다시 감. 교보의 차단 기준을 모름
### B안: 지금 원칙 그대로 (보내지 않음)
- 장점: 교보 서버에 가는 양이 0
- 단점: 1,203곳의 대출 현황이 늘 확인 못 함, 목록이 10-07에 머묾
- 채택하지 않은 이유: "원칙을 바꿀 때가 되었어" (2026-10-12)
### C안: 서비스 조회도 동시 1건·1초
- 단점: 응답 4~6초 서버라 8초 안에 1곳 정도만 답이 옴
- 채택하지 않은 이유: "서비스 실시간 조회 1초는 서비스가 불가능해" (2026-10-12)
### D안: 동시 3건을 본 서비스 한 곳에서 모든 조회 서버를 합쳐 셈 (ADR-0011 그대로)
- 장점: 조회 서버가 몇 대든 교보 서버는 동시 3건까지만 받음
- 채택하지 않은 이유: [이유 미확인] (사용자가 "조회 서버 안에서 각자 3건씩 세고 평소에는 한 대만 씀"을 고름, 2026-10-13)
### E안: 조회 서버 여러 대에 나눠 보내고 각자 3건
- 단점: 교보 서버가 우리 IP 여러 개에서 동시 6건 이상을 받음, 새 원칙의 "서버 전체 동시 상한"과 부딪힘
- 채택하지 않은 이유: [이유 미확인] (고르지 않음)
### F안: 동시 5건
- 채택하지 않은 이유: 사용자 질문 "5건으로 했다가 막힐 위험은?" 뒤 3건을 고름 (2026-10-13)

## 결과
- 좋아지는 점: 교보 서버를 쓰는 도서관의 대출 현황이 다시 나옴. 막힌 IP와 다른 IP를 나눠 다룸
- 감수하는 점: 다른 IP로 다시 가는 것이 차단을 피하는 것으로 읽힐 수 있음(대법원 2021도1533은 보호조치 여부로 판단, 다른 IP 재접근을 직접 다룬 한국 판례는 찾지 못함). 조회 서버를 동시에 여러 대 쓰게 되면 교보 서버가 받는 수가 "3 × 조회 서버 수"가 됨 → 평소 한 대만 쓰는 조건을 지켜야 함
- dev에 넘길 것: 수집기의 `*.dkyobobook.co.kr` 거름을 "막힌 IP(집)에서만"으로, 서비스 교보 서버 묶어 세기·동시 3건(조회 서버 안에서)·스스로 줄이기·멈추기·"확인 불가" 응답. 넘기는 시점은 배포 사이클
- 나중에 서비스로 분리할 때: 조회 서버가 이미 따로 배포되는 단위라 바꿀 것 없음
