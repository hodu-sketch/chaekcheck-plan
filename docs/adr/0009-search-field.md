# ADR-0009: 검색 필드: 제목 필드로 검색하고 캐시 키에 검색 필드를 넣음

Status: Accepted
Date: 2026-09-27
Cycle: 01-ebook-availability-search
Supersedes: 없음

## 배경
사이클 01 설계는 두 사이트 모두 통합검색(제목+저자+출판사)을 썼다. 교보는 `schClst=all`, YES24는 `srch_order` 없음이었다. spec은 "책 제목 검색"인데, 개발 중 `한강`을 통합검색하면 교보 15건, 제목 필드로는 3건이 나왔다. 두 사이트 모두 제목 검색은 부분 일치다. 이 결정은 사이클 01 개발 중(2026-09-27)에 내렸고, 사이클 02 시작 때 늦게 기록한다. 캐시 방식 자체(ADR-0006)는 바꾸지 않고, 캐시 키에 필드 하나를 더한다.

## 결정
사이클 01 검색은 제목 필드로 한다(교보 `schClst=ctts`, YES24 `srch_order=title`). `availability` 안에 검색 필드 `SearchField`(TITLE, AUTHOR, PUBLISHER)를 두고, 캐시 키를 (libraryId, field, 정규화한 q, page)로 한다. 저자·출판사 검색 API(`field` 파라미터)는 아직 열지 않는다.

## 검토한 대안
### A안: 제목 필드 + 내부 검색 필드 구조 (채택)
- 장점: spec의 "제목 검색"과 맞고 관계없는 결과가 줄어듦. 저자·출판사 검색을 붙일 때 캐시와 adapter를 다시 짜지 않아도 됨
- 단점: 저자 이름으로 찾던 사용자는 결과를 못 봄. 교보는 옮긴이 검색 불가
### B안: 통합검색 유지 (설계 원안)
- 장점: 결과가 많아 놓치는 책이 적음
- 단점: 저자·출판사가 같은 관계없는 책이 섞임
- 채택하지 않은 이유: [이유 미확인]
### C안: 제목 필드로만 바꾸고 필드 구조는 두지 않음
- 장점: 코드가 가장 단순함
- 단점: 저자·출판사 검색을 추가할 때 캐시 키와 adapter 호출을 다시 바꿔야 함
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 결과가 제목 기준으로 좁혀짐. 나중에 `field=title|author|publisher` 파라미터를 붙이기 쉬움 (dev feedback 제안 [안])
- 감수하는 점: 필드가 늘면 캐시 항목도 필드 수만큼 늘어남. 교보는 저자 칸에 옮긴이가 없어 옮긴이 검색 결과가 사이트마다 다름
- 나중에 되돌리거나 서비스로 분리할 때: 통합검색으로 되돌리려면 adapter URL 값과 필드 값 하나만 바꾸면 됨. 캐시를 Redis로 옮길 때 키에 field를 포함해야 함
