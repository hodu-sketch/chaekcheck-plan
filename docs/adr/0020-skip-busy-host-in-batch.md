# ADR-0020: 묶음 안에서 바쁜 호스트의 후보는 뒤로 미룸

Status: Accepted
Date: 2026-09-29
Cycle: 02-library-expansion
Supersedes: 없음

## 배경
사이클 02 개발 중 dev에서 사용자가 정한 결정을 사이클 03 시작 때(2026-09-29) 기록한다. ADR-0014(묶음 단위 검색)를 보완한다.
인계서 9단계 `[안]`은 "같은 호스트는 throttle이 차례로 보내며, 순서를 바꿔 피하지 않는다"였다. seed를 넣은 뒤, 경남교육청 서버(`ebook.gne.go.kr`)를 쓰는 여러 도서관이 한 묶음에 몰리면 1초 간격 줄서기로 묶음 8초를 넘겨 일부가 `upstream_timeout`이 됐다(`채식주의자` 첫 묶음, 30곳 중 2곳, dev plan-feedback 11단계 seed 결과).

## 결정
- 묶음 실행기는 같은 묶음에서 같은 호스트(포트 무시)의 요청이 진행 중이거나, 끝난 지 `host-min-interval`(1초)이 지나지 않았으면 그 후보를 건너뛰고 다음 후보를 먼저 시작한다. 서버가 비면 건너뛴 후보를 후보 순서대로 먼저 시작한다.
- 시작 마감까지 시작하지 못한 후보는 요청하지 않고 실패로도 보내지 않는다. 브라우저가 다음 묶음에서 다시 보낸다.
- `HostThrottle`의 동시 1건·1초 규칙(ADR-0010), 계획 순서, API·SSE 형식은 바꾸지 않는다.

## 이유 (사용자 발언)
- "이거 승인" (dev 설명 페이지의 추천안에 대해, 2026-09-29, dev plan-feedback C2-U-12)

## 검토한 대안
### A안: 바쁜 호스트의 후보를 건너뛰고 다음 후보 먼저 (채택)
- 장점: 한 서버에 도서관이 몰려도 묶음 시간을 다른 도서관이 씀
- 단점: 요청 시작 순서가 계획 순서와 조금 달라짐
### B안: 차례로 기다림 (인계서 `[안]`)
- 장점: 단순함, 시작 순서 = 계획 순서
- 단점: 같은 서버 도서관이 묶음 마감을 넘겨 시간 초과됨
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 같은 서버를 쓰는 도서관이 많아도 묶음 안 시간 초과가 줄어듦. backlog 후보 "같은 호스트 사이트가 한 묶음에 몰리지 않게 순서 바꾸기"를 대신함
- 감수하는 점: 계획 순서와 실제 시작 순서가 다를 수 있음(결과 표시 순서는 계획 순서 기준 정렬이라 화면은 그대로)
- 본 서비스를 여러 대로 늘리면 "바쁨" 판단이 서버마다 따로 이루어짐 (ADR-0021)
