# ADR-0061: 도서관 사이트 연결에만 최상위 인증 기관 하나를 더 믿는다

Status: Accepted
Date: 2026-10-05
Cycle: 07-candidate-libraries
Supersedes: 없음 (ADR-0022 보완)

## 배경
우리 서버는 도서관 사이트에 https로 접속할 때 Java(JDK)에 들어 있는 최상위 인증 기관만 믿기로 했다(ADR-0022). 사이클 07에서 후보 도서관을 넣고 보니 세계사이버대, 서울신학대, 충북 전자도서관 3곳은 JDK 25에 없는 기관(OISTE WISeKey Global Root GB CA)의 인증서를 써서 늘 연결에 실패했고, 12곳은 사이트가 중간 인증서를 보내지 않아 실패했다(dev `docs/plan-feedback.md` "handoff 밖 추가 작업 A", dev `docs/library-site-issues.md` 3-2절, 2026-10-05). 결정은 개발 중에 사용자가 했고, 기록은 사이클 07 회고에서 남긴다.

## 결정
OISTE WISeKey Global Root GB CA를 **도서관 사이트 연결에만** 더 믿는다(로그인 등 다른 연결에는 쓰지 않음). 빠진 중간 인증서 3개도 같은 폴더 `tls/library-roots/`(본 서비스와 조회 서비스 둘 다)에 둔다. 새 기관을 더할 때는 사용자 승인을 받는다. ADR-0022의 나머지는 그대로다.

## 이유 (사용자 발언)
- "이거 신뢰해줘" (2026-10-05, dev 기록)
- 기록 시기: "지금 이것만 먼저 기록." (2026-10-05, 사이클 07 dev 남은 질문 #8)

## 검토한 대안
### A안: 이 기관을 도서관 연결에만 더 믿음 (채택)
- 장점: 3곳 결과가 나옴. 믿는 범위가 도서관 연결로 좁음
- 단점: JDK 밖에서 관리하는 인증서가 생김(만료·교체를 따로 챙겨야 함)
### B안: 그대로 두고 3곳은 "확인 실패"로 보임
- 장점: 보안 설정이 그대로
- 단점: 3곳 결과가 나오지 않음
- 채택하지 않은 이유: [이유 미확인]
### C안: 3곳을 끔
- 장점: 실패가 보이지 않음
- 단점: 그 도서관이 검색에서 빠짐
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 3곳 연결이 됨. 사이클 02 기록 "Sectigo R46은 JDK에 있음"은 틀렸다(JDK 25에는 없음, USERTrust 교차 인증서로 풀림, dev 확인 2026-10-05)
- 나중에 분리할 때: 조회 서비스도 같은 폴더를 읽으므로 두 배포 단위에 같은 인증서를 둔다
