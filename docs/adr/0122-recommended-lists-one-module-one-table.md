# ADR-0122: 추천 목록 셋(이동진·사서·서울대)은 `picks` 모듈 하나가 맡고, 책 줄은 표 `list_book` 하나에 담음 (`pick` 표 없앰)

Status: Accepted (사용자 승인, 2026-10-16, 설계 정리 페이지)
Date: 2026-10-16
Cycle: 21-recommended-books
Supersedes: 없음

## 배경
사이클 21에서 머리말 「추천도서」 아래 목록이 셋(이동진 추천도서, 사서 추천도서, 서울대 100선)이 되었다. 세 목록은 같은 화면·같은 응답·같은 판 고르기 규칙을 쓴다(scope 확정). 사서추천도서는 사이클 14에서 `picks` 모듈이 서버에서 주 1회 받아 표 `pick`에 담고 있었다.

## 결정
- 세 목록을 `picks` 모듈 하나가 맡는다. 새 표 `list_field`(목록별 분야)·`list_book`(목록의 책 한 줄, `list_key`로 목록을 나눔)을 두고 `pick` 표는 지운다
- 사서추천도서 받기는 지금처럼 서버가 주 1회 하되 받은 목록을 `list_book`에 `list_key = librarian`으로 적는다. 서버 받기는 `librarian` 줄만, 가져오기 반영은 `leedongjin`·`snu100` 줄만 바꾼다. 받기 기록 `fetch_run`은 그대로

## 이유 (사용자 발언)
- 설계 결정 #1(picks 한 모듈) 제안 → 승인 (2026-10-16)
- "사서추천도서도 가져오기로 같이 하는게어떨까해" → "아니다 사서 추천은 따로 가자" (2026-10-16)
- "그리고 PICK테이블이 왜 필요해? 사서추천만을 위한 것이면 불필요한거아니야?", "지금 구조로 가되 PICK 테이블은 없앨 수 있는 거 아니야?" → 제안 → 승인 (2026-10-16, 설계 결정 3 페이지 #1)

## 검토한 대안
### A안: `picks` 하나, 표 하나 (채택)
- 장점: 화면·API가 한 표를 읽음, 표지·캐시·고르기 코드 한 벌. 단점: 사이클 14의 받기·캐시 코드를 고침, 한 표를 서버 받기와 가져오기가 나눠 씀
### B안: 새 모듈(`booklists` 등)을 따로
- 단점: 표지·캐시·고르기·화면 API가 두 벌. 채택하지 않은 이유: [이유 미확인] (추천하지 않은 안, 사용자는 A 승인)
### C안: `picks` 하나에 표 둘(`pick` 그대로 + `list_book`)
- 단점: 책 줄 표가 둘이라 두 곳을 읽음. 채택하지 않은 이유: 사용자 "PICK테이블이 … 불필요한거아니야?" (2026-10-16)
### D안: 사서추천도서도 수집기 → 가져오기 길로
- 채택하지 않은 이유: 사용자 "아니다 사서 추천은 따로 가자" (2026-10-16)

## 결과
- ADR-0089(사서추천 출처와 모듈)는 그대로. 표 `pick`을 정한 사이클 14 설계는 이 ADR로 바뀜. 나중에 분리할 때: `picks` 서비스 하나 = 스키마 `picks` 하나
