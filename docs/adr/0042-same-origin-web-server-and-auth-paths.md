# ADR-0042: 화면 파일은 앞단 웹 서버가 내려 주고 API와 같은 주소를 쓰며, 인증 주소는 /api/v1/auth 아래에 모음

Status: Accepted
Date: 2026-10-04
Cycle: 05-login-account
Supersedes: 없음

## 배경
운영에서 화면 파일(React 빌드)을 누가 내려 줄지 정해진 적이 없었고, 화면 쪽 보안 헤더를 붙일 곳이 없었다. 토큰 쿠키(`SameSite=Lax`, `Domain` 없음)와 CSRF 토큰은 화면과 API가 같은 주소일 때 추가 설정 없이 동작한다.

## 결정
운영에서는 앞단 웹 서버가 화면 파일을 내려 주고 `/api` 요청을 Spring으로 넘긴다(같은 출처). 보안 헤더는 화면 파일에 웹 서버가, API 응답에 Spring Security가 붙인다. dev는 웹 서버 설정 예시 파일을 저장소에 둔다. 인증 흐름의 주소는 모두 `/api/v1/auth/**`에 두고, 액세스 토큰 쿠키는 `Path=/api/v1/me`, 리프레시 토큰 쿠키는 `Path=/api/v1/auth`로 좁힌다.

## 이유 (사용자 발언)
- "이것도 지금에서 하는 게 맞다고 보는데 화면에서 보안적인 구성" (2026-10-04)
- "운영에서 spring이 파일 화면을 내려주고 싶지는 않아 react를 쓰는 의미가 없어지잖아" (2026-10-04)
- 주소와 쿠키 경로: 승인만 함 [이유 미확인]

## 검토한 대안
### A안: 화면 파일은 앞단 웹 서버가 내려 주고 API와 같은 주소를 쓰며, 인증 주소는 /api/v1/auth 아래에 모음 (채택)
- 장점 / 단점: "결과" 절 참고
### B안: Spring이 화면 파일도 내려 줌
- 장점: 헤더를 한 곳에서 관리
- 채택하지 않은 이유: 위 사용자 발언(2026-10-04)
### C안: 화면을 다른 주소의 정적 호스팅·CDN에 올림
- 장점: 화면 파일이 우리 서버를 거치지 않음
- 채택하지 않은 이유: [이유 미확인] (같은 주소 안을 승인. 쿠키·CSRF 설계를 다시 열어야 함)
### D안: Spring 기본 주소(`/oauth2/…`, `/login/…`, `/logout`)와 `Path=/` 쿠키
- 장점: 설정이 적음
- 채택하지 않은 이유: [이유 미확인] (주소를 모으는 안을 승인)

## 결과
- 좋아지는 점: 검색 같은 공개 API에는 토큰이 가지 않아 토큰 문제로 검색이 막히지 않음. 개발 환경(Vite가 `/api`만 넘김)과 같은 모양
- 감수하는 점: `__Host-` 쿠키 접두어를 쓸 수 없음(`Path=/`가 필요). 범위 문서의 주소 둘이 바뀜(`POST /logout` → `POST /api/v1/auth/logout`, `POST /api/v1/me/consents` → `POST /api/v1/auth/signup`). 헤더 설정이 두 곳
- 되돌리는 비용: 주소를 바꾸면 제공자 콘솔의 돌아올 주소를 다시 등록. CDN은 같은 주소 앞에 붙일 수 있어 설계가 바뀌지 않음
