1ADR-0048: 둘째 회원 모듈은 "내 도서관" 전용 mylibrary

2026-10-01의 ADR-0036("로그인 모듈 auth와 회원 자료 모듈 member를 나눔")을 이 기록으로 바꿉니다. 나누는 것은 그대로이고, 둘째 모듈의 이름과 맡는 일만 바뀝니다.

auth
로그인·탈퇴←계정 번호·탈퇴 소식만 받음—mylibrary (새)
지역 + 직접 추가 도서관
칸적히는 내용
결정로그인(auth)과 내 도서관(mylibrary)을 다른 모듈로 둔다. mylibrary는 사용자와 도서관을 잇는 일(거주·직장 지역, 직접 추가 도서관)만 맡고, 알림의 관심 책은 넣지 않는다
이유사용자: "member말고 도서관-사용자 매핑용 모듈은?" → "매핑 전용 모듈로"(2026-10-04). 이름 mylibrary는 제안 → 승인. 그 밖의 이유 [이유 미확인]
대안member 그대로(채택 안 함: 사용자가 매핑 전용을 고름), patron(채택 안 함: [이유 미확인]), 도서관 모듈 안에 둠(채택 안 함: 검색이 회원을 알게 됨)
바뀌는 기록ADR-0036의 상태를 "ADR-0048로 대체됨"으로 바꿈(내용은 그대로 둠)

2ADR-0049: 내 도서관 화면이 쓰는 목록과 저장 방법

내 도서관 화면은 도서관 모듈이 공개하는 목록 하나로 그리고, 저장은 지역은 통째로·직접 추가 도서관은 하나씩 합니다.

칸적히는 내용
결정① 도서관 모듈이 로그인 없이 쓰는 공개 목록 GET /api/v1/libraries?residenceRegionIds=&workRegionIds=를 둔다. 줄마다 "누구나 가입 / 거주로 됨 / 직장으로 됨" 표시가 붙고, 화면이 이것으로 여섯 구역·누구나 가입 줄·이름 검색을 만든다. ② 저장은 /api/v1/me/regions(통째로), /api/v1/me/libraries/{도서관 번호}(하나씩 넣고 빼기). ③ 다시 묻지 않는 메모와 스위치 값은 그 브라우저 안에 둔다
이유[이유 미확인] (제안 → 승인, 2026-10-04)
대안내 도서관 모듈이 서버에서 다 계산(채택 안 함: [이유 미확인]), 세 목록으로 나눠 줌(채택 안 함: [이유 미확인]), 직접 추가 목록도 통째로 저장·지역과 한 묶음 저장(채택 안 함: [이유 미확인])
감수하는 점도서관 278곳을 한 번에 내려받음(크기는 dev가 잼). 수천 곳이 되면 서버에서 이름으로 거르는 방식으로 바꿈

2ADR-0049를 위 내용으로 씀 [안]

공개 목록은 회원을 모르므로 "검색은 회원을 모르고 화면이 번호를 넘긴다"(ADR-0037)를 그대로 지킵니다.

질문: 지역을 "통째로" 저장하면 거주와 직장은 어떻게 나뉘나요?

한 번 보낼 때 거주 칸과 직장 칸이 따로 들어 있고, 서버도 줄마다 "거주"인지 "직장"인지 적어 둡니다. "통째로"는 거주 목록과 직장 목록을 한꺼번에 새 값으로 바꾼다는 뜻이지, 둘을 섞는다는 뜻이 아닙니다. 그림으로 보면 이렇습니다.

① 화면: 지역 고르기 창
거주: 서울 마포구
직장: 서울 중구, 경기 성남시
[저장]을 누름
→
② 서버로 가는 내용 (한 번)
거주 칸: [서울 마포구]
직장 칸: [서울 중구, 경기 성남시]
칸 이름이 따로 있어서 섞이지 않음 (residenceRegionIds / workRegionIds)
→
③ 서버에 저장된 줄
거주 · 서울 마포구
직장 · 서울 중구
직장 · 경기 성남시
줄마다 "거주/직장" 칸(kind)이 있음

API 구조로 보면: POST가 아니라 PUT(있던 값을 통째로 새 값으로 바꾸는 요청)이고, 요청 본문(JSON) 안에 거주와 직장이 서로 다른 칸으로 들어 있습니다.

요청본문 / 응답
PUT /api/v1/me/regions
(헤더 X-XSRF-TOKEN)
{
  "residenceRegionIds": [1114],
  "workRegionIds": [1101, 4113]
}
두 칸 모두 필수(빈 배열 가능), 칸마다 최대 20, 고른 순서 유지. 응답 200은 저장한 값 그대로
GET /api/v1/me/regions
{ "residenceRegionIds": [1114], "workRegionIds": [1101, 4113] }
오류400 validation_error(칸 빠짐·형식·20개 초과, errors[].field가 residenceRegionIds 또는 workRegionIds), 422 invalid_region(폐지·없음·시도 ID, 어느 칸의 몇 번인지 표시), 401, 403 csrf_invalid

칸 이름은 지금 검색 API가 쓰는 residenceRegionIds·workRegionIds와 같습니다. 직접 추가 도서관은 PUT/DELETE /api/v1/me/libraries/{도서관 번호}로 하나씩입니다(본문 없음).

내 도서관 화면에서 "거주 지역 선택"의 [변경]만 눌러 거주를 바꿀 때도, 화면이 직장 칸에는 지금 값을 그대로 담아 함께 보냅니다. 그래서 직장은 바뀌지 않습니다.

다른 방법 거주와 직장을 주소부터 따로 둠(거주만 저장, 직장만 저장). 화면 구역과 딱 맞고, 두 탭에서 한쪽은 거주·다른 쪽은 직장을 동시에 바꿔도 서로 덮어쓰지 않습니다. 대신 주소가 둘로 늘어납니다. 지금 제안(한 번에 둘 다)은 한 사람이 두 탭에서 동시에 지역을 바꾸는 드문 경우에만 나중 저장이 이깁니다. 따로 두기를 원하시면 2번에 기타로 적어 주세요.

3ADR-0050: 직접 추가한 도서관은 검색에서 맨 앞, 자격 규칙의 예외

직접 추가한 도서관은 "이미 가입해서 넣은 곳"으로 보고, 검색 계획에 "직접 추가" 표시를 붙여 맨 앞에 둡니다. 자격 배지와 "방문 없이 가입" 거르기에서 빠집니다.

칸적히는 내용
결정검색 요청에 libraryIds(직접 추가 도서관 번호)를 받고, 그 도서관에 "직접 추가" 표시를 붙여 결과 맨 앞에 둔다(스위치가 "전체"여도). 원래 무리(내 시군구 등)는 그대로 둔다. 가입 자격 배지 대신 "직접 추가"만 보이고, "방문 없이 가입"을 켜도 빼지 않는다
이유사용자: "직접 추가한 도서관은 예외임. \"가입 자격 확인 필요\" 필요없음", "이미 가입된 도서관이라서 넣는다 이거 간단하게 표시하고 넣어줘" (2026-10-04). 맨 앞에 두는 것과 표시 방식은 제안 → 승인
대안새 무리 "직접 추가"로 바꿈(채택 안 함: [이유 미확인]. 원래 무리를 잃음), "전체"에서는 앞에 두지 않음(채택 안 함: [이유 미확인]), 자격 배지를 그대로 보임·"방문 없이 가입"이면 뺌(채택 안 함: 위 사용자 말)

3ADR-0050을 위 내용으로 씀 [안]

방문 가입 순서를 정한 ADR-0027과 함께 읽히도록 서로 이어 둡니다.

4ADR-0051: 저장과 탈퇴가 겹쳐도 지워진 계정의 자료가 남지 않게

저장할 때 로그인 모듈의 계정 줄을 잠깐 잠그고, 탈퇴 뒤 지우는 처리가 실패해 남으면 서버를 다시 켤 때 다시 처리합니다.

칸적히는 내용
결정① 로그인 모듈이 "계정이 아직 있으면 그 줄을 잠근다" 기능 하나를 공개하고, 내 도서관 모듈은 저장할 때마다 이것을 먼저 부른다(같은 계정의 저장이 한 줄로 서서 20곳 상한도 정확함). ② 탈퇴 소식 처리가 실패해 남으면 서버를 다시 켤 때 자동으로 다시 처리한다(설정 한 줄)
이유[이유 미확인] (제안 → 승인, 2026-10-04). 지켜야 할 조건은 명세 AC-12 "지워진 계정의 줄이 생기지 않는다"(사용자 승인)
근거PostgreSQL 문서 13.3 Row-Level Locks(https://www.postgresql.org/docs/current/explicit-locking.html), Spring Modulith Events(https://docs.spring.io/spring-modulith/reference/events.html). 둘 다 2026-10-04 설계 에이전트가 확인
나중에 나눌 때서비스로 나누면 잠금을 쓸 수 없으므로 "하루 한 번 대조해 지움"으로 바꾼다. 서버를 여러 대로 늘리면 다시 처리 방식을 다시 본다

4ADR-0051을 위 내용으로 씀 [안]

사이클 05의 ADR-0041(탈퇴 소식을 저장해 두고 처리함)과 이어 둡니다.
