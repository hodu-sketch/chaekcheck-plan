내용이 맞으면 승인해 주세요.

ADR은 "무엇을, 왜 그렇게 정했나"를 나중에 찾아볼 수 있게 남기는 문서입니다(docs/adr/). 지금까지 고르신 결정을 네 묶음으로 정리했고, 이유 칸에는 하신 말씀을 그대로 옮겼습니다. 승인하면 파일로 씁니다.

1ADR-0113 저자 정리:
기호 떼기 · 붙은 역할 나누기 · 저자 칸 정리

정한 것이유 (하신 말)
꺾쇠 < >·＜ ＞는 뗌, 〈 〉「 」《 》는 표시만 떼고 글자는 남김, [ ]는 그대로"〈 〉 「 」 《 》의 괄호 표시만 떼고 글자는 남김 으로 하자"
「…저이소연 역」 같은 붙은 역할은 좁은 규칙 + 보호 장치로 나눔(셋째 역할까지)"좁은 규칙 + 보호 장치로 해"
책 저자 칸은 기호를 떼고 붙은 역할 뒤를 띄워 넣음(「밥 프록터 저 이재경 역 조성희 감수」)"고쳐 주는게 좋지 않을까? 이거 추가하는 것도 그렇게 어렵지 않아 보이는데"
같은 규칙을 저자 검색어에도, 정리 함수는 저자 정리 쪽(catalog)에제안 → 승인

검토한 다른 선택(표 넣는 쪽에서 정리, 괄호를 그대로 둠, 화면은 원문대로)과 채택하지 않은 이유도 적었습니다. 초안 파일: 0113-author-marks-and-glued-roles-in-normalize.md

이 초안대로 ADR-0113을 씁니다. [안]
요청: 이것도 수집기가 하는 거고, AI가 md를 보고 잘 할 수 있도록 문서랑 python 코드랑 잘 구조화되어 있도록 방향 지침을 했으면 해
먼저 바로잡을 점: 저자 정리는 수집기(Python)가 아니라 가져오기(백엔드 Java)에서 합니다. 수집기는 도서관 화면의 원문을 그대로 수집 DB에 넣고, 정리는 가져올 때 합니다(dev docs/maintenance/2-crawl.md 27행 "수집 DB는 원문만 두고 정리는 거기서"). 그래도 방향 지침은 수집기와 가져오기 모두에 필요하므로 아래처럼 하겠습니다.

방향 지침 (제안)

  • 규칙 목록 문서 하나(#2에서 말씀드린 dev docs/maintenance/rules-index.md)에 수집기·가져오기·도서관 규칙을 모두 적음: 어디에(파일·상수) / 뜻 / 데이터로 확인하는 법 / 바꾸는 법과 그 뒤 할 일
  • Python 수집기: 사람이 정한 값(사이트별 쪽 크기, 공유 서버, 출판사가 먼저인 포털 등)은 파일 맨 위 "규칙" 묶음에 모으고, 상수마다 규칙 목록의 줄을 가리키는 주석. 목록이 길어지면 표 파일(scripts/library/rules/)로 옮김
  • Java 가져오기: 저자 정리(Contributors의 역할 낱말·기호)와 같은 책 묶기(SameTextKey의 판 낱말·남길 낱말) 상수도 같은 주석과 규칙 목록 줄
  • 점검: 수집·가져오기 문서의 시작 점검 목록이 규칙 목록의 "확인하는 법"을 돌리게 함 → 다른 세션의 Claude가 문서만 보고 규칙을 검증·고칠 수 있음

승인하시면 이 지침을 따로 결정 기록 ADR-0117("사람이 정한 규칙은 코드·표 파일에 두고 규칙 목록 문서로 찾고 검증한다")로 초안을 만들어 다음 페이지에서 확인받고, ADR-0113~0115는 그 지침을 따른다고 한 줄씩 적겠습니다.

질문: 가져오기도 어차피 운영 서버가 아니라 내 PC에서 하는 거니까 괜찮은 거지?
네, 맞습니다. 저자 정리·같은 책 묶기·규칙 파일 읽기는 모두 내 PC 가져오기에서만 돌고, 운영 서버는 다 만든 책 목록 파일을 받아 넣기만 합니다(ADR-0078). 그래서 규칙을 바꾸면 내 PC에서 다시 가져와 반영하면 됩니다.
이번 사이클에서 바뀌는 것도는 곳
저자 정리, 같은 책 묶기, 앞 괄호, 공급사 코드, 뒤바뀐 칸, 규칙 파일내 PC (가져오기)
수집기 포털 칸 순서내 PC (수집)
사용자가 검색창에 친 저자 글자에서 기호 떼기운영 서버 (검색할 때마다) — 그래서 반영 뒤 서비스를 새 판으로 다시 켬
"캐시 답" 세기운영 서버 (사용 기록) — 새 판 서비스와 칸 하나 더하기

운영 서버 쪽은 이 두 가지만 바뀌고, 둘 다 새 판 서비스를 켜면 함께 들어갑니다.

2ADR-0114 같은 책 묶기:
같은 공급사 코드로 잇기 · 제목 앞 괄호

정한 것이유 (하신 말)
같은 공급사의 상품 코드가 같으면 저자를 보지 않고 같은 책(ISBN 잇기 단계에 함께)"각각의 서비스들에 대해서 코드를 다르게 취급" → "같은 공급사의 코드끼리만 견주고, 제목 조건은 두지 않습니다. 이걸로 해줘"
공급사 이름 묶음은 규칙 파일(예: Y2Books 전자책 = 와이투북스)제안 → 승인
같은 책 견줄 제목에서만 앞 괄호를 뗌, 판·원서·형태·뒷권과 "…판"은 남김(코드 상수)승인 (질문 "이거 db에 정보 두는 건 이상하나"에 답한 뒤)

근거: 수집 DB에서 9자리 번호를 북큐브와 YES24가 함께 씀, KORMARC 245 관제 규칙. 초안 파일: 0114-grouping-supplier-codes-and-leading-notes.md

이 초안대로 ADR-0114를 씁니다. [안]
질문: 이거 수집기의 구체적으로 어느 부분에서 이렇게 되었다는 거야? md?
공급사 코드와 공급사 이름은 수집기가 도서관 화면에서 읽어 수집 DB에 넣은 값입니다. 코드 자리와 기록한 문서는 아래와 같습니다.
화면 종류수집기에서 읽는 곳 (dev scripts/crawl/crawl_catalog.py)수집 DB에 들어가는 칸
북큐브784~787행: 목록 XML의 legacyCode → 공급사 코드, supplier → 공급사 이름holding.alt_code, holding.supplier (예: 1210492004114, 「Y2Books 전자책」)
교보575행: 목록의 상품 번호(brcd)와 span.store → 공급사 이름holding.item_key, holding.supplier (예: 1210492004114, 「와이투북스」)
YES24618~620행: 상품 번호(goods_id)와 셋째 칸 → 공급사 이름holding.item_key, holding.supplier
  • "9자리 번호를 북큐브와 YES24가 함께 쓴다"는 수집기 코드가 아니라 수집 DB에 쌓인 값을 세어서 안 것입니다(2026-10-15, 공급사별 번호 모양). 기록 문서: plan docs/cycles/19-author-angle-brackets/research.md "공급사 코드 모양" 절
  • 북큐브가 다른 공급사 책을 팔 때 그 공급사의 번호를 공급사 코드로 내보내는 것으로 보입니다(같은 코드가 교보 화면 와이투북스 줄과 같음). 북큐브 쪽 공식 설명은 확인 못 함
  • 화면별로 어느 칸을 읽는지는 dev docs/maintenance/platforms.md에 있습니다. 이번에 쓰는 "공급사 코드" 뜻은 ADR-0114와 인계서에 함께 적습니다
질문: 다른 세션이 수집기 문서로 검증할 때 이 규칙도 들어가야 하고, 규칙은 바뀔 수 있어야 해. 코드에 있되 AI가 파악하기 쉽게 되어 있어? 안 되면 그렇게 가야 해
절반만 그렇습니다. 표 파일로 둔 도서관 규칙은 AI가 찾기 쉽게 정리돼 있지만, 코드 상수로 둔 규칙(수집기 Python, 같은 책 묶기 Java)은 흩어져 있고 모아 둔 문서가 없습니다. 그래서 "규칙 목록" 문서 하나를 두는 것을 이 결정에 더하기를 추천합니다.
규칙이 있는 곳예AI가 찾고 바꾸기 쉬운가
dev scripts/library/rules/*.tsv이름 고침, 같은 사이트, 가입 범위 … (이번에 supplier_families.tsv, author_publisher_swapped.tsv 더함)쉬움 — 폴더 README.md에 파일마다 칸·뜻·출처·고친 뒤 할 시험이 표로 있음
수집기 scripts/crawl/crawl_catalog.py 맨 위 상수PAGE_SIZE_BY_HOST, SHARED_HOSTS … (이번에 PUBLISHER_FIRST_PORTAL_HOSTS)덜 쉬움 — 1,300줄 한 파일 안 상수, 짧은 주석뿐, 수집 문서가 가리키지 않음
가져오기 SameTextKey.java 상수판 낱말 11개, 꼬리 표시 … (이번에 남길 낱말 목록)덜 쉬움 — 코드 주석에만 뜻이 있음

추천 보탬:

  • dev docs/maintenance/에 규칙 목록 문서(예: rules-index.md)를 하나 둡니다. 사람이 정한 규칙마다 한 줄: 어디에 있나(파일·상수 이름) / 뜻 / 데이터로 맞는지 확인하는 법(예: 포털 칸 순서는 새 책 목록 한 쪽 열기, 공급사 묶음은 수집 DB 공급사 이름 세기) / 바꾸는 법과 그 뒤 할 일(다시 수집 또는 다시 가져오기)
  • 코드 상수마다 "규칙 목록의 어느 줄"을 가리키는 주석을 답니다 → AI가 상수를 보면 문서로, 문서를 보면 상수로 갈 수 있음
  • 수집 문서(2-crawl.md)와 가져오기 문서(3-import.md)의 시작 점검 목록에 "규칙 목록의 확인 칸을 한 번씩 돌림"을 넣습니다 → 다른 세션이 수집·가져오기 할 때 이 규칙도 검증됨
  • 규칙 내용은 지금처럼 코드·표 파일에 두므로 바꿀 수 있고, 바꾼 이력은 git에 남습니다

이 보탬을 ADR-0114(같은 책 묶기)와 ADR-0115(뒤바뀐 포털)에 함께 적고, 19 인계서의 dev 문서 할 일에 넣겠습니다. 이대로면 이 칩에 "승인"을, 다르게 하시려면 "기타"에 적어 주세요.

3ADR-0115 저자·출판사가 뒤바뀐 세 포털

정한 것이유 (하신 말)
가져올 때 줄을 읽는 순간 두 칸을 바꿈(규칙 파일, 수집 번호 11·12·15)"같이하자 어짜피 cycle19가 내용이 그렇게 안 많아"
고친 수집기 뒤 사본이면 멈추고, 다시 검증한 뒤에만 규칙 줄을 지움"잊지 않게 막되 다음에도 이 규칙이 맞는가 검증은 해야 해 지금이 뜻하는 데이터 가공 방향으로"
수집기 상수로 세 포털만 바꿔 읽고, 수집 전 점검 목록에 칸 순서 확인"이거 md에서 기록해놔서 다음에 수집할 때 고려가 되어야하는지 잘 체크하게 해줘"

초안 파일: 0115-swapped-author-publisher-portals.md

이 초안대로 ADR-0115를 씁니다. [안]
질문: 이거 수집기 클로드나 너와 같은 AI랑 같이 잘 돌도록 구성되어 있는 거지?
네, 그렇게 짜여 있습니다. 수집·가져오기는 dev 운영 문서를 Claude 세션이 읽고 돌리는 방식이고, 이번 장치도 그 흐름에 맞췄습니다. 다만 "다시 검증"을 사람 손 SQL이 아니라 스크립트 하나로 만들면 AI가 더 확실하게 돌립니다 — 이것을 더하기를 추천합니다.
  • 지금 근거: dev docs/maintenance/1-libraries.md 114행 "보고서는 Claude(수집 세션)가 먼저 읽고, 의심·바뀐 곳만 사용자에게" — 사람이 정한 규칙(TSV)·멈춤 메시지·문서 절차로 AI가 따라 하게 되어 있음
  • 이번 장치: 가져오기가 멈출 때 메시지에 "어느 규칙 줄, 무엇을 하라"를 적고, 절차는 3-import.md에 적음
  • 추천 보탬: 비율 검사(사이클 19 실험 (d))를 dev 스크립트(예: scripts/library/check_author_publisher_swap.py)로 만들어, 수집 사본을 넣으면 도서관마다 "바름 / 뒤바뀜 / 판단 못 함"을 찍게 함. Claude는 "바름"이면 줄을 지우고 다시 가져오고, 그 밖이면 사용자에게 물음

이 보탬까지 ADR-0115에 넣으려면 이 칩에 "기타: 검증 스크립트 넣어"라고 적어 주세요. 그대로면 승인만 하시면 됩니다.

4ADR-0116 사용 기록 "캐시 답" 수

정한 것이유 (하신 말)
도서관별 하루 표에 cached_count, 결과 값 CACHED, 새 변경 파일, 사이클 19에 끼움"도서관별 하루 표에 \"캐시 답\" 칸을 하나 더하자" (모양·때·이름·자리는 제안 → 승인)

칸을 더해도 표를 다시 쓰지 않음(PostgreSQL 18 공식 문서, 확인 2026-10-15). 초안 파일: 0116-usagelog-cached-answer-count.md
