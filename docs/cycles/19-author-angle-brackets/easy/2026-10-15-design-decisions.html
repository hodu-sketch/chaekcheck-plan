사이클 19 설계 결정입니다.
"어디를 어떻게 고칠지" 11개를 골라 주세요.

무엇을 고칠지는 명세에서 모두 정했습니다. 여기서는 dev 코드의 어느 자리에 넣을지만 정합니다. 표 구조는 사용 기록 표에 칸 하나를 더하는 것뿐이고, 화면·API 모양은 바뀌지 않습니다. 원본은 architect-proposal.md(그림이 든 원본 페이지 따로)입니다.

어디가 바뀌나 (한눈에)

파란 칸이 고치는 자리입니다. 책 목록 표의 모양은 그대로이고 들어가는 값만 바뀝니다.

1공급사 코드로 잇기를
지금 "ISBN 잇기" 단계에 함께 넣을지

지금 같은 책 묶기는 ① 화면 번호 → ② ISBN으로 잇기 → ③ 국가서지 → ④ 같은 글 순서입니다. 공급사 코드(예: 와이투북스 1210492004114)를 ②에서 ISBN과 같이 "같은 값이면 잇는 표"로 셉니다.

② 단계를 넓혀 ISBN과 (공급사, 코드)로 함께 잇습니다. 다시 가져오기 전 미리 돌려 볼 때 "코드로 이었는데 ISBN이 둘 이상인 묶음" 수를 세어 0이 아니면 plan에 묻습니다. [안]

다른 선택: ②와 ③ 사이에 새 단계를 두고 ISBN이 다른 묶음은 잇지 않음 → 더 안전하지만 세 묶는 방식(compact·objects·sql)을 모두 크게 고쳐야 해 공개일(10/18) 일정에 부담.

2목록에 없는 공급사 이름은
어떻게 다룰지

공급사 이름을 같은 묶음으로 모으는 목록을 둡니다(예: 「Y2Books 전자책」 = 「와이투북스」). 확인해 보니 「김근아 저자」 줄은 「Y2Books 전자책」, 같은 코드의 교보 줄은 「와이투북스」라서 이 묶음이 있어야 모입니다.

목록에는 "다른 이름 → 같은 묶음"만 적고, 목록에 없는 이름은 다듬은 이름 그대로 한 공급사로 봅니다(예: 「교보문고」와 「(주)교보문고」는 다듬으면 같음). [안]

다른 선택: 목록에 있는 공급사만 코드로 이음 → 더 조심스럽지만 dev가 공급사 이름을 모두 검토해 목록에 넣어야 함.

3세 도서관의 저자·출판사를
줄을 읽을 때 바꿀지

가져오기가 수집 줄을 읽는 순간 두 칸을 바꿉니다. 그래서 책 화면의 도서관 줄 정보까지 바른 값이 됩니다. 이 세 도서관의 소장 줄은 "수집 원문 그대로"가 아니게 되므로 데이터 모델 문서에 적어 둡니다. [안]

다른 선택: 같은 책 묶기와 책 만들기에서만 바꿈 → 고칠 곳이 늘고, 책 화면 도서관 줄의 저자·출판사는 계속 뒤바뀜.

4규칙 파일 두 개를
어디에 어떻게 둘지

파일 (dev scripts/library/rules/)칸내용
author_publisher_swapped.tsvcollection_id, name, decided_on, swap_before, note수집 번호 11·12·15
supplier_families.tsvsupplier, family, decided_on, note같은 공급사 이름 묶음 (dev가 수집 DB에서 만들어 보고)
위 두 파일을 사람이 정한 도서관 규칙 폴더에 두고, 가져오기 설정 rules-dir로 읽습니다. 파일이 없으면 가져오기가 멈춥니다. [안]

다른 선택: 백엔드 코드 안 자료로 둠 → 설정은 필요 없지만 사람이 정하는 규칙이 두 곳으로 나뉨.

5세 도서관 줄을 지우는 것을
잊지 않게 막을지

명세에서 "고친 수집기로 새로 받은 사본을 가져올 때 이 규칙 줄을 지운다"고 정했습니다. 잊고 두면 바르게 받은 줄을 다시 뒤바꿉니다.

규칙 줄에 "고친 수집기가 들어간 날"을 적고, 그 뒤에 받은 사본이면 가져오기가 "규칙 줄을 지우세요"로 멈춥니다. [안]

다른 선택: 막는 장치 없이 dev 절차 문서에 한 줄만 적음 → 코드는 작지만 잊으면 세 도서관이 다시 뒤바뀜.

6저자 칸 정리 함수를
저자 정리 쪽(catalog)에 둘지

사람 이름을 나누는 규칙과 책 화면 저자 칸을 정리하는 규칙이 같아야 어긋나지 않습니다.

저자 정리 공개 함수 둘을 둡니다: 기호만 떼는 stripMarks(이름 나누기 맨 처음, 저자 검색어에도 씀), 기호를 떼고 붙은 역할 뒤를 띄우는 displayText(가져오기가 책 표 저자 칸을 넣을 때 한 번 부름). 세 묶는 방식은 고치지 않습니다. [안]

다른 선택: 책 표를 쓰는 쪽(catalog의 표 넣기)에서 정리 → 지금은 가져오기가 정리된 값을 넘기는 약속이라 그 뜻이 바뀜.

7제목 앞 괄호에서 남길 낱말 목록을
코드 상수로 둘지

지금 같은 책 묶기의 목록(판 낱말 11개, 꼬리 표시 등)은 모두 코드 상수이고, 바꾸면 다시 가져옵니다(ADR-0069).

남길 낱말 목록도 같은 자리의 코드 상수로 둡니다. [안]

다른 선택: 규칙 파일 → 빌드 없이 고칠 수 있지만 묶기 규칙의 원본이 둘로 나뉨.

질문: 이거 무슨 말이야? 그림과 표로 어느 DB에서 어느 값으로 사용하는지 알려줘
"남길 낱말 목록"은 어느 DB에도 저장되지 않고 가져오기 프로그램 코드 안에 적힌 목록입니다. 가져올 때 한 번 쓰이고, 그 결과(어떤 줄을 한 책으로 모았는지)만 책 목록 DB에 남습니다.

"코드 상수로 둔다"는 이 목록을 프로그램 코드 안에 적는다는 뜻입니다. 다른 선택인 "규칙 파일"은 같은 목록을 dev 폴더의 표 파일(scripts/library/rules/)에 적고 가져올 때 읽게 하는 것입니다. 어느 쪽이든 DB에는 들어가지 않고, 목록을 바꾸면 책 목록을 다시 가져와야 효과가 납니다.

질문: 이거 DB에 정보 두는 건 이상하나?
이상하지는 않습니다. 다만 이 목록은 DB에 두어도 얻는 것이 적고 할 일만 늘어서 코드 상수를 그대로 추천합니다.
둘 곳좋은 점걸리는 점
코드 상수 (추천)지금 같은 책 묶기 목록(판 낱말 11개 등)과 같은 자리. 바꾼 이력이 git에 남고 dev 시험이 바로 씀낱말을 더하려면 코드를 고치고 빌드
규칙 파일 (dev git 표 파일)빌드 없이 고침. 이력은 git에 남음(도서관 규칙들과 같은 방식, ADR-0085)묶기 규칙의 원본이 코드와 파일 둘로 나뉨
DB 표SQL로 보고 고칠 수 있음새 표·변경 파일·고치는 방법이 필요. 가져오기는 내 PC에서만 돌므로 운영 DB에 둬도 쓰이지 않고, 내 PC DB에만 있으면 백업·이력이 git보다 약함. 바꿔도 결국 다시 가져와야 효과가 남

DB에 두기 알맞은 것은 운영 중에 서비스가 읽고 바로 반영되는 값입니다(예: 도서관을 켜고 끄는 enabled, 공지 글). 이 목록은 가져올 때만 쓰이는 묶기 규칙이라 코드 쪽이 맞다고 봅니다. 그래도 빌드 없이 고치고 싶으시면 "기타"에 "규칙 파일로"라고 적어 주세요.

8"캐시 답"을 알리는 방법

지금 사용 기록에 도서관 응답 결과는 넷(성공·실패·시간 초과·건너뜀)으로 알립니다.

결과 값에 "캐시 답"(CACHED)을 하나 더합니다. 캐시에서 답을 꺼낸 두 곳이 이 값으로 알리고, 하루 표의 cached_count가 1 늘어납니다. 서버 로그 줄은 쓰지 않습니다. [안]

다른 선택: 따로 알리는 새 함수 → 뜻은 더 분명하지만 공개 함수가 늘어남 / 기존 함수에 "캐시냐" 표시를 더함 → 부르는 곳이 모두 바뀜.

9"캐시 답" 칸을 더하는 변경 파일

공식 문서로 확인: 상수 기본값으로 칸을 더하면 표를 다시 쓰지 않아 빠릅니다(PostgreSQL 18 ALTER TABLE, postgresql.org, 확인 2026-10-15).

사용 기록 쪽 새 변경 파일 하나(usagelog/002-library-response-cached-count.yaml)로 칸을 더하고, 기존 파일은 고치지 않습니다. [안]

다른 선택: 아직 공개 전이니 기존 usagelog/001에 접어 넣음 → 이미 적용한 내 PC DB들과 어긋나 다시 만들어야 함.

10수집기의 포털 목록을
코드 상수로 둘지

수집기는 이미 사이트별 값(쪽 크기 등)을 코드 상수로 둡니다.

"출판사가 먼저 나오는 포털" 세 곳(lib.goe.go.kr, library.daegu.go.kr, lib.jbe.go.kr)을 수집기 상수로 두고, 그 사이트만 두 칸을 바꿔 읽습니다. [안]

다른 선택: 규칙 파일 → 수집기에 파일 읽기가 새로 생김.

11운영 반영 직후 잠깐의 틈을
받아들일지

새 책 목록으로 바꿔 끼운 뒤 서비스를 새 코드로 다시 켜기까지 짧은 틈이 있습니다(ADR-0069 "바꿔 끼우자마자 다시 켬").

그 틈에는 "<김정은>"처럼 기호를 넣은 저자 검색만 잠깐 못 찾습니다. "김정은" 검색은 맞습니다. 이 정도는 받아들입니다. [안]

다른 선택: 서비스를 먼저 내리고 바꿔 끼움 → 그동안 검색 전체가 멈춤.

질문: 그냥 수집에서 잘 하면 되는 거 아니야? 새 책 목록으로 끼우기 전에 다듬으면 되고 왜 그래?
맞습니다. 책 목록(데이터)은 끼우기 전에 이미 다 다듬어집니다. 틈이 생기는 곳은 데이터가 아니라 사용자가 검색창에 친 글자를 다듬는 서버 프로그램입니다.
  • 책 이름 「<김정은>」은 새 목록에서 이미 「김정은」으로 저장돼 있음 → "김정은"으로 찾으면 틈에도 찾아짐
  • 사용자가 검색창에 「<김정은>」처럼 기호까지 쳐서 찾을 때만, 옛 프로그램은 기호를 떼지 않아 못 찾음 — 프로그램을 새 판으로 다시 켜면 해결
  • 프로그램을 먼저 새 판으로 켜도 같은 크기의 틈이 반대쪽에 생깁니다(새 프로그램 + 옛 목록). 그래서 "끼우자마자 다시 켜기"(ADR-0069)가 틈이 가장 짧습니다

그래서 11번은 "그 짧은 틈에 기호를 넣은 검색만 잠깐 못 찾는 것을 받아들인다"는 확인입니다. 데이터를 미리 다듬는 것은 말씀하신 대로 이미 그렇게 합니다.
