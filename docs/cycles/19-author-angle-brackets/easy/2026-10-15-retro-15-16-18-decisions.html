사이클 15: 사용 기록

1"정확히 찾기" 기록 칸을
칸 목록으로 둘지

설계는 정확히 찾기를 켰는지(참·거짓)만 남기는 칸이었는데, dev가 어느 칸(제목·저자·출판사)을 정확히 찾았는지 목록으로 남기게 바꿨습니다. 정확히 찾기는 여러 칸에 동시에 켤 수 있어서 참·거짓 하나로는 받은 값을 그대로 남길 수 없었습니다.

예: 제목과 저자를 정확히 찾으면 지금은 {title, author}로 남고, 설계대로였다면 "켜짐" 하나만 남았을 것입니다.

dev가 바꾼 칸 목록(text[])을 그대로 확정합니다. [안]

다른 선택: 참·거짓으로 되돌림 → 어느 칸을 정확히 찾았는지 잃고, dev 코드·시험을 다시 고쳐야 함.

2책 페이지에서 거르기를 바꾸면
"책 열기"가 한 번 더 남는 것

책 페이지에서 "전체 / 지금 빌릴 수 있는"을 바꾸면 화면이 책 정보를 다시 받아 "책 열기" 기록이 한 줄 더 생깁니다. dev는 고치지 않고 plan에 판단을 넘겼습니다.

지금은 그대로 두고, 나중에 통계를 만들 때 "같은 사람·같은 책·몇 초 안"은 한 번으로 셉니다. 이 규칙을 data-model.md에 메모합니다. [안]

다른 선택: 거르기를 바꿀 때 책 정보를 다시 받지 않게 웹을 고침 → 작은 웹 일이지만 사이클 17·19 사이에 끼워야 함.

3도서관 응답 수를 셀 때
3분 캐시에서 나온 답은 빼는 규칙

같은 검색을 3분 안에 다시 하면 도서관에 묻지 않고 저장해 둔 답을 씁니다. dev는 이때 도서관 응답으로 세지 않게 했습니다. 도서관에 실제로 요청을 보내지 않았기 때문입니다.

한계: 같은 페이지를 다른 검색과 함께 기다린 경우는 두 번 셀 수 있습니다. 묶음 마감 뒤에 온 성공한 답은 "시간 초과"로 셉니다.

dev 규칙을 확정합니다: 도서관에 실제로 보낸 요청만 셉니다. [안]

다른 선택: 캐시 답도 셈 → 도서관이 얼마나 빨리 답했는지 숫자가 실제보다 좋아 보임.

질문: 캐시에서 가져온 건 또 따로 기록이 되나?
따로 기록되지 않습니다. 캐시 답이면 도서관별 응답 수에도, 서버 로그 줄에도 남지 않고 바로 빠집니다(dev BatchRunner.java 334~338행: if (fromCache) return;). 사용자가 검색한 일 자체(검색 기록)는 캐시와 상관없이 남습니다.

그래서 지금은 "검색은 했는데 도서관에는 묻지 않은 횟수"를 알 수 없습니다. 이 수가 필요하면 도서관별 하루 표에 "캐시 답" 칸을 하나 더하는 작은 고침이 됩니다(기록 표 칸 + 검사 조건 하나). 지금 안대로 두려면 승인, 캐시 답도 따로 세고 싶으면 "기타"에 적어 주세요.

한꺼번에 확정할지

아래 값은 설계가 dev에게 맡긴 범위 안에서 dev가 정했고, 모두 시험을 통과했습니다.

5"내 도서관" 목록을 10곳씩 보이게 바꾼 것을
어떻게 기록할지

사용자 요청으로 내 도서관 화면의 긴 목록 세 곳이 20곳씩에서 10곳씩 + "더 보기"로 바뀌었습니다(사용자: "최대 10개까지 뜨고 그 이후에 더보기같은걸로 되게 해요 지금 너무 많이 떠서 불편해"). "직접 추가한 도서관"은 그대로입니다.

ADR-0058(목록 20곳씩)에 "2026-10-14 사용자 요청으로 10곳씩(세 목록)" 덧붙임만 하고 새 ADR은 쓰지 않습니다. docs/current만 고치고 사이클 07 문서는 그대로 둡니다. [안]

다른 선택: 새 ADR로 ADR-0058을 바꿈 → 결정의 큰 틀(목록 전체 보여 주기)은 그대로라 기록만 늘어남.

6모듈 그림 자동 출력이
옛 빌드 그대로인 것

dev의 모듈 그림 자동 출력(Spring Modulith Documenter)이 사이클 13·14 전 빌드 그대로라 새 모듈(usagelog·sitecontent·picks)이 없습니다. 이번 회고는 코드의 모듈 선언으로 대신 견줬습니다.

다음 인계서 "dev에 알릴 것"에 "main에서 ./gradlew build 뒤 모듈 그림 출력을 새로 만들어 세 모듈 그림 확인"을 한 줄 넣습니다. [안]

다른 선택: 그대로 둠 → 다음 회고도 그림으로 견줄 수 없음.

사이클 16: 공지·약관

7"바뀐 점"에 표를 쓸 수 없는 것

화면이 쓰는 글 그리기 도구(react-markdown)는 표를 그리지 않습니다. 그래서 처리방침 표는 이미 목록으로 바꿨습니다(사용자 결정 2026-10-14). 그런데 명세 R3-3은 약관이 바뀔 때 "바뀌기 전·후 표"를 쓸 수 있다고 적고 있어 지금 코드와 맞지 않습니다.

명세 R3-3과 운영 SQL 안내를 "바뀐 점은 목록으로(표 안 됨)"로 고치고 ADR-0098에 덧붙입니다. 코드는 그대로입니다. [안]

다른 선택: 표 그리기 도구(remark-gfm)를 더함 → 의존성이 하나 늘고 화면 파일이 커지며, 폰에서 표가 옆으로 넘침.

8공지 "판" 기능을 줄일지

공지는 약관처럼 판(고친 이력)을 남기게 만들어졌습니다. 폰 확인 때 사용자가 "어짜피 기능 공유해서 이런거니까 공지 판 있는 설정으로 안 쓰면 되는거아닌가?"라고 물었고, dev는 코드를 그대로 두고 운영 규칙("공지는 보통 고치지 않음. 꼭 고칠 때만 새 판, 아니면 숨기고 새 공지")을 운영 메모에 적었습니다.

코드는 그대로 두고 운영 규칙만 씁니다. 판이 하나뿐이면 화면에 날짜 고르기 칸이 안 보이므로 평소에는 판 기능이 보이지 않습니다. [안]

다른 선택: 공지를 판 하나로 줄임 → 공개 전이라 바꿀 수는 있지만 API·화면·시험을 다시 손보고 ADR-0098을 바꿔야 함.

9화면 파일이 38kB 커진 것과
보안 점검 경고 1건

글 그리기 도구를 넣어 첫 화면에 받는 파일이 170 → 208kB(압축 기준)로 커졌습니다. 또 웹 의존성 점검(npm audit)에 높음 1건(source-map-js)이 있는데, 이 도구를 넣기 전부터 있던 것입니다.

백로그에 두 줄을 넣습니다: "글 화면만 늦게 불러오기(첫 배포 뒤 측정 보고)", "사이클 17 배포 점검표에서 npm audit 한 번". [안]

다른 선택: 지금 사이클 17에 넣음 → 배포 전 일이 늘어남.

질문: 보통 이 정도 크기야?
보통보다 작습니다. 웹 페이지 통계(HTTP Archive Web Almanac 2024 "JavaScript" 장)에서 한 페이지가 받는 자바스크립트의 중앙값은 폰 558KB, PC 613KB입니다. 우리 첫 화면은 208kB(압축 기준)입니다.

출처: almanac.httparchive.org/en/2024/javascript (확인 2026-10-15). 그 장의 숫자가 압축 기준인지는 확인 못 함. 그래서 지금 크기는 급하지 않고, 백로그 "글 화면만 늦게 불러오기"는 첫 배포 뒤 실제 속도를 보고 정하면 됩니다.

10실제 카카오 가입과 안내 기준일 줄은
첫 배포 뒤 확인할지

약관 판 번호로 가입이 기록되는지는 서버 시험으로만 확인했습니다(사용자: "지금은 일단 가짜응답으로만확인"). 서비스 안내의 "가입 조사 기준일" 줄도 개발 DB에 값이 없어 화면으로는 못 봤습니다.

사이클 17 점검표에 두 줄을 넣습니다: "첫 배포 뒤 실제 카카오 가입 1번으로 동의 기록 판 1 확인", "운영 /about에 기준일 줄이 보이는지". 사이클 17에는 공유 파일로 알립니다. [안]

다른 선택: 서버 시험으로 충분하다고 보고 넣지 않음.

사이클 18: 빈 도서관

11실제 확인 때 다른 도서관에도
요청이 나간 것

밑줄 주소 도서관을 실제로 확인할 때, dev가 지역 없이 검색을 불러 다른 도서관 21곳에 1건씩 요청이 나갔습니다. 그중 2건은 "요청하지 않기로" 한 교보 구독형 서버였습니다. 이미 나간 요청은 되돌릴 수 없고, 요청 간격 규칙은 지켜졌습니다.

회고에 기록하고, 다음 인계서 공통 제약에 "실제 확인은 도서관 하나만 부르는 주소(/availability/libraries/{id}/ebooks)로"를 한 줄 넣습니다. [안]

다른 선택: 기록만 함 → 같은 실수가 다시 날 수 있음.

12가져오기 전·후 시험 비교를 건너뛴 것

계획은 미리 돌려 보기(dry run) 전·후 비교였는데, dev는 "빨리 마무리"(사용자 말)를 이유로 진짜 가져오기 기록을 같은 사본의 이전 기록과 비교했습니다. 결과는 현대제철(2624) 말고는 판정이 바뀐 줄이 없었습니다.

이 비교로 충분하다고 보고 확정합니다. [안]

다른 선택: 미리 돌려 보기를 다시 함 → 약 30분과 확인 하나가 더 들지만 새로 얻는 것은 거의 없음.

13현대제철 전자책 241권을
원래 DB와 첫 배포에 넣는 길

사이클 18 가져오기는 복사본 DB에서만 해서, 원래 DB(내 PC)에는 현대제철 241권이 아직 없습니다. 사이클 19가 원래 DB에 책 목록을 다시 가져오면 고친 코드로 241권도 함께 들어옵니다. 첫 배포(사이클 17)는 19 반영 뒤의 책 목록을 씁니다.

따로 가져오기를 하지 않고 사이클 19 다시 가져오기에 맡깁니다. 19 인계서 완료 기준에 "2624 소장 241권 확인"을 넣고, 사이클 17에는 공유 파일로 알립니다. [안]

다른 선택: 지금 원래 DB에서 한 번 더 가져옴 → 약 30분이 더 들고 19 때 또 가져옴.

15ADR 0110~0112에
실제로 만든 방법을 덧붙일지

결정은 바뀌지 않았지만, 만드는 법에서 중요한 사실이 나왔습니다. 자바 기본 기능은 밑줄 주소의 인증서 이름 검사를 거절해서, 검사를 끄지 않으려고 HttpClient의 검사 기능을 썼습니다.

세 ADR의 상태는 그대로 두고 "결과" 절에 실제 이름과 방법을 덧붙입니다(0111: HttpClient 인증서 이름 검사, 0112: 주소의 @를 따로 거부, 0110: "전자책 0권" 검사가 규칙 파일 오류 검사보다 앞). [안]

다른 선택: 덧붙이지 않음 → 나중에 밑줄 주소 코드를 고칠 때 왜 이렇게 했는지 알기 어려움.
