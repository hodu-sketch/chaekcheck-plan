# 기능 명세: 조회 상태 신호와 브라우저 확장 조회

- 범위: [`scope.md`](scope.md) (범위 결정 8개 모두 확정, 2026-10-15). 조사: [`research.md`](research.md)
- 결정 페이지: [`easy/2026-10-15-spec-decisions.html`](easy/2026-10-15-spec-decisions.html)
- 명세 결정 14개 모두 확정 (2026-10-15, 캔버스). 폰 앱은 backlog (사용자: "Google Play 폰 앱 만드는 것을 백로그에 해줘")
- 전반 점검 13개 반영 (2026-10-17, [`easy/2026-10-17-overall-review.html`](easy/2026-10-17-overall-review.html), 모두 사용자 결정): 개발은 세 단계(#1, 단계 표는 `design-delta.md` "개발 단계"), 동시 검색 자리 40(#13), 해석 자리 8(#4), 1분 요약 로그(#5), gzip·1MB 넘음 기록(#6), 이어 부르기 3묶음(#7), 확장 판 번호(#8), DB 오류 회색(#9), 장부 밀어내기(#10), 계획 주소 `/api/v1/lookup-plans` 밑(#11), IP 울타리 (3) 뺌(#12), 확장 결과 2단계부터 나눔(#2), 「밀려요」 1단계(#3). 수용 기준 AC-32~40

## 사용자 이야기

- 책을 찾는 사람은 검색을 누르기 전에 머리말 신호로 **지금 조회가 원활한지** 알고 싶다. 몰릴 때 503 안내만 받는 것보다 먼저 아는 쪽이 낫기 때문이다.
- 책을 찾는 사람은 한 도서관만 줄이 서서 그 줄만 "실패"가 날 때 **왜 그런지** 그 줄에서 알고 싶다.
- (뺌, 화면 흐름 #4·#7: 안내 줄·카드 글 없음) ~~혼잡할 때 도서관 사이트에서 직접 확인하는 길~~ → 대신 확인하지 못한 도서관을 맨 아래에 따로 보고 싶다.
- 크롬을 쓰는 사람은 확장을 설치해 도서관 조회를 **자기 브라우저에서** 하고, 서버 혼잡과 상관없이 검색하고 싶다.
- 운영자는 서버의 조회 자리(동시 검색 20개, 전반 점검 #13으로 40개)와 메모리를 아끼고 싶다 (사용자: "이 서비스는 메모리 점유가 더 문제", 2026-10-15).

## 동작 규칙

- **R1 단계 판정** [확정] (범위 #2): 자리 40개(전반 점검 #13, 처음 20개) 중 쓰는 중이 20개 미만 → 초록, 20개 이상 → 노랑, 40개(모두 참) 또는 **최근 10초 안에 503 `server_busy`를 한 번이라도 냄** → 빨강. 서버가 판정해서 단계 값을 줌(화면은 숫자로 다시 계산하지 않음). 자리 수가 설정(`max-concurrent-searches`)에서 바뀌면 절반·전부도 그에 따름. **덧붙임**: Webshare 길이 한꺼번에 멈춘 동안(업체 오류 407·429·계정 문제, 또는 데이터 90%) 단계는 최소 노랑, 둘째 줄 "지금은 조회가 평소보다 느려요". 빨강 규칙은 그대로, 다시 켜지면 원래 규칙. 사이클 22의 "업체 길 멈춤" 값을 읽기만 함 [확정] (세 관점 검토 #21 승인, 2026-10-16). 화면이 둘째 줄을 고르도록 상태 응답에 `reason=VENDOR_PAUSED`를 줌, 값은 사이클 17/22 나가는 길 코드의 읽기 전용 포트로 읽고 포트가 없으면 `NONE`·기본 규칙 [확정] 검토 #28 승인 2026-10-16. **덧붙임 2**: 나가는 길 설정이 `프록시만`이고 Webshare 길이 모두 멈춘 동안은 서버 모드로 갈 길이 없으므로 빨강, 둘째 줄 "지금은 도서관 조회를 할 수 없어요"(확장 모드는 그대로) [확정] (사용자 승인, 2026-10-16, 세 관점 검토 #24; 인계 `../17-first-deploy/from-cycle-20-proxy-only.md`). 상태 응답 `reason=NO_LANE`(빨강 우선) [확정] 검토 #28 승인 2026-10-16. **덧붙임 3 (DB 오류)**: 최근 **30초** 안에 DB 오류가 있었으면 회색, 말풍선 둘째 줄 「상태를 확인할 수 없어요」(상태 응답 `level=GRAY`, `reason=DB_ERROR` 값 이름 [안]) — 상태 응답이 DB를 보지 않아 DB 장애로 검색이 실패해도 초록이던 문제 [확정] (사용자 승인, 2026-10-17, 전반 점검 #9). 다른 판정보다 앞섬 [안].
- **R2 503 즉시 빨강** [확정] (범위 #3): 검색 중 503을 받으면 다음 묻기를 기다리지 않고 바로 빨강으로 바꾸고, 다음 상태 응답이 오면 그 값으로 돌아감.
- **R3 상태 요청의 한도**: 상태 요청은 도서관을 부르지 않으므로 도서관 호출 IP 한도(30r/m)에 넣지 않음 [확정] (범위 #3). 대신 일반 `/api/` 한도(사이클 17 `chaekcheck_api` 5r/s)에는 들어감. 묻기 10초 간격이면 1명당 0.1r/s.
- **R4 줄이 선 도서관** [확정] (기준 값 사용자 승인, 2026-10-15, 명세 결정 #5): 어떤 도서관 호스트에 (가) 지금 자리를 기다리는 요청이 1건 이상 있거나 (나) **최근 60초** 안에 그 호스트에서 자리 대기 시간 초과(`InMemoryHostThrottle` 포기)가 1건 이상이면 "줄이 섬". 호스트 하나에 도서관이 여럿(통합 포털)이면 그 도서관 모두. **나가는 길(조회 서버 N대·프록시·직접)마다 호스트 자리(동시 1건·1초)가 따로 있으므로 (가)(나)는 길마다 따로 세고**, 길이 N개면 그 호스트의 자리도 N개로 본다(어느 한 길의 자리를 기다리는 요청이 있으면 그 길에서 줄이 섬). 어느 길에서든 줄이 섰으면 표시 [확정] (범위 #8; 사용자: "계산할 때 조회 서버 여러대이면 그 여러대만큼으로 분류되는 거 생각해서 하고", 2026-10-15, 명세 결정 #5). **그 호스트에서 막힌(멈춘) 길은 자리로 세지 않고 줄이 선 판정에서도 뺀다**(ADR-0094·0095: 막힌 IP는 그 사이트에서만 멈춤) [확정] (사용자: "조회 서버마다 접근이 안 되는 곳들 따로 관리할건데 그곳은 또 빼야 해", 2026-10-15). 모든 길이 막힌 호스트는 줄이 선 것이 아니라 ADR-0094의 "확인 불가". **(가)의 기다림은 시작한 지 10초(마감 8초 + 2초) 안의 것만 셈** — 서버 안에서 기다림 끝을 놓쳐도 「밀려요」가 최대 10초 뒤 사라짐(스스로 낫기), 1단계 [확정] (사용자: "지금 가자", 2026-10-17, 전반 점검 #3).
- **R5 상태 묻기 실패** [확정] (사용자 승인, 2026-10-15, 명세 결정 #7): 상태 응답을 못 받으면(네트워크 오류, 5xx) 마지막 값을 **30초**까지 유지하고, 그 뒤에는 점을 회색·글 「상태 모름」으로 바꿈. 다시 받으면 그 값으로. 30초는 **마지막으로 성공한 응답 시각**부터 셈 — 탭을 오래 숨겼다 돌아왔을 때 이미 30초가 지났으면 바로 회색(검토 반영 2026-10-16).
- **R6 확장 모드 결정**: 화면이 뜰 때 한 번 확장에 인사하고(첫 검색은 답을 최대 500ms 기다림, 결과는 앱 전체에 보관), 답(확장 판 번호)이 오면 그 방문 동안 확장 모드. **단, 답의 약속 판 번호가 화면이 요구하는 최소 판보다 낮으면 확장 모드로 가지 않고 서버 모드 + 한 줄 안내 「확장을 새로 깔아 주세요」** [확정] (사용자 승인, 2026-10-17, 전반 점검 #8; 개발자 모드 확장은 자동 갱신이 없어 화면만 새로 배포되면 모든 줄이 조용히 「확인하지 못한 도서관」이 될 수 있음). 확장 port가 끊기면(사용자가 끔·업데이트·service worker 잠듦) 인사를 최대 3번(바로·1초·2초 뒤) 다시 하고, 답이 오면 확장이 남은 도서관을 다시 요청, 셋 다 답이 없으면 남은 도서관은 「확인하지 못한 도서관」, 파란 불을 지우고 다음 검색부터 서버 모드(상태 묻기 바로 1회). 서버는 대신 부르지 않음 [확정] (명세 결정 #9; 사용자: "한 번만 인사하고 포기하지 말고 몇 번 더 인사해서 살아나면 확장이 남은 도서관을 다시 요청하게 … 이렇게 해", 2026-10-16, 세 관점 검토 #4).
- **R7 확장 모드 조회 흐름** [확정] (범위 #5, ADR-0015 모양): 화면 → 서버 "계획" 요청(검색어·범위) → 서버가 묶음 1의 주소 목록을 줌(자리를 잡지 않음) → 화면이 확장에 주소 목록을 넘김 → 확장이 호스트마다 동시 1건·1초 간격으로 GET → 받은 (상태 코드, 바이트)를 화면이 서버 "해석" 요청에 올림 → 서버가 adapter로 해석·판정·캐시 → 줄 응답 → 다음 묶음. 서버 모드의 이벤트 순서(`targets` → 결과 → `batch-done` → `row-verdict` → `done`)와 같은 뜻의 결과를 돌려줌(형태는 설계에서).
- **R8 확장 모드의 한도**: 묶음 마감 8초·후보 50·줄 상한은 서버 모드와 같음(줄 상한은 R15대로 10). 확장은 호스트마다 동시 1건·최소 1초 [확정] (범위 #7). 응답 머리까지 10초, 본문은 묶음 마감까지(브라우저 `fetch`는 연결·읽기를 따로 못 잼; 설계 결정 #8이 명세 결정 #10의 5초·5초를 바꿈). 확장이 받아오지 못한 도서관(시간 초과·네트워크 오류·상태 코드 4xx/5xx)은 서버가 다시 부르지 않고 그 줄을 "실패"로 [확정] (사용자 승인, 2026-10-15, 명세 결정 #10). **예외**: 처음부터 정해 둔 서버 대행 목록(확장이 못 여는 도서관, 설정)에 있는 도서관만 서버가 불러 줌(그때만 서버 자리 1개) [확정] (세 관점 검토 #16 승인 2026-10-16; 3단계, 전반 점검 #1 — 2단계에서 그 도서관은 「확인하지 못한 도서관」); 그 자리가 모두 찼을 때 [확정] (검토 #29 승인 2026-10-16: 그 도서관만 「확인하지 못한 도서관」, 나머지는 확장으로 계속).
- **R9 해석 요청의 보호** [확정] (사용자 승인, 2026-10-15, 명세 결정 #11): "해석" 요청은 같은 방문의 "계획" 응답에 들어 있던 **일회성 계획 번호**와 짝이 맞아야 받음(남이 임의의 바이트를 올려 캐시를 더럽히지 못하게). 계획 번호는 10분 뒤 버림. 해석 요청은 도서관을 부르지 않으므로 도서관 호출 한도 밖, 일반 `/api/` 한도 안. 계획·해석·닫기 주소는 모두 `/api/v1/lookup-plans` 밑 [확정] (전반 점검 #11, 2026-10-17). **2단계**(확장 최소판)에서는 계획에 만든 공인 IP(/64)를 적고 해석·닫기는 같은 IP에서만 받음(IP가 바뀌면 화면이 사용자 조작 없이 남은 도서관만 다시 계획) [확정] (전반 점검 #1). 아래 브라우저 번호·장부·쿠키·잠금·울타리는 **3단계**(웹스토어에 올릴 때 또는 거절 기록에 남용이 보일 때) [확정] (전반 점검 #1). **사람(브라우저)마다 세기** [확정] (세 관점 검토 #22 승인 2026-10-16): 계획·잠금은 **브라우저 번호**마다 셈. 번호는 **서버가 줌** [확정] (검토 #27, 사용자: "이걸로 해줘", 2026-10-16) — 서버가 무작위 번호를 만들어 메모리의 **브라우저 번호 장부**(번호 → 받은 공인 IP·받은 시각·열린 계획 수·계획 무게·최근 실패)에 적고 [확정] (검토 #32, 사용자: "브라우저 번호랑 아이피랑 합쳐서 서버에서 관리하면 되겠다", 2026-10-16), **자바스크립트가 읽지 못하는 쿠키**(HttpOnly·Secure·SameSite=Strict, 경로 `/api/v1/lookup-plans` 하나(전반 점검 #11), 1일)로 줌 [확정] (검토 #33, 사용자: "브라우저 번호 이거 xss로 뭐 오염되지 않도록 조심해야 해", 2026-10-16). 화면은 번호를 만들지도 읽지도 않음. 서명은 쓰지 않음: 장부에 없는 번호는 거절. 요청마다 "장부에 있나 + 받은 IP = 지금 IP"를 보고, IP가 바뀌었으면(폰 와이파이↔LTE) 화면이 사용자 조작 없이 새 번호를 받아 남은 도서관만 다시 계획(잠금에 세지 않음). 서버를 다시 켜면 장부가 비고 화면은 자동으로 새 번호를 받음. 장부 상한 5만 줄·1일(설정), **차면 가장 오래 안 쓴 줄을 밀어냄** — 밀려난 사람은 다음 요청에서 400을 받고 화면이 조용히 새 번호로 남은 도서관만 다시 계획 [확정] (사용자: "가. 오래된 줄 밀어내기 … 이걸로 가자", 2026-10-17, 전반 점검 #10). 계획은 만든 번호로만 해석·닫기·지우기. 열린 계획 20·10분 잠금은 번호별. **공인 IP 울타리 둘** [확정] (검토 #31, 2026-10-16; 셋째 "잠긴 번호 5개 → IP 10분"은 전반 점검 #12로 뺌, 2026-10-17): ① 그 IP에 준 번호들의 계획 무게 합이 보관함의 20%(주소 5,000)를 넘음 ② 한 IP에 새 번호가 1분에 30개를 넘음. 둘 다 그 IP의 새 계획 요청만 거절하고 화면은 「잠시 후 다시」(서버 모드로 넘기지 않음), 다음 검색은 다시 확장 모드로 시도. 보관함 전체가 찬 경우(검토 #8)만 그 검색 한 번 서버 모드. 숫자의 근거는 `../../settings-index.md` 6절.

- **R12 빨강일 때의 결과와 확인하지 못한 줄** (처음 이름 "빨강 안내 줄"): 빨강이어도 **카드에 더하는 것 없음**, 조회가 되면 결과를 그대로 보임(지금도 503은 새 검색만 막고 받은 결과는 남김) [확정] (사용자: "똑같은데 도서관에서 보기 추가하는 의미가 없지 않아? 해당 도서관 대출 결과가 없으면 없다고 보여주고 빨가이어도 조회가 되면 조회 결과를 보여줘야지 대출 결과를 못 찾을 때 어느 순서에 둘 건지를 고려해야지", 2026-10-15, 화면 흐름 #7). 안내 줄도 없음 [확정] (화면 흐름 #4·#5). 대신 **대출 정보를 확인하지 못한 줄**(조회 실패·시간 초과·줄 밀림·확장이 못 받아옴)의 자리를 정함 [확정] (사용자 승인, 2026-10-15, 화면 흐름 결정 #7): 지금은 `UNKNOWN`으로 "예약하고 기다려요" 묶음 맨 아래에 섞이고 "지금 빌릴 수 있는 책만" 거름에서는 숨겨짐(dev `sortBatch.ts`·`holdingPlan.ts` 2026-10-15 확인) → **결과 맨 아래 따로 묶음 「확인하지 못한 도서관」**(계획 순서, 거름 둘 모두에서 보임), 줄 글은 지금 「확인 실패」 → 「대출 정보를 확인하지 못했어요」 [확정] (사용자 승인, 2026-10-15, 화면 흐름 결정 #7). (앞선 안 "카드에 「도서관에서 보기 →」 글"은 사용자 지적으로 뺌: 카드가 같은데 글만 더하는 것은 뜻이 없음)
- **R14 머리말은 모든 화면에서 같음** [확정] (사용자: "왜 이용약관이랑 개인정보처리방침은 왜 머릿말이 달라? 그것들도 같아야지", 2026-10-15, 화면 흐름 #4): 약관(`/terms`)·처리방침(`/privacy`)에서도 메뉴·신호·「로그인/로그아웃」을 보임. 사이클 05(2026-10-04 "S8·S9에는 로그인·로그아웃 버튼을 두지 않음")·10·14의 예외를 없앰(dev `AppLayout.tsx`의 `legal` 분기 제거). - **R15 검색 결과 수 10** [확정] (사용자: "별개로 지금 도서 검색 정보 바로 검색이든 도서책 기준 검색이든 검색 결과 수를 줄여야겠다 10개로", 세 관점 검토 #23 승인 2026-10-16): 바로 검색은 결과 줄이 10줄 넘게 모이면 새 도서관 요청을 멈춤(`batch.row-limit` 20 → 10, 서버·확장 모드 같음). 책 기준 검색(`GET /api/v1/books`)은 화면이 `pageSize=10`을 보내고 API 기본값도 10(최대 20 그대로). 「다음 쪽」·「더 보기」는 지금과 같음. 효과(어림): 검색 한 번이 쓰는 도서관 요청이 대략 반 → 같은 서버로 받는 검색 약 2배

- **R16 서버 메모리와 운영 기록** (전반 점검 #4·#5·#6, 사용자 승인 2026-10-17, 1단계): ① 도서관 페이지 해석은 서버 모드·확장 모드가 함께 쓰는 해석 자리 **8**(설정) 안에서만, 자리가 없으면 최대 2초 기다린 뒤 그 도서관만 실패(「확인하지 못한 도서관」) [확정] ② 앱이 **1분마다** 운영 요약 로그 한 줄(검색 자리 사용, 503 수, 힙, 멈춘 길, 1MB 넘음 수, DB 오류 수, 확장/서버 요청 수 등) [확정]; 경보는 사이클 17(`../17-first-deploy/from-cycle-20-observability.md`) ③ 서버 모드 도서관 요청은 압축(gzip)을 받고, 풀었을 때도 1MB 상한. 1MB를 넘어 실패한 도서관은 서버 로그 한 줄(도서관 번호·주소·받은 크기·시각)과 사용 기록에 남기고 요약 로그에 셈 [확정] (사용자: "1MB 넘는 거 잘 기록하고") / 사용 기록에 따로 셀 칸 [안]

- 결과 없음: 줄이 선 도서관 목록이 비면 결과 줄에 표시 없음
- 외부 API 오류·지연: 도서관 쪽 오류는 지금처럼 그 줄 "실패". 상태 요청 실패는 R5. 확장이 받아오지 못하면 R8
- 입력 오류: 해석 요청의 계획 번호가 없거나·지났거나·지워졌거나, 쪽 번호가 없거나 이미 받았거나, 계획을 만든 브라우저 번호와 다르거나 Origin이 다르면 400 `invalid_plan` [확정] (명세 결정 #14, 번호는 검토 #22·#32) → 화면은 오류를 띄우지 않고 남은 줄을 「확인하지 못한 도서관」으로 둠. 브라우저 번호 쿠키가 없거나 장부에 없으면 400 `invalid_client_key`, 번호를 받은 IP(2단계는 계획을 만든 IP)와 지금 IP가 다르면 400 `client_ip_changed`(두 코드 이름 [안]) → 화면은 오류 없이 남은 도서관만 새 계획으로 다시 요청(새 번호를 받음) [확정] (검토 #32). 계획 요청이 공인 IP 울타리에 걸리면 429 → 「잠시 후 다시」 [확정] (검토 #31). **도서관 페이지가 해석되지 않거나(사이트 화면 바뀜·차단 안내) 상태 코드가 200이 아니면 400이 아니라 그 도서관만 실패**(200 `library-failed`) — 검토 반영 2026-10-16. 바이트가 상한을 넘으면 413, 로그인 기능이 켜졌는데 CSRF 머리가 없으면 403 `csrf_invalid`
- 확장은 있는데 책첵 주소가 아닌 페이지가 말을 걸면 확장은 무시(`externally_connectable`로 브라우저가 먼저 막음)

## 수용 기준

- AC-1: 검색 첫 화면을 열면 11초 안에(1초 메모 + 10초 묻기) 머리말 「로그인」 왼쪽에 초록 점과 「조회 원활」이 보인다. 약관·처리방침 화면에서도 같은 머리말(사이클 21 메뉴 「추천도서」·「마이페이지」·점·「로그인」)이 보인다(R14).
- AC-2: 동시 검색을 20개 띄우면 다음 상태 응답에서 노랑, 40개를 띄우면 빨강으로(자리 40, 전반 점검 #13) 바뀌고, 모두 끝나면 11초 안에(1초 메모 + 10초 묻기) 초록으로 돌아온다 (상태 API 값과 화면이 같음).
- AC-3: 검색 중 503 `server_busy`를 받으면 그 즉시 신호가 빨강이 되고, 지금 503 안내("지금 찾는 사람이 많아요…")는 그대로 나온다.
- AC-4: 빨강일 때 검색하면 받은 결과 카드가 평소와 같은 모양으로 보이고(더해지는 글 없음), 확인하지 못한 줄은 결과 맨 아래 「확인하지 못한 도서관」 묶음에 「대출 정보를 확인하지 못했어요」로 보이며 "지금 빌릴 수 있는 책만"에서도 보인다 [확정] (사용자 승인, 2026-10-15, 화면 흐름 결정 #7).
- AC-5: 한 도서관 호스트에 요청이 겹쳐 자리 대기가 생기면, 다음 상태 응답의 줄이 선 도서관 목록에 그 도서관이 들어가고, 그 도서관의 **조회 중인 줄**에 「지금 이 도서관 조회가 밀려요」가 보인다. 이미 결과를 받은 줄에는 없다. 그 줄이 실패로 끝나면 「확인하지 못한 도서관」 안에서 글이 새 검색 전까지 남는다(세 관점 검토 #5).
- AC-6: 탭을 다른 탭 뒤로 보내면 상태 요청이 멈추고(네트워크 탭), 다시 앞으로 오면 즉시 한 번 요청한다.
- AC-7: 상태 API를 1분에 60번 불러도 429가 나지 않는다(도서관 호출 한도 밖). 응답은 도서관 요청을 하나도 만들지 않는다(서버 로그).
- AC-8: 폰 폭(375px)에서는 점만 보이고, 점을 누르면 설명 한 줄이 뜨며 가로 스크롤이 생기지 않는다.
- AC-9: (서버 대행 목록이 비어 있을 때) 확장을 개발자 모드로 설치한 크롬에서 책첵을 열면 머리말에 파란 점과 「내 브라우저에서 조회 중」이 보이고 상태 요청이 나가지 않으며, 검색하면 도서관 요청이 확장(service worker)의 네트워크 탭에 찍히며 서버 로그에는 그 검색의 도서관 요청이 없다.
- AC-10: 확장 모드 검색의 결과 줄·판정이 같은 검색어의 서버 모드 결과와 같다(같은 책, 같은 대출 가능 표시). 그 직후 확장 없는 브라우저에서 같은 검색을 하면 3분 캐시에서 답한다(`cached_count` 증가).
- AC-10a: 서버 캐시에 값이 있어도 확장 모드는 모든 도서관을 확장으로 부르고, 서버 출처 캐시 값은 덮지 않는다(design-delta 결정 #9).
- AC-11: 확장 모드에서 한 호스트에 쪽 3개를 보낼 때 요청 사이가 1초 이상이고 동시에 2개가 나가지 않는다(확장 네트워크 탭 시각). **탭 두 개에서 같은 도서관을 동시에 검색해도** 같다(전역 호스트 큐).
- AC-12: (서버 대행 목록이 비어 있을 때) 서버 동시 검색 자리를 40개 모두 채운 상태(빨강)에서도 확장 모드 검색은 503 없이 결과를 받는다.
- AC-13: 계획 번호 없이 또는 틀린 번호로, 또는 계획을 만든 것과 다른 브라우저 번호로 해석 요청을 보내면 400 `invalid_plan`, 번호 쿠키 없이 또는 서버가 준 적 없는 번호로 보내면 400 `invalid_client_key`이고 둘 다 캐시에 아무것도 들어가지 않는다(검토 #22·#32).
- AC-14: 확장이 없는 크롬·폰 브라우저에서는 이 사이클 전과 같은 흐름으로 검색된다(확장 감지 실패가 화면에 오류로 보이지 않음).
- AC-15: 확장 모드 검색의 도서관 응답 수가 `library_response_daily`에 `source=extension`으로 쌓인다.
- AC-16: "지금 빌릴 수 있는 책만"을 켠 채 확인하지 못한 줄만 있는 묶음이면, 「확인하지 못한 도서관」 묶음이 보이고 빈 결과 문구에 "N곳은 확인하지 못했어요"가 붙는다(검토 반영).
- AC-17: 확장 모드에서 도서관이 바뀐 화면(해석 안 되는 페이지)을 주면 그 도서관만 「확인하지 못한 도서관」에 들어가고, 검색 전체가 오류가 되지 않으며 그 브라우저 번호·IP가 잠기지 않는다(검토 반영).
- AC-18: 다른 도서관 주소로 가는 `detailUrl`이 든 페이지를 올리면 그 링크는 저장·표시되지 않고 서버가 그 주소를 부르지 않는다(서버 모드 캐시 경로 포함, 검토 반영).
- AC-19: 로그인 기능을 켠 운영 설정에서 확장 모드 검색이 403 없이 된다(CSRF 머리, 검토 반영).
- AC-20: 화면 낭독기로 머리말을 읽으면 점에 "조회 상태: 원활"처럼 읽히고, 단계가 바뀔 때만 한 번 알린다(검토 반영).

- AC-21: 결과가 많은 책으로 바로 검색하면, 결과 줄이 10줄에 닿은 뒤 새로 시작한 도서관 요청이 없다 — 서버 모드는 서버 로그의 도서관 요청 수, 확장 모드는 확장 네트워크 탭의 요청 수로 확인(이미 나간 요청의 줄은 더해질 수 있음). 책 기준 검색 첫 쪽은 책 10권이다(`GET /api/v1/books` 응답의 책 수).
- AC-22: 해석 자리 8개(서버·확장 함께, 전반 점검 #4)를 모두 채운 상태에서 확장 모드 올리기가 오면 2초 뒤 503이 나고, 그 도서관만 「확인하지 못한 도서관」에 들어가며 나머지 도서관 결과는 그대로 보인다(검토 #7).
- AC-23: 계획 보관함이 가득 찬 상태에서 확장 모드 검색을 하면 계획 요청이 503이고, 그 검색 한 번은 서버 모드(SSE 스트림)로 결과를 받으며 다른 사람의 계획은 지워지지 않는다(검토 #8).
- AC-24: 서버 모드 검색 도중 화면을 떠나면, 그 뒤 그 묶음에서 새로 시작한 도서관 요청이 서버 로그에 없다(이미 나간 요청은 끝까지 받아 캐시에 들어감, 검토 #14).
- AC-25: 서버 대행 목록에 도서관이 있으면 확장 모드 검색에서 그 도서관은 확장 네트워크 탭에 없고 서버 로그에 있으며, 사용 기록에 `source=server_for_extension`으로 쌓인다(검토 #16).
- AC-26: (3단계) 같은 공인 IP 뒤의 브라우저 두 개(서로 다른 브라우저 번호)는 각자 열린 계획 20개를 가지며, 한 탭이 잠겨도(1분 실패 30번) 다른 탭의 계획 요청·올리기는 막히지 않는다(검토 #22).
- AC-27: 업체 길이 멈춘 상태로 만들면 머리말이 최소 노랑이고 팝오버 둘째 줄이 「지금은 조회가 평소보다 느려요」, 나가는 길 설정 `프록시만`에서 업체 길이 모두 멈추면 빨강과 「지금은 도서관 조회를 할 수 없어요」가 보인다(검토 #21·#24, `reason`은 검토 #28).

- AC-28: 책 기준 검색 첫 쪽(책 10권)을 열면, 보이는 10권의 소장 도서관 상태가 줄 수와 상관없이 채워진다(묶음이 여러 번이면 화면이 이어서 요청 — 서버 로그의 holding 묶음 수와 요청 수로 확인). 자동 이어 부르기는 AC-36의 3묶음까지.
- AC-29: (3단계) 한 공인 IP에서 (가) 그 IP 번호들의 열린 계획 무게 합이 주소 5,000을 넘거나 (나) 1분에 새 번호를 31개째 받으려 하면, 그 IP의 새 계획 요청은 429이고 화면에 「잠시 후 다시」 안내가 보이며 그 검색은 서버 모드로 가지 않는다(서버 로그에 그 검색의 도서관 요청 없음). 다른 공인 IP의 확장 모드 검색은 그대로 된다. 그 뒤 같은 브라우저의 다음 검색은 다시 확장 모드로 시도한다(검토 #31). 잠긴 번호가 5개가 되어도 IP째 거절되지 않는다(전반 점검 #12). 보관함 전체가 찬 경우는 AC-23대로 서버 모드.
- AC-30: 확장 모드 검색 도중 브라우저의 공인 IP가 바뀌면(2단계는 계획을 만든 IP 기준, 3단계는 번호를 받은 IP 기준)(폰 와이파이↔LTE, 시험은 VPN 켜기) 올리기가 400 `client_ip_changed`를 받고, 화면은 오류 없이 새 번호를 받아 남은 도서관만 다시 계획해 결과를 채운다. 이 400은 번호 잠금에 세지 않는다. 서버를 다시 켠 뒤 검색해도 화면은 자동으로 새 번호를 받아 확장 모드로 검색한다(검토 #32).
- AC-31: (3단계) 브라우저 개발자 도구에서 브라우저 번호 쿠키가 `HttpOnly`·`Secure`·`SameSite=Strict`이고 경로가 `/api/v1/lookup-plans` 하나이며, 화면 자바스크립트(`document.cookie`)에서 보이지 않고, 요청에 `X-Lookup-Client` 같은 번호 머리글이 없다. 다른 사이트에서 우리 해석 주소로 보낸 요청과 서버 모드 「더 보기」 GET에는 번호 쿠키가 붙지 않는다(검토 #33, 전반 점검 #11).

- AC-32: (1단계, 전반 점검 #3) dev 단위 시험 둘이 통과한다: 기다리는 중 오류를 던져도 그 도서관의 기다림 수가 0으로 돌아오고, 시작한 지 10초가 지난 기다림은 줄 선 도서관 목록에서 빠진다. 화면에서는 「지금 이 도서관 조회가 밀려요」가 기다림이 끝나거나 10초가 지나면 다음 상태 응답에서 사라진다.
- AC-33: (1단계, 전반 점검 #4) 서버 모드 검색과 확장 모드 올리기가 같은 해석 자리 8개를 함께 쓴다 — 동시에 해석 중인 페이지가 8개를 넘지 않고(서버 로그·지표), 서버 모드에서 자리를 2초 안에 못 얻은 도서관은 그 도서관만 「확인하지 못한 도서관」이 된다.
- AC-34: (1단계, 전반 점검 #6) 서버 모드 도서관 요청에 `Accept-Encoding: gzip`이 붙는다. 풀었을 때 1MB가 넘는 응답(시험용 큰 페이지 또는 압축 폭탄)은 그 도서관만 실패하고, 서버 로그에 도서관 번호·주소·받은 크기·시각 한 줄, 사용 기록에 실패로 하루 수가 쌓이며, 1분 요약 로그의 "1MB 넘음" 수가 1 오른다.
- AC-35: (2단계, 전반 점검 #8) 약속 판 번호가 최소 판보다 낮은 확장을 깐 크롬에서는 파란 불이 아니라 서버 모드 상태 불이 보이고, 「확장을 새로 깔아 주세요」 안내가 한 번 보이며, 검색은 서버 모드로 결과를 받는다.
- AC-36: (1단계, 전반 점검 #7) 소장 도서관이 아주 많은 책들로 책 기준 검색을 하면, 화면이 자동으로 부르는 대출 상태 묶음은 첫 묶음 포함 3번까지이고(서버 로그·네트워크 탭), 그 뒤 남은 줄에는 「더 보기」가 보이며 누르면 이어서 부른다.
- AC-37: (1단계, 전반 점검 #9) DB를 멈추고 검색(또는 책 찾기)을 해 DB 오류를 낸 뒤, 다음 상태 응답에서 머리말이 회색이고 말풍선 둘째 줄이 「상태를 확인할 수 없어요」이다. DB를 다시 켜고 30초가 지나 DB 오류가 없으면 원래 단계로 돌아온다.
- AC-38: (2단계, 전반 점검 #11) 확장 모드의 계획·올리기·닫기와 「더 보기」 계획 요청 주소가 모두 `/api/v1/lookup-plans` 밑이고, 확장 모드 「더 보기」를 1분에 31번 넘게 눌러도 도서관 호출 한도(1분 30) 때문에 429가 나지 않는다(계획 구역 한도만 받음).
- AC-39: (3단계, 전반 점검 #10) 장부 상한을 작게(예: 2줄) 설정하고 브라우저 셋으로 검색하면 503이 나지 않고, 가장 오래 안 쓴 브라우저의 다음 올리기가 400 `invalid_client_key`를 받은 뒤 화면이 오류 없이 새 번호로 남은 도서관을 다시 계획해 결과를 채운다.
- AC-40: (1단계, 전반 점검 #5) 앱을 켜 두면 서비스 로그에 1분마다 운영 요약 줄이 하나씩 찍히고, 검색 자리 사용·503 수·힙·멈춘 길·1MB 넘음 수가 들어 있다.
