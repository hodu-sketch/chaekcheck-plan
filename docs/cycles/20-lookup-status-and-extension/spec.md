# 기능 명세: 조회 상태 신호와 브라우저 확장 조회

- 범위: [`scope.md`](scope.md) (범위 결정 8개 모두 확정, 2026-10-15). 조사: [`research.md`](research.md)
- 결정 페이지: [`easy/2026-10-15-spec-decisions.html`](easy/2026-10-15-spec-decisions.html)
- 명세 결정 14개 모두 확정 (2026-10-15, 캔버스). 폰 앱은 backlog (사용자: "Google Play 폰 앱 만드는 것을 백로그에 해줘")

## 사용자 이야기

- 책을 찾는 사람은 검색을 누르기 전에 머리말 신호로 **지금 조회가 원활한지** 알고 싶다. 몰릴 때 503 안내만 받는 것보다 먼저 아는 쪽이 낫기 때문이다.
- 책을 찾는 사람은 한 도서관만 줄이 서서 그 줄만 "실패"가 날 때 **왜 그런지** 그 줄에서 알고 싶다.
- 혼잡할 때 책을 찾는 사람은 설치 없이 **도서관 사이트에서 직접** 확인하는 길을 바로 보고 싶다.
- 크롬을 쓰는 사람은 확장을 설치해 도서관 조회를 **자기 브라우저에서** 하고, 서버 혼잡과 상관없이 검색하고 싶다.
- 운영자는 서버의 조회 자리(동시 검색 20개)와 메모리를 아끼고 싶다 (사용자: "이 서비스는 메모리 점유가 더 문제", 2026-10-15).

## 동작 규칙

- **R1 단계 판정** [확정] (범위 #2): 자리 20개 중 쓰는 중이 10개 미만 → 초록, 10개 이상 → 노랑, 20개(모두 참) 또는 **최근 10초 안에 503 `server_busy`를 한 번이라도 냄** → 빨강. 서버가 판정해서 단계 값을 줌(화면은 숫자로 다시 계산하지 않음). 자리 수가 설정(`max-concurrent-searches`)에서 바뀌면 절반·전부도 그에 따름.
- **R2 503 즉시 빨강** [확정] (범위 #3): 검색 중 503을 받으면 다음 묻기를 기다리지 않고 바로 빨강으로 바꾸고, 다음 상태 응답이 오면 그 값으로 돌아감.
- **R3 상태 요청의 한도**: 상태 요청은 도서관을 부르지 않으므로 도서관 호출 IP 한도(30r/m)에 넣지 않음 [확정] (범위 #3). 대신 일반 `/api/` 한도(사이클 17 `chaekcheck_api` 5r/s)에는 들어감. 묻기 10초 간격이면 1명당 0.1r/s.
- **R4 줄이 선 도서관** [확정] (기준 값 사용자 승인, 2026-10-15, 명세 결정 #5): 어떤 도서관 호스트에 (가) 지금 자리를 기다리는 요청이 1건 이상 있거나 (나) **최근 60초** 안에 그 호스트에서 자리 대기 시간 초과(`InMemoryHostThrottle` 포기)가 1건 이상이면 "줄이 섬". 호스트 하나에 도서관이 여럿(통합 포털)이면 그 도서관 모두. **나가는 길(조회 서버 N대·프록시·직접)마다 호스트 자리(동시 1건·1초)가 따로 있으므로 (가)(나)는 길마다 따로 세고**, 길이 N개면 그 호스트의 자리도 N개로 본다(어느 한 길의 자리를 기다리는 요청이 있으면 그 길에서 줄이 섬). 어느 길에서든 줄이 섰으면 표시 [확정] (범위 #8; 사용자: "계산할 때 조회 서버 여러대이면 그 여러대만큼으로 분류되는 거 생각해서 하고", 2026-10-15, 명세 결정 #5). **그 호스트에서 막힌(멈춘) 길은 자리로 세지 않고 줄이 선 판정에서도 뺀다**(ADR-0094·0095: 막힌 IP는 그 사이트에서만 멈춤) [확정] (사용자: "조회 서버마다 접근이 안 되는 곳들 따로 관리할건데 그곳은 또 빼야 해", 2026-10-15). 모든 길이 막힌 호스트는 줄이 선 것이 아니라 ADR-0094의 "확인 불가".
- **R5 상태 묻기 실패** [확정] (사용자 승인, 2026-10-15, 명세 결정 #7): 상태 응답을 못 받으면(네트워크 오류, 5xx) 마지막 값을 **30초**까지 유지하고, 그 뒤에는 점을 회색·글 「상태 모름」으로 바꿈. 다시 받으면 그 값으로.
- **R6 확장 모드 결정**: 화면이 뜰 때 한 번 확장에 인사하고, 답(확장 판 번호)이 오면 그 방문 동안 확장 모드. 중간에 확장이 꺼지면 다음 검색의 첫 주소 요청이 실패 → 그 검색부터 서버 모드로 되돌리고 파란 불을 지움 [확정] (사용자 승인, 2026-10-15, 명세 결정 #9).
- **R7 확장 모드 조회 흐름** [확정] (범위 #5, ADR-0015 모양): 화면 → 서버 "계획" 요청(검색어·범위) → 서버가 묶음 1의 주소 목록을 줌(자리를 잡지 않음) → 화면이 확장에 주소 목록을 넘김 → 확장이 호스트마다 동시 1건·1초 간격으로 GET → 받은 (상태 코드, 바이트)를 화면이 서버 "해석" 요청에 올림 → 서버가 adapter로 해석·판정·캐시 → 줄 응답 → 다음 묶음. 서버 모드의 이벤트 순서(`targets` → 결과 → `batch-done` → `row-verdict` → `done`)와 같은 뜻의 결과를 돌려줌(형태는 설계에서).
- **R8 확장 모드의 한도**: 묶음 마감 8초·후보 50·줄 상한 20은 서버 모드와 같음. 확장은 호스트마다 동시 1건·최소 1초 [확정] (범위 #7). 연결·읽기 시간 제한은 서버와 같은 5초·5초. 확장이 받아오지 못한 도서관(시간 초과·네트워크 오류·상태 코드 4xx/5xx)은 서버가 다시 부르지 않고 그 줄을 "실패"로 [확정] (사용자 승인, 2026-10-15, 명세 결정 #10).
- **R9 해석 요청의 보호** [확정] (사용자 승인, 2026-10-15, 명세 결정 #11): "해석" 요청은 같은 방문의 "계획" 응답에 들어 있던 **일회성 계획 번호**와 짝이 맞아야 받음(남이 임의의 바이트를 올려 캐시를 더럽히지 못하게). 계획 번호는 10분 뒤 버림. 해석 요청은 도서관을 부르지 않으므로 도서관 호출 한도 밖, 일반 `/api/` 한도 안.
- **R10 확장 모드와 신호** [확정] (사용자 제안, 2026-10-15, 명세 결정 #12): 확장 모드에서는 **서버 상태를 묻지 않고** 머리말 신호 자리에 파란 점 + 「내 브라우저에서 조회 중」(글 [확정], 명세 결정 #4)만 보임. 빨강 안내 줄(R12)과 링크 앞세우기도 없음. 확장 모드 검색은 서버 자리를 쓰지 않으므로 서버 혼잡과 무관 [확정] (범위 #5). (처음 안 "서버 상태를 그대로 보이고 안내 줄만 숨김"은 사용자 제안으로 바뀜)
- **R11 사용 기록**: 확장 모드의 도서관 응답은 `usagelog.library_response_daily`에 `source=extension`으로 따로 셈 [확정] (사용자 승인, 2026-10-15, 명세 결정 #13) (지금 `direct_search`·`holding_fill` CHECK에 값 추가). 성공·실패·시간은 확장이 보낸 값으로.
- **R12 빨강 안내 줄** [확정] (방법 비교 #4, 문구 명세 #3): 빨강일 때 결과 판 위에 한 줄 안내. **바로잡음 (2026-10-15, flow 작성 중 dev 확인)**: 지금 결과 카드에는 따로 「도서관에서 보기」 버튼이 없고 **카드 전체가 도서관 페이지 링크**(dev `ResultRow.tsx` 2026-10-05 사용자 요청, `detailUrl` 없으면 `librarySearchUrl`). 그래서 "링크를 앞세움"은 할 수 없고, 대신 빨강일 때 카드 상태 칸 아래에 보이는 글 「도서관에서 보기 →」를 띄움 [안] (flow 결정 #7). 노랑·초록에서는 지금처럼 글 없음.
- **R13 확장 설치**: 이 사이클은 dev 저장소 `extension/` 폴더의 압축 해제 확장을 개발자 모드로 설치해 확인 [확정] (사용자, 2026-10-15). 웹에 설치 안내 페이지는 만들지 않음(웹스토어 올릴 때). 확장은 `externally_connectable`에 책첵 주소(운영·개발)만 적음 [확정] (범위 #6).

## 상태별 동작

- 로딩: 첫 상태 응답 전에는 점·글을 그리지 않음(자리는 비워 두어 머리말이 흔들리지 않게) [확정] (사용자 승인, 2026-10-15, 명세 결정 #8)
- 결과 없음: 줄이 선 도서관 목록이 비면 결과 줄에 표시 없음
- 외부 API 오류·지연: 도서관 쪽 오류는 지금처럼 그 줄 "실패". 상태 요청 실패는 R5. 확장이 받아오지 못하면 R8
- 입력 오류: 해석 요청의 계획 번호가 틀리거나 지났으면 400 `invalid_plan` [확정] (사용자 승인, 2026-10-15, 명세 결정 #14); 바이트가 4MB를 넘으면 413 (지금 서버 모드의 상한과 같음)
- 확장은 있는데 책첵 주소가 아닌 페이지가 말을 걸면 확장은 무시(`externally_connectable`로 브라우저가 먼저 막음)

## 수용 기준

- AC-1: 검색 첫 화면을 열면 10초 안에 머리말 「로그인」 왼쪽에 초록 점과 「조회 원활」이 보인다.
- AC-2: 동시 검색을 10개 띄우면 다음 상태 응답에서 노랑, 20개를 띄우면 빨강으로 바뀌고, 모두 끝나면 10초 안에 초록으로 돌아온다 (상태 API 값과 화면이 같음).
- AC-3: 검색 중 503 `server_busy`를 받으면 그 즉시 신호가 빨강이 되고, 지금 503 안내("지금 찾는 사람이 많아요…")는 그대로 나온다.
- AC-4: 빨강일 때 결과 판 위에 "도서관 사이트에서 직접 확인" 안내 한 줄이 보이고, 결과 카드마다 「도서관에서 보기 →」 글이 보인다 [안]. 초록·노랑이면 안내 줄도 글도 없다(카드 전체 링크는 그대로).
- AC-5: 한 도서관 호스트에 요청이 겹쳐 자리 대기가 생기면, 다음 상태 응답의 줄이 선 도서관 목록에 그 도서관이 들어가고, 결과 줄 이름 옆에 「지금 이 도서관 조회가 밀려요」가 보인다. 60초 뒤 겹침이 없으면 사라진다.
- AC-6: 탭을 다른 탭 뒤로 보내면 상태 요청이 멈추고(네트워크 탭), 다시 앞으로 오면 즉시 한 번 요청한다.
- AC-7: 상태 API를 1분에 60번 불러도 429가 나지 않는다(도서관 호출 한도 밖). 응답은 도서관 요청을 하나도 만들지 않는다(서버 로그).
- AC-8: 폰 폭(375px)에서는 점만 보이고, 점을 누르면 설명 한 줄이 뜨며 가로 스크롤이 생기지 않는다.
- AC-9: 확장을 개발자 모드로 설치한 크롬에서 책첵을 열면 머리말에 파란 점과 「내 브라우저에서 조회 중」이 보이고 상태 요청이 나가지 않으며, 검색하면 도서관 요청이 확장(service worker)의 네트워크 탭에 찍히며 서버 로그에는 그 검색의 도서관 요청이 없다.
- AC-10: 확장 모드 검색의 결과 줄·판정이 같은 검색어의 서버 모드 결과와 같다(같은 책, 같은 대출 가능 표시). 그 직후 확장 없는 브라우저에서 같은 검색을 하면 3분 캐시에서 답한다(`cached_count` 증가).
- AC-11: 확장 모드에서 한 호스트에 쪽 3개를 보낼 때 요청 사이가 1초 이상이고 동시에 2개가 나가지 않는다(확장 네트워크 탭 시각).
- AC-12: 서버 동시 검색 자리를 20개 채운 상태(빨강)에서도 확장 모드 검색은 503 없이 결과를 받는다.
- AC-13: 계획 번호 없이 또는 틀린 번호로 해석 요청을 보내면 400 `invalid_plan`이고 캐시에 아무것도 들어가지 않는다.
- AC-14: 확장이 없는 크롬·폰 브라우저에서는 이 사이클 전과 같은 흐름으로 검색된다(확장 감지 실패가 화면에 오류로 보이지 않음).
- AC-15: 확장 모드 검색의 도서관 응답 수가 `library_response_daily`에 `source=extension`으로 쌓인다.

## 비목표

- 웹스토어 등록·심사, 설치 안내 페이지, 자동 갱신 — 사용자: "돌아가게만 만들고 승인은 나중에" (2026-10-15)
- 엣지·파이어폭스·사파리·폰 브라우저 확장 — 범위 제외
- 확장의 설정 화면(켜기/끄기, 도서관 고르기) — 크롬 확장 관리 화면에서 끄는 것으로 갈음 [이유 미확인]
- 머리말 신호에 도서관별 상태 합치기, 조회 대기열, fetch-service 쉼 상태 — 범위 제외
- 노랑일 때 안내 줄·링크 앞세우기 — 빨강만 (방법 비교 #4)
- 확장 모드에서 서버가 대신 다시 불러 주기(실패한 도서관의 되살리기) — R8대로 하지 않음 (명세 결정 #10)
- 상태 API를 외부(운영 모니터링)에 공개 — 사이클 17 Actuator 지표가 맡음

## 확인한 것 (2026-10-15)

- 일반 `/api/` 한도: 사이클 17 `chaekcheck_api` 5r/s burst 30 nodelay (`docs/cycles/17-first-deploy/design-delta.md` 141행). 상태 묻기 10초 간격(0.1r/s)과 확장 모드의 계획·해석 요청(묶음당 2번)은 이 안에 넉넉히 들어감 → R3 [확정]
