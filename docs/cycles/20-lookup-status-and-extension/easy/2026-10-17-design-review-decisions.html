사이클 20 설계 검토에서 정할 것 4개 (2026-10-17)

/cycle-close 2단계로 design-reviewer가 사이클 20 문서를 검토했습니다. 꼭 고칠 것 7개 중 낡은 문구·태그 불일치·빠진 수용 기준(인사 재시도, 상태 응답 끊김, 확장 시간 초과, 올리기 429, 확장 캐시 3분)·단계 표시는 제가 고치고 있습니다. 아래 4개는 판단이 필요해 묻습니다. 다 정해지면 docs/current 반영 → 인계서로 갑니다.

1장부가 꽉 찼을 때 방금 받은 번호가 지워지지 않게

무엇인가. 3단계의 브라우저 번호 장부(서버 메모리, 5만 줄)가 차면 줄 하나를 지우고 새 번호를 넣기로 정했습니다(전반 점검 #10). 문서는 이걸 Caffeine 크기 상한으로 만든다고 적었는데, Caffeine 공식 위키는 "들어온 줄과 기존 줄 중 쓴 횟수가 많은 쪽을 남긴다"고 하고, 공격으로 횟수를 부풀리면 "새로 들어오는 것이 모두 거절된다"고도 적습니다(https://github.com/ben-manes/caffeine/wiki/Design , 2026-10-17 확인). 그러면 공격 중에 정상 사용자가 받은 새 번호가 바로 지워지고, 올리기마다 400 → 다시 계획 → 또 400이 되어 확장 모드를 못 씁니다.

[안] 장부는 Caffeine 대신 "가장 오래 안 쓴 줄부터 지우는" 단순한 표(Java LinkedHashMap 접근 순서 + 잠금)로 만들고, 요구사항에 "방금 받은 번호는 밀려나지 않는다"를 적습니다. 5만 줄이라 메모리(약 5MB)·속도 차이는 없습니다.

다른 선택: Caffeine 그대로 두고 공격 중 확장 모드가 꺼지는 것을 감수.

2결과 10개·gzip 같은 "부하 줄이기" 결정을 ADR 하나로

무엇인가. 다음 결정은 dev 코드의 기본값과 API를 바꾸는데 ADR이 없고 설계 문서에만 있습니다: 검색 결과 20→10(batch.row-limit, /books 기본 pageSize), 책 화면 대출 상태 자동 이어 부르기 최대 3묶음, 도서관 요청 gzip + 풀었을 때 1MB 상한(지금 4MB) + 1MB 넘음 기록, 1분 운영 요약 로그. 모두 사용자가 승인한 결정입니다(spec R15·R15-1·R16).

[안] 새 ADR-0132 「조회 부하 줄이기: 결과 10, 이어 부르기 3묶음, gzip·1MB, 1분 요약 로그」를 Accepted로 씁니다. 내용은 승인된 결정과 사용자 말 인용 그대로, 새 결정은 넣지 않습니다.

다른 선택: 기존 ADR-0131(떠나면 멈춤)에 덧붙임.

3DB 오류 시각을 누가 적나

무엇인가. 전반 점검 #9로 "최근 30초 안에 DB 오류가 있었으면 머리말 회색"을 정했습니다. 그런데 DB 오류는 책 찾기·검색 등 여러 모듈에서 나고, 상태를 판정하는 곳은 availability입니다. 문서는 "공통 오류 처리가 적음 (안: dev)"으로만 두어, dev가 모듈 경계를 넘는 공유 코드를 만들 위험이 있다는 지적입니다. dev 코드 확인: 모든 API 오류를 받는 ApiExceptionHandler가 맨 위 패키지 com.chaekcheck에 있습니다.

[안] availability가 "DB 오류가 났다고 알리기" 메서드 하나만 공개하고, ApiExceptionHandler가 DB 오류(DataAccessException 등)를 받을 때 그것을 부릅니다. 새 모듈·이벤트·공유 모듈 없음, 모듈 경계 시험(ModularityTests) 그대로 통과.

다른 선택: 상태 응답이 10초마다 DB에 아주 가벼운 질의를 직접 해 보고 실패하면 회색(다른 모듈과 연결이 전혀 없지만 "최근 30초 오류"가 아니라 "지금 DB가 응답하나"로 뜻이 조금 바뀜).

4DB 오류와 빨강이 겹치면 무엇을 보이나

무엇인가. 예: 검색 자리 40개가 다 찼거나(빨강) 프록시 길이 모두 멈춘(빨강 「지금은 도서관 조회를 할 수 없어요」) 상태에서 DB도 오류가 나면, 머리말 점을 빨강으로 둘지 회색으로 둘지입니다. 문서에는 "회색이 앞섬"이 제안으로만 있고 수용 기준 AC-37이 그것을 전제합니다.

회색 = 「상태 모름 · 상태를 확인할 수 없어요」 / 빨강 = 「붐벼요 · 잠시 뒤 다시」 또는 「도서관 조회를 할 수 없어요」

[안] 회색이 앞섬. DB가 오류면 책 찾기부터 실패할 수 있어 빨강의 안내(잠시 뒤 다시)가 맞는지 서버도 알 수 없기 때문입니다. 30초 동안 DB 오류가 없으면 원래 색으로 돌아옵니다.

다른 선택: 빨강이 앞섬(붐빔 안내를 먼저).
