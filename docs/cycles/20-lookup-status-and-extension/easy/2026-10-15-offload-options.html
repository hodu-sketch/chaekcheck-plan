조회 부담을 사용자 쪽으로 옮기는 방법을
일곱 가지 살펴봤습니다. 정할 것 5개입니다.

"크롬 확장 말고도 다른 방식이 있으면 좋아"에 대한 조사 결과입니다. 결론부터: 설치 없이 웹 페이지만으로 사용자 브라우저가 도서관을 부르게 하는 길은 없습니다(도서관 사이트 12곳을 실제로 불러 확인). 사용자 PC에 무언가를 설치하는 방법이 셋(확장, 사용자 스크립트, 도우미 프로그램), 설치 없이 부담만 덜어 주는 방법이 하나(도서관 사이트로 바로 보내기) 남습니다. 판정은 각 항목의 승인·미승인·기타 버튼으로 고르고 "저장"을 눌러 주세요. 앞 페이지(범위 결정 7개)는 그대로 유효합니다.

왜 웹 페이지만으로는 안 되는가

브라우저는 다른 사이트의 응답을, 그 사이트가 허락 머리(Access-Control-Allow-Origin)를 보낼 때만 페이지 스크립트에 보여 줍니다. 도서관 사이트 12곳의 첫 페이지를 우리 사이트인 척(Origin 머리) 불러 보니, 응답한 8곳 모두 그 머리가 없었습니다. 4곳은 응답 자체가 오지 않았습니다(인증서나 차단으로 추정, 원인은 확인 못 함).

또 우리 사이트는 https인데 도서관 몇 곳(예: 전주 전자도서관 ebook.jeonju.go.kr:8095)은 http://라서, 페이지 스크립트가 부르면 브라우저가 "혼합 콘텐츠"로 막습니다. 예외는 내 컴퓨터 자신(127.0.0.1)만입니다.

근거: MDN CORS, MDN Mixed content (2026-10-15 확인). 호출 시험 표는 `research.md` 1.1절. 도서관 수백 곳 전부를 본 것은 아닙니다(아래 #5).

일곱 가지 방법 한눈에

방법사용자가 할 일되는 곳판정
A 브라우저 확장스토어에서 설치 1회크롬·엣지(같은 파일), 파이어폭스(PC·안드로이드), 사파리(별도 포장·연 99달러)가능
B 사용자 스크립트 (Tampermonkey 같은 관리자 확장 + 우리 스크립트)관리자 확장 설치 → 스크립트 설치 → 도메인 허용 (3단계)관리자 확장이 되는 브라우저가능, 설치가 길다
C 로컬 도우미 프로그램 (PC에 설치, 우리 페이지가 127.0.0.1로 말함)설치 파일 내려받아 실행PC 전부, 폰 불가조건부: 크롬의 사설망 접근 제한, 운영체제 경고·서명
D 웹 페이지가 직접 부르기없음—불가 (위 시험)
E 도서관 사이트로 바로 보내기 (결과 줄의 "도서관에서 보기" 링크를 혼잡일 때 앞세움)링크 클릭전부, 폰 포함가능, 대출 가능 판정은 못 보여 줌
F 조회 서버·업체 프록시 늘리기없음전부부담이 사용자로 가지 않음(사이클 17에 이미 있음)
G 캐시 길게·인기 책 미리 조회없음전부부담을 줄이기만 함(보조)

제외한 생각: iframe(다른 사이트 내용은 못 읽음), 북마클릿(D와 같은 제한), 공개 CORS 프록시(남의 서버), 데스크톱 앱으로 서비스 통째 포장(과함).

A·B·C 어느 쪽을 골라도 서버 입구는 하나입니다: 주소를 주고, 받아온 원본을 돌려받아 서버가 해석합니다(앞 페이지 #5와 같음).

1첫 번째로 만들 것:
브라우저 확장(A), 크롬·엣지 함께

[안] 브라우저 확장을 먼저 만들고, 같은 파일을 Chrome Web Store와 Microsoft Edge Add-ons 두 곳에 올립니다. 엣지는 크롬 확장을 그대로 받으며 심사는 최대 7영업일(마이크로소프트 문서, 2026-10-15). 파이어폭스는 같은 규격(WebExtension)이라 뒤에 작은 손질로 올릴 수 있고, 안드로이드 폰에서는 파이어폭스만 확장을 지원합니다(공식 문서, PC와 기능 차이 있음). 사파리는 앱으로 포장하고 연 99달러가 들어 뺍니다.

이유: 설치가 한 번이고, 스토어가 갱신을 자동으로 밀어 주며, 우리 사이트에서 "설치" 버튼 하나로 안내할 수 있습니다. 세 설치 방법 중 사용자가 할 일이 가장 적습니다.

다른 선택 ①: 크롬만. 올리는 곳이 하나 줄지만 엣지 사용자는 못 씁니다(엣지는 같은 파일이라 추가 일이 거의 없음). 다른 선택 ②: 파이어폭스까지 처음부터. 안드로이드 폰 일부가 들어오지만 Manifest V2 권장·service worker 미지원이라 코드를 두 갈래로 다듬어야 합니다. 뒤로 미루는 쪽을 추천합니다.

2사용자 스크립트(B)는
만들지 않고 backlog

[안] 지금은 만들지 않습니다. 확장과 같은 일을 하지만 사용자가 관리자 확장(Tampermonkey 등, 남의 제품)을 먼저 깔고, 우리 스크립트를 깔고, 도메인 허용 창을 지나야 합니다. 확장(A)이 있으면 같은 사람들이 쓸 수 있는 더 쉬운 길이 이미 있습니다.

살릴 때: 스토어 심사가 막히거나 오래 걸릴 때의 우회로. 확장과 같은 메시지 약속을 쓰면 스크립트 하나를 더 쓰는 정도의 일입니다. backlog에 한 줄 남깁니다.

다른 선택: 확장과 함께 제공. 심사 없이 바로 배포되고 고치면 바로 반영되지만, 설치 안내 페이지가 두 갈래가 되어 사용자가 고르기 어렵습니다.

3로컬 도우미 프로그램(C)은
만들지 않고 backlog

[안] 지금은 만들지 않습니다. 브라우저와 상관없이 PC 전체에서 되는 장점이 있지만, 설치 파일을 내려받아 실행해야 하고(윈도·맥 경고를 피하려면 코드 서명 비용), 폰에서는 못 쓰며, 크롬이 준비 중인 "사설망 접근 제한"(공개 사이트가 내 컴퓨터의 프로그램에 말을 걸 때 확인 절차)에 걸릴 수 있어 프로토타입으로 확인해야 합니다(크롬 블로그: 배포 보류 중, 2026-10-15 확인).

다른 선택: 확장과 같이 만들기. 확장을 못 깔게 막힌 회사 PC 등에서 유용하지만 설치형 프로그램 두 운영체제 빌드·서명·갱신을 우리가 떠안습니다. 개인 서버 규모에는 과하다고 봅니다.

4설치 없는 길(E)을
사이클 20(신호)에 함께 넣기

[안] 신호가 빨강(혼잡)일 때 결과 줄에 이미 있는 "도서관에서 보기" 링크(detailUrl, 없으면 도서관 검색 페이지)를 앞세우고 한 줄 안내를 붙입니다: "지금 찾는 사람이 많아요. 도서관 사이트에서 직접 확인할 수 있어요". 설치가 없어 폰 사용자도 바로 쓰고, 우리 서버는 그 조회를 하지 않습니다. 대출 가능 판정은 사용자가 도서관 사이트에서 직접 봅니다.

이미 있는 것: 결과 줄마다 도서관 상세 주소 링크(`api.md` items[] `detailUrl`, 없으면 `librarySearchUrl`). 새로 만드는 것은 빨강일 때의 안내 문구와 자리뿐입니다.

다른 선택: 넣지 않음. 신호만 보고 사용자가 기다리게 됩니다. 비용이 거의 없어 넣기를 추천합니다.

5확장 사이클(21) 전에
확인 시험 두 가지

[안] dev에 작은 시험 둘을 먼저 부탁합니다. ① 확장 프로토타입: 빈 확장 하나로 `http://` 도서관(전주), 중간 인증서가 빠진 도서관, 보통 https 도서관 3곳을 받아와 우리 서버 adapter로 해석되는지. ② 전체 도서관 호스트 CORS 일괄 확인: 수백 곳 전부에 Origin 머리를 붙여 허락 머리가 있는지. 전부 없으면 "웹 페이지가 직접 부르기(D)"는 완전히 제외하고, 있는 곳이 있으면 그 도서관만 설치 없이 직접 부르는 길이 생깁니다.

두 시험은 사이클 20(신호) 개발과 같이 돌릴 수 있고, 결과가 사이클 21 명세의 전제가 됩니다.

다른 선택: 시험 없이 바로 21 설계. 확장 안에서 http 사이트가 열리지 않는 경우 설계를 되돌려야 합니다(공식 문서에 이 경우가 적혀 있지 않아 확인 못 함).
