1ADR-0118: 조회 상태 신호는 화면이 10초마다 묻고, 서버는 자리·줄 선 호스트를 메모리에서 길마다 센다

무엇인가. 원문 docs/adr\0118-lookup-status-polling-and-host-queue-board.md. 결정 줄 앞부분:

  • 머리말 신호는 화면이 `GET /api/v1/lookup-status`를 **10초마다** 묻는 방식(SSE 아님). 탭이 숨으면 멈추고, 503을 받으면 즉시 빨강, 30초 넘게 답이 없으면 회색. 확장 모드에서는 묻지 않는다.
  • 상태 주소는 nginx 도서관 호출 구역(`/api/v1/availability/`, 30r/m) 밖, 일반 `/api/` 구역 안에 둔다.
  • 서버는 동시 검색 자리 사용 수, 최근 503 시각(`SearchSlots.lastRefusedAt`), 그리고 **길(나가는 IP)마다** 줄이 선 호스트(기다리는 요청 1건 이상 또는 최근 60초 안 시간 초과; 그 호스트에서 막힌 길은 자리로 세지 않음)를 throttle 옆의 작은 부품 `HostQueueBoard`에서 세어 1초 캐시로 돌려준다. 단계는 서버가 판정한다(초록 / 노랑 = 자리 절반 이상 / 빨강 = 모두 참 또는 최근 10초 안 503).
  • 업체(Webshare) 길이 한꺼번에 멈춘 동안(업체 오류 또는 데이터 90%, 사이클 22) 단계는 **최소 노랑**, 둘째 줄 「지금은 조회가 평소보다 느려요」. 빨강 규칙은 그대로, 다시 켜지면 원래 규칙 (사이클 20 세 관점 검토 #21, 사용자 승인 2026-10-16).
  • 나가는 길 설정이 `프록시만`이고 업체 길이 모두 멈춘 동안은 서버 모드로 갈 길이 없으므로 **빨강**, 둘째 줄 「지금은 도서관 조회를 할 수 없어요」(확장 모드는 그대로) (세 관점 검토 #24, 사용자 승인 2026-10-16).
  • 위 두 값은 사이클 17/22의 나가는 길 코드가 주는 읽기 전용 포트로 읽고, 상태 응답에 `reason`(`NONE`·`VENDOR_PAUSED`·`NO_LANE`)을 더해 화면이 둘째 줄을 고른다. 포트가 없으면 `NONE`과 기본 규칙 — 이 방법은 [확정] (검토 #28 승인 2026-10-16).
  • (전반 점검 2026-10-17, 결정 페이지 `docs/cycles/20-lookup-status-and-extension/easy/2026-10-17-overall-review.html`; ADR이 Proposed라 본문에 더함)
  • 이 ADR의 모든 것(상태 묻기·`HostQueueBoard`·도서관별 「밀려요」 포함)은 사이클 20 **1단계**에 만든다 (전반 점검 #1·#3).

[안] 이 ADR을 Accepted로 바꿉니다(내용은 승인된 결정 그대로).

2ADR-0119: 크롬 확장은 "사용자 쪽 조회 서버"다 — 화면이 원본을 올리고 서버가 해석·검사한다

무엇인가. 원문 docs/adr\0119-extension-as-user-side-fetcher-server-parses-and-checks.md. 결정 줄 앞부분:

  • 확장은 도서관 페이지를 GET만 해서 화면(port)에 돌려주고 **우리 API를 모른다**. 화면이 서버의 계획 입구 셋으로 원본 바이트를 올린다: `POST /api/v1/lookup-plans/searches`(책 화면은 `/api/v1/lookup-plans/holdings`, 「더 보기」는 `/api/v1/lookup-plans/more`; 끝 이름 (안: dev가 맞춤]) → `POST /api/v1/lookup-plans/{planId}/items/{itemId}`(원본 그대로, 응답에 결과 이벤트와 포털용 상세 주소) → `POST /api/v1/lookup-plans/{planId}/close`. **계획·올리기·닫기 주소는 모두 `/api/v1/lookup-plans` 밑**: 번호 쿠키
  • 서버는 `LibraryPageFetcher`·`DetailPageFetcher`에 **받은 응답을 넣는 입구(`accept`)**를 달아 해석 → 캐시 → 결과 줄 → 판정을 서버 모드와 같은 코드로 하고(포털 상세 조회는 "상세 주소 뽑기"와 "받은 상세로 판정" 2단계로 나눔), `SearchSlots`와 호스트 throttle은 쓰지 않는다.
  • 올라온 바이트는 본문을 읽기 전에 ⑥ `Origin`(설정의 허용 origin과 대조) → 브라우저 번호 쿠키가 장부에 있음 → 장부의 받은 IP(`X-Real-IP`, IPv6는 /64) = 지금 IP → ⑨ 번호 잠금 → ①⑤ 계획 있음·쪽 번호·처음·계획을 만든 번호와 같음 → ② `Content-Length` 상한·`Content-Encoding` 없음 → 해석 자리(서버 모드와 함께 쓰는 하나, 8, 전반 점검 #4) 순으로 거르고, 그 뒤 상한까지만 읽어 ② status 200 → ③ adapter 해석(⑩ adapter는 계획 URL로만) → ⑪ `detailUrl`·상세 주소는 도서관과 같은 호스트만(서버 모드 `DetailLookupResolver`에도 같은 검사) → ④ 캐시 넣기(빈 칸이
  • 바이트 상한은 상수가 아니라 설정 하나(`chaekcheck.availability.max-body-size`, 지금 4MB → 1MB, 세 관점 검토 #7)로, nginx `client_max_body_size`도 배포 변수 하나(`LOOKUP_MAX_BODY_MB`)에서 템플릿으로 같은 값. 올리기 경로는 nginx 별도 요청 수 구역.
  • 사용 기록은 `library_response_daily.source=extension`(CHECK를 새 changeset으로 다시 걺). 서버 대행 목록 도서관은 `server_for_extension`(검토 #16).
  • **사람(브라우저)마다 세기** (세 관점 검토 #22, 사용자 승인 2026-10-16): 계획은 만든 브라우저 번호로만 올리기·닫기·지우기, 열린 계획 20과 10분 잠금은 번호별, 공인 IP는 울타리로만.
  • **브라우저 번호는 서버가 주고 서버 장부로 관리** (검토 #27·#32, 사용자 승인 2026-10-16): 서버가 무작위 번호(16바이트)를 만들어 메모리의 브라우저 번호 장부(번호 → 받은 공인 IP(/64)·받은 시각·열린 계획 수·계획 무게 합·최근 실패)에 적는다. 서명(HMAC)은 쓰지 않는다 — 장부에 없는 번호는 거절. 요청마다 "장부에 있나 + 받은 IP = 지금 IP"를 보고, IP가 다르면 400(이름 (안] `client_ip_changed`) → 화면이 조용히 새 번호를 받아 남은 도서관만 다시 계획(잠금에 안 셈). 장부 상한 5만 줄·받은 지 1일, 값은 설정. **장부가 차면 가장 오래 안 쓴 줄을 밀어내고**(503 아님) 밀려난 사람은 다음 올리기·닫기에
  • **번호는 HttpOnly 쿠키로** (검토 #33, 사용자 승인 2026-10-16): `HttpOnly`·`Secure`·`SameSite=Strict`, `Path=/api/v1/lookup-plans` 하나(전반 점검 #11), 수명 1일(설정). 자바스크립트는 번호를 보지 못하고, 머리글 `X-Lookup-Client`는 없앤다. CORS는 열지 않음(기본 거절). POST의 CSRF 머리(`X-XSRF-TOKEN`)는 그대로. 근거: MDN Set-Cookie (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie , 2026-10-16 확인).

[안] 이 ADR을 Accepted로 바꿉니다(내용은 승인된 결정 그대로).

직접 확인해 고친 것

장부가 찼을 때 "가장 오래 안 쓴 줄부터 밀어냄"(전반 점검 #10)은 캐시 라이브러리 Caffeine의 크기 상한으로 만드는데, Caffeine은 순수한 "가장 오래 안 쓴 것" 순서가 아니라 쓰인 횟수와 최근을 함께 보는 방식(W-TinyLFU)입니다(Caffeine 공식 위키 Design, https://github.com/ben-manes/caffeine/wiki/Design , 2026-10-16 확인). 효과(공격자가 채워도 정상 사용자는 400 한 번 뒤 새 번호로 이어 감)는 같아서 결정은 그대로 두고, 설계 문서 문구를 "오래되거나 드물게 쓴 줄부터"로 고칩니다.
