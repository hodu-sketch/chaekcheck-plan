동시 검색 수(서버 전체)20개. 검색 한 번 = 도서관 5곳씩 묶어 부름바로 503, 화면 노란 안내

모든 사용자의 도서관 조회가 우리 서버 한 곳의 자리 20개를 나눠 씁니다.

1신호와 확장을
사이클 둘로 나눌지

[안] 사이클 20 = 머리말 신호, 사이클 21 = 크롬 확장으로 나누기를 추천합니다. 신호는 작은 일(API 하나 + 머리말 표시)이고, 확장은 새 프로그램 하나(크롬 웹스토어 등록·심사 포함)라 크기가 다릅니다.

나누면 신호는 사이클 17 첫 배포·19 뒤 바로 이어 개발하고, 확장은 그동안 프로토타입(아래 #5·#6의 확인 사항)을 먼저 해 볼 수 있습니다. 두 사이클은 이 한 세션에서 이어서 맡습니다.

다른 선택: 한 사이클(20)에 둘 다. 문서는 하나로 줄지만, 확장의 확인 사항이 끝나기 전에는 인계서를 쓸 수 없어 신호도 함께 기다립니다.

2신호 기준: 자리 20개 중
몇 개가 차면 빨강인지

[안] 두 단계. 초록 = 자리가 남아 있음, 빨강 = 자리가 모두 찼거나 최근 10초 안에 503이 한 번이라도 났음. 기준은 "동시 검색 자리" 하나만 봅니다(도서관 한 곳의 1건·1초 제한은 보지 않음).

예: 지금 검색 20개가 돌고 있으면 빨강, 19개면 초록입니다. 어떤 검색이 끝나 자리가 비면 다음 확인 때 초록으로 돌아옵니다.

다른 선택 ①: 세 단계(초록 / 노랑 = 절반(10개) 이상 / 빨강). 몰리기 시작하는 것을 먼저 알 수 있지만 사용자가 "노랑이면 해도 되나"를 생각해야 합니다. 다른 선택 ②: 빨강 기준을 20개가 아니라 16개(80%)부터. 503을 더 일찍 예고하지만 실제로는 아직 되는데 빨강이 켜지는 때가 생깁니다.

3화면이 상태를
언제 묻는지

[안] 검색 화면(첫 화면·검색 결과·책 화면)이 열려 있는 동안 10초마다 새 주소 GET /api/v1/availability/status에 묻고, 검색 중 503을 받으면 묻지 않고 바로 빨강으로 바꿉니다. 이 주소는 도서관을 부르지 않고 숫자만 돌려주므로 nginx의 "1분에 30번" 제한 밖에 둡니다. 탭이 뒤로 가 있으면(보이지 않으면) 묻지 않습니다.

돌려주는 값은 자리 수(20), 쓰는 중(예 7), 단계(GREEN / RED) 셋입니다(제안).

다른 선택 ①: 검색을 시작할 때만 한 번 묻기. 요청이 가장 적지만 가만히 보고 있는 동안은 바뀌지 않습니다. 다른 선택 ②: 검색 스트림(SSE) 이벤트에 자리 수를 끼워 보내기. 검색 중에만 갱신되고 검색하지 않는 사람은 못 봅니다. 10초 간격은 사용자 100명이 열어 두면 1초에 10번꼴로, 숫자만 주는 요청이라 서버 부담은 작습니다.

4머리말 어디에,
어떤 모양으로

[안] 머리말 오른쪽, "사서추천도서" 링크와 로그인 버튼 사이에 작은 둥근 점 + 짧은 글. 초록 점 "조회 원활", 빨강 점 "조회 혼잡". 폰(640px 이하)은 점만 보이고 누르면 "지금 찾는 사람이 많아 검색이 거절될 수 있어요" 같은 한 줄 설명이 뜹니다(제안). 색만으로 구분하지 않도록 글(또는 폰의 설명)을 함께 둡니다.

아래 그림은 자리와 순서만 보이는 배치도입니다. dev 머리말 코드(`web/src/components/AppLayout.tsx`, 2026-10-15 확인)대로 다시 그렸습니다: 왼쪽에 「책첵」과 「사서추천도서」, 오른쪽에 「로그인」(로그인 뒤 「로그아웃」)뿐이고 폰도 같은 구성입니다. 앞 그림에 있던 설명 글과 「내 도서관 관리」는 머리말에 없습니다(「내 도서관 관리」는 검색 화면의 설정 줄에 있음). 점+글은 「로그인」 바로 왼쪽입니다.

머리말에는 네 가지만: 책첵 · 사서추천도서 · (새) 점+글 · 로그인. 폰은 점만 남기고 누르면 설명 한 줄.

다른 선택 ①: 머리말이 아니라 검색 칸 바로 아래 한 줄. 검색하려는 순간에 더 잘 보이지만, 책 화면·사서추천 화면에서는 안 보입니다. 다른 선택 ②: 초록일 때는 아무것도 안 보이고 빨강일 때만 띄우기. 평소 머리말이 깨끗하지만 "원활하다"는 안심을 주지 못합니다.

5확장이 하는 일의 범위:
받아오기만 / 해석까지

[안] 확장은 "사용자 쪽 조회 서버"로 둡니다. 우리 서버가 어느 도서관의 어느 주소를 볼지 계획을 세워 보내면, 확장이 그 주소를 사용자의 브라우저로 받아와 원본 그대로 우리 서버에 돌려주고, 해석(어느 책이 몇 권, 대출 가능 여부)은 지금처럼 우리 서버의 adapter가 합니다. 이 사용자의 조회는 서버의 자리 20개를 쓰지 않습니다.

이 모양은 이미 있는 조회 서버 약속(ADR-0015: 조회 서버는 URL을 GET으로 받아 상태 코드와 원본 바이트만 돌려줌)과 같아서, 도서관 해석 코드 9종(교보·교보 구독형·예스24 세 판·알라딘·북큐브·통합 포털·강남)을 한 곳에만 둡니다. EUC-KR 사이트도 바이트 그대로 올리므로 서버가 지금처럼 읽습니다. 해석한 결과는 서버 캐시(3분)에 들어가 확장이 없는 다른 사용자도 같은 책을 바로 봅니다.

도서관을 부르는 일만 사용자의 브라우저로 옮기고, 계획과 해석은 서버에 남습니다.

다른 선택: 확장이 해석까지 하고 서버에는 결과만 보냄. 우리 서버가 도서관 원본을 받지 않아 더 가볍지만, 해석 코드 9종을 자바와 자바스크립트 두 곳에 두고 고칠 때마다 두 번 고쳐야 하며, 확장을 배포(심사 며칠~몇 주)해야 고침이 사용자에게 닿습니다. 추천하지 않습니다.

확인 못 함(프로토타입 필요): 확장 안에서 http:// 도서관 사이트와 중간 인증서가 빠진 사이트가 열리는지. 공식 문서는 확장 안(service worker)에서는 host 권한만 있으면 다른 사이트에 요청할 수 있다고 적고, 페이지 안 스크립트(content script)는 안 된다고 적습니다 (developer.chrome.com/docs/extensions/develop/concepts/network-requests, 2026-10-15).

6확장이 요구하는 사이트 권한:
모든 사이트 / 도서관 목록

[안] 모든 http·https 사이트 권한(http://*/*, https://*/*)으로 둡니다. 도서관 사이트가 수백 곳이고 새 도서관이 들어올 때마다 확장을 다시 심사받지 않기 위해서입니다. 설치할 때 크롬이 "모든 사이트의 데이터를 읽고 바꿀 수 있음" 종류의 경고를 보이므로, 설치 안내 페이지에 "도서관 사이트의 검색 결과만 받아옵니다. 책첵 화면이 보낸 주소만 열고, 다른 사이트는 건드리지 않습니다"를 적습니다(제안).

확장은 책첵 화면(우리 주소)에서 온 요청만 받도록 externally_connectable에 우리 주소만 적습니다(공식 문서, 2026-10-15). 다른 사이트의 스크립트는 확장에 말을 걸 수 없습니다.

질문에 답: 모든 사이트 권한으로 두면 구글 심사를 통과할까

통과를 보장하는 문서는 없지만, 넓은 사이트 권한 자체는 거절 사유가 아니고 "심사가 길어지는" 요인입니다. 조건은 둘입니다: 그 권한이 기능에 정말 필요하다는 것, 그리고 심사 창의 "권한 사유" 칸에 왜 필요한지 적는 것.

공식 문서 그대로: 정책은 "기능 구현에 필요한 가장 좁은 권한을 요청"하라고 하고(여러 권한이 가능하면 데이터 접근이 가장 적은 쪽), 심사 안내는 "넓은 host 권한이나 민감한 실행 권한을 요청하는 확장은 심사가 더 오래 걸릴 수 있다", "요청한 권한마다 실제로 필요하고 적절히 쓰이는지 확인한다"고 적습니다. 거절은 "정책 위반이 발견될 때"입니다. 심사 창에는 권한마다 사유를 적는 칸과 "단일 목적" 설명 칸이 있습니다 (developer.chrome.com/docs/webstore/program-policies/permissions, …/review-process, …/cws-dashboard-privacy, 2026-10-15 확인).

우리 경우 "가장 좁은 권한"을 따지면: dev 도서관 목록의 서로 다른 호스트가 2,794개(교보 구독형 `*.dkyobobook.co.kr` 491개 포함, 2026-10-15 세어 봄)입니다. 목록을 다 적는 것은 가능하지만 도서관이 바뀔 때마다 재심사이고, 이 많은 호스트 목록도 심사자에게는 "넓은 권한"과 다르지 않게 보입니다. 사유 칸에는 "전자도서관 수백 곳의 검색 결과 페이지를 사용자 브라우저에서 받아와 책첵 화면에 보여 주는 단일 목적, 책첵 사이트가 보낸 주소만 열고 다른 사이트는 읽지 않음"처럼 적습니다.

덜 놀라게 하는 변형: optional_host_permissions(설치 때가 아니라 쓸 때 "허용" 창을 띄우는 방식, 공식 문서 "Granted by the user at runtime"). 첫 검색 때 한 번 허용하면 되고 설치 경고가 줄지만, 권한 범위 자체는 같아 심사 시간에는 차이가 없다고 볼 근거가 없습니다. 실제 승인 여부는 올려 봐야 알 수 있어 "확인 못 함"으로 둡니다. 거절되면 그때 호스트 목록 방식으로 바꾸는 길이 남습니다.

질문에 답: 확장이 도서관 정보를 불러오는 게 정말 될까, 다른 확장은 되었나

됩니다. 같은 일을 하는 확장이 이미 있습니다. 미국의 「Library Extension」(개발사 Quotidian LLC)은 아마존·Goodreads에서 책을 보는 동안 사용자가 고른 공공도서관의 온라인 목록을 브라우저에서 확인해 소장·대출 가능 여부를 같은 페이지에 보여 줍니다. Chrome Web Store에 올라 있고 사용자 10만 명, 평점 4.9(3.8천 개), "전 세계 5,000곳 넘는 도서관 지원", 크롬·파이어폭스·엣지용입니다 (chromewebstore.google.com/detail/library-extension/chkgcmmjoejpekoegkedcpifgfhpjmec, libraryextension.com, 2026-10-15 확인). 우리가 하려는 것(사용자 브라우저가 도서관 사이트를 불러 결과를 보여 주기)과 구조가 같고, 웹스토어 심사도 통과한 사례입니다.

기술적으로도 공식 문서가 적는 방식 그대로입니다: 확장 안(service worker)에서는 host 권한만 있으면 다른 사이트에 요청해 응답을 읽을 수 있습니다(developer.chrome.com/docs/extensions/develop/concepts/network-requests, 2026-10-15 확인). 우리 서버가 지금 자바로 하는 GET 요청을 확장이 자바스크립트 fetch()로 하고, 받은 바이트를 우리 서버에 올리는 것뿐입니다.

그 확장의 최근 변경 기록에 참고할 점이 하나 있습니다: 일부 도서관 시스템(SirsiDynix)이 확장의 검색을 "자동 트래픽으로 의심해 막았다"가, 사용자가 그 도서관 사이트를 한 번 직접 방문하면 다시 되는 식으로 부분 해결됐다고 합니다 (libraryextension.com/release-notes/2026.810.1, 2026-10-15 확인). 우리도 도서관이 사용자 IP의 반복 요청을 막을 수 있으므로 #7(1건·1초)을 지키고, 막히면 그 도서관 줄에 "확인 불가"로 보이는 처리가 필요합니다. 국내 서점·전자도서관을 다루는 같은 종류의 확장은 검색에서 찾지 못했습니다(확인 못 함).

우리 도서관 사이트 쪽에서 아직 확인 못 한 것은 앞서 적은 둘입니다: http:// 사이트와 중간 인증서가 빠진 사이트가 확장 안에서 열리는지. 이것이 사이클 시작 전 dev 시험(방법 비교 #5, 승인)입니다.

다른 선택: 도서관 호스트 목록을 확장에 적기. 경고가 "이 사이트들" 수준으로 좁아지지만, 목록이 수백 줄이고 도서관이 늘 때마다 확장을 다시 배포·심사받아야 하며, 그 사이 새 도서관은 확장 없이 서버로 돌아갑니다. 공식 문서는 넓은 host 권한이 심사를 길게 할 수 있다고 적습니다 (developer.chrome.com/docs/webstore/review-process, 2026-10-15).

7확장도 도서관 한 곳에
1건·1초를 지킬지

[안] 지킵니다. 확장은 도서관 한 곳에 동시 1건·요청 사이 1초(지금 서버와 같은 값)를 사용자 브라우저 안에서 지킵니다. 사용자의 집 IP가 도서관에서 막히지 않게 하기 위해서입니다. 한 사용자가 한 번에 검색 하나만 하므로 체감 속도는 지금과 비슷합니다.

다른 선택: 제한 없이 보냄. 조금 빨라지지만 도서관이 사용자 IP를 막으면 그 사용자는 확장을 꺼야 하고, 우리가 알 수도 없습니다.

함께 적어 둔 것(결정 아님): 확장 배포는 Chrome Web Store, 크롬만 먼저(사용자, 2026-10-15, 방법 비교 #1), 1회 등록비(금액은 등록 페이지에 없음)·심사 며칠~몇 주. 엣지·파이어폭스는 뒤로, 폰 브라우저는 제외. 확장 이름은 사이클 21에서 정합니다.

8#2 이어서: 특정 도서관에
몰릴 때는 어떻게 보일지

머리말 신호는 서버 전체 자리(20개)만 봅니다. 그런데 도서관 한 곳에는 동시 1건·1초 간격으로만 보내므로, 여러 사람이 같은 도서관을 찾으면 전체 자리는 남아도 그 도서관 줄만 밀려 8초 뒤 "실패"가 납니다. [안] 이 경우는 머리말이 아니라 그 도서관의 결과 줄에 표시합니다: 서버가 상태 응답에 "지금 줄이 선 도서관" 목록(기다리는 요청이 있거나 최근 1분 안 시간 초과가 난 호스트)을 함께 주고, 화면은 그 도서관 줄 이름 옆에 작은 글 "지금 이 도서관 조회가 밀려요"를 붙입니다. 그 줄의 "도서관에서 보기" 링크는 그대로 눌러 직접 볼 수 있습니다.

예: 경기교육청 통합 전자도서관을 5명이 동시에 찾으면, 머리말은 초록인데 그 도서관 줄에만 "밀려요"가 뜨고, 다른 도서관 줄은 평소처럼 나옵니다.

전체 상태는 머리말, 한 도서관의 몰림은 그 도서관 줄에. 자리와 순서만 보이는 배치도입니다.

다른 선택 ①: 머리말 신호에도 합치기(줄이 선 도서관이 하나라도 있으면 노랑). 한눈에 보이지만 다른 도서관을 찾는 사람에게는 틀린 경고가 됩니다. 다른 선택 ②: 표시하지 않고 지금처럼 8초 뒤 그 줄만 "실패"로. 만들 것이 없지만 사용자는 왜 실패했는지 모릅니다. 다른 선택 ③: 몰린 도서관은 자동으로 사용자 브라우저(확장)로 돌리기 — 확장이 있는 사람에게만 되고, 이번 설계에서는 확장이 있으면 어차피 모든 도서관을 사용자 쪽에서 부르므로 따로 필요 없습니다.

근거: dev `InMemoryHostThrottle.java`(호스트마다 동시 1건·최소 1초, 마감 8초까지 대기 뒤 시간 초과 → SSE `library-failed`), 2026-10-15 확인. "줄이 선 도서관" 판정 값(기다리는 요청 수, 최근 1분)은 명세에서 정합니다.
