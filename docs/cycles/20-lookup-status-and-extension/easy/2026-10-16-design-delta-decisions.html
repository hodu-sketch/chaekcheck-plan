#9 승인 반영 (2026-10-16): 확장 모드는 서버 캐시를 읽지 않고 자기 결과만 보며, 서버는 넣기만 합니다. design-delta·ADR-0119를 고쳤고, #5는 이것으로 정리되어 "확장 모드엔 캐시 답 없음"이 됐습니다(5번에 표시). 남은 것: #1~#4, #5(확인), #6~#8, 새로 #10(화면을 떠나면 서버 요청 멈추기 — 질문에 답). #1 승인, #2 질문(변수 방식 성능)은 2번 아래에 답함.

설계 문서 초안을 쓰면서
아직 정하지 않은 작은 값 7개가 남았습니다.

앞 페이지에서 "어떻게 만들지"(설계 결정 13개)는 다 정했고 ADR 4개도 승인됐습니다. 이 페이지는 그것을 설계 문서로 적다 보니 숫자·이름을 넣어야 하는 자리 7곳을 묻는 것입니다. 먼저 확장 모드 검색 한 번이 어떻게 흘러가는지와 낱말을 풀고, 항목마다 (1) 이 값이 구조의 어디에 붙는지 그림 (2) 사용자 화면에서 무엇이 달라지는지 그림 (3) 숫자를 그렇게 잡은 계산 (4) 다른 선택과 그 결과를 적었습니다. 길지만 한 번 읽으면 설계 문서 전체가 보이도록 썼습니다.

먼저: 확장 모드로 책 한 권을 검색하면 벌어지는 일

사용자가 크롬 확장을 설치한 상태에서 「백만장자 마인드」를 검색하면, 화면·확장·우리 서버가 아래 여섯 단계를 돕니다. 이 페이지의 값 7개는 모두 이 여섯 단계 어딘가에 붙는 숫자·이름입니다. 확장이 없는 사용자(폰 포함)는 지금처럼 서버가 도서관을 부르므로 이 그림과 상관없습니다.

①에서 "계획"이 생기고, ④가 "올리기 경로"입니다. 아래 값 7개는 ①②④⑤에 붙습니다.

낱말뜻어느 단계
계획서버가 검색 한 묶음(도서관 5곳)마다 만들어 화면에 주는 "볼 주소 목록 + 계획 번호". 확장은 이 목록대로만 도서관을 부릅니다. 번호는 추측할 수 없는 긴 글자이고 10분 지나면 못 씁니다①

서버가 계획을 들고 있는 방법 (①)

1서버가 계획을 몇 개까지,
얼마나 오래 들고 있나

어디에 붙는 값인가. ①에서 만든 계획은 ④에서 페이지가 올라올 때 "정말 이 계획에 있던 주소인가, 처음 올라오는가"를 맞춰 보려고 서버 메모리에 남겨 둡니다. 계획이 없으면 올라온 페이지를 믿을 근거가 없으므로(앞 페이지 보안 ①⑤⑩), 계획을 얼마나 오래·몇 개까지 들고 있을지가 이 값입니다. DB에는 쓰지 않습니다 — 10분짜리 임시 메모이고, 서버가 한 대라 메모리로 충분합니다(ADR-0014 "조회 계획은 서버가 저장하지 않는다"의 예외가 아니라, 확장 모드에서만 검사를 위해 잠깐 드는 메모).

계획은 서버 메모리의 임시 보관함에 10분 머물고, 보관함은 2,000개를 넘지 않습니다.

사용자 화면에서는. 평소에는 아무것도 보이지 않습니다. 검색 한 번이 8초(묶음 마감)~30초(포털 상세) 안에 끝나므로 10분은 넉넉합니다. 보관함이 넘쳐 오래된 계획이 버려지거나 10분이 지난 뒤 늦게 올라오는 경우에만 서버가 400을 돌려주고, 화면은 그 묶음을 "검색하지 못했어요. 잠시 뒤 다시 시도해 주세요."(지금 있는 일반 오류 문구, 화면 흐름 #6)로 보이며 다음 검색은 새 계획으로 다시 시작합니다.

숫자 계산. 보통 사용자는 검색 한 번에 계획 1~4개(묶음 수)를 만듭니다. 동시에 100명이 검색해도 400개입니다. 2,000개는 그 5배이고, 계획 하나가 수 KB라 상한에 닿아도 약 10MB입니다. 상한이 필요한 까닭은 보안 ⑦(IP별 계획 한도)이 뚫리는 경우의 두 번째 울타리입니다 — 예를 들어 여러 IP에서 계획만 만들어 대면 상한이 없을 때 메모리가 계속 늡니다. 10분은 명세 #11에서 이미 정한 값입니다.

[안] 보관 10분(확정값 그대로), 동시에 최대 2,000개, 넘으면 가장 오래된 것부터 버림. 값은 설정(`chaekcheck.availability.plan-store.max-size` [안 이름])으로 두어 바꿀 수 있게.

다른 선택과 결과. ① 개수 상한 없음 — 코드는 한 줄 줄지만 IP별 한도가 뚫리면 메모리가 늘고, 한 대 서버에서 메모리가 가장 중요하다고 하셨으므로 추천하지 않습니다. ② 더 짧은 보관(2분) — 메모리는 더 작지만 포털 상세 2단계가 느린 도서관에서 30초를 넘기면 늦게 올라온 쪽이 400이 됩니다. ③ DB에 저장 — 재시작해도 남지만 10분짜리 값에 DB 쓰기가 붙어 무겁습니다.

올리기 경로를 지키는 숫자 (④)

2한 사람이 1초에 몇 번까지
올릴 수 있게 할지 (nginx)

어디에 붙는 값인가. 우리 서버 앞의 nginx는 "IP마다 1초에 몇 번"으로 요청을 제한합니다. 지금 두 구역이 있습니다: 도서관을 부르는 요청(검색 스트림 등, 1분 30번)과 그 밖의 `/api/` 요청(사이클 17: 초당 5번, 몰아서 30번). 앞 페이지 #12에서 "올리기 경로는 세 번째 구역으로 따로 둔다"고 정했고, 그 구역의 숫자가 이 값입니다. 올리기는 도서관을 부르지 않지만(확장이 이미 받아온 것을 넘길 뿐) 요청 수가 많아 일반 구역에 넣으면 한도에 걸칩니다.

올리기 경로만 세 번째 구역으로 떼어 초당 20번까지 받습니다. 다른 두 구역은 그대로입니다.

사용자 화면에서는. 한도 안이면 아무 차이가 없습니다. 한도를 넘으면 nginx가 429를 돌려주고, 화면은 지금 있는 안내 줄 "검색을 너무 자주 했어요. 1분쯤 뒤에 다시 해 주세요."(사이클 08)를 보이고 받은 결과는 남깁니다. 제안 값이면 보통 사용은 절대 닿지 않고, 스크립트로 수백 번 올리는 경우에만 걸립니다.

숫자 계산. 묶음 하나 = 도서관 5곳 동시 → 쪽 5개가 0.3~1초 사이에 올라옴 → 초당 약 5번. 포털 상세 2단계와 다음 묶음이 겹치는 순간 7~8번. 그래서 평소의 4배인 20을 두고, 순간 몰림을 위해 60까지 몰아서(burst) 허용합니다. 사이클 17의 일반 구역 값(5/30)과 같은 비율입니다.

[안] IP당 초당 20번, 몰아서 60번. 이 값은 #12에서 변수로 뺀 "페이지 크기 상한"과 달리 바꿀 일이 적어 nginx 설정의 상수로 둡니다(원하시면 같은 변수 방식으로).

질문에 답: 변수 방식으로 해도 성능 문제는 없나

없습니다. 변수는 nginx 컨테이너가 켜질 때 한 번 공식 이미지의 시작 스크립트가 템플릿에 값을 채워 보통 설정 파일(`/etc/nginx/conf.d/…conf`)로 써 두는 것이고, 그 뒤 nginx는 숫자가 박힌 보통 설정을 읽습니다. 요청을 처리할 때마다 변수를 찾는 일이 없어 상수로 적은 것과 처리 속도·메모리가 같습니다(hub.docker.com/_/nginx "Using environment variables in nginx configuration": 템플릿을 `envsubst`로 처리해 `/etc/nginx/conf.d`에 출력, 2026-10-16 확인).

변수는 켤 때 한 번 채워지고, 그 뒤로는 상수와 똑같습니다.

그래서 요청 수 한도도 페이지 크기처럼 변수로 빼는 편이 일관됩니다. 원하시면 이 항목을 "초당 20번·몰아서 60번, `prod.env`의 `LOOKUP_UPLOAD_RATE=20`·`LOOKUP_UPLOAD_BURST=60` 변수로"로 고쳐 승인해 주세요(기타에 "변수로"라고만 적어도 됩니다).

다른 선택과 결과. ① 초당 10번, 몰아서 30 — 더 조이지만 포털 상세가 겹치는 순간 429가 나 그 묶음이 끊깁니다. ② 올리기도 일반 구역에 — 설정이 하나 줄지만 초당 5번에 딱 걸쳐 확장 모드 검색이 자주 끊깁니다(앞 페이지 #12에서 이미 따로 두기로 함). ③ 한도 없음 — 가짜 올리기 폭주를 nginx에서 못 막아 서버가 다 받습니다.

3한 IP가 계획을 너무 많이 만들거나
검사에 자꾸 걸리면

어디에 붙는 값인가. 앞 페이지 #6에서 더한 보안 장치 가운데 ⑦ "IP별 계획 만들기 한도"와 ⑨ "검사 실패가 잦은 IP는 잠시 막기"의 숫자입니다. ⑦은 ①(계획 만들기)에, ⑨는 ④(올리기 검사)에 붙습니다. 둘 다 nginx가 아니라 우리 서버 안의 IP별 카운터(메모리, 1분 창)입니다 — nginx 구역(#2)은 "요청 수"만 보고 "검사에 걸렸는지"는 모르기 때문입니다.

계획 한도(⑦)는 입구에서, 검사 실패 한도(⑨)는 올리기에서 IP별로 셉니다. 걸린 IP만 잠시 멈춥니다.

사용자 화면에서는. 보통 사용자는 어느 쪽에도 닿지 않습니다. 걸린 IP에서 검색하면 계획 요청이 429로 돌아와 "검색을 너무 자주 했어요" 안내가 보이고, 10분 뒤 다시 됩니다. 확장 모드가 아닌(서버 모드) 검색에는 이 두 장치가 적용되지 않습니다 — 서버 모드는 계획을 만들지 않기 때문입니다.

숫자 계산. ⑦ 20개/분: 검색 한 번이 계획 1~4개이니 1분에 검색 5번(보통 사람은 1분에 1~2번)까지 여유. 집·회사에서 IP 하나를 여럿이 쓰는 경우도 5명이 1분에 4번씩 검색해야 닿습니다. ⑨ 30번/분: 검사 실패는 정상 사용에서 거의 0이고(계획 만료·중복 정도), 30번이면 분명한 자동 시도입니다. 10분 거절은 사이클 17의 "막힌 IP 첫 시험 10분"과 같은 길이로 맞췄습니다.

[안] ⑦ 한 IP는 계획을 1분에 20개까지(넘으면 429). ⑨ 검사 실패(400)가 한 IP에서 1분에 30번을 넘으면 그 IP의 계획 만들기를 10분 거절하고, 실패는 사용 기록 `rejected_event`에 종류 "계획 검사 실패"로 셈. 세 숫자는 설정값으로.

다른 선택과 결과. ① 한도 없이 기록만 — 시도가 있었음은 통계로 알지만 막지는 못해, 가짜 페이지를 계속 올려 캐시 칸을 3분마다 다시 채울 수 있습니다. ② 더 낮게(계획 5개/분) — 빠르게 여러 책을 찾는 사용자나 IP를 함께 쓰는 집이 걸립니다. ③ nginx에서 세기 — nginx는 "검사에 걸렸는지"를 모르므로 ⑨는 서버에서만 가능합니다.

캐시와 사용 기록 (②·⑤)

4가짜가 발견됐을 때
확장이 넣은 캐시 칸을 비우는 방법

어디에 붙는 값인가. 앞 페이지 보안 ⑧은 "캐시 값에 '확장 출처' 표시와 넣은 시각을 남기고, 확장 출처 칸만 한 번에 비울 수 있게"였습니다. 표시를 남기는 것은 정해졌고, "한 번에 비우는 방법"이 이 항목입니다. 캐시는 서버 메모리의 표(②)이고 값마다 3분 뒤 저절로 사라집니다.

캐시 값마다 출처와 시각이 남습니다. 비우기는 이번엔 재시작으로, 전용 명령은 관리 화면 때 함께.

사용자 화면에서는. 가짜가 들어간 3분 동안 그 도서관 줄에 틀린 "대출 가능" 표시가 보일 수 있습니다(흉내 낸 페이지만 검사를 통과하므로 드묾). 운영자가 재시작하면 그 뒤 첫 검색은 캐시가 비어 평소보다 몇 초 느리고(도서관을 다시 부름), 그다음부터는 같습니다.

[안] 이번에는 서비스 재시작으로 갈음. 캐시 값에는 출처(`via=extension`)와 넣은 시각만 남겨 로그·조사에 씀. 전용 비우기 명령·관리 화면은 만들지 않음(관리 화면은 이미 backlog).

다른 선택과 결과. ① 관리 포트(Actuator) 엔드포인트 — 재시작 없이 비우지만 사이클 17의 관리 포트 설정 위에 코드·인증·시험을 더 얹어야 하고, 쓸 일이 드뭅니다. ② 확장 출처 값은 캐시에 넣지 않음 — 비울 일 자체가 없지만 "확장도 캐싱"(AC-10)과 어긋납니다. ③ 확장 출처 값은 1분만 보관 — 노출이 짧아지지만 확장 사용자가 낸 결과를 다른 사용자가 덜 재사용합니다.

5확장 모드 검색의 "캐시로 답한 건"을
사용 기록에 어떻게 셀지

어디에 붙는 값인가. ⑤에서 묶음을 닫을 때 사용 기록(`usagelog.library_response_daily`, 하루×도서관×출처마다 한 줄)에 숫자를 더합니다. 지금 출처(`source`)는 "직접 찾기"와 "소장 채우기" 둘이고, 앞 페이지 #9에서 "확장"을 더하기로 했습니다. 그런데 ②에서 서버 캐시로 바로 답한 도서관은 확장이 한 일이 아니므로 어느 출처·어느 결과 칸에 셀지가 남았습니다. 사이클 19가 마침 "캐시로 답한 수"(`cached_count`, 결과 값 `CACHED`) 칸을 더하는 중이라 그 칸을 같이 쓸 수 있습니다.

출처를 모두 `extension`으로 두면 "확장 모드 검색이 하루 몇 건, 그중 캐시가 몇 건, 실패가 몇 건"을 한 줄로 셀 수 있습니다.

사용자 화면에서는. 아무 차이가 없습니다. 이 표는 운영자가 보는 통계(사이클 15, Grafana·SQL)에만 쓰입니다. 나중에 "확장을 쓰는 사람이 얼마나 되나, 확장 조회가 서버 조회보다 더 실패하나"를 볼 때 이 칸들을 봅니다.

왜 출처를 `extension`으로. 통계의 단위는 "어떤 검색이었나"입니다. 캐시 답 2건을 서버 출처로 적으면 그 검색이 확장 모드였다는 사실이 사라져 "확장 모드 검색 수"를 다시 셀 수 없습니다. 반대로 `extension` + `cached`로 적으면 "확장 모드 검색 5건 중 캐시 2·성공 2·실패 1"이 그대로 읽힙니다. 사이클 19의 `CACHED` 값은 서버 모드에서도 같은 뜻으로 쓰이므로 칸을 새로 만들 필요가 없습니다.

#9 승인으로 바뀜(2026-10-16): 확장 모드는 서버 캐시를 읽지 않으므로 확장 모드 검색에는 "캐시로 답한 건"이 생기지 않습니다. 사용 기록은 출처 `extension`으로 성공·실패·건너뜀만 셉니다. 아래 원래 제안은 기록으로 남깁니다.

[안] (원래 제안) 캐시로 답한 도서관은 19의 `CACHED` 칸에, 출처는 그 검색이 확장 모드였으니 `extension`. 확장이 받아와 해석된 것은 성공/실패, 확장이 보내지 못한 것(close의 `notSent`)은 건너뜀. 19와 같은 표를 고치므로 Liquibase 파일은 따로 두고 나중에 합치는 쪽이 순서를 맞춤(19 세션과 합의).

다른 선택과 결과. ① 캐시 답은 출처 `direct_search`로 — "캐시는 서버 것"이라는 뜻에는 맞지만 확장 모드 검색 수를 잃습니다. ② 확장용 출처를 둘로(`extension_search`·`extension_holding`) — 검색과 책 화면을 나눠 셀 수 있지만 명세 #13에서 하나로 정했습니다. ③ 캐시 답은 세지 않음 — 표가 단순하지만 19가 그 칸을 만드는 이유(캐시 효과 보기)와 어긋납니다.

이름

6코드에 들어갈 이름 몇 개

어디에 붙는 값인가. 설계 문서에 이름을 적어 두어야 dev가 만든 뒤 회고에서 "설계대로 됐나"를 대조할 수 있습니다. 아래 이름들은 각각 다른 파일에 들어갑니다. dev가 코드 사정에 맞게 바꿔도 되고, 바뀌면 회고에 적습니다(지금까지의 사이클과 같은 방식).

이름은 확장·화면·서버 세 곳의 파일에 나뉘어 들어갑니다.

무엇제안 이름어디서 쓰나
화면이 확장에 보내는 첫 인사와 답`{type:'hello'}` → `{version}`화면이 뜰 때 "확장 있니?" (500ms 안에 답 없으면 서버 모드)
조회 메시지(주소 목록 ↔ 받은 페이지)`{type:'fetch', items}` ↔ `{type:'page', itemId, status, contentType, base64, ms}`③
웹이 확장 ID를 읽는 설정 이름`VITE_EXTENSION_ID`웹 빌드 설정(.env)
개발 중 책첵 주소(확장이 말을 받아 주는 주소)`http://localhost:5173/*` + 운영 `https://chaekcheck.com/*`확장 manifest
사용 기록 표를 고치는 Liquibase 파일`usagelog/003-library-response-source-extension.yaml`DB 변경 기록(19의 002 다음)
「더 보기」의 계획 주소`POST /api/v1/availability/libraries/{libraryId}/ebooks/plans`앞 페이지 #7

[안] 위 표의 이름대로 설계 문서에 적습니다.

다른 선택과 결과. 이름은 전부 dev에 맡기고 문서에는 안 적음 — 문서가 짧아지지만 인계서·회고에서 "설계대로 됐나"를 대조할 기준이 없어지고, 확장·화면·서버 세 곳이 서로 다른 이름을 쓰게 될 수 있습니다.

아직 확인 못 한 것에 대비 (③)

7확장이 못 여는 도서관이 있으면
그 도서관만 서버가 대신 부르기

어디에 붙는 값인가. ③에서 확장이 도서관을 부를 때, `http://` 주소 도서관(예: 전주 전자도서관 `ebook.jeonju.go.kr:8095`)이나 중간 인증서가 빠진 도서관을 확장 안에서 열 수 있는지는 공식 문서에 적혀 있지 않아 아직 모릅니다(인계 전 dev 프로토타입으로 확인). 못 여는 도서관이 나왔을 때 그 도서관을 어떻게 할지 미리 정해 두는 규칙입니다. 서버는 그 도서관들을 지금도 잘 부릅니다(사이클 07·18에서 처리).

못 여는 도서관만 서버가 대신 부르고, 사용자에게는 같은 결과 목록으로 보입니다.

사용자 화면에서는. 결과 목록에 차이가 없습니다. 전주처럼 서버가 대신 부른 도서관도 같은 카드로 나옵니다. 다만 그 한 곳은 서버 자리를 잠깐 쓰므로, 서버가 빨강(자리 모두 참)일 때는 그 도서관 줄만 "확인하지 못한 도서관"에 들어갈 수 있습니다(다른 도서관은 확장이 하므로 영향 없음).

왜 미리 정하나. 프로토타입 결과가 "안 열림"으로 나오면 그때 설계를 다시 열어야 합니다. 지금 갈래를 정해 두면 dev가 결과에 따라 규칙을 넣거나 빼기만 하면 됩니다. 못 여는 도서관 목록은 도서관 표에 칸을 더하지 않고 설정 목록(도서관 번호)으로 두어 Liquibase 변경 없이 바꿀 수 있게 합니다.

[안] 프로토타입에서 못 여는 도서관이 나오면, ① 계획을 만들 때 그 도서관은 `items`에서 빼고 서버가 직접 부른 결과를 `events`로 함께 돌려주는 규칙을 더합니다(그때만 서버 자리 1개 사용, 목록은 설정). 모두 열리면 이 규칙은 넣지 않습니다.

다른 선택과 결과. ① 못 여는 도서관은 확장 모드에서 "확인하지 못한 도서관"으로 — 규칙이 하나 줄지만 그 도서관 결과를 확장 사용자는 영영 못 보고, 왜 안 되는지도 모릅니다. ② 못 여는 도서관이 하나라도 있으면 그 검색 전체를 서버 모드로 — 단순하지만 전주 한 곳 때문에 나머지 4곳도 서버 자리를 쓰게 되어 확장의 뜻이 줄어듭니다.

8이 문서대로 다음 단계로

무엇을 묻나. 위 7개가 정해지면 설계 문서(design-delta.md)가 완성됩니다. 사이클의 남은 단계는 아래 그림처럼 셋이고, 그중 둘은 사이클 17(첫 배포) 회고 뒤에 합니다 — 20이 17이 만드는 nginx 파일·나가는 길 코드 위에 얹히므로, 17이 실제로 어떻게 만들어졌는지 보고 인계서를 써야 하기 때문입니다.

검토는 바로, 반영과 인계는 17 회고 뒤.

[안] 이 문서대로 다음 단계로 갑니다. 지금은 설계 검토만 돌리고, `docs/current/` 반영과 인계서는 사이클 17 회고 뒤에 합니다(`CLAUDE.md` 규칙).

9질문에 답: 확장 모드는 서버 캐시를 안 쓰고
자기가 받은 것만 보여 주면 되지 않나

됩니다, 그리고 더 단순해집니다. 말씀하신 대로 하면 확장 모드 사용자는 언제나 자기 브라우저가 방금 받아온 결과를 보고, 우리 서버는 그 결과를 해석한 김에 캐시에 넣어 다른 사용자(확장 없는 사람)가 3분 동안 재사용합니다. 이것은 앞서 승인한 설계 #4의 "계획 응답이 3분 캐시에 이미 있는 도서관은 주소 대신 결과를 바로 준다"를 바꾸는 것이라 다시 묻습니다.

달라지는 것은 ① 계획 단계에서 서버가 캐시를 보느냐뿐. 캐시에 넣는 것(④)은 그대로입니다.

지금 설계 (캐시 먼저)제안 (확장은 항상 직접)
사용자가 보는 결과섞임: 일부는 남이 최대 3분 전에 본 값모두 방금 자기 브라우저가 본 값 — "사용자로 접근하니 사용자 것으로"
도서관에 가는 요청(사용자 IP)캐시 hit만큼 줄어듦검색마다 모두(호스트 1건·1초는 그대로라 막힐 위험은 같음)
서버 일계획 때 캐시 조회 + 해석해석만(계획 때 캐시 안 봄) → 더 단순
사용 기록 셈(#5)확장 모드에도 `CACHED` 있음확장 모드에는 `CACHED` 없음 → #5는 "확장 모드엔 캐시 답 없음"으로 정리
캐시 오염 위험같음 (넣는 쪽 규칙 그대로)같음
검색 속도캐시 hit 도서관은 즉시모두 확장이 받아와 1~수 초. 다만 서버 모드처럼 줄 서지 않음

[안] 사용자 제안대로: 확장 모드에서는 서버가 계획 때 캐시를 보지 않고 모든 주소를 확장에 주며, 사용자는 자기 브라우저가 받은 결과만 봅니다. 서버는 올라온 결과를 해석해 캐시에 넣어 다른 사용자가 씁니다(빈 칸이면 넣고, 서버 출처 값은 덮지 않고, 확장 출처 값은 새 값으로 갱신). 이에 따라 설계 #4의 "캐시에 있는 도서관은 결과 바로"를 빼고, #5는 "확장 모드에는 캐시 답이 없음"으로 정리하며, ADR-0119(Proposed)도 고칩니다.

다른 선택: 지금 설계 그대로(캐시 먼저). 사용자 IP 요청이 조금 줄지만 결과가 섞이고 서버가 계획 때 캐시를 한 번 더 봐야 합니다.

10질문에 답: 화면을 떠나면
기다리던 조회 요청이 사라지나

지금은 사라지지 않습니다 — 고려하지 못했던 부분입니다. dev 코드를 확인해 보니(2026-10-16) 화면은 떠날 때 검색 스트림을 끊지만(`useSearch.ts` "leaving the page aborts the open stream"), 서버는 사용자가 떠난 것을 보지 않고 그 묶음을 끝까지 돌립니다. 아직 시작 안 한 도서관도 시작 마감(3초)까지 계속 보내고, 호스트 줄(1건·1초)에서 기다리던 요청도 그대로 기다리며, 서버 자리(20개 중 1개)는 묶음 마감(8초, 포털 상세는 30초)까지 붙들립니다. 코드 주석에도 "Requests still count after the browser left"라고 적혀 있습니다(`BatchRunner.java` 70행). 결과를 보낼 곳이 없어 `send`가 false를 돌려줘도 실행 고리는 그 값을 보지 않습니다(`SseEventSink.java`, `BatchRunner.runTasks`).

떠난 사용자의 묶음이 자리와 호스트 줄을 붙들지 않게, 알아챈 순간 새 시작과 줄 대기를 멈춥니다.

왜 이번 사이클과 관계있나. 이번 사이클은 "자리가 꽉 찼는지"(신호)와 "호스트 줄에 기다림이 있는지"(줄이 선 도서관)를 사용자에게 보여 줍니다. 떠난 사용자의 묶음이 자리와 줄을 계속 붙들면 신호가 실제보다 붉게, 「밀려요」가 실제보다 오래 보이고, 503도 그만큼 더 납니다. 화면을 오가며 검색어를 바꾸는 사람이 많을수록 커집니다.

[안] 서버 모드에서 사용자가 떠난 것을 알아채면 그 묶음을 멈춥니다: (1) 알아채는 법 — 이벤트 보내기가 실패하거나(`send`가 false) 서블릿이 연결 끊김을 알릴 때(`SseEmitter` onError/onCompletion), (2) 멈추는 것 — 새 도서관 시작 안 함, 호스트 줄에서 아직 자리를 못 받은 요청은 취소, 서버 자리는 바로 반납, (3) 남기는 것 — 이미 도서관에 나간 요청은 끝까지 받아 캐시에 넣고(다른 사용자용) 사용 기록에도 셈, 시작 못 한 것은 "건너뜀". 확장 모드는 화면이 떠나면 확장 port가 닫히므로 확장이 자기 줄의 남은 주소를 버리고, 서버의 계획은 그대로 10분 뒤 만료(올라올 것이 없으니 할 일 없음). 「더 보기」도 같은 규칙.

다른 선택과 결과. ① 지금대로(끝까지 돌림) — 코드 변경이 없지만 위 문제(신호가 실제보다 붉음, 자리·줄 낭비)가 남습니다. ② 이미 도서관에 나간 요청까지 끊음 — 자리는 더 빨리 비지만 도서관은 이미 일했고 결과를 버리게 되어 캐시 재사용을 잃습니다. ③ 화면이 떠날 때 "그만" 요청을 따로 보냄 — 끊김을 더 확실히 알지만 새 주소가 필요하고, 브라우저를 그냥 닫으면 보내지 못할 수 있어 (1)과 함께 써야 합니다.
