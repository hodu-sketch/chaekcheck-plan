상태 신호

1상태 주소: /api/v1/lookup-status

[안] 상태를 주는 주소를 GET /api/v1/lookup-status로 둡니다. 범위 때 예시로 적은 /api/v1/availability/status는 nginx의 "도서관 호출" 구역(`/api/v1/availability/`, 1분 30번) 안에 있어, 예외 블록을 하나 더 적어야 하고 운영 설정에서 그 블록이 빠지면 상태 묻기가 429로 막힙니다. 새 이름은 저절로 일반 `/api/` 구역에 들어가 설정을 바꿀 것이 없습니다.

다른 선택: 예시 이름 그대로 두고 nginx에 정확 일치 예외 블록 추가. 이름은 익숙하지만 설정 실수 하나가 AC-7을 깨뜨립니다.

2"줄이 선 도서관"을 세는 자리:
새 부품 HostQueueBoard

[안] 지금 도서관 호출 간격을 재는 부품(`InMemoryHostThrottle`)에 세는 일을 더 얹지 않고, 옆에 작은 부품 HostQueueBoard를 둡니다. throttle은 "기다리기 시작/끝/시간 초과"가 날 때 (길, 호스트, 도서관)만 알려 주고, 보드가 길마다 기다리는 수와 마지막 시간 초과 시각을 들고 있습니다. 상태 서비스가 보드 + 사이클 17의 "막힌 길" 기록으로 R4를 판정합니다.

이유: 사이클 17이 같은 throttle 파일을 "길마다 따로 세기"로 고치는 중이라, 20도 거기를 고치면 두 사이클의 변경이 한 파일에서 겹칩니다. 보드는 따로 시험할 수 있습니다.

한계: 호스트 → 도서관 번호를 서버가 요청을 보내면서 배우므로, 서버를 다시 켠 뒤 한 번도 불리지 않은 포털 소속 도서관은 목록에 빠질 수 있습니다(그 도서관은 결과 줄도 없어 화면 차이는 없을 것으로 봄, 확인 필요).

다른 선택: throttle 안에 넣기. 클래스가 늘지 않지만 17의 변경과 같은 파일에서 겹칩니다.

확장 모드

3받아온 바이트를 서버에 올리는 쪽:
확장이 아니라 화면

[안] 확장은 도서관을 GET 해서 결과(상태 코드·바이트·걸린 시간)를 화면에 돌려주기만 하고, 우리 서버에 올리는 것은 화면(웹)이 합니다. 그러면 확장은 우리 API를 전혀 모르는 "사용자 쪽 조회 서버"가 되어, 나중에 서버나 웹 API를 바꿔도 확장을 다시 배포·심사(며칠~몇 주)할 필요가 없습니다. CSRF·CORS 예외도 필요 없습니다.

승인 조건(사용자, 2026-10-15): "그런데 조작되지 않도록 보안에 신경써줘" → 설계에 적을 보안 장치: 일회성 계획 번호(10분)·item은 한 번만·서버가 계획에 적은 URL만 씀(올린 URL은 받지 않음)·4MB 상한·올라온 바이트의 해석 검사(#6)·캐시는 빈 칸만(#6). 확장 자체는 책첵 주소에서 온 요청만 받음(externally_connectable).

다른 선택: 확장이 서버에 직접 올리기. 바이트가 메시지(base64, 최대 약 322KB)를 거치지 않지만, 확장이 API 주소·판에 묶여 API를 바꿀 때마다 재심사가 필요하고 CSRF 예외·확장 origin CORS 확인이 생깁니다.

4확장 모드 입구: 새 JSON 요청 셋
(계획 → 쪽 올리기 → 닫기)

[안] 지금 검색 스트림(SSE)을 고치지 않고 JSON 요청 셋을 새로 둡니다. ① POST /api/v1/ebook-searches/plans(책 화면은 /book-availabilities/plans): 검색 조건을 보내면 계획 번호(10분), 볼 주소 목록, 그리고 서버 3분 캐시에 이미 있는 도서관은 주소 대신 결과를 돌려줍니다(사용자 IP 요청이 줍니다). 서버 자리(20)는 쓰지 않습니다. ② POST /api/v1/lookup-plans/{planId}/items/{itemId}: 받아온 원본 바이트를 그대로 올리면 서버가 해석해 결과 줄·판정과, 포털 줄에 필요한 상세 주소 목록을 돌려줍니다(2단계). ③ POST …/close: 못 보낸 것을 알리고 묶음 끝 이벤트를 받습니다. 응답 안의 이벤트는 지금 SSE와 이름·내용이 같아 화면이 같은 코드로 처리합니다.

이유: 요청마다 답하고 끊어 연결을 붙들지 않습니다("메모리 점유가 더 문제"와 맞음). 틀린 계획 번호는 400 invalid_plan, 4MB 초과는 413.

다른 선택 ①: 지금 SSE 스트림에 확장 모드 값을 더하고 업로드는 옆 주소로 받아 SSE로 밀어 줌. 화면 코드는 그대로지만 검색마다 연결을 최대 35초 붙들고 두 통로를 짝지어야 하며 nginx 도서관 호출 구역에 걸립니다. 다른 선택 ②: 묶음을 한 번에 올리기. 다 받아야 올려 결과가 순서대로 뜨지 않고 본문이 최대 50×4MB.

5서버 안에서 올라온 바이트가 들어가는 길:
"받은 응답" 입구 하나

[안] 지금 도서관 페이지를 받아 해석하는 부품(`LibraryPageFetcher`·`DetailPageFetcher`)에 "이미 받은 응답을 넣어 주는 입구(accept)"를 더합니다. 그 뒤의 해석 → 캐시 → 결과 줄 → 판정은 서버 모드와 같은 코드를 지나고, 도서관을 부르는 부분과 간격 재기만 건너뜁니다. 포털의 상세 조회는 "상세 주소 뽑기"와 "받은 상세로 판정" 두 단계로 나눕니다(책 화면 쪽은 이미 나뉘어 있음).

그림으로 다시 설명: 서버 안에서 도서관 페이지가 지나는 길

지금 서버 모드에서 도서관 페이지 하나는 네 칸을 차례로 지납니다. 확장 모드는 앞의 두 칸(간격 재기, 도서관 부르기)을 사용자 브라우저가 대신하고, 받아온 바이트를 세 번째 칸 앞에 넣어 주는 문(accept)만 새로 답니다. 그 뒤는 서버 모드와 한 글자도 다르지 않은 코드가 돕니다.

새로 다는 것은 초록 "문"(accept) 하나와 ④의 "상세 주소 돌려주기"뿐. 해석·캐시·판정(③④)은 서버 모드와 같은 코드를 씁니다.

왜 이 방식인지: ③④를 복사하지 않으니 adapter나 판정 규칙을 고칠 때 한 곳만 고치고, 확장 모드 결과가 서버 모드와 같아집니다(AC-10). 서버의 간격 재기(①)를 건너뛰므로 확장 사용자는 서버 줄에 서지 않고, "줄이 선 도서관" 판정에도 끼지 않습니다.

다른 선택 ①: 업로드를 기다리는 가짜 SiteFetcher. 서버의 호스트 간격 줄에 확장 사용자가 서게 되어 사용자 IP와 서버 길이 섞이고, 기다리는 스레드와 "지금 받아 와" 밀어주기 통로가 필요합니다. 다른 선택 ②: 고정 응답 SiteFetcher로 fetcher를 하나 더 만들기. 포털 상세 조회가 결국 서버 fetcher를 불러 ①·②를 섞어야 합니다.

6가짜 결과가 캐시를 더럽히는 것:
빈 칸일 때만 채움

[안] 확장이 올린 결과는 서버 3분 캐시에 그 칸이 비어 있을 때만 넣습니다. 서버가 직접 받아 둔 값은 덮지 않습니다. 계획 번호(명세 #11)는 "모르는 사람이 아무 때나 올리기"는 막지만 "계획을 받은 사람이 가짜 바이트를 올리기"는 못 막는데, 이 규칙이면 가짜가 들어가도 서버가 본 값을 밀어내지 못하고 3분이면 사라집니다.

질문에 답: 3분 안이면 어차피 캐시로 답하니 의미 없지 않나

거의 맞습니다. #4대로 서버는 캐시에 있는 도서관은 확장에 주소를 보내지 않으므로, 확장이 올리는 결과는 원래 빈 칸에만 들어갑니다. "빈 칸일 때만"이 실제로 작동하는 때는 딱 하나, 계획을 준 뒤 업로드가 오기까지 몇 초 사이에 다른 사용자의 서버 조회가 같은 칸을 먼저 채운 경우뿐입니다(그때 서버가 본 값을 지킴). 그래서 이 규칙은 "가짜가 서버 값을 덮는 것"만 막고, 빈 칸에 가짜를 넣어 3분간 보이게 하는 것은 막지 못합니다 — 이것이 architect가 말한 한계입니다.

가짜가 들어오는 것 자체를 줄이려면 올라온 바이트를 서버가 받으면서 검사하는 수밖에 없습니다: 계획에 적힌 주소의 도서관 adapter로 해석이 되는지(해석 실패면 버림), 상태 코드 200인지, item은 한 번만, 4MB 이하. 이 검사는 ③의 해석 과정에서 공짜로 얻어지므로 비용이 거의 없습니다. 그래도 "그 도서관 페이지 모양을 흉내 낸 HTML"까지는 못 걸러내고, 그런 것은 3분 뒤 사라집니다.

다시 고르는 선택지(제안) 추천: (나′) 빈 칸일 때만 + 해석 검사(위 네 가지 검사에 걸리면 400 `invalid_plan`으로 버리고 캐시에 넣지 않음). 3분 노출은 받아들입니다.

다른 선택 ①: 검사만 하고 "빈 칸일 때만"은 뺌 — 몇 초 사이 경쟁은 드물어 실질 차이는 거의 없음. 다른 선택 ②: 확장 결과는 그 사람에게만(공유 안 함) — 가짜 노출 0이지만 "확장도 캐싱"(AC-10)과 어긋남. 다른 선택 ③: 아무것도 안 함(3분이면 사라짐).

다른 선택 ①: 그대로 둠(3분이면 사라짐). 가장 단순하지만 그 3분 동안 다른 사용자가 가짜를 봅니다. 다른 선택 ②: 확장 결과는 그 사람에게만 보이고 공유하지 않음. 가짜 걱정은 없지만 "다른 사용자도 캐시에서 본다"(명세 AC-10, 사용자 요청 "확장도 캐싱")와 어긋납니다.

7확장 모드에서 「더 보기」(도서관별 다음 쪽)

[안] 결과 카드의 「더 보기」(도서관 하나의 다음 쪽, 지금 /api/v1/availability/libraries/{id}/ebooks, 서버 자리 1개 사용)도 확장 모드에서는 #4의 계획 입구를 그대로 써서 사용자 브라우저가 받아옵니다. 명세에 없던 항목이라 묻습니다.

다른 선택: 「더 보기」만 서버 모드로 둠. 만들 것이 하나 줄지만, 확장 사용자가 더 보기를 누르는 순간 서버 자리를 쓰고 혼잡하면 503을 받아 "내 브라우저에서 조회 중"과 어긋납니다.

8확장이 지키는 동시 수와 시간 제한

[안] 확장은 호스트마다 동시 1건, 앞 요청이 끝난 뒤 1초(명세 #7, 서버와 같음), 한 묶음 안에서 동시에 도는 도서관 수는 서버와 같은 5. 브라우저 fetch는 연결 시간과 읽기 시간을 따로 재지 못하므로 "응답 머리까지 10초, 본문은 묶음 마감(8초)까지"로 서버의 5초·5초를 대신합니다. 리다이렉트는 따라가지 않고 쿠키는 보내지 않습니다.

다른 선택: 머리까지 5초. 서버 값과 같지만 사용자 집 인터넷이 느리면 멀쩡한 도서관도 실패로 보일 수 있습니다.

9사용 기록 source=extension:
제약을 다시 걸고 값 하나 추가

[안] 사용 기록 표 `library_response_daily`의 `source` 제약을 새 changeset으로 지우고 `direct_search`·`holding_fill`·`extension` 셋으로 다시 겁니다(기존 changeset은 고치지 않음). 확장의 검색 조회와 책 화면(소장) 조회는 한 값으로 합쳐 셉니다. 지금 제약에 이름이 없어 실제 이름은 dev가 확인합니다.

다른 선택: `extension_search`·`extension_holding` 둘로 나누기. 더 자세하지만 명세 #13에서 `extension` 하나로 정한 것과 다릅니다.

10「확인하지 못한 도서관」 묶음에
판정 "모름" 줄도 넣기

[안] 맨 아래 묶음(화면 흐름 #7)에는 요청 자체가 실패한 줄뿐 아니라, 상세 조회 시간 초과 등으로 대출 가능 여부 판정이 "모름"(UNKNOWN)으로 끝난 줄도 넣습니다. 명세가 "시간 초과"를 확인 못 한 경우로 함께 들고 있기 때문입니다. 지금 그런 줄은 「대출 가능 여부 확인 필요」로 예약 묶음 맨 아래에 있습니다.

다른 선택: 요청 실패 줄만. 묶음이 작아지지만 "모름" 줄은 지금처럼 예약 묶음에 섞여 거름에서 숨겨집니다.

11확장 꾸러미: 빌드 없이 extension/ 폴더

[안] dev 저장소 맨 위에 extension/ 폴더를 두고, 빌드 도구 없이 파일 그대로 둡니다: manifest.json(MV3, ID 고정용 `key`, 모든 http·https 사이트 권한, 책첵 운영·개발 주소만 `externally_connectable`), background.js(service worker, 호스트 간격 모듈). 압축을 풀어 개발자 모드로 바로 불러옵니다(범위 #6). 시험은 Node 내장 테스트.

다른 선택: Vite·TypeScript로 빌드. 타입 검사가 있지만 빌드 결과물을 불러와야 하고 설정이 늘어납니다. 파일이 몇 개라 과합니다.

12올리는 경로의 nginx 한도:
본문 4MB, 별도 구역 20r/s

[안] 바이트를 올리는 경로(/api/v1/lookup-plans/)에 client_max_body_size 4m(기본 1m)과 JSON 모양의 413 응답을 두고, 요청 수 한도는 일반 `/api/` 구역(사이클 17: 초당 5번, 몰아서 30번)과 따로 초당 20번, 몰아서 60번으로 둡니다. 쪽마다 한 번 올리면 초당 약 5번이라 일반 구역에 딱 걸칩니다. 사이클 17의 운영 nginx 파일과 맞춰 넣습니다.

다른 선택: 일반 구역 그대로. 설정이 없지만 묶음이 빠르게 돌면 429가 나서 확장 모드 검색이 끊깁니다.
