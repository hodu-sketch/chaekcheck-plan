3"이 도서관 조회가 밀려요" 도서관별 표시를 미룰까

어디서 생기나. 상태 응답의 "줄 선 도서관 목록"(HostQueueBoard)은 길·호스트·도서관별로 기다리는 수를 세고, 짝(시작·끝)을 반드시 맞춰야 합니다(어긋나면 "밀려요"가 계속 남는 버그). 그런데 나가는 길이 21개가 되어 같은 도서관도 21건까지 함께 가므로 줄이 거의 서지 않습니다(설계 문서의 사이클 22 맞춤 표).

그림으로: 어느 화면의 어느 요청이고, 서버 안에서 무엇을 하나

"밀려요" 표시는 바로 검색·책 화면 결과 줄에 붙는 한 줄 글(「지금 이 도서관 조회가 밀려요」)입니다. 화면이 10초마다 보내는 상태 요청(GET /api/v1/lookup-status) 응답에 "지금 줄이 선 도서관 번호 목록"(queuedLibraryIds)이 들어 있고, 화면은 그 목록에 있는 도서관의 아직 조회 중이거나 실패한 줄에 이 글을 붙입니다(#5 결정). 서버는 그 목록을 만들려고 도서관 요청이 "차례를 기다리기 시작/끝"할 때마다 숫자를 셉니다 — 이 세는 장치가 HostQueueBoard입니다.

화면 → 상태 요청 → 서버의 HostQueueBoard가 센 "줄 선 도서관"을 돌려줌 → 화면이 그 도서관 줄에 글을 붙임.

HostQueueBoard는 "기다림 시작 +1 / 끝 −1"을 길·도서관마다 셉니다. 길이 21개라 기다리는 일이 드물어, 만드는 품에 비해 보이는 일이 적습니다.

제안: 3단계로 미룸설계대로 지금
화면시간 초과로 실패한 줄에만 "밀려서 확인하지 못했어요" (실패 이유는 지금도 결과에 실려 옴 — 상태 요청 필요 없음)조회 중인 줄에도 미리 "밀려요"
서버세는 장치 없음HostQueueBoard + 상태 응답의 목록
위험없음짝이 어긋나면 글이 계속 남는 버그

[안] 도서관별 "밀려요"는 3단계로 미루고, 지금은 시간 초과로 실패한 줄에만 이유를 붙입니다(이미 받는 실패 정보로).

다른 선택: 설계대로 지금 만듦.

4서버 모드 해석에도 동시 상한 (메모리 지키기)

5운영 감시: 앱이 죽어도 메일이 오지 않는 문제

어디서 생기나. 지금 CloudWatch 경보는 "서버가 꺼짐"과 "디스크 90%" 둘뿐입니다. 앱 프로세스가 죽거나, Cloudflare 터널이 끊기거나, 힙이 차거나, 503이 몰려도 아무 메일이 없습니다. dev에는 Actuator도 없습니다. 이 일은 사이클 17(배포) 몫이라, 정해지면 17에 공유 파일로 넘깁니다.

제안 (비용 거의 0)무엇을 알게 되나
앱이 1분마다 운영 요약 로그 한 줄 (자리 사용, 503 수, 힙, 멈춘 길, 계획 무게, 장부 크기, 확장/서버 요청 수)한 줄로 지금 상태
CloudWatch 에이전트가 그 로그를 보내고 경보 3개: 요약 줄이 5분 없음(앱 죽음), 힙 85% 넘음, 503 급증앱 죽음·메모리·혼잡을 메일로 (무료 경보 10개 안)
메모리 사용 90% 경보, 스왑 파일 1~2GB, PostgreSQL 컨테이너 상한 1GB → 약 512MB2GB 서버 전체가 넘쳐 꺼지는 것 막기

로그 수집 비용은 확인 필요. 사이클 22의 메일 5가지도 같은 길로 보낼 수 있음.

정함 (2026-10-17): 승인 — 사이클 17에 공유 파일 docs/cycles/17-first-deploy/from-cycle-20-observability.md로 넘김(요약 로그 → 경보 3개, 메모리 90% 경보·스왑·PostgreSQL 상한, graceful 종료, cloudflared 재시작). 앱 쪽 1분 요약 로그는 이 사이클 1단계.

[안] 위 네 줄을 사이클 17 인계에 넣도록 공유 파일로 넘기고, 이 사이클 1단계에 앱 쪽 요약 로그를 넣음.

다른 선택: 지금처럼 경보 둘 — 앱이 죽어도 사용자가 알려 주기 전에는 모름.

6도서관 요청에 압축(gzip) 받기

어디서 생기나. 서버가 도서관에 요청할 때 압축을 받겠다는 머리글(Accept-Encoding)을 보내지 않습니다(dev 코드에서 0건). 압축을 받으면 Webshare 데이터와 받는 시간이 몇 분의 일로 줄 수 있습니다(압축률은 재 봐야 함).

정함 (2026-10-17): 승인 + "1MB 넘는 거 잘 기록하고" — 서버 모드 요청에 gzip, 풀었을 때도 1MB 상한. 1MB를 넘어 실패한 도서관은 ① 서버 로그 한 줄(도서관 번호·주소·받은 크기·시각) ② 사용 기록의 실패 이유 body_too_large(도서관별 하루 집계에 셈)로 남기고, 1분 요약 로그에 "1MB 넘음 n건"을 넣어 기준을 올릴지 판단할 근거로 씀.

[안] 서버 모드 요청에 gzip을 받고, 풀었을 때의 크기에도 1MB 상한을 겁니다(압축 폭탄 막기). 압축률은 dev가 도서관 몇 곳에서 재서 기록.

다른 선택: 지금처럼 압축 없이.

7책 화면 "보이는 10권 다 채우기"(#26)에 상한 하나

어디서 생기나. #26으로 책 화면은 줄 상한 없이 묶음을 이어 불러 10권을 다 채웁니다. 소장 도서관이 많은 책이 몰리면 묶음을 여러 번 돌며 검색 자리를 계속 씁니다 — 결과 10개로 줄인 효과를 깎을 수 있습니다.

그림으로: "이어 부르기"가 정확히 무엇인가

화면: 책 기준 검색 결과(책 10권이 나온 목록 화면). 요청: 그 10권의 도서관별 대출 상태를 채우는 GET /api/v1/book-availabilities/stream(첫 묶음)과 GET /api/v1/book-availabilities/batches/stream(다음 묶음). "이어 부르기" = 첫 묶음(최대 8초)이 끝났는데 아직 상태를 못 채운 도서관이 남았을 때, 화면이 사람 조작 없이 다음 묶음 요청을 자동으로 또 보내는 것입니다(#26에서 "보이는 10권 다 채우기"로 정함).

첫 묶음이 못 채운 상태를 화면이 자동으로 다시 요청하는 것이 "이어 부르기"입니다. 제안은 그 횟수를 최대 3묶음(약 24초)으로 묶는 것.

최대 3묶음 (제안)상한 없음 (#26 그대로)

서버검색 하나가 자리를 최대 3번남은 게 있는 한 계속

정함 (2026-10-17): 승인 — 책 화면 이어 부르기는 최대 3묶음, 그 뒤 남은 상태는 「더 보기」. 값은 설정(settings-index에 적음).

10브라우저 번호 장부(5만 줄)가 차면

어디서 생기나. 보안 점검에서: 가정용 IPv6는 /64 주소 묶음을 수백 개 가질 수 있어, "IP당 새 번호 1분 30개"를 피해 몇 분 만에 장부를 채울 수 있습니다. 이때 "찼으면 503 → 서버 모드"로 하면 공격 한 번에 모두의 확장 모드가 꺼집니다.

오래된 줄 밀어내기 (제안)찼으면 503 → 서버 모드
공격 효과거의 없음 — 밀려난 사람은 자동으로 새 번호 받고 다시 계획모두의 확장 모드가 꺼짐
만들 것캐시 기본 동작분기 하나

그림으로: 어느 화면의 어느 요청이고, 장부가 차면 무슨 일이 생기나

화면: 확장이 깔린 PC에서 하는 바로 검색·책 화면(파란 불, 확장 모드). 요청: 그 화면이 보내는 계획 요청(POST …/plans)과 받은 페이지 올리기(POST /api/v1/lookup-plans/{계획}/items/{쪽}). 이 요청마다 브라우저가 "브라우저 번호" 쿠키를 붙이고, 서버는 메모리의 번호 장부(#32: 번호 → 받은 IP·시각·열린 계획)에서 그 번호를 찾아 봅니다. 장부는 최대 5만 줄입니다.

장부가 꽉 찼을 때 오래된 줄을 밀어내면, 밀려난 사람은 화면이 알아서 새 번호를 받아 이어 갑니다. 거절하면 공격 한 번에 모두의 확장 모드가 꺼집니다.

[안] 장부가 차면 오래된 줄부터 밀어냅니다(밀려난 사람은 400 → 새 번호로 조용히 다시 계획). 3단계에 함께.

다른 선택: 찼으면 503 → 그 검색은 서버 모드.

11「더 보기」 계획 주소를 계획 경로 밑으로 옮기기

어디서 생기나. 두 가지가 걸립니다. ① 쿠키는 경로 하나만 가지므로 #33의 번호 쿠키를 경로 4개로 나눠 줬는데, 그중 「더 보기」용 /api/v1/availability/libraries는 서버 모드 「더 보기」에도 쿠키가 붙습니다(MDN Set-Cookie 경로 규칙, 2026-10-17 확인). ② dev nginx에 location ^~ /api/v1/availability/가 있어 정규식으로 잡으려던 「더 보기」 계획 주소가 계획 한도(1분 300)가 아니라 도서관 호출 한도(1분 30)에 걸립니다(nginx 공식 문서 location 규칙).

그림으로: 어느 화면의 어느 요청이고, 무엇이 문제인가

화면: 바로 검색 결과에서 한 도서관 줄의 「더 보기」 버튼(그 도서관의 다음 쪽 결과). 요청: 확장 모드에서 「더 보기」를 누르면 화면이 서버에 POST /api/v1/availability/libraries/{도서관}/ebooks/plans(「더 보기」 계획)를 보냅니다. 다른 두 계획 주소(/api/v1/ebook-searches/plans, /api/v1/book-availabilities/plans)와 올리기(/api/v1/lookup-plans/…)는 경로가 다 다릅니다. 여기서 두 가지 문제가 생깁니다.

「더 보기」 계획 주소만 /api/v1/availability/ 밑에 있어서, 쿠키와 nginx 한도 둘 다 꼬입니다.

[안] 「더 보기」 계획 주소를 POST /api/v1/lookup-plans/more(이름은 dev가 맞춤)로 옮겨 계획 주소를 모두 /api/v1/lookup-plans 밑에 둡니다 — 쿠키 경로 하나, nginx 구역 하나로 둘 다 해결. (설계 결정 #6의 주소 이름을 바꿈)

다른 선택: 주소는 그대로 두고 nginx에 중첩 location을 넣고, 쿠키가 「더 보기」 GET에 붙는 것은 무해로 둠.

12IP 울타리 (3) "잠긴 번호 5개 → IP 10분"을 뺄까

어디서 생기나. 보안 점검에서: (3)은 (1) IP 무게 20%, (2) 새 번호 1분 30개, 번호 잠금이 이미 막는 것과 겹칩니다. 개인 서비스에는 장치가 하나 많고, 같은 IP의 정상 사용자까지 10분 막을 수 있습니다.

정함 (2026-10-17): 승인 — IP 울타리 (3) "잠긴 번호 5개 → IP 10분"을 뺌. 남용은 (1) IP 무게 20%·(2) 새 번호 1분 30개·번호 잠금과 거절 기록으로 봄. 3단계.

[안] (3)을 뺍니다. 남용은 (1)·(2)·번호 잠금과 거절 기록으로 봄. 3단계에 함께.

다른 선택: #31대로 (3) 유지.

13동시 검색 상한 20을 올리기
(사용자 요청, 2026-10-17)

어디서 생기나. 사용자 말씀(웹셰어 세션 경유): "이걸 올리는 게 나을 것 같은데 사이클 20에게 알려줘". 근거는 docs/research/deploy/multi-source-ip.md 10절과 docs/research/deploy/easy/2026-10-17-load-memory-sim.html 6번 카드(어림, 측정 아님): 기본 검색(상세 10개) 기준으로 동시 검색 20이면 나가는 길이 20개여도 초당 약 3~4건에서 503(빨간 불)이 먼저 납니다. 상한을 풀면 한 지역 몰림 초당 16건, 3개 지역 49건까지 길이 버티고, 다음 벽은 힙 512MB(약 초당 100건)입니다. 동시 검색 자리는 서버 모드 바로 검색·책 화면 대출 상태 조회·「더 보기」가 함께 씁니다(dev max-concurrent-searches).

상한초당 검색 (어림, 비례)진행 중 요청의 메모리 (검색당 약 19개 × 약 0.2MB)상태 불 (명세 R1: 절반 노랑, 전부 빨강)
20 (지금)약 3~4약 76MB10 노랑 · 20 빨강
40 (제안)약 6~8약 150MB20 노랑 · 40 빨강
60약 9~12약 230MB30 노랑 · 60 빨강

메모리는 보통 크기 페이지 기준 어림입니다. 1MB 페이지가 몰리는 최악은 #4(해석 자리를 서버·확장 모드가 함께 쓰는 상한 + 메모리 바닥나면 자동 재시작)로 막아야 안전합니다. 상태 불 기준은 명세 R1에 "자리 수가 설정에서 바뀌면 절반·전부도 그에 따름"이 이미 있어 따로 바꿀 것이 없습니다.

질문에 답: 동시 검색 상한은 왜 있고, 다른 것으로 조절할 수 없나

상한이 하는 일은 셋입니다: ① 서버 메모리 보호(진행 중인 도서관 응답을 통째로 메모리에 들고 있으므로), ② 넘치면 바로 「잠시 후 다시」(503)를 줘서 서버가 버티지 못할 만큼 받지 않기, ③ 상태 불의 기준(절반 노랑·전부 빨강). 도서관을 보호하는 건 이 상한이 아니라 길(IP)·사이트마다 "동시 1건·1초" 규칙입니다.

다른 조절 장치지금 있나상한 대신이 되나
도서관마다 동시 1건·1초 (길 21개)있음도서관 보호는 이것이 함. 서버 메모리는 못 지킴
해석 자리 8 (서버·확장 함께, #4 승인)이번에 넣음①의 큰 몫(해석 메모리)을 이것이 맡음 → 검색 상한을 올려도 메모리가 덜 위험해짐
진행 중 도서관 요청 수 상한 (예: 200, 넘치면 1~2초 줄)없음검색 수 대신 "실제로 받는 중인 요청 수"로 묶는 방식. 더 정확하지만 상태 불 기준도 이 숫자로 바꿔야 함
503 대신 1~2초 줄 세우기없음 (범위 밖으로 뺐었음)잠깐 몰릴 때 빨간 불이 깜빡이는 것을 줄임

그래서 #4(해석 자리 8)가 들어가면 검색 상한은 "메모리 보호"보다 "넘치면 바로 거절 + 상태 불 기준" 역할이 커지고, 그만큼 올려도 됩니다. 제안 40은 그대로 두고, 배포 뒤 기록을 보고 "진행 중 요청 수 상한"으로 바꿀지 정하는 것을 다른 선택에 적었습니다.

[안] 동시 검색 상한을 40으로 올립니다(설정값, 환경 변수 CHAEKCHECK_AVAILABILITY_MAXCONCURRENTSEARCHES). #4의 해석 상한·메모리 보호와 함께 넣고, 배포 뒤 힙과 503 기록(#5 요약 로그)을 보고 60까지 올릴지 정합니다. 상태 불은 R1대로 절반(20) 노랑·전부(40) 빨강.

다른 선택: 60으로 바로(메모리 여유가 더 작음), 20 그대로, 또는 검색 수 대신 "진행 중 도서관 요청 수 상한(예: 200) + 1~2초 줄"로 바꾸고 상태 불도 그 숫자로.
