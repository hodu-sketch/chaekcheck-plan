설계에서 빼도 되는 것 세 가지

앞 페이지의 질문(2번 "왜 hidden이 있어?", 9번 고정 공지, 11번 "다시 동의 필요가 없지 않나?")에 답하면서 추천을 "빼기"로 바꿨습니다. 칩만으로는 처음 제안과 바꾼 추천 중 어느 쪽을 고르셨는지 알 수 없어서, 바꾼 추천만 여기 따로 올립니다. 승인 = 뺌, 미승인 = 둠입니다.

1공지 표의 "숨김" 칸

1공지 "숨김" 칸을 빼고, 잘못 올린 공지는 SQL로 지움 [안]

뺀 뒤: 공지 표에는 번호만 남습니다. 잘못 올린 공지는 Claude가 그 공지와 판을 지웁니다(되살리기는 백업에서만). 명세 R4-1의 "지우지 않고 숨김"을 고칩니다.

미승인(둠): 숨김을 "예"로 바꿔 화면에서만 내리고 DB에는 남김.

추천: 뺌. "이전 기록이 보였으면"은 고친 공지의 옛 판 이야기라, 내린 공지를 남기는 것과 다릅니다.

바로잡을 것: "어짜피 리퀴베이스에 기록되니"

운영 중에 Claude가 SQL로 직접 넣거나 지우는 것은 Liquibase에 기록되지 않습니다. Liquibase는 dev 코드 안의 DB 변경 파일(changelog)만 순서대로 실행하고, 그 실행한 파일 목록만 남깁니다. 그 파일은 서버를 새 판으로 올릴 때(배포) 실행됩니다.

넣는 길Liquibase 기록배포 필요쓰는 곳
dev 코드의 DB 변경 파일남음 (파일과 실행 기록)예처음 판(seed) — 이번 설계
Claude가 운영 DB에 SQL 직접 실행안 남음아니요공지 올리기·고치기·지우기, 약관 새 판 — 이번 설계 ("배포 없이"로 정함)

그래서 숨김 칸을 빼고 공지를 지우면, 지운 공지는 DB 백업에만 남습니다. 둘 중 하나를 골라 주세요(이 칩의 기타에).

적어 주실 말뜻
그대로 빼기숨김 칸 없음. 지운 공지는 백업에만 남아도 됨
숨김 두기DB에 남기고 싶으면 숨김 칸을 둠(앞 설계대로)

질문: "그러면 기록용으로 뭐 어떻게 하면 좋아?"

기록을 남기고 싶으시면 "숨김 칸을 두는 것"이 가장 단순합니다. 칸 하나만 있으면, 내린 공지가 제목·본문·모든 판까지 DB에 그대로 남고 화면에서만 사라집니다. 따로 기록하는 일이 없습니다.

방법남는 것더 드는 일
숨김 칸 둠 (추천)내린 공지 전체가 DB에 남음. 되살리기도 칸 하나만 바꾸면 됨칸 하나, "숨긴 공지는 목록·주소에서 안 보임" 규칙 하나
지우기 전에 Claude가 운영 기록 파일에 적어 둠지운 날, 제목, 본문이 파일에 남음DB는 단순하지만, 지울 때마다 파일을 쓰는 절차가 생기고 빠뜨릴 수 있음
지운 공지를 담는 표를 따로 둠지운 공지와 지운 때표가 하나 늘어남 — 이 규모엔 과함
DB 백업만 믿음백업 보관 기간 동안만찾으려면 백업을 되살려야 함

처음에 숨김 칸을 넣었던 이유가 바로 이것이었습니다. 앞에서 "빼기"를 추천한 것은 기록이 필요 없다고 보았기 때문이고, 기록을 원하시면 숨김 칸을 두는 쪽으로 추천을 되돌립니다. 이 칩을 미승인(= 칸을 둠)으로 바꿔 보내 주시면 그렇게 하겠습니다.

질문: "숨김 칸을 두면 나중에 공지가 많아지면 문제고 표를 나눠야겠지만, 지금 단계는 아닌 거지?"

지금 단계에서 나눌 일은 없고, 공지가 많아져도 숨김 칸 때문에 표를 나눌 일은 거의 없습니다(추론).

  • 숨김 칸은 "예/아니요" 한 칸이라 공지 하나에 아주 작은 자리만 씁니다.
  • 목록을 읽을 때는 "숨김이 아니요인 공지"만 고릅니다. 공지가 수천 개가 되어도 이 정도 고르기는 DB가 빠르게 합니다. 느려지는 때가 오면 표를 나누지 않고 "숨기지 않은 공지만 따로 찾는 색인" 하나를 더하는 것으로 충분합니다.
  • 공지가 많아질 때 먼저 손볼 곳은 숨김 칸보다 목록 쪽 나누기(10개씩)인데, 이것은 이미 설계에 있습니다.

그래서 숨김 칸을 두어도 지금 따로 대비할 것은 없습니다. 칸을 두시려면 이 칩을 미승인(= 칸을 둠)으로 보내 주세요.

다시 답: "DB WHERE 절 검색 이야기한 건데"

WHERE NOT hidden이 붙어도 지금은 문제가 없고, 커지면 "숨기지 않은 줄만 담는 부분 색인(partial index)" 하나로 해결합니다. 표를 나눌 필요는 없습니다.

-- 공지 목록 1쪽 (개념) SELECT … FROM sitecontent.notice n JOIN sitecontent.notice_version v … WHERE NOT n.hidden ORDER BY 게시일 DESC LIMIT 10 OFFSET 0;
  • 지금(수십~수백 줄): PostgreSQL은 표 전체를 훑어도(순차 스캔) 순식간에 끝납니다. 색인이 있어도 이 크기면 안 쓰는 경우가 많습니다.
  • 숨김 칸에 보통 색인은 소용이 적음: 대부분의 공지가 "숨김 아님"이라, "숨김 아님"을 찾는 조건은 거의 모든 줄에 맞습니다. PostgreSQL 문서도 "전체 줄의 몇 퍼센트 넘게 맞는 값을 찾는 질의는 어차피 색인을 쓰지 않는다"고 합니다.
  • 커지면: 목록이 실제로 쓰는 정렬 순서(게시일)로, 숨기지 않은 줄만 담는 부분 색인을 만듭니다. 예: CREATE INDEX … ON sitecontent.notice (…) WHERE NOT hidden; 그러면 WHERE NOT hidden … ORDER BY … LIMIT 10이 이 색인에서 앞 10개만 읽고 끝납니다. 문서의 예(청구 안 된 주문만 색인)와 같은 쓰임입니다.
  • 게시일이 공지 판 표(notice_version)에 있어서, 커졌을 때의 정확한 색인 모양은 그때 실제 질의 계획(EXPLAIN)을 보고 정합니다. 지금 정하지 않습니다.

출처: PostgreSQL 공식 문서 "Partial Indexes" https://www.postgresql.org/docs/current/indexes-partial.html (2026-10-13 확인) — "A partial index is an index built over a subset of a table…", "a query searching for a common value … will not use the index anyway". 공지 수와 속도 판단은 추론입니다.
