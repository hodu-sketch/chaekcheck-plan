처리방침에 바깥 업체를
어떻게 적을까

사이클 17(첫 배포)이 물어 온 것입니다. 첫 배포에서 Cloudflare, AWS, 프록시 업체를 쓰게 됩니다. 이들을 처리방침의 "처리 위탁"이나 "국외 이전"에 적어야 하는지 공식 자료로 확인했습니다. 정할 것은 4가지입니다. 법률 자문이 아니라 공개 자료를 읽고 정리한 것입니다.

1사용자의 요청이 지나가는 길

사용자가 책첵을 열면 요청은 Cloudflare(미국 회사)의 망을 지나 서울의 AWS 서버에 닿습니다. 도서관에 대출을 물을 때는 프록시 업체를 지날 수 있습니다.
사용자 브라우저보내는 것: IP 주소, 요청 주소(검색어가 들어 있음)
↓
Cloudflare Tunnel (Cloudflare, Inc., 미국)모든 요청이 지나감. Cloudflare 계약서는 스스로를 "처리자(Processor)"라고 쓰고, IP가 든 기록을 만든다고 씀
↓
책첵 서버 — AWS Lightsail 서울회원 정보와 이용 기록이 들어 있는 DB가 이 서버에 있음. 비밀 값은 AWS Parameter Store 또는 Secrets Manager
↓ 대출 조회
프록시 업체 (아직 안 정함) → 도서관 사이트보내는 것: 검색어만. 사용자 IP·회원 번호·쿠키는 보내지 않음

그림: 빨강 테두리가 국외 회사, 파랑 테두리가 우리 서버입니다. 서버 상태를 재는 Prometheus·Grafana는 우리 서버 안에서 돌고, 개인정보를 넣지 않습니다.

2"위탁"과 "국외 이전"이 무엇인가

남에게 개인정보 처리를 맡기면 "위탁"이고, 맡긴 곳이 외국이면 "국외 이전"도 됩니다. 둘 다 처리방침에 누구에게 무엇을 맡겼는지 적어야 합니다.
구분처리방침에 적을 것근거
처리 위탁맡은 회사(수탁자) 이름, 맡긴 일. "~등"으로 줄이면 안 됨개인정보 보호법 제26조②, 제30조①4호, 작성지침 PDF 44쪽
국외 이전옮기는 항목, 나라·시기·방법, 받는 회사 이름·연락처, 목적·보유 기간, 거부 방법과 거부하면 생기는 일시행령 제31조①2호, 법 제28조의8②, 작성지침 PDF 47~50쪽

위탁이 아닌 경우: 내용을 확인할 수 없이 단순히 전달·통과만 시키는 통신사 같은 경우는 위탁이 아닙니다(개인정보 처리 통합 안내서 PDF 167쪽). 클라우드는 접근권한이 있고 처리에 관여하면 위탁, 물리적 자리만 빌려주면 위탁이 아닙니다(같은 안내서 PDF 182쪽).

동의가 필요한가: 계약을 이행하려고 국외에 처리를 맡기는 경우, 처리방침에 공개하면 동의 없이 할 수 있습니다(법 제28조의8①3호). 위탁 자체에는 동의 요건이 없습니다.

출처(2026-10-13 확인): 국가법령정보센터 개인정보 보호법·시행령, 개인정보보호위원회 작성지침(2026.4.)·통합 안내서(2025.7.)·질의응답 모음집(2025.12.) Q90, Cloudflare Customer DPA v6.4, AWS Data Privacy FAQ. 자세히 research.md 6절.

3업체마다 어떻게 적을까

Cloudflare는 위탁과 국외 이전 둘 다, AWS는 위탁만 적기를 추천합니다. 프록시 업체와 모니터링은 적지 않습니다.

1AWS(서울)는 "처리 위탁"에 적음 (국외 이전은 아님) [안]

예: 처리방침의 위탁 표에 "Amazon Web Services / 서버 운영과 데이터 보관"을 적습니다. 서울 리전이라 국외 이전에는 넣지 않습니다.

AWS 공식 문서는 "고객 동의 없이 콘텐츠에 접근하지 않는다"고 하지만, AWS가 수탁자인지는 밝히지 않습니다. 위탁인지를 가르는 "실질적 접근권한"은 확인하지 못했습니다. 그래서 적어 두는 쪽이 안전합니다. 적어서 생기는 문제는 없습니다.

다른 방법: 물리적 자리만 빌린 것으로 보고 적지 않음. 접근권한이 있다고 판단되면 공개 의무를 어기게 됩니다.
추천: 위탁에 적음. 계약 주체가 AWS의 어느 법인인지는 배포 때 계정에서 확인합니다.

질문: "AWS에서 개인 노트북으로 갈 거긴 한데" — 그러면 어떻게 되나요?

AWS를 쓰는 동안만 위탁에 적고, 노트북으로 옮기는 날 AWS 줄을 뺀 처리방침 새 버전을 넣으면 됩니다.

처음 2주: 서버 = AWS Lightsail 서울처리방침 위탁 표에 AWS 있음
↓ 서버를 집 노트북으로 옮기는 날
처리방침 새 버전(시행일 = 옮기는 날) + 공지 하나위탁 표에서 AWS를 뺌. 이전 버전은 날짜 고르기 칸에 남음
  • 집 노트북은 운영자가 직접 돌리는 서버라 다른 회사에 맡기는 것이 아닙니다. 그래서 서버 보관에 대한 위탁 기재는 필요 없습니다.
  • 대신 처리방침의 "안전성 확보 조치"(시행령 제31조①3호, 반드시 적는 항목)에 노트북을 어떻게 지키는지(접근 통제, 디스크 암호화 등)를 적게 됩니다. 이 문구는 옮길 때 정합니다.
  • 노트북으로 옮겨도 Cloudflare Tunnel은 그대로 쓰므로 2번은 남습니다.
  • 이번 사이클에서 처리방침에 버전을 남기기로 했으므로, 이렇게 바꾸는 것이 SQL 한 번으로 됩니다.

그래서 1번 추천(AWS를 쓰는 동안 위탁에 적음)은 그대로입니다.

질문: "개인 노트북을 어떻게 지키는지도 처리방침에 써야 하나?"

써야 합니다. 다만 "개인 노트북"이라는 기기 이야기나 자세한 설정을 쓰는 것이 아니라, 실제로 하고 있는 보호 조치를 관리적·기술적·물리적 세 갈래로 적습니다. 보안에 해가 될 만큼 자세히 쓸 필요는 없다고 지침이 밝히고 있습니다.

지침이 말하는 것위치
처리방침에 안전성 확보조치를 기재하여야 함 (시행령 제31조①3호)작성지침(2026.4.) 항목 11, 49쪽
"관리적·기술적·물리적 보호조치를 중심으로 실제 수행하고 있는 조치를 기재"같은 쪽
"공개로 인해 개인정보 침해 위협이 증가할 우려가 있는 경우에는 … 표현 수준을 조절하여 기재할 수 있음"같은 쪽

작성지침의 예시는 이런 모양입니다(대기업 기준이라 우리에게 맞는 것만 고름).

물리적전산실·자료보관실 접근통제, 잠금장치, 재해 대비서버 기기를 둔 곳의 접근 제한 등

출처: 개인정보보호위원회 「개인정보 처리방침 작성지침(2026.4. 개정)」 항목 11, 49쪽 (2026-10-13 확인). 지침은 자세한 기준으로 「개인정보의 안전성 확보조치 기준」(고시)과 그 안내서(2025.11.)를 가리킵니다. 그 고시가 노트북 서버에 실제로 무엇을 요구하는지는 아직 확인하지 않았습니다 — 노트북으로 옮기는 때(처리방침 새 버전을 쓸 때) 확인합니다.

그래서 1번 추천은 그대로이고, 노트북으로 옮길 때 "안전성 확보조치" 항목을 그 실제 조치에 맞게 고쳐 씁니다.

질문: "보통 AWS 쓰면 처리 위탁이라고 해?"

실제 서비스 처리방침을 보면 AWS 같은 클라우드를 위탁(보관)으로 적는 곳이 있습니다. 다만 개인정보위 기준은 "늘 위탁"이 아니라 "AWS가 실제로 접근·관여하는지"에 따라 다르다고 합니다.

서비스 (2026-10-13 확인)처리방침에 적힌 것
리디 https://policy.ridi.com/legal/privacy"개인정보 처리업무의 위탁" 국내 표에 AWS — 회원정보, 결제 정보 등 보관. 국외 이전에도 AWS(미국, 재난 대비 국가 간 백업)
당근 https://privacy-policy.daangn.com/국외 이전 항목에 "데이터 보관 및 인프라 운영"을 위해 해외 서비스를 쓴다고 적음. 업체 이름은 본문에 없고 따로 연결된 표에 있음(그 표는 확인 안 함)
토스가져온 페이지에 본문이 없어 확인 못 함

개인정보위 기준(통합 안내서 PDF 182쪽, 질의응답 Q90): 클라우드가 개인정보 처리를 예정하고, 접근권한을 가지거나 처리에 관여하면 위탁입니다. 자리만 빌려주고 접근·관여가 없으면 위탁이 아닙니다. Lightsail은 서버만 빌려주는 형태라 위탁이 아니라고 볼 여지도 있지만, AWS의 접근권한을 공식 자료로 확인하지 못했습니다.

그래서 추천은 그대로입니다. 리디처럼 "AWS — 서버 운영과 데이터 보관"으로 적어 두고, 노트북으로 옮기면 뺍니다.

2Cloudflare는 "처리 위탁"과 "국외 이전(미국)"에 모두 적고, 동의 대신 처리방침 공개로 함 [안]

Cloudflare 계약서(DPA)가 스스로를 처리자라고 쓰고, IP가 든 기록을 만들고, 미국 법인이 받는다고 씁니다. 그래서 단순 통과(통신사)보다는 위탁 + 국외 이전으로 보는 쪽이 안전합니다.

남은 걱정: 동의 없이 하는 근거(법 제28조의8①3호)는 "계약 이행"입니다. 로그인하지 않은 방문자에게도 이 근거가 맞는지는 공식 자료를 찾지 못했습니다(아래 4번).

다른 방법: 단순 통과로 보고 적지 않음. Cloudflare가 스스로 처리자라고 쓰고 있어 맞지 않습니다.
추천: 위탁 + 국외 이전으로 적음.

질문: "이거 해야 해? 클라우드플레어 미국 서버 공유하는 거였어?"

우리 서버가 미국으로 가는 것은 아닙니다. 사용자의 요청이 Cloudflare라는 미국 회사의 망을 한 번 지나서 우리 서버에 오는 구조입니다. 그 회사가 요청을 다루는 동안 IP 같은 기록을 남기기 때문에, 처리방침에 "그 회사에 맡겼다"고 적어야 할 가능성이 큽니다.

사용자 브라우저 (한국)
↓ 가장 가까운 Cloudflare 데이터센터로
Cloudflare 데이터센터 (Cloudflare 목록에 "Seoul, KR" 있음)운영 회사: Cloudflare, Inc. (미국). 요청을 다루며 IP가 든 기록을 남김

우리 서버 (AWS 서울 → 나중에 집 노트북)공인 IP나 열린 포트가 필요 없음

그림: Cloudflare 공식 문서 — cloudflared는 "가장 가까운 Cloudflare 데이터센터"로 바깥 방향 연결을 만들고, 서버는 공인 IP 없이도 됨. Cloudflare 네트워크 목록에 서울 데이터센터가 있음(둘 다 2026-10-13 확인).

질문답확실한 정도
"위탁"으로 적어야 하나적어야 할 가능성이 큼. 남에게 처리를 맡기면 공개해야 하고(법 제26조②), Cloudflare 계약서가 스스로를 처리자라고 씀규칙은 확인, Cloudflare에 적용하는 것은 추론
"국외 이전"으로 적어야 하나애매함. 한국 사용자는 보통 서울 데이터센터를 지날 것으로 보이지만 늘 그런지는 확인 못 함. 다만 받는 회사가 미국 법인이고, 계약서에 다른 나라·하청 회사에서 처리할 수 있다고 적혀 있음추론. 4번 확인 목록에 넣은 것과 같은 문제
안 적으면위탁에 해당한다고 판단되면 공개 의무를 어긴 것이 됨. 많이 적어서 생기는 문제는 찾지 못함추론

Cloudflare를 안 쓰는 길도 있습니다: 그러면 위탁·국외 이전 문제는 사라지지만, 집 노트북을 바깥에 열려면 공인 IP와 열린 포트가 필요해집니다. Cloudflare Tunnel을 쓰는 것은 사이클 17에서 이미 정했습니다.

그래서 추천은 2번 그대로(위탁 + 국외 이전으로 적음)이고, 국외 이전이 꼭 필요한지는 4번처럼 배포 전에 확인합니다.

질문: "보통 Cloudflare 쓰면 위탁·국외 이전 다 표기해? 사용자들이 너무 의심스럽게 보지 않을까?"

그렇게 적는 국내 서비스를 찾았습니다. 다만 Cloudflare를 쓰면서 아무것도 적지 않는 곳이 얼마나 되는지는 알 수 없습니다(처리방침만 보고는 Cloudflare를 쓰는지 모름).

Cloudflare 자신의 한국 이용자 부속서 https://www.cloudflare.com/privacypolicy/southkorea-addendum/Cloudflare도 자기 서비스의 해외 수탁자를 회사·나라·항목·"네트워크를 통한 전송"으로 표에 적음(Cloudflare가 쓰는 업체 이야기라 우리 경우와는 다름)
맘맘, 삼성SDS 처리방침Cloudflare 언급 없음(이들이 Cloudflare를 쓰는지는 모름)

의심스러워 보일까: 이 걱정은 사실로 확인할 수 있는 것이 아니라 판단의 문제입니다. 다만 몇 가지는 말씀드릴 수 있습니다.

  • 처리방침의 위탁·국외 이전 표는 큰 서비스일수록 길게 적습니다. 리디는 AWS를 국외 이전(미국)에까지 적고 있습니다.
  • 적는 문구를 담담하게 쓸 수 있습니다. 예: "웹사이트 요청 전달과 보안 — Cloudflare, Inc.(미국)".
  • 안 적었는데 위탁에 해당하면, 그때는 공개 의무를 어긴 것이 됩니다. 적어서 생기는 법적 문제는 찾지 못했습니다.

그래서 추천은 그대로입니다. 문구는 KED Global처럼 "웹 요청 전달·보안"으로 짧게 쓰고, 나라는 "미국 및 Cloudflare 네트워크가 있는 나라"로 적는 안을 초안에 넣겠습니다(4번 확인과 함께 확정).

3프록시 업체(검색어만 받음)와 자체 모니터링은 적지 않음 [안]

개인정보인지는 받는 쪽이 다른 정보와 쉽게 합쳐 사람을 알아볼 수 있는지로 판단합니다(통합 안내서 PDF 13쪽, 대법원 2019다242045). 프록시 업체는 검색어만 받고 IP·회원 번호를 받지 않아 사람을 알아보기 어렵습니다. 모니터링은 우리 서버 안에서 서버 상태 숫자만 모읍니다.

남는 위험: 사용자가 검색어에 사람 이름 같은 개인정보를 넣는 경우입니다. 업체를 정할 때 나라·계약 조건을 다시 봅니다.

추천: 적지 않음. 프록시 업체를 정하면 다시 확인합니다.

4확인하지 못한 것을 어떻게 다룰까

공식 자료로 끝내 확인하지 못한 것이 셋 있습니다. 첫 배포 전 확인 목록에 넣기를 추천합니다.
확인 못 한 것왜 중요한가
로그인하지 않은 방문자에게도 "계약 이행" 근거로 국외 이전이 되는지안 되면 Cloudflare를 쓰기 전에 동의를 받거나 다른 근거가 필요
Cloudflare 데이터센터가 있는 나라를 모두 적어야 하는지작성지침은 "여러 나라면 모두 기재"라고 함
AWS에 실질적 접근권한이 있는지위탁 여부를 가르는 사실(1번은 적는 쪽으로 정해 영향 작음)

4위 셋을 사이클 17(첫 배포)의 배포 전 확인 목록에 넣고, 개인정보보호위원회 상담 창구 등에 물어 답을 받은 뒤 처리방침을 확정 [안]

처리방침 확정은 이미 "사이클 15가 정해진 뒤"로 미뤄져 있고, 접속 기록 보관 기간도 사이클 17이 정합니다. 그래서 같은 때에 묶어 확정합니다. 묻는 일은 사용자가 하거나, 물을 내용을 Claude가 써 드립니다.
