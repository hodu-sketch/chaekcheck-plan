사이클 16 범위: 공지사항과
안내·약관 글을 DB로

공지사항 페이지를 새로 만들고, 네 가지 글을 DB에 둡니다. 범위에서 아직 정하지 않은 것 7가지를 골라 주세요. 연락처 이메일은 6번의 기타 칸에 적어 주시면 됩니다.

1정해진 것

아래는 대화에서 이미 정한 내용입니다(2026-10-12). 여기서는 고르지 않습니다.
정한 것내용
공지사항 페이지새로 만듭니다.
글을 두는 곳공지사항, 서비스 안내(/about), 이용약관(/terms), 개인정보 처리방침(/privacy) 네 가지 글을 모두 DB에 둡니다. 화면은 서버에서 글을 받아 보여 줍니다. 사용자 말: "B. DB 표 + 읽기 API 이걸로 해주고", "1. 셋 다 DB로"
글 쓰는 법SQL이나 Claude 명령으로 넣습니다. 운영자 페이지는 만들지 않습니다.
같이 할 것연락처 채우기, 약관·처리방침 문구 확정("검토 전 문구" 표시 떼기), 바닥글 링크 한 줄 정리. 사용자 말: "이거 다 할거긴 해"
약관 링크지금처럼 로그인 기능이 꺼져 있으면 약관·처리방침 링크와 페이지가 보이지 않습니다(사이클 05에서 정함). 사용자 말: "로그인 방침에 따라서 다르게 보여야 하는 거 아니야?"

2약관과 처리방침의 버전

약관과 처리방침은 고칠 때마다 새 글을 하나 더 넣고, 옛 글도 지우지 않기를 추천합니다.

까닭: 지금 가입할 때 "이용약관 2026-10-04 버전에 동의했다"는 기록이 남습니다(dev 코드 확인, 2026-10-12). 옛 글을 지우면 그 사람이 무엇에 동의했는지 보여 줄 수 없습니다.

1약관·처리방침은 버전마다 글을 남김 [안]

예: 12월에 약관을 고치면 DB에 "12월 버전" 글이 하나 더 생깁니다. 화면에는 12월 버전이 보이고, 10월 버전 글은 DB에 그대로 남습니다.

다른 선택: 글 하나를 덮어씀. 표는 단순해지지만, 10월에 가입한 사람이 동의한 글을 다시 볼 수 없습니다.

추천: 버전마다 남기기.

2가입 화면이 쓰는 "지금 버전"을 서버 설정 파일에서 DB로 옮김 [안]

지금은 서버 설정 파일(application.yml)에 버전 날짜 2026-10-04가 적혀 있습니다. DB로 옮기면, 새 약관 글을 넣을 때 그 글이 곧 "지금 버전"이 됩니다. 설정 파일을 따로 고치거나 서버를 다시 배포하지 않아도 됩니다.

다른 선택: 버전 날짜는 설정 파일에 두고, 글만 DB에 둠. 로그인 부분(auth)은 바뀌지 않습니다. 대신 글을 넣은 뒤 설정도 고쳐 배포해야 하고, 둘이 어긋날 수 있습니다.

추천: DB로 옮기기. 로그인 부분은 "지금 버전"을 새 글 모듈에게 묻는 한 곳만 바뀝니다.

3서비스 안내와 공지는 버전 없이 고쳐 씀 [안]

예: 서비스 안내 문장을 고치면 DB의 글이 바로 바뀌고, 옛 문장은 남지 않습니다. 동의 기록이 가리키는 글이 아니기 때문입니다.

다른 선택: 네 글 모두 버전을 남김. 구조가 하나로 같아지지만, 공지 오타 하나를 고쳐도 새 버전이 생깁니다.

추천: 버전 없이 고쳐 쓰기.

3약관·처리방침 문구

문구는 Claude가 초안을 쓰고 사용자가 검토하기를 추천합니다. 처리방침은 사이클 15에서 무엇을 기록할지 정해진 뒤에 확정하기를 추천합니다.

4Claude가 초안, 사용자가 검토 [안]

Claude가 법에서 처리방침에 꼭 넣으라는 항목을 공식 자료로 확인합니다. 근거는 개인정보 보호법 제30조, 같은 법 시행령 제31조, 개인정보보호위원회 작성지침입니다(아직 확인 못 함, 명세 단계에서 확인). 그 항목에 맞춰 초안을 쓰고, 사용자가 읽고 고칩니다.

다른 선택: 사용자가 직접 씀. 원하는 문장 그대로 들어가지만, 빠진 항목은 Claude가 따로 확인해 알려 드려야 합니다.

추천: Claude 초안 + 사용자 검토.

5처리방침 확정은 사이클 15에서 기록할 것이 정해진 뒤에 함 [안]

사이클 15(사용자 행동 기록)는 다른 세션에서 조사 중입니다. 검색 기록과, 도서관 사이트로 넘어가는 클릭을 기록하려고 합니다(docs/research/usage-log/storage.md). 무엇을 기록하는지는 처리방침에 적어야 할 수 있습니다. 그래서 15가 정해진 뒤에 문구를 확정합니다. 그 전에는 초안까지만 씁니다.

다른 선택: 지금 확정하고, 15가 끝나면 새 버전을 하나 더 넣음. 일찍 끝나지만 처리방침 버전이 바로 하나 더 생깁니다.

추천: 15가 정해진 뒤 확정.

4연락처

바닥글의 "문의: 준비 중"과 서비스 안내의 "로고 내림 요청 연락처" 자리에 이메일을 넣습니다.

6연락처는 이메일 하나를 두 곳에 같이 씀 [안]

바닥글과 서비스 안내에 같은 이메일을 적습니다. 쓸 이메일 주소는 이 칸의 기타에 적어 주세요. 승인만 누르시면 주소는 나중에 받겠습니다.

다른 선택: 문의용과 로고 요청용을 따로 둠. 주소가 둘 필요합니다.

추천: 이메일 하나.

5다른 사이클과 나란히 하는 법

12·13·14는 dev에서 개발 중이고, 15는 다른 세션에서 조사 중입니다. 겹치지 않게 이렇게 진행하기를 추천합니다.
사이클겹치는 곳이 사이클에서 할 일
13서비스 안내에 "가입 조건 조사 기준일" 한 줄을 넣기로 함그 한 줄을 DB의 서비스 안내 글과 어떻게 합칠지 명세에서 여쭙니다.
14바닥글·머리말을 바꾸는지 아직 확인 못 함설계 전에 14 문서를 확인합니다.
15처리방침 문구, 둘 다 새 DB 묶음을 만듦, ADR 번호처리방침은 5번처럼 합니다. 이름은 15와 겹치지 않게 맞춥니다. ADR 번호는 만들 때마다 다시 확인합니다.

7범위·명세·화면·설계 대안까지 먼저 하고, 설계 확정과 인계서는 12·13·14 회고 뒤에 함 [안]

12·13·14는 아직 개발 중이라 회고를 할 수 없습니다. 특히 13이 서비스 안내 화면을 바꾸므로, 실제로 만들어진 코드를 본 뒤에 설계를 확정합니다. 함께 쓰는 파일(CLAUDE.md, docs/backlog.md, docs/current/)은 고치기 바로 전에 다시 읽습니다. 커밋은 이 사이클 파일만 골라서 합니다.

다른 선택: 설계까지 지금 확정함. 빨리 끝나지만, 13의 실제 코드와 다르면 다시 고쳐야 합니다.

추천: 회고 뒤 확정.
