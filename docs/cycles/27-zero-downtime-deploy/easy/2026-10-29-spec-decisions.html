배포할 때 몇 초를 기다리고, 언제는 배포를 멈추고,
무엇은 지금과 같아도 괜찮은지 정합니다.

사이클 27 명세(spec.md)에서 아직 정하지 않은 것만 모았습니다. dev 코드를 직접 읽어 확인한 내용이 근거입니다. 정할 것은 6개입니다.

먼저: 코드를 읽어 보니

바꿔 끼우는 방법 자체에는 문제가 없습니다. 다만 지금 설정 그대로면 세 군데가 막습니다. 이건 설계에서 고칩니다.

막는 곳지금고치는 방향
자리 이름·포트서비스가 서버 포트 8080을 혼자 잡고, nginx는 이름 하나(backend-host)만 압니다. 둘째 서비스를 띄울 자리가 없습니다.파랑·초록 자리마다 이름을 따로 둡니다(설계).
기다리는 시간Docker는 서비스를 내릴 때 10초만 기다리고 강제로 끕니다. 대출 조회 답은 최대 35초까지 이어집니다.2번 항목에서 정합니다.
준비 확인"다 떴다"를 알려 주는 주소가 서비스에 없습니다. release.sh도 확인 없이 끝납니다.3번 항목에서 정합니다.

좋은 소식: AI 책 찾기에서 이어 묻기는 브라우저가 앞 대화를 매번 같이 보내서, 서비스가 바뀌어도 이어집니다. AI 하루 예산도 DB에 있어 서비스가 둘이어도 맞게 셉니다.

1바뀌는 순간 잠깐 달라지는 것은
그대로 받아들이기

[안] 아래 것들은 서비스마다 따로 기억합니다. 새 판은 처음부터 다시 셉니다. 대부분 지금 배포(내렸다 다시 띄우기)에서도 똑같이 일어나서, 따로 고치지 않습니다.

무엇바뀔 때지금 배포와
막힌 Webshare 길 쉬게 하기새 판은 모름 → 길마다 다시 5번 실패해야 쉼같음
AI 검색 한도 (한 사람 분당 10번·하루 100번)새 판은 0부터같음
검색 결과 캐시새 판은 비어 있어 처음 몇 분 도서관 요청이 조금 늘어남같음
카카오 로그인하는 중이던 사람드물게 "다시 로그인" 화면같음
도서관마다 "한 번에 1개, 1초 간격"옛 판이 하던 요청을 끝내는 최대 35초 동안 잠깐 2개까지새로 생김 (짧음)

다른 선택: 두 서비스가 같이 쓰는 저장소(Redis)를 새로 두기 — 메모리를 더 쓰고 관리할 것이 늘어납니다. 겹치는 시간이 짧아 얻는 것이 적습니다.

2옛 판을 내릴 때
최대 40초 기다리기

[안] 옛 판은 하던 요청을 끝낼 때까지 최대 40초 기다립니다(서비스 설정). Docker는 그보다 넉넉히 60초 기다린 뒤에야 강제로 끕니다.

값왜
40초가장 긴 대출 조회 답이 35초 + 여유 5초. AI 책 찾기 답은 최대 30초.
60초40초 뒤에 이용 기록 마지막 저장 같은 뒷정리가 남아 있어서. 지금 Docker 기본값 10초면 이게 빠질 수 있습니다.

예: 배포 10초 전에 대출 조회를 시작한 사람은 25초 더 답을 받고 끝납니다. 그 사이 새로 들어온 사람은 이미 새 판으로 갑니다.

다른 선택: 30초(서비스 기본값)로 두기 — 35초 걸리는 조회는 끝 5초가 잘릴 수 있습니다.

3새 판 "준비됐다" 확인:
서버 안에서만, 최대 3분 기다리기

[안] 서비스에 준비 확인 주소(/actuator/health/readiness)를 넣습니다. 이 주소는 서버 안에서만 부를 수 있고, chaekcheck.com으로는 열리지 않습니다. 새 판이 3분 안에 준비되지 않으면 실패로 보고 새 판을 내립니다. 사이트는 옛 판 그대로입니다.

3분은 임시 값입니다. 새 판은 시작할 때 책 벡터 80MB와 AI 첫 단계 모델을 읽고, 책 정보 약 7만 7천 줄도 불러옵니다. 실제로 뜨는 데 걸리는 시간을 재 보고 그에 맞춰 줄입니다.

다른 선택: 이미 있는 버전 주소(/api/v1/version)로 확인 — 새로 넣을 것이 없지만, "웹 서버가 떴다"까지만 알고 시작 때 하는 일이 다 끝났는지는 모릅니다.

4새벽 3시 25분 ~ 5시 10분에는
배포하지 않기

[안] 이 시간에 release.sh를 돌리면 배포하지 않고 "정해진 일이 도는 시간"이라고 알립니다.

시각서비스가 하는 일
03:30「나에게 맞는 책」 목록 만들기 (지금은 꺼 둠)
04:00지난 로그인 기록·탈퇴 계정 정리 (카카오에 묻기 포함)
04:30오래된 이용 기록 정리
05:00추천도서 가져오기 (지금은 꺼 둠)

그 순간 서비스가 둘이면 같은 일을 두 번 합니다. 카카오에 묻는 횟수도 두 배가 됩니다.

다른 선택: 두 번 돌지 않게 DB 잠금(ShedLock 등)을 넣기 — 새벽 배포도 되지만, 서비스 코드를 고칠 곳이 늘어납니다.

5메모리가 모자라면
디스크 메모리(스왑)를 두기

[안] 서버 메모리를 잰 뒤, 서비스 둘이 잠깐 같이 떠도 남는 메모리가 넉넉하지 않으면 스왑 파일을 둡니다. 평소에는 거의 쓰이지 않고, 바꿔 끼우는 몇십 초 동안만 씁니다.

무엇메모리
서비스 하나 (dev 문서 실측)약 648MB
바꿔 끼우는 동안 하나 더약 648MB 더
서버 전체 (배포 설정 주석)약 2GB [아직 못 잼]

다른 선택: 서비스 Java 메모리를 640MB보다 줄이기 — AI 책 벡터 80MB 등을 들고 있어서 평소에 모자랄 수 있습니다.

다른 선택: 서버를 한 단계 큰 것으로 — 매달 값이 오릅니다.

6운영자가 보는 것과
더 확인할 것

[안] 명령은 지금과 같은 release.sh 1.21.0. 되돌릴 때 서버에 이미 있는 판이면 다시 만들지 않고 바꿔 끼우기만 합니다. 실패하면 이유와 새 판 로그 마지막 몇 줄을 보여 주고 실패 코드로 끝납니다.

범위에서 정한 확인 넷에 더해, 아래도 끝났는지 볼 때 확인합니다.

더 확인할 것보이면 되는 것
화면만 배포실패 0번이고 첫 화면이 새 화면으로 바뀜
옛 판이 곱게 내려감배포 뒤 서비스가 하나만 돌고, 옛 판 로그 끝이 강제 종료가 아님
이용 기록이 안 빠짐배포 직전 몇 초 기록이 남아 있음
새벽 배포 막힘4번 시간에 돌리면 배포하지 않고 알림
준비 확인 주소 숨김chaekcheck.com/actuator/…가 열리지 않음

아직 재야 하는 것

서버 실제 메모리·스왑과 서비스가 뜨는 시간입니다. 설계는 먼저 쓰고, 설계를 확정하기 전에 잽니다. 서버에서 아래 결과를 보내 주시거나 dev 세션에서 재면 됩니다.
