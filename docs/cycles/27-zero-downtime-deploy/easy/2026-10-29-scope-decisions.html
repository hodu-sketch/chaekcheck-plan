새 판을 올리는 동안에도 사이트가 끊기지 않게,
같은 서버에서 새 판을 먼저 띄우고 바꿔 끼우는 쪽을 제안합니다.

사이클 27(무중단 배포)의 범위를 정하는 페이지입니다. dev의 배포 파일을 직접 읽어 지금 상태를 확인했습니다. 정할 것은 6개입니다. 항목마다 승인·미승인·기타를 골라 주세요.

먼저: 지금 배포하면 왜 끊기나

지금은 옛 서비스를 먼저 내리고 새 서비스를 띄웁니다. 새 서비스가 다 뜰 때까지 들어온 사람은 Cloudflare 오류 화면(502)을 봅니다.

PCrelease.sh→서버로 새 판 전송→옛 서비스 멈춤→새 서비스 뜨는 중이 사이 502→새 서비스

지금 배포 순서입니다. 노란 칸 동안 사이트를 쓸 수 없습니다.

무엇지금
배포 명령PC에서 release.sh를 돌리면 서버의 up.sh가 서비스를 다시 만듭니다.
끊기는 곳서비스(백엔드)와 화면(nginx) 둘 다 컨테이너를 새로 만듭니다.
오래 걸리는 요청대출 조회와 AI 책 찾기는 답을 조금씩 이어서 보냅니다. 배포 순간에 열려 있으면 중간에 끊길 수 있습니다.
메모리서비스 하나가 Java 메모리 640MB를 씁니다. AI 질문 벡터는 따로 있는 임베딩 서버가 맡아서, 이 서버에는 모델 450MB가 올라가 있지 않습니다.

아직 못 잰 것: 서버의 실제 메모리와 서비스가 뜨는 데 걸리는 시간. 이 작업 공간의 보호 규칙이 서버 접속 명령을 막아서 재지 못했습니다. 설계 전에 잽니다.

1방식: 같은 서버에서
새 판을 먼저 띄우고 바꿔 끼우기

[안] 서비스 자리를 둘(파랑·초록) 둡니다. 새 판을 빈자리에 띄우고, 준비됐다는 확인이 오면 nginx가 새 자리로 보내게 바꿉니다. 옛 판은 하던 요청을 끝낸 뒤 내립니다.

바뀌는 순간에도 nginx는 계속 떠 있어서 사이트가 비는 때가 없습니다.

nginx가 보내는 곳을 바꿀 때는 설정만 다시 읽습니다. nginx 공식 문서에 따르면, 이때 옛 일꾼은 하던 연결을 끝까지 처리하고 나서 끝납니다(nginx.org/en/docs/control.html, 확인 2026-10-29). 서비스 쪽(Spring Boot 4.1)은 끝낼 때 새 요청은 받지 않고, 처리 중인 요청은 끝까지 처리하는 게 기본입니다(docs.spring.io graceful-shutdown, 확인 2026-10-29).

조건: 바꿔 끼우는 몇십 초 동안 서비스가 둘 떠 있어서 메모리가 640MB쯤 더 듭니다. 서버 메모리를 재 보고 모자라면, 배포할 때만 쓰는 디스크 메모리(스왑)를 둡니다.

다른 선택 1: 서버 두 대 + 로드밸런서 — 가장 확실하지만 서버와 로드밸런서 값이 늘고, 관리할 것도 늘어납니다.

다른 선택 2: 지금처럼 끊기되 "업데이트 중" 안내 화면과 자동 다시 시도만 넣기 — 가장 간단하지만, 몇십 초 동안 검색이 멈추는 건 그대로입니다.

2화면 판 바꾸기도
끊김 없이

[안] 화면(nginx 컨테이너)은 다시 만들지 않습니다. 새 화면 파일과 설정만 넣고 nginx가 다시 읽게 합니다. Cloudflare Tunnel이 붙어 있는 nginx가 내려가는 순간이 없어집니다.

예: 화면 글자 하나만 고친 판도, 서비스만 고친 판도 똑같이 끊김 없이 올라갑니다.

다른 선택: 서비스만 무중단으로 하고, 화면은 지금처럼 컨테이너를 다시 만들기 — 할 일은 줄지만 화면을 바꿀 때마다 1~2초 끊김이 남습니다(정확한 시간은 재지 않음).

3새 판이 안 뜨면 옛 판 그대로,
되돌리기도 같은 방법으로

[안] 새 판이 준비 확인을 정해진 시간 안에 통과하지 못하면, 바꿔 끼우지 않습니다. 새 판은 내리고 옛 판이 그대로 일합니다. release.sh는 실패를 알립니다. 앞 판으로 되돌릴 때도 같은 바꿔 끼우기를 씁니다.

예: 설정 값을 빠뜨린 판을 올리면, 사용자는 아무 일도 못 느끼고 PC 화면에만 "새 판이 뜨지 않아 옛 판을 유지함"이 나옵니다.

다른 선택: 실패해도 바꿔 끼우고 사람이 되돌리기 — 단순하지만 실패한 판이 사이트에 나갑니다.

4DB 변경 규칙:
옛 판·새 판이 같이 돌아도 되는 것만

[안] 바꿔 끼우는 동안 옛 판과 새 판이 같은 DB를 씁니다. 그래서 DB 변경은 옛 판이 써도 깨지지 않는 것만 무중단 배포로 올립니다. 칸 지우기나 이름 바꾸기는 두 번의 배포로 나눕니다.

하고 싶은 일무중단으로 하는 법
새 칸·새 표 추가한 번에 됩니다. 옛 판은 새 칸을 모르고 그냥 지나칩니다.
칸 지우기1차 배포: 새 판이 그 칸을 안 씀 → 2차 배포: 칸 지움
칸 이름 바꾸기새 칸 추가하고 옮겨 쓰기 → 다음 배포에서 옛 칸 지움

이 규칙을 지킬 수 없는 큰 변경은 "점검 배포"로 따로 합니다. 지금처럼 짧게 내리고, 그동안 점검 안내를 보입니다.

사이클 26은 이미 "한 번에 옮기고, 옛 표는 다음 배포에서 지우는" 방식으로 정해 두었습니다. 이 규칙과 맞습니다.

다른 선택: DB 변경이 든 판은 늘 점검 배포로 — 규칙은 쉽지만, DB를 바꾸는 판이 잦으면 끊김도 잦습니다.

5이번에 하지 않는 것

[안] 서버 두 대와 로드밸런서, GitHub에서 자동으로 배포하기, DB(PostgreSQL)와 Cloudflare Tunnel 프로그램 판 올리기의 무중단은 이번에 하지 않습니다. 이 셋은 백로그에 적어 두었습니다.

DB와 Tunnel 프로그램은 판을 올리는 일이 드물어서, 그때는 점검 배포로 짧게 내립니다.

다른 선택: 자동 배포까지 이번에 같이 — 한 사이클이 커집니다.

6다 됐는지 확인하는 방법

[안] 아래 넷을 직접 보면 끝난 것으로 봅니다.

확인보이면 되는 것
배포 중 계속 불러 보기다른 창에서 1초마다 첫 화면과 버전 주소(/api/v1/version)를 불러도 실패가 0번이고, 버전 숫자가 옛 판에서 새 판으로 한 번 바뀝니다.
열려 있던 검색배포 직전에 시작한 대출 조회와 AI 책 찾기 답이 끝까지 옵니다.
일부러 망가진 판사이트는 옛 판 그대로이고, release.sh가 실패를 알립니다.
되돌리기앞 판으로 되돌릴 때도 첫 줄과 같은 결과가 나옵니다.
