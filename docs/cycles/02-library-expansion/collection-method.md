# 도서관 목록 조사·수집 방법 (재확인용)

도서관 주소, 플랫폼, 보유 수, 가입 자격을 어떻게 모았는지 적은 문서입니다. 운영 중 주소가 바뀌거나 도서관이 새로 생기면 이 순서대로 다시 확인합니다.

- 처음 작성: 2026-09-28 (사이클 02 조사)
- 결과: `research.md`
- 이 문서의 절차와 값은 조사 방법입니다. 서비스 규칙(호출 간격, 캐시 등)은 spec과 ADR을 따릅니다.

## 0. 공통 원칙

- 모든 요청에 우리를 밝히는 User-Agent를 붙입니다. 조사 때는 `chaekcheck-research/0.1 (planning survey)`를 썼습니다. 다른 봇(구글봇 등)인 척하지 않습니다.
- 같은 호스트에는 1초 넘게 간격을 둡니다. 도서관마다 조사 요청은 몇 건 이내로 합니다.
- robots.txt를 먼저 읽습니다. robots.txt가 막고 있는 도서관을 조회 대상에 넣을지는 사용자 결정 사항입니다 (research.md "확인 필요").
- 응답 원문은 조사용 임시 폴더에만 두고 저장소에 넣지 않습니다.

## 1. 도서관 목록 얻기

### 교보

1. 교보문고 디지털도서관 구축 기관 페이지를 받습니다: https://ebook.kyobobook.co.kr/dig/cff/e-library
2. HTML 안의 분류 제목 `<strong class="hidden">공공도서관</strong>`부터 다음 분류(`기업`) 전까지가 공공도서관입니다.
3. 그 구간에서 `<a href="주소" target="_blank">이름</a>`을 모두 뽑습니다. 2026-09-28에 216개였습니다.
4. 주의할 점
   - `http://https://…`처럼 잘못 적힌 주소가 있습니다. 앞의 `http://`를 떼고 씁니다.
   - 이름이 도서관이 아닌 항목(교육청, 시청, 문화회관)도 섞여 있습니다.
   - 공식 페이지 구조가 바뀌면 3번이 깨집니다. 개수가 크게 줄면 구조 변경부터 의심합니다.

## 2. 도서관마다 확인할 것 (순서대로)

도서관 하나에 요청은 2건입니다 (robots.txt 1건, 검색 1건).

| 순서 | 요청 | 보는 것 | 결과 분류 |
|---|---|---|---|
| 1 | `{목록 주소}/robots.txt` (리다이렉트 따라감) | `User-agent: *`가 검색 경로를 막는지 | 막힘 → `ROBOTS_DISALLOW`, 검색 요청을 보내지 않음 |
| 2 | 검색 1건 (아래 URL, 리다이렉트 따라감) | 최종 주소, 결과 줄 수, 전체 건수 | 아래 표 |

검색 URL (검색어는 공백 한 칸 = 전체 건수가 나옴):

- 교보: `{origin}/elibrary-front/search/searchList.ink?schTxt=%20&schClst=all&schDvsn=000&recordCount=10&pageIndex=1`
- YES24: `{origin}/search/?src_key=&sort=title&page_num=1`

결과 분류:

| 분류 | 판정 | 뜻 |
|---|---|---|
| `OK` | 교보 `p.use` 줄이 있음 / YES24 `div.stat`이 있음 | 사이클 01 adapter로 읽을 수 있음. 전체 건수 = 보유 수 후보 |
| `SUBSCRIPTION_API` | 화면에 `api.dkyobobook.co.kr`가 있음 | 교보 구독형. 스크립트로 그리는 화면이라 지금 adapter로는 못 읽음 |
| `ERROR` | 연결 실패, 4xx/5xx | 주소가 없어졌거나 막힘. 3절 참고 |
| `OTHER` | 200인데 결과 줄이 없음 | 다른 시스템이거나 화면 구조가 다름. 사람이 열어 봄 |

**최종 주소를 저장합니다.** 목록에 적힌 `http://호스트:포트`가 `https://호스트:다른포트`로 302 리다이렉트되는 도서관이 많습니다(예: 고창 `:10094` → `:10124`). 서비스 구현은 리다이렉트를 따라가지 않으므로(3xx는 `upstream_error`), `library.base_url`에는 리다이렉트를 따라간 뒤의 origin을 넣습니다.

## 3. 오류가 났을 때 다시 볼 것

- **인증서 문제일 수 있습니다.** 2026-09-28 조사에서 Python과 Git for Windows curl은 일부 사이트(중간 인증서를 보내지 않는 사이트 등)에서 실패했고, Windows 내장 curl은 성공한 경우가 있었습니다. `ERROR`는 다른 클라이언트로 한 번 더 확인하고, 서비스와 같은 JDK로도 확인합니다.
- 404: 주소가 옮겨졌을 수 있습니다. 도서관 본 홈페이지의 "전자도서관" 링크를 다시 따라가 새 주소를 찾습니다.
- 503·시간 초과: 일시 장애일 수 있어 다른 날 다시 봅니다.

## 4. 가입 자격 조사

- 공공데이터(전국도서관표준데이터)에는 자격 항목이 없습니다.
- 교보 전자도서관의 이용 안내(`/elibrary-front/helpDesk/libraryGuide.ink`)는 모든 도서관이 같은 공통 문구라 자격이 없습니다.
- 자격은 **도서관 본 홈페이지의 회원가입 안내**에 있습니다. 다음 순서로 찾습니다.
  1. 운영 기관으로 묶습니다. 교육청, 시·군·구 통합도서관처럼 한 기관이 여러 도서관을 운영하면 규칙이 같은 경우가 많습니다.
  2. "<도서관 또는 운영 기관> 회원가입 자격 / 대출회원 가입 대상"으로 찾아 본 홈페이지 안내를 읽습니다.
  3. 근거(거주·재직·재학·누구나)와 범위(시·군·구 / 시·도)를 `eligibility_rule` 모양으로 적고, 출처 URL과 확인일을 같이 적습니다.
  4. 전자도서관만 쓰는 회원과 대출회원의 자격이 다른 곳이 있습니다(예: 인천교육청은 전자도서관만 쓰면 홈페이지 가입으로 가능하다고 안내). 전자도서관 기준으로 적습니다.
- 찾지 못하면 "자격 미확인"으로 둡니다 (scope [확정]).

## 4-2. 조사 도구에서 겪은 문제

- **Python 기본 TLS 설정으로는 연결되지 않는 도서관 사이트가 많음.** 중간 인증서를 보내지 않는 곳(`unable to get local issuer certificate`, 교보 216곳 중 24곳)과 오래된 TLS 방식만 받는 곳(`handshake failure`, 도서관 포털 다수)이 있음
- **Windows 내장 curl(`C:\Windows\System32\curl.exe`)은 대부분 연결됨.** Git for Windows의 curl은 일부 인증서(강서구 Sectigo R46)에서 실패함
- Git Bash의 `while read` 반복문 안에서 Windows curl을 부르면 전부 실패하거나 제한 시간을 지키지 않는 일이 있었음. Python의 `subprocess`로 curl을 부르면 됨
- 인증서 검증을 끄는 방법은 쓰지 않음. 서비스(JDK)에서도 같은 문제가 날 수 있으므로 개발 때 JDK로 실제 연결을 시험해야 함 (research.md 8절)
- 응답 원문과 조사 스크립트는 조사용 임시 폴더에만 두었고 저장소에 넣지 않음

## 4-3. 가입 자격 조사 기록

- 방법: 운영 기관 이름 또는 도서관 이름 + "전자도서관 회원 가입 자격 / 이용 대상"으로 웹 검색하고, 검색 결과가 가리키는 도서관 공식 페이지 주소를 출처로 적음
- 한계: 대부분 검색 결과 요약으로 확인했으므로 `[확인 필요]`. seed에 넣기 전에 출처 페이지를 직접 열어 확인해야 함
- 지역 규칙이 광역 단위로 같은 경우가 많음: 서울 구립도서관은 "서울 거주·재직·재학"(마포, 서초, 노원), 경기도 시·군 도서관은 "경기도 거주"(고양, 과천, 군포), 부산은 "부산 거주·재직·재학"(부산광역시 전자도서관)
- 자격을 찾지 못하면 "못 찾음"으로 두고, 다른 도서관 규칙으로 추정하지 않음 (사용자, 2026-09-28)
- **원문 확인** (2026-09-28): 검색 요약으로 적은 곳의 출처 주소 151개를 하나씩 열어 자격 문구를 그대로 가져옴
  - 결과: 확인됨 33, 원문이 달라 고침 22, 판단 보류 1(제주), 페이지는 열렸지만 자격 문구 없음 67, 열리지 않음 28
  - 문구가 없던 이유: 전자책 안내 페이지에는 "OO도서관 정회원"만 있고 가입 자격은 회원가입 안내 페이지에 따로 있음. 회원가입 안내 페이지를 다시 찾아 열면 확인되는 경우가 많았음(천안, 양산, 김해, 영주)
  - 열리지 않은 이유: 인증서 오류(중간 인증서 누락·만료), 도메인 없음(주소 바뀜), 404, 연결 거부, 다른 주소로 이동(행정구역·기관 통합: 인천 동구 → 제물포구 `lib.jemulpo.go.kr`, 광주교육청 `lib.gen.go.kr` → `lib.jge.go.kr`, 세종교육청 → `life.sje.go.kr`)
  - 검색 요약이 틀린 예: 강북문화정보도서관(요약 "웹회원이면 누구나" → 원문 "서울 시민·학생·직장인"), 송파구(요약 "서울 또는 경기도" → 원문에서 확인 못 함)
  - 그래서 seed에는 원문 확인된 값만 쓰고, 나머지는 원문을 다시 찾아야 함
- 결과: `eligibility.md`(요약), `eligibility-by-library.md`(전자도서관별 자격과 알아낸 방법)

## 4-4. 같은 플랫폼 안에서도 화면이 여러 세대일 수 있음

2026-09-28 조사에서 본 것입니다. **다른 플랫폼과 새로 넣는 도서관에서도 같은 일이 생길 수 있으니**, 목록을 새로 만들거나 재조사할 때 이 표를 먼저 봅니다.

| 플랫폼 | 지금 방식 (adapter가 읽음) | 옛 방식·바뀐 주소 | 조사 때 결과 |
|---|---|---|---|
| 교보 | `/elibrary-front/search/searchList.ink` | 구독형 `/search/searchList.ink` (앞 경로 없음, 수량 없음) / 옛 경로 `/Kyobo_T3_Mobile` | 구독형은 HTML로 읽힘. `/Kyobo_T3_Mobile`은 404 |
| YES24 | 루트의 `/search/?src_key=` (UTF-8) | 같은 경로지만 **EUC-KR** 화면(한 세대 전) / `…/YES24`, `…/yes24` 경로 / `…/B2B_…` 경로 | EUC-KR 화면은 검색어를 EUC-KR로 보내면 읽힘(12곳). `/YES24`는 대부분 YES24 오류 화면, `/B2B_`는 모두 404 |

- 결과를 못 읽으면 먼저 **응답 인코딩**을 봅니다(`charset=euc-kr`이면 검색어도 EUC-KR로 보냄). 2026-09-28에는 이걸 몰라 12곳을 "결과 못 읽음"으로 잘못 분류했다가 재조사에서 바로잡았습니다.

| 통합 전자도서관 포털 (광역·교육청) | `{포털}/module/elib/search/index.do?menu_idx=10&search_text=` | — | 부산·대구·인천교육청은 읽힘, 경북·전북·경기교육청은 결과 줄 모양이 조금 다름. 여러 업체 책을 한 화면에 보여 주고 보유 수는 없음 (research.md 12절) |

- 옛 YES24·B2B 주소가 404나 오류 화면이면, 그 지역·교육청의 **통합 전자도서관 포털**로 옮겼는지 먼저 봅니다.
- 제3자 목록(웹러브 북스)에는 옛 주소가 그대로 남아 있을 수 있습니다. 404가 나면 도서관 홈페이지의 "전자도서관" 링크에서 새 주소를 찾습니다.
- 목록 주소가 다른 포트의 `https`로 넘어가는 경우가 많습니다(교보 155곳 중 135곳). 최종 주소를 저장합니다.
- 옛 방식 화면이 발견되면 그 화면용 선택자를 따로 조사해 adapter 변형으로 넣습니다 (사이클 02에서 YES24 옛 방식 28곳과 주소가 바뀐 34곳을 포함하기로 함, 사용자 2026-09-28).
- 한 도서관이 여러 플랫폼·여러 세대 사이트를 동시에 운영하기도 합니다(research.md 10절). 도서관 하나에 사이트 여러 개를 붙여 기록합니다.

## 5. 운영 중 다시 확인할 때

바뀐 것을 알아차리는 신호 (서비스 로그에서):

| 신호 | 의심할 것 | 할 일 |
|---|---|---|
| 한 도서관이 계속 `upstream_error` (3xx) | 주소 이전, http→https 전환 | 2절 순서로 최종 주소 다시 확인 |
| 계속 `upstream_error` (파싱 실패) 또는 결과가 늘 0건 | 화면 구조 변경, 플랫폼 교체 | 사람이 열어 보고 adapter 선택자 확인 |
| 계속 `upstream_timeout` | 서버 장애, 우리 요청 차단 | 다른 날 재확인. 차단이면 도서관에 문의 |
| robots.txt 변경 | 운영자 정책 변경 | 1절 규칙에 따라 대상 여부 다시 결정 |

- 정기 재확인은 backlog의 "도서관 정보 주기적 재조사"로 올렸습니다 (사용자, 2026-09-28). 주기는 정하지 않았습니다 [확인 필요]. 목록 전체(1~2절)를 다시 돌리면 교보 216곳 기준 약 400건 요청, 20분 남짓 걸렸습니다.
- 보유 전자책 수(순위에 쓸 값)도 같은 검색으로 얻으므로 재확인 때 함께 갱신할 수 있습니다.
