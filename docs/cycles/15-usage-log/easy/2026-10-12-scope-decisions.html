사이클 15 "검색·도서관 클릭 기록"의 범위입니다. 남은 여섯 가지를 골라 주세요

2026-10-12 · 원본 docs/cycles/15-usage-log/scope.md · 저장할 곳·남길 것·1년 보관은 앞 조사에서 이미 정했습니다.

0이미 정한 것

아래 다섯 가지는 조사 결정 페이지에서 승인하신 그대로 범위에 넣었습니다.
무엇정한 내용
저장할 곳지금 쓰는 PostgreSQL에 기록 칸을 새로 만듦
검색사용자가 검색한 처음 요청만 한 줄. 검색어, 결과 수, 거주·직장 지역, 고른 도서관을 같은 줄에
도서관 클릭링크는 그대로 새 탭으로 열고, "이 도서관 눌렀음"만 따로 우리 서버에 알림. 누르는 곳 여섯 모두
남기지 않는 것회원 번호, IP, 브라우저 식별값
보관1년 지난 기록은 지움

이번에 하지 않는 것: 통계(집계·그래프·운영자 화면), 분석 전용 저장소로 옮기기, 개인정보 처리방침 문구(사이클 16이 씀). 책 상세 열기처럼 검색·클릭 밖의 행동은 다음 단계(명세)에서 넣을지 여쭙니다.

11년 지난 기록은 누가 지우나

서버가 매일 한 번 알아서 지우는 것을 추천합니다.

1서버가 매일 자동으로 1년 지난 기록을 지움 [안]

이렇게 되면: 2026년 10월 20일 기록은 2027년 10월 21일 새벽에 서버가 스스로 지웁니다. 사람이 챙길 일이 없습니다. 법은 보관 기간이 지나면 지체 없이 지우라고 합니다(개인정보 보호법 제21조, 국가법령정보센터, 확인 2026-10-12).

다른 선택: 사람이 가끔 명령으로 지움 → 만들 것은 적지만 잊으면 1년이 넘은 기록이 남습니다.

2기록을 쓰는 방식

앞 조사에서 DB 부담을 줄이려고 말씀드린 방식을 설계의 출발점으로 삼는 것을 추천합니다. 자세한 모양은 설계 단계에서 다시 보여 드립니다.

2검색 응답과 떨어져서, 몇 초마다 묶어, 기록만 비동기 커밋으로 설계 [안]

방식뜻
검색 응답과 떨어져서검색 결과는 먼저 보내고, 기록은 그 뒤에 따로 씀. 기록이 늦거나 실패해도 검색은 그대로
몇 초마다 묶어서서비스 메모리에 모았다가 한 번에 넣음. DB에 가는 횟수가 줄어듦
기록만 비동기 커밋기록을 넣을 때만 디스크 쓰기를 기다리지 않음. 서버가 갑자기 꺼지면 마지막 1초 안쪽이 빠질 수 있지만 DB는 깨지지 않음 (PostgreSQL 문서)
Spring Modulith 이벤트는 안 씀기록 한 줄에 DB 쓰기가 세 번이 되므로 (회원 탈퇴에만 쓰는 기능)

다른 선택: 검색할 때마다 바로 한 줄씩 넣음 → 만들기는 가장 쉽지만, 사람이 몰리면 검색과 DB 연결을 다투고 검색 응답이 기록만큼 늦어집니다.

3다 됐는지 어떻게 확인하나

기록은 화면에 보이지 않으므로, 화면에서 한 행동이 DB에 남는지와 "검색이 느려지지 않았는지"를 확인합니다.

3기록을 켜기 전·후로 검색 속도와 메모리를 재서 비교 [안]

이렇게 되면: dev가 같은 검색을 기록 없이, 기록을 켜고 각각 돌려 응답 시간과 서비스·DB 메모리를 적어 줍니다. 4GB 서버 걱정을 숫자로 확인할 수 있습니다. 얼마나 차이 나면 안 되는지는 다음 단계(명세)에서 정합니다.

다른 선택: 재지 않고 기록이 남는지만 확인 → 일이 줄지만 메모리·속도 걱정은 운영에 올린 뒤에야 알게 됩니다.

4기록은 SQL이나 Claude 명령으로 봄 (화면 없음) [안]

이렇게 되면: "어제 검색 기록 10줄 보여 줘" 같은 요청을 Claude가 SQL로 실행해 보여 드립니다. 보는 화면은 통계 사이클에서 만듭니다. 사이클 16의 공지 넣기도 같은 방식입니다.

다른 선택: 기록을 보는 간단한 운영자 화면을 이번에 같이 → 로그인한 운영자만 들어오게 하는 권한부터 새로 만들어야 해서 일이 커집니다.

4언제까지 무엇을 하나

사이클 16과 같은 방식으로, 지금은 명세·화면·설계 대안까지 하고 설계 확정과 인계서는 12·13·14 회고 뒤에 하는 것을 추천합니다.

5설계 확정과 인계서는 12·13·14 개발이 끝나고 회고한 뒤 [안]

이렇게 되면: 12·13·14가 검색 코드와 결과 줄을 바꾸는 중이라, 그 결과를 본 뒤에 기록을 어디에 끼울지 확정합니다. 그 전에는 명세(무엇을 남기는지), 검색 로봇·가짜 클릭을 거를지, 설계 대안까지 해 둡니다.

다른 선택: 지금 설계를 확정하고 인계서까지 → 빨리 넘길 수 있지만 12·13·14가 바꾼 코드에 맞춰 다시 고칠 수 있습니다.

5서버 안 어디에 만드나

기록만 맡는 새 부분(모듈)을 하나 만들고, 검색 쪽은 그 부분에 "기록해 줘"라고 넘기기만 하는 것을 추천합니다.

6기록 전용 새 모듈 하나 (이름 예: usagelog) [안]

이렇게 되면: 기록 칸, 클릭 알림 받는 주소, 모아서 넣기, 1년 지우기가 한곳에 모입니다. 나중에 기록을 다른 저장소로 옮길 때 이 부분만 바꾸면 됩니다. 웹은 결과 줄·로고·요약 막대의 링크에 클릭 알림을 더합니다. 이름과 자세한 모양은 설계 단계에서 대안과 함께 다시 보여 드립니다.

다른 선택: 검색 모듈(catalog) 안에 기록 칸을 같이 둠 → 모듈은 안 늘지만, 직접 찾기(availability)와 클릭 기록까지 catalog에 들어가 맡은 일이 섞입니다.

6다음 단계에서 여쭐 것 (지금 고르지 않음)

  • 검색 로봇이나 같은 요청 반복이 기록을 채우지 않게 거를지
  • 클릭 알림 주소를 아무나 불러 가짜 클릭을 넣지 못하게 할지
  • 책 상세 열기, 사서 추천 보기도 기록할지
  • 사이클 16이 처리방침에 쓸 수집 항목 목록 넘기기
