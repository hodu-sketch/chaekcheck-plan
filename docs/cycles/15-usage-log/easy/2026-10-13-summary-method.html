1요약을 어떻게 만드나

서비스가 메모리에서 "오늘·이 도서관·이 출처" 칸별로 숫자만 세다가, 5초 묶음 때 DB의 그날 줄에 더하는 것을 추천합니다. 요청 하나하나는 DB에 한 번도 들어가지 않습니다.

1메모리에서 칸별로 세다가 5초 묶음 때 DB 그날 줄에 더함 [안]

이렇게 되면: 다른 기록과 같은 5초 묶음·같은 트랜잭션에 함께 들어가 따로 도는 작업이 없습니다. 메모리 칸은 5초 동안 만난 도서관 수만큼만 생깁니다(많아야 수백 개). 서버가 갑자기 꺼지면 마지막 5초 치 숫자가 빠집니다(다른 기록과 같음).

다른 선택
① 요청마다 임시 표에 넣고 매일 밤 요약을 만든 뒤 지움 → 하루가 끝나야 요약이 생기고, 그동안 요청마다 DB 쓰기가 생겨 "DB에는 요약만"과 어긋납니다.
② 서버 로그를 밤에 읽어 요약 → DB 쓰기는 가장 적지만, 로그 모양이 바뀌면 요약이 깨집니다.

추천 메모리에서 세어 더하기

2무엇을 숫자로 남기나

2평균 대신 "시간 합"과 "가장 긴 시간"을 남기고, 시간은 성공한 요청만 셈 [안]

칸뜻
성공 수, 실패 수, 시간 초과 수, 건너뜀 수건너뜀 = 도서관을 묻지 않고 넘어감 (예: 막힘 신호로 멈춘 도서관)
성공 시간 합 (ms)볼 때 ÷ 성공 수 = 평균
가장 긴 성공 시간 (ms)그날 가장 느렸던 한 번

왜: 평균을 저장하면 5초마다 더할 수가 없습니다(평균끼리 더하면 틀림). 합과 수를 남기면 언제든 정확한 평균이 나옵니다. 실패·시간 초과는 시간이 "정해진 한도"라 평균에 섞으면 흐려져서 성공만 셉니다.

다른 선택: 느린 정도를 더 자세히(예: 1초 안·1~3초·3~5초·5초 넘음 칸) → "대부분 빠른데 가끔 느린지"를 볼 수 있지만 칸이 네 개 늘어납니다. 상위 5% 시간 같은 값은 합으로 만들 수 없어 이 방식으로는 못 남깁니다.

추천 합·가장 긴 시간, 성공만

3"요청 하나"는 도서관 사이트에 실제로 보낸 요청 한 번으로 셈 (다시 시도도 한 번씩) [안]

이렇게 되면: 같은 도서관에 다시 시도한 것도 각각 셉니다. 그래서 "사이트가 몇 번 실패했나"가 그대로 보입니다. 한 도서관에 여러 쪽을 묻는 경우(도서관별 더 보기)도 쪽마다 한 번입니다.

다른 선택: 사람의 검색 한 번에 그 도서관을 한 번으로 셈(다시 시도는 마지막 결과만) → "사람이 본 결과" 기준이 되지만, 사이트가 몇 번 실패했다가 성공했는지는 사라집니다.

추천 실제 보낸 요청 한 번
