1검색 기록 한 줄

세 가지 모두 "검색 한 번을 한 줄로 어떻게 적을지"에 대한 것입니다.

1화면이 보낸 검색 조건을 서버가 받은 그대로 적음 [안]

예 거주 강남구·직장 성남시로 설정한 사람이 제목 "채식주의자"를 최신순으로 찾으면, 기록에 아래 여섯 칸이 한 줄로 남습니다.

검색어는 서버가 앞뒤 공백을 떼고, 여러 칸 공백을 하나로 줄인 뒤의 값을 적습니다. 검색어는 지금도 2~50자만 받습니다. 고르지 않은 값(예: 정렬)은 "기본"으로 적고, 고른 도서관 중 지금은 없는 번호가 섞여 있어도 받은 그대로 적습니다.

왜 이렇게: 다음 사이클에서 "어느 지역 사람이 어떤 조건으로 찾나"를 보려면 조건이 다 있어야 합니다. 승인하신 "지역·도서관도 남기기"를 그대로 따른 것입니다.

다른 선택: 검색어만 적음 → 칸이 줄지만 지역·도서관을 남기기로 한 결정과 맞지 않습니다.

추천 받은 그대로 적기

2결과를 실제로 받은 검색만 세고, 다시 하면 또 한 줄, 0권도 남김 [안]

왜 "다시 하면 또 한 줄"인가: 같은 사람이 다시 한 것인지 알려면 IP나 쿠키가 필요한데, 둘 다 남기지 않기로 했습니다. 그래서 겹친 검색을 거를 수 없습니다.

왜 0권도 남기나: 사람들이 찾다가 못 찾은 책이 무엇인지 알 수 있어서입니다 (제안).

다른 선택: 몇 초 안에 같은 검색을 다시 하면 하나로 침 → 같은 사람인지 알 값이 필요해 "남기지 않는 것" 결정과 부딪칩니다.

추천 위 그림대로

3"도서관에서 직접 찾기"의 결과 수는 첫 묶음이 끝날 때 센 수 [안]

왜 따로 정하나: "도서관에서 직접 찾기"는 우리 DB가 아니라 도서관 사이트에 직접 물어봅니다. 한 번에 다 묻지 않고 도서관을 묶음으로 나눠 차례로 물어서, 처음에는 전체 결과 수를 모릅니다. 대신 서버는 첫 묶음이 끝나면 그 묶음에서 찾은 책 줄 수를 셉니다 (dev 코드 확인, 2026-10-12).

다른 선택
① 결과 수를 아예 비움 → 만들기는 가장 쉽지만 직접 찾기에서 "못 찾음"을 알 수 없습니다.
② 브라우저가 화면에 보인 수를 합쳐 따로 보냄 → 가장 정확하지만 알림이 하나 더 생기고 빠질 수 있습니다.

추천 첫 묶음이 끝날 때 센 수

2로봇과 로그인

기록이 사람이 아닌 것으로 채워지지 않게 하고, 로그인 설정과 상관없이 남기는 것입니다.

4이름에 bot·crawler·spider가 든 요청은 기록하지 않음 [안]

덧붙이신 것에 대한 답: 로봇을 막아 우리와 도서관을 지키려면

도서관 쪽은 이미 지금 코드가 지키고 있습니다. 로봇이 몰릴 때 실제로 터지는 쪽은 우리 서비스(다른 사람의 검색이 막힘)라서, 들어오는 요청을 거르는 작은 장치를 이번에 더하고, 큰 장치(AWS WAF)는 배포 때 보는 것을 추천합니다.

덧붙이신 말: "이와 별개로 우리는 bot crawler spider등을 제한하고 싶어 우리만 터지는 게 아니라 도서관들도 터져서 접속을 안전하게 제한할 방법을 더 알아야 해" (2026-10-13)

지금 이미 있는 것 (dev 코드 2026-10-13 확인)

장치지금 값
① nginx 요청 수 제한직접 찾기·대출 조회 주소만, IP마다 1분에 30번, 동시 6개 (dev deploy/nginx/rate-limits.conf)
② 서버 동시 검색 상한20개 (max-concurrent-searches: 20)
③ 도서관 사이트별 상한한 사이트에 동시 1건, 끝난 뒤 1초 쉬고 다음 (host-max-concurrency: 1, host-min-interval: 1s)
수집 목록 검색(/api/v1/books)제한 없음 (우리 DB만 씀, 도서관에 안 감)
robots.txt, 로봇 이름 거르기없음

그래서 로봇이 몰리면: 도서관에는 ③ 때문에 1초에 한 번 넘게 가지 않습니다. 대신 로봇이 ② 검색 칸 20개를 차지하면, 그동안 사람의 직접 찾기가 거절되거나 ③에서 오래 기다립니다. 막아야 할 것은 "로봇이 우리 검색 칸을 차지하는 것"입니다.

막는 방법들 (공식 문서, 확인 2026-10-13)

방법무엇을 막나조건
robots.txt에 /api/ 금지규칙을 지키는 로봇(Google 등)만. 강제력 없음, 보안 장치가 아님 (Google, RFC 9309)무료, 파일 하나
nginx가 이름(User-Agent)에 bot·crawler·spider가 든 요청을 직접 찾기 주소에서 거절스스로 로봇이라고 밝힌 것. 이름을 속이면 못 막음 (nginx map)무료, 설정 몇 줄
nginx 요청 수 제한을 다른 검색 주소에도IP 하나에서 쏟아지는 요청. IP를 바꿔 가며 오면 약함 (nginx limit_req, 막지 않고 세기만 하는 시험 모드 있음)무료
AWS WAF (요청 수 규칙, Bot Control)이름을 속이는 로봇까지(Bot Control Targeted). 서버에 닿기 전에 거름 (AWS 문서)EC2에 바로 못 붙음. 앞에 CloudFront나 로드밸런서가 필요 (AWS 문서). Bot Control은 추가 요금, 금액 확인 못 함

한국 공식 기관(KISA)의 로봇 차단 지침은 찾지 못했습니다.

추천: 이번 사이클에 robots.txt와 "이름 밝힌 로봇은 직접 찾기에서 거절"만 더하고, AWS WAF는 배포 사이클에서 봅니다. 고르실 칩은 이어서 페이지 #1 (다른 탭).

브라우저와 프로그램은 요청마다 "나는 무엇이다"라는 글(User-Agent)을 함께 보냅니다. 서버가 이 글을 보고 로봇이면 기록을 건너뜁니다. 이 글 자체는 기록에 남기지 않습니다.

근거: Google 검색 로봇은 이름에 "Googlebot"이 들어가고, 페이지의 JavaScript를 실행합니다 (Google 문서, 확인 2026-10-12). 실행하면서 우리 검색까지 부르는지는 문서에 없어 확인 못 함입니다. 운영 뒤 서버 기록으로 봅니다.

다른 선택
① 거르지 않음 → 로봇 검색이 섞여 통계가 흐려질 수 있습니다.
② 이름을 속이는 로봇까지 거름 → IP를 확인해야 해서 일이 커집니다.

5로그인 기능이 꺼져 있어도 기록함 [안]

덧붙이신 것에 대한 답: 로그인 여부는 어떻게 아나

지금 서버는 검색 요청을 받을 때 그 사람이 로그인했는지 모릅니다. 화면이 "로그인함/안 함"을 함께 보내는 것을 추천합니다.

덧붙이신 말: "로그인상태 비로그인상태 이것도 기록해줘" (2026-10-13). 로그인 여부는 "예/아니오" 하나라 회원 번호를 남기지 않기로 한 결정(앞 조사 #4)과 부딪치지 않습니다.

왜 서버가 모르나

추천: 화면이 검색 요청과 클릭 알림에 "로그인함/안 함"을 함께 보내고 서버는 그대로 적습니다. 고르실 칩은 이어서 페이지 #2.

다른 선택: 로그인 기능이 켜졌을 때만 → 지금 운영은 로그인이 꺼져 있어 기록이 하나도 남지 않습니다.

7서버가 알림 값을 확인하고, 이상하면 조용히 버림 [안]

질문에 대한 답: 이상한 값도 기록해 두면 나중에 차단에 쓸 수 있나

IP를 남기지 않기로 해서, 이상한 값을 기록해도 "누가" 보냈는지 몰라 그것만으로는 차단할 수 없습니다. 그래서 이상한 알림은 날짜별·이유별 개수만 남기고, 차단이 필요하면 nginx가 이미 남기는 접속 기록(IP 포함)에서 찾아 막는 것을 추천합니다.
남기는 방법알 수 있는 것드는 것
이유별 개수만 (추천)"10/20 없는 도서관 번호 132건" → 공격이 있었다개인정보 없음
이상한 요청만 IP와 함께 7일"1.2.3.4가 132건" → 바로 그 IP를 막음IP를 남기지 않기로 한 결정을 이 경우만 바꿈, 처리방침에 적어야 함
nginx 접속 기록 (이미 있음)모든 요청의 IP·시각·주소 → 필요할 때 찾아 막음보관 기간을 아직 정한 곳이 없음

이 답은 고르실 수 있게 이어서 페이지(2026-10-13-spec-followup-decisions.html, 캔버스의 다른 탭) #3·#4에 칩으로 올려 두었습니다. 이 항목의 칩(#7)은 "이유별 개수만 + nginx 접속 기록"으로 가실 거면 승인, 다른 길이면 기타로 적어 주세요.

왜 같은 답인가: 일부러 이상한 값을 보내는 사람에게 무엇이 막혔는지 알려 주지 않기 위해서입니다. 링크는 이 알림과 상관없이 이미 열렸으므로 사람이 보는 화면에는 아무 차이가 없습니다.

다른 선택: 잘못된 값이면 오류를 돌려줌 → 개발하며 고칠 때는 편하지만 이상한 값을 보내는 쪽에 힌트를 줍니다.

4가짜 클릭 막기

클릭 알림 주소는 누구나 부를 수 있습니다. 서버의 보안 검사와 요청 수 제한을 어떻게 할지 정합니다.

8클릭 알림 주소 하나만 서버의 보안 검사(CSRF)에서 뺌 [안]

질문에 대한 답: fetch(keepalive)로 하는 건?

됩니다. 그리고 우리 화면에는 이미 CSRF 표시를 붙여 주는 코드가 있어서, fetch(keepalive)로 보내면 보안 검사를 빼지 않고 그대로 둘 수 있습니다. 우리 링크는 새 탭으로 열려 지금 화면이 닫히지 않으므로, sendBeacon만의 장점(화면이 닫혀도 보냄)도 크지 않습니다. 그래서 이 방법이 더 낫다고 봅니다.

fetch(keepalive)란: 화면이 서버에 요청을 보내는 일반 방식(fetch)에 "화면이 닫혀도 요청을 끝까지 보내라"는 옵션을 켠 것입니다. sendBeacon과 달리 표시(헤더)를 붙일 수 있고 서버의 답도 받을 수 있습니다. 보내는 내용은 64KiB까지입니다 (MDN, 확인 2026-10-13).

sendBeacon + 검사에서 뺌 (지금 안)fetch(keepalive) + 검사 그대로
보안 검사이 주소만 예외모든 보내기 요청과 같음, 예외 없음
화면 코드한 줄짜리 보내기이미 있는 CSRF 코드를 씀, 조금 더 김
처음 누를 때요청 1번표시가 없으면 요청 2번
탭을 바로 닫으면보냄keepalive로 보냄
브라우저주요 브라우저 지원Chrome 66, Edge 15, Safari 13, Firefox 133부터 (MDN 호환성 데이터, 확인 2026-10-13). 더 옛 Firefox는 옵션 없이 보통 요청으로 감
로그인 기능이 꺼져 있을 때그대로 됨검사가 없으므로 표시 없이 보냄 (화면이 로그인 기능 상태를 보고 표시 받아 오기를 건너뛰어야 함, 설계에서)

정리: fetch(keepalive)로 가면 "보안 검사 예외"가 아예 없어져 더 단순한 보안 규칙이 됩니다. 이 방법으로 하시려면 #8 칩에서 기타에 "fetch keepalive로"라고 적어 주세요(이 경우 #8의 처음 안은 바뀝니다). 처음 안(검사에서 빼기)으로 가셔도 위험은 없습니다.

질문에 대한 답: CSRF 검사가 무엇이고, 왜 클릭 알림 주소만 빼야 하나

CSRF 검사는 "다른 사이트가 사람 몰래 우리 서버에 무언가를 시키는 것"을 막는 장치입니다. 클릭 알림은 이 검사에 필요한 표시를 붙일 수 없는 방식으로 보내지기 때문에, 그대로 두면 로그인 기능을 켜는 순간 클릭 기록이 하나도 안 남습니다. 클릭 알림은 회원 정보를 바꾸지 않으므로 이 주소만 검사에서 빼도 위험이 없습니다.

1) CSRF 공격이 무엇인가 — 사람이 우리 사이트에 로그인한 상태로 다른 사이트(나쁜 사이트)를 열었다고 해 봅니다.

2) 우리 서버는 어떻게 막고 있나 — 우리 화면만 읽을 수 있는 표시(토큰)를 요청에 붙이게 합니다. 서버는 "보내기" 요청(가입, 내 도서관 저장 등)마다 이 표시가 맞는지 보고, 없으면 거절(403)합니다. 나쁜 사이트는 이 표시를 읽을 수 없어서 흉내 낼 수 없습니다 (Spring Security 문서, dev SecurityConfiguration.java 2026-10-12 확인: 로그인 기능이 켜져 있을 때 모든 보내기 요청에 적용, 예외는 결제 알림 받는 주소 둘뿐).

3) 클릭 알림에서 생기는 문제 — 클릭 알림은 브라우저의 sendBeacon이라는 기능으로 보냅니다. 새 탭이 열리며 화면이 넘어가는 순간에도 알림이 끊기지 않게 해 주는 기능입니다. 대신 이 기능은 요청에 표시(헤더)를 붙일 수 없습니다 (Beacon 명세: "custom request headers"를 넣을 수 없음, 확인 2026-10-12).

4) 빼도 괜찮은 이유

CSRF로 막으려는 것클릭 알림 주소에서는
회원 정보를 몰래 바꾸기 (가입, 내 도서관 저장·삭제, 탈퇴)회원 정보를 읽지도 바꾸지도 않음. 로그인 쿠키도 쓰지 않음
본인인 척 무언가를 시키기할 수 있는 일은 "기록 한 줄 남기기"뿐
나쁜 사이트가 가짜 알림을 많이 보내면?#7 이상한 값은 따로 기록, #9 같은 IP 1분 60번 제한으로 막음

다른 방법(다른 선택)과 비교: sendBeacon 대신 fetch(keepalive)라는 다른 보내기 기능을 쓰면 표시를 붙일 수 있어 검사를 그대로 둘 수 있습니다. 다만 화면이 표시 값을 읽어 붙이는 코드가 더 들고, 지금 운영처럼 로그인 기능이 꺼져 있으면 어차피 검사가 없습니다. 그래서 추천은 "클릭 알림 주소만 검사에서 빼기"입니다. 이해되셨으면 #8 칩에서 골라 주세요.

CSRF 검사란: 로그인 기능이 켜져 있으면 우리 서버는 "보내기" 요청마다 "우리 화면에서 보낸 것"이라는 표시(토큰)를 확인합니다. 다른 사이트가 사람 몰래 우리 서버에 요청을 보내는 것을 막기 위해서입니다 (Spring Security 문서).

문제: 클릭 알림에 쓰는 브라우저 기능 sendBeacon은 이 표시를 붙일 수 없습니다 (Beacon 명세, 확인 2026-10-12). 그대로 두면 로그인 기능이 켜진 뒤 클릭 알림이 모두 거절됩니다.

다른 선택: sendBeacon 대신 표시를 붙일 수 있는 다른 보내기(fetch keepalive)를 씀 → 검사를 그대로 둘 수 있지만, 로그인이 꺼진 지금 운영에서는 어차피 검사가 없고 화면 코드가 조금 늘어납니다.
