질문하신 것의 답: 모듈로 두면 부하가 더 심해지나 — #1 제목 바로 아래 파란 상자

0전체 모양

기록만 맡는 새 부분(모듈) usagelog를 하나 만들고, 검색·책 상세를 처리하는 부분이 "기록해 줘"라고 넘기면, 새 부분이 모았다가 5초마다 DB에 넣습니다.

1검색 기록을 어떻게 넘기나

1usagelog가 공개한 "기록해 줘" 창구를 catalog·availability가 직접 부름 [안]

질문에 대한 답: 따로 모듈로 두면 왔다 갔다 하는 부하가 더 심해지지 않나

심해지지 않습니다. 여기서 "모듈"은 따로 도는 서버가 아니라 같은 프로그램 안의 코드 폴더 구분입니다. 모듈끼리 부르는 것은 같은 프로그램 안의 보통 함수 호출이라 네트워크를 타지 않고, 같은 모듈 안에서 부르는 것과 비용이 같습니다.

근거: 우리 서비스는 Spring Modulith로 만든 "한 덩어리 프로그램(modular monolith)"입니다 (dev CLAUDE.md). Spring Modulith에서 모듈은 한 프로그램 안의 Java 패키지(코드 폴더)이고, 다른 모듈의 공개된 부분을 부르는 것은 일반 메서드 호출입니다 (Spring Modulith 문서, 확인 2026-10-13).

부하가 생기는 경우이번 설계
모듈을 다른 서버로 나눔나누지 않음 (같은 프로그램)
Spring Modulith 이벤트로 넘김 (이벤트마다 DB에 한 줄 적고 지움)쓰지 않음, 함수 직접 호출
호출할 때마다 DB에 씀메모리에 넣기만, 5초마다 한 번 DB

그래도 따로 두는 이유: 기록 규칙(모으기, 5초 넣기, 30일 IP 비우기, 1년 지우기, 클릭 알림 주소)이 한 폴더에 모여, 검색 코드와 섞이지 않습니다. 나중에 기록을 다른 저장소로 옮길 때 이 폴더만 바꾸면 됩니다. "새 모듈 하나"는 범위 단계에서 이미 승인하신 것입니다(scope #6).

이렇게 되면: 수집 목록 검색(첫 쪽)·책 상세·직접 찾기(첫 묶음 끝)에서 각각 한 줄을 넘깁니다. 이벤트 기능(Spring Modulith 이벤트)을 쓰지 않아 DB 쓰기가 늘지 않습니다.

다른 선택
① usagelog가 들어오는 요청을 가로채 스스로 읽음(필터) → 검색 코드를 안 고치지만, 직접 찾기의 결과 수를 볼 수 없어 명세(결과 수, 끊기면 빈 값)를 못 지킵니다.
② catalog·availability가 각자 기록 칸을 가짐 → 모듈 사이 호출은 없지만 모으기·지우기 코드가 세 벌이 되고, catalog 칸은 책 목록을 통째로 바꿔 끼울 때 함께 다뤄져 위험합니다.

추천 공개 창구 직접 부르기

2DB 칸 모양

2기록 종류마다 표를 따로, 값마다 칸을 따로 (표 다섯) [안]

이렇게 되면: "어떤 정렬을 많이 쓰나" 같은 통계를 SQL 한 줄로 셀 수 있습니다. 종류 값은 글자 그대로(예: result_card) 두어 사람이 읽기 쉽고, 지역·도서관 목록은 번호 묶음 칸에 둡니다. 표를 달마다 나누는 일(파티션)은 하지 않습니다(1년 1~2GB 어림, 서버 메모리보다 작음).

다른 선택: 표 하나에 내용을 통째로(JSON) 넣음 → 모양을 바꾸기 쉽지만 값 검사가 없고 통계 SQL이 길어지며, "IP 칸이 30일 뒤 비는지" 같은 확인이 어려워집니다.

추천 표 다섯, 칸 나눔

3IP는 같은 줄의 칸으로 두고, 매일 04:30에 30일 지난 줄의 IP 칸을 비움 [안]

이렇게 되면: 지우기 작업 하나가 ① 30일 지난 IP 칸 비우기 ② 30일 지난 이상한 알림 지우기 ③ 1년 지난 줄 지우기를 차례로 합니다. 하루에 비우는 줄은 30일 전 하루치(수만 줄 어림)라 DB 부담이 작습니다.

다른 선택: IP만 따로 표에 두고 30일 뒤 그 표에서 지움 → 칸 비우기(고쳐 쓰기) 대신 지우기라 깔끔하지만, 표가 하나 더 늘고 IP를 볼 때마다 두 표를 맞춰 봐야 합니다.

추천 같은 줄의 칸

3넣는 방법과 클릭 알림 주소

45초 묶음은 Spring의 묶어 넣기(JdbcTemplate.batchUpdate)로, 기록용 트랜잭션만 비동기 커밋 [안]

이렇게 되면: 5초 동안 모인 줄을 한 트랜잭션으로 넣습니다. 지금 서비스가 DB를 다루는 방식(JdbcClient)과 같은 계열이라 새 도구가 없습니다. 처음에는 DB 연결 설정을 바꾸지 않고, 측정(10%·50MB 기준)에서 느리면 그때 연결 설정(reWriteBatchedInserts)을 켭니다.

다른 선택: 여러 줄을 한 문장으로 직접 조립 → 가장 빠를 수 있지만 SQL을 만드는 코드가 늘고 한 번에 넣을 수 있는 값 수에 맞춰 나눠야 합니다.

추천 batchUpdate

5클릭 알림 주소는 POST /api/v1/library-clicks, 내용은 JSON, 답은 늘 "받았음(204)" [안]

이렇게 되면: 화면이 {"libraryId":12,"place":"result_card","screen":"picks","bookId":345,"loggedIn":false} 같은 내용을 fetch(keepalive)로 보냅니다. 보안 표시(CSRF)는 다른 보내기 요청과 같이 붙습니다. nginx가 이 주소에 IP당 1분 60번 제한을 겁니다.

다른 선택: 주소 이름을 /api/v1/usage/clicks처럼 기록 쪽 이름으로 → 나중에 다른 기록 주소가 생기면 묶기 쉽지만, 지금은 하나뿐입니다.

추천 /api/v1/library-clicks

4이름과 IP 읽는 곳

6새 모듈과 DB schema 이름은 usagelog [안]

이렇게 되면: 코드 폴더 com.chaekcheck.usagelog, DB usagelog.search_event 등. 사이클 16의 sitecontent와 겹치지 않습니다. 둘 다 DB 변경 목록 파일 끝줄을 고치므로 합칠 때 순서만 확인합니다.

다른 선택: activity, analytics → 뜻이 넓어 나중에 통계 계산까지 이 이름에 들어갈 수 있습니다. 통계는 다음 사이클에서 따로 정합니다.

추천 usagelog

7IP는 nginx가 넘겨주는 X-Real-IP에서 읽고, 사이클 17 배포 설정과 맞춤 [안]

이렇게 되면: 서비스는 nginx가 이미 붙여 주는 X-Real-IP만 읽습니다. 그 값이 진짜 사용자 IP가 되는 것은 사이클 17의 nginx 설정에 달려 있어, 설계 확정 때 17 설정을 확인합니다.

다른 선택: 서비스가 CF-Connecting-IP를 직접 읽음 → nginx 설정과 무관하지만, Cloudflare를 거치지 않는 요청(로컬·시험)에서는 값이 없고, 누구나 이 머리글을 꾸며 보낼 수 있어 nginx에서 정리된 값보다 믿기 어렵습니다.

추천 X-Real-IP + 17과 맞춤
