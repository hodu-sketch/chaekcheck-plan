?질문에 대한 답: 보통 서비스에서 이렇게까지 기록하나

네, 남기는 행동의 종류는 보통 수준입니다. Google Analytics는 켜기만 해도 페이지 보기·스크롤·바깥 링크 클릭·사이트 검색 결과 보기 등을 저절로 기록합니다. 우리가 보통보다 더 하는 것은 하나, IP를 30일 남기는 것입니다.
우리가 남기는 것Google Analytics 4가 저절로 남기는 것 (향상된 측정)
검색 (처음 요청)사이트 검색 결과 보기 (view_search_results)
도서관 링크 누르기바깥 도메인 링크 클릭 (click, outbound)
책 상세·사서 추천 보기, 더 보기페이지 보기 (page_view, "끌 수 없음"), 스크롤
지역·내 도서관 바꾸기폼 시작·제출 (form_start, form_submit), 그 밖은 직접 정한 이벤트로 흔히 남김
도서관 응답 결과·시간(사용자 행동이 아니라 운영 기록. 서비스가 바깥 사이트 응답을 지켜보는 일은 보통 따로 함)

출처: Google Analytics 도움말 "향상된 측정 이벤트" (support.google.com/analytics/answer/9216061, 확인 2026-10-13). 페이지 보기는 "자동으로 수집되며 끌 수 없다"고 적혀 있습니다.

보통보다 더 하는 것: IP — Google Analytics는 EU·스위스·영국 사용자의 IP를 "기록하거나 저장하지 않고" 대략적인 위치를 알아낸 뒤 버린다고 밝힙니다 (Google 도움말, 확인 2026-10-13, 다른 지역은 이 페이지에 없음). 우리는 IP를 30일 남기기로 했습니다(이상한 요청 차단, 같은 사람 흐름 보기). 그래서 처리방침에 적고(사이클 16), 30일 뒤 비우는 것입니다.

정리: 남기는 행동의 양은 흔한 수준이라 이대로 가도 됩니다. 아래 여섯 가지는 그 만드는 방법을 고르는 것입니다. 기록을 줄이고 싶으시면 해당 칩에서 미승인으로 알려 주세요.

1화면이 보내는 알림

도서관 클릭에 더해 사서 추천 보기, 지역·내 도서관 바꾸기도 화면이 알림을 보냅니다. 받는 주소를 하나로 합치는 것을 추천합니다. 앞서 정하신 주소 이름(#5 /api/v1/library-clicks)을 바꾸는 안입니다.

1화면 알림은 한 주소 POST /api/v1/usage-events로 받고, 내용에 종류를 적음 (#5의 주소 이름을 바꿈) [안]

이렇게 되면: {"type":"library_click","libraryId":12,…}, {"type":"region_change",…}처럼 보냅니다. 늘 "받았음(204)"으로 답하는 것과 fetch(keepalive)·CSRF는 그대로입니다. nginx 설정도 주소 하나에만 겁니다.

다른 선택: /api/v1/library-clicks는 그대로 두고 /api/v1/screen-events를 더함 → 앞서 정한 이름을 지키지만, 주소마다 nginx 한도·검사를 두 번 둡니다.

추천 한 주소

2로그인한 뒤의 지역 저장·내 도서관 넣기·빼기도 화면 알림 하나로 기록 (서버 저장 코드는 안 고침) [안]

질문에 대한 답: 지역·내 도서관은 지금 로그인 전/후 어떻게 저장되나

로그인 전에는 브라우저에만 저장되어 서버가 모릅니다. 로그인한 뒤에는 서버에도 저장됩니다. 그래서 "화면 알림 하나"로 하면 두 경우를 같은 길로 기록할 수 있습니다.
화면 알림 하나 (추천)로그인 뒤는 서버가 직접
만들 길하나둘 (로그인 전 화면 알림 + 로그인 뒤 서버)
내 도서관 모듈안 고침기록 모듈을 부르게 고침
광고 차단 시빠질 수 있음로그인 뒤는 빠지지 않음

왜 묻나: 로그인한 사람의 지역·내 도서관은 서버에도 저장되므로(PUT /api/v1/me/regions, /api/v1/me/libraries/…, dev 확인), 서버가 저장할 때 직접 기록할 수도 있습니다. 로그인 전 지역은 브라우저에만 저장돼 화면 알림이 필요합니다.

이렇게 되면: 로그인 전후 모두 같은 길(화면 알림)이라 만들 것이 하나입니다. 내 도서관 모듈(mylibrary)은 고치지 않습니다.

다른 선택: 로그인한 사람은 서버가 저장할 때 기록 → 광고 차단에도 빠지지 않지만, 내 도서관 모듈이 기록 모듈을 알게 고쳐야 하고(지금 허용된 의존: auth·library·region) 길이 둘이 됩니다.

3사서 추천 보기·지역/내 도서관 바꾸기는 표 하나(screen_event)에 종류별 칸을 두고 씀 (JSON 칸 없음) [안]

종류채우는 칸
사서 추천 목록 보기분야
추천 책 창 열기분야, 책 번호
지역 바꾸기거주 지역들, 직장 지역들
내 도서관 넣기 / 빼기도서관 번호, 넣기·빼기

이렇게 되면: 앞서 고르신 "값마다 칸을 따로"(설계 #2)를 지키면서 표는 하나만 늘어납니다. 종류에 맞지 않는 칸은 비워 둡니다(DB가 규칙으로 검사).

다른 선택: ① 종류마다 표를 따로(셋) → 가장 깔끔하지만 표가 열 개가 됩니다. ② 표 하나 + 내용은 JSON 칸 → 새 종류를 더하기 가장 쉽지만, 앞서 피하기로 한 방식입니다.

추천 표 하나, 종류별 칸

4더 보기 기록(search_more)에도 검색 기록과 같은 조건 칸을 모두 둠 [안]

왜: 검색과 더 보기를 잇지 않기로 했으므로(#10), 더 보기 줄만 보고도 "어떤 검색에서 더 보기를 눌렀나"를 알려면 검색어·범위·지역·도서관이 그 줄에 있어야 합니다. 이 값들은 더 보기 요청에도 실려 옵니다.

다른 선택: 검색어와 몇 번째만 → 칸이 적지만 지역·범위별로 더 보기를 나눠 볼 수 없습니다.

추천 같은 조건 칸

3도서관 응답 기록은 양이 많습니다

직접 찾기 한 번에 도서관마다 한 줄이 생겨, 다른 기록보다 훨씬 빨리 쌓입니다. 범위와 보관 기간을 따로 정하는 것을 추천합니다.

5도서관 응답은 첫 묶음뿐 아니라 다음 묶음·더 보기까지 모든 도서관 요청을 남김 [안]

질문에 대한 답: 직접 찾기 말고도 도서관에 묻는 곳의 응답 기록은?

우리 서버가 도서관 사이트에 묻는 곳은 직접 찾기 말고 하나 더 있습니다: 책 페이지·수집 목록 결과·사서 추천 창에서 "대출 수 채우기". 둘 다 같은 도서관 조회 코드를 지나므로 함께 남기는 것을 추천합니다. 수집기(책 목록 수집)는 서비스가 아니라 따로 도는 프로그램이라 이번 기록에 넣지 않습니다.
도서관에 묻는 곳지금 결정추천
직접 찾기 (첫·다음 묶음, 도서관별 더 보기)남김 (#5 승인)그대로
대출 수 채우기 (책 페이지, 수집 목록 결과, 사서 추천 창)빠져 있었음함께 남김 — 같은 표, "어디서 물었나" 칸으로 구분
수집기의 책 목록 수집해당 없음남기지 않음 (사이클 13에서 수집기가 dev로 옮겨지며 자기 실행 기록을 가짐)

양: 대출 수 채우기는 결과에 보이는 도서관마다 묻기 때문에 도서관 응답 기록이 더 늘어납니다. 그래서 #6의 "90일 보관"이 더 의미가 있습니다.

이대로 하시려면 #5 칩을 다시 눌러 기타에 "대출 수 채우기도"라고 적어 주세요(또는 채팅으로). 직접 찾기만으로 두셔도 됩니다.

이렇게 되면: "어느 도서관이 자주 응답하지 않나, 느린가"를 빠짐없이 봅니다(운영 목적). 사람을 알아보는 값은 없습니다.

다른 선택: 첫 묶음만 → 양이 줄지만 뒤 묶음에서만 묻는 도서관은 볼 수 없습니다.

추천 모든 도서관 요청

6도서관 응답 기록은 90일만 보관 (다른 기록은 1년 그대로) [안]

질문에 대한 답: 대출 수 채우기 같은 바깥 요청까지 보통 수집하나

바깥 사이트 요청의 성공·실패·걸린 시간을 지켜보는 것은 보통 합니다. 다만 보통은 요청 하나하나를 DB에 남기기보다 "몇 번 성공·실패, 평균 몇 초" 같은 집계 숫자(지표)로 모읍니다. 우리처럼 요청마다 DB에 한 줄 남기는 것은 그보다 자세한 편입니다.
방법보통 쓰는 곳근거
집계 지표 (횟수·시간·실패 수)대부분의 서비스. Spring Boot도 HTTP 요청 지표를 기본으로 만듦Spring Boot는 RestTemplate·WebClient·RestClient 요청을 http.client.requests 지표로 기록 (Spring Boot 문서, 확인 2026-10-13). 사이클 17이 Prometheus를 띄움
요청마다 한 줄 (지금 고른 것)문제 추적이 필요할 때—

지표로만 하면 생기는 문제: 도서관이 2,400곳이 넘어 "도서관마다" 숫자를 따로 두면 Prometheus 지표가 매우 많아집니다. Prometheus는 사용자 ID처럼 값 종류가 많은 것을 라벨로 쓰지 말라고 안내합니다 (Prometheus 문서: "Do not use labels to store dimensions with high cardinality"). 그래서 지표로는 "업체별"까지만 보고, "어느 도서관이"는 DB 기록으로 보는 것이 맞습니다.

안"어느 도서관이 자주 실패하나"양
요청마다 한 줄, 90일 (지금 #5·#6)볼 수 있음, 요청 하나까지가장 많음
도서관마다 하루 한 줄 요약 (성공·실패·시간 초과 수, 평균·가장 긴 시간), 1년볼 수 있음, 하루 단위하루 많아야 도서관 수만큼 (수천 줄)

제 생각: "어느 도서관이 문제인가"가 목적이면 하루 요약으로도 충분하고, 양이 훨씬 적어 1년을 둘 수 있습니다. 요청 하나하나를 보고 싶은 때는 서버 로그가 있습니다. 지금 #5(요청마다)는 승인하신 상태라, 바꾸시려면 #6 칩의 기타에 "하루 요약으로"라고 적어 주세요. 그대로 두시려면 #6을 승인하시면 됩니다(요청마다, 90일).

이렇게 되면: 사이트가 요즘 응답하는지 보는 데는 최근 몇 달이면 충분하고, 4GB·40GB 서버의 디스크를 아낍니다. 매일 04:30 지우기에서 함께 지웁니다.

다른 선택: ① 1년 그대로 → 규칙이 하나지만 가장 큰 표가 1년 쌓입니다. ② 원본은 30일, 하루 도서관별 요약(성공·실패 수, 평균 시간)은 1년 → 오래 볼 수 있지만 요약을 만드는 작업이 하나 더 생깁니다.
