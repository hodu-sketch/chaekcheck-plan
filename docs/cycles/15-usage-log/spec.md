# 기능 명세: 사용자 행동 기록 (검색·도서관 클릭)

- 범위: `scope.md` 포함 1~6. 결정 근거 `docs/research/usage-log/storage.md` 6절
- dev 코드 확인 2026-10-12 (아래 경로는 dev `backend/src/main/java/com/chaekcheck/` 또는 `web/src/` 기준)

## 사용자 이야기

- 운영자(사용자 본인)는 사람들이 어떤 책을 어떤 조건으로 찾는지 기록으로 남기고 싶다, 다음 사이클에서 통계를 내기 위해 (사용자: "나중에 통계에 쓸까 해", 2026-10-12)
- 운영자는 검색 결과에서 사람들이 어느 도서관으로 넘어가는지 남기고 싶다, 어느 도서관이 실제로 쓰이는지 보기 위해 [이유 미확인: "도서관 페이지를 클릭할 때 정보를 기록"까지만 말함]
- 검색하는 사람은 기록 때문에 검색이 느려지거나 링크가 늦게 열리지 않기를 바란다 (사용자의 4GB 메모리·DB 부담 걱정, 2026-10-12)

## 동작 규칙

### R1. 검색 기록

- R1-1 남기는 때: 수집 목록 검색(`GET /api/v1/books`)은 `page`가 1이거나 없을 때 [확정] (scope 포함 2). 직접 찾기는 첫 묶음 주소(`GET /api/v1/ebook-searches/stream`)일 때만, 다음 묶음(`…/batches/stream`, `batchNo` ≥ 2)과 도서관별 더 보기(`/api/v1/availability/libraries/{id}/ebooks`)는 남기지 않음 [확정] (같은 곳)
- R1-2 잘못된 요청(400·422)과 요청 수 제한(429)은 남기지 않음 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #2). 사람이 실제로 결과를 받은 검색만 셈
- R1-3 같은 검색을 다시 하면(새로고침, 다시 누르기) 다시 한 줄 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #2). 같은 사람인지 알 값이 없으므로(결정 4) 겹침을 거르지 않음
- R1-4 직접 찾기의 결과 수: 직접 찾기는 전체 결과 수가 한 번에 정해지지 않음(묶음마다 도서관에 물어봄, `availability/internal/web/StreamEvents.java:30-42,97-127`). 첫 묶음이 끝날 때 서버가 센 "찾은 책 줄 수"(`BatchDone.countedRows`)를 결과 수로 남기고, 그 전에 사용자가 떠나면 빈 값 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #3). 그래서 직접 찾기 기록은 요청을 받은 때가 아니라 첫 묶음이 끝나거나 끊긴 때 한 번 남김(시각은 요청을 받은 때)
- R1-5 검색 로봇 거르기: User-Agent에 `bot`·`crawler`·`spider`가 들어 있는 요청은 기록하지 않음 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #4). 덧붙임 (사용자: "이와 별개로 우리는 bot crawler spider등을 제한하고 싶어 우리만 터지는 게 아니라 도서관들도 터져서 접속을 안전하게 제한할 방법을 더 알아야 해") → 조사 결과(지금 이미 도서관 사이트마다 동시 1건·1초 간격, 서버 동시 검색 20, 직접 찾기 nginx IP당 1분 30번; dev 설정 2026-10-13 확인. **고침 2026-10-13**: 이 "도서관 사이트마다 1초에 한 번"은 나가는 IP가 하나일 때만 맞음. ADR-0095(제안됨)로 대출 조회가 업체 프록시 여러 곳을 거치면 "나가는 IP 수만큼 1초에 한 번"이 되고, 교보 구독형 서버는 IP마다 동시 3건(ADR-0094, 제안됨). 근거 `docs/research/deploy/to-cycle15-2026-10-13.md` 2·3절) 뒤 결정: "이번 사이클에 robots.txt와 \"이름 밝힌 로봇은 직접 찾기에서 거절\"만 더하자" [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #4)
- R1-7 robots.txt: `/api/`를 크롤러에 금지 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #4). 강제력은 없고 규칙을 지키는 크롤러만 따름 (https://developers.google.com/search/docs/crawling-indexing/robots/intro , https://www.rfc-editor.org/rfc/rfc9309.html , 확인 2026-10-13). 파일 위치·내용 [안: 웹 `public/robots.txt`에 `User-agent: *` / `Disallow: /api/`]
- R1-8 nginx가 User-Agent에 `bot`·`crawler`·`spider`가 든 요청을 직접 찾기·대출 조회 주소(지금 요청 수 제한이 걸린 두 location)에서 서버에 넘기기 전에 거절 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #4). 응답 코드 [안: 403] (https://nginx.org/en/docs/http/ngx_http_map_module.html , 확인 2026-10-13). AWS WAF(이름을 속이는 로봇까지)는 배포 사이클로 [확정] (같은 발언, backlog). **2026-10-13 사이클 17 전달로 바뀐 전제**: 처음 2주 운영 서버는 EC2가 아니라 AWS Lightsail 서울 4GB이고 앞에 Cloudflare Tunnel을 둠 [확정: 17]. 17은 AWS WAF를 범위에서 뺐고(Lightsail 앞에 바로 붙지 않을 수 있음, 확인 안 함), Cloudflare 무료 요청 한도 규칙(1개, IP 기준, 10초 단위, https://developers.cloudflare.com/waf/rate-limiting-rules/ , 17 확인 2026-10-12)으로 대신할지 17에서 다시 봄 (`docs/research/deploy/to-cycle15-2026-10-13.md`) User-Agent 자체는 남기지 않음(결정 4). Google 검색 로봇은 화면의 JavaScript를 실행함 [확정] (https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics, 확인 2026-10-12)이지만, 실행 중 검색 API까지 부르는지는 문서에 없음 [확인 필요: 운영 뒤 서버 로그]
- R1-6 로그인 기능이 꺼져 있어도 기록함 (검색은 로그인 없이 되므로) [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #5). 덧붙임 (사용자: "로그인상태 비로그인상태 이것도 기록해줘"): 검색·클릭 기록에 로그인 여부를 남김 [확정]. 방법: (바뀜 2026-10-14) 서버가 로그인 쿠키로 직접 확인 [확정] (사용자: #5 미승인 "서버가 로그인 쿠키로 직접 확인", `easy/2026-10-14-remaining-proposals.html`). 로그인 쿠키(`access_token`) 경로를 `/api/v1`로 넓힘 [확정] (사용자 승인, 2026-10-14, `easy/2026-10-14-login-cookie.html` #1). 서명이 맞으면 만료됐어도 "로그인함", 서명이 틀리거나 없으면 "안 함" (기록에만 씀, 권한과 무관) [확정] (사용자 승인, 2026-10-14, `easy/2026-10-14-login-cookie.html` #2). 검색·책 상세·사용 알림은 계속 로그인 없이 되고 쿠키 확인 실패는 오류가 아님 [확정] (사용자 승인, 2026-10-14, `easy/2026-10-14-login-cookie.html` #3). 덧붙임 (사용자: "이 서비스 로그인 한거 안한거 분류되도록 해야 하니까 그거 주의해서 설계해야 해 / 로그인 안 쓰기 설정이 되어 있으면 체크 안 하게 / 이거 코드 안 더러워지도록 … 한 데 모아서 관리하거나 관리하는 부분을 정해서 했으면 해"): 로그인 기능이 꺼져 있으면 쿠키를 확인하지 않음 [확정], 판별을 맡는 곳·칸 값은 `easy/2026-10-14-login-status.html` [확인 필요: 사용자에게 질문]. (처음 결정: 화면이 검색 요청과 클릭 알림에 "로그인함/안 함"을 함께 보내고 서버는 그대로 적음) (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #5) (사용자: "이렇게 해줘"). 지금 로그인 쿠키는 `/api/v1/me`로만 가서 서버는 검색 때 로그인 여부를 모름 (dev `AuthCookies.java:9`). 로그인 기능이 꺼져 있으면 늘 "안 함". 화면이 로그인 상태를 아직 확인 중일 때(첫 응답 전)나 확인에 실패했을 때 한 검색·클릭은 "모름"(빈 값) — 칸은 함/안 함/모름 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-13-check-results.html` #1). 덧붙임 (사용자: "로그인 기능 on/off인 경우 모두 되게 개발해야 해"): 검색·책 상세·클릭 기록 모두 로그인 기능이 켜진 경우와 꺼진 경우 둘 다 동작해야 함 [확정] — 꺼짐 때 클릭 알림은 CSRF 표시 없이 보냄(R2-4)

### R2. 도서관 클릭 기록

- R2-1 링크는 지금처럼 새 탭으로 바로 열리고, 같은 클릭에서 화면이 `fetch(…, {keepalive: true})`로 우리 서버에 짧은 알림을 보냄 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #8: "fetch(keepalive)로 하자"). 처음 범위의 `sendBeacon`(scope 포함 3)에서 바뀜. keepalive는 화면이 닫혀도 요청을 끝까지 보내고, 본문 64KiB까지, 헤더를 붙일 수 있음 (https://developer.mozilla.org/en-US/docs/Web/API/RequestInit , 확인 2026-10-13). 지원: Chrome 66, Edge 15, Safari 13, Firefox 133 (https://github.com/mdn/browser-compat-data/blob/main/api/Request.json , 확인 2026-10-13)
- R2-2 알림에 담는 것: 도서관 번호, 누른 곳, 화면, 책 번호(있을 때) [확정: 화면·책 번호 더함] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #6). 화면이 지금 아는 값 (dev 2026-10-12): 결과 줄은 `row.libraryId`, 책 줄(수집 목록·책 페이지·사서 추천)은 책 번호를 `page` 칸에 담아 씀(`features/.../holdingPlan.ts:128-142`), 직접 찾기 줄은 우리 책 번호가 없음. 로고(`components/LibraryLogo.tsx:5-13`)는 도서관 번호를 받지 않으므로 넘겨 줘야 함. 결과 줄은 자기가 어느 화면에 있는지 모르므로 넘겨 줘야 함
- R2-3 서버는 도서관 번호가 서비스 도서관에 있는지, 누른 곳·화면이 정한 값인지 확인하고, 아니면 클릭 기록에 넣지 않음. 어느 경우든 같은 응답(204) [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #7). 처음 안 "이상하면 조용히 버림"은 미승인 → 이상한 알림은 **IP와 함께 따로 남김** [확정] (사용자: "ip도 남기는 거로 바꿨으면 해", 2026-10-13). 남기는 것: 시각, IP, 이유(없는 도서관 번호 / 정하지 않은 값 / 형식 오류), 받은 값. 보관 30일 [확정] (사용자 제안 "30일 보관", 2026-10-13, `easy/2026-10-13-spec-followup-decisions.html` #1, 제안 7일은 미승인). 30일 지난 것은 매일 기록 지우기 때 함께 지움. 이 경우만 "IP를 남기지 않음"(앞 조사 #4)의 예외이며 처리방침에 적어야 함 (사이클 16)
- R2-4 보안 검사(CSRF): 클릭 알림도 다른 보내기 요청과 같이 CSRF 검사를 받음, 예외 주소 없음 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #8: "fetch(keepalive)로 하자"). 화면은 이미 있는 CSRF 코드(보내기 요청에 `XSRF-TOKEN` 값을 `X-XSRF-TOKEN`으로 붙이고, 없으면 `/api/v1/auth/csrf-token`으로 받아 오고, `csrf_invalid` 403이면 한 번 더 시도; dev `web/src/api/auth.test.ts`)를 씀. 로그인 기능이 꺼져 있으면 서버에 검사가 없으므로 표시 없이 보냄 [안]. 확인 결과(2026-10-13): 로그인이 꺼지면 표시 받아 오는 주소가 없어(404) 지금 화면 코드를 그대로 쓰면 알림이 안 나감 → 화면이 로그인 기능 상태(`/api/v1/me` 404=꺼짐)를 보고 켜졌을 때만 표시를 받아 옴 (`architect-proposal.md` 확인 결과)

### R5. #14에서 바뀐 것 (사용자: "책 상세 열기도 기록하려고 하는데 그리고 ip도 기록하려고해", 2026-10-13, #14 미승인)

- R5-1 책 상세 열기도 기록함 [확정] (같은 발언). 책 페이지가 서버에 책 정보를 처음 요청할 때(`GET /api/v1/books/{bookId}`) 한 줄, 칸은 시각·책 번호·지역·고른 도서관·로그인 여부·IP. 대출 수 채우기는 세지 않음, 새로고침하면 다시 한 줄 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-13-spec-followup2-decisions.html` #3)
- R5-2 IP도 기록함 [확정] (같은 발언). 앞 조사 결정 #4 "IP를 남기지 않음"(2026-10-12)을 바꿈 → ADR. 범위: 검색·도서관 클릭·책 상세 열기 세 기록 모두 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-13-spec-followup2-decisions.html` #1). 보관: IP 칸만 30일 뒤 비우고 나머지 칸은 1년 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-13-spec-followup2-decisions.html` #2) (매일 04:30 작업에서 함께). IP는 nginx가 넘겨주는 `X-Real-IP`(dev `chaekcheck-locations.conf:17`, 값은 nginx의 `$remote_addr`)에서 읽음 [안]. 사이클 17(첫 배포)이 서버 앞에 Cloudflare Tunnel을 두고 nginx가 `CF-Connecting-IP`를 사용자 주소로 읽게 하기로 함 [확정: 17 결정] (17 `scope.md`, 사용자가 전달 2026-10-13). 그 설정이 들어가면 `$remote_addr`가 사용자 IP가 되어 `X-Real-IP`도 사용자 IP가 됨. 설정이 없으면 모든 요청이 터널 프로그램(cloudflared) 주소 하나로 보여 IP 기록·nginx IP별 요청 수 제한(R2-5, 직접 찾기 1분 30번)이 모두 틀어짐 [확인 필요: 17 배포 설정 확인, 15 설계에서 서비스가 어느 값을 쓰는지 확정]. 서비스는 `request.getRemoteAddr()`가 아니라 nginx가 붙인 `X-Real-IP` 머리글을 직접 읽는 방향 [안] (설계 결정 페이지 #7) — 그러면 Spring의 forwarded 머리글 설정 없이 nginx 값만 믿게 됨. **조사로 확인 (2026-10-13, 사이클 15)**: Cloudflare Tunnel에서는 원 서버가 방문자 대신 cloudflared 주소를 보고, HTTP는 `CF-Connecting-IP` 머리글로 방문자 IP를 받음 [확정] (https://developers.cloudflare.com/cloudflare-one/networks/connectivity-options/ : "Your origin sees the `cloudflared` process IP instead of the original client IP", "For HTTP traffic, use the `CF-Connecting-IP` header to retrieve the client IP", 확인 2026-10-13). 이 머리글은 Cloudflare에서 원 서버로 가는 요청에만 붙음 [확정] (https://developers.cloudflare.com/fundamentals/reference/http-headers/ , 확인 2026-10-13). nginx는 `ngx_http_realip_module`의 `real_ip_header CF-Connecting-IP`와 `set_real_ip_from`으로 바꿈 [확정] (https://developers.cloudflare.com/support/troubleshooting/restoring-visitor-ips/restoring-original-visitor-ips/ , 확인 2026-10-13). Tunnel에서는 nginx에 붙는 쪽이 cloudflared뿐이므로 `set_real_ip_from`에는 Cloudflare 주소 목록이 아니라 cloudflared가 nginx에 붙는 주소(같은 서버면 127.0.0.1, Docker면 그 네트워크 주소)를 적음 [안: 공식 문서의 원리에서 추론]. **사이클 17 답 (사용자가 전달, 2026-10-13)**: 운영은 nginx와 cloudflared를 각각 컨테이너로 띄우므로 nginx가 보는 상대 주소는 `127.0.0.1`이 아니라 Docker 네트워크 주소. compose에서 둘을 같은 네트워크에 두고 주소 범위를 직접 정해(예: `172.30.0.0/24`) `set_real_ip_from`에는 그 범위만 적음, nginx 포트는 바깥에 열지 않음 → 17 명세 R3 "믿는 주소 범위"에서 정함 [안: 17]. dev 시험용 `tunnel-test.conf`는 127.0.0.1과 사설 범위 전체를 믿음(집 PC 시험용). 배포 뒤 nginx 접속 기록에 실제 휴대폰 IP가 찍히는지로 확인 남은 확인: nginx 이미지에 realip 모듈이 있는지(`nginx -V`에 `--with-http_realip_module`; nginx.org 패키지는 추가 라이브러리 없는 모듈을 모두 넣는다고 함, https://nginx.org/en/linux_packages.html — 추론), Cloudflare의 "Remove visitor IP headers" 설정을 끈 채로 둘 것, nginx를 바깥에 직접 열지 않을 것(머리글을 꾸며 보낼 수 없게) [확인 필요: 배포 때 `nginx -V` 한 줄과 지인 기간 시험에서 기록된 IP 확인] IP가 들어가면 기록은 개인정보로 볼 가능성이 커져 처리방침(사이클 16)에 항목·목적·보관 기간을 적어야 함 (개인정보 보호법 제2조 제1호·제30조, `storage.md` 4절)

## 상태별 동작

- 로딩: 기록은 화면에 아무것도 보이지 않음. 검색 로딩·링크 열림은 지금과 같음
- 결과 없음: 수집 목록 검색 결과가 0권이어도 기록함(결과 수 0) [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #2). 무엇을 찾다 못 찾았는지가 통계에 쓸모 있음 [이유 미확인: 제안]
- 외부 오류·지연: 직접 찾기에서 도서관이 응답하지 않아도 첫 묶음이 끝나면 기록(R1-4). 기록 DB 쓰기 실패는 R3-3
- 입력 오류: 검색 400·422는 기록하지 않음(R1-2). 클릭 알림의 잘못된 값은 기록하지 않고 204(R2-3)

## 수용 기준

- AC-1: 수집 목록에서 "채식주의자"를 검색하면 → 검색 기록이 한 줄 생기고 검색어·결과 수(`totalCount`)·지역·고른 도서관이 들어 있다 (SQL로 확인)
- AC-2: 같은 검색에서 다음 쪽(`page=2`)을 보면 → 검색 기록이 늘지 않는다
- AC-3: 직접 찾기로 검색하고 첫 묶음이 끝나면 → 한 줄 생기고 결과 수가 들어 있다. "다음 묶음"·도서관별 더 보기를 눌러도 줄이 늘지 않는다
- AC-4: 직접 찾기 첫 묶음이 끝나기 전에 창을 닫으면 → 결과 수가 빈 한 줄이 생긴다
- AC-5: 검색어가 1자(400)이거나 없는 지역 번호(422)면 → 기록이 생기지 않는다
- AC-6: User-Agent에 `Googlebot`이 든 검색 요청을 보내면 → 기록이 생기지 않는다 (API 호출로 확인)
- AC-7: 결과 카드를 누르면 → 전자도서관 새 탭이 지금처럼 바로 열리고, 클릭 기록에 도서관 번호·"결과 카드"·화면이 한 줄 생긴다. 여섯 누른 곳 모두 각각 확인
- AC-8: 책 페이지의 결과 카드를 누르면 → 클릭 기록에 그 책 번호가 들어 있다. 직접 찾기 결과에서는 책 번호가 비어 있다
- AC-9: 로그인 기능을 켠 상태에서 클릭 알림이 CSRF 표시를 붙여 기록된다(표시 없는 알림은 403). 로그인 기능을 끈 상태에서도 기록된다
- AC-22: 직접 찾기에서 "다음 묶음"·도서관별 더 보기, 수집 목록 2쪽을 보면 더 보기 기록이 한 줄씩 생기고 검색 기록은 늘지 않는다
- AC-23: 사서 추천 목록·추천 책 창을 열면, 지역 설정을 바꾸거나 내 도서관에 넣고 빼면 각각 한 줄 생긴다 (회원 번호 없음)
- (확인 필요) 밤 DB 백업(매일 03:00, 사이클 17)에도 기록이 들어가 백업 보관 기간만큼 지운 기록이 더 남음 → 17의 백업 보관 기간 확인 [확인 필요: 17에 질문]
- AC-24: 직접 찾기·대출 수 채우기를 한 뒤 하루 요약 작업이 돌면 도서관마다 그날 성공·실패·시간 초과 수와 평균·가장 긴 시간이 한 줄씩 생긴다
- AC-21: 기록 설정 값이 꺼져 있으면 검색·책 상세·클릭을 해도 기록이 생기지 않고, 켜면 생긴다 (테스트)
- AC-20: 로그인 기능 켬·끔 두 설정 각각에서 AC-1~AC-19가 통과한다. 꺼짐에서는 로그인 여부가 "안 함", 확인 중에 보낸 검색은 "모름"으로 남는다 (테스트)
- AC-10: 없는 도서관 번호나 정하지 않은 "누른 곳" 값으로 알림을 보내면 → 204가 오고 클릭 기록은 생기지 않으며, 이상한 알림 기록에 IP·이유가 한 줄 생긴다 (API 호출)
- AC-6b: User-Agent에 `bot`이 든 요청으로 직접 찾기를 부르면 → nginx가 거절하고 서버 검색 칸을 쓰지 않는다 (API 호출). `/robots.txt`에 `/api/` 금지가 보인다
- AC-11: 같은 IP에서 클릭 알림을 R2-5의 한도보다 많이 보내면 → 넘친 것은 기록되지 않는다
- AC-12: 기록 칸에 회원 번호·User-Agent·쿠키 값 칸이 없다 (표 정의로 확인)
- AC-17: 책 페이지를 열면 책 상세 기록이 한 줄 생기고, 대출 수 채우기로 줄이 늘지 않는다
- AC-18: 받은 지 31일 된 기록은 IP 칸이 비어 있고 나머지 칸은 남아 있다. 29일 된 기록은 IP가 있다 (테스트)
- AC-19: 기록 DB 쓰기를 일부러 실패시킨 뒤 다시 성공하면 → 버린 묶음 기록(시각·줄 수·이유)이 한 줄 생기고 서버 로그에도 있다 (테스트)
- AC-13: 받은 시각이 1년 1일 전인 기록과 364일 전인 기록을 넣고 지우기 작업을 돌리면 → 앞의 것만 지워진다 (테스트)
- AC-14: 기록 DB 쓰기를 일부러 실패시켜도 → 검색 결과와 링크는 정상이다 (테스트)
- AC-15: 서버를 정상 종료하면 → 종료 직전 검색까지 기록에 남아 있다 (테스트)
- AC-16: 같은 검색 묶음을 기록을 끈 상태와 켠 상태로 돌려 → 검색 응답 시간 중앙값의 차이가 10% 안, 서비스·DB 컨테이너 메모리 차이가 각각 50MB 안이다 [확정] (사용자 승인, 2026-10-13, `easy/2026-10-12-spec-decisions.html` #13) (dev 측정표로 확인). 같은 4GB 서버에 Prometheus·Grafana·node_exporter가 함께 돎(사이클 17 [확정]) → 잴 때 이들을 켠 상태로, 이들 메모리도 함께 적음 [안]
