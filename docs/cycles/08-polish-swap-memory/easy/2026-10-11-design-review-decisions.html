사이클 08 설계를 마무리하기 전에
검토에서 찾은 문제를 고칩니다.

사이클 마무리 첫 단계로, 검토 담당(design-reviewer)이 범위·요구·화면 흐름·설계 문서와 결정 기록(ADR)을 서로 맞대 봤습니다. "반드시 고칠 것" 10가지를 9개 항목으로 묶었고, 마지막 항목은 "고치면 좋은 것"까지 고칠지입니다. 모두 문서끼리 어긋난 곳을 맞추는 일이고, 이미 정하신 방향을 바꾸는 것은 없습니다. 6·7·8번만 새 값(대기 시간, 목표)이 들어갑니다.

1가져오기 순서와 기록

1가져오기 그림의 순서를 고침: 책 번호를 먼저 정하고, 그 번호 순으로 씀 [안]

지금 설계 그림(흐름 A)은 "새 표에 책 번호 순으로 쓰기" 다음에 "책 번호 잇기(옛 번호와 맞대기)"가 옵니다. 그런데 책 번호가 정해져야 그 순서로 쓸 수 있으니 거꾸로입니다.

고친 뒤: 그림 흐름 A와 모듈 표의 catalog 줄을 이 순서로 고칩니다. 조사(research.md 10절 D-2)에 적은 순서와 같습니다.

다른 선택 쓰고 나서 번호를 다시 매기기: 한 번 더 다 고쳐 써야 해서 느려짐. 추천하지 않음.

2ADR-0065에 "국가서지 부분은 ADR-0069로 바뀜" 표시 [안]

ADR-0065에는 아직 "국가서지 결과를 정리 규칙 판과 함께 남긴다"가 적혀 있어, 나중에 읽는 사람이 ADR-0069와 어긋난다고 느낄 수 있습니다. 확정된 기록은 본문을 고칠 수 없고 상태 줄만 바꿀 수 있습니다.

고친 뒤: ADR-0065 상태 줄을 Accepted (국가서지 부분은 ADR-0069가 바꿈), ADR 목록(README)에도 같은 표시. 조사 문서 research.md의 E-1(판 번호와 함께 남기기) 옆에 "기록용, ADR-0069로 바뀜"을 붙입니다.

3DB 트리거 파일은 SQL 파일(.sql)로 씀 [안]

설계에 트리거(updated_at을 DB가 채우는 장치) 파일 이름을 .yaml로 적었는데, dev 프로젝트 규칙(CLAUDE.md)은 함수·트리거를 --liquibase formatted sql 형식의 .sql 파일로, splitStatements:false, CREATE OR REPLACE, runOnChange:true로 쓰라고 합니다.

고친 뒤: library/013-updated-at-trigger.sql, region/00N-updated-at-trigger.sql. 칸 더하기·이름 고침 같은 나머지 파일은 .yaml 그대로입니다.

4설계 그림 제목의 "초안" 글자를 지움 [안]

흐름 A·B 그림 제목에 "ADR-0065 초안", "ADR-0066 초안"이 남아 있습니다. 둘 다 확정됐으니 "ADR-0065", "ADR-0066"으로 고칩니다.

2국가서지 표와 바꿔 끼우기 실패

5국가서지 두 표를 자세히 적고, 다시 뽑다 실패하면 어떻게 할지 정함 [안]

지금 설계에는 칸 이름만 있습니다. dev가 그대로 만들 수 있게 이렇게 적습니다.

표칸규칙
national_bibliography_recordisbn13 글자 13자리, 비어 있지 않음
title_raw 글자, 비어 있지 않음
author_raw, publisher_raw 글자, 비어도 됨		같은 ISBN이 여러 줄일 수 있어 따로 기본 키 번호(id)를 둠. 가져오기는 처음부터 끝까지 읽기만 해서 색인은 두지 않음
national_bibliography_sourcesource_fingerprint 글자, 비어 있지 않음
built_at 시각, 비어 있지 않음		항상 한 줄. 지문 = TTL 파일 이름 + 크기(바이트) + 고친 시각을 |로 이은 글자

다른 선택 ①~③을 한 트랜잭션으로: 실패하면 옛 원문이 그대로 남지만, 수백만 줄을 한 트랜잭션에 넣어 DB 기록(WAL)이 커짐. 지문 마지막 쓰기가 더 단순해 추천.

답: TTL이 무슨 약자인가요?
파일 확장자 .ttl에서 온 이름으로, Turtle(Terse RDF Triple Language, "짧게 쓰는 RDF 세 칸 언어")의 줄임입니다. 국립중앙도서관이 국가서지를 "이 책 — 제목은 — ○○"처럼 주어·서술어·값 세 칸씩 적어 내려 주는 형식이라, 한 권의 정보가 여러 줄에 흩어져 있어 풀어 모으는 데 6.5~9분이 걸립니다. 출처: W3C Turtle 표준, https://www.w3.org/TR/turtle/ (확인 2026-10-11).

6바꿔 끼우기가 잠금을 못 얻으면: 2초 기다림 × 5번, 다 실패하면 새 표 지우고 실패로 기록 [안]

바꿔 끼우는 짧은 트랜잭션은 옛 표를 읽고 있는 검색이 끝나야 들어갈 수 있습니다. 너무 오래 기다리면 그 뒤에 온 검색이 줄을 섭니다. 그래서 기다리는 한도(lock_timeout)를 둡니다. PostgreSQL 설명: 잠금을 얻으려고 정한 시간보다 오래 기다리는 문장은 멈춘다, 기본값 0은 한도 없음 (PostgreSQL 18 문서, 확인 2026-10-11).

  • 한도 2초, 실패하면 10초 쉬고 다시, 최대 5번. 값은 dev 측정 뒤 바꿀 수 있음
  • 5번 다 실패: catalog_next를 지우고 옛 표 그대로, 가져오기 기록에 실패(이유: 잠금 못 얻음). 다른 실패와 같은 처리

다른 선택 catalog_next를 남겨 두고 "바꿔 끼우기만" 다시 하는 명령을 둠: 30분 넘는 가져오기를 다시 안 해도 되지만 명령이 하나 더 생김. 실제로 5번 다 실패하는 일이 생기면 그때 더하는 쪽을 추천.

7"바꿔 끼우는 순간 실패 0건"을 둘로 나눔 [안]

소장 번호는 바꿔 끼운 뒤 새로 매겨지므로(ADR-0065), 바꿔 끼우기 전에 연 책 화면이 옛 소장 번호로 대출 현황을 물으면 그 번호는 없습니다. 지금 dev 코드는 없는 번호를 오류가 아니라 "찾을 수 없음"(missing)으로 돌려줍니다(BookAvailabilityBatchStreamController). 이것까지 "실패"로 세면 AC-8을 지킬 수 없습니다.

  • AC-8: 바꿔 끼우는 순간 검색·책 화면 요청에 서버 오류(5xx)나 끊김이 0건
  • AC-8c(새로): 바꿔 끼운 뒤 옛 소장 번호로 온 대출 현황 요청은 오류 없이 "찾을 수 없음"으로 답함, 다시 검색하면 정상. 그때 화면에 무엇이 보이는지는 웹 코드에서 찾지 못해 확인 못 함 → 인계서에서 dev가 확인

답: 중간 단계(번호 맞춤 표)를 두면?
좋은 생각입니다. 살펴보니 더 단순한 길도 있습니다. 가져올 때 이미 옛 소장 줄과 새 소장 줄을 (도서관, 도서관 안 책 열쇠 item_key)로 맞대어 책 번호를 잇고 있어서, 소장 번호도 같은 맞대기로 그대로 이어 쓸 수 있습니다. 그러면 맞춤 표도, 요청의 버전 번호도 필요 없습니다. 또 맞춤 표를 두더라도 새 번호가 옛 최대 번호 다음부터라 옛 번호와 겹치지 않으므로 버전 번호 없이 "지금 표에 없으면 맞춤 표에서 찾기"로 됩니다. 두 안을 다음 페이지(2026-10-11-holding-id-followup)에 그림과 함께 올렸습니다.

3태그·목표 맞추기

8이미 정한 것인데 "안"으로 남은 표시를 확정으로 맞춤 [안]

  • 요구 R7(가져오기·교체): 0번의 "아래 1~5는 고를 때의 규칙 (제안)", 1번, 4번 → ADR-0065로 정했으니 확정. 2번 "바꿔 끼우는 순간 외에는 기다리지 않음"도 확정
  • 요구 R9.4, 범위 15번 끝 "책 화면이 계획한 도서관 줄만 읽기 (제안)" → 설계 검토에서 승인(ADR-0066, holdingsOf)했으니 확정
  • 요구 "입력과 출력" 표: 옛 검색 설정 지우기, 429·503 문구가 본문(R1.4, R2.1)은 확정인데 표만 (제안) → 확정

9가져오기 시간 목표(AC-8b): 검색이 기다리는 시간 10초 안, 전체 시간은 40분 36초보다 짧게 [안]

AC-8b에 "몇 분까지는 방향을 고른 뒤"라고 남아 있는데, 방향(새 표에 쓰고 바꿔 끼우기)은 정해졌습니다. 이 방식에서 검색이 기다리는 것은 바꿔 끼우는 순간뿐이라 숫자를 둘 수 있습니다.

전체 시간은 숫자 대신 "사이클 07 2회차보다 짧게"만 둡니다. 쓰기 단계 안을 나눠 잰 뒤(ADR-0065) 더 줄일 곳을 정하기 때문입니다. 10초는 6번(2초 × 5번 + 쉬는 시간)을 넘지 않는 성공 경우를 기준으로 했습니다.

다른 선택 숫자 없이 "짧게"만: 지켰는지 판단이 흐려짐. 전체 시간도 숫자(예: 30분 안): 재 보기 전이라 근거가 없음.

10"고치면 좋은 것"도 이번에 같이 고침 [안]

꼭은 아니지만 dev가 헷갈리지 않게 손보면 좋은 것들입니다. 모두 정한 내용을 문서에 옮겨 적는 일이고 새로 정하는 것은 없습니다.

  • 범위(scope.md)에 이미 정한 일 더하기: 흡수된 학교 사이트 확인, 검색 계획을 SQL로 거르기, 응답 복사 줄이기, 503에 "5초 뒤"
  • 검사 기준(AC) 더하기: 국가서지 원문 다시 쓰기, 정리 규칙 바꿀 때 순서, 검색 계획 결과가 전과 같음, 503 Retry-After: 5, 응답 복사 줄인 뒤 결과 같음, 폰 사이트 다름 13곳 표시
  • 오래된 태그 정리: spec.md 첫머리·확인 필요 표, flow.md 본문·확인 필요
  • 새 칸·단계별 시간 이름 옆에 ADR 번호, 연결 풀에서 다시 계획되는지 확인을 AC에, 인계서에 "catalog로 들어오는 외래 키 없음 다시 확인", 도서관 목록 CSV를 고치는 이유 한 줄
  • 모듈 그림에 catalog :: normalize 이름표, 이름 고침 목록의 예외 규칙을 둘 곳 적기

다른 선택 미승인이면 반드시 고칠 것(1~9)만 고치고 나머지는 그대로 인계서로 넘어갑니다.
