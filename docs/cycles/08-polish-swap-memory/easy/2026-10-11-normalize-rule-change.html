정리 규칙을 바꿀 때의 순서를
하나 정해 주세요.

질문("정리 규칙이 바뀌면 어떻게 하기로 한거지?")에 답하다 보니, 규칙을 바꿨을 때의 순서가 정해져 있지 않았습니다. 설계 페이지에는 칩을 더할 수 없어 이 페이지에서 따로 여쭙니다. 설명 그림은 설계 페이지 DB 칸 안에 있습니다.

1정리 규칙을 바꿀 때

정리 규칙(제목·저자·출판사를 다듬는 규칙)은 검색어와 저장값이 같이 씁니다. 코드만 바꾸고 다시 가져오지 않으면, 검색어는 새 규칙으로 다듬어지는데 저장값은 옛 규칙 그대로라 검색이 일부 안 맞을 수 있습니다.

1정리 규칙을 바꾸면 판 번호를 올리고, 그 코드를 올릴 때 같은 사본으로 반드시 다시 가져온다 [안]

순서(질문 뒤 고침): ① 규칙 코드를 고치고 판 번호(normalize_version)를 올림 → ② 옛 서비스는 켜 둔 채, 새 코드로 같은 사본을 가져와 새 표를 준비(국가서지도 새 판으로 다시 풂) → ③ 바꿔 끼우자마자 서비스를 새 코드로 다시 켬. 검색이 어긋나는 시간은 ③의 다시 켜는 동안뿐.

dev 규칙 문서와 가져오기 절차(docs/maintenance/3-import.md)에 이 순서를 적습니다. 정리 규칙의 예상 결과 목록(테스트 벡터)에 판 번호를 함께 적어, 결과가 달라졌는데 번호가 그대로면 빌드가 실패하게 합니다(번호 올리기를 잊지 않게). 규칙 자체는 DB에 남기지 않고, 판 번호는 국가서지 결과가 옛 규칙으로 만든 것인지 가리는 데만 씁니다(아래 질문 답 참고).

다른 선택 (가) 규칙을 바꾸면 다음 정기 가져오기 때 맞춰짐: 일이 없지만 그 사이 검색이 어긋날 수 있음. (나) 저장값을 SQL로 다시 계산: 묶기 결과는 못 바꿔서 결국 다시 가져와야 함.

질문: 규칙을 DB에 남겨야 하나요? 어차피 새 규칙으로 DB를 새로 만들어야 하지 않나요?

맞습니다. 규칙 자체는 DB에 남기지 않습니다(규칙은 코드에만 있음). 그리고 규칙이 바뀌면 다시 가져와서 책·사람·소장 표를 새 규칙으로 새로 만드는 것이 정답입니다. DB에 남기는 것은 규칙이 아니라 판 번호 숫자 하나뿐이고, 쓰는 곳도 한 곳입니다.

무엇규칙이 바뀌면판 번호가 필요한가
책·사람·소장 표다시 가져오면 통째로 새로 만들어짐아니요
국가서지 결과(남겨 두고 다시 쓰는 것)다시 가져와도 "파일이 같으니 다시 쓰자"고 옛 규칙 결과를 그대로 쓸 수 있음 → 틀린 묶음예. "이 결과는 몇 판 규칙으로 만들었나"를 알아야 버리고 다시 풂

그래서 아래 제안을 단순하게 고쳤습니다. 처음 적었던 "판 번호가 다르면 서버가 시작할 때 경고"는 빼고, 판 번호는 국가서지 결과에만 씁니다. 다시 가져오기는 절차로 지킵니다.

질문: 규칙 번호가 수집과 DB에서 도대체 어떻게 표시되나요?

규칙 번호는 코드 안의 숫자 하나에서 시작하고, 수집 DB에는 전혀 없으며, 서비스 DB에는 국가서지 결과의 한 줄짜리 표에만 적힙니다. 수집은 원문을 그대로 모으기만 하고, 규칙은 가져올 때와 검색할 때만 쓰이기 때문입니다.

자리번호가 있나어떻게 보이나
정리 규칙 코드 (catalog.normalize)있음 (원본)코드 안 상수 하나. 규칙을 고칠 때 개발자가 1 올림
수집 DB (SQLite)없음원문만 있음. 규칙이 바뀌어도 수집 DB는 그대로
서비스 DB 책·사람 표없음다듬은 값(title_norm 등)만. 다시 가져오면 새 규칙 값으로 통째로 바뀜
서비스 DB 국가서지 결과의 판 표 (한 줄)있음normalize_version 칸에 "이 결과를 만든 번호"
검색할 때없음검색어를 지금 코드로 다듬을 뿐

원하시면 가져오기 기록 한 줄에도 같은 번호를 적어 "지금 서비스 DB가 몇 번 규칙으로 만들어졌나"를 사람이 볼 수 있게 할 수 있습니다(칸 하나). 필요하면 기타에 적어 주세요.

질문: 정리 규칙 코드(catalog.normalize)가 책마다 있는 건가요?

아닙니다. 서비스 전체에 한 벌만 있는 프로그램 코드입니다. 책 데이터가 아니라 "글자를 다듬는 기계"이고, 160만 권 모두와 이용자가 친 검색어가 같은 기계를 지나갑니다. 그래서 판 번호도 서비스 전체에 하나입니다.

이 코드가 하는 일 예(사이클 04·07 규칙, search-and-normalization.md 4절): 전각·반각 문자 통일(NFKC), 영어 소문자, 공백 없애기, 본제목 떼기(부제 앞까지), 저자 이름 나누기와 역할(옮긴이·그림·엮은이) 가리기, 출판사 이름 다듬기, 출판일 읽기, ISBN 검사. dev 코드 위치: catalog/normalize/의 CatalogText, Contributors, Isbn, PublishedDates(사이클 07에 이 자리로 옮김, ADR-0060).

예시 검색어 다듬기 결과는 공백 제거 규칙을 보이려는 것이고, 실제 검색은 글자 조각(bigram)으로도 찾습니다.

질문: 정리 규칙 코드와 국가서지 판 표는 뭐가 다른가요? 각각 보여 주세요. 정리 방법이 바뀌었다는 건 어떻게 전달되나요?

정리 규칙 코드는 DB에 없습니다. 프로그램(소스 코드) 안에 있고, 그 안에 "지금 판 번호"가 숫자로 적혀 있습니다. 국가서지 판 표는 DB에 있는 한 줄이고, "남겨 둔 국가서지 결과를 몇 번 판으로 만들었는지"를 적어 둔 기록입니다. 앞은 "지금 규칙", 뒤는 "결과를 만들 때의 규칙"입니다.

정리 규칙 코드국가서지 판 표
어디에dev 저장소의 Java 코드 (catalog/normalize/), 서버 프로그램 안서비스 DB (collection.national_bibliography_source)
무엇글자를 다듬는 규칙 자체 + 지금 판 번호숫자 한 줄: 결과를 만들 때의 판 번호, 파일 지문, 만든 시각
누가 바꾸나개발자가 규칙을 고칠 때가져오기가 결과를 새로 만들 때 자동으로
몇 개한 벌한 줄

바뀌었다는 것이 전달되는 길

2번 테스트는 정리 규칙의 예상 결과 목록(테스트 벡터, ADR-0031이 이미 "정리 규칙을 테스트 벡터 하나로 고정"으로 정함)에 판 번호를 함께 적어 두고, 결과가 달라졌는데 번호가 그대로면 빌드가 실패하게 하는 것입니다. 사람이 번호 올리기를 잊어도 막아 줍니다. 위 #1 제안에 이 테스트를 포함했습니다.

질문: 보통 이렇게 Java 코드의 상수로 전달하나요?

정해진 표준은 없고, 흔히 쓰는 방법이 셋 있습니다. "남겨 둔 결과가 지금 규칙으로 만든 것인가"를 가리는 문제는 캐시를 언제 버릴지의 문제와 같아서, 빌드 도구 같은 곳에서도 같은 고민을 합니다.

방법어떻게좋은 점아쉬운 점
가. 손으로 올리는 판 번호 (지금 제안)코드에 숫자 상수, 규칙을 고칠 때 개발자가 올림가장 단순, 사람이 읽기 쉬움올리기를 잊을 수 있음 → 테스트로 막음
나. 자동 지문규칙의 예상 결과 목록(테스트 벡터)을 지금 코드로 돌린 결과를 짧은 값(해시)으로 만들어 판으로 씀손으로 올릴 일이 없음. 결과가 달라지면 저절로 판이 바뀜테스트 벡터에 없는 경우의 변화는 못 잡음(가도 같음). 판 값이 사람이 읽기 어려운 글자
다. 앱 배포 번호를 판으로새로 배포할 때마다 판이 바뀜잊을 일이 전혀 없음규칙과 상관없는 배포에도 국가서지를 매번 다시 풂(6.5~9분 손해)

"나"와 같은 생각의 공식 예: Gradle 빌드 캐시는 작업의 구현과 입력 값이 캐시 키를 이루고, 키가 같을 때만 지난 결과를 다시 씀(Gradle Build Cache 개념, 확인 2026-10-11). 이 서비스에 어느 쪽이 "보통"인지 말해 주는 공식 기준은 확인 못 함입니다.

추천은 그대로 "가 + 잊지 않게 하는 테스트"입니다(단순, 판 번호가 사람 눈에 보임). 손으로 올리는 일을 없애고 싶으시면 위 #1 칩의 기타에 "나로"라고 적어 주세요.

질문: "3. 서버에 올림", "4. 같은 사본으로 다시 가져옴"을 구체적으로

지금은 배포가 보류라 "서버"는 이 PC입니다(로컬 + Cloudflare 터널). 3은 서비스를 새 코드로 다시 켜는 것이고, 4는 서비스를 켜 둔 채 다른 창에서 가져오기 명령을 한 번 돌리는 것입니다. 가져오기는 웹 서버 없이 한 번 돌고 끝나는 따로 된 실행이라, 서비스와 동시에 돌 수 있습니다(dev docs/maintenance/3-import.md).

4-1의 실제 명령 (dev 3-import.md 32행의 명령에서 시험 실행 표시만 뺀 것, 사본 경로는 그때 쓰는 사본):

cd backend
./gradlew bootRun --args='--spring.profiles.active=collection-import --chaekcheck.collection.import.sqlite-path=../../chaekcheck-data/snapshots/ebook-catalog-2026-10-05-0745.sqlite --chaekcheck.collection.import.ttl-path=../data/nlk/ttl'

프로필 collection-import는 웹 서버 없이 한 번 돌고 끝나며 로그인 기능은 늘 꺼집니다(dev 3-import.md 34행). 이번 사이클에 가져오기 Java 메모리 상한(-Xmx)이 이 명령에 더해집니다.

"같은 사본"인 까닭: 규칙만 바꿨으니 데이터는 그대로 두고 다듬기만 다시 하려는 것입니다. 새 사본이 있으면 그걸로 해도 되지만, 그러면 규칙 효과와 데이터 변화가 섞여 결과를 비교하기 어렵습니다.

어긋나는 시간을 줄이려면: 이용자가 적은 시간(새벽)에 3-2와 4-1을 바로 이어서 합니다. 4를 먼저 하고 3을 나중에 해도 반대 방향으로 어긋날 뿐이라 시간은 비슷합니다. → 이 문장은 틀렸습니다. 아래 답을 보세요.

질문: 표를 미리 만들어 두고 이름만 바꾸는 거 아니었나요? 가져오기를 먼저 하고 이름을 바꾸면 되지 않나요?

맞습니다. 순서를 거꾸로(가져오기 먼저, 서비스 다시 켜기는 바꿔 끼운 직후) 하는 것이 맞고, 그러면 검색이 어긋나는 시간이 약 40분에서 "서비스를 다시 켜는 동안"으로 줄어듭니다. 앞서 "순서를 바꿔도 시간은 비슷하다"고 쓴 것은 틀렸습니다. 새 표는 바꿔 끼우기 전까지 아무도 읽지 않으므로, 그동안 옛 코드 서비스는 옛 표를 읽어 서로 맞습니다.

더 줄이고 싶으면 가져오기를 "새 표 준비"까지만 하고 멈춘 뒤, 서비스를 끄는 순간에 바꿔 끼우기만 따로 실행하는 방법도 있습니다(가져오기 명령에 "바꿔 끼우기는 따로" 선택지). 처음엔 위 단순한 순서로 하고, 필요하면 더합니다.

위 #1 제안의 순서를 이렇게 고쳤습니다: ① 규칙 고치고 판 번호 올림 → ② 옛 서비스는 켜 둔 채 새 코드로 같은 사본을 가져옴(새 표 준비) → ③ 바꿔 끼우자마자 서비스를 새 코드로 다시 켬.

질문: "실행 설정 backend-no-login"은 뭔가요?

dev 프로젝트에 저장해 둔 "서비스를 켜는 방법" 이름 중 하나로, 로그인 기능을 끈 채 서비스를 켜는 설정입니다. 지금 Cloudflare 터널로 공개 시험할 때 쓰는 켜기 방법입니다(dev 공개 시험 기록, 사이클 07).

이름하는 일실제 명령
backend서비스를 평소대로 켬 (로그인 설정은 .env를 따름)gradlew -p backend bootRun
backend-no-login서비스를 켜되 로그인 기능은 끔 (카카오 로그인·약관·처리방침 화면이 안 보임)gradlew -p backend bootRun --args=--chaekcheck.auth.enabled=false
web, web-lan화면 개발 서버를 켬 (web-lan은 같은 와이파이의 폰에서도 열림)npm --prefix web run dev …

출처: dev .claude/launch.json(Claude Code가 서비스를 켤 때 쓰는 설정 파일, 2026-10-11 읽음). 앞 칸의 "새 코드로 다시 켬"은 이 중 지금 쓰는 켜기 방법으로 다시 켠다는 뜻입니다. 로그인을 켜고 운영한다면 backend로 켭니다.

질문: 표를 통째로 바꿔 끼우는 거면 판 번호(3→4)는 필요 없지 않나요?

맞습니다. 책·사람·소장 표에는 필요 없습니다. 판 번호가 필요한 곳은 "국가서지 결과를 남겨 두고 다시 쓰는 것" 하나뿐이었는데, 이것도 남기는 내용을 바꾸면 판 번호를 아예 없앨 수 있습니다.

지금 제안은 국가서지를 풀어 다듬은 키를 남깁니다. 다듬은 키는 규칙이 바뀌면 틀려지니 판 번호가 필요했습니다. 대신 다듬기 전 원문(ISBN, 제목, 저자, 출판사)을 남기고, 가져올 때마다 그 원문을 지금 규칙으로 다듬으면 규칙이 바뀌어도 남긴 것이 틀려지지 않습니다.

새 추천: 국가서지는 원문을 남기고 가져올 때마다 다듬는다. 판 번호는 두지 않는다. 규칙을 바꿨을 때 할 일은 "옛 서비스 켜 둔 채 새 코드로 다시 가져오기 → 바꿔 끼우자마자 서비스 다시 켜기"뿐입니다.

위 #1 칩은 처음 제안(판 번호 + 테스트)입니다. 새 추천으로 하시려면 #1에 기타로 "원문으로"라고 적어 주세요. 설계 페이지의 국가서지 표도 그에 맞춰 고치겠습니다(판 표에서 normalize_version을 빼고, 결과 표를 원문 칸으로).

질문: 왜 서비스를 다시 켜야 하나요?

돌고 있는 서비스는 켜질 때 읽어 들인 코드로만 움직이기 때문입니다. 검색어를 다듬는 규칙도 그 코드 안에 있어서, 새 규칙 코드를 만들어도 서비스를 다시 켜기 전까지는 옛 규칙으로 검색어를 다듬습니다. Java 서비스는 켜진 채로 코드를 바꿔 끼우지 않습니다.

그래서 어떤 규칙을 바꿨느냐에 따라 다시 켜야 하는지가 갈립니다.

바꾼 규칙어디서 쓰나서비스 다시 켜기
제목·저자·출판사 다듬기 (공백, 대소문자, 본제목, 저자 나누기 등)가져오기(저장값) + 검색할 때(검색어)필요 — 검색어와 저장값이 같은 규칙이어야 찾아짐
같은 책 묶기 ①~④, 대표값 고르기, 날짜 읽기, 빼는 줄 규칙가져오기에만필요 없음 — 다시 가져와 바꿔 끼우기만 하면 됨

앞의 순서에서 "바꿔 끼우자마자 서비스 다시 켜기"는 첫째 경우(다듬기 규칙)에만 하면 됩니다. 둘째 경우는 다시 가져오기만 합니다.

질문: 트랜잭션으로 표만 교체하면 알아서 되는 것 아닌가요? 검색어 다듬기 규칙이 바뀔 때만 다시 켜면 되는 것 아닌가요?

둘 다 맞습니다.

  • 표 교체는 알아서 됩니다. 바꿔 끼우기는 한 트랜잭션 안에서 옛 표를 지우고 새 표를 같은 이름 자리로 옮깁니다. 켜져 있는 서비스는 다음 검색부터 같은 이름의 새 표를 읽습니다. 서비스가 미리 준비해 둔 쿼리도, PostgreSQL이 "쿼리가 쓰는 표가 바뀌면 쓰기 전에 다시 분석·계획한다"고 공식 문서에 적고 있어 새 표를 봅니다(PostgreSQL 18 PREPARE, 확인 2026-10-11). 그래서 서비스를 다시 켤 필요가 없습니다. 다만 우리 서비스(연결 풀)에서 실제로 그런지는 만들어 보고 확인합니다(설계 확인 필요 표에 있음).
  • 서비스 다시 켜기는 검색어 다듬기 규칙이 바뀔 때만입니다. 그 규칙이 서비스 코드 안에 있기 때문입니다. 묶기·대표값·날짜 규칙만 바꿨거나, 규칙은 그대로이고 새 사본을 가져올 때(정기 갱신)는 가져오기만 하면 됩니다.
상황할 일
새 사본으로 갱신 (규칙 그대로)가져오기만 → 바꿔 끼우기. 서비스는 그대로
묶기·대표값·날짜 규칙을 고침새 코드로 가져오기만 → 바꿔 끼우기. 서비스는 그대로
검색어 다듬기 규칙을 고침옛 서비스 켜 둔 채 새 코드로 가져오기 → 바꿔 끼우자마자 서비스를 새 코드로 다시 켬
