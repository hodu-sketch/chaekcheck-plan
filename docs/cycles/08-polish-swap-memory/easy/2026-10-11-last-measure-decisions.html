2가져오기가 중간에 죽었을 때 남는 빈 표

설계는 "가져오기가 실패하면 새 표(catalog_next)가 남지 않는다"였습니다. 실제로는 DB나 가져오기 프로그램 자체가 죽으면 빈 새 표가 남고, 다음 가져오기가 시작할 때 지웁니다.

어느 경우든 서비스가 쓰는 책 데이터와 검색 결과는 그대로였습니다(dev 확인: 책 1,615,125, 소장 17,714,665, 검색 응답 같은 해시).

빈 표가 다음 가져오기까지 남는 것을 받아들임 [안]

빈 표는 서비스에 쓰이지 않고 디스크도 거의 차지하지 않습니다. dev가 짚은 대로, 서비스가 켜질 때 지우게 하면 가져오는 중에 서비스를 다시 켤 때 진행 중인 표까지 지워 버립니다.

다른 선택 — 남은 빈 표를 지우는 명령을 따로 만듦: 바로 지울 수 있지만, 다음 가져오기가 어차피 지우므로 쓸 일이 거의 없습니다.

추천: 받아들임. 설계 문서의 AC-9 설명을 "보통 실패에서는 남지 않음, DB·프로그램이 죽으면 다음 가져오기가 지움"으로 고칩니다. 가져오기 #4를 따로 돌리지 않은 것도 받아들입니다(#3b의 실제 실패가 같은 경우를 보여 줌).

3새로 알게 된 제약: 가져오기와 DB 메모리 상한

가져오기는 색인을 만들 때 DB에 메모리를 1GB까지 쓰라고 합니다(maintenance_work_mem). 그런데 운영 DB 컨테이너 상한은 1GB로 권장했습니다. 이대로면 운영에서 가져올 때 DB가 죽을 수 있습니다.

실제로 #3b에서 dev가 측정 때 걸어 둔 DB 상한 512MB를 풀지 않은 채 가져오다가 DB가 메모리 부족으로 죽었습니다(OOMKilled). 상한을 풀고 다시 돌린 #3c는 끝까지 됐습니다.

이 제약을 사이클 11(가져오기 따로 하기)과 배포 사이클의 입력으로 넘김 [안]

dev가 낸 길은 둘입니다.

  • 운영 DB에서 가져올 때는 그 값을 256MB 이하로 줌(색인 만드는 시간이 길어질 수 있음, 얼마나인지는 모름)
  • 가져오기를 다른 곳에서 하고 결과만 운영에 옮김 — 이미 사이클 11로 잡아 두신 일

사이클 11이 바로 두 번째 길이므로, 이 제약을 사이클 11 설계와 배포 사이클의 확인 항목으로 넘기고 지금은 따로 고치지 않습니다. backlog에 한 줄 남깁니다.

다른 선택 — 지금 dev 설정 기본값을 256MB로 낮춤: 운영에서 바로 안전하지만, 지금 로컬 가져오기의 색인 시간이 늘 수 있고 사이클 09 dev 작업에 끼어듭니다.
