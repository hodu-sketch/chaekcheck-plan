3배포 뒤 seed를 어떻게 고치나

dev가 짚은 문제입니다. seed 파일을 다시 만들면 DB가 "이미 적용한 파일이 바뀌었다"며 시작을 멈춥니다. 사이클 09에서 이름 약 285곳을 고치므로 지금 방향을 정해 두면 좋습니다.

DB 변경 도구(Liquibase)는 이미 적용한 변경의 지문(checksum)을 기억합니다. 적용한 뒤 그 변경을 고치면 지문이 달라져 오류를 냅니다(Liquibase 공식 문서 runOnChange, https://docs.liquibase.com/concepts/changelogs/attributes/runonchange.html, 확인 2026-10-11). seed CSV 파일이 바뀌어도 같다는 것은 dev 설명이고, 공식 문서에서 CSV에 대한 문장은 확인 못 함.

제안하는 순서. 가운데(주황)는 배포 전이라 DB를 새로 만들어도 되는 마지막 기회입니다.

배포 전엔 번호로 고치는 변경 파일, 첫 배포 직전 한 번 seed 정리, 배포 뒤엔 seed 고정 [안]

배포 뒤에는 seed 생성 스크립트가 seed 파일을 다시 쓰지 않고, 바뀐 도서관(새 도서관, 이름 고침, 대출 방식)만 새 변경 파일로 출력합니다. 사이클 08과 09가 쓰는 방식을 배포 뒤에도 이어 가는 것입니다.

다른 선택 — seed를 "바뀌면 다시 돌기"로 바꿈: seed 파일 하나가 늘 정답이 되지만, 다시 돌 때 번호로 덮어써서 운영 중에 바꾼 값(꺼진 도서관 등)을 되돌릴 수 있고, 지워진 줄은 지우지 못합니다.

다른 선택 — 배포 뒤에도 seed를 다시 만들고 지문 오류를 그때그때 허용: 손이 덜 가지만, 운영 DB에서 무엇이 바뀌었는지 기록이 남지 않습니다.

추천: 제안대로. 언제 어떤 이름이 바뀌었는지 변경 파일로 남고, 운영 DB를 다시 만들 일이 없습니다. 첫 배포 직전 정리는 backlog에 있는 "002~006 seed 옛 이름 정리"와 같이 합니다.
