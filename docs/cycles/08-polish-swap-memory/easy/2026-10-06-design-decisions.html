사이클 08 설계: 어떻게 만들지
정해 주세요.

스펙과 화면 흐름은 정해졌습니다. 여기서는 구조(가져오기 방식, 메모리를 줄이는 구조, 작은 구조 항목)를 고릅니다. 각 칩은 추천안이고, 장단점 그림은 앞서 보낸 "가져오기 시간 줄이는 길", "메모리 구조 바꾸는 안" 페이지에 있습니다. 고르시면 이대로 design-delta.md를 쓰고 구조 그림을 보여 드립니다. 원본: architect-proposal.md, research.md 9·10절.

1가져오기·교체 시간

지금 36~41분, 그중 쓰기 끝부분 동안 검색이 멈춥니다. 여덟 방향(새 표 바꿔 끼우기, 바뀐 것만, 도서관별 나누기, 색인 나중에, 국가서지 남기기, 동시에 읽기, 색인 없애기, 다른 DB) 중 셋을 묶는 것을 추천합니다.

1가져오기 = 새 표에 색인 없이 쓰기 → 색인 나중에 → 이름 바꿔 끼우기, 여기에 국가서지 푼 결과 남기기 [안]

검색이 멈추는 시간이 바꿔 끼우는 순간만으로 줄고, 국가서지 6.5~9분이 거의 없어질 것으로 봅니다. 새 표에 책 번호 순으로 써서 "같은 책 소장 줄 붙여 저장"도 함께 됩니다. 표 만들기·바꿔 끼우기는 catalog 안, 국가서지 결과 보관은 collection 안에서 합니다(모듈 경계 그대로).

다른 선택 바뀐 줄만 고치기(옛 줄이 쌓임, 9월 30일에 피하자고 하심), 도서관별로 표 나누기(책 화면이 2,650조각을 다 뒤져 느려질 위험), 지금 흐름에서 색인만 나중에(검색은 여전히 멈춤).

2먼저 쓰기 단계별 시간을 잰 뒤(dev가 시간 기록을 넣고 같은 사본으로 한 번 더), 가장 느린 곳만 더 고침 [안]

두 번째 읽기 없애기, 서비스에 없는 도서관 줄(약 7%) 처음부터 안 읽기, 국가서지 동시에 풀기, 가져오기 전용 색인 없애기는 잰 결과를 보고 고릅니다.

질문: "먼저 쓰기"는 뭔가요?

문장을 헷갈리게 썼습니다. "먼저 + 쓰기 단계의 시간을 잰다"는 뜻입니다. "쓰기 단계"는 가져오기의 마지막 단계(서비스 DB에 책·소장을 써 넣는 부분)로, 지금 22~27분이 걸리고 이 동안 검색이 멈춥니다.

지금은 27분 전체만 알고, 이 네 조각이 각각 몇 분인지는 모릅니다(dev 보고에 나눈 값 없음).

제안을 다시 쓰면: #1을 만들 때 쓰기 단계 안의 네 조각에 시간 기록을 넣고, 같은 사본으로 한 번 돌려 어느 조각이 가장 느린지 본 뒤, 그 조각만 더 고칠지 정한다입니다. 이대로면 #2를 승인해 주세요.

3소장 번호를 지난번 최대 번호 다음부터 매김 [안]

지금은 가져올 때마다 1부터라 가져오는 동안 열려 있던 책 화면의 "더 보기"가 다른 도서관 줄을 가리킬 수 있습니다. 이어 매기면 옛 번호는 "없음"으로 실패할 뿐입니다. 책 번호도 지금처럼 다시 쓰지 않습니다.

4바꿔 끼운 뒤 옛 표는 바로 지움 [안]

다른 선택 다음 가져오기까지 한 벌 남김(되돌리기 쉬움, 디스크 약 10GB 더).

2메모리를 줄이는 구조

5검색 계획을 만들 때 도서관 2,700곳을 다 읽지 않고, 들어갈 약 390곳만 DB에서 읽음 [안]

"도서관 켜짐 여부는 요청마다 읽음"(ADR-0004)은 그대로 지킵니다. 내 도서관 화면용 전체 목록은 그대로 다 읽습니다.

다른 선택 30초 동안 메모리에 기억(DB 읽기는 거의 없어지지만 끈 도서관이 최대 30초 늦게 반영, ADR-0004를 바꿔야 함).

질문: "약 390곳"의 기준이 뭔가요? 종류별로

기준은 사이클 07에서 정한 "가입 조사 상태"입니다. 직접 추가하지 않은 사람의 검색에는 조사가 된 곳과 안내를 못 찾은 곳만 들어가고, 구성원용·종류 모름은 직접 추가했을 때만 들어갑니다(ADR-0053). 그래서 2,674곳 중 대부분은 처음부터 계획에 들어갈 수 없습니다.

지역이나 "가입 가능한 곳"을 고르면 이 안에서 더 줄어듭니다(예: 지역 1개 + 가입 가능 114곳, 사이클 07 측정). #5는 "이 385곳 + 직접 추가한 곳만 DB에서 읽자"는 제안입니다. 지금은 2,674곳을 다 읽고 앱에서 같은 규칙으로 버립니다.

6책 화면은 찾을 도서관 줄만 DB에서 읽음. 가져오기용 색인과 원문 칸은 남김 [안]

공개 기능에 "책 번호 + 도서관 번호로 소장 읽기"를 더합니다. 소장 줄을 붙여 저장한 뒤에는 차이가 작을 수 있어, 측정 결과를 보고 끝까지 할지 정합니다.

질문: #6 맥락 설명

언제: 결과 화면에서 책 카드의 도서관별 대출 현황을 채울 때(바로 보기·책 화면 S3)입니다. 서버는 화면에 보이는 책 최대 20권의 소장 줄을 소장 표에서 읽습니다.

dev 코드: JdbcCatalogHoldings.holdingsOf가 책 번호로만 읽고, BookAvailabilityStreamController가 앱에서 계획 도서관만 남김(2026-10-06 읽음).

왜 낭비인가: 같은 책을 학교·회사 등 구성원용 도서관도 많이 가졌습니다. 이들은 직접 추가하지 않으면 계획에 없으므로, 읽어 놓고 대부분 버립니다. 인기 책 한 권에 소장 줄이 수백 줄일 수 있습니다(정확한 분포는 재지 않음).

"가져오기용 색인과 원문 칸은 남김"의 뜻: 소장 표에는 서비스가 읽지 않는 것 두 가지가 있습니다. ① (도서관, 책 코드) 색인 1,075MB — 가져오기 때 책 번호를 이어 붙이는 데만 씀, ② 제목·저자·출판사 원문 칸 — "원문 보존"으로 정해 둔 것. 지우면 디스크는 줄지만, ①은 같은 책 코드가 두 번 들어가는 것을 DB가 막아 주는 역할도 해서 남기길 권합니다. 평소 검색은 이 둘을 읽지 않아 메모리를 차지하지 않습니다.

7캐시 둘은 개수 상한을 두고 통계(맞힌 비율, 밀려난 수)를 켜서 잰 뒤, 캐시마다 상한을 따로 정함 [안]

코드로 센 추정은 가득 차도 약 15MB입니다. 상한 값이 바뀌면 캐시 결정(ADR-0006)을 새 기록으로 남깁니다.

다른 선택 크기(무게)로 상한(비동기 캐시에서 어떻게 세는지 확인 못 함), 담는 값 줄이기(줄어드는 양이 작음).

8재는 도구는 따로 더하지 않고, Java 명령(jcmd)과 캐시 통계 로그로 잼 [안]

새 의존성이 없고, 밖에서 열리는 주소도 생기지 않습니다.

다른 선택 측정 때만 Actuator(앱 상태 도구)를 내 PC에서만 열리는 관리 포트로 켬. 운영 모니터링은 backlog.

9DB 메모리 값은 Docker 실행 설정(compose.yaml)에 두어 재시작만으로 바꾸고, 가져오는 동안에만 DB 정렬·색인 메모리를 올림. Java 힙 상한은 실행 설정에 [안]

다른 선택 DB 이미지 파일에 넣음(바꿀 때마다 다시 만들어야 함).

10도서관 응답 본문을 두세 벌 복사하는 것은 측정에서 눈에 띌 때만 고침 [안]

질문: #10 맥락 설명

언제: 이용자가 검색하면 우리 서버가 도서관 사이트에 직접 물어보고(검색 결과 쪽, 책 상세 쪽), 그 응답(HTML·XML)을 받아 숫자를 읽어 냅니다. 이 응답 본문을 받는 동안 서버 메모리에 잠깐 담습니다.

dev 코드: BodyLimit, FetchServiceSiteFetcher(2026-10-06 읽음). 322KB는 dev 보고("handoff 밖 추가 작업 C"). 지금 기본은 조회 서버를 거치지 않는 직접 호출(application.yml).

왜 나중에: 응답을 다 읽으면 바로 버려지는 잠깐의 메모리라, 캐시나 DB처럼 계속 차지하지 않습니다. 고치기 쉽지만 효과가 작을 수 있어, 측정에서 이 부분이 눈에 띌 때만 고치자는 제안입니다.

3작은 구조 항목

11고친 시각: 도서관·지역 모듈마다 자기 스키마에 "고칠 때 시각 적기" 장치(트리거)를 두고, 값이 그대로여도 고치면 시각이 바뀜 [안]

공용 장치 하나를 두지 않는 것은 모듈끼리 DB를 나눠 쓰지 않기 위해서입니다. dev 규칙 문서(postgres-patterns)에도 같은 지침을 더합니다.

12YES24 폰 안내: 도서관 표에 "폰에서 사이트가 다르게 보임" 칸(참/거짓)을 더하고 13곳을 켬. 공개 목록과 검색 계획 응답에 그 칸을 실어 보냄 [안]

13도서관 이름 고치기: 새 DB 변경 파일에서 번호로 고치고, seed 스크립트가 "이름 고침 목록"(근거 칸 포함)을 읽어 다음에도 유지 [안]

이미 적용한 seed 파일은 고치지 않습니다(DB 변경 도구가 내용 지문으로 막음).

질문: 도서관 이름이 바뀌는 경우도 있지 않나요? 이력 조사

꽤 자주 바뀝니다. 대학 통합, 정부기관 개편, 회사 사명 변경, 학교 교명 변경, 공공도서관 이름 변경, 행정구역 변경이 있고, 우리 도서관 중 확인된 것만 15곳 남짓입니다. 그래서 이름을 고칠 때 옛 이름·바뀐 날·근거를 함께 남기길 권합니다. 원본: docs/research/library-join/name-changes-2026-10-10.md (출처 확인 2026-10-10).
