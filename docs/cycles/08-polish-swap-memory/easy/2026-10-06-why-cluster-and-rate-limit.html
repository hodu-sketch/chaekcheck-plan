두 질문을 그림으로 풀었습니다.

① 책 제목에 색인이 있는데 왜 같은 책 줄을 붙여 저장하면 메모리가 줄어드나, ② 다른 서비스는 요청 제한과 실제 사용자 IP를 어떻게 하나. 근거는 PostgreSQL·nginx·Cloudflare·GitHub 공식 문서와 우리 DB 측정값입니다(확인 2026-10-06).

1질문 ①: 표가 둘, 하는 일이 둘

제목 색인(GIN)은 "책 표"에서 책을 찾을 때 씁니다. 붙여 저장하는 것은 "소장 표"에서 그 책을 가진 도서관 줄을 꺼낼 때의 이야기입니다.

위 줄(검색 목록)은 붙여 저장해도 그대로입니다. 아래 줄(책 화면)만 달라집니다. 검색 목록은 소장 표를 읽지 않고(dev PgBigmBookSearch), 책 화면만 읽습니다(dev JdbcCatalogHoldings).

2DB는 줄이 아니라 "쪽"을 통째로 읽습니다

PostgreSQL은 표를 8KB짜리 쪽(page)을 이어 붙여 저장하고, 줄 하나를 읽어도 그 줄이 든 쪽 하나를 통째로 메모리에 올립니다.

공식 문서: "모든 표와 색인은 고정 크기(보통 8kB) 쪽의 배열로 저장된다" (PostgreSQL 18 Database Page Layout). 우리 소장 표는 한 쪽에 평균 26.6줄이 들어갑니다(측정, db-memory.md).

책 777의 줄 3개를 읽으려고 쪽 3개를 통째로 올립니다. 쪽마다 나머지 26줄은 다른 책 줄이라 이번엔 쓸모가 없습니다.

3지금 우리 소장 표는 얼마나 흩어져 있나 (측정)

무작위로 고른 책 200권의 소장 11,234줄이 10,732쪽에 흩어져 있습니다. 거의 한 줄에 한 쪽입니다.

위 막대는 측정값(docs/research/deploy/db-memory.md, 2026-10-05), 아래 막대는 한 쪽 평균 26.6줄로 나눈 계산값입니다. MB는 쪽 수 × 8KB로 계산했습니다. 상관도는 0이면 순서가 아무 관계 없음, 1이면 같은 순서입니다.

4메모리에서 무엇이 달라지나

DB는 자주 읽는 쪽을 자기 메모리(shared_buffers)와 운영체제 메모리에 들고 있습니다. 인기 책의 소장을 빠르게 보이려면 그 쪽들이 메모리에 있어야 하는데, 흩어져 있으면 들고 있어야 할 쪽이 훨씬 많습니다.

출처: docs/research/deploy/db-memory.md. 빨간 막대는 로컬 DB 측정, 초록 막대는 계산값이라 붙여 본 뒤 다시 잽니다.

공식 문서도 같은 말을 합니다. CLUSTER(같은 값 줄을 붙여 다시 쓰는 명령) 설명: 한 색인 값에 맞는 줄이 여럿일 때 붙여 두면 "색인이 첫 줄의 쪽을 찾으면 나머지 맞는 줄도 아마 같은 쪽에 있어 디스크 접근을 아끼고 쿼리가 빨라진다"고 적습니다. 반대로 줄 하나씩 무작위로 읽을 때는 순서가 상관없다고 합니다 (PostgreSQL 18 CLUSTER, Notes). 우리 책 화면은 "책 번호 하나에 맞는 줄 여럿"이라 앞의 경우입니다.

6질문 ②: 요청 제한은 "양동이"로 막습니다

nginx는 "새는 양동이" 방식으로 사용자(IP)마다 요청을 일정한 속도로만 흘려보내고, 넘치면 거절합니다.

공식 문서: nginx limit_req는 "leaky bucket" 방식, 분당 단위는 30r/m처럼 쓰고, burst는 한도를 넘어 잠시 받아 둘 수 있는 수, 기본 거절 코드는 503 (nginx limit_req). 우리 숫자(분당 30, 몰림 20, 연결 6)는 dev가 넣은 제안 값입니다.

7막을 때 알려 주는 표준

HTTP/1.1 429 Too Many Requests
Retry-After: 60
"검색을 너무 자주 했어요. 1분쯤 뒤에 다시 해 주세요."

표준(RFC 6585 4절): 429는 "요청이 너무 많음". 응답에 사정을 설명해야 하고(SHOULD), 다시 해도 되는 때를 Retry-After로 알려 줄 수 있으며(MAY), 이 응답은 캐시하면 안 됩니다 (RFC 6585). 지금 우리 서버가 Retry-After를 붙이는지는 확인하지 않았습니다(확인 필요, 설계 때 dev 코드로 봄).

8큰 서비스는 얼마나 막나: GitHub API

출처: GitHub REST API rate limits (확인 2026-10-06). 넘으면 403 또는 429와 retry-after, 남은 횟수는 x-ratelimit-remaining 머리글로 알려 줌. 따로 "동시 요청 100개", "분당 점수 900" 같은 2차 한도도 둠.

우리는 막는 까닭이 다릅니다. 검색 한 번이 서버에서 여러 도서관 사이트로 요청을 퍼뜨립니다. 그래서 우리 한도는 "우리 서버 보호"보다 "도서관 사이트 보호"가 중심입니다. 다른 서비스가 숫자를 어떻게 정했는지 근거는 공식 문서에 없어 확인 못 함입니다.

9실제 사용자 IP는 "믿을 앞단"이 알려 줄 때만

앞에 Cloudflare 같은 중간 단계가 있으면 nginx에는 모든 요청이 Cloudflare 주소로 보입니다. 그래서 Cloudflare가 붙여 준 머리글에서 진짜 IP를 읽는데, 그 머리글은 믿을 앞단에서 온 요청일 때만 믿습니다.

공식 문서: nginx set_real_ip_from은 "올바른 대체 주소를 보낸다고 알려진 믿을 주소"를 정하고, real_ip_header는 그 대체 주소를 읽을 머리글을 정함 (nginx realip). Cloudflare는 IP가 하나만 들어 있는 CF-Connecting-IP를 X-Forwarded-For 대신 보라고 권함 (Cloudflare HTTP headers). 지금 터널 시험 설정은 이미 이렇게 되어 있습니다(dev 공개 시험 기록).

정해 두신 대로, 숫자 확정과 운영의 실제 IP 설정은 배포할 때 실제 이용량과 앞단 구성을 보고 정합니다.
