원본은 spec.md입니다. 화면 모양(폰 설정 창, 상태 칸 색, 글꼴, 돌아가기 등)은 다음 단계인 화면 흐름 페이지에서 그림과 함께 여쭙니다. 구조(어떻게 만들지)는 그다음 설계 단계에서 여쭙니다. 이미 정하신 것은 칩 없이 적었습니다.

2검색 조건 기억

정하신 것: 범위·방문 없이 가입·"지금 빌릴 수 있는 책만"·보기 방식·직접 찾기는 기억하고, 정렬·완전 일치·옮긴이·그림·엮은이는 기억하지 않습니다.

1이미 브라우저에 저장된 정렬·완전 일치·역할 값은 다음 방문 때 지움 [안]

사이클 07 판을 쓴 브라우저에는 이 값이 이미 저장돼 있습니다. 새 판은 그 값을 읽지 않고 지웁니다. 완료 기준: 그 브라우저로 새 판을 열면 정렬이 "기본 순서"이고 저장값에서 사라짐.

다른 선택 읽지만 않고 남겨 둠: 해는 없지만 브라우저에 쓰지 않는 값이 남음.

3막혔을 때와 폰 안내

2429·503은 따로 안내하고, 이미 받은 결과는 지우지 않음 [안]

문구 제안: 429 "검색을 너무 자주 했어요. 1분쯤 뒤에 다시 해 주세요.", 503 "지금 찾는 사람이 많아요. 잠시 뒤에 다시 해 주세요." 두 코드를 API 오류표에도 더합니다. 문구를 바꾸고 싶으면 기타에 적어 주세요.

3YES24 13곳 안내는 폰 폭(640px 이하)에서만 보이고, 링크는 막지 않음 [안]

도서관마다 "폰에서 사이트가 다르게 보임" 표시를 두고 13곳에 켭니다. 문구 "폰에서는 사이트가 다른 화면을 보여요. PC에서 열어 주세요". 어느 링크 옆에 둘지는 화면 페이지에서 그림으로 여쭙니다.

다른 선택 태블릿까지 보임: 태블릿에서도 YES24가 모바일판을 보내는지는 확인 못 함.

4도서관 이름, 고친 시각, 수집 기간

정하신 것: 공식 개명·틀린 이름은 고치고 번호는 그대로. 고칠 목록은 제가 사이트를 확인해 따로 여쭙니다. 고친 시각은 어느 길로 고쳐도 적히게. 가져오기 기록에 사본 수집 기간.

4고친 이름은 seed 스크립트의 "이름 고침 목록"에 남겨 다음 seed에서도 유지 [안]

안 남기면 다음에 seed를 다시 만들 때 옛 이름으로 돌아갈 수 있습니다.

5수집 기간은 서비스에 들어간 도서관의 수집 시각만으로 셈 (건너뛴 도서관은 뺌) [안]

완료 기준: 가져오기 기록의 기간이 서비스 DB의 도서관별 수집 시각 최솟값·최댓값과 같음.

다른 선택 사본 전체(건너뛴 도서관 포함)로 셈: 사본이 언제 것인지는 더 정확하지만 서비스에 보이는 책과 어긋남.

고친 시각 완료 기준: 값을 그대로 두는 고치기 명령을 DB에 직접 실행해도 그 줄의 고친 시각이 바뀜(도서관 표, 지역 표).

5가져오기 시간

정하신 것: 목표는 시간 줄이기. 방법은 여러 방향을 보고 고름(설계 단계, 가져오기 시간 안 페이지 참고).

6"됐다"의 기준: 같은 사본으로 다시 가져올 때 전체 시간과 검색이 멈춘 시간이 둘 다 지난번(40분 36초, 쓰기 27분 동안 멈춤)보다 짧고, 가져오는 동안 검색 첫 쪽이 1초 안 [안]

몇 분까지 줄일지는 방향을 고른 뒤 정합니다. 함께 확인: 가져오다 실패하면 검색 결과가 가져오기 전과 같음, 책 번호가 그대로 이어짐(지난번처럼 1,617,445권 모두).

다른 선택 목표 시간을 지금 숫자로 정함(예: 20분 안): 단계별 시간을 아직 재지 않아 근거가 없음.

7같은 책 소장 줄을 붙여 저장했다는 기준: DB 통계의 책 번호 정렬 정도(상관도)가 0.9 이상 [안]

지금은 0.01입니다(완전히 흩어짐). 1에 가까울수록 붙어 있습니다.

질문: 책 제목에 GIN 색인이 이미 있는데, 같은 책 줄을 붙여 저장하는 게 뭐가 다른가요?

둘은 다른 표의 다른 일입니다. GIN 색인은 책 표에서 "제목이 맞는 책"을 찾는 일이고, 붙여 저장하는 것은 소장 표(도서관 × 책 줄, 2천만 줄)에서 "그 책을 가진 도서관 줄들"을 읽는 일입니다.

단계읽는 표쓰는 것
1. 검색 목록 "사랑"책 표 (160만 줄)제목 GIN 색인 → 맞는 책 번호. 여기서 끝, 소장 표는 안 읽음
2. 책 화면·대출 현황소장 표 (2천만 줄)(책 번호, 도서관) 색인 → 그 책의 소장 줄 위치 → 그 줄들을 실제로 읽음

색인은 "줄이 어디 있는지"만 알려 줍니다. 줄 자체는 DB가 8KB짜리 쪽(page) 단위로 메모리에 올려야 읽을 수 있습니다. 지금은 한 책의 소장 줄이 표 곳곳에 흩어져 있어서, 줄 하나를 읽으려고 쪽 하나를 통째로 올립니다.

그래서 메모리에 미치는 것: DB는 자주 읽는 쪽을 메모리에 들고 있습니다. 흩어져 있으면 인기 책 몇천 권의 소장을 들고 있으려고 그 책과 상관없는 줄이 대부분인 쪽까지 잔뜩 들고 있어야 합니다. 측정: 상위 1,000권의 소장이 지금 1,727MB의 쪽에 흩어져 있고, 붙이면 약 127MB로 계산됩니다(계산값, docs/research/deploy/db-memory.md). 같은 속도에 필요한 메모리가 줄어드는 까닭입니다.

GIN 색인이 하는 1번(검색 목록)에는 영향이 없습니다. 효과는 2번(책 화면·대출 현황)에만 있습니다.

6메모리 줄이기

정하신 것: 먼저 재고 그다음 줄임. 너무 줄여 느려지면 안 됨.

8최적점 기준: 검색 첫 쪽이 1초 안이고, 줄이기 전보다 20% 넘게 느려지기 직전 단계 [안]

완료 기준: 줄이기 전·뒤 측정표(DB 설정, DB가 쓸 수 있는 메모리, 버퍼 적중률, Java 힙, 캐시 항목 수·적중률, 응답 시간)가 있고 고른 설정이 이 기준을 지킴. 가져오기도 고른 Java 힙으로 끝까지 돎.

다른 선택 10%(더 조심), 1초만 지키면 됨(더 많이 줄임).

9찾은 값은 내 PC(WSL, 32GB) 기준으로 쓰고, 운영 서버를 정하면 다시 잼 [안]

10상태별 동작 [안]

  • 가져오는 중: 검색·책 화면은 평소처럼. 교체하는 짧은 순간에 온 요청은 기다렸다 새 데이터로 답함
  • 가져오기 실패: 옛 데이터 그대로, 가져오기 기록에 실패를 남김
  • YES24 안내 도서관이 "확인 실패"일 때도 안내는 보임
  • 메모리를 너무 낮춰 DB가 꺼지면(측정 중에만) 그 단계는 "못 씀"으로 적고 앞 단계로

11이번에 하지 않는 것 [안]

  • 정렬·완전 일치를 계정에 저장
  • 요청 제한 숫자 확정, 실제 사용자 IP 받기 (배포 때)
  • YES24 13곳 링크 숨기기·끄기 (안내만)
  • 도서관 단위 일부 갱신, 자동 갱신 (사이클 09 후보)
  • Redis 같은 바깥 캐시 (서버 한 대)
  • 소장 표 나누기, 상세 주소 저장 안 하기 (디스크가 부담될 때)

질문: 요청 제한 숫자와 실제 사용자 IP 받기를 다른 서비스는 보통 어떻게 하나요?

보통 "IP(또는 계정)마다 시간당·분당 몇 번"으로 막고, 막을 때 429와 "몇 초 뒤 다시"를 알려 줍니다. 실제 IP는 앞단(Cloudflare 등)이 넣어 주는 머리글을, 믿을 수 있는 앞단에서 온 요청일 때만 씁니다.

무엇보통 하는 방법공식 출처 (확인 2026-10-06)
막을 때 응답429 Too Many Requests. 이유를 적고, "몇 초 뒤 다시"를 Retry-After 머리글로 알려 줄 수 있음. 429 응답은 캐시하면 안 됨RFC 6585 4절
큰 서비스 예: GitHub API로그인 안 한 요청은 IP마다 시간당 60번, 로그인하면 시간당 5,000번. 따로 동시 요청 100개, 분당 점수 900 같은 2차 제한. 남은 횟수를 응답 머리글로 알려 주고, 넘으면 403 또는 429 + retry-afterGitHub REST API rate limits
nginx로 막기 (우리가 쓰는 것)"새는 양동이" 방식. IP 주소를 키로, 예: rate=1r/s나 30r/m, 잠깐 몰리는 것은 burst로 허용. 기본 거절 코드는 503이라 429로 바꿔 둠(dev가 이미 그렇게 함)nginx limit_req
실제 IP 받기 (nginx)"믿을 앞단 주소"(set_real_ip_from)에서 온 요청일 때만 그 머리글 값으로 사용자 IP를 바꿈. 믿지 않는 곳에서 온 머리글은 무시 → 사용자가 머리글을 꾸며도 소용없음nginx realip
Cloudflare 뒤일 때X-Forwarded-For 대신 IP 하나만 담긴 CF-Connecting-IP를 보라고 권함Cloudflare HTTP headers

우리에게 대 보면: 지금 숫자(IP마다 분당 30번, 몰림 20번, 동시 연결 6개)는 GitHub의 "로그인 안 한 요청 시간당 60번"보다 훨씬 넉넉합니다. 우리는 검색 한 번이 도서관 수십 곳에 요청을 보내므로 막는 이유가 도서관 사이트 보호라는 점이 다릅니다. 그래서 숫자는 배포 때 실제 이용량을 보고 정하는 쪽(승인하신 대로)이 맞습니다. 지금 Cloudflare 터널 시험 설정은 이미 CF-Connecting-IP를 쓰고, 믿을 주소를 로컬·사설 주소로만 두었습니다(dev 공개 시험 기록).

다른 서비스가 숫자를 어떻게 정했는지(근거)는 공식 문서에 없어 확인 못 함입니다.
