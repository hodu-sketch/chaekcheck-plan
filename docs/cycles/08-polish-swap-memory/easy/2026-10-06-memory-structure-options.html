메모리를 덜 쓰게
구조를 바꾸는 안입니다.

dev 코드를 읽고 메모리가 어디서 쓰이는지 본 뒤, 바꿀 수 있는 곳마다 안을 2~3개씩 만들었습니다. 결정은 돌아오시면 canvas에서 받습니다. 가져오기 시간을 줄이는 안은 조사가 끝나는 대로 따로 보내 드립니다. 원본: architect-proposal.md.

1요청마다 도서관 2,700곳을 다 읽는 것

검색할 때마다 서버가 DB에서 도서관 2,700곳과 가입 규칙을 전부 읽은 뒤, 실제로 찾을 약 390곳만 남기고 나머지를 버립니다.
안내용좋은 점아쉬운 점
가. 필요한 곳만 읽기 (추천)DB에 "검색에 들어가는 도서관만" 달라고 함메모리·DB 읽기 둘 다 줄어듦. 예전 결정("도서관 켜짐 여부는 요청마다 읽음")을 그대로 지킴내 도서관 화면용 전체 목록은 그대로 다 읽음
나. 30초 동안 기억해 두기한 번 읽은 목록을 서버 메모리에 잠깐 둠DB 읽기가 거의 없어짐운영자가 도서관을 끄면 최대 30초 늦게 반영. 예전 결정을 바꿔야 함. 메모리는 오히려 늘 수 있음
다. 목록 응답 미리 만들어 두기내 도서관 화면용 목록을 미리 만들어 둠그 화면만 빨라짐지역마다 내용이 달라 효과가 작음

2책 화면에서 모든 도서관 줄을 읽는 것

책 화면의 대출 현황은 그 책을 가진 모든 도서관의 줄을 DB에서 읽은 뒤, 찾을 도서관만 앱에서 남깁니다.
안좋은 점아쉬운 점
가. DB에서 처음부터 거르기 (추천)인기 책이면 수백 줄이 앱 메모리에 안 올라옴. 이미 있는 색인을 씀같은 책 줄을 붙여 저장한 뒤라면 DB 쪽 차이는 작을 수 있어 재 보고 정함
나. 그대로바꿀 것 없음낭비가 남음

함께 본 것: 가져오기 때만 쓰는 색인(1,075MB)은 남기는 것을 추천합니다. 검색이 읽지 않아 평소 메모리를 차지하지 않고, 같은 도서관 책 코드가 겹치지 않게 막아 줍니다. 원문 칸(제목·저자·출판사 원문)도 "원문 보존" 결정대로 남깁니다.

3캐시 둘

코드 모양으로 세어 보면 두 캐시는 가득 차도 합쳐 약 15MB로 작을 가능성이 큽니다(재 보지 않은 추정). 그래서 "줄이기"보다 "재기"가 먼저입니다.
안내용좋은 점아쉬운 점
가. 개수 상한 그대로 + 통계 켜기 (추천)맞히는 비율·밀려난 수를 보고 캐시마다 상한을 따로 정함단순함. 상세 판정 캐시는 한 칸이 작아 늘려도 메모리가 거의 안 늘어남캐시 상한 결정 기록(ADR-0006)을 고쳐야 함
나. 크기(무게)로 상한담긴 줄 수로 무게를 매김크기가 들쭉날쭉할 때 정확함지금 캐시 방식에서 어떻게 세는지 확인 못 함. 크기가 들쭉날쭉하다는 근거가 없음
다. 담는 값 줄이기안 쓰는 칸을 뺌조금 줄어듦줄어드는 양이 작음

4도서관 응답 본문 복사 (작은 개선)

도서관 사이트 응답을 받을 때 같은 내용을 두세 벌 복사합니다. 고치기 쉽지만 효과는 측정에서 보일 때만 합니다.
  • 받을 때 크기를 미리 정해 복사를 한 번 줄임 (위험 낮음)
  • 조회 서버를 거치는 길에서 한 벌을 줄임. 지금 기본은 직접 호출이라 우선순위가 낮음

정할 것추천다른 안

7새로 찾은 빈틈 하나

가져올 때마다 소장 번호를 1부터 다시 매겨서, 가져오기 직전에 열어 둔 책 화면의 "더 보기"가 다른 도서관 줄을 가리킬 수 있습니다.

지금은 가져오는 동안 검색이 멈춰서 거의 드러나지 않지만, 가져오는 동안에도 검색이 되게 바꾸면 드러납니다. 안: 소장 번호도 지난번 최대 번호 다음부터 매겨, 옛 번호는 "없음"으로 실패하게 함. 가져오기 안을 고를 때 함께 여쭙겠습니다.
