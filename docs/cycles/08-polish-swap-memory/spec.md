## 사용자 이야기

- 이용자는 다음에 열었을 때 고른 범위·방문 없이 가입·"지금 빌릴 수 있는 책만"·보기 방식·직접 찾기는 그대로이고, 정렬과 상세검색 체크는 새로 시작하고 싶다 (scope 1)
- 이용자는 검색이 막혔을 때 "내가 너무 자주 했는지" "서버가 바쁜지" 알고 싶다 (scope 2)
- 폰 이용자는 YES24 모바일판이 이상한 도서관 링크를 누르기 전에 PC에서 열어야 한다는 것을 알고 싶다 (scope 3)
- 이용자는 도서관이 지금 쓰는 이름으로 찾고 싶다 (scope 4)
- 운영자는 언제 어느 길로 고친 줄인지(고친 시각), 가져온 사본이 언제부터 언제까지 모은 것인지(수집 기간)를 알고 싶다 (scope 6·7)
- 이용자는 운영자가 책 목록을 다시 가져오는 동안에도 검색하고 싶다 (scope 9)
- 운영자는 서비스가 쓰는 메모리(DB, 캐시, Java)를 줄이되 검색이 느려지지 않기를 바란다 (scope 10~16, 사용자: "너무 메모리에 맞춰서 줄였다가 느려지면 또 그건 별로니까")
- 이용자는 폰에서 화면이 덜 어색하고 첫 화면이 빨리 뜨기를 바란다 (scope 8)

## 동작 규칙

### R1. 검색 설정 기억 (scope 1)
1. 저장하는 것: 범위(로그인 전 `guestScope`, 로그인 후 `myScope`), 방문 없이 가입, 결과 거르기(지금 빌릴 수 있는 책만/전체), 보기 방식, 직접 찾기 [확정]
2. 저장하지 않는 것: 정렬, 완전 일치(칸별), 옮긴이·그림·엮은이 [확정]. 새로 열면 기본값(기본 순서, 체크 없음)
3. 주소에 값이 있으면 주소가 이김(공유 주소). 그대로 [확정] (사이클 07 구현)
4. 이미 브라우저에 저장된 정렬·완전 일치·역할 값은 다음 방문 때 지움 [확정] (사용자 승인, 2026-10-06)

### R2. 막혔을 때 안내 (scope 2)
1. 웹은 429와 503을 일반 오류와 따로 보이고, 위 문구를 씀 [확정] (사용자 승인, 2026-10-06)
2. API 오류표(`docs/current/api.md`)에 `too_many_requests`(429), `server_busy`(503)를 더함
3. 제한 숫자(분당 30, burst 20, 연결 6, 동시 검색 20, 본문 4MB, 15초)는 [안] 그대로, 배포 때 정함 [확정]

### R3. 폰 사이트 안내 (scope 3)
1. 도서관 표에 "폰에서 사이트가 다르게 보임" 표시를 둠. 값은 dev 검사 결과 13곳 [안: 칸 모양은 설계] → 설계에서 정함: `library.library.mobile_site_differs` boolean 칸 [확정] (사용자 승인, 2026-10-10; `design-delta.md` "데이터"), 칸 이름 [안]
2. 폭 640px 이하(지금 폰 기준 폭)에서만 안내를 보임 [확정] (사용자 승인, 2026-10-06). PC·태블릿에서는 보이지 않음
3. 링크는 막지 않음(누르면 그대로 열림)

### R4. 도서관 이름 고치기 (scope 4)
1. 공식 개명이 확인되거나 이름이 틀린 도서관만 고침. 번호는 바꾸지 않음 [확정]
2. 고칠 목록은 plan이 사이트를 한 번씩 열어(같은 사이트 1건·1초) 표로 만들고 사용자가 곳마다 고름 [확정]
3. 고친 이름은 seed 생성 스크립트에 "이름 고침" 목록으로 남겨 다음 seed에서도 유지 [확정] (사용자 승인, 2026-10-06). 고친 이름 자체도 다시 검증함(공식 출처·사이트 제목으로 확인한 근거를 목록에 함께 적음) (사용자: "그러면서 그 이름 자체에 대한 검증도 다시 했으면 해", 2026-10-06)

### R5. 고친 시각 (scope 6)
1. `updated_at` 칸이 있는 표(지금 `library.library`, `region.region`)는 줄이 고쳐질 때마다 DB가 시각을 적음 [안: 트리거] → 설계에서 정함: 트리거 [확정] (ADR-0068)
2. dev `postgres-patterns` 스킬에 "고친 시각 칸을 두는 표는 이 장치를 함께 둔다"를 더함 [확정 방향]

### R6. 사본 수집 기간 (scope 7)
1. 가져오기 기록 한 줄에 그 가져오기에 들어간 도서관 수집 시각의 가장 이른 값과 가장 늦은 값을 적음 [확정]
2. 서비스에 들어가지 않은(건너뛴) 도서관은 셈에서 뺌 [확정] (사용자 승인, 2026-10-06)

### R7. 가져오기·교체 시간 줄이기 (scope 9)
0. 목표는 가져오기·교체에 걸리는 시간(지금 36~41분)과 그동안 검색이 기다리는 시간을 줄이는 것 [확정]. 방법은 `research.md` 10절의 여러 방향 중 사용자가 고름. 방향은 "새 표에 쓴 뒤 바꿔 끼우기"로 정함(ADR-0065), 아래 1~5가 그 규칙 [확정] (사용자 승인, 2026-10-11, 설계 검토)
1. 가져오기는 기존 책 표를 그대로 둔 채 새 표에 씀. 다 쓰고 색인·통계까지 끝난 뒤 한 번에 바꿔 끼움 [확정] (ADR-0065)
2. 바꿔 끼우는 순간 외에는 책 검색(`/books`, `/books/{id}`)과 대출 현황 스트림이 기다리지 않음 [확정] (사용자 승인, 2026-10-11, 설계 검토)
3. 바꿔 끼우기 전에 실패하면 기존 표가 그대로 남음(지금 "한 트랜잭션, 실패하면 이전 그대로"와 같은 결과)
4. 바꿔 끼운 뒤 옛 표는 지움 [확정] (ADR-0065). 디스크는 가져오는 동안 책 표 두 벌만큼 필요(`research.md` 3절)
5. 책 번호 잇기(사이클 07)는 그대로 지켜짐: 같은 사본으로 다시 가져오면 kept = 전체, new = 0
6. 소장 번호도 같은 소장(도서관, `item_key`)이면 옛 번호를 그대로 이음. 새 소장만 옛 최대 번호 다음부터. 빠진 책·소장은 따로 알림 [확정] (사용자 승인, 2026-10-11, ADR-0070)

### R8. 같은 책 소장 줄 붙여 저장 (scope 10)
1. 새 소장 표에 책 번호 순으로 씀 [확정 방향: DB 메모리 안 1]
2. 가져온 뒤 `pg_stats`의 `book_id` 상관도가 1에 가까워야 함 상관도 0.9 이상 [확정] (사용자 승인, 2026-10-06)

### R9. 메모리 줄이기 (scope 12~16)
1. 먼저 잼, 그다음 줄임. 측정 순서는 `research.md` 7절 [안]
2. 줄이는 대상: PostgreSQL 설정(`shared_buffers` 등), DB 컨테이너가 쓸 수 있는 메모리, 두 캐시(검색 쪽·상세 판정), 서비스 Java 힙, 가져오기 Java 힙 [확정 대상]
3. 멈추는 기준: 검색 첫 쪽 p95가 1초를 넘거나 기준선보다 20% 넘게 늘어나는 첫 단계의 바로 앞 단계를 고름 [확정] (사용자 승인, 2026-10-06)
4. 대출 현황 스트림(책 화면)은 계획한 도서관 줄만 읽음(`CatalogHoldings.holdingsOf(bookIds, libraryIds)`, DB 메모리 안 3) [확정] (ADR-0066)
5. 찾은 값은 로컬 PC(WSL2, 32GB) 기준이고, 운영 서버가 정해지면 다시 잼 [확정] (사용자 승인, 2026-10-06)

### R10. 화면 수정 ⑤ (scope 8, dev 화면 질문 여섯) — 결과는 `flow.md` "검토 결과"

3. 남은 상태 칸 색을 보유 칸과 같은 연보라로 맞춤 [확정] (사용자 승인, 2026-10-06, 화면 흐름 검토)
4. 카드 전체 링크는 그대로 두고, 글자 선택 문제는 두지 않음(신고가 오면 다시) [확정] (사용자 승인, 2026-10-06, 화면 흐름 검토)
5. 글꼴: 한국어 자주 쓰는 글자만 담은 작은 파일로 줄임(서브셋) [확정] (사용자 승인, 2026-10-06, 화면 흐름 검토). 줄인 파일은 다른 글꼴 이름 (OFL 1.1 예약 이름 조건, 나눔바른고딕에 예약 이름이 있는지는 확인 못 함)
6. 돌아가기 [확정] (사용자 제안, 2026-10-06): S8·S9는 맨 아래 오른쪽 "← 돌아가기"(이전 화면, 없으면 첫 화면). S10 내 도서관·S2 지역 고르기에도 오른쪽 아래 "← 돌아가기" + 제목 옆 ⓘ에 "고르는 즉시 저장돼요"(문구 [안]). 사용자: "따로 저장 버튼 없으니 헷갈리거든? 그냥 돌아가기도 우측 아래에 두고 어디 작게 바로바로 저장된다고 i인가 뭐 이런거에 마우스나 손가락 올리면 보이도록 해줘"

- 가져오기 실패: 옛 표 그대로, 새 표는 지움, 가져오기 기록에 실패를 남김 [확정] (사용자 승인, 2026-10-06)
- 막힘(429·503): R2 문구, 결과 목록은 비우지 않고 위에 안내 [확정] (사용자 승인, 2026-10-06)

## 수용 기준

설계 검토(2026-10-11)에서 더한 기준. 지킬 동작은 이미 정한 것(근거를 함께 적음)이고, 확인하는 방법은 따로 적지 않으면 [안]입니다.

- AC-15: 국가서지 원문 다시 쓰기. TTL 파일 지문이 남긴 지문과 같으면 TTL을 풀지 않고 남긴 원문을 쓴다(단계별 시간의 국가서지 단계가 풀기 시간 6.5~9분보다 짧다). 지문이 다르면(또는 처음이면) 지문 줄 지우기 → 원문 표 비우고 다시 뽑아 쓰기 → 맨 마지막에 지문 줄 쓰기 순서로 하고, 중간에 멈추면 지문이 없어 다음 가져오기가 처음부터 다시 푼다 [확정] (사용자 승인, 2026-10-11, 설계 검토; ADR-0069, `design-delta.md` `collection.national_bibliography_source`)
- AC-16: 정리 규칙을 바꿀 때. 묶기·대표값·날짜 규칙만 고친 경우 새 코드로 가져오기 → 바꿔 끼우기를 하고 서비스를 다시 켜지 않아도 다음 검색부터 새 표가 보인다. 검색어 다듬기 규칙을 고친 경우 옛 서비스를 켜 둔 채 새 코드로 가져오고, 바꿔 끼우자마자 서비스를 새 코드로 다시 켠다. 이 순서가 dev `docs/maintenance/3-import.md`에 적혀 있다 [확정] (사용자 제안 "이렇게 해줘", 2026-10-11; ADR-0069)
- AC-17: 검색 계획(`planSearch`)을 들어갈 도서관만 SQL로 읽게 바꾼 뒤에도, 같은 입력(지역, 직접 추가, 로그인 전·후)에서 계획 결과(들어갈 도서관 목록과 순서)가 바꾸기 전과 같다. 바꾸는 것은 [확정] (ADR-0066), 같은지 보는 방법(바꾸기 전 결과와 비교하는 시험) [안]
- AC-18: 동시 검색 상한으로 받는 503 `server_busy` 응답에 `Retry-After: 5` 머리가 있다 [확정] (사용자 승인, 2026-10-11, 설계 검토; `design-delta.md` "API")
