사이클 17 설계:
서버 안을 어떻게 짤지 열 가지

서비스의 모듈·표·API는 바뀌지 않습니다. 정할 것은 서버 안의 구성(컨테이너, 비밀 값, 지표, 백업, 이미지 옮기기)입니다. 설계 제안은 architect-proposal.md에 있습니다. (2026-10-13)

1서버 안 구성 한 장

컨테이너를 두 무리로 나눕니다. 바깥에서 오는 요청을 받는 무리(edge)와, 안에서만 쓰는 무리(app)입니다. 어떤 컨테이너도 서버 바깥에 포트를 열지 않습니다.

nginx는 두 네트워크에 함께 걸쳐 있습니다. Prometheus만 backend의 지표 포트(8081)를 읽습니다.

1네트워크를 edge·app 둘로 나누고, edge 주소 범위는 10.x에서 고름 (예 10.250.0.0/24) [안]

명세에 적은 예시 172.30.0.0/24는 Docker가 저절로 쓰는 주소 범위(172.17~31) 안이라 다른 네트워크와 겹칠 수 있어서 바꾸는 안입니다. Lightsail 사설망 대역과 겹치지 않는지는 서버에서 확인합니다.

네트워크 하나: 단순합니다. 대신 nginx가 믿는 범위에 backend·DB까지 들어갑니다.

추천: 둘로 나눔, 10.x 범위.

2비밀 값과 지표

비밀 값은 backend만 쓰지 않습니다(DB 비밀번호는 DB, 터널 토큰은 cloudflared, Grafana 비밀번호는 grafana). 그래서 모든 컨테이너가 같은 방식으로 받게 하는 안입니다.

2띄우기 스크립트가 Parameter Store에서 값을 읽어 권한을 막은 파일에 쓰고, compose가 그 파일을 읽음 [안]

예: up.sh를 실행하면 /chaekcheck/prod/ 아래 값을 한 번에 받아 본인만 읽을 수 있는 파일로 쓰고, 그 파일로 컨테이너를 띄웁니다. 값을 못 받으면 멈추고 지금 컨테이너는 그대로 둡니다. 코드는 바꾸지 않습니다.

값마다 파일로 넘기기(compose secrets): 컨테이너 설정 화면(docker inspect)에 값이 안 보입니다. 대신 재부팅 때 따로 돌릴 것이 생기고 고칠 곳이 많습니다.
Spring이 직접 읽기(Spring Cloud AWS): backend만 해결되고, 지금 Spring Boot 4.1과 맞는지 공식 표에 없습니다.

추천: 띄우기 스크립트.

3도서관 호출 포기 횟수는 코드에서 직접 셈 (Micrometer 카운터, 포기 이유 두 가지로 나눔) [안]

지금 포기하는 길이 둘인데 하나만 로그를 남깁니다. 두 곳 모두에서 숫자를 올리고, 빠진 로그도 더합니다. 도서관마다 따로 세지는 않습니다(수백 곳이라 숫자 종류가 너무 많아짐).

로그에서 세기: 코드를 덜 고칠 것 같지만, 로그가 없는 길 때문에 어차피 고쳐야 하고 컨테이너가 늘어납니다.

추천: 코드에서 셈.

4지표 주소는 서비스 포트(8080)와 다른 포트(8081)에만 둠 [안]

지금 서비스는 로그인이 필요한 몇 곳 말고는 누구나 부를 수 있게 되어 있습니다. 지표를 다른 포트에 두면 nginx 설정을 실수로 넓혀도 바깥에 나가지 않습니다. 다른 포트에 로그인 검사가 어떻게 걸리는지는 시험으로 확인합니다.

같은 포트, nginx에서만 막기: 설정이 가장 적습니다. 대신 막는 장치가 nginx 규칙 하나입니다.

추천: 다른 포트.

5429 횟수는 nginx 접속 기록을 읽는 exporter로 셈 [안]

한도로 나는 429는 nginx가 돌려줘서 서비스는 모릅니다. 그래서 서비스 지표만으로는 Grafana의 "오류 수(429 포함)"가 0으로 나옵니다. 접속 기록을 읽는 컨테이너 하나를 두면 상태 코드별 횟수와 사용자가 겪는 응답 시간이 나옵니다. 이 도구의 관리 상태와 라이선스는 확인하지 못했습니다.

429는 Cloudflare 대시보드에서만: 더할 것이 없습니다. 대신 정한 Grafana 묶음과 어긋납니다.

추천: exporter. 도구 상태가 나쁘면 Cloudflare로 바꿀지 다시 여쭙니다.

6컨테이너 메모리는 cAdvisor로 셈 [안]

DB뿐 아니라 모든 컨테이너의 메모리가 보여, 이번에 하는 "4GB에 다 들어가는지 재기"에 그대로 씁니다. cAdvisor 자신이 쓰는 메모리는 서버에서 잽니다.

1분마다 숫자를 파일로 쓰는 스크립트: 가장 가볍습니다. 대신 직접 짜는 스크립트가 생깁니다.

추천: cAdvisor. 무거우면 스크립트로 바꿉니다.

3백업

수집한 책 목록은 내 PC가 원본이므로 매일 백업에서 빼고, 회원·내 도서관·기록처럼 운영 중에만 생기는 것만 매일 백업하는 안입니다.

7매일 백업은 수집 책 목록을 뺀 나머지 DB만, 책 목록은 PC의 마지막 반영 파일을 백업으로 봄 [안]

파일이 작고 03:00에 DB 부담이 적을 것으로 봅니다(크기는 재 봄). 되살릴 때는 두 단계입니다: 덤프 복원 → 책 목록 반영 파일 다시 넣기(사이클 11에서 만든 방법).

DB 전체: 되살리기가 한 번에 끝납니다. 대신 DB가 약 8.5GiB라 덤프가 GB 단위이고, 되살릴 때 검색 색인을 다시 만드느라 오래 걸립니다.

추천: 책 목록은 빼고.

8내 PC는 Windows 작업 스케줄러가 백업 전용 SSH 키로 받아 오고, 7개 넘는 것을 지움 [안]

백업 전용 계정은 백업 폴더만 읽을 수 있게 막습니다. PC가 꺼져 있던 날은 켜지자마자 받습니다. 집 IP가 바뀌면 서버 SSH 허용 주소를 고칠 때까지 실패합니다.

Lightsail 버킷을 거침: PC가 꺼져 있어도 쌓입니다. 대신 저장소와 키가 하나 늘고, 요금은 확인하지 못했습니다.

추천: 작업 스케줄러 + SSH.

4조회 서버와 이미지 옮기기

9조회 서버(fetch-service)는 compose에 넣어 두되 꺼 둠 [안]

범위(scope 포함 1)에는 "조회 서버를 띄움"으로 적었는데, 지금 조회 방식이 서버가 직접 묻는 방식(direct)이라 조회 서버를 쓰지 않습니다. 쓰지 않는 Java 프로그램 하나가 4GB에서 메모리를 쓰므로 꺼 두는 안입니다. 대출 조회 나가는 길(ADR-0095)을 다시 정한 뒤 켭니다.

늘 띄움: 범위 글 그대로입니다. 메모리를 씁니다.

추천: 넣어 두되 꺼 둠.

10이미지는 내 PC에서 만들어 SSH로 서버에 옮김 (레지스트리 없음) [안]

PC에서 docker build 뒤 docker save로 묶어 서버에서 docker load합니다. 계정과 비밀 값이 늘지 않습니다. 서버 CPU가 Intel·AMD여야 PC 이미지를 그대로 씁니다(서버를 만든 뒤 확인).

GitHub 비공개 이미지 저장소: 옮기기가 편합니다. 토큰이 하나 늘어납니다.
서버에서 빌드: 4GB에서 빌드가 서비스와 메모리를 다툽니다.

추천: PC에서 만들어 옮김.

5바로잡을 것 하나 (결정 아님, 시험으로 확인)

명세에 접속 기록을 "$uri로 경로만"이라고 적었는데, 화면 주소(/search 등)는 nginx 안에서 /index.html로 바뀐 뒤 기록될 것으로 봅니다. 그러면 어느 화면을 열었는지 안 남습니다.

설계에서는 원래 주소($request_uri)에서 ? 앞까지만 잘라 남기는 방식으로 쓰고, dev가 시험(/search?q=x 요청 뒤 기록 확인)으로 확인합니다. "검색어는 빼고 경로만"이라는 결정은 그대로입니다.
