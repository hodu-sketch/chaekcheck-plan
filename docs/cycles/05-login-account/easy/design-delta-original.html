카카오 연결 해제 웹훅우리 POST /api/v1/auth/webhooks/kakao-unlink가 받음. Authorization: KakaoAK 헤더와 app_id 확인3초 안에 200검증 실패 401, 삭제 없음[확정]
네이버 연결끊기 Callback우리 POST /api/v1/auth/webhooks/naver-unlink가 받음. HmacSHA256 서명 확인, AES128/CBC 복호화(research.md 3절), timestamp가 지금과 5분 넘게 다르면 거절204. 네이버는 다시 보내지 않음검증 실패 401, 삭제 없음[확정] (5분은 사용자 승인, 설계 검토 10)
운영 웹 서버화면 파일을 내려 주고 /api를 Spring으로 넘김(같은 출처). 화면 파일 응답에 Content-Security-Policy, X-Frame-Options: DENY, Strict-Transport-Security, X-Content-Type-Options: nosniff, Referrer-Policy: same-origindev가 설정 예시 파일을 저장소에 둠. 제품과 위치는 배포할 때 정함—[확정] 모양 / CSP 문장 [확인 필요: dev 빌드 결과로 시험]

인계서에 넣을 제약

  1. 상태를 바꾸는 요청은 GET으로 만들지 않음. 변경 메서드는 모두 CSRF(X-XSRF-TOKEN) — 예외는 웹훅 두 곳뿐(ignoringRequestMatchers)
  2. 내 자료 API는 /api/v1/me/...이고, 주소에 계정 번호를 넣지 않음. 계정은 토큰의 sub로만 정함
  3. React에서 dangerouslySetInnerHTML 금지(도서관에서 읽어 온 글자, 약관 본문 포함)
  4. 웹은 토큰 쿠키(access_token, refresh_token)와 세션 쿠키를 읽지 않음(HttpOnly라 읽을 수도 없음). 웹이 읽는 쿠키는 CSRF용 XSRF-TOKEN 하나뿐이고, 그 값을 X-XSRF-TOKEN 헤더에 넣음(이 쿠키는 HttpOnly가 아니고 Secure, SameSite=Lax). 로그인 여부는 /api/v1/me로만 앎. 토큰을 localStorage·sessionStorage에 두지 않음(sessionStorage에는 돌아올 주소만)
  5. 제공자 토큰은 DB에도 서버 기록에도 남기지 않음. Spring 기본 InMemoryOAuth2AuthorizedClientService가 제공자 토큰을 메모리에 계속 쌓지 않게 설정 [확인 필요: 구현 때 Spring 문서]. oauth2Login 성공이 세션 로그인을 만들지 않게 함(SecurityContext 저장소 교체)
  6. Security를 넣어도 기존 경로는 모두 permitAll. 기본 form login, HTTP Basic, 자동 생성 사용자 비밀번호는 끔. 보호 경로는 /api/v1/me/**만
  7. redirect URI는 설정 값으로 명시함(환경 변수. 이름은 dev가 정함). Vite changeOrigin: true인 채로 {baseUrl}을 쓰지 않음
  8. 어드민 키, client secret, JWT 키는 환경 변수로만 둠. 값을 코드나 설정 파일에 쓰지 않음
  9. 웹훅·콜백은 멱등. 서명 비교는 시간이 일정한 비교(MessageDigest.isEqual)로. Kakao 웹훅은 3초 안에 응답
  10. AccountDeleted 안에는 accountId만 넣음(엔티티나 제공자 번호를 넣지 않음)
  11. 401/403은 필터 단계에서 ProblemDetail(code)로 응답함(MVC advice에 오지 않으므로)
  12. 테스트: ModularityTests, 리프레시 교체·재사용·만료, 동시 갱신, 웹훅·콜백 검증 실패, 저장소 기록(AC-15), 비로그인 요청과 토큰이 붙은 요청의 기존 SSE. 다시 로그인(R3), 세션 만료 때 가입 대기의 제공자 연결 끊기, 로그아웃이 리프레시 줄을 지우는지, 쿠키 만료 응답의 Path. AC-15의 "실패하면 기록이 남음"은 테스트 전용 실패 listener로 확인
  1. 결과 코드: 주소에는 정해진 코드만 넣고 토큰·회원번호 같은 값은 넣지 않음. 웹은 목록에 있는 코드만 정해진 문구로 바꿔 보이고 코드 글자를 화면에 그대로 찍지 않음. 서버는 코드로 판단하지 않음. 돌아갈 주소는 /로 시작하고 //로 시작하지 않는 경로만 씀
  2. 임시 값은 HttpSession으로만 다루고, 한 서버에서만 통하는 방식(정적 변수, 직접 만든 메모리 맵)으로 들고 있지 않음. 나중에 Spring Session(Redis)을 설정으로 켰을 때 코드가 그대로 동작해야 함
  3. 리프레시 토큰은 CSPRNG 256비트, DB에는 SHA-256 해시만. JWT는 HS256 하나로 고정하고 키는 사람이 지은 문자열을 쓰지 않음
  4. 발행 저장소는 completion-mode=delete. AC-15는 테스트로 확인(발행 → 기록 생김 → listener 완료 뒤 기록 없음, listener 실패 때 기록 남음)
  5. 별명·프로필 사진은 이번에 받지 않음. 다만 나중에 auth.account에 칸을 더할 수 있게, 계정 조회 응답과 화면 위쪽 배치를 이 확장을 막는 모양으로 굳히지 않음(backlog)
  6. 세션이 만료될 때(10분) 가입 대기가 남아 있으면 제공자 연결을 끊음(카카오 unlink, 네이버 revoke). 실패는 서버 로그에만 남김. 서버를 다시 켜면 메모리 세션이 사라져 그 연결은 끊기지 않음(알고 있는 한계. 사용자가 네이버·카카오의 "연결된 서비스"에서 직접 끊을 수 있고, 우리 DB에는 아무것도 없음)
  7. 쿠키를 지우는 응답(로그아웃, 갱신 실패, 탈퇴)은 발급할 때와 같은 이름·Path·속성으로 만료시킴. 액세스 쿠키는 Path=/api/v1/me, 리프레시 쿠키는 Path=/api/v1/auth. 쿠키 수명(Max-Age)은 액세스 15분, 리프레시는 남은 로그인 기간
  8. 리프레시 갱신은 token_hash와 previous_token_hash 둘 다로 줄을 찾음. 지금 값이면 교체, 바로 앞 값이면 그 줄 삭제(재사용), 어느 쪽도 아니면 줄을 지우지 않고 401(ADR-0038의 한계)
  9. JWT 서명 키를 바꾸는 절차: 환경 변수를 바꾸고 재시작. 옛 키의 액세스 토큰은 401이 되어 웹이 갱신으로 새 토큰을 받음. 리프레시 토큰에는 영향 없음. 자동 교체는 하지 않음(비목표)
  10. /api/v1/me 응답의 loginMethods는 화면에 보이지 않음(AC-5)
  11. POST /api/v1/auth/signup은 201이지만 Location 헤더를 주지 않음(만들어진 것을 조회할 주소가 따로 없음). auth.refresh_token.rotated_at과 루트 패키지의 AccountId는 이번 사이클에 쓰는 곳이 적고 사이클 06을 위한 준비임
  12. 가입 동의 화면을 열어 둔 사이 문서 버전이 바뀌어 409 document_version_mismatch가 오면, 웹은 "약관이 바뀌었어요. 다시 확인해 주세요"를 보이고 GET /api/v1/auth/signup으로 새 버전을 받아 확인란을 모두 비운 상태로 다시 보임 [확정] (사용자 승인, 2026-10-04, 사이클 닫기 검토)
  13. DELETE /api/v1/me의 403 reauthentication_required(본인 확인 기록 없음)는 웹에서 reauthentication_expired와 같은 문구("본인 확인 시간이 지났어요. 탈퇴를 다시 눌러 주세요")로 보임 [확정] (사용자 승인, 2026-10-04, 사이클 닫기 검토)
  14. POST /api/v1/auth/signup이 같은 (method, subject)로 두 번 와서 UNIQUE에 걸리면, 오류로 답하지 않고 먼저 만들어진 계정으로 로그인 처리함(같은 201과 쿠키) [확정] (사용자 승인, 2026-10-04, 사이클 닫기 검토)
  15. 문서 버전의 원본은 서버 설정. 웹의 약관·처리방침 파일에 적힌 버전·시행일이 서버 설정과 같은지 확인하는 테스트를 둠 [확정] (사용자 승인, 2026-10-04, 사이클 닫기 검토)
  16. 카카오 연결 대조: 하루 한 번 카카오 "사용자 목록 가져오기"(GET /v1/user/ids, 어드민 키, 한 번에 100명)로 연결된 회원번호를 모두 받아, 우리 login_method(KAKAO, …)에는 있는데 그 목록에 없는 계정을 탈퇴와 같은 순서(삭제 + AccountDeleted)로 지움. 목록을 끝까지 받지 못한 날(호출 실패, 한도 초과)은 아무도 지우지 않음. 놓친 연결 해제 웹훅을 메우기 위한 것 [확정] (사용자 제안: "카카오는 이렇게 해줘", 2026-10-04)
  17. 오래 로그인하지 않은 계정 정리: 하루 한 번 auth.account.last_login_at이 1년을 넘은 계정을 찾아 탈퇴와 같은 순서(제공자 연결 끊기 시도는 카카오만 가능: 어드민 키. 네이버는 토큰이 없어 건너뜀 → 삭제 + AccountDeleted)로 지움. 놓친 네이버 연결끊기 Callback을 메우고, 쓰지 않는 계정의 자료를 오래 두지 않기 위한 것 [확정] (사용자 승인, 2026-10-04, 사이클 닫기 검토). 1년은 근거 문서가 있는 값이 아니라 제안을 승인한 값. 가입 동의 화면의 "보유·이용 기간"과 처리방침에 "탈퇴할 때까지, 또는 마지막 로그인 뒤 1년"을 적음
  18. chaekcheck.auth.enabled가 꺼져 있으면 사이클 04와 같은 동작(로그인 주소 없음, 보안 필터 없음, 웹에 로그인 관련 요소 없음). 기본값 꺼짐
  19. 세션 쿠키(로그인 도중의 임시 값용): Secure, HttpOnly, SameSite=Lax, Path=/api/v1, 수명 10분 [확정] (사용자 승인, 2026-10-04, 사이클 닫기 검토 4). 로그인 상태를 담지 않으며 공개 API는 이 쿠키를 보지 않음. 여러 서버 대비는 ADR-0040과 backlog
  20. 탈퇴 안내 창(S7)에 "네이버와 chaekcheck의 연결도 끊어요"(카카오로 로그인한 사람에게는 "카카오와…") 한 줄을 보임 [확정] (사용자 제안: "탈퇴할 때 네이버/카카오에 연결된 계정이 탈퇴될거다라는 설명 정도는 보여줘도 되지 않을까?", 2026-10-04). 어느 쪽인지는 그 사람이 로그인한 제공자로 정해지며 사용자에게 묻지 않음. 화면이 이를 알 수 있게 GET /api/v1/me 응답에 loginMethods를 둠. 제공자 이름이 보이는 곳은 이 창 한 곳뿐(AC-5는 그대로)

값의 근거

  • HS256 키 32바이트 이상: RFC 7518 3.2절 [확정] (https://www.rfc-editor.org/rfc/rfc7518.html, 2026-10-04)
  • 리프레시 토큰 256비트: OWASP ASVS 5.0 7.2.3의 "128비트 이상"보다 크게 잡은 값 [확정: 하한] (research.md 8절, 2026-10-03)
  • 시계 오차 60초: Spring Security Resource Server 기본값 [확정] (https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html, 2026-10-04)
  • 외부 연동 표의 [확정]: 출처는 spec.md "데이터 출처"(2026-10-01)와 research.md 3·12·13절
  • modulith.event_publication 공식 DDL: 확인일 2026-10-04 (설계 담당 에이전트). 이 표는 ADR-0002(스키마는 모듈별)의 예외이고, 예외는 이 표 하나뿐이며 어느 모듈의 코드도 이 표를 직접 읽지 않음(ADR-0041)

결정 기록

  • ADR-0036 계정(auth)과 회원 자료(member)를 다른 모듈로 둠 (결정 문장의 "provider + provider_user_id", "세션"은 ADR-0038·0039로 구체화됨)
  • ADR-0037 검색 모듈은 회원을 모르고, 웹이 "내 도서관"을 파라미터로 넘김 (이번 사이클에는 구현 없음. 사이클 06)
  • ADR-0038 로그인 유지는 JWT (짧은 액세스 토큰 + DB의 리프레시 토큰)
  • ADR-0039 로그인 수단 표를 소셜 전용으로 만들지 않고, 제공자 번호는 프로필 API로 받음
  • ADR-0040 로그인 도중의 임시 값은 HttpSession에 두고, 서버 수에 따라 저장소를 설정으로 고름
  • ADR-0041 계정 삭제는 AccountDeleted 이벤트로 알리고, 발행 저장소의 완료 기록은 지움
  • ADR-0042 화면 파일은 앞단 웹 서버가 내려 주고 API와 같은 주소를 쓰며, 인증 주소는 /api/v1/auth 아래에 모음
  • ADR-0043 중요한 기능에만 다시 본인 확인을 받고, 탈퇴는 제공자 재인증 전용 등록으로 처리
  • ADR-0044 앱 전체의 보안 설정은 auth 모듈이 가지고, 보호하는 주소는 /api/v1/me 아래뿐
  • ADR-0045 로그인·탈퇴 결과는 주소 뒤의 코드로 화면에 알리고, 돌아갈 주소는 화면이 기억함
  • ADR-0046 로그인 기능은 서버 설정으로 켜고 끔 (저장소는 나누지 않음)
