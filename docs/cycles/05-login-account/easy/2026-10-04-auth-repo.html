로그인·인증 코드를 다른 저장소에 두고
설정으로 켜고 끌 수 있게 하는 것을 정리했습니다.

캔버스에 남기신 요청입니다(2026-10-04): "이 로그인/인증 기능은 또다른 저장소에 저장하고 싶어 이렇게 하도록 dev에게 알려주게 해", "application파일에 넣든 뭐든 선택해서 할 수 있게", "만들어 달라는 게 아니라 만들도록 dev에게 시켜줘". dev에게 넘기는 인계서에 넣겠습니다. 그 전에 제가 이해한 것이 맞는지, 그리고 지금까지 정하신 것과 부딪치는 곳이 없는지 확인합니다. 고르실 것은 넷입니다(넷째는 2026-10-04에 주신 질문 뒤에 더한 결정 기록).

!저장소 분리는 취소했습니다 (2026-10-04)

"아니다 취소해줘 너 설명 들으니까 저장소 분리 안 하는 것이 나은 것 같아"라고 하셔서, 저장소는 나누지 않는 것으로 되돌렸습니다.
항목지금 상태
1번 (auth 코드를 새 저장소에)취소. auth는 지금 저장소 안의 모듈로 둠
2번 (가져오는 방식과 조건)취소. 필요 없어짐
3번 (설정으로 로그인 기능을 켜고 끔)그대로 두었습니다. 저장소와 상관없이 쓸모가 있습니다(키가 준비되기 전이나 네이버 검수 전에 꺼 둔 채로 배포). 이것도 빼시려면 3번 칩을 미승인으로 바꿔 주세요
4번 (ADR-0046)내용을 "설정으로 켜고 끔"만 남기도록 줄였습니다. 저장하지 않으시려면 미승인으로

설계 문서와 수용 기준에서도 저장소에 관한 부분을 뺐습니다. 비밀 값(키)을 저장소에 넣지 않는다는 규칙은 그대로입니다. 아래 내용은 기록으로 남겨 둔 것이고, 1·2번에 관한 부분은 더는 유효하지 않습니다.

가제가 이해한 모양

코드를 두는 저장소는 둘, 실행되는 서버 프로그램은 지금처럼 하나입니다.

이렇게 이해한 이유는 오늘까지 정하신 것들이 "서버 프로그램 하나"를 전제로 하기 때문입니다. 토큰 쿠키와 확인용 토큰은 화면과 API가 같은 주소일 때 동작하고(ADR-0042), auth는 같은 프로그램 안의 모듈로 정하셨습니다(ADR-0036). 저장소만 나누면 이 결정들은 그대로입니다.

다르게 뜻하신 것이라면: 로그인 서버를 따로 띄우는 것(프로그램 둘)을 뜻하셨다면 1번을 미승인하고 적어 주세요. 그 경우 쿠키와 주소에 관한 결정 몇 가지를 다시 봐야 합니다.

나정해 주실 것 (3가지)

저장소를 나누는 범위, 가져오는 방식, 켜고 끄는 방식입니다.

1auth 모듈의 서버 코드를 새 저장소에 두고, 지금 저장소의 서버가 그것을 가져와 한 프로그램으로 실행함 [안]

새 저장소에 두는 것: auth 모듈의 서버 코드, 그 테스트, auth 표를 만드는 DB 변경 파일. 지금 저장소에 남는 것: 검색 모듈 넷, 화면 코드 전체(로그인 버튼과 가입 동의 화면 포함), 실행 설정.

화면 코드를 지금 저장소에 두는 이유는 로그인 버튼이 검색 화면 위에 있고 화면이 하나의 앱이기 때문입니다.

알아 두실 점: "auth가 다른 모듈에 의존하지 않고 다른 모듈도 auth에 의존하지 않는다"(수용 기준 AC-18)는 그대로 지킵니다. 저장소가 나뉘면 이 경계가 오히려 더 분명해집니다. 대신 두 저장소의 버전을 맞추는 일이 생깁니다.

새 저장소의 이름과 공개 여부는 글 상자에 적어 주세요(예: chaekcheck-auth, 비공개). 적지 않으시면 이름은 dev가 제안하고 사용자가 정하는 것으로 인계서에 적습니다. 왜 나누려 하시는지도 적어 주시면 결정 기록(ADR)의 이유 칸에 그대로 넣습니다. 적지 않으시면 "[이유 미확인]"으로 남깁니다.

다른 선택 1: 저장소는 하나로 두고 auth를 별도 폴더(빌드 단위)로만 나눔. 버전 맞추기가 없지만 코드가 같은 저장소에 있습니다.
다른 선택 2: 로그인 서버를 따로 띄움(프로그램 둘).

2가져오는 방식은 dev가 제안하고, 조건 셋을 인계서에 적음 [안]

다른 저장소의 코드를 가져와 함께 빌드하는 방법은 여럿입니다(저장소 안에 저장소를 끼워 넣기, 빌드 도구의 "함께 빌드" 기능, 패키지 저장소에 올리고 버전으로 받기). 어느 것이 맞는지는 dev 저장소의 빌드 구성을 보고 정하는 것이 낫습니다. 기획 쪽에서는 방법을 못 박지 않고 조건만 겁니다.

조건이유
한 번의 빌드 명령으로 두 저장소의 코드가 함께 빌드되고 테스트됨모듈 경계 테스트(ModularityTests)가 auth까지 포함해 돌아야 함
auth의 DB 변경 파일이 본 프로그램의 DB 변경 순서에 끼워져 실행됨표를 만드는 순서가 어긋나면 서버가 켜지지 않음
방법을 고르면 사용자에게 설명하고 승인받은 뒤 진행. 비밀 값(키, 시크릿)은 어느 저장소에도 넣지 않음저장소 구성은 되돌리기 번거로운 결정

다른 선택: 방법을 지금 정해 주심(글 상자에 적어 주세요).

3서버 설정 파일의 값 하나로 로그인 기능을 켜고 끔. 꺼져 있으면 로그인 없는 지금의 검색 서비스 그대로 [안]

"application 파일에 넣든 뭐든 선택해서 할 수 있게"를 이렇게 이해했습니다. 서버 설정(application.yml이나 환경 변수)에 값 하나를 두고(이름 제안: chaekcheck.auth.enabled), 이 값으로 로그인 기능 전체를 켜고 끕니다.

켜져 있을 때꺼져 있을 때
서버로그인·가입·탈퇴 주소가 동작그 주소들이 없음(404). 보안 설정도 끼어들지 않아 지금과 같은 응답
화면"로그인" 버튼이 보임"로그인" 버튼, 설정 창의 "계정" 절, 가입 동의 화면이 보이지 않음
DBauth 표를 씀auth 표를 쓰지 않음(표를 만들지 말지는 dev가 제안)
네이버·카카오 키있어야 서버가 켜짐없어도 서버가 켜짐

화면이 켜져 있는지 아는 방법은 dev가 제안합니다(예: 서버에 한 번 물어봄). 키가 준비되기 전이나 네이버 검수 전에는 꺼 둔 채로 배포할 수 있습니다.

기본값: 꺼짐을 제안합니다. 설정을 빠뜨렸을 때 키 없이 서버가 켜지지 않는 일을 막습니다. 켜짐이 좋으시면 적어 주세요.

다르게 뜻하신 것이라면: "선택"이 켜고 끄는 것이 아니라 "어느 저장소의 코드를 쓸지 고른다"는 뜻이었다면 적어 주세요.

인증 코드까지 공개하면 위험한가

코드를 공개하는 것 자체가 위험하지는 않습니다. 위험한 것은 비밀 값(키)이 공개되는 것입니다. 그래도 따로 두시려는 뜻은 그대로 반영했습니다.

공개되면위험한가우리 설계
JWT 서명 키, 네이버·카카오 시크릿, 카카오 어드민 키위험함. 누구든 아무 계정으로 로그인하거나 계정을 지울 수 있음어느 저장소에도 넣지 않고 서버 환경 변수로만 둠(인계서 제약)
인증 코드(어떻게 로그인을 처리하는지)그 자체로는 아님. 안전한 설계는 방법이 알려져도 뚫리지 않아야 함. Spring Security, 여러 오픈소스 서비스가 인증 코드를 공개함따로 두기로 하심. 실수로 생긴 약점을 남이 찾기 어렵게 하는 보조 효과는 있음

따로 두면서 생기는 것 둘

① 공개 저장소만 받은 사람도 빌드하고 실행할 수 있어야 합니다. 그래서 조건을 하나 더했습니다: "새 저장소 없이도 빌드·실행되고, 그때는 로그인 없는 검색 서비스로 동작한다". 3번에서 승인하신 "꺼져 있으면 지금의 검색 서비스 그대로"와 같은 동작입니다.

② 코드를 감춰도 구조가 드러나는 곳이 둘 남습니다. 화면 쪽 로그인 코드(공개 저장소에 있음)와 이 기획 저장소의 설계 문서입니다. 기획 저장소(chaekcheck-plan)는 지금 비공개로 되어 있는 것을 확인했습니다(2026-10-04). 이 저장소를 나중에 공개하시면 표 구조, 주소, 토큰 방식이 모두 읽히게 됩니다. 설계가 공개되는 것도 위 표의 둘째 줄과 같은 종류라 그 자체로 위험하지는 않지만, 코드를 감추려는 뜻과 맞추려면 비공개로 두시는 편이 일관됩니다.

"방법이 알려져도 안전해야 한다"는 것은 보안 설계의 오래된 원칙(케르크호프스의 원칙)이고, OWASP도 감추는 것에만 기대지 말라고 합니다. 이번에 원문을 다시 열어 인용하지는 않았습니다.

4"설정으로 로그인 기능을 켜고 끔"을 ADR-0046으로 저장 [안]

저장소 분리를 취소하셨으므로 결정 기록에는 켜고 끄는 설정만 남깁니다. 저장소를 나누려다 취소한 것은 "고르지 않은 안"으로 적습니다.

칸적을 내용
결정서버 설정 값 하나(기본 꺼짐)로 로그인 기능 전체를 켜고 끔. 꺼져 있으면 사이클 04와 같은 검색 서비스. auth는 지금 저장소 안의 모듈. 비밀 값은 저장소에 넣지 않음
이유 (하신 말 그대로)"application파일에 넣든 뭐든 선택해서 할 수 있게" / 저장소 분리 취소: "아니다 취소해줘 너 설명 들으니까 저장소 분리 안 하는 것이 나은 것 같아"
고르지 않은 안auth 서버 코드를 별도 저장소에 둠(위 취소 말씀이 이유) / 켜고 끄는 설정을 두지 않음
감수하는 점켜짐·꺼짐 두 경우를 모두 테스트해야 함. 저장소를 공개하면 인증 코드도 공개됨(비밀 값은 저장소에 없음)

다정해지면 하는 일

dev에게 시키는 것이므로 인계서에 들어갑니다. 기획 쪽에서 코드를 만들지 않습니다.
어디에무엇을 적나

설계 문서 (design-delta.md)저장소 둘의 경계, 가져오는 조건 셋, 설정 값과 꺼졌을 때의 동작
인계서dev가 먼저 가져오는 방식을 제안하고 승인받을 것, 그다음 구현
