검토 에이전트가 설계 문서를 대조했습니다.
고칠 것 16가지는 고쳤고, 정하실 것이 9가지 나왔습니다.

사이클을 닫기 전에 하는 검토입니다(2026-10-04). 검토 에이전트가 설계 문서(design-delta.md)를 명세, 화면 흐름, 범위 문서, ADR, dev 규칙과 대조했습니다. 큰 틀(모듈 경계, 표 규칙, 수용 기준 연결)은 문제없다고 봤고, 빠진 것과 어긋난 것을 찾아냈습니다. 여덟 가지 모두 작은 세부이고 제 추천이 적혀 있습니다.

가이미 고친 것

정하신 것과 어긋나거나 빠져 있던 것들입니다. 새로 정할 것이 없어서 바로 고쳤습니다.
무엇이 문제였나어떻게 고쳤나
이미 가입한 사람이 다시 로그인하는 길이 순서도에 없었음순서도에 더함. 가입할 때와 같은 방식으로 토큰을 내줌
"동의 화면을 떠난 사람은 10분 뒤 연결을 끊는다"를 실제로 할 곳이 설계에 없었음인계서 제약과 테스트 목록에 더함. 서버를 다시 켜면 이 일은 일어나지 않는다는 한계도 적음
"화면은 쿠키를 읽지 않는다"와 "확인용 토큰을 헤더에 넣는다"가 서로 맞지 않았음"토큰 쿠키는 읽지 않고, 확인용 토큰 쿠키 하나만 읽는다"로 고침
로그아웃이 DB의 리프레시 토큰 줄을 지운다는 말이 없었음. 쿠키를 지울 때 주소 범위를 맞춰야 한다는 말도 없었음둘 다 적음
결과 코드 표의 문구가 "…"로 잘려 있었음정하신 문구 전체를 옮김. 탈퇴 쪽 오류에도 네이버인지 카카오인지를 함께 알려 주게 함
액세스 토큰에 "발급 시각"이 들어가 있었음. 명세는 "계정 번호와 만료 시각만"발급 시각을 뺌
범위 문서와 명세에 옛 내용이 남아 있었음(옛 주소, 옛 표 이름, "세션 만료 전까지")명세의 주소를 고치고, 범위 문서에 "설계 단계에서 바뀐 것" 표를 더함
결정 기록 목록에 ADR-0037이 빠져 있었음더함
그 밖: 리프레시 토큰을 찾는 방법의 오류, 쿠키 수명 규칙, 키를 바꾸는 절차, 값의 근거 표시, 낡은 표현, 확인 필요 항목 셋모두 반영

고칠 수 없었던 것이 하나 있습니다. 승인된 ADR은 고치지 못하게 되어 있어서, ADR-0036과 ADR-0040·0041에 덧붙일 설명("나중 ADR로 구체화됨", "서버를 다시 켰을 때의 한계", "기록 표는 모듈별 구역 규칙의 예외")은 ADR이 아니라 설계 문서에 적었습니다.

나정해 주실 것 (9가지)

설계에 답이 없던 세부입니다. 화면 동작 둘, 서버 쪽 값 넷, 기록 둘입니다.

1가입 동의 화면을 열어 둔 사이 약관이 바뀌었으면: 새 약관을 다시 보여 주고 다시 동의받음 [안]

가입 동의 화면을 열 때 화면은 "지금 약관은 몇 번 버전"을 받아 둡니다. 그 화면을 열어 둔 사이 운영자가 약관을 바꾸면, "가입"을 눌렀을 때 서버가 "버전이 다르다"고 거절합니다(서버 코드 document_version_mismatch). 이때 화면이 어떻게 할지가 화면 흐름에 없었습니다.

제안: 안내 문구 "약관이 바뀌었어요. 다시 확인해 주세요"를 보이고, 새 버전을 받아 확인란을 모두 비운 상태로 다시 보여 줍니다.

다른 선택: "저장하지 못했어요. 다시 해 주세요"(이미 있는 저장 실패 상태)로 묶음. 만들 것은 줄지만 왜 실패했는지 알 수 없습니다. 아주 드문 경우입니다.

2본인 확인 기록이 없는데 탈퇴 요청이 오면: "본인 확인 시간이 지났어요"와 같은 문구로 [안]

탈퇴 요청은 "5분 안의 본인 확인 기록"이 있어야 통과합니다. 기록이 아예 없는 경우가 있습니다. 누가 만든 가짜 주소를 눌렀거나, 본인 확인 뒤 서버가 다시 켜진 경우입니다. 서버는 "5분이 지남"과 다른 코드(reauthentication_required)로 답하는데, 화면 문구가 정해져 있지 않았습니다.

제안: 사용자에게는 같은 일이므로 5분 초과와 같은 문구 "본인 확인 시간이 지났어요. 탈퇴를 다시 눌러 주세요"를 보입니다.

다른 선택: 따로 문구를 둠(예: "본인 확인이 필요해요. 탈퇴를 다시 눌러 주세요").

3"가입"이 두 번 눌려 같은 사람이 두 번 가입되려 하면: 두 번째는 이미 만들어진 계정으로 로그인 처리 [안]

버튼을 빠르게 두 번 누르거나 탭 두 개에서 동시에 가입하면 같은 요청이 두 번 갈 수 있습니다. DB는 같은 네이버·카카오 회원번호로 계정이 둘 생기지 않게 막습니다. 두 번째 요청에 무엇을 답할지가 없었습니다.

제안: 오류를 보이지 않고, 먼저 만들어진 계정으로 로그인된 것으로 처리합니다. 사용자는 한 번 가입한 것처럼 보입니다.

다른 선택: 오류로 답하고 "이미 가입돼 있어요"를 보임.

세션 쿠키를 넓게 붙이면 서버가 여러 대일 때 문제가 되지 않나

쿠키가 붙는 범위와 서버 대수는 서로 상관이 없습니다. 서버가 여러 대일 때의 문제는 "쿠키가 어디에 붙느냐"가 아니라 "쿠키가 가리키는 임시 값을 그 서버가 가지고 있느냐"입니다.

상황무슨 일이 생기나정하신 대비
서버 한 대 (지금)임시 값이 그 서버 메모리에 있음. 쿠키가 오면 찾음그대로 동작
서버 여러 대, 임시 값이 각 서버 메모리에로그인을 시작한 서버와 돌아온 요청을 받은 서버가 다르면 임시 값을 못 찾아 "로그인 시간이 지났어요"가 됨이렇게 두지 않음
서버 여러 대, 임시 값이 Redis에어느 서버가 받아도 같은 Redis에서 찾음ADR-0040: 설정으로 Redis를 켬

세 경우 모두 쿠키 범위가 /api/v1인지 더 좁은지는 결과를 바꾸지 않습니다. 걱정하신 문제는 ADR-0040에서 정하신 "여러 대가 되면 Redis로"로 풀리는 문제입니다.

세션을 쓰지 않는 다른 방법이 있나

있습니다. 임시 값을 서버가 들고 있지 않고, 암호화해서 쿠키에 담아 브라우저에 맡기는 방법입니다. 설계 검토 3번에서 "다른 선택"으로 보여 드렸던 길입니다. 그때는 "서버 메모리에 두되 Redis 대비"를 고르셨습니다(ADR-0040).

지금 정해진 것: 서버가 세션으로 들고 있음다른 방법: 암호화한 쿠키에 담음
서버가 여러 대가 되면Redis를 붙여야 함(설정으로 전환)아무것도 안 붙여도 됨. 어느 서버가 받아도 쿠키를 풀어 읽음
서버를 다시 켜면그 순간 로그인하던 사람은 처음부터 다시영향 없음
쿠키가 붙는 범위세션 쿠키 하나를 /api/v1에 넓게 붙임(이 항목의 제안)쿠키를 쓰임새별로 나눠 좁게 붙일 수 있음. 가입용은 /api/v1/auth, 탈퇴 본인 확인용은 /api/v1/me
만들 것Spring 기본 기능 그대로값을 암호화해 쿠키에 넣고 읽는 부품을 직접 만듦. 암호화 열쇠 하나를 더 관리함
동의 화면을 그냥 떠난 사람의 연결 끊기(설계 검토 4번에서 승인)10분 뒤 서버가 끊음못 함. 서버가 그 사람을 기억하지 않음. 연결이 네이버·카카오 쪽에 남음(카카오는 하루 한 번 대조에서 "우리 쪽에 없는 연결"로 보이지만, 그것을 끊는 일은 따로 만들어야 함)
브라우저로 나가는 것뜻 없는 세션 번호암호화된 임시 값. 탈퇴 때는 네이버 접근 토큰이 암호화된 채로 5분 동안 브라우저 쿠키에 있음

세션을 유지하실 때: 여러 서버 대비는 이미 두 곳에 적혀 있습니다. ADR-0040("여러 대가 되면 Spring Session(Redis)을 설정으로 켠다")과 backlog의 "서버 여러 대 대비" 줄입니다. 인계서 제약에도 "임시 값은 세션 창구로만 다루고 한 서버에서만 통하는 방식으로 들고 있지 않는다"가 있습니다.

제 생각: 여러 서버를 분명히 계획하고 계시고 Redis를 늘리고 싶지 않다고 하셨으므로, 암호화 쿠키 쪽이 그 뜻에 더 맞습니다. 대가는 지금 만들 것이 늘어나는 것과 "동의 화면을 떠난 사람의 연결 끊기"를 포기하는 것입니다. 지금 서버가 한 대인 동안은 세션 쪽이 더 단순합니다.

4로그인 도중의 임시 값은 정하신 대로 세션에 두고(ADR-0040, 여러 서버 대비는 backlog에 적혀 있음), 세션 쿠키는 /api/v1 아래 요청에 붙임 [안]

로그인 도중의 임시 값(10분)은 서버가 세션 쿠키로 "누구의 임시 값인지"를 알아봅니다. 이 쿠키는 가입 주소(/api/v1/auth/…)와 탈퇴 주소(/api/v1/me) 양쪽에 붙어야 하므로, 붙는 범위를 둘을 다 덮는 /api/v1로 잡아야 합니다.

그러면 로그인이나 탈퇴를 하는 10분 동안은 검색 요청에도 이 쿠키가 따라갑니다. 9번 설계 결정에서 "검색에는 토큰이 가지 않게"로 정하신 것과 조금 어긋나 보일 수 있어 여쭙니다. 이 쿠키는 토큰이 아닙니다. 로그인 상태를 담지 않고 10분 뒤 사라지며, 검색 쪽은 이 쿠키를 보지 않습니다. 검색이 막힐 일은 없습니다.

쿠키 표시는 토큰 쿠키와 같습니다: Secure, HttpOnly, SameSite=Lax.

다른 선택 1: 세션을 쓰지 않고 암호화한 쿠키에 담음(위 표의 오른쪽). 고르시면 ADR-0040을 대신하는 새 결정 기록을 쓰고, "동의 화면을 떠난 사람의 연결 끊기"는 뺍니다. 미승인에 "암호화 쿠키로"라고 적어 주세요.

다른 선택 2: 탈퇴 주소를 /api/v1/auth 아래로 옮겨 세션 쿠키 범위를 좁힘. 그러면 액세스 토큰 쿠키의 범위를 다시 넓혀야 해서 주소에 관한 결정(ADR-0042)을 다시 열게 됩니다.

기다리는 시간에 대해 공식 문서가 권하는 값이 있나

"몇 초로 하라"는 숫자를 주는 공식 문서는 찾지 못했습니다. "반드시 정해 두라"는 권고는 있습니다.

누가무엇이라고 하나
Spring Boot 문서연결·응답 대기 시간을 설정으로 정할 수 있다고 안내함(spring.http.clients.connect-timeout, read-timeout). 문서의 예시 값은 2초와 1초. 기본값은 이 문서에 적혀 있지 않음
AWS SDK 모범 사례"멈춰 있는 요청을 막으려면 대기 시간을 정해 두라. 일시적인 문제가 있을 때 빨리 실패하게 하라"고 권함. 숫자는 주지 않음
카카오우리가 카카오의 알림에 3초 안에 답하라고 요구함(반대 방향이지만, 카카오가 보는 "정상 응답 시간"의 기준)
네이버·카카오 로그인 문서우리가 기다릴 시간에 대한 안내는 찾지 못함 [확인 못 함]

그래서 제안은 그대로 연결 3초, 응답 5초입니다. 사람이 로그인 버튼을 누르고 기다리는 자리라 길면 답답하고, 너무 짧으면 멀쩡한 로그인이 실패합니다. dev가 실제로 불러 보고 조정하도록 확인 필요에 적습니다.

5네이버·카카오 서버를 부를 때 기다리는 시간: 연결 3초, 응답 5초 [안]

네이버·카카오가 응답하지 않을 때 우리 서버가 얼마나 기다릴지입니다. 값이 없으면 사용자가 로그인 화면에서 한없이 기다릴 수 있습니다. 시간이 지나면 "네이버(카카오) 쪽 문제로 로그인하지 못했어요"를 보입니다.

알아 두실 점: 3초와 5초는 근거 문서가 있는 값이 아니라 제 제안입니다. dev가 실제로 불러 보고 너무 짧으면 조정하도록 "확인 필요"에도 적습니다.

6약관 버전의 원본은 서버 설정. 약관 화면에 보이는 버전과 같은지는 dev 테스트로 확인 [안]

약관 본문은 화면 쪽 파일에 있고, "지금 버전"은 서버 설정에 있습니다. 한쪽만 고치면 화면에 보이는 버전과 동의 기록에 적히는 버전이 달라질 수 있습니다.

제안: 서버 설정을 원본으로 두고, 화면 파일의 버전이 서버 설정과 같은지 확인하는 테스트를 dev가 둡니다. 주소나 표는 늘지 않습니다.

다른 선택: 서버가 "지금 버전"을 알려 주는 공개 주소를 하나 더 만들고 약관 화면이 그것을 받아 표시. 어긋날 일이 없지만 주소가 하나 늘어납니다.

탈퇴할 때 "네이버·카카오와의 연결도 끊긴다"는 설명을 보여 주기

좋은 생각이라 제안에 넣었습니다. 탈퇴 안내 창에 한 줄을 더합니다. 가입한 곳이 네이버면 "네이버", 카카오면 "카카오"로 보입니다.

되돌릴 수 없어요.
가입한 계정으로 한 번 더 로그인해 확인합니다.

"네이버 계정은 그대로 남아요"를 붙인 이유는 "탈퇴하면 네이버 계정이 없어지나" 하는 오해를 막기 위해서입니다. 끊기는 것은 chaekcheck와의 연결뿐입니다.

이 한 줄 때문에 화면이 그 사람이 네이버로 가입했는지 카카오로 가입했는지 알아야 합니다. 그래서 아래 제안(응답에 로그인 수단을 넣음)과 함께 갑니다. 10월 1일에 정하신 "로그인한 화면에 네이버로 로그인됨 같은 표시를 하지 않는다"는 그대로이고, 제공자 이름이 보이는 곳은 탈퇴 안내 창 한 곳뿐입니다.

탈퇴할 때 네이버·카카오를 사용자가 고르게 하면 되지 않나

고르게 할 수도 있습니다. 다만 한 계정은 네이버나 카카오 중 하나로만 가입돼 있어서, 사용자가 고를 것이 실제로는 없습니다.

사용자가 고르게 함화면이 알아서 보냄 (제안)
탈퇴 안내에서 "계속"을 누르면"네이버 / 카카오" 선택 창이 한 번 더 나옴가입한 곳으로 바로 감
잘못 고르면카카오로 가입한 사람이 네이버를 고르면 네이버에서 로그인한 뒤 "가입한 계정으로 확인해 주세요"가 나오고 처음부터 다시잘못 고를 일이 없음
"네이버와의 연결도 끊어요" 안내어느 쪽인지 몰라 "네이버 또는 카카오와의 연결도 끊어요"로만 쓸 수 있음가입한 곳 이름으로 정확히 보임
필요한 것없음"내 계정" 응답에 로그인 수단을 넣음

로그인할 때는 누구인지 아직 모르므로 사용자가 골라야 합니다. 탈퇴할 때는 이미 로그인한 상태라 서버가 그 사람이 어디로 가입했는지 알고 있습니다. 아는 것을 다시 묻지 않으려는 것이 이 제안입니다.

7번을 말씀하신 대로 정리했습니다 (2026-10-04)

제가 같은 설명을 되풀이했습니다. 죄송합니다. 말씀하신 대로입니다. 사용자는 네이버나 카카오 중 하나로 로그인해 있으므로 어느 쪽인지는 이미 정해져 있고, 고를 것도 따로 설명할 것도 없습니다.

그래서 이렇게 정했습니다. 탈퇴 안내 창에 "네이버와 chaekcheck의 연결도 끊어요" 한 줄만 보입니다. 카카오로 로그인한 사람에게는 "카카오와…"로 보입니다. 앞서 덧붙였던 "계정은 그대로 남아요" 문장은 뺐습니다. 화면이 어느 쪽인지 알 수 있게 서버가 알려 주는 것은 dev가 만드는 부분이라 더 여쭙지 않습니다.

7탈퇴 안내 창에 "네이버와 chaekcheck의 연결도 끊어요" 한 줄을 보임 (로그인한 곳이 카카오면 "카카오와…") [안]

탈퇴할 때 화면은 그 사람을 네이버로 보낼지 카카오로 보낼지 알아야 합니다. 그래서 "내 계정" 응답에 로그인 수단을 넣습니다. 명세에는 "계정 번호와 동의 상태"만 적혀 있어서 여쭙니다. 화면에 "네이버로 로그인됨"을 보이지 않는다는 결정(AC-5)은 그대로 지킵니다. 탈퇴 버튼을 눌렀을 때 보낼 곳을 고르는 데만 씁니다.

다른 선택: 응답에 넣지 않고, 탈퇴 본인 확인 시작 주소를 하나로 만들어 서버가 알아서 보냄. 응답은 깔끔해지지만 서버 쪽 주소 구조가 달라집니다.

8결정 기록 둘을 더 남김 (ADR-0044, ADR-0045) [안]

검토 에이전트가 "구조에 영향을 주는데 기록이 없는 결정" 둘을 짚었습니다. 둘 다 이미 정하신 내용이고, 기록만 따로 남기는 것입니다.

번호내용이유로 적을 말
ADR-0044앱 전체의 보안 설정(어느 주소가 로그인이 필요한지, 401·403 응답)은 auth 모듈이 가짐. 로그인이 필요한 주소는 /api/v1/me 아래뿐이고 나머지는 열어 둠[이유 미확인] (설계 안을 승인)
ADR-0045로그인·탈퇴 결과는 주소 뒤의 코드로 화면에 알림. 돌아갈 주소는 화면이 기억함"이렇게 해도 보안 상 안전한거니? 안전하면 이렇게 해줘" (2026-10-04)

다른 선택: 따로 남기지 않음. 내용은 설계 문서에만 있게 됩니다.

카카오는 대조하기로, 네이버는 다른 방법이 있는지

카카오: 말씀하신 대로 정했습니다. 하루 한 번 "연결된 사용자 목록"을 받아 우리 쪽과 대조하고, 목록에 없는 계정을 지웁니다. 목록을 끝까지 받지 못한 날은 아무도 지우지 않습니다(잘못 지우는 일을 막기 위해서입니다).

네이버: 더 알아봤지만 토큰 없이 연결 상태를 묻는 방법은 없었습니다.

알아본 것결과
네이버 가이드의 "연결 상태 확인" 방법없음. 가이드가 안내하는 것은 "접근 토큰이 유효한지 확인"뿐이고, 그 사람의 토큰이 있어야 함
놓친 알림을 다시 받기없음. "실패 요청에 대해서 재시도를 수행하지 않습니다"라고 적혀 있음
카카오처럼 연결된 사용자 목록 받기가이드에서 찾지 못함
네이버 로그인을 쓰는 다른 사이트들이 어떻게 하는지정리된 공식 자료가 없음 [확인 못 함]. 개인 블로그 글들은 "탈퇴 때 토큰을 폐기한다"까지만 다룸

그래서 네이버에 쓸 수 있는 길은 셋입니다.

방법대가
가 (제안)마지막 로그인이 1년을 넘은 계정을 지움놓친 사람의 자료가 길게는 1년 남음. 오래 안 쓴 정상 사용자도 지워짐(다시 로그인하면 새로 가입)
나네이버 갱신 토큰을 암호화해 저장해 두고, 하루 한 번 토큰이 살아 있는지 확인"제공자 토큰을 저장하지 않는다"는 결정을 바꿈. 탈퇴 때 다시 로그인하지 않아도 되는 길이 열리지만 지킬 것이 늘어남
다네이버는 하지 않음놓친 사람의 자료가 그 사람이 돌아올 때까지 남음

아래 제안은 "카카오는 하루 한 번 대조(정해짐) + 네이버는 가"입니다. "가"는 카카오 계정에도 똑같이 적용돼, 대조가 실패한 날이 이어져도 끝이 있습니다.

네이버 개발 가이드(접근 토큰 유효성 확인, 연결끊기 Callback의 재시도 없음): https://github.com/naver/naver-openapi-guide/blob/master/ko/login/devguide/devguide.md (2026-10-04, 요약 도구로 읽음)

9놓친 "연결 끊김" 알림: 카카오는 하루 한 번 목록 대조(정해짐), 여기에 더해 마지막 로그인이 1년을 넘은 계정을 지움(네이버를 위한 방법) [안]

2026-10-04에 주신 질문("만약 우리 서버가 내려가 있다면? 몰아서 받을 수 있도록 못하나?")에서 나온 항목이라 끝에 더했습니다. 놓친 알림을 다시 받는 기능은 네이버·카카오 모두 없습니다. 놓치면 연결을 끊은 사람의 자료가 우리 쪽에 남습니다.

제안: 마지막 로그인이 1년을 넘은 계정을 하루 한 번 찾아 지웁니다. 로그인은 30일마다 다시 하므로, 쓰고 있는 사람의 "마지막 로그인"은 늘 한 달 안입니다. 1년 넘게 로그인하지 않은 계정은 연결을 끊고 떠났거나 쓰지 않는 사람입니다. 네이버와 카카오를 똑같이 다룰 수 있고, 쓰지 않는 사람의 자료를 오래 두지 않는다는 점에서도 맞습니다. 지울 때는 탈퇴와 같은 순서("계정 삭제됨" 알림 포함)를 따릅니다. 가입 동의 화면과 처리방침의 "보유 기간"에 "마지막 로그인 뒤 1년"을 적습니다.

알아 두실 점: 1년은 근거 문서가 있는 값이 아니라 제 제안입니다. 놓친 알림의 자료가 길게는 1년 남습니다. 이번 사이클에 할 일이 하나 늘어납니다(하루 한 번 도는 정리 작업).

다른 선택 1: 카카오만 하루 한 번 "연결된 사용자 목록"을 받아 대조해서 지움. 카카오는 하루 안에 맞춰지지만 네이버는 방법이 없어 그대로 남습니다. 위 제안에 더해 함께 할 수도 있습니다.

다른 선택 2: 이번에는 하지 않고 backlog에 둠. 서버가 내려가 있는 동안에만 생기는 일이라 드뭅니다.

네이버 연결끊기 Callback은 실패해도 다시 보내지 않음: research.md 3절(네이버 개발 가이드 4.4절). 카카오 웹훅의 재전송은 문서에 없음: spec.md 데이터 출처. 카카오 "사용자 목록 가져오기"(/v1/user/ids, 어드민 키, 한 번에 100명, 분당 100회): https://developers.kakao.com/docs/ko/kakaologin/rest-api (2026-10-04, 요약 도구로 읽음)

다확인이 하나 더 생겼습니다

카카오의 "연결 끊김" 알림이 어떤 방식으로 오는지입니다. 정하실 것은 아니고, 알려 드립니다.

카카오 문서는 이 알림이 "GET 또는 POST"로 온다고 적습니다. 우리는 "무언가를 바꾸는 요청은 GET으로 만들지 않는다"로 정했으므로 POST로 받도록 설계했습니다. 카카오 개발자 화면에서 POST를 고를 수 있는지는 확인하지 못했습니다. 웹훅 주소를 등록하실 때 방식 선택이 보이면 POST로 골라 주세요. GET만 된다면 그 주소 하나만 예외로 두도록 설계 문서에 적어 두었습니다.
