먼저 보내신 넷(1·2·3·6)의 답입니다.
3번과 6번은 말씀대로 정했고, 1번과 2번을 다시 여쭙니다.

4번과 5번은 승인으로 적었습니다. 7~12번은 앞 페이지에서 계속 골라 주세요(2026-10-04). 출처는 research.md 13절에 있습니다.

2여러 기기에서 로그인했을 때는 어떻게 되나

걱정하신 문제는 생기지 않습니다. 기기(브라우저)마다 리프레시 토큰이 따로라서 서로 영향을 주지 않습니다.

"이미 쓴 토큰이 또 오면 그 로그인을 끊는다"는 규칙은 한 줄 안에서만 적용됩니다. 폰이 내미는 토큰은 102번 줄의 것이라 101번 줄과 비교되지 않습니다. 여러 기기에서 동시에 로그인하는 것은 9번 명세 결정대로 그대로 됩니다.

문제가 생길 수 있는 곳은 같은 브라우저의 여러 탭뿐입니다. 탭들은 쿠키 하나를 함께 쓰기 때문에, 동시에 갱신하면 한 탭만 새 토큰을 받고 나머지는 옛 토큰을 내밀게 됩니다. 제안 2는 이 탭들 사이에서만 순서를 정하는 것입니다. 같은 PC의 크롬과 엣지도 서로 다른 브라우저라 줄이 따로입니다.

2같은 브라우저의 탭끼리는 화면이 한 번에 한 탭만 갱신하게 함 [안]

처음 제안 그대로입니다. 기기가 여럿인 경우는 따로 처리할 것이 없습니다.

다른 선택: 서버가 바로 앞 토큰을 몇 초 동안 받아 줌(규칙에 예외가 생김).

1서명 방식 둘의 장단점

차이는 "토큰을 확인하는 쪽이 토큰을 만들 수도 있느냐"입니다. 확인하는 곳이 우리 서버 하나뿐인 지금은 그 차이가 드러나지 않습니다.
가. 비밀 키 하나 (HS256, 추천)나. 키 한 쌍 (ES256·RS256)
키하나. 서명과 확인에 같은 키둘. 서명용(비밀)과 확인용(공개해도 됨)
확인하는 쪽이 가진 것으로 토큰을 만들 수 있나있음. 그래서 확인하는 곳이 늘면 비밀을 나눠 가져야 함없음. 확인용 키로는 만들 수 없음
키가 새면누구든 아무 계정의 토큰을 만들 수 있음서명용 키가 새면 같음. 확인용 키는 새도 괜찮음
키를 만드는 법무작위 32바이트 이상. 사람이 지은 비밀번호를 쓰면 안 됨키 쌍을 만들어 파일이나 환경 변수로 보관. 형식을 다루는 일이 늘어남
토큰 크기 (서명 부분)32바이트ES256 64바이트, RS256 256바이트
서명·확인 속도가장 빠름더 느림 (이 서비스 규모에서는 체감 차이 없음)
잘 맞는 경우만드는 곳과 확인하는 곳이 같은 서버다른 서버나 다른 회사가 우리 토큰을 확인해야 할 때
나중에 바꾸는 비용어느 쪽에서 어느 쪽으로든 작음. 액세스 토큰이 15분짜리라 바꾼 뒤 15분 안에 모두 새 방식으로 넘어감. 리프레시 토큰은 서명과 상관없는 DB 값

"가"에서 지킬 것 둘: 키는 무작위 값으로 만듭니다(표준이 사람이 외울 수 있는 비밀번호를 키로 쓰지 말라고 함). 서버는 정한 방식 하나만 받습니다(토큰에 적힌 방식을 그대로 믿으면 생기는 공격이 알려져 있음. Spring의 확인 부품은 방식을 하나로 고정해 씀).

RFC 7518 3.2절(HS256 키는 256비트 이상), RFC 8725 2.1·2.2·3.1·3.5절(방식 바꿔치기, 약한 키, 방식 고정, "Human-memorizable passwords MUST NOT be directly used as the key"). https://www.rfc-editor.org/rfc/rfc8725.txt (2026-10-04). 속도는 일반적인 성질로 적었고 직접 재지 않았습니다.

1비밀 키 하나로 서명하는 방식(HS256, 표의 "가"), 키는 무작위 값을 서버 환경 변수에 [안]

처음 제안 그대로입니다. 서버가 여러 대가 되어도 같은 서비스의 서버들이라 같은 키를 환경 변수로 주면 됩니다. "나"가 필요해지는 때는 다른 서비스가 우리 토큰을 확인하게 될 때입니다.

다른 선택: "나"(ES256). 지금 얻는 것은 없고 키 관리가 늘어납니다.

3로그인 도중의 임시 값: 지금은 서버 메모리에 두고, 서버가 여러 대가 되면 Redis로 바꿀 수 있게

말씀하신 대로 정했습니다. 지금은 서버 메모리에 두고, 서버가 여러 대가 되면 설정만 바꿔 Redis에 두게 합니다. 코드는 두 경우에 같습니다.

어떻게 선택형이 되나

임시 값을 Spring의 세션 창구(HttpSession)에만 넣고 꺼내도록 만듭니다. Spring Session이라는 공식 부품을 더하고 설정을 켜면, 같은 창구가 서버 메모리 대신 Redis에 저장합니다. 공식 문서도 이때 HttpSession을 쓰는 코드는 고칠 필요가 없다고 합니다. 그래서 "한 대: 메모리 / 여러 대: Redis"를 설정으로 고를 수 있습니다.

이번 사이클에서 만드는 것은 메모리 쪽뿐입니다. Redis는 넣지 않습니다. 인계서에는 "임시 값은 세션 창구로만 다루고, 서버 한 대에서만 통하는 방식(전역 변수 등)으로 들고 있지 않는다"를 제약으로 적습니다.

확인이 남은 것: 4번에서 승인하신 "10분 뒤 연결 끊기"는 임시 값이 사라지는 순간을 서버가 알아채야 합니다. Redis로 바꿨을 때 이 알림을 받으려면 Spring Session의 설정이 하나 더 필요하다고 문서에 나옵니다. 전환할 때 확인할 것으로 적어 둡니다.

검색 자료처럼 지금 메모리에 두는 다른 것들도 같은 식으로 고를 수 있게 하자는 말씀은 로그인 범위 밖이라 backlog에 한 줄로 적었습니다.

Spring Session: Redis로 HttpSession을 대신함, 애플리케이션 코드 변경 불필요. https://docs.spring.io/spring-session/reference/configuration/redis.html (2026-10-04, 요약으로 읽음)

이런 값을 Redis에 올려도 안전한가

조건을 지키면 안전합니다. Redis 공식 문서는 Redis를 "믿을 수 있는 환경 안에서, 믿을 수 있는 프로그램만 접속하는 것"으로 설계했다고 적습니다. 그래서 안전은 Redis를 어떻게 두느냐에 달려 있습니다.

지킬 것이유 (Redis 공식 문서)
인터넷에서 Redis에 직접 닿지 못하게 함 (방화벽, 우리 서버만 접속)포트가 밖에 열려 있으면 명령 하나로 자료 전체가 지워질 수 있다고 경고함
접속 비밀번호(사용자별 권한, ACL)를 둠방화벽이 뚫려도 한 겹 더 막기 위함. 비밀번호는 길게
서버와 Redis 사이를 암호화(TLS)비밀번호를 포함한 모든 명령이 기본으로는 암호화 없이 오감. 같은 기기 안이 아니면 TLS를 켬
값마다 수명을 둠 (10분)사라져야 할 값이 남지 않게 함. Spring Session이 자동으로 붙임

우리가 올릴 값 가운데 가장 조심할 것은 네이버가 준 접근 토큰입니다. 탈퇴나 가입 취소 때 연결을 끊으려고 몇 분 들고 있는 값입니다. 이 값은 서버 메모리에 있을 때와 Redis에 있을 때 위험이 같은 종류입니다. 저장소에 닿을 수 있는 사람이 읽을 수 있습니다. 그래서 위 넷을 지키는 것이 조건입니다. Redis가 저장한 값을 스스로 암호화하는지는 이 문서에서 확인하지 못했습니다 [확인 못 함].

로그인 유지(JWT와 리프레시 토큰)는 Redis와 상관없습니다. 리프레시 토큰은 DB에 지문으로만 있습니다.

Redis security: "Redis is designed to be accessed by trusted clients inside trusted environments", protected mode, ACL, TLS. https://redis.io/docs/latest/operate/oss_and_stack/management/security/ (2026-10-04)

값을 암호화해서 Redis나 메모리에 두면 더 안전한가

Redis에 둘 때는 더 안전해집니다. 서버 메모리에 둘 때는 달라지는 것이 거의 없습니다. 차이는 "암호를 푸는 열쇠가 값과 다른 곳에 있느냐"에서 나옵니다.

값을 두는 곳열쇠가 있는 곳암호화로 막는 것못 막는 것
Redis (서버가 여러 대일 때)우리 서버의 환경 변수. Redis와 다른 곳Redis에 누가 접속하거나, Redis의 저장 파일·백업이 새거나, 서버와 Redis 사이 통신을 엿보는 것. 읽어도 뜻 모를 글자만 보임우리 서버 자체가 뚫린 경우 (열쇠도 함께 넘어감)
서버 메모리 (지금)같은 서버의 같은 프로그램 안거의 없음. 값을 읽을 수 있는 사람은 열쇠도 읽을 수 있음—

그래서 이렇게 적어 둡니다. 지금(서버 메모리)은 암호화하지 않습니다. 얻는 것이 없기 때문입니다. 나중에 Redis로 바꿀 때는 민감한 값(네이버가 준 접근 토큰)을 암호화해서 넣습니다. 방식은 AES-GCM이고 열쇠는 서버 환경 변수에 둡니다. 앞의 조건 넷(인터넷에서 못 닿게, 접속 비밀번호, 통신 암호화, 값 수명 10분)에 한 겹을 더하는 것입니다. Redis를 넣는 일 자체가 이번 사이클 밖이므로 이 내용은 backlog의 "서버 여러 대 대비" 줄에 함께 적었습니다.

가장 좋은 보호는 저장하지 않는 것입니다. 그래서 이 값들은 10분 뒤 사라지고, 가입이나 탈퇴가 끝나면 그 자리에서 지웁니다.

OWASP Cryptographic Storage Cheat Sheet: "The best way to protect sensitive information is to not store it in the first place", 열쇠는 암호화한 자료와 다른 곳에 둘 것, AES(가능하면 256비트)와 GCM 같은 인증 방식 사용. https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html (2026-10-04). 표의 "막는 것"은 이 원칙을 우리 구성에 대어 본 것입니다.

6주소 뒤에 결과 코드를 붙여도 안전한가

안전합니다. 코드는 "어떤 문구를 보여 줄지"만 정하고, 로그인 여부나 탈퇴는 코드를 믿고 정하지 않기 때문입니다. "안전하면 이렇게 해줘"라고 하셔서 이대로 정했습니다.
누가 가짜 주소를 만들어 보내면일어나는 일
…?result=login_success아무 일도 없음. 로그인 여부는 쿠키와 서버가 정함. 코드로는 로그인되지 않음
…?result=login_cancelled"로그인을 취소했어요" 한 줄이 보임. 그뿐
…?result=withdraw_reauthenticated화면이 탈퇴를 요청하지만, 서버에 그 사람의 본인 확인 기록(5분)이 없으면 거절함. 탈퇴되지 않음
…?result=<이상한 글자>목록에 없는 코드는 무시함. 코드 글자를 화면에 그대로 찍지 않으므로 화면에 나쁜 코드를 심을 수 없음

지킬 규칙 넷 (인계서 제약에 넣습니다)

① 주소에는 정해진 코드만 넣고, 토큰·회원번호 같은 값은 넣지 않습니다. 주소는 브라우저 기록과 서버 기록에 남기 때문입니다. ② 화면은 목록에 있는 코드만 정해진 문구로 바꿔 보여 줍니다. ③ 서버는 코드가 아니라 쿠키와 자기 기록으로만 판단합니다. ④ "보던 화면으로 돌아가기"는 우리 사이트 안의 주소(/로 시작)만 받아들입니다.

OWASP: 민감한 정보를 주소(query string)에 넣지 말 것, 검증하지 않은 주소로 이동시키지 말 것. 코드에는 민감한 정보가 없고 이동할 주소는 서버가 받지 않으므로 둘 다 해당하지 않음. 이 판단은 설계 안과 위 규칙에 따른 것이고, 구현 뒤 dev 테스트로 확인합니다.
