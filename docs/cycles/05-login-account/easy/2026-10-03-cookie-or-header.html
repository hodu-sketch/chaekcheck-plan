CSRF는 로그인 정보가
"자동으로 같이 전송되기 때문에" 생깁니다.

세션이냐 JWT냐와는 상관없습니다. 로그인 정보를 쿠키에 두면 CSRF 방어가 필요하고, 헤더로 직접 보내면 CSRF는 없지만 XSS에 약해집니다. chaekcheck는 HttpOnly 쿠키 + CSRF 토큰으로 갑니다. 공식 문서 확인일 2026-10-03.

1질문과 답

사용자 질문: "세션으로 하면 굳이 고려할 필요가 없는 거 아니야? 세션 정보를 그냥 필요할 때 같이 전송하면 되는 거 아니야?"
  • "같이 전송되는 것"은 방어가 아니라 원인입니다세션 번호는 쿠키에 있고, 브라우저는 우리 사이트로 가는 요청이면 누가 시작했든 쿠키를 붙입니다. 그래서 다른 사이트가 시작한 요청에도 로그인 정보가 실려 옵니다. OWASP CSRF Prevention Cheat Sheet: "Since browser requests automatically include all cookies including session cookies, this attack works unless proper authorization is used."
  • "필요할 때만 직접 골라서 전송"이라면 맞는 방법입니다우리 화면 코드가 로그인 값을 헤더에 직접 넣어 보내면 브라우저가 자동으로 붙이지 않으므로 CSRF가 없습니다. 대신 그 값을 스크립트가 읽을 수 있는 곳에 둬야 합니다. 여기서 다른 위험(XSS)이 생깁니다. 카드 3에서 설명합니다.

2쿠키에 두면: 다른 사이트가 시작한 요청에도 붙습니다

나쁜 사이트는 우리 쿠키를 읽을 수 없습니다. 하지만 읽을 필요가 없습니다. 브라우저가 대신 붙여 주기 때문입니다.
  • 막는 방법: 자동으로 안 붙는 자리에 값을 하나 더 요구서버가 무작위 값(CSRF 토큰)을 주고, 우리 화면이 바꾸는 요청마다 그 값을 헤더에 넣게 합니다. 나쁜 사이트는 그 값을 읽을 수 없어 헤더를 채우지 못합니다. Spring Security CSRF 문서: 토큰은 브라우저가 자동으로 넣지 않는 자리(HTTP 파라미터나 헤더)에 있어야 하고, 쿠키로 요구하면 소용없음
  • 보조: 쿠키의 SameSite다른 사이트에서 시작한 요청에는 쿠키를 붙이지 말라고 브라우저에 알립니다. 보조로만 쓰라고 합니다. OWASP CSRF Prevention Cheat Sheet: "SameSite is useful as a defense-in-depth control but it does not replace a proper CSRF defense in most deployments."

3헤더로 직접 보내면: CSRF는 없고, 대신 스크립트가 값을 읽을 수 있습니다

헤더는 화면 코드가 넣어야 붙습니다. 그러려면 화면 코드가 그 값을 읽을 수 있어야 하고, 그러면 화면에 끼어든 남의 스크립트도 읽을 수 있습니다.
  • CSRF가 없는 이유다른 사이트는 우리 주소로 가는 요청에 임의의 헤더를 붙일 수 없습니다. 브라우저의 같은 출처 규칙이 막습니다. 값이 헤더로만 오는 구조라면 다른 사이트가 시작한 요청에는 로그인 값이 실리지 않습니다. OWASP CSRF Prevention Cheat Sheet "Disallowing simple requests": 사용자 정의 헤더가 붙은 요청은 브라우저가 먼저 허락을 구함(preflight)
  • 대신 생기는 문제: 값을 둘 곳헤더에 넣으려면 값을 화면 코드가 꺼낼 수 있는 곳에 둬야 합니다. 브라우저에서는 보통 localStorage입니다. 여기에 둔 값은 그 페이지에서 실행되는 모든 스크립트가 읽습니다. XSS가 한 번 나면 값을 통째로 가져갑니다. OWASP HTML5 Security Cheat Sheet: "Do not store session identifiers in local storage as the data is always accessible by JavaScript. Cookies can mitigate this risk using the httpOnly flag." "A single Cross Site Scripting can be used to steal all the data in these objects"
  • HttpOnly 쿠키는 스크립트가 못 읽습니다그래서 쿠키 쪽은 XSS가 나도 값 자체를 밖으로 빼 가지 못합니다. OWASP Session Management Cheat Sheet: HttpOnly는 브라우저가 스크립트에 document.cookie로 쿠키를 주지 않게 함

4두 자리의 비교

한쪽 위험을 없애면 다른 쪽 위험이 생깁니다. 어느 쪽이 방어하기 쉬운가로 고릅니다.
HttpOnly 쿠키 (브라우저가 자동 전송)스크립트가 읽는 곳 + 헤더로 직접 전송
CSRF방어 필요 CSRF 토큰으로 막음. Spring Security가 기본 제공없음
XSS가 났을 때 로그인 값못 읽음빼 갈 수 있음 공격자가 자기 컴퓨터에서 계속 씀
XSS가 났을 때 그 밖의 피해그 페이지가 열려 있는 동안 사용자인 척 요청을 보낼 수 있음같음
세션이냐 JWT냐상관없음상관없음
  • 쿠키 쪽도 XSS에 안전한 것은 아닙니다HttpOnly는 값을 훔쳐 가는 것만 막습니다. 끼어든 스크립트는 우리 화면 안에서 요청을 보낼 수 있고, 그 요청에는 쿠키가 붙습니다. CSRF 토큰도 읽을 수 있습니다. 그래서 XSS는 화면에서 따로 막아야 합니다. OWASP Session Management Cheat Sheet: XSS와 CSRF가 결합되면 브라우저가 쿠키를 붙여 보냄. OWASP CSRF Prevention Cheat Sheet: "Cross-Site Scripting (XSS) can defeat all CSRF mitigation techniques!"

5chaekcheck의 선택

웹은 로그인 토큰을 HttpOnly 쿠키에 두고 CSRF 토큰으로 막습니다. CSRF는 프레임워크가 기본으로 막아 주고, 토큰을 통째로 빼앗기는 것은 한번 나면 되돌릴 방법이 적기 때문입니다.
무엇어떻게
액세스 토큰, 리프레시 토큰HttpOnly·Secure·SameSite=Lax 쿠키. 스크립트가 못 읽음
CSRF 토큰쿠키 XSRF-TOKEN(스크립트가 읽을 수 있음) → 화면이 헤더 X-XSRF-TOKEN에 넣음. 대상은 로그아웃, 가입 동의, 탈퇴, 토큰 갱신
CSRF 대상이 아닌 것검색 등 읽기(GET) 요청. 카카오 웹훅·네이버 콜백(브라우저가 아니라 제공자 서버가 보냄. 어드민 키·서명으로 확인)
XSS화면에서 글자를 글자로만 출력(dangerouslySetInnerHTML 금지). 도서관 사이트에서 온 책 제목·저자도 글자로만
폰 앱 (나중)반대로 갑니다. 토큰을 기기의 보안 저장소에 두고 헤더로 보냅니다. 앱에는 다른 사이트의 스크립트가 끼어들 자리가 없고, 쿠키 자동 전송도 없어 CSRF가 없습니다
