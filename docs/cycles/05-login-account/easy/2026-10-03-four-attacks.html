네 공격 모두 서버가
"요청을 보낸 사람"을 잘못 믿게 만듭니다.

로그인 가로채기, 세션 고정·탈취, 클릭재킹, 남의 자료 접근. 각각 어떻게 일어나고 누가 어떤 원리로 막는지 적었습니다. 막는 방법은 모두 "믿기 전에 하나를 더 확인한다"입니다. 공식 문서 확인일 2026-10-03. chaekcheck 적용은 로그인 유지를 JWT로 정한 것(2026-10-03) 기준입니다.

1로그인 가로채기: 소셜 로그인 절차 중간에 끼어드는 것

소셜 로그인은 네이버·카카오가 브라우저를 우리 주소로 돌려보내며 한 번만 쓰는 code를 주소에 붙여 주는 절차입니다. 이 "돌아오기"를 위조하거나, 오가는 code를 훔치는 공격이 둘 있습니다.

가. 가짜 돌아오기 요청 (로그인 CSRF)

  • 막는 원리: state우리 서버가 로그인을 시작할 때 무작위 값을 만들어 그 브라우저에 묶어 두고, 네이버·카카오에 같이 보냅니다. 돌아올 때 그 값이 다시 붙어 옵니다. 서버는 "이 브라우저가 시작한 로그인의 값과 같은가"를 봅니다. 피해자의 브라우저는 로그인을 시작한 적이 없어서 값이 맞지 않고, 요청은 버려집니다. RFC 6749 10.12: state를 요청과 돌아오기 사이의 상태 유지에 쓰고 CSRF 방지에 써야 함(SHOULD). 네이버는 필수, 카카오는 권장. Spring Security가 자동으로 만들고 확인

나. code 훔치기

  • 어떻게 일어나나code는 주소에 붙어 브라우저를 지나갑니다. 폰에서는 나쁜 앱이 정상 앱과 같은 주소 형식을 등록해 돌아오는 code를 대신 받을 수 있습니다. 훔친 code를 네이버·카카오에 내면 토큰을 받습니다. RFC 7636 1절: authorization code interception attack
  • 막는 원리 넷
    1. code는 한 번만 쓸 수 있고 금방 만료됩니다(최대 10분 권고).
    2. code를 토큰으로 바꿀 때 Client Secret이 필요합니다. 이 값은 우리 서버에만 있고 브라우저에 내려가지 않습니다.
    3. 돌아갈 주소는 앱에 등록한 것과 글자 그대로 같아야 합니다. 공격자 주소로는 code가 가지 않습니다.
    4. PKCE: 로그인을 시작할 때 무작위 값의 해시를 보내고, 토큰으로 바꿀 때 원래 값을 냅니다. code만 훔친 사람은 원래 값을 몰라 실패합니다.
    RFC 6749 10.5(만료·1회 사용), RFC 9700 2.1(주소 정확 일치), RFC 7636 4절(code_verifier 43~128자, S256)
  • chaekcheck에서웹은 1~3번으로 막습니다. Client Secret과 카카오 어드민 키는 서버 환경 변수에만 둡니다. PKCE는 네이버가 받는지 시험해 보고 켜고, 카카오는 문서에 없어 끕니다. 폰 앱을 만들 때는 PKCE가 필수라(RFC 8252) 그때 다시 봅니다.

2세션 고정·탈취: 로그인 상태를 나타내는 값을 손에 넣는 것

로그인한 뒤 브라우저가 들고 다니는 값(세션 번호나 토큰)은 "가진 사람이 곧 그 사용자"입니다. 고정은 로그인 전에 값을 심어 두는 것이고, 탈취는 로그인 뒤에 값을 훔치는 것입니다.

가. 세션 고정

  • 어떻게 일어나나
    1. 공격자가 우리 사이트에 접속해 세션 번호 하나를 받습니다(아직 로그인 전).
    2. 피해자의 브라우저가 그 번호를 쓰게 만듭니다.
    3. 피해자가 그 번호로 로그인합니다. 서버가 번호를 그대로 두면, 공격자가 알고 있는 번호가 "로그인된 번호"가 됩니다.
    OWASP Session Fixation: 원인은 "When authenticating a user, it doesn't assign a new session ID"
  • 막는 원리: 로그인하면 값을 새로 발급로그인에 성공하는 순간 예전 번호를 버리고 새 번호를 줍니다. 공격자가 심어 둔 번호는 로그인 전 것이라 쓸모없습니다. Spring Security의 기본 동작입니다. OWASP Session Management Cheat Sheet: 권한이 바뀌면 세션 ID를 새로 만들 것. OWASP ASVS 5.0 7.2.4. Spring Security: 기본 changeSessionId

나. 세션(토큰) 탈취

  • 어떻게 일어나나OWASP가 드는 경로: 예측할 수 있는 값, 통신을 엿듣기, 화면에 끼어든 스크립트(XSS), 중간에서 가로채기. OWASP Session Hijacking Attack
  • 막는 원리: 경로마다 하나씩
    경로막는 것원리
    예측무작위 값128비트 이상 무작위. JWT는 서명이라 값을 지어낼 수 없음
    엿듣기·가로채기HTTPS, 쿠키 Secure, HSTS 헤더암호화된 연결로만 쿠키를 보냄. HSTS는 브라우저가 처음부터 https로 접속하게 함
    스크립트쿠키 HttpOnly스크립트가 쿠키를 읽지 못함
    OWASP Session Management Cheat Sheet(Secure, HttpOnly), ASVS 7.2.3, Spring Security Headers 문서: 기본 Strict-Transport-Security: max-age=31536000 ; includeSubDomains ; preload
  • chaekcheck에서 (JWT)로그인 뒤에는 세션 번호 대신 토큰 둘을 씁니다. 같은 원리가 그대로 적용됩니다. 두 토큰 쿠키에 Secure·HttpOnly를 붙이고 HTTPS만 씁니다. 로그인할 때마다 토큰을 새로 발급하므로 고정이 성립하지 않습니다. 리프레시 토큰은 쓸 때마다 바뀌어서, 훔친 옛 값이 다시 오면 알아챌 수 있습니다. 액세스 토큰은 훔쳐도 최대 15분입니다.

3클릭재킹: 우리 화면을 남의 페이지 안에 숨겨 놓고 누르게 하는 것

공격자가 자기 페이지 안에 우리 화면을 투명한 틀(iframe)로 겹쳐 놓습니다. 사용자는 공격자 페이지의 버튼을 누른다고 생각하지만 실제로는 그 아래 우리 화면의 버튼을 누릅니다.
  • 막는 원리: "이 페이지를 틀 안에 넣지 마라"는 응답 헤더서버가 응답에 X-Frame-Options: DENY를 붙이면 브라우저가 그 페이지를 어떤 틀 안에도 그리지 않습니다. 공격자 페이지에는 빈 틀만 남습니다. Spring Security가 기본으로 붙입니다. 같은 일을 하는 새 방식은 Content-Security-Policy의 frame-ancestors입니다. Spring Security Headers 문서: "By default, Spring Security disables rendering pages within an iframe … X-Frame-Options: DENY". OWASP Clickjacking Defense Cheat Sheet: DENY는 어떤 도메인도 틀에 넣지 못함
  • 보조: 쿠키의 SameSite다른 사이트의 틀 안에서 우리 화면이 열릴 때 로그인 쿠키가 붙지 않게 합니다. 로그인 안 된 화면만 보이므로 "탈퇴" 같은 버튼이 없습니다. OWASP Clickjacking Defense Cheat Sheet
  • chaekcheck에서대상은 탈퇴, 로그아웃, 가입 동의 화면입니다. 주의할 점이 하나 있습니다. Spring Security의 헤더는 Spring이 보내는 응답에만 붙습니다. React 화면 파일을 다른 서버(예: 웹 서버)가 내려 주면 그 서버에도 같은 헤더를 설정해야 합니다. 화면 파일을 어디서 내려 줄지는 아직 정하지 않았습니다 확인 필요: 배포 구성

4남의 자료 접근: 로그인한 사람이 번호만 바꿔 남의 것을 보는 것

공격자도 정상으로 로그인한 사용자입니다. 요청 속의 번호를 자기 것에서 남의 것으로 바꿨을 때 서버가 그대로 내주면 성립합니다. 영어로 IDOR 또는 BOLA라고 부릅니다.
  • 어떻게 일어나나자기 정보 주소가 /users/123인 사용자가 주소를 /users/124로 바꿉니다. 서버가 "로그인했는가"만 보고 "124가 이 사람 것인가"를 보지 않으면 남의 정보가 나옵니다. 요청 본문에 든 번호도 마찬가지입니다. OWASP IDOR Prevention Cheat Sheet의 예
  • 막는 원리: "누구 것을 다룰지"를 요청에서 받지 않음서버는 로그인 정보(우리는 토큰에 든 계정 번호)에서 "지금 누구인가"를 알고, 그 사람의 자료만 찾습니다. 요청에 적힌 계정 번호는 믿지 않습니다. 번호를 추측하기 어렵게 만드는 것(긴 무작위 번호)은 보조일 뿐 대신할 수 없습니다. OWASP IDOR Prevention Cheat Sheet: 현재 사용자를 세션 정보에서 정하고, 객체마다 접근 검사. OWASP ASVS 5.0 8.2.2(자료 단위 접근 제한), 8.3.1(신뢰할 수 있는 서버 쪽에서 강제, 화면의 스크립트에 맡기지 않음)
  • 라이브러리가 대신 못 하는 이유Spring Security는 "이 주소는 로그인한 사람만"까지는 규칙으로 걸러 줍니다. 하지만 "이 자료가 그 사람 것인가"는 우리 표의 구조를 알아야 판단할 수 있습니다. 그래서 우리 코드가 합니다.
  • chaekcheck에서내 자료 주소를 /api/v1/me, /api/v1/me/regions처럼 번호가 없는 모양으로 정했습니다. 바꿀 번호 자체가 주소에 없습니다. 서버는 토큰의 계정 번호로만 찾습니다. 사이클 06의 지역·내 도서관도 같은 규칙입니다. 이 규칙을 인계서의 제약에 넣습니다.
