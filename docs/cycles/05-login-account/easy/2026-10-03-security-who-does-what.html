OAuth는 "누구인지 확인받는 절차"이고,
Spring Security는 "우리 서버로 오는 요청을 거르는 장치"입니다.

CSRF는 Spring Security가 막고, XSS는 둘 다 직접 막지 못해 화면(React)과 응답 헤더가 막습니다. 공식 문서 확인일 2026-10-03.

1셋이 맡는 구간이 다릅니다

OAuth는 우리 서버와 네이버·카카오 사이의 일입니다. Spring Security는 브라우저와 우리 서버 사이의 일입니다. 화면(React)은 브라우저 안의 일입니다.

2OAuth 2.0: 네이버·카카오에게 "이 사람이 누구인지" 받아 오는 절차

OAuth는 통신 규약(RFC 6749)입니다. 프로그램이 아닙니다. 우리가 비밀번호를 받지 않고도 네이버·카카오가 확인한 결과를 받아 오게 해 줍니다. 우리 서버로 오는 요청을 지키는 일은 하지 않습니다.
순서일어나는 일
1브라우저가 네이버·카카오 화면으로 이동합니다. 우리 서버가 무작위 값 state를 만들어 같이 보냅니다
2사용자가 그쪽에서 로그인합니다. 비밀번호는 우리 서버를 지나가지 않습니다
3네이버·카카오가 브라우저를 우리 주소로 돌려보내며 한 번만 쓰는 code와 state를 붙입니다
4우리 서버가 state가 1번에서 보낸 값과 같은지 확인하고, code와 서버만 아는 비밀값(Client Secret)을 네이버·카카오에 보내 토큰을 받습니다
5그 토큰으로 "이 사람의 번호"를 물어봅니다. 이 번호가 우리 계정을 찾는 열쇠입니다
  • state가 막는 것: 가짜 돌아오기 요청공격자가 자기 code를 붙인 주소를 피해자에게 열게 하면, 피해자가 공격자 계정으로 로그인됩니다. state는 "이 돌아오기가 내가 시작한 로그인에 대한 것인지"를 확인합니다. RFC 6749 10.12. 네이버 필수, 카카오 권장
  • PKCE가 막는 것: code 가로채기1번에서 무작위 값의 해시를 보내고, 4번에서 원래 값을 보냅니다. code를 훔친 사람은 원래 값을 몰라 토큰을 못 받습니다. 네이버는 OIDC 문서에 있고 카카오는 문서에 없습니다. RFC 7636, RFC 9700. 사이클 05 research.md 1절
  • 돌아올 주소를 미리 등록: 엉뚱한 곳으로 보내기 방지네이버·카카오는 앱에 등록된 주소(Callback/Redirect URI)로만 돌려보냅니다. 공격자 사이트로 code가 가지 않습니다. RFC 9700 2.1 "exact string matching"

4CSRF: 다른 사이트가 내 쿠키로 요청을 보내게 하는 것

브라우저는 우리 사이트로 가는 요청에 쿠키를 자동으로 붙입니다. 그래서 다른 사이트가 사용자 모르게 "탈퇴" 같은 요청을 보내게 만들 수 있습니다. Spring Security가 "쿠키 말고 하나 더"를 요구해서 막습니다.
  • 왜 가능한가로그인한 사용자가 나쁜 사이트를 열면, 그 사이트가 숨긴 양식으로 우리 주소에 요청을 보냅니다. 나쁜 사이트는 우리 쿠키를 읽지는 못하지만, 브라우저가 쿠키를 붙여서 보내 줍니다. 서버는 진짜 요청과 구별할 수 없습니다. Spring Security CSRF 문서: "the cookies associated with your bank are still sent along with the request"
  • 막는 원리: CSRF 토큰서버가 무작위 값을 만들어 우리 화면만 읽을 수 있는 곳에 둡니다. 화면은 바꾸는 요청(POST·PUT·DELETE)마다 그 값을 요청 헤더에 넣습니다. 헤더는 브라우저가 자동으로 붙이지 않고, 다른 사이트는 그 값을 읽을 수 없습니다. 값이 없거나 틀리면 403입니다. 같은 문서: 토큰은 "not automatically included by the browser"인 자리에 있어야 함
  • 로그인 값과 CSRF 토큰은 무엇이 다른가둘 다 서버가 만든 무작위 값이고, 기본 방식에서는 둘 다 같은 세션에 딸려 있습니다. 저장하는 곳은 차이가 아닙니다. 차이는 브라우저가 그 값을 서버로 돌려보내는 길입니다.

Spring Security CSRF 문서: 기본은 "stores the expected CSRF token in the HttpSession". CookieCsrfTokenRepository는 "writes to a cookie named XSRF-TOKEN and reads it from an HTTP request header named X-XSRF-TOKEN", HttpOnly를 false로 두는 이유는 자바스크립트가 읽어야 해서. 로그인·로그아웃 성공 때 쿠키를 지움
  • 보조: 쿠키의 SameSite다른 사이트에서 시작된 요청에는 쿠키를 붙이지 말라는 표시입니다. Spring 문서는 이것을 유일한 방어가 아니라 보조로 쓰라고 합니다.
  • chaekcheck에서검색 API는 읽기(GET)라 해당 없습니다. 대상은 로그아웃, 가입 동의, 탈퇴입니다. React 화면이라 위 표의 둘째 방식(csrf.spa())을 씁니다. 토큰이 세션이 아니라 쿠키에 있으므로, 나중에 로그인 유지 방식을 바꿔도 이 방어는 그대로입니다. JWT를 쿠키에 담아도 CSRF 방어는 똑같이 필요합니다. Spring 문서: 무상태여도 쿠키를 쓰면 CSRF에 취약

5XSS: 우리 화면에서 남의 스크립트가 실행되는 것

XSS는 브라우저 안에서 일어납니다. OAuth도 Spring Security도 직접 막지 못합니다. 화면이 "글자를 글자로만 출력"해서 막고, 쿠키 표시와 응답 헤더가 피해를 줄입니다.
  • 왜 가능한가바깥에서 온 글자(검색어, 도서관 사이트에서 읽어 온 책 제목)를 화면이 HTML로 해석하면, 그 안의 <script>가 우리 사이트 권한으로 실행됩니다. 실행된 스크립트는 로그인한 사용자인 척 요청을 보낼 수 있습니다. CSRF 토큰도 읽을 수 있어서 CSRF 방어까지 뚫립니다.
  • 1차 방어: 화면이 글자를 글자로만 출력<를 &lt;로 바꿔 출력하면 태그로 해석되지 않습니다. React는 값을 넣을 때 이 처리를 기본으로 합니다. 예외는 dangerouslySetInnerHTML이고, 이것을 쓰지 않는 것이 규칙입니다. OWASP XSS Prevention Cheat Sheet: 모든 변수를 검증하고 이스케이프. React의 dangerouslySetInnerHTML은 보호의 빈틈
  • 피해 줄이기: 쿠키의 HttpOnly스크립트가 세션 쿠키를 읽지 못하게 합니다. XSS가 나더라도 세션 번호를 밖으로 빼 가지 못합니다. 로그인 토큰을 localStorage에 두면 이 보호가 없습니다.
  • 피해 줄이기: Content-Security-Policy 헤더"이 페이지는 우리 주소의 스크립트만 실행"을 브라우저에 알립니다. Spring Security는 이 헤더를 기본으로 넣지 않습니다. 직접 정책을 적어야 합니다. OWASP는 이것을 1차 방어로 삼지 말라고 합니다. Spring Security Headers 문서: "does not add Content Security Policy by default"
