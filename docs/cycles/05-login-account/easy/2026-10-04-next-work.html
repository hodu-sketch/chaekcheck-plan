plan 세션이 할 일과, 나란히 할 수 있는 일을 정리했습니다.

2여섯 작업마다 plan이 할 일

절반은 이미 조사나 제안이 있어서, 새로 조사할 것보다 사용자께 여쭤서 정할 것이 많습니다.
작업이미 있는 것plan이 할 일
① 책 묶기 알려주기같은 책을 하나로 묶는 규칙은 사이클 04에서 만들어짐(docs/research/ebook-catalog/same-book-isbn.md)이 말의 뜻을 먼저 확인(아래 4번 카드). 그 뒤 화면과 문구를 정함
② 책검색, 직장/지역 UI검색 화면과 지역 고르기 창이 있음무엇을 바꾸고 싶으신지 여쭤보고, 지금 화면을 보고 바뀐 화면을 PC·태블릿·폰으로 그려 정함
③ 직장별 도서관 매핑가입 자격 규칙에 "직장"이 이미 있고(ADR-0004), 검색이 직장 지역을 받음뜻을 먼저 확인(아래 4번 카드). 직장 지역 기준이면 새로 만들 것은 "저장"뿐
④ 내 도서관밑그림과 제안이 있음(docs/research/member-and-alerts/outline.md 2절, integration-plan.md 3.2절). 모듈 둘로 나누기와 검색 연결 방식은 이미 정하심남은 질문 넷을 여쭘: 자동으로 들어온 도서관을 뺄 수 있게 할지 / 로그인 뒤 기본 필터 / 직접 추가한 도서관의 정렬 위치와 개수 상한 / /api/v1/me에 합쳐 줄지. 그 뒤 설계와 인계서
⑤ 정렬, UI 이상한 것 수정정렬 후보 목록이 있음(docs/backlog.md "검색·조회" 첫 항목). "이상한 것"의 목록은 없음이상한 곳의 목록을 받아 적고(화면 캡처면 충분), 정렬은 후보 가운데 이번에 넣을 것만 고르시게 함
⑥ 배포(카카오 로그인만)카카오만 켜는 설정, 웹 서버 설정 예시공식 문서로 조사: 올릴 곳 후보와 값, 검색에 쓰는 PostgreSQL 확장 pg_bigm을 허용하는지, 책 68만 권을 운영 DB로 옮기는 방법. 그리고 공개 전에 채울 것 목록(아래 6번 카드)
남은 질문 넷: integration-plan.md 6절 "05b". pg_bigm이 서버 설정을 요구한다는 것: chaekcheck-dev docs/plan-feedback.md "새로 알게 된 제약" (2026-10-04 확인)

나란히 해도 되는 것이유
배포 조사와 기능 문서서로 다른 것을 다룸. CLAUDE.md가 사이클 밖 조사를 docs/research/에 두도록 허용함
dev가 06을 만드는 동안 plan이 07 문서를 씀07은 검색 화면, 06은 회원 저장이라 정할 내용이 겹치지 않음
서버 쪽 06과 0706은 새 member 모듈, 07은 catalog 모듈. 모듈끼리 서로의 안쪽을 건드리지 않는 것이 이 프로젝트의 규칙(ADR-0001)
나란히 하면 안 되는 것이유
dev 두 곳이 06과 07을 동시에 구현둘 다 검색 화면 파일(SearchPage.tsx)을 고침. 06은 "내 도서관만" 스위치, 07은 정렬과 화면 수정. 합칠 때 충돌함
인계서 둘을 한꺼번에 넘김dev가 읽는 docs/current/handoff.md는 "지금 인계서 하나만" 두는 파일(CLAUDE.md)
④ 내 도서관을 ③보다 먼저내 도서관은 "지역으로 자동 + 직접 추가"를 합친 목록이라 지역 저장이 먼저 있어야 함(outline.md 2.2)

1세 갈래로 나누고, plan과 dev를 한 사이클씩 엇갈려 진행 [안]

사이클 06은 회원(지역·직장 저장, 직장 매핑, 내 도서관), 사이클 07은 검색 화면(책 묶기 알려주기, 책검색 화면, 정렬, 이상한 곳 수정)으로 묶습니다. 배포 조사는 사이클 밖에서 지금 시작합니다. 06 인계서를 넘기면 dev를 기다리지 않고 바로 07 문서를 씁니다. 07 인계서가 먼저 끝나면 사이클 폴더에만 두었다가, dev가 06을 마치면 docs/current/handoff.md로 옮깁니다.

지금 규칙에서 달라지는 것: CLAUDE.md는 "앞 사이클이 실제로 만들어진 것을 본 뒤 다음 사이클을 시작"하게 되어 있습니다. 이 안에서는 07을 시작할 때 06이 아직 만들어지지 않았으므로, 06 되돌아보기는 dev가 끝낸 뒤로 미룹니다. 06을 만들다 설계가 달라지면 07 문서를 고쳐야 할 수 있습니다.

다른 선택: 지금처럼 한 사이클씩 차례로(안전하지만 dev가 만드는 동안 plan이 기다림). 여섯 작업을 사이클 하나로(문서 한 벌이지만 인계서가 커지고 하나가 막히면 전부 늦어짐). 06과 07을 dev 두 곳에서 동시에(가장 빠를 수 있지만 검색 화면 파일 충돌을 손으로 풀어야 함).

2사이클마다 캔버스 결정을 두 번으로 줄임: "규칙과 화면" 한 번, "설계" 한 번 [안]

사이클 05에서는 명세, 화면, 설계, 결정 기록, 검토, 인계서를 따로따로 결정하셨습니다(결정 60개 남짓). 이번에는 명세와 화면을 한 페이지에서, 설계와 결정 기록을 한 페이지에서 받습니다. 문서 자체(spec, flow, design-delta, handoff)와 마지막 검토는 그대로 만듭니다. 결정 기록(ADR)은 모듈이나 표가 새로 생기는 결정에만 씁니다.

다른 선택: 지금처럼 단계마다 따로(꼼꼼하지만 사용자께서 캔버스를 여는 횟수가 두 배 이상). 감수하는 점: 한 페이지가 길어지고, 화면을 보다가 규칙을 바꾸면 같은 페이지 안에서 다시 고쳐야 합니다.

4뜻을 확인해야 하는 두 가지

두 작업은 적어 주신 말만으로 범위가 갈립니다. 제가 이해한 뜻을 적었으니, 다르면 기타에 적어 주세요.

3"책 묶기 알려주기"는 검색 결과와 책 화면에서 "여러 도서관의 책을 한 책으로 묶어 보여 준다"는 것을 화면에 알려 주는 일로 이해함 [안]

예: 책 화면에 "제목·지은이·출판사가 같은 책을 하나로 묶었어요" 같은 안내와, 묶인 판(종이책 ISBN이 다른 판 등)을 볼 수 있는 자리를 둡니다. 문구와 자리는 사이클에서 그려 정합니다. 묶는 규칙 자체는 바꾸지 않습니다.

다른 뜻일 수 있는 것: 묶는 규칙을 고치는 일(같은 책인데 따로 나오거나 다른 책이 묶이는 것을 고침). 수집 세션이 정한 "책 번호 유지"를 넣는 일. 어느 쪽인지 확인 못 함.

4"직장별 도서관 매핑"은 직장이 있는 시·군·구를 저장하면 그 지역 재직자가 가입할 수 있는 도서관이 내 도서관에 자동으로 들어오는 일로 이해함 [안]

예: 직장을 "서울 중구"로 저장하면, 서울 재직자가 가입할 수 있는 도서관이 내 도서관에 들어옵니다. 판정은 지금 검색이 쓰는 것을 그대로 씁니다. 새로 만드는 것은 로그인한 사람의 지역을 서버에 저장하는 것입니다.

다른 뜻일 수 있는 것: 회사·대학이 직원에게 주는 전자도서관(소속 자격)을 넣는 일. 이쪽은 기관 목록과 가입 자격 조사, 서비스에 없는 기관 2,506곳을 넣는 일이 먼저 필요해서(docs/backlog.md "웹러브 북스 기관을 서비스 도서관으로 넣기") 10월 6일 안에는 어렵다고 봅니다.

5수집 세션이 정한 "책 번호 유지"를 언제 넣나

내 도서관이 도서관만 저장하면, 책 번호 유지는 배포 뒤로 미뤄도 됩니다.

정해진 것은 "책 번호 유지는 회원이 책을 저장하는 기능보다 먼저"입니다. 내 도서관 밑그림이 저장하는 것은 지역과 도서관 번호뿐이고, 책을 저장하는 것은 알림(관심 책)입니다.

docs/research/ebook-catalog/catalog-refresh.md 5.2절 4번, outline.md 2.1 "저장하는 것", integration-plan.md 5절 "06 알림: 관심 책"

5이번 여섯 작업에서는 책을 저장하지 않고, 책 번호 유지는 배포 뒤 알림 사이클 앞에 넣음 [안]

내 도서관은 도서관만 저장합니다. 감수하는 점: 배포한 뒤 책 목록을 다시 가져오면 책 번호가 바뀔 수 있어서, 누군가 공유해 둔 책 주소(/books/번호)가 "책을 찾을 수 없어요"로 나올 수 있습니다.

다른 선택: 책 번호 유지를 배포 전에 넣음(공유한 주소가 유지되지만 작업이 하나 늘어 10월 6일이 더 빠듯해짐).
