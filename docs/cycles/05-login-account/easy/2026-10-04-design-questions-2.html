9·10·11번은 승인으로 적었습니다.
7·8·12번을 그림과 함께 다시 설명합니다.

설계 검토 두 번째 답입니다(2026-10-04). 10번에 남기신 질문의 답도 여기 있습니다. 고르실 것은 7, 8, 12-가, 12-나 넷입니다.

10리프레시 토큰을 DB에 안전하게 넣는 방법

값 그대로가 아니라 "지문"만 저장합니다. DB를 통째로 도둑맞아도 그것으로는 로그인을 이어 갈 수 없습니다.
장치무엇을 막나
토큰은 추측할 수 없는 긴 무작위 값 (256비트)값을 찍어서 맞히는 것
DB에는 그 값의 지문(SHA-256 해시)만 저장. 지문에서 원래 값을 되찾을 수 없음DB가 새거나 DB를 볼 수 있는 사람이 토큰을 꺼내 쓰는 것
원래 값은 사용자 브라우저의 쿠키에만 있고, 화면 코드가 읽지 못함 (HttpOnly)화면에 심긴 나쁜 코드가 토큰을 읽어 가는 것
쓸 때마다 새 값으로 바꾸고, 이미 쓴 값이 또 오면 그 로그인을 끊음 (승인하신 규칙)훔친 토큰을 계속 쓰는 것
로그인한 지 30일이 지나면 만료, 로그아웃·탈퇴 때 그 줄을 지움오래된 토큰이 남아 쓰이는 것

비밀번호와 달리 느린 해시나 소금(salt)은 쓰지 않습니다. 비밀번호는 사람이 지어 짧고 뻔하기 때문에 그런 장치가 필요하지만, 이 토큰은 기계가 만든 긴 무작위 값이라 지문을 보고 원래 값을 찾아낼 수 없습니다.

OWASP ASVS 5.0 7.2.3: 참조 토큰은 암호학적으로 안전한 난수로 128비트 이상 (research.md 8절, 2026-10-03). 해시로 저장하는 것은 설계 안의 제안이고 승인하신 10번에 들어 있습니다.

7탈퇴 본인 확인: 두 방법이 어떻게 다른가

맞게 보셨습니다. 추천안(가)은 "돌아올 주소"가 더 필요합니다. 다른 안(나)은 주소는 그대로인 대신 서버 코드가 늘어납니다. 어느 쪽 부담을 질지의 선택입니다.

서버가 풀어야 할 문제는 하나입니다. 네이버·카카오에서 사람이 돌아왔을 때 "로그인하러 갔던 사람인지, 탈퇴 본인 확인하러 갔던 사람인지"를 알아야 합니다. 앞의 사람에게는 로그인을 시켜 주고, 뒤의 사람에게는 로그인 대신 "같은 계정이 맞나"만 확인해야 하기 때문입니다.

가. 돌아올 주소를 따로 둠 (추천)나. 주소는 하나, 떠날 때 "탈퇴용" 표시를 남김
돌아오는 주소로그인: …/code/naver
본인 확인: …/code/naver-reauth		둘 다 …/code/naver
서버가 구분하는 법돌아온 주소를 봄떠날 때 임시 값에 적어 둔 표시를 돌아왔을 때 찾아봄
네이버·카카오 화면에서 취소하고 돌아오면주소만 봐도 "탈퇴를 취소했어요"인지 "로그인을 취소했어요"인지 앎취소 응답에는 표시가 없으므로, 임시 값을 다시 뒤져 찾아야 함
사용자(개발자)가 하실 일네이버·카카오 개발자 화면에 돌아올 주소를 하나씩 더 등록없음
서버 코드Spring 설정 두 줄 추가Spring이 기본으로 해 주지 않는 부분을 직접 만듦 (표시를 넣는 부품, 돌아왔을 때 꺼내는 부품)

"나"가 복잡해지는 이유는 Spring의 구조 때문입니다. 로그인이 끝난 뒤 실행되는 Spring의 처리 단계에는 "돌아온 사람이 누구인지"만 전달되고, 떠날 때 적어 둔 표시는 전달되지 않습니다. 그래서 표시를 따로 보관했다가 꺼내는 코드를 직접 만들어야 합니다.

Spring Security: 제공자에 보낼 추가 값은 설정의 로그인 주소에 붙이거나 직접 만든 OAuth2AuthorizationRequestResolver로 넣음. https://docs.spring.io/spring-security/reference/servlet/oauth2/client/authorization-grants.html (2026-10-04). "처리 단계에 표시가 전달되지 않는다"는 설계 담당 에이전트의 판단이고 dev가 구현 때 확인합니다. 네이버가 돌아올 주소를 여러 개 받아 주는지는 등록 화면에서 확인해야 합니다 [확인 못 함].

본인 확인용 주소를 따로 등록하면 네이버·카카오가 승인해 주나

돌아올 주소는 승인받는 것이 아니라 개발자 화면에 직접 적어 넣는 설정입니다. 두 회사 문서 어디에도 "돌아올 주소를 심사한다"거나 "용도를 따진다"는 내용은 없었습니다. 다만 몇 개까지 넣을 수 있는지는 문서로 확인하지 못해, 등록 화면에서 직접 보셔야 합니다.

카카오네이버
등록하는 곳앱 관리 페이지 > 카카오 로그인 설정의 Redirect URI개발자센터 > 내 애플리케이션의 Callback URL
등록에 심사가 있나문서에 없음. 카카오 로그인 자체도 검수가 없음문서에 없음
검수(네이버만)에서 보는 것—서비스 내용, 로그인 화면 구성, 받은 정보를 실제로 쓰는지, 로고와 앱 이름. 돌아올 주소의 개수나 용도는 항목에 없음
몇 개까지 등록되나[확인 못 함] 문서에서 찾은 "10개"는 로그아웃용 주소의 한도였음[확인 못 함] 가이드에 개수가 적혀 있지 않음
다시 로그인시키는 기능공식 기능 (prompt=login)공식 기능 (auth_type=reauthenticate). 가이드가 쓰임을 "서비스 해지 또는 탈퇴"로 적음. 따로 승인이 필요하다는 문장은 없음

하실 일: 앱을 등록하실 때 돌아올 주소 칸에 두 줄을 넣어 보세요(로그인용, 본인 확인용). 두 줄이 들어가면 이 방식 그대로 갑니다. 네이버나 카카오가 한 줄만 받는 것으로 나오면 알려 주세요. 그 제공자는 주소 하나로 구분하는 다른 방식(표의 "나")으로 바꿉니다. 설계 문서에 이 갈림을 적어 두겠습니다.

카카오 로그인 설정하기: https://developers.kakao.com/docs/ko/kakaologin/prerequisite · 네이버 개발 가이드와 검수 가이드: https://github.com/naver/naver-openapi-guide (ko/login/devguide/devguide.md, ko/login/verify/verify.md) (2026-10-04, 요약 도구로 읽음. "문서에 없음"은 승인이 필요 없다는 공식 확인은 아닙니다)

7"가": 본인 확인용 돌아올 주소를 따로 둠 [안]

네이버·카카오 개발자 화면에 주소를 하나씩 더 등록하는 일이 생기지만 한 번이면 끝나고, 서버 코드는 단순해집니다. 네이버가 주소를 여러 개 받지 않는 것으로 확인되면 "나"로 바꿉니다.

다른 선택: "나". 등록할 것이 늘지 않고 코드가 늘어납니다.

8"기록 표"가 무엇이고 어떻게 쓰이나

기록 표는 "알림을 보냈는데 받는 쪽이 일을 끝냈는지"를 적어 두는 DB 표입니다. 서버가 도중에 꺼져도 할 일이 사라지지 않게 하려고 둡니다.

왜 필요한가

계정이 지워지면 다른 모듈도 할 일이 생깁니다. 다음 사이클의 "내 도서관" 모듈은 그 계정의 지역과 내 도서관 자료를 지워야 합니다. 탈퇴 처리(auth)가 그 모듈을 직접 부르지 않고 "계정 12가 지워졌다"는 알림을 냅니다(모듈끼리 서로 모르게 하려는 것으로, ADR-0036에서 정하신 구조입니다). 문제는 알림을 낸 직후 서버가 꺼지는 경우입니다. 계정은 지워졌는데 내 도서관 자료는 남게 됩니다. 기록 표가 이것을 막습니다.

기록 표에 실제로 적히는 것

받는 쪽무슨 알림알림 내용낸 때끝난 때
내 도서관 모듈의 처리기AccountDeleted계정 1210:00:0010:00:01
내 도서관 모듈의 처리기AccountDeleted계정 3710:05:00(비어 있음: 아직 안 끝남)

"끝난 때"가 비어 있는 줄은 받는 쪽이 일을 끝내지 못한 것입니다. 서버가 다시 켜진 뒤 이 줄들을 다시 보내 마저 처리합니다. 이 표는 Spring Modulith(우리가 쓰는 모듈 도구)가 만들어 주는 기능이고, 표 이름은 event_publication입니다.

Spring Modulith 공식 문서 "Working with Application Events", Event Publication Registry: "writes entries for each of them … into an event publication log as part of the original business transaction", 받는 쪽이 성공하면 그 기록을 완료로 표시하고 실패하면 그대로 둠, 남은 것은 다시 보낼 수 있음. https://docs.spring.io/spring-modulith/reference/events.html (2026-10-04, 2.1.1)

이번 사이클의 문제

위 인용의 "each of them"은 받는 쪽마다 한 줄이라는 뜻입니다. 이번 사이클에는 받는 쪽이 아직 없습니다(내 도서관 모듈은 다음 사이클). 그러면 기록이 0줄입니다. 그런데 명세의 수용 기준 AC-15는 "계정이 지워질 때마다 기록이 생긴다"입니다. 그대로는 통과할 수 없습니다. "받는 쪽이 0이면 0줄"은 인용에서 따라 나오는 결론이고, dev가 테스트로 확인합니다.

가. auth 안에 받는 쪽을 하나 둠 (추천)나. AC-15를 바꿈
무엇을 하나알림을 받아 서버 기록에 "계정 12 삭제됨" 한 줄을 남기는 작은 처리기기록 표는 만들어 두되, 이번에는 "알림을 냈는지"만 테스트로 확인
AC-15그대로 통과문구를 고쳐야 함
기록 표가 실제로 쓰이는 때이번 사이클부터. 저장 → 알림 → 끝남 표시가 지금 검증됨다음 사이클에 처음
아쉬운 점하는 일이 거의 없는 코드가 하나 생김다음 사이클에서 기록 표 문제까지 함께 풀어야 함

"서버 기록"이 무엇인가, DB에 남기면 안 되나

"서버 기록"은 로그를 말한 것입니다. 서버 프로그램이 돌면서 "몇 시에 무슨 일이 있었다"를 글자로 쌓는 파일입니다. DB에 남기는 것도 됩니다. 실제로는 이번 설계에서 기록이 남는 곳이 둘이고, 셋째를 더할지가 질문하신 부분입니다.

기록어디에무엇이 적히나누가 보나이번 설계
① 알림 기록 표DB (event_publication)"계정 12 삭제 알림을 냈고, 받는 쪽이 끝냈다"서버 프로그램 (못 끝낸 일을 다시 하려고)있음
② 로그서버의 로그 파일"10:00 계정 12 삭제됨" 한 줄운영자 (문제가 생겼을 때 찾아봄)처음 제안의 "작은 처리기"가 하는 일
③ 탈퇴 기록 표DB에 새 표계정 번호, 지운 때, 지워진 경로(본인 탈퇴 / 카카오에서 끊김 / 네이버에서 끊김)운영자 ("왜 지워졌나" 문의에 답함, 탈퇴 수 세기)말씀하신 방식. 더할 수 있음

보통 어디에 기록하나: OWASP의 로그 안내서는 사용자 추가·삭제를 "기록해야 할 일"로 꼽고, 기록하는 곳으로 파일, DB, 따로 모으는 로그 서버를 모두 듭니다. 어느 하나가 정답이라고 하지는 않습니다. 로그에는 비밀번호·토큰 같은 값을 넣지 말고, 보관 기간을 정해 그 뒤에는 지우라고 합니다. 다른 서비스들이 탈퇴 기록을 어디에 두는지 정리한 공식 자료는 찾지 못했습니다 [확인 못 함].

③을 더할 때 따져 볼 것

좋은 점: 로그 파일은 시간이 지나면 지워지거나 서버를 옮기면 사라지지만, 표는 남습니다. "언제 어떤 경로로 지워졌나"를 바로 찾을 수 있고, 처음 제안에서 하는 일이 거의 없던 "작은 처리기"가 이 표에 한 줄 쓰는 진짜 일을 맡게 됩니다.

조심할 점: 탈퇴하면 자료를 복구할 수 없게 지우기로 하셨습니다. 그래서 이 표에는 우리 계정 번호, 시각, 경로만 적고 네이버·카카오 회원번호는 적지 않습니다. 계정 번호는 다른 자료가 모두 지워진 뒤라 누구인지 알 수 없는 숫자입니다. 그래도 보관 기간을 정해 지우고, 개인정보 처리방침에 "탈퇴 기록을 얼마 동안 둔다"를 적어야 합니다. 표가 하나 늘고 알림에 "경로" 칸이 하나 늘어납니다.

OWASP Logging Cheat Sheet: 기록할 일에 "addition or deletion of users", 기록하는 곳으로 파일 시스템·데이터베이스·원격 수집, 넣지 말 것에 비밀번호·세션 값·접근 토큰, 보관 기간을 지킬 것. https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html (2026-10-04)

처리가 끝나면 기록을 지우는 것, 또는 구간을 나눠 통째로 버리는 것이 적절한가

"끝나면 지운다"는 적절하고, 도구가 공식으로 지원하는 설정입니다. 구간을 나눠 버리는 방식(partition, drop)은 이 표에는 과합니다.

방식어떻게 되나이 표에 맞나
끝나면 지움 (말씀하신 첫째)받는 쪽이 일을 끝내면 그 줄을 바로 지움. 표에는 아직 못 끝낸 줄만 남음맞음. Spring Modulith에 이 설정이 있음(completion-mode: delete). 지워진 계정의 번호가 DB에 남지 않아 "복구할 수 없게 지운다"와도 맞음
끝난 때만 적어 둠 (도구의 기본값, 처음 설계 안)줄이 계속 쌓임. 따로 정리하는 일을 만들어야 함쌓인 줄에 지워진 계정 번호가 남음. 보관 기간을 정해야 함
구간을 나눠 통째로 버림 (말씀하신 둘째)표를 달마다 나누고 오래된 달을 통째로 버림과함. 하루에 수백만 줄이 쌓이는 표에 쓰는 방식인데, 이 표는 탈퇴할 때만 한 줄 생김. 도구가 정한 표 모양도 고쳐야 함

"끝나면 지움"으로 하면 바뀌는 것 하나: 수용 기준 AC-15는 "계정이 지워질 때마다 기록 표에 기록이 생긴다"입니다. 끝난 줄을 지우면 나중에 표를 들여다봐도 줄이 없습니다. 그래서 AC-15의 확인 방법을 "알림이 나가고, 받는 쪽이 처리하고, 처리 뒤 줄이 지워지는 것을 테스트로 확인"으로 고칩니다. 지키려는 것(알림이 사라지지 않는다)은 그대로입니다.

앞에서 여쭌 "DB에 탈퇴 기록 표를 따로 둘지"는 이것과 별개입니다. 끝나면 지우자고 하신 것으로 보아 오래 남기는 표는 원하지 않으시는 것으로 읽었고, 아래 제안에는 넣지 않았습니다. 탈퇴 기록을 남기고 싶으시면 적어 주세요.

Spring Modulith 설정 spring.modulith.events.completion-mode: update(기본) / delete / archive. https://docs.spring.io/spring-modulith/reference/appendix.html (2026-10-04, 설계 담당 에이전트가 확인). 구간 나누기가 과하다는 것은 이 표에 쌓이는 양(탈퇴할 때만 한 줄)을 보고 내린 제 판단입니다.

8auth 안에 "계정 삭제됨" 알림을 받는 작은 처리기를 하나 두고, 알림 기록 표는 별도 구역에 두며, 처리가 끝난 줄은 바로 지움 [안]

기록 표는 어느 한 모듈의 것이 아니라 모든 모듈의 알림이 함께 쓰는 표입니다. 그래서 auth 구역이 아니라 따로 만든 구역(스키마 modulith)에 둡니다.

처리기가 하는 일은 서버 로그에 "계정 12 삭제됨" 한 줄을 남기는 것입니다. 바뀐 점(2026-10-04): 말씀하신 대로 처리가 끝난 줄은 지웁니다. 표에는 못 끝낸 줄만 남고, AC-15의 확인 방법을 테스트로 바꿉니다.

다른 선택 1 (말씀하신 방식): 처리기가 로그 대신 DB의 탈퇴 기록 표에 한 줄을 씁니다(계정 번호, 시각, 경로). 고르시려면 "기타"에 "DB에 기록"이라고 적어 주세요. 보관 기간도 함께 적어 주시면 그대로 넣고, 없으면 1년을 제안으로 넣어 다시 여쭙니다. 1년은 근거 문서가 있는 값이 아닙니다.

다른 선택 2: 받는 쪽을 두지 않고 AC-15를 "알림을 냈는지만 테스트로 확인"으로 바꿈.

12화면 쪽 보안 구성을 지금 정하기

미루지 않고 지금 정하겠습니다. 운영에서 Spring이 화면 파일을 내려 주지 않는 것도 말씀대로 합니다. 그러면 정할 것은 둘입니다.

참고로, Spring이 빌드된 화면 파일을 내려 주더라도 React가 하는 일은 달라지지 않습니다. 파일을 건네주는 곳만 다릅니다. 다만 화면과 API를 따로 배포하고 싶으신 것이면 나누는 쪽이 맞고, 그렇게 설계합니다.

서버 부담이 적은 쪽은 어디인가

우리 서버의 부담이 가장 적은 것은 화면 파일을 CDN이 대신 내려 주는 구성입니다. 다만 어느 구성이든 화면 파일이 주는 부담은 작습니다. 서버가 실제로 힘을 쓰는 곳은 검색과 도서관 조회 같은 API이고, 그 부담은 세 구성이 같습니다.

구성화면 파일을 내려 주는 곳우리 서버의 부담주소오늘 정한 쿠키·확인용 토큰
앞단 웹 서버 (제안 12-가)우리 서버에 함께 띄운 웹 서버 (Nginx 등)작음. 만들어 둔 파일을 그대로 건네주는 일이라 가벼움. Spring은 API만 함하나그대로 동작
앞단 웹 서버 + 그 앞에 CDNCDN이 화면 파일을 기억해 두고 대신 내려 줌가장 작음. 화면 파일 요청이 우리 서버까지 거의 오지 않음하나 (CDN이 같은 주소로 앞에 섬)그대로 동작
화면을 다른 주소의 정적 호스팅에 올림호스팅 회사가장 작음 (화면 파일은 0)둘다시 짜야 함
Spring이 화면 파일도 내려 줌 (하지 않기로 하심)Spring셋 중 가장 큼. 그래도 작은 편하나그대로 동작

화면 파일의 부담이 작은 이유는 둘입니다. 화면 파일은 요청마다 새로 만드는 것이 아니라 미리 만들어 둔 파일입니다. 그리고 브라우저가 한 번 받은 파일을 기억해 두고 다시 받지 않습니다. React를 빌드하면 파일 이름에 내용에 따른 꼬리표가 붙어서, 내용이 바뀌기 전까지는 브라우저가 가진 것을 그대로 씁니다.

그래서 12-가를 고르셔도 길이 막히지 않습니다. 12-가는 "주소는 하나, 화면 파일은 Spring이 아닌 앞단에서"라는 모양만 정합니다. 처음에는 웹 서버 하나로 시작하고, 사용자가 늘어 부담이 보이면 그 앞에 CDN을 붙이면 됩니다. 주소가 그대로라 오늘 정한 쿠키와 확인용 토큰은 손대지 않습니다.

Vite 공식 문서(빌드 결과 파일 이름에 해시를 붙여 오래 캐시할 수 있게 함): https://vite.dev/guide/build 를 근거로 삼았으나 이번에 다시 열어 확인하지는 않았습니다. 표의 부담 비교는 측정값이 아니라 구성에서 따라 나오는 제 판단입니다.

12-가화면 파일은 앞단의 웹 서버가 내려 주고, 화면과 API는 같은 주소를 씀 [안]

웹 서버(예: Nginx, Caddy) 하나가 앞에 서서 화면 파일을 내려 주고 /api 요청을 Spring으로 넘깁니다. 지금 개발 환경(Vite가 /api만 Spring으로 넘김)과 같은 모양입니다.

주소를 하나로 두는 이유는 오늘 정하신 것들이 그 전제 위에 있기 때문입니다. 토큰 쿠키(SameSite=Lax, Domain 없음)와 확인용 토큰(CSRF)은 화면과 API가 같은 주소일 때 추가 설정 없이 동작합니다.

다른 선택: 화면은 정적 호스팅·CDN의 다른 주소(예: app.…), API는 api.…. 쿠키에 Domain을 주고, 다른 주소에서 오는 요청을 허용하는 설정(CORS)과 확인용 토큰 전달 방식을 다시 짜야 합니다. 오늘 정한 8번 명세 결정(쿠키 표시)을 다시 열게 됩니다.

어떤 웹 서버 제품을 쓸지, 어디에 올릴지는 배포할 때 정하시면 됩니다. 여기서 정하는 것은 "앞단 웹 서버 + 같은 주소"라는 모양입니다.

API 쪽 넷(X-Frame-Options, Strict-Transport-Security, X-Content-Type-Options, Cache-Control)은 Spring Security가 기본으로 붙입니다. 화면 파일 쪽은 웹 서버 설정 파일에 적어야 하므로, dev가 웹 서버 설정 예시 파일을 저장소에 함께 만들어 둡니다. 실제 서버에 올리는 일은 배포 때 합니다.

확인이 남은 것: Content-Security-Policy의 정확한 문장은 화면 부품(Radix)이 화면에 넣는 스타일에 따라 조정이 필요할 수 있습니다. dev가 빌드 결과로 시험해 확정합니다.
