1ADR-0038: 로그인 유지는 JWT (짧은 액세스 토큰 + DB의 리프레시 토큰)

액세스 토큰은 계정 번호와 만료 시각만 담은 JWT(HS256, 15분). 리프레시 토큰은 무작위 값으로 DB에 SHA-256 해시로 저장하고 쓸 때마다 교체하며, 이미 쓴 값이 다시 오면 그 로그인을 끊는다. 로그인한 때부터 30일이면 만료(미사용 기한은 따로 없음). 두 토큰은 Secure·HttpOnly·SameSite=Lax 쿠키. 로그인이 필요한 API는 요청마다 그 계정이 아직 있는지만 확인한다. 여러 탭의 동시 갱신은 웹이 Web Locks로 한 번에 한 탭만 하게 한다.

왜 정해야 했나

로그인한 상태를 유지하는 방법을 정해야 했다. 2026-10-01에는 세션을 DB에 두는 방식(Spring Session JDBC)으로 정했으나, 사용자가 서버가 여러 대가 될 때 늘어나는 것을 줄이고 싶어 했고 나중에 폰 앱도 같은 로그인으로 쓰려 한다.

이유로 적을 말 (하신 말 그대로)

  • "가능하면 jwt로 했으면 좋겠어 세션을 쓰더라도 나중에 확장될 멀티 서버 환경에서 redis등이 필요해지는데 음 가능하면 줄이고 싶어" (2026-10-03)
  • "jwt로 가려고 해" (2026-10-03)
  • 서명 방식: "우리 서비스만 토큰을 확인하면 되니까 '가'로 가자" (2026-10-04)
  • 계정 확인: "'나'로 하되 이렇다는 걸 명시하고" (2026-10-04)
  • 30일 하나로, SameSite=Lax, 탭 갱신 방식: 승인만 함 [이유 미확인]

요청마다 로그인 기록(리프레시 토큰 줄)까지 확인로그아웃한 토큰도 바로 끊김"리프레시 토큰을 db에 두면 세션이랑 다를 바가 없어 보여서" (2026-10-04)

  • 되돌리는 비용: 서명 방식·키는 15분이면 바뀜. 세션 방식으로 돌아가려면 발급·갱신 부분을 다시 만들어야 함. 나중에 분리할 때 다른 서비스가 토큰을 확인하게 되면 키 한 쌍 방식으로 바꿈

2ADR-0039: 로그인 수단 표를 소셜 전용으로 만들지 않고, 제공자 번호는 프로필 API로 받음

계정 표(auth.account)와 로그인 수단 표(auth.login_method)를 나누고, 로그인 수단 표의 칸을 method(NAVER, KAKAO, 나중에 PASSWORD)와 subject(그 수단 안의 식별자)로 짓는다. 두 제공자 모두 OAuth 2.0 + 프로필 API로 식별자를 받는다. 이메일·이름·제공자 토큰은 저장하지 않는다.

  • 감수하는 점: 탈퇴 재인증이 실제로 일어났는지는 제공자에 보낸 요청(prompt=login, auth_type=reauthenticate)을 믿는 수준
  • 되돌리는 비용: OIDC로 바꾸려면 네이버 sub와 id가 같은지 먼저 확인. 다르면 기존 계정과 연결이 끊김

3ADR-0040: 로그인 도중의 임시 값은 HttpSession에 두고, 서버 수에 따라 저장소를 설정으로 고름

임시 값은 HttpSession으로만 다룬다(수명 10분). 이번 사이클은 서버 메모리 구현만 만든다. 서버가 여러 대가 되면 Spring Session(Redis)을 설정으로 켜서 같은 코드가 Redis에 저장하게 한다. 동의 화면을 그냥 떠난 사람은 임시 값이 만료될 때 제공자 연결을 끊는다. 로그인 유지(JWT)는 이 세션과 무관하다.

로그인 도중에는 몇 분 동안 들고 있어야 하는 값이 있다: 제공자에 보낸 확인 값(state), 가입 동의 전의 제공자 번호, 탈퇴 재인증 증명과 네이버 접근 토큰. "가입 전에는 DB에 아무것도 저장하지 않는다"는 결정 때문에 DB에는 둘 수 없다.

  • "일단 (가)로 가되 여러 백엔드 서버가 동시에 존재하더라도 잘 되도록 redis가 차후 도입되었을 때를 대비해서 설계되었으면 해" (2026-10-04)
  • "선택으로 멀티서버/원 서버 환경에서 각각 돌아가도록 했으면 해" (2026-10-04)

고르지 않은 안

안그 안의 좋은 점고르지 않은 이유로 적을 말

결과

  • 좋아지는 점: Spring 기본 기능 그대로라 만들 것이 적음. 버려진 가입 대기의 제공자 연결을 끊을 수 있음
  • 감수하는 점: 서버를 다시 켜면 그 순간 로그인하던 사람은 처음부터 다시 함. 여러 대가 되면 Redis(또는 같은 서버로 보내는 설정)가 필요함

4ADR-0041: 계정 삭제는 AccountDeleted 이벤트로 알리고, 발행 저장소의 완료 기록은 지움

  • 감수하는 점: 완료된 뒤에는 표에서 이력을 볼 수 없어 AC-15를 테스트로 확인함. 이번 사이클의 받는 쪽은 로그 한 줄만 남김
  • 되돌리는 비용: 완료 기록을 남기려면 설정 한 줄. 나중에 분리할 때 이 이벤트는 서비스 사이의 메시지가 됨

5ADR-0042: 화면 파일은 앞단 웹 서버가 내려 주고 API와 같은 주소를 쓰며, 인증 주소는 /api/v1/auth 아래에 모음

운영에서는 앞단 웹 서버가 화면 파일을 내려 주고 /api 요청을 Spring으로 넘긴다(같은 출처). 보안 헤더는 화면 파일에 웹 서버가, API 응답에 Spring Security가 붙인다. dev는 웹 서버 설정 예시 파일을 저장소에 둔다. 인증 흐름의 주소는 모두 /api/v1/auth/**에 두고, 액세스 토큰 쿠키는 Path=/api/v1/me, 리프레시 토큰 쿠키는 Path=/api/v1/auth로 좁힌다.

왜 정해야 했나

운영에서 화면 파일(React 빌드)을 누가 내려 줄지 정해진 적이 없었고, 화면 쪽 보안 헤더를 붙일 곳이 없었다. 토큰 쿠키(SameSite=Lax, Domain 없음)와 CSRF 토큰은 화면과 API가 같은 주소일 때 추가 설정 없이 동작한다.

이유로 적을 말 (하신 말 그대로)

  • "이것도 지금에서 하는 게 맞다고 보는데 화면에서 보안적인 구성" (2026-10-04)
  • "운영에서 spring이 파일 화면을 내려주고 싶지는 않아 react를 쓰는 의미가 없어지잖아" (2026-10-04)
  • 주소와 쿠키 경로: 승인만 함 [이유 미확인]

고르지 않은 안

안그 안의 좋은 점고르지 않은 이유로 적을 말
Spring이 화면 파일도 내려 줌헤더를 한 곳에서 관리위 사용자 발언(2026-10-04)
화면을 다른 주소의 정적 호스팅·CDN에 올림화면 파일이 우리 서버를 거치지 않음[이유 미확인] (같은 주소 안을 승인. 쿠키·CSRF 설계를 다시 열어야 함)
Spring 기본 주소(/oauth2/…, /login/…, /logout)와 Path=/ 쿠키설정이 적음[이유 미확인] (주소를 모으는 안을 승인)

결과

  • 좋아지는 점: 검색 같은 공개 API에는 토큰이 가지 않아 토큰 문제로 검색이 막히지 않음. 개발 환경(Vite가 /api만 넘김)과 같은 모양
  • 감수하는 점: __Host- 쿠키 접두어를 쓸 수 없음(Path=/가 필요). 범위 문서의 주소 둘이 바뀜(POST /logout → POST /api/v1/auth/logout, POST /api/v1/me/consents → POST /api/v1/auth/signup). 헤더 설정이 두 곳
  • 되돌리는 비용: 주소를 바꾸면 제공자 콘솔의 돌아올 주소를 다시 등록. CDN은 같은 주소 앞에 붙일 수 있어 설계가 바뀌지 않음

6ADR-0043: 중요한 기능에만 다시 본인 확인을 받고, 탈퇴는 제공자 재인증 전용 등록으로 처리

다시 본인 확인을 받는 기준은 셋이다: 되돌릴 수 없는 일, 로그인 수단을 바꾸는 일, 연락처를 바꾸는 일. 이번 사이클에서는 탈퇴가 해당한다. 탈퇴는 두 제공자 모두 재인증(네이버 auth_type=reauthenticate, 카카오 prompt=login)을 거치고 5분 안에만 진행된다. 재인증은 전용 등록(naver-reauth, kakao-reauth)과 전용 돌아올 주소로 구분한다. 제공자 콘솔이 돌아올 주소를 둘 이상 받지 않으면 그 제공자는 등록 하나에 목적 표시를 붙이는 방식으로 바꾼다.

왜 정해야 했나

JWT 방식에서는 로그아웃한 액세스 토큰이 최대 15분 남는다(ADR-0038). 이 틈으로 중요한 일이 일어나지 않게 할 장치가 필요했고, 탈퇴 때 네이버 연결을 끊으려면 새 네이버 토큰이 있어야 한다.

이유로 적을 말 (하신 말 그대로)

  • "로그인이 필요한 기능 중 중요한 부분들을 사용자 인증을 받는 식으로 가는게 어떨까" (2026-10-04)
  • "응 그 기준으로 확정해줘" (2026-10-04)
  • 탈퇴 재인증: 네이버·카카오 둘 다 (2026-10-01), 5분과 전용 등록은 승인만 함 [이유 미확인]

고르지 않은 안

안그 안의 좋은 점고르지 않은 이유로 적을 말
카카오는 확인 창만, 네이버만 재인증카카오 사용자의 탈퇴가 한 단계 짧음[이유 미확인] (둘 다 재인증을 승인)
네이버 갱신 토큰을 저장해 두고 확인 창만둘 다 재인증 없이 탈퇴[이유 미확인] (제공자 토큰을 저장하지 않는 결정과 충돌)
등록 하나 + 요청에 목적 표시콘솔에 등록할 주소가 늘지 않음[이유 미확인] (전용 등록을 승인)

결과

  • 좋아지는 점: 훔친 액세스 토큰으로는 탈퇴 같은 중요한 일을 할 수 없음. 나중 사이클(연락처 등록, 다른 소셜 계정 연결)이 같은 기준을 따름
  • 감수하는 점: 탈퇴에 한 단계가 더 있음. 제공자 콘솔에 돌아올 주소를 하나씩 더 등록
  • 되돌리는 비용: 기준을 바꾸면 해당 기능의 흐름만 고침
