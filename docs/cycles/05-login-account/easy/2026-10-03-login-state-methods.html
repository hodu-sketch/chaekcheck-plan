브라우저가 든 토큰에 담느냐의 차이입니다.

결정(2026-10-03): 사용자가 "라. 짧은 JWT + DB에 두는 리프레시 토큰"을 골랐습니다. 아래는 고르기 전에 쓴 비교입니다. 어느 방식도 Redis가 꼭 필요하지는 않습니다. chaekcheck에 맞는 것은 "DB에 두는 세션"과 "짧은 JWT + DB에 두는 리프레시 토큰" 둘이고, 고르는 기준은 나중에 만들 폰 앱과 지금 만들 양입니다. 공식 문서 확인일 2026-10-03.

1원리는 두 가지뿐입니다

로그인에 성공한 뒤, 다음 요청이 "같은 사람"임을 서버가 어떻게 아는가의 문제입니다. HTTP 요청은 서로 이어져 있지 않아서, 브라우저가 요청마다 무언가를 같이 보내야 합니다.
  • 세션서버가 무작위 번호(세션 ID)를 만들어 쿠키로 주고, 그 번호에 딸린 로그인 기록을 서버 쪽 저장소에 둡니다. 번호 자체에는 아무 뜻이 없어야 합니다. OWASP Session Management Cheat Sheet: "The session ID content (or value) must be meaningless", 로그인 기록은 "session objects or a session management database or repository"에 둠
  • JWT(JSON Web Token)"누구인지, 언제 만료되는지"를 적은 글에 서버가 서명을 붙인 문자열입니다. 서버는 서명이 자기 것인지와 만료 시각만 확인합니다. 내용은 암호화된 것이 아니라서 누구나 읽을 수 있고, 서명 때문에 고칠 수만 없습니다. RFC 7519: "a compact, URL-safe means of representing claims", 4.1.4 "exp ... MUST NOT be accepted" 뒤에는 받지 않음, 11.1 서명 없이는 신뢰 불가

2실제로 쓰는 방식은 넷입니다

위 두 원리를 어디에 저장하고 어떻게 섞느냐에 따라 넷으로 나뉩니다. "즉시 끊기"가 되는지와 "서버가 여러 대일 때"가 갈리는 지점입니다.
방식로그인 정보가 있는 곳요청마다 하는 일서버 여러 대즉시 끊기
가. 메모리 세션서버 프로세스의 메모리메모리에서 찾음안 됨 서버마다 따로됨
나. 저장소 세션 (DB 또는 Redis)모든 서버가 같이 보는 저장소저장소를 한 번 읽음됨됨
다. JWT 하나 (만료가 긴 토큰)브라우저의 토큰서명 확인만됨안 됨
라. 짧은 JWT + 리프레시 토큰짧은 토큰(예: 15분)은 브라우저, 긴 리프레시 토큰은 DB서명 확인만. 15분마다 한 번 DB를 읽어 새 토큰을 받음됨최대 15분 늦음

"라"가 움직이는 방식: 요청에는 15분짜리 JWT를 씁니다. 만료되면 브라우저가 30일짜리 리프레시 토큰을 보내 새 JWT를 받습니다. 리프레시 토큰은 무작위 값이고 DB에 저장하며, 쓸 때마다 새것으로 바꿉니다. 로그아웃·탈퇴 때 DB의 그 줄을 지우면 새 JWT를 못 받으므로 15분 안에 끊깁니다. JWT 하나(다)의 "끊을 수 없다"를 줄이려고 세션의 원리를 리프레시 토큰에만 쓴 것입니다. RFC 9700: 리프레시 토큰은 교체(rotation)하거나 보낸 쪽에 묶을 것

"서버가 여러 대면 Redis가 필요하다"는 말은 가에서 나로 옮길 때 나오는 이야기입니다. 나의 저장소는 Redis일 수도 있고 지금 쓰는 PostgreSQL일 수도 있습니다. Spring Session은 둘 다 지원합니다. Spring Session 4.1.1 문서: JDBC, Redis 설정. Spring Security 문서: "Clustered sessions with Spring Session"

3세션의 장단점

서버가 기록을 쥐고 있어서 통제가 쉽습니다. 대신 요청마다 그 기록을 읽습니다.
  • 좋은 점: 끊기와 바꾸기가 즉시기록을 지우면 그 순간 로그아웃입니다. 탈퇴하면 그 계정의 기록을 모두 지우면 됩니다. 만료 기간을 바꾸거나 "모든 기기에서 로그아웃"을 만드는 것도 서버에서 끝납니다.
  • 좋은 점: 만들 것이 적음Spring Security가 로그인 정보를 세션에 넣는 것이 기본 동작이고, 로그인 때 세션 번호를 새로 발급하는 보호도 기본입니다. Spring Security Session Management 문서
  • 나쁜 점: 요청마다 저장소를 읽음로그인한 사용자의 요청마다 세션 표를 한 번 읽습니다. 저장소가 느려지거나 멈추면 로그인한 사용자 전체가 영향을 받습니다.
  • 나쁜 점: 저장소가 읽히면 세션도 샘Spring Session은 세션 번호를 표(SPRING_SESSION)에 그대로 저장합니다. DB를 읽을 수 있는 사람은 살아 있는 세션 번호로 접속할 수 있습니다. Redis에 둘 때도 번호가 키 이름에 그대로 들어갑니다. Spring Session 스키마 파일, Redis 설정 문서
  • 나쁜 점: 폰 앱에는 따로 길이 필요쿠키 세션은 브라우저에 맞춘 방식입니다. 앱은 보통 토큰을 헤더로 보내므로, 나중에 앱을 만들면 토큰 발급 경로를 더해야 합니다.

4JWT의 장단점

서버가 아무것도 읽지 않고 확인할 수 있습니다. 대신 한번 내준 토큰은 서버가 거둬들일 수 없습니다.
  • 좋은 점: 요청마다 저장소를 안 읽음서명과 만료 시각만 확인합니다. 서버가 몇 대든 같은 키만 갖고 있으면 됩니다. Spring Security Resource Server 문서: 서명, exp·nbf·iss 검증
  • 좋은 점: 웹과 앱이 같은 방식토큰은 쿠키로도, 헤더로도 보낼 수 있습니다. 폰 앱이 생겨도 같은 토큰을 씁니다.
  • 나쁜 점: 즉시 끊기가 그대로는 안 됨로그아웃하거나 탈퇴해도 이미 내준 토큰은 만료 시각까지 서명이 맞습니다. 끊으려면 서버에 기록을 다시 둬야 합니다. ASVS는 방법 셋을 듭니다: 끊은 토큰 목록을 두기, 사용자별로 "이 시각 이전 토큰은 거절"을 두기, 사용자별 서명 키를 바꾸기. 셋 다 요청마다 무언가를 읽게 되어 "안 읽는다"는 장점이 줄어듭니다. OWASP ASVS 5.0 7.4.1, 7.4.2(계정 삭제 시 모든 세션 종료). OWASP JWT Cheat Sheet: 세션에 JWT를 쓰면 무효화 방법이 필요하고, 일반 세션을 고려하라고 함
  • 나쁜 점: 흐름을 직접 조립해야 함Spring Security에는 JWT를 검증하는 기능과 서명해 만드는 부품(NimbusJwtEncoder)이 둘 다 있습니다. 없는 것은 "로그인이 끝나면 내주고 만료되면 갱신하는" 흐름입니다. 직접 만드는 것: 로그인 성공 때 쿠키로 내주기, 쿠키에서 읽어 검증하기, 리프레시 토큰 표와 갱신 API, 웹의 자동 갱신, 로그인 도중의 임시 값(state)을 둘 곳. 양은 코드 몇백 줄과 표 하나 정도로 크지 않습니다. 부담은 양보다 리프레시 토큰 교체처럼 틀리기 쉬운 보안 코드를 우리가 책임진다는 점입니다. (2026-10-03 정정: 처음에는 "발급 기능이 없다, 만들 것이 많다"고 적었는데 과장이었습니다.) Spring Security API 문서: NimbusJwtEncoder(5.6부터). Resource Server 문서: 토큰은 기본으로 Authorization 헤더에서 읽음. OAuth2 Client 문서: 로그인 요청은 기본으로 HttpSession에 보관
  • 나쁜 점: 내용이 보임토큰에 적은 것은 누구나 읽을 수 있습니다. 계정 번호와 만료 시각 말고는 넣지 않아야 합니다. 서명 키가 새면 누구든 아무 계정의 토큰을 만들 수 있습니다.

5표에 없는 방식 둘

카드 2의 넷 말고 이름이 따로 있는 방식이 둘 더 있습니다. 새 원리는 아닙니다. 하나는 세션과, 하나는 JWT와 원리가 같고, 값을 실어 보내는 자리만 다릅니다.
  • 뜻 없는 토큰을 헤더로 (opaque token)"opaque"는 받은 쪽이 안을 들여다볼 수 없다는 뜻입니다. 서버가 무작위 문자열을 만들어 주고, 그 문자열이 어느 계정의 것이고 언제 만료되는지를 서버 쪽 표에 적어 둡니다. 프로그램은 요청마다 이 문자열을 헤더에 넣어 보내고(Authorization: Bearer 문자열), 서버는 표에서 찾아 누구인지 압니다. 표의 줄을 지우면 그 토큰은 바로 못 씁니다.

    즉 세션과 원리가 같고, 값을 실어 보내는 자리만 쿠키에서 헤더로 바뀐 것입니다. 헤더는 자동으로 붙지 않아서 값을 프로그램이 보관해야 합니다. 폰 앱은 기기의 보안 저장소에 둘 수 있어 이 방식이 잘 맞습니다. 웹 화면은 스크립트가 읽을 수 있는 곳에 둬야 해서 XSS에 약해지므로 쿠키가 낫습니다.

    이미 쓰고 있는 예: 카카오·네이버가 우리에게 주는 액세스 토큰이 이것입니다. 우리는 그 문자열의 뜻을 모르고, 헤더에 넣어 그쪽 서버에 보내면 그쪽이 자기 저장소에서 찾아 답합니다.

    chaekcheck에서는: 세션 방식(나)으로 가면 폰 앱은 이 방법으로 붙입니다(사용자 결정, 2026-10-03). 폰 앱을 만들 때 JWT가 꼭 필요한 것은 아닙니다. 세션을 DB에 두는 방식(나)에서, 앱에는 같은 세션 번호를 헤더로 주고받게 할 수 있습니다. Spring Session에 이 기능이 있습니다(세션 번호를 쿠키 대신 X-Auth-Token 헤더로). 그러면 웹과 앱이 같은 세션 표를 쓰고, 탈퇴 때 즉시 끊기는 것도 같습니다. RFC 6750 1.2(가진 사람이 쓸 수 있는 토큰), 2.1(Authorization: Bearer), 5.3(TLS 필수). OWASP ASVS 5.0 7.2.2·7.2.3: "reference token", 128비트 이상 무작위. Spring Session REST 가이드: HeaderHttpSessionIdResolver.xAuthToken()
  • 쿠키에 세션 내용을 통째로 넣기서버에 기록을 두지 않고, 로그인 정보를 서명(또는 암호화)해 쿠키에 넣는 방식입니다. 원리는 JWT 하나(다)와 같아서 즉시 끊기가 안 되는 점도 같습니다. Spring Security의 기본 구성에는 없습니다.

7정리: 무엇을 기준으로 고르나

Redis를 피하는 것은 두 방식 모두 됩니다. 실제 기준은 "지금 만들 양"과 "폰 앱을 얼마나 가까이 보느냐"입니다.
이것이 더 중요하면고를 것이유
이번 사이클을 작게, 탈퇴 즉시 끊기를 확실히나. 세션을 DB에Spring이 주는 것을 그대로 씀. 직접 만드는 보안 코드가 가장 적음
폰 앱을 곧 만들 것이고 웹과 한 방식으로라. 짧은 JWT + 리프레시앱과 웹이 같은 토큰. 대신 토큰 관리 코드를 직접 만들고 지킴
지금은 작게, 앱은 그때 가서나로 시작 → 앱 때 헤더로 세션 번호를 주고받는 길을 추가계정·동의·탈퇴와 세션 표를 그대로 씀. 앱에는 같은 세션 번호를 헤더로 보냄(카드 5의 "뜻 없는 토큰"). JWT를 새로 만들지 않아도 됨

제 추천은 셋째 줄입니다. 로그인한 사용자의 요청이 적은 서비스라 요청마다 DB를 읽는 부담이 작고, 혼자 운영하는 서비스에서 직접 만든 토큰·키 관리 코드는 계속 지켜야 할 대상이 됩니다. 폰 앱이 다음 몇 사이클 안에 있다면 처음부터 "라"로 가는 편이 두 번 일하지 않습니다.
