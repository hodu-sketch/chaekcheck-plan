나토큰 (2가지)

정하신 JWT 방식을 실제로 만들 때 갈리는 두 곳입니다.

1서명 방식: 비밀 키 하나로 서명하고 확인 (HS256) [안]

JWT는 서버가 "이 토큰은 내가 만들었다"고 서명한 것입니다. 서명 방식은 둘입니다. 하나는 같은 비밀 키로 서명하고 확인하는 방식이고, 다른 하나는 키 한 쌍(서명용, 확인용)을 쓰는 방식입니다. 토큰을 만드는 곳과 확인하는 곳이 우리 서버 하나뿐이므로 비밀 키 하나면 됩니다. 키는 서버 환경 변수에만 둡니다.

키를 바꿀 때는 환경 변수를 바꾸고 서버를 다시 켭니다. 옛 키로 만든 액세스 토큰은 거절되고, 화면이 알아서 새 토큰을 받습니다. 사용자는 다시 로그인하지 않습니다.

다른 선택: 키 한 쌍(ES256). 나중에 다른 서버가 토큰을 확인하게 될 때 필요합니다. 지금은 키 관리만 늘어납니다. 나중에 바꿔도 영향은 15분입니다.

RFC 7518 3.2절: HS256의 키는 256비트 이상이어야 함. https://www.rfc-editor.org/rfc/rfc7518.html (2026-10-04)

2여러 탭이 동시에 토큰을 새로 받을 때: 화면이 한 번에 한 탭만 하게 함 [안]

탭을 셋 열어 두면 15분 뒤 세 탭이 동시에 갱신을 요청할 수 있습니다. 첫 탭이 리프레시 토큰을 새것으로 바꾸면, 나머지 두 탭은 이미 쓴 옛 토큰을 내밀게 됩니다. 7번에서 정하신 규칙("이미 쓴 토큰이 또 오면 그 로그인을 끊음")대로면 멀쩡한 사용자가 로그아웃됩니다.

추천은 화면 쪽에서 막는 것입니다. 브라우저 기능(Web Locks)으로 탭끼리 순서를 정해, 한 탭이 갱신하는 동안 다른 탭은 기다렸다가 새 쿠키를 그대로 씁니다. 서버의 규칙은 엄격한 그대로입니다.

이 길의 약점: 서버는 토큰을 바꿨는데 응답이 인터넷에서 사라지는 드문 경우, 그 브라우저는 다음 갱신 때 로그아웃됩니다. 다시 로그인하면 됩니다.

다른 선택: 서버가 바로 앞 토큰을 몇 초 동안은 받아 줌. 위 약점까지 막지만, "이미 쓴 토큰이 오면 끊는다"는 규칙에 몇 초짜리 예외가 생깁니다.

MDN Web Locks API: 같은 출처의 다른 스크립트가 같은 잠금을 동시에 얻지 못함. 2022년 3월부터 주요 브라우저 지원. https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API · Auth0도 "몇 초 받아 줌" 설정이 있고 기본은 꺼짐. https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-rotation (2026-10-04)

다로그인 도중 (4가지)

로그인 버튼을 누른 뒤부터 가입이 끝나기까지 몇 분 동안의 일입니다.

3로그인 도중의 임시 값: 서버 메모리에 몇 분만 둠 [안]

로그인 도중에는 잠깐 들고 있어야 하는 값이 있습니다. 네이버·카카오에 보낸 확인 값, 가입 동의 전의 회원번호, 탈퇴 본인 확인 기록입니다. 이 값들을 둘 곳이 선택입니다.

가. 서버 메모리 (추천)나. 암호화한 쿠키
만들 것Spring 기본 기능 그대로값을 암호화해 쿠키에 넣고 읽는 코드를 직접 만듦
서버가 여러 대가 되면같은 사람의 요청이 같은 서버로 가게 설정하거나, 그때 "나"로 바꿔야 함그대로 동작
동의 화면을 그냥 떠난 사람몇 분 뒤 서버가 알아채고 네이버·카카오 연결을 끊을 수 있음서버가 알 수 없음
서버를 다시 켜면그 순간 로그인하던 사람은 "로그인 시간이 지났어요"영향 없음

알고 고르실 점: "여러 서버가 되어도 Redis 같은 것을 늘리고 싶지 않다"고 하신 것과 정면으로 맞는 쪽은 "나"입니다. 그래도 "가"를 추천하는 이유는 셋입니다. 지금은 서버가 한 대입니다. 몇 분짜리 값이라 나중에 "나"로 바꿔도 옮길 자료가 없습니다. Redis는 "가"에서도 필요 없습니다. 이미 로그인한 사람의 로그인 유지는 이 선택과 상관없이 JWT라서 서버 대수의 영향을 받지 않습니다.

Spring Security: 로그인 요청은 기본으로 HttpSession에 보관, 다른 곳에 두려면 직접 구현. https://docs.spring.io/spring-security/reference/servlet/oauth2/client/authorization-grants.html (2026-10-04)

4동의 화면을 그냥 떠난 사람: 10분 뒤 네이버·카카오 연결을 끊음 [안]

동의 화면에서 "취소"를 누르면 연결을 끊기로 3번에서 정하셨습니다. 창을 그냥 닫은 사람은 "취소"를 누르지 않았으므로 네이버·카카오의 "연결된 서비스"에 chaekcheck가 남습니다. 임시 값이 사라지는 10분 뒤에 서버가 그 연결을 끊습니다. 위 3번에서 "가"를 고를 때만 할 수 있습니다.

다른 선택: 끊지 않음. 그 사람이 다시 와서 로그인하면 이어서 가입할 수 있습니다. 카카오 정책의 "가입하지 않은 사용자 정보는 24시간 안에 파기"는 우리가 아무것도 저장하지 않으므로 어느 쪽이든 지켜집니다.

5회원번호 받는 방식: 두 제공자 모두 "로그인 뒤 내 정보 조회" [안]

회원번호를 받는 길이 둘입니다. 로그인 뒤 "내 정보" 주소를 한 번 더 불러 받는 길과, 로그인 응답에 함께 오는 신분 토큰(OIDC)에서 꺼내는 길입니다. 카카오는 둘이 같은 번호라고 문서에 적혀 있습니다. 네이버는 둘이 같은 번호인지 문서에 없습니다. 번호가 다르면 나중에 방식을 바꿀 때 이미 가입한 사람을 못 알아봅니다. 그래서 확인된 길(내 정보 조회)로 둘을 똑같이 처리합니다.

다른 선택: 신분 토큰(OIDC). 카카오는 "언제 다시 로그인했는지"를 받을 수 있어 탈퇴 본인 확인이 더 단단해집니다. 네이버 번호 확인이 먼저 필요합니다.

알아 두실 점: 추천안에서는 "정말 다시 로그인했는지"를 서버가 따로 확인할 근거가 없고, 네이버·카카오에 보낸 "다시 로그인시켜 달라"는 요청을 믿습니다.

카카오: ID 토큰의 sub는 회원번호. https://developers.kakao.com/docs/ko/kakaologin/rest-api · 네이버 가이드 3.5절에는 해당 문장 없음 [확인 못 함] (2026-10-04)

6로그인 결과를 화면에 알리는 방법: 정해진 주소 뒤에 결과 코드를 붙임 [안]

네이버·카카오에서 돌아오면 서버가 화면을 /auth/complete?result=login_cancelled 같은 주소로 보냅니다. 화면은 코드를 보고 정하신 문구("로그인을 취소했어요" 등)를 보여 준 뒤 주소에서 코드를 지웁니다. 코드에는 비밀이 없습니다. 실패 문구 11가지에 대응하는 코드 목록은 architect-proposal.md 결정 8에 있습니다.

"보던 화면으로 돌아오기"는 화면이 로그인 버튼을 누를 때 지금 주소를 브라우저의 임시 저장 공간(탭을 닫으면 사라짐)에 적어 두고, 돌아와서 꺼내 이동합니다. 서버는 돌아갈 주소를 받지 않으므로, 가짜 주소로 사람을 엉뚱한 사이트에 보내는 공격이 통하지 않습니다.

다른 선택: 결과를 쿠키로 전달(화면이 쿠키를 읽게 됨), 화면이 서버에 한 번 더 물어봄(요청이 늘어남).

라탈퇴와 계정 삭제 (2가지)

7탈퇴 본인 확인용 로그인 설정을 따로 둠 [안]

"다시 로그인"은 보통 로그인과 같은 길을 타지만 끝난 뒤 할 일이 다릅니다. 새 로그인을 만들면 안 되고, 같은 계정인지만 확인해야 합니다. 서버 설정에 "본인 확인용"을 네이버·카카오 각각 하나씩 더 두면, 돌아온 주소만 보고도 로그인인지 본인 확인인지 알 수 있습니다. 취소하고 돌아온 경우에도 구분됩니다.

사용자가 하실 일이 늘어납니다: 네이버·카카오 개발자 화면에 "돌아올 주소"를 하나씩 더 등록합니다(제공자마다 둘). 네이버가 주소를 여러 개 받아 주는지는 등록 화면에서 확인해야 합니다 [확인 못 함].

다른 선택: 설정은 하나로 두고 요청에 "탈퇴용" 표시를 붙임. 등록할 주소는 늘지 않지만 코드가 복잡해집니다.

Spring Security: 제공자에 보낼 고정 값은 로그인 주소 설정에 붙이는 방법을 안내. https://docs.spring.io/spring-security/reference/servlet/oauth2/client/authorization-grants.html (2026-10-04)

8"계정이 지워졌다" 기록이 남도록, 그 알림을 받는 작은 처리기를 auth 안에 하나 둠 [안]

계정이 지워지면 "계정 삭제됨" 알림을 내고 기록 표에 남기기로 하셨습니다(다음 사이클의 내 도서관 모듈이 이 알림을 받아 자기 자료를 지웁니다). 그런데 공식 문서를 보니 기록은 알림을 받는 쪽 하나마다 한 줄 생깁니다. 이번 사이클에는 받는 쪽이 없어서 기록이 0줄이 되고, 수용 기준 AC-15("삭제될 때마다 기록이 생긴다")를 통과할 수 없습니다.

추천은 auth 안에 받는 쪽을 하나 두는 것입니다. 하는 일은 서버 기록에 "계정 12 삭제됨" 한 줄을 남기는 것뿐입니다. 그러면 AC-15가 그대로 통과하고, 기록 표에 쓰고 완료 표시하는 길을 이번에 실제로 시험하게 됩니다.

기록 표는 어느 모듈의 것도 아니므로 별도 구역(스키마 modulith)에 둡니다. 다음 사이클의 모듈도 같은 표를 씁니다.

다른 선택: 받는 쪽을 두지 않고 AC-15를 "알림을 냈는지만 테스트로 확인"으로 바꿈. 하는 일 없는 코드는 없지만, 기록 표는 다음 사이클에 처음 쓰이게 됩니다.

Spring Modulith: "writes entries for each of them"(받는 쪽마다 기록). https://docs.spring.io/spring-modulith/reference/events.html · 받는 쪽이 0이면 0줄이라는 것은 이 문장에서 나온 추론이고 테스트로 확인 예정 (2026-10-04)

마주소와 이름 (2가지)

9로그인 관련 주소를 전부 /api/v1/auth/ 아래에 모으고, 토큰 쿠키가 가는 주소를 좁힘 [안]

쿠키에는 "이 주소로 갈 때만 붙여라"를 정할 수 있습니다. 액세스 토큰은 /api/v1/me로 갈 때만, 리프레시 토큰은 /api/v1/auth로 갈 때만 붙게 합니다.

요청붙는 쿠키
검색, 책 조회 (/api/v1/books…)없음
내 계정, 다음 사이클의 내 도서관 (/api/v1/me…)액세스 토큰
토큰 갱신, 로그아웃, 가입 (/api/v1/auth…)리프레시 토큰

검색에는 토큰이 아예 가지 않으므로, 토큰이 만료되거나 잘못돼도 검색이 막힐 일이 없습니다("로그인 안 해도 검색은 그대로"를 지키는 장치입니다). 리프레시 토큰이 오가는 곳도 줄어듭니다.

범위 문서(scope)의 주소 둘이 바뀝니다.

범위 문서에 적힌 것바꾸는 것
로그아웃POST /logoutPOST /api/v1/auth/logout
가입 동의POST /api/v1/me/consentsPOST /api/v1/auth/signup (동의하는 순간에는 아직 계정이 없어 "me"가 아님)

사용자가 하실 일: 네이버·카카오에 등록할 "돌아올 주소"가 …/api/v1/auth/login/oauth2/code/naver 같은 모양이 됩니다.

다른 선택: Spring 기본 주소(/oauth2/…, /login/…, /logout)를 그대로 쓰고 쿠키를 모든 주소에 붙임. 설정은 적지만 검색 요청에도 토큰이 따라갑니다.

MDN Set-Cookie의 Path: 지정한 경로와 그 아래 경로에만 쿠키를 보냄. https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie (2026-10-04)

10표와 칸의 이름, 작은 값들 [안]

로그인 수단 표는 정하신 대로 소셜 전용 이름을 쓰지 않습니다. 칸 이름을 "제공자", "제공자 번호"가 아니라 "종류"(method)와 "그 안의 식별자"(subject)로 짓습니다. 나중에 이메일·비밀번호 로그인은 종류에 값 하나를 더하고 비밀번호만 담는 표를 붙이면 됩니다.

무엇제안
표 이름auth.account, auth.login_method, auth.account_consent, auth.refresh_token
리프레시 토큰 저장값 그대로가 아니라 지문(SHA-256 해시)으로. DB가 새어도 그 값으로 로그인을 이어 갈 수 없음
쿠키 이름access_token, refresh_token
임시 값 수명10분
만료된 리프레시 토큰 줄 정리하루 한 번
약관 문서 버전 표기시행 날짜 (예: 2026-11-01)
네이버 "연결 끊김" 알림에 적힌 시각지금과 5분 넘게 차이 나면 거절 (누가 옛 알림을 다시 보내 계정을 지우는 것을 막음)

다른 선택: 바꾸고 싶은 이름이나 값을 글 상자에 적어 주세요. 5분과 10분은 근거 문서가 있는 값이 아니라 제 제안입니다.

가운데 둘의 정확한 이름은 Spring Boot 4.1 공식 목록에서 확인하지 못했습니다 [확인 못 함]. dev가 구현 때 공식 문서로 확인합니다. 넣고 나면 기존 검색 응답의 내용은 같지만 보안 헤더 몇 개가 더 붙습니다.

12보안 헤더를 붙이는 곳과 운영 배포 구성은 이번에 정하지 않고 뒤로 미룸 [안]

Spring Security가 붙이는 보안 헤더는 Spring이 보내는 응답에만 붙습니다. 화면 파일(React)을 운영에서 누가 내려 줄지는 아직 정해진 적이 없습니다. dev 코드에도 그 구성이 없습니다. 그래서 화면 파일 쪽 헤더(다른 사이트가 우리 화면을 틀에 넣지 못하게 하는 것 등)는 배포를 정하는 사이클에서 함께 정하고, backlog에 적어 둡니다. 이번 사이클에서는 API 응답에 Spring 기본 헤더를 붙이는 것까지 합니다.

다른 선택: 지금 "운영에서도 Spring이 화면 파일을 내려 준다"로 정함. 헤더를 한 곳에서 관리하게 되지만 배포 방식을 이 사이클에서 정하게 됩니다.
