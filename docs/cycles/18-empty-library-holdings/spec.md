# 기능 명세: 소장이 비었거나 덜 모인 도서관

- 범위: [scope.md](scope.md) (범위 결정 10개, 조사 결정 5개 모두 승인, 2026-10-14). 조사 근거: [research.md](research.md)
- 이 사이클은 화면을 바꾸지 않습니다. 이용자에게 보이는 변화는 "책이 없는 도서관이 목록에서 빠짐"과 "현대제철 책이 검색에 나옴" 둘입니다.

## 사용자 이야기

- 이용자는 "내 도서관"이나 검색 범위로 고를 수 있는 도서관이 실제로 책을 가진 곳이기를 바란다. 골라도 결과가 늘 0인 도서관은 헷갈리기 때문이다 (사용자 의도: 사이클 12 분포 검사에서 따로 사이클로 뺌 "이거 따로 사이클 빼게 문서에 적어두고")
- 운영자(사용자)는 새 도서관을 넣을 때 같은 일이 다시 생기지 않기를 바란다 (조사 결정 #2 승인)

## 동작 규칙

### R1. 22곳을 끔

| 원인 | 서비스 번호 | 사이트 원문으로 적을 것 |
|---|---|---|
| 오디오북만 있음 (14) | 112, 168, 305, 318, 378, 425, 455, 514, 537, 622, 623, 625, 626, 721 | 첫 화면 분류 메뉴(예: 정관도서관 "전체 (2,982종) / 오디오북 (2,982종)"), BookLive 화면은 "10월의 오디오북" |
| 사이트에 책이 없음 (1) | 323 | "전체 (0종)" |
| 교보 구독형, 수집 때 0권 (4) | 1045, 1131, 1620, 2023 | 2026-10-04 수집 기록 "사이트 권수 0" (지금 사이트는 열지 않음) |
| 수집 안 함으로 알려짐 (2) | 44, 269 | 수집 DB `crawl_skip` 문구 |
| 다른 사이트로 옮김 (1) | 261 | `crawl_skip` 문구 "… = library 46" |

- R1-1. 끈 도서관은 지금 꺼진 도서관(사이클 07에서 끈 135·2194·2198 등)과 똑같이 다룸: 도서관 목록 API와 범위 고르기에서 빠지고, 이미 "내 도서관"에 직접 추가해 둔 사람에게는 지금처럼 "쓸 수 없는 도서관"으로 보임 (`docs/current/module-map.md`의 "쓸 수 없는 도서관" 줄, `api.md`의 "직접 추가 상한"·`library_not_found` 줄) [확정: 지금 동작]
- R1-2. 끄는 방법(사이클 07처럼 새 Liquibase 변경 파일, 또는 다른 방법)은 설계에서 정함 [확인 필요]
- R1-3. 사이클 13의 "서비스에서 빠진 도서관 목록"(dev `docs/library-left-out.md` B절, 만드는 스크립트 `list_left_out.py`)에도 22곳이 나오게 함. 국회·군포·김천은 이미 "확인한 곳"으로 있으므로 B절은 8곳에서 27곳(끈 27)이 됨 [확정] (사용자 승인, 2026-10-14, 명세 결정 #2)
- R1-4. 교보 구독형 4곳은 다른 IP에서 교보 구독형 서버를 다시 받을 때(backlog) 책이 있으면 다시 켬. 이 사이클에서는 다시 켜는 장치를 만들지 않음 [확정] (조사 결정 #4)

### R2. 새 도서관을 넣을 때 전자책이 0권인 곳은 넣지 않음

- R2-1. 넣기 명령이 수집 사본에서 도서관마다 "서비스로 가져올 줄 수"를 셈. 셈은 가져오기가 줄을 거르는 규칙과 같음: 지운 표시, 오디오북·동영상 책 등 빼는 종류, 소리·영상 종류, 책 주소 없음·읽을 수 없음, 제목 없음을 뺀 나머지 (dev `CollectedCatalog.skipReason`) [확정] (사용자 승인, 2026-10-14, 명세 결정 #3)
- R2-2. 그 수가 0이면 그 도서관은 "넣지 않음"으로 빠지고 보고서의 빠진 이유에 "전자책 0권"([확정] (사용자 승인, 2026-10-14, 명세 결정 #1))으로 나옴. 지금 빠진 이유(교보 대여·혼합, 받지 않음, 수집 성공 없음, 체험용·운영 중단, 같은 사이트, 시험용) 다음, 맨 마지막 차례로 봄. 교보 대여·혼합 판정은 바뀌지 않음(책을 받지 않아 책 수가 0이므로, 0권을 먼저 보면 대여·혼합이 "전자책 0권"으로 잘못 나옴) [확정] (사용자 승인, 2026-10-14, 명세 결정 #4)
- R2-3. 이미 서비스에 있는 도서관에는 이 규칙을 적용하지 않음 (넣기 명령은 새 곳만 넣음). 이미 있는 곳은 R1처럼 사람이 정해 끔 [확정: 넣기 명령의 지금 동작, 사이클 13]

### R3. 밑줄이 있는 호스트를 읽음

- R3-1. 가져오기는 책 주소의 호스트에 밑줄이 있어도 같은 도서관 주소로 알아보고 들어오게 함. 현대제철(2624)의 전자책 241줄이 가져오기 고침 뒤 첫 가져오기 때 들어감(가져오기 고침은 사이클 19 뒤, R5). 다시 수집하지 않음 [확정] (조사 결정 #3)
- R3-2. 대출 조회와 "도서관에서 직접 찾기"도 같은 주소에서 동작해야 함 → 밑줄 호스트용 요청 길을 따로 만듦 [확정] (사용자, 2026-10-14, ADR-0111). dev 코드를 읽어 보니 대출 조회의 호스트별 간격 키(`HostThrottle.key`)와 책 상세 주소 검사(`DetailPageFetcher.checkedUri`)가 같은 Java 주소 읽기(`getHost()`)를 써서, 밑줄 호스트면 호스트가 비어 조회가 안 될 것으로 보임 (실제로 어떻게 실패하는지는 확인 못 함) [확인 필요]
- R3-3. 고칠 곳의 범위: 도서관 주소·책 주소에서 호스트를 읽는 모든 곳. 어떻게 고칠지(밑줄을 허용하는 읽기로 바꾸기 등)는 설계에서 정함
- 근거: Java 21 `java.net.URI` 문서 `getHost()` 절 — 호스트 이름의 각 칸은 영문·숫자·`-`만 허용, https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/net/URI.html (확인 2026-10-14)

### R4. 덜 모인 것처럼 보인 6곳

- 할 일 없음. research.md 3절에 기록으로 끝냄 [확정] (조사 결정 #5)

### R5. 순서

- dev 작업은 사이클 13이 main에 들어간 뒤(들어감), 운영 반영은 사이클 17 첫 배포 뒤 보통 반영(ADR-0078) [확정] (범위 결정 #8)
- 가져오기 고침(R3-1, R2의 거르기 규칙 한 벌)과 넣기 "전자책 0권"은 사이클 19가 main에 들어간 뒤 [확정] (사용자: "19뒤에 하자", 2026-10-14). 22곳 끄기와 밑줄 호스트 요청 길은 언제든 (17과 순서 상관없음, 사용자 2026-10-14)

## 상태별 동작

- 로딩·결과 없음·외부 오류: 화면을 바꾸지 않으므로 지금 동작 그대로
- 현대제철 대출 조회가 실패할 때: 지금처럼 그 도서관만 실패로 보임. R3-2를 고치면 생기지 않아야 함
- 넣기 보고서에서 "전자책 0권"으로 빠진 곳이 생겼을 때: 다른 빠진 이유와 같이 보고서에만 나오고, 사용자에게 따로 묻지 않음 (넣기 명령은 의심·바뀐 곳·사라진 곳만 물음) [확정] (사용자 승인, 2026-10-14, 명세 결정 #5)

## 수용 기준

- AC-1: 22곳 끄기와 현대제철 가져오기(19 뒤)가 둘 다 끝난 뒤 내 PC 서비스 DB에서, 켜져 있는데 소장이 0인 도서관을 세는 SQL(사이클 12 분포 검사와 같은 SQL)을 돌리면 0곳이다
- AC-2: `GET /api/v1/libraries` 응답에 R1의 22곳이 하나도 없다
- AC-3: 22곳 중 하나를 "내 도서관"에 직접 추가해 둔 계정으로 "내 도서관 관리"를 열면 그 도서관이 "쓸 수 없는 도서관"으로 보인다 (지금 동작)
- AC-4: 검색 범위에 현대제철(2624)만 고르고 수집 DB에 있는 현대제철 책 제목(예: 「1984」)을 검색하면 결과에 나오고, 그 줄의 대출 조회가 "대출 가능 여부 확인 필요"(조회 실패 때 화면 문구)가 아닌 보유·대출 수를 보인다
- AC-5: 다음 가져오기 기록의 건너뜀 이유 `detail_url_not_http`가 241줄 줄어든다 (283 → 42)
- AC-6: 오디오북만 있는 도서관이 든 수집 사본으로 넣기 미리 보기를 돌리면 그 도서관이 보고서의 빠진 곳에 "전자책 0권"으로 나오고, 넣기 뒤 서비스 도서관 표에 없다 (시험 데이터로 확인)
- AC-7: dev `library-site-issues.md`에 22곳이 원인·원문·확인일과 함께 있다
- AC-8: 운영 서버 반영 뒤 AC-1의 SQL을 운영 DB에서 돌려도 0곳이다 (사이클 17 첫 배포 뒤)

## 비목표

- 오디오북 가져오기 — 우리는 전자책만 다룸(가져오기에서 오디오북을 뺌) [이유 미확인]
- 책이 없는 도서관을 화면에 표시하거나 목록에서만 숨기기 — 범위 결정 #5로 끄기만 함 (backlog)
- 도서관을 끈다는 공지 — 범위 결정 #5
- 사이트 권수(`holdings_count`)를 전자책만 센 값으로 고치기 — 정렬에 쓰여 순서가 바뀜, 조사 결정 #5
- 끈 도서관을 자동으로 다시 켜는 장치 — R1-4
- 이미 서비스에 있는 도서관을 가져오기 때마다 0권인지 자동으로 검사해 알리기 — 범위 밖 (backlog에 한 줄)
