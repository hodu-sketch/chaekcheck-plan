사이클 18 2차 검토:
조회 서버 앱 결정을 기록으로 남기기

2차 검토에서 "조회 서버 앱에도 같은 길" 결정이 여러 문서에 덜 퍼져 있다는 지적이 나와 모두 맞췄습니다(scope·spec·설계·인계서·지금 설계 문서). 남은 것은 이 결정을 ADR로 남기는 것 하나입니다. (2026-10-14)

1맞춘 것

  • 범위·명세·설계·인계서에 "조회 서버 앱(fetch-service)도 같은 밑줄 길"을 넣음
  • 인계서: 바뀌는 곳에 조회 서버 앱, 그 앱의 빌드·시험, 의존성은 앱마다 하나(같은 라이브러리)
  • 조회 서버 앱의 주소 검사는 지금 하는 보호를 그대로 둠: 밑줄 이름으로 DNS를 풀어 내부망 주소면 거부, 사용자 정보가 든 주소 거부. "밑줄 이름이 내부망으로 풀리면 거부" 시험을 넣음
  • module-map.md에 사이클 18 구성도·도메인 모델 그림, 조회 서버 줄 갱신

2ADR 초안

ADR-0111은 본 서비스(가져오기·대출 조회)만 다뤘습니다. 조회 서버 앱은 따로 도는 앱이고 보안 검사도 고치므로, 이 결정을 ADR-0112로 남깁니다. ADR-0111은 그대로 두고 보완합니다.

1ADR-0112: 밑줄 호스트 요청 길을 조회 서버 앱에도 넣는다

[안] 내용: 조회 서버 앱의 주소 검사는 밑줄 호스트를 읽되 실제 연결할 이름과 같은 이름으로 DNS를 풀어 내부망이면 거부하고, 요청은 본 서비스와 같은 라이브러리·같은 조건으로 보냄. 이유: "같이 해 굳이 왜 나눠서 해 조회 서버도 같이 해". 대안: 직접 조회에만 넣기(미승인). 승인하면 docs/adr/에 확정(Accepted)으로 쓰고, 설계·인계서·지금 설계 문서의 ADR 줄에 연결합니다.

다른 선택: ADR 없이 설계 문서에만 적음 → 규칙상 구조 결정은 ADR로 남기는 쪽이 맞습니다.
