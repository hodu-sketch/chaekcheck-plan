사이클 18 명세:
새 도서관을 넣을 때 "전자책 0권"을 어떻게 거를지

명세의 대부분은 이미 정한 것(22곳 끄기, 현대제철 고치기)을 받아 적은 것입니다. 새로 정할 것은 6가지이고, 모두 "다음에 새 도서관을 넣을 때 책이 없는 곳을 어떻게 거르고 어디에 보이게 할지"에 관한 것입니다. (2026-10-14)

1명세에 받아 적은 것 (이미 정함)

화면은 바꾸지 않습니다. 이용자에게 보이는 변화는 둘입니다. 책이 없는 22곳이 도서관 목록에서 빠지고, 현대제철 책이 검색에 나옵니다.

무엇어떻게
22곳 끄기오디오북만 있는 14곳, 책 0종 1곳, 교보 구독형 4곳, 국회·김천·군포 3곳. 끈 뒤에는 지금 꺼진 도서관과 똑같이 목록·범위에서 빠지고, "내 도서관"에 직접 넣어 둔 사람에게는 "쓸 수 없는 도서관"으로 보입니다(지금 동작)
끈 이유 적기dev library-site-issues.md에 도서관마다 원인과 사이트 원문, 확인일
현대제철밑줄(_)이 있는 주소를 가져오기가 읽게 고쳐 전자책 241권을 넣음. 다시 수집은 안 함
6곳할 일 없음, 기록만

명세를 쓰며 새로 안 것: 대출 조회와 "도서관에서 직접 찾기"도 같은 방식으로 주소를 읽습니다. 그래서 밑줄 주소에서는 현대제철 책이 검색에 나와도 대출 조회가 안 될 것으로 보입니다. 코드를 읽어서 본 것이고, 실제로 어떻게 실패하는지는 확인 못 했습니다. 고칠 곳에 대출 조회도 넣었습니다(명세 R3-2, 정해진 결정 "현대제철을 고친다"의 범위 안).

2새 도서관 넣기에서 거르기

사이클 13에서 만든 "새 도서관 넣기" 명령은 미리 보기 보고서를 만들고, 넣지 않을 곳을 이유별로 보여 줍니다. 여기에 "전자책 0권"이라는 이유를 하나 더하는 일입니다.

어느 이유에도 걸리지 않은 곳만 넣습니다. 새 이유는 맨 마지막에 봅니다.

1보고서에 쓰는 이유 이름: "전자책 0권"

[안] 보고서와 "서비스에서 빠진 도서관 목록"에 "전자책 0권"으로 적습니다. 오디오북만 있는 곳과 아무 책도 없는 곳을 한 이름으로 묶습니다.

다른 선택: 둘로 나눔("오디오북만 있음" / "책 없음") → 원인이 더 잘 보이지만 이유가 하나 더 늘어납니다.

추천: "전자책 0권" 하나.

2이번에 끄는 22곳도 "서비스에서 빠진 도서관 목록"에 나오게 함

[안] 사이클 13에서 만든 dev docs/library-left-out.md는 "수집했지만 안 넣은 곳"과 "서비스에 있지만 문제 있는 곳"을 한 문서에 모아 둔 목록입니다(스크립트로 만듦). 이번에 끄는 22곳도 이 목록의 "서비스에 있지만 문제 있는 곳"에 이유와 함께 나오게 합니다. 국회·군포·김천 3곳은 이미 이 칸에 "확인한 곳"으로 있으므로, 이 칸은 지금 8곳(끈 5 + 확인한 3)에서 27곳(끈 27)이 됩니다.

다른 선택: library-site-issues.md에만 적음 → 문서가 둘로 나뉘어, 꺼진 도서관 전체를 보려면 두 곳을 봐야 합니다.

추천: 목록에도 나오게 함.

3"전자책 0권"을 세는 방법: 가져오기가 거르는 규칙과 똑같이

[안] 넣기 명령이 도서관마다 "서비스로 가져올 수 있는 줄"을 셉니다. 가져오기가 줄을 거르는 규칙을 그대로 씁니다. 지운 표시, 오디오북·동영상 책, 소리·영상 종류, 책 주소 없음, 제목 없음은 세지 않습니다. 예: 정관도서관은 2,982줄이 모두 오디오북이라 0 → 넣지 않음.

다른 선택: 수집 기록의 사이트 권수가 0인 곳만 거름 → 간단하지만, 이번 14곳처럼 오디오북만 있는 곳은 못 거릅니다.

추천: 가져오기와 같은 규칙. 넣었는데 가져오면 0권이 되는 일이 없어집니다.

4"전자책 0권"은 다른 이유 다음에 봄

[안] 그림처럼 지금 있는 여섯 이유를 먼저 보고, 어디에도 걸리지 않은 곳만 책 수를 셉니다. 예: 교보 대여·혼합 사이트이면서 책도 0인 곳은 "교보 대여·혼합"으로 나옵니다.

다른 선택: 맨 앞에서 봄 → 빈 곳은 모두 "전자책 0권"으로 나오지만, 원래 이유(대여·혼합, 체험용 등)가 가려집니다.

추천: 맨 마지막.

5"전자책 0권"으로 빠진 곳은 사용자에게 따로 묻지 않음

[안] 넣기 명령은 지금 "의심·바뀐 곳·사라진 곳"만 사용자에게 묻고, 빠진 곳은 보고서에만 적습니다. "전자책 0권"도 빠진 곳이므로 보고서에만 나오고 따로 묻지 않습니다.

다른 선택: 이 이유만 사용자에게 물음 → 나중에 전자책을 들일 수도 있는 곳을 사람이 한 번 더 볼 수 있지만, 넣을 때마다 묻는 일이 늘어납니다.

추천: 묻지 않음.

3다음 단계

이 사이클은 화면이 바뀌지 않아, 화면 흐름 단계는 "바뀌는 화면 없음"을 확인하는 짧은 문서로 끝납니다.

6이 명세대로 설계로 감

[안] 판정은 "설계 진행 가능"입니다. 남은 확인 세 가지(끄는 방법, 대출 조회가 실제로 어떻게 실패하는지, 넣기 명령이 책 수를 셀 수 있는지)는 설계 때 dev 코드를 읽거나 개발 때 시험해서 풉니다. 설계 확정과 인계서는 사이클 12~14 회고 뒤에 씁니다(범위 결정 #8).

다른 선택: 셋을 먼저 풀고 명세를 다시 봄 → 하루 정도 늦어지지만 명세가 더 단단해집니다.

추천: 설계로 감.
