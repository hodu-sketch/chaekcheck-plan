사이클 18 설계 후속:
밑줄 주소용 요청 길을 미리 만들기

설계 결정 3번에서 "그 줄만 실패" 안이 미승인되고, 밑줄 주소는 따로 처리하도록 미리 개발하기로 정해졌습니다. 그러면서 새로 정할 세부가 5가지 생겼습니다. 그중 하나는 사이클 17이 같은 코드를 고치는 것과 관련됩니다. 여기에 사이클 15 세션이 회고에서 알려 온 사이클 19와의 순서 하나를 더해 6가지입니다. (2026-10-14)

1정해진 것

사용자: "java개발 따로 해 _ 은 다르게 처리하도록 그냥 미리 개발해두는거야" (2026-10-14, 설계 결정 3번 미승인과 함께)

  • 대출 조회에서 주소 호스트에 밑줄이 있으면, Java 기본 요청 기능 대신 따로 만든 요청 길로 보냅니다
  • 그래서 명세의 수용 기준 AC-4("현대제철 줄의 대출 조회가 '확인 불가'가 아닌 값")는 바꾸지 않고 그대로 둡니다
  • 지금은 현대제철 한 곳뿐이지만, 앞으로 밑줄 주소 도서관이 들어와도 같은 길을 씁니다

2새로 확인한 사실: 보안 연결

밑줄 주소는 Java의 보안 연결에서도 걸리는 곳이 하나 있습니다. 다만 현대제철 사이트는 그 부분 없이도 맞는 인증서를 보냅니다.

무엇결과근거
Java가 보안 연결을 열 때 "어느 사이트에 연결하는지" 이름을 먼저 알리는 기능(SNI)이 이름에 밑줄을 넣을 수 없음 (영문·숫자·하이픈 규칙)Java 21 SNIHostName 문서: 이름을 STD3 규칙으로 검사, 어기면 거절 https://docs.oracle.com/en/java/javase/21/docs/api/java.base/javax/net/ssl/SNIHostName.html (확인 2026-10-14). 밑줄을 거절한다는 문장은 문서에 없고 규칙에서 미루어 봄
현대제철 사이트에 이름을 알리지 않고 연결하면인증서 *.yes24library.com을 보냄 (이름을 알릴 때와 같음)2026-10-14 openssl s_client로 한 번씩 연결해 확인
그 인증서가 hs_partners.yes24library.com에 맞는지(이름 검사)와일드카드 한 칸 규칙으로는 맞아야 함. 실제 Java 검사 통과 여부는 확인 못 함개발 때 시제품으로 확인

3정할 것

1밑줄 주소 길은 대출 조회와 "도서관에서 직접 찾기" 둘 다에 씀

[안] 우리 서버가 도서관 사이트에 요청을 보내는 곳은 둘입니다. 책마다 대출 상태를 묻는 대출 조회와, 우리 목록에 없는 책을 사이트 검색창으로 찾는 직접 찾기. 둘 다 같은 요청 부품을 쓰므로, 그 부품 안에서 "호스트에 밑줄이 있으면 따로 만든 길"로 가르게 합니다. 밑줄이 없는 2,679곳은 지금 길 그대로입니다.

다른 선택: 대출 조회만 → 현대제철을 직접 추가한 사람이 직접 찾기를 켜면 그 도서관만 실패로 남습니다.

추천: 둘 다.

2어떤 요청 라이브러리를 쓸지는 dev가 시제품으로 고름 (첫 후보 Apache HttpClient 5)

[안] 고르는 조건을 정하고, dev가 현대제철 주소로 실제 요청을 보내 보고 고릅니다. 조건: ① 밑줄 호스트로 실제 요청이 됨 ② 지금 길과 같은 시간 제한·응답 크기 제한·도서관 사이트 인증서 설정을 씀 ③ 새로 들이는 라이브러리는 하나 ④ 인증서 이름 검사를 끄지 않음. 첫 후보는 자바에서 많이 쓰는 Apache HttpClient 5이지만, 이 라이브러리가 밑줄 호스트를 받는지는 문서로 확인 못 했습니다(소스에서 주소 해석이 Java 기본 기능에 기대는 부분이 있어 시제품이 필요).

다른 선택: 지금 plan에서 라이브러리를 하나로 정함 → 확인 못 한 채 정하게 되어, 안 되면 다시 정해야 합니다.

추천: 조건만 정하고 dev가 시제품으로 고름. 고른 결과는 인계 뒤 기록으로 받습니다.

3보안 연결: 이름 알리기(SNI)는 빼고, 인증서 이름 검사는 그대로 켬

[안] 2번 표처럼 밑줄 이름은 SNI로 보낼 수 없으므로 SNI 없이 연결합니다. 대신 받은 인증서가 그 주소에 맞는지는 지금처럼 검사합니다. 검사가 통과하지 않으면 그 줄만 "확인 필요"가 됩니다(4번).

다른 선택: 인증서 이름 검사를 꺼서라도 연결 → 다른 사이트로 연결돼도 모르게 되어 쓰지 않습니다.

추천: SNI만 빼고 검사는 켬.

4밑줄 주소 길이 실패하면 그 줄만 "대출 가능 여부 확인 필요"

[안] 따로 만든 길로도 연결이 안 되면(인증서 검사 실패, 시간 초과 등) 다른 도서관과 똑같이 그 줄만 실패로 보이고, 나머지 줄과 직접 찾기는 영향을 받지 않습니다. 지금 숨어 있는 오류(직접 찾기가 밑줄 주소에서 멈출 수 있는 곳)도 이때 함께 없앱니다.

다른 선택: 실패하면 Java 기본 길로 한 번 더 → 기본 길은 밑줄 주소로 요청을 만들 수 없어 의미가 없습니다.

추천: 그 줄만 실패.

5사이클 17이 고치는 요청 부품 위에 얹음 (17 개발 뒤에 18 개발)

[안] 사이클 17은 같은 요청 부품(availability의 사이트 요청)에 "나가는 길 고르기(직접/업체 프록시/조회 서버), 나가는 IP마다 세기, 막힌 IP 멈추기, 일반 브라우저 User-Agent"를 넣습니다(ADR-0095). 18의 밑줄 길은 17이 만든 구조 위에서 "직접 나가는 길"의 한 갈래로 넣고, 17이 정한 User-Agent·셈·멈춤 규칙을 그대로 따릅니다. 그래서 18의 이 부분은 17 개발이 끝난 뒤에 개발합니다. 18의 나머지(22곳 끄기, 가져오기 고침, 넣기 거르기)는 17과 겹치지 않아 순서와 상관없습니다. 17 세션에는 겹치는 파일만 짧게 알립니다.

범위 결정 #8("dev 작업은 13 뒤")에 "밑줄 길만 17 개발 뒤"를 더하는 안입니다.

다른 선택: 17과 상관없이 먼저 개발 → 같은 파일을 두 사이클이 동시에 고쳐 합칠 때 부딪힙니다.

추천: 17 뒤.

6가져오기 코드 고침은 사이클 19 개발 뒤에, 그때 옛 이름도 함께 바꿈

[안] 사이클 15 세션이 12·13·14 회고에서 알려 온 것입니다(docs/cycles/15-usage-log/to-cycle-18.md). 사이클 19(꺾쇠 저자 표기)는 가져오기 코드와 저자 정리를 고치고 17 첫 배포 전에 책 목록을 다시 가져옵니다. 18도 같은 가져오기 파일(CollectedCatalog)을 고치므로, 18의 가져오기 고침(밑줄 주소 읽기, 거르기 규칙 한 벌로 꺼내기)은 19 개발이 main에 들어간 뒤에 합니다. 이때 회고에서 정한 대로 사이클 12의 시험용 설정 이름 exclude-candidate-libraries(옛 용어가 든 이름)도 함께 바꿉니다.

다른 선택: 19와 같은 때 나란히 개발 → 같은 파일을 둘이 고쳐 합칠 때 부딪힙니다. / 이름은 그대로 둠 → 회고 결정("다음에 가져오기 코드를 고칠 때 바꿈")과 어긋납니다.

추천: 19 뒤, 이름도 함께.
