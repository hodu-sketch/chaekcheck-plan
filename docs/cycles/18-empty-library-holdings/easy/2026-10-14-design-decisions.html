사이클 18 설계:
새 표·새 화면 없이, 끄기는 DB 변경 파일 하나로

설계 대안을 dev 코드를 읽어 만들었습니다. 새 표, 새 칸, 새 API, 새 화면은 없습니다. 정할 것은 7가지입니다. 그중 하나(2번)는 앞서 정한 수용 기준을 바꾸는 안이라 먼저 읽어 주세요. (2026-10-14)

1무엇이 바뀌나

세 모듈의 안쪽만 고칩니다. 모듈 사이의 관계는 그대로입니다.

모듈바뀌는 것
library (도서관 표)22곳을 끄는 DB 변경 파일 하나. 코드 변경 없음
collection (가져오기·새 도서관 넣기)밑줄 주소 읽기, 가져오기의 책 거르기 규칙을 넣기 명령도 같이 쓰게, 빠진 이유 "전자책 0권"

화면, 다른 모듈바뀌지 않음

222곳을 내 PC와 운영 서버에서 끄는 방법

운영 서버로 책 목록을 옮길 때, 우리 프로그램은 "켜진 도서관 목록"이 내 PC와 운영 서버에서 같은지부터 봅니다. 다르면 안전하게 멈춥니다. 그래서 끄는 일이 두 곳에 똑같이 들어가야 합니다.

사이클 07에서 3곳을 끌 때와 같은 방식입니다. 파일이 앱과 함께 가므로 한쪽만 빠뜨릴 수 없습니다.

1DB 변경 파일(Liquibase)로 끔

[안] 22곳을 끄는 변경 파일 하나를 dev에 더합니다. 내 PC에서 앱을 새 판으로 켜면 꺼지고, 운영 서버에 같은 판을 올려 반영하면 거기서도 꺼집니다. 순서: 내 PC를 새 판으로 → 가져오기·내보내기 → 운영에 같은 판 → 반영. 끄기 전 판으로 내보내면 반영이 멈추므로 절차 문서에 한 줄 적습니다.

다른 선택: 손으로 SQL을 두 번 실행 → 가장 빠르지만 한쪽을 빠뜨리면 반영이 멈추고, 새로 만드는 DB에는 들어가지 않으며 기록이 git에 남지 않습니다. / 새 도서관 넣기 명령이 끄기도 하게 → 사이클 13에서 만든 명령과 반영 파일 모양을 다시 고쳐야 합니다.

추천: DB 변경 파일. 교보 구독형 4곳을 나중에 다시 켤 때도 변경 파일 하나를 더합니다.

2국회·군포·김천을 "확인하고 켜 둔 곳" 목록에서 지움

[안] 사이클 13은 이 3곳을 규칙 파일 gone_known.tsv에 "사라졌지만 서비스에 켜 둔 곳"으로 적었습니다. 이번에 끄므로 이 줄을 지우고, 대신 "꺼 둔 이유" 파일(disabled_reasons.tsv)에 22곳을 모두 적습니다.

다른 선택: 그대로 둠 → 해는 없지만(꺼진 곳은 비교에서 빠짐) "켜 둠"이라는 설명이 틀린 채 남습니다.

추천: 지움.

3현대제철: 책은 나오지만 대출 조회는 안 되는 문제

설계 중 새로 안 것입니다. 우리 서버가 도서관에 요청을 보낼 때 쓰는 Java 기본 기능은 주소에 밑줄이 있으면 요청 자체를 만들지 않습니다. 주소 읽기를 고쳐도 현대제철에는 요청을 보낼 수 없습니다.

근거: Java 21 URI 문서 https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/net/URI.html, JDK 21 요청 만들기 코드 checkURI "unsupported URI" https://github.com/openjdk/jdk21u/blob/master/src/java.net.http/share/classes/jdk/internal/net/http/HttpRequestBuilderImpl.java, OpenJDK 문제 기록 JDK-8180809 "Not an Issue" https://bugs.openjdk.org/browse/JDK-8180809 (모두 확인 2026-10-14)

3현대제철 대출 조회는 "그 줄만 실패"로 두고 수용 기준 AC-4를 고침

[안] 대출 조회는 호스트를 못 읽는 주소면 요청하지 않고 그 도서관 줄만 실패로 보입니다. 지금은 이런 주소에서 오류로 멈출 수 있는 곳(직접 찾기)이 있어 그것도 같이 막습니다. 명세 AC-4 "대출 조회가 '확인 불가'가 아닌 값"을 "현대제철 책이 검색에 나오고, 그 줄의 대출 조회는 실패로 보이며 다른 도서관 줄에는 영향이 없다"로 고칩니다.

명세 결정에서 승인한 AC-4를 바꾸는 안입니다. 그때는 이 Java 동작을 몰랐습니다.

다른 선택: 밑줄 주소만 다른 요청 라이브러리로 보냄 → AC-4를 그대로 지킬 수 있지만, 한 도서관을 위해 라이브러리와 인증서 설정이 두 벌이 되고, 밑줄 주소에서 보안 연결(인증서 이름 검사)이 통과하는지 확인 못 했습니다. / 현대제철을 끔 → 조사 결정 #3과 어긋납니다.

추천: 그 줄만 실패. 다른 라이브러리로 보내는 일은 backlog에 적습니다.

질문: 3번을 그림으로 자세히 설명해 주세요

요약: 현대제철 책 241권은 이번에 검색에 나오게 됩니다. 다만 그 책 줄의 "대출 중인지, 예약이 몇 명인지"는 우리 서버가 현대제철 사이트에 물어볼 수 없어서 "대출 가능 여부 확인 필요"로 보입니다. 이용자는 그 줄의 도서관 링크로 사이트를 열어 직접 볼 수 있습니다.

① 문제는 주소의 "호스트" 부분에 든 밑줄 하나입니다

도서관 주소는 몇 부분으로 나뉩니다. 그중 "호스트"는 어느 컴퓨터에 연결할지를 정하는 이름입니다.

브라우저는 이 주소를 문제없이 엽니다(2026-10-14 앱 안 브라우저로 열림). 막히는 것은 우리 서버 프로그램(Java)입니다.

② 우리 서버가 하는 일 세 가지와, 각각 밑줄에서 어떻게 되는지

우리 서버가 하는 일지금이번에 고친 뒤 (추천안)
가져오기: 모아 둔 책 목록을 서비스 DB에 넣음주소를 "읽을 수 없음"으로 보고 241권을 모두 버림 → 검색에 안 나옴고침. 밑줄을 받는 주소 읽기로 바꿔 241권이 들어감 → 검색에 나옴
대출 조회: 검색 결과의 책마다 도서관 사이트에 "지금 대출 중인가"를 물어봄(책이 없어서 일어날 일 없음)Java가 밑줄 주소로는 요청을 만들지 않음 → 그 줄만 "대출 가능 여부 확인 필요"
도서관에서 직접 찾기: 우리 목록에 없는 책을 사이트 검색창으로 찾음현대제철을 직접 추가한 사람이 켜면 오류로 멈출 수 있음 (코드로 봄)오류 대신 현대제철만 실패로 넘어가고 다른 도서관은 계속 찾음

대출 조회의 요청은 Java에 들어 있는 기본 요청 기능이 만듭니다. 이 기능은 주소에서 호스트를 못 읽으면 요청을 보내기 전에 거절합니다(JDK 21 코드 "unsupported URI"). 우리 코드의 주소 읽기를 고쳐도 이 기본 기능은 그대로입니다.

③ 이용자 화면에서는 이렇게 보입니다 (PC 검색 결과의 한 책)

모양은 위치와 문구만 보인 것이고 실제 디자인과 다릅니다. 문구 "대출 가능 여부 확인 필요"는 지금 dev 화면(ResultRow.tsx)이 조회를 못 했을 때 쓰는 문구입니다. 폰·태블릿도 같은 문구가 그 줄에 나옵니다.

④ 왜 이 안을 추천하나

  • 현대제철은 "구성원만 가입" 도서관입니다. 이용자가 "내 도서관"에 직접 넣었을 때만 검색 범위에 들어갑니다. 지금 그런 이용자는 없습니다(가입자는 시험 사용자 한 명)
  • 다른 안(밑줄 주소만 다른 요청 라이브러리로 보냄)은 대출 수까지 보여 줄 수 있지만, 이 한 도서관을 위해 요청 라이브러리와 보안 연결 설정을 하나 더 두어야 하고, 밑줄 주소에서 보안 연결이 실제로 통과하는지 확인 못 했습니다
  • 나중에 필요해지면 그 안을 이 위에 더할 수 있습니다(backlog에 적음)

그래서 바뀌는 수용 기준 AC-4는: "현대제철만 범위로 골라 그 책을 검색하면 결과에 나오고, 그 줄은 '대출 가능 여부 확인 필요'로 보이며, 다른 도서관 줄과 직접 찾기는 영향받지 않는다"입니다.

질문: 현대제철 말고도 밑줄 주소가 있을 수 있는데, Java 쪽에서 고쳐야 하는 것 아닌가요?

지금은 현대제철 한 곳뿐입니다. 그리고 Java 자체는 우리가 고칠 수 없어서, "Java에서 고친다"는 것은 실제로는 "우리 코드가 Java 기본 요청 기능 대신 다른 요청 라이브러리를 쓴다"(다른 선택)는 뜻입니다.

4코드를 어디에 두나

두 가지 모두 "이미 있는 것을 한 곳에 모아 같이 쓰기"입니다.

4밑줄 주소 읽기는 collection 모듈 안에 둠

[안] 새 도서관 넣기 명령에는 이미 밑줄을 받는 주소 읽기가 있습니다. 이것을 collection 모듈 안에서 가져오기와 같이 쓰게 옮깁니다. availability는 3번 안이면 주소를 읽을 필요가 없습니다.

다른 선택: library 모듈의 공개 기능으로 둠 → 책 상세 주소는 도서관 정보가 아니라 결국 각 모듈이 다시 읽고, library가 주소 도구 모음이 됩니다. 모든 모듈이 같이 쓰는 공용 모듈은 dev 규칙(공용 모듈 금지)에 걸려 뺐습니다.

추천: collection 안.

5책 거르기 규칙을 한 벌로 꺼내 가져오기와 넣기 명령이 같이 씀

[안] 가져오기가 줄을 거르는 판정(지운 표시, 오디오북, 주소, 제목 등)을 따로 꺼내, 넣기 명령이 새 도서관의 "가져올 줄 수"를 셀 때도 같은 판정을 씁니다. 명세에서 승인한 "가져오기와 같은 규칙"이 코드로 보장됩니다.

다른 선택: 넣기 명령이 SQL 한 줄로 셈 → 짧지만 규칙이 두 벌이 되어 나중에 어긋날 수 있고, 주소 비교는 SQL로 하기 어렵습니다.

추천: 한 벌로 꺼냄.

5남은 작은 것

6드문 경우: 넣을 주소와 책 주소의 호스트가 달라 0줄이면 "전자책 0권"으로 나와도 둠

[안] 새 도서관의 최종 주소(리다이렉트를 따라간 주소)와 책 상세 주소의 호스트가 다르면, 가져오기 규칙상 책이 모두 걸러져 0줄이 됩니다. 이때도 "전자책 0권"으로 나옵니다. 이런 곳이 얼마나 있는지는 확인 못 했습니다. 보고서에 나오면 사람이 보고 알 수 있으므로 따로 나누지 않습니다.

다른 선택: "주소 호스트 다름"을 따로 이유로 나눔 → 원인이 바로 보이지만 이유가 하나 더 늘어납니다(backlog 후보).

추천: 그대로 둠.

질문: 이 경우를 먼저 파악할 수 없나요?
