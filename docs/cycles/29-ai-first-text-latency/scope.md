# 사이클 29 (측정·기록): 운영 AI 책 찾기 「첫 글」 지연 원인 규명

- 시작 2026-11-08, 다른 plan 세션이 시작시킴. 사용자가 운영 AI 책 찾기가 문서의 2.3초보다 느리다고 느낌, 특히 첫 질문. 사용자 요청: 원인마다 따로 시험하고 결과를 기록하고 사이클 29로 [확정]
- 직전 사이클 28은 인계만 끝나고 dev 전이라 회고는 dev 뒤에 쓴다 (27 때와 같은 방식) [안]
- 이 사이클은 기능을 만들지 않는다. 결과물은 측정 기록(`measurements.md`)과 고칠 방법 결정. 결정된 고침만 인계서로 dev에 넘긴다

## 목표 (한 문장)

운영에서 AI 책 찾기 새 질문의 첫 글(첫 `head-delta`·`card`·`ask` 이벤트)이 같은 질문 반복보다 늦는 까닭을 가설별로 따로 재서 확인/기각/미확정으로 기록하고, 측정이 뒷받침하는 고침만 [안]으로 낸다.

## 포함

1. 가설 6개를 하나씩 시험 (방법·원 숫자·판정은 `measurements.md`)
   1. DB 차가운 페이지(벡터 int8 줄, `catalog.book_search_bm25`, 책 요약)
   2. 서버가 바깥으로 여는 연결(Haiku·임베딩 서버)이 쉬는 동안 닫힘 (JDK `HttpClient` 기본 30초)
   3. 임베딩 서버(따로 둔 작은 EC2) 느림
   4. Haiku 첫 토큰까지 시간의 흔들림
   5. 사용자 PC → Cloudflare Tunnel → 시드니 네트워크 기본 시간
   6. 짧은 첫 질문(4낱말 이하)은 되묻기 형식이라 첫 글이 늦음
2. 서버 `steps` 로그(사용자 터미널에서 뽑아 붙여 줌)와 바깥 측정을 맞춰 보기
3. 고칠 방법 [안]과 사용자 결정 (결정 페이지)

## 제외

- 측정이 뒷받침하지 않는 고침 설계
- 답 품질, 모델 바꾸기, 비용 상한 변경
- 서버 크기 올리기는 결정 페이지에 선택지로만 (설계 안 함)

## 완료 기준

- `measurements.md`에 가설마다 방법·원 숫자·판정
- 사용자가 결정 페이지에서 고침 [안]을 정함
- 결정된 고침이 있으면 인계서, 없으면 기록만으로 닫음
