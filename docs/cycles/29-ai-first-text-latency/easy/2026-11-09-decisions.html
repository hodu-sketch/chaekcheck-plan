AI 책 찾기 첫 글이 가끔 3~7초 걸리던 까닭과, 고칠 것을 한 장으로 다시 정리했습니다.

어제 페이지 두 장을 대신합니다. 이미 정하신 것은 맨 위에 적고, 남은 6개만 골라 주세요. 원 숫자: measurements.md.

이미 정한 것

[확정] AI 검색은 책 목록을 메모리에 들고 있고, 1분마다 책 표 전체를 세던 일(손님 질문 안에서 1.3초)을 없앱니다. 서버가 켜질 때 한 번 읽고, 가져오기가 끝나면 백엔드의 「다시 읽기」 REST 요청 하나로 새 판을 적용합니다. 다시 읽는 동안은 옛 목록으로 계속 답합니다.

가져오기 끝→「다시 읽기」 요청 1번서버 안에서만, 밖에서 안 닿음→뒤에서 새 목록 읽고 바꿔 끼움손님은 기다리지 않음

왜 가져오기 직후 10초를 기다리나

가져오기는 AI 검색 표의 줄을 모두 지우고 새로 넣습니다. PostgreSQL은 지운 줄의 자리를 바로 돌려주지 않아서 넣은 직후 표가 두 배 가까이 부풀고(운영 2026-10-26: 216MB), 통계를 다시 내는 자동 작업이 몇 분~15분 CPU를 썼습니다. 그래서 dev가 넣기 끝에 VACUUM (FULL, ANALYZE)(표를 통째로 새로 써서 빈자리를 없애고 통계를 냄)를 붙였습니다. 이 작업은 표를 잠가서 그동안(약 10초) AI 검색이 기다립니다(dev docs/maintenance/6-aisearch.md 238·242행, JdbcAiSearchIndex.java 322행, 2026-11-08 확인).

즉 꼭 필요한 기다림은 아닙니다. 빈자리 정리를 잠그지 않는 방법으로 하면 됩니다. 아래 1번.

남은 결정

1가져오기 직후 10초 기다림 없애기

[안] 가져오기를 「새 표에 다 넣고 → 이름을 바꿔 끼우기」로 바꿉니다. 손님은 넣는 동안 옛 표로 검색하고, 바꿔 끼우는 순간(1초 안)만 지나면 새 표를 씁니다. 옛 표는 통째로 지워 빈자리가 남지 않으니 VACUUM FULL이 필요 없습니다. dev 문서에 이미 적힌 개선안입니다(244행).

다른 선택 ㄱ: VACUUM FULL 대신 잠그지 않는 보통 VACUUM (ANALYZE) — 바꿀 코드가 한 줄. 기다림은 없어지지만 빈자리가 디스크에 남아(다음 넣기 때 다시 씀) 표가 커진 채 있고, 메모리가 빠듯한 서버라 읽는 양이 늘 수 있습니다.

다른 선택 ㄴ: 그대로 두기 — 가져오기는 드물게(책 목록이 바뀔 때만) 하므로 10초는 드문 일.

2DB 미리 데우기는 지금 하지 않기

[안] 가져오기 직후·오래 쉰 뒤 첫 질문이 느린 것(가까운 책 찾기 0.4~2.1초)은 이번에 손대지 않고, 1분 세기를 없앤 뒤 다시 재서 정합니다. 서버 남은 메모리 87MB·스왑 633MB라 억지로 올리면 다른 것이 밀려납니다.

다른 선택: pg_prewarm으로 AI 검색 색인만 미리 올리기 / 서버 메모리 늘리기(금액 확인 못 함).

3바깥 연결 유지 설정은 넣지 않기

[안] Haiku·임베딩 서버 연결을 붙잡아 두는 설정은 넣지 않습니다. 60초·5분 쉰 뒤에도 그 단계 시간이 평소와 같았습니다.

4「찾는 중」 신호 먼저 보내기는 백로그로

[안] 실제 시간을 줄이는 일이 아니라 이번에 넣지 않고 백로그에 한 줄로 둡니다.

5고친 뒤 같은 질문 10개로 다시 재고 닫기

[안] 배포 뒤 이번과 같은 질문·같은 쉬는 시간으로 다시 재서 measurements.md에 「고친 뒤」 표를 붙입니다. 목표: 1분 넘긴 요청의 1.3초 멈춤 0, 가져오기 직후 기다림 0(1번을 고치면).

6ADR 하나로 남기기
