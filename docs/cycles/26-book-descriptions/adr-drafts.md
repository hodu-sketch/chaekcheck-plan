# ADR-0161: 책 설명(요약·판 표지·꼬리표·프로필·AI 찾기)은 `catalog`가 맡고, 다른 모듈은 공개 API로만 읽음

Status: Proposed
Date: 2026-10-28
Cycle: 26-book-descriptions
Supersedes: 없음 (ADR-0149의 "꼬리표·사전은 `picks`", ADR-0151의 "찾기용 한 줄은 `aisearch` 표"를 이 결정이 바꿈 → 승인되면 두 ADR의 해당 부분을 이 ADR이 대신한다고 README에 적음)

## 배경
dev 세션이 "책 설명을 한 곳에 모으기"를 plan에 넘김(dev `plan-feedback.md` 2026-10-27). 같은 책의 설명이 `picks`(요약 파일, 꼬리표), `foryou`(요약, 표지), `aisearch`(찾기용 한 줄, 프로필 파일)에 흩어져 화면마다 다른 요약이 보이고, 일반 검색·책 상세에는 요약이 없으며, `aisearch`가 `foryou` 공개 API를 빌려 씀.

## 결정
- 요약(책마다 하나, 책첵 요약 한 종류), 판 표지, 꼬리표와 사전, 책 프로필, AI 찾기용 한 줄과 찾기 색인을 `catalog` 스키마의 종류별 표(`book_summary`, `book_cover`, `book_profile`, `book_search`, `tag_dictionary`, `book_tag`)에 둔다
- 다른 모듈은 목적별 공개 읽기 API(`BookTexts`, `CoverUrls`, `BookProfiles`, `AiSearchIndex`)로만 읽고, 쓰기는 `collection`이 `BookTextsTransfer`로 한다
- 추천목록 요약 파일(`picks/ai-summaries.tsv`)은 없앤다
- 사이클 26을 23·24 dev보다 먼저 만들고, 23·24 dev 세션이 맞춰 고친다

## 이유 (사용자 발언)
- 맡는 모듈 `catalog`: [이유 미확인] (범위 결정 #1 승인)
- "추천목록에 요약을 아예 빼 그리고 일원화해" (2026-10-27)
- "책 프로필도 DB로 / AI 검색이든 뭐든 사용하는데 지장없도록 해" (2026-10-27)
- 표 모양·읽는 API: [이유 미확인] (설계 결정 #1·#2 승인)
- "지금 이거 먼저 하고 DEV23,24에게 알려줘서 알아서 고치라고 해" (2026-10-27)

## 검토한 대안
### A안: `catalog`가 맡음, 종류별 표, 목적별 API (채택)
- 장점: 책 번호를 정하는 다시 가져오기와 같은 모듈이라 버려진 번호의 설명을 같은 작업에서 지움(ADR-0162), 책 상세가 이미 `catalog`를 읽음
- 단점: `catalog`가 커짐, 다시 가져오기의 색인 다시 만들기를 책 목록 표 4개로 거르는 고침이 필요
### B안: 새 모듈 `bookinfo`
- 장점: 책 목록과 설명이 나뉨
- 단점: 버려진 번호를 따로 알려 주는 단계가 생김
- 채택하지 않은 이유: [이유 미확인]
### C안: 표 하나 `book_text(book_id, kind, text)`
- 단점: 프로필(8칸)·꼬리표(여러 줄)가 맞지 않음
- 채택하지 않은 이유: [이유 미확인]
### D안: 지금처럼 흩어 두고 화면에서 고름
- 채택하지 않은 이유: "일원화해" (2026-10-27)

## 결과
- 좋아지는 점: 어느 화면이든 같은 요약, 책 상세에 요약·표지, `aisearch → foryou` 의존이 없어짐
- 감수하는 점: 추천목록 줄 중 책 번호가 없는 책은 요약이 없음. 매달 새 사서추천 책 요약은 PC 배치로 만듦(사람이 고치던 요약 파일 대신)
- 나중에 서비스로 분리할 때: 설명 표 묶음을 "책 설명" 서비스로 함께 가져감

# ADR-0162: 설명은 책 번호로 저장하고, 다시 가져오기 때 버려진 번호의 설명을 같은 작업에서 지우며, 설명 넣기 파일에 가져오기 번호를 검사함

Status: Proposed
Date: 2026-10-28
Cycle: 26-book-descriptions
Supersedes: 없음

## 배경
dev 메모는 "다시 가져오면 책 번호가 새로 매겨진다"고 적었으나, 2026-10-05부터 다시 가져오기는 소장 겹침으로 옛 번호를 이어 줌(dev `Ids.decide`). 합쳐진 책의 큰 번호와 사라진 책 번호는 버려지고 옮겨 주는 표가 없음. `book-texts` 넣기에는 가져오기 번호 검사가 없어 사람이 손으로 확인함.

## 결정
- 설명 표는 `book_id`로 저장하고 `catalog.book`으로의 FK는 두지 않는다(가져오기 때 `book`을 DROP하므로)
- 바꿔 끼우기(`swap`)의 같은 트랜잭션, DROP 앞에서 `catalog_next.book`에 없는 `book_id`의 설명을 지우고 지운 수를 기록한다
- `book-texts`와 새 `book-profiles` 넣기 파일 첫 줄에 `# export_id=<uuid>`를 적고, 마지막 SUCCEEDED 가져오기와 다르면 파일 전체를 거절한다(`neighbours`와 같은 강제 설정)

## 이유 (사용자 발언)
- [이유 미확인] (범위 결정 #2 승인, 2026-10-27)

## 검토한 대안
### A안: 책 번호 + 정리 + 번호 검사 (채택)
### B안: ISBN 기준
- 단점: ISBN 없는 책은 설명을 가질 수 없음, 지금 요약 6.8만 권을 바꿔야 함
- 채택하지 않은 이유: [이유 미확인]
### C안: 작품 키를 만들어 저장
- 단점: 가져오기에 새 단계
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 설명이 엉뚱한 책에 붙지 않음, 넣기 실수를 명령이 막음
- 감수하는 점: 새 번호(새 책·갈라진 책)는 다음 넣기 때까지 설명 없음

# ADR-0163: 모든 표지 그림은 S3(시드니) + CloudFront 기본 주소에 두고, PC만 올림

Status: Proposed
Date: 2026-10-28
Cycle: 26-book-descriptions
Supersedes: 없음 (ADR-0091의 "사서추천 표지를 `picks.cover`에 저장", ADR-0148의 운영 서버 `/srv/chaekcheck/covers/` 표지 자리를 이 결정이 바꿈)

## 배경
책 상세에 표지를 보이려면 책 134만 권의 표지(장당 약 9~11KB, 합 약 12~15GB [추론])가 필요한데 운영 디스크 여유는 약 11GB. 계정은 AWS 무료 플랜(크레딧). 사서추천 표지만 DB 안 그림(bytea)으로 저장되어 있음.

## 결정
- 판 표지와 추천목록 그림을 비공개 S3 버킷(`covers/<sha1>.jpg`)에 두고, CloudFront 기본 도메인(`<id>.cloudfront.net`)으로 OAC를 거쳐 보낸다. CSP `img-src`에 그 주소를 더한다. DB에는 그림 이름(sha1)만 두고 주소는 설정으로 만든다
- PC만 S3에 올린다(그 버킷 올리기만 되는 IAM 사용자 키). 운영 서버에는 S3 권한을 주지 않는다. "그림 먼저, 연결 나중"
- `picks.cover`의 그림은 파일로 꺼내 함께 올리고 표는 지운다

## 이유 (사용자 발언)
- "디스크는 뭐 따로 S3이라던가 프리티어에서 할 수 있는 거 생각해보자 아니면 라이트세일로옮긴다던가" (2026-10-28)
- "무료 크레딧에서 되는 것들인지 확인하고 그것들만 알려줘" (2026-10-28)
- "S3 + CloudFront 이걸로 하자" (2026-10-28)
- "나는 DB에 이미지를 넣는게 이해가 안 가거든" (2026-10-28)
- 기본 도메인·PC만 올림: [이유 미확인] (설계 결정 #3·#4 승인)

## 검토한 대안
### A안: S3 + CloudFront (채택)
- 근거: S3는 무료 플랜 두 플랜 모두 사용, CloudFront 늘 무료 1TB/월(https://aws.amazon.com/free/, https://aws.amazon.com/free/networking/, 2026-10-28). 시드니 S3 $0.025/GB-월, PUT $0.0055/1,000건(AWS 가격 데이터, 2026-10-28). 저장 월 약 $0.38, 첫 올리기 약 $7.4 [추론]
### B안: 운영 디스크(EBS) 30 → 50GB
- 단점: 무료 플랜에서 30GB 넘게 늘릴 수 있는지 문서에 없음, 월 약 $1.92
- 채택하지 않은 이유: [이유 미확인] (사용자가 S3를 고름)
### C안: 라이트세일로 이사 ($12/월, SSD 60GB)
- 채택하지 않은 이유: [이유 미확인]
### D안: Cloudflare R2
- 채택하지 않은 이유: [이유 미확인]
### E안: WebP로 줄여 지금 디스크에
- 채택하지 않은 이유: [이유 미확인]
### 주소: 그림 전용 하위 도메인 / nginx가 S3로 넘김
- 채택하지 않은 이유: [이유 미확인]
### 올리기: PC + 운영 서버(EC2 역할)
- 채택하지 않은 이유: [이유 미확인] (운영 사서추천 받기가 꺼져 있음, `deploy/prod/compose.yaml:67`)

## 결과
- 좋아지는 점: 운영 디스크를 쓰지 않음, DB 안 그림이 없어짐
- 감수하는 점: S3·CloudFront·IAM 키 관리, CSP 변경. 무료 플랜이 끝나기 전(약 2027-04) 유료 플랜으로 올려야 함(방법과 무관)

# ADR-0164: 데이터는 "무엇에 대한 사실인가"의 주인에게 한 번만 두고, 추천목록 줄 표지는 우리 책의 판 표지를 먼저 씀

Status: Proposed
Date: 2026-10-28
Cycle: 26-book-descriptions
Supersedes: 없음

## 배경
추천목록 줄은 여러 판을 대표하는 "추천된 책"이고 그 판 하나(소장 많은 판, ADR-0125)로 연결됨. 줄마다 따로 찾은 표지가 있고, 우리 책 목록에 없는 책도 있음. 판 표지는 `catalog`에 있음.

## 결정
- 원칙: 데이터는 "무엇에 대한 사실인가"를 묻고 그 주인 모듈에 한 번만 둔다. 다른 곳은 번호로 가리킨다(예외는 ADR-0160)
- 추천목록 줄 표지: ① 줄이 연결한 판의 `catalog` 표지 ② 없으면 같은 책 다른 판 중 최신 판 → 소장 많은 판의 `catalog` 표지 ③ 없거나 우리 책 목록에 없는 책이면 추천목록이 찾은 그림. 추천목록 그림은 `catalog`에 넣지 않는다
- 판 표지는 수집이 받은 모든 책 표지로 채운다(ADR-0163)

## 이유 (사용자 발언)
- "어떻게 해야 결과적으로 데이터를 잘 나눈걸까" (2026-10-27)
- "지금 추천목록은 여러 판을 하나로 관리한다는것에서 좀다르지 않나?" (2026-10-27)
- "만약에 카탈로그에 있는 거면 그거 가져다가 쓰고 없는 거만 따로 처리 안되나" (2026-10-28)
- "추천도서(여러 판 가능) -> 카탈로그에 있음 -> 카탈로그에 있는 것 중 최신(우선순위 더높음)이거나 보유량 많은거(우선순위 더 낮음) 책 표지를 지정하도록 함" (2026-10-28)
- "그건 카탈로그에 표지도 있도록 수집해야 하는 거 아니야? 지금 수집 중이고 반영할 것이지 않나?" (2026-10-28)
- 줄이 연결한 판 먼저: [이유 미확인] (명세 결정 #11 승인)

## 검토한 대안
### A안: 위 차례 (채택)
### B안: 추천목록 표지는 모두 추천목록에 (명세 #8)
- 채택하지 않은 이유: 사용자 제안("카탈로그에 있는 거면 그거 가져다가 쓰고")으로 바뀜
### C안: 추천목록 그림을 `catalog`에 넣고 출처·같은 판 여부 표기 (명세 #9·#10)
- 채택하지 않은 이유: "이거 따로 표기해야 할 것 같은데 판이 다른 도서의 표지가 들어가거나.." (2026-10-27) 뒤 사용자 구조로 바뀜
### D안: 최신 판 표지 먼저
- 채택하지 않은 이유: [이유 미확인] (누르면 다른 판이 열릴 수 있음)

## 결과
- 좋아지는 점: 우리 책이면 어디서나 같은 판 표지, 다른 판 그림이 `catalog`에 섞이지 않음
- 감수하는 점: 추천목록에서 보던 그림이 `catalog` 표지로 바뀔 수 있음

# ADR-0165: AI 검색 사본 표(`aisearch.search_book`)를 없애고 `catalog`에서 찾으며, 책 프로필은 DB에 두고 서버 시작 때 한 번 읽음

Status: Proposed
Date: 2026-10-28
Cycle: 26-book-descriptions
Supersedes: ADR-0151의 "`aisearch` 표의 사본에서 DB 낱말 맞추기" 부분

## 배경
AI 검색은 `catalog`의 제목·저자·소장 도서관을 복사한 사본 표(76,759권)에서 찾고, 프로필은 모델 폴더 파일(77,551권)에서 시작 때 읽음. 사용자는 중복 저장을 원하지 않음.

## 결정
- `aisearch.search_book`을 없앤다. 찾기용 한 줄·찾기 글 색인(pg_bigm)·찾기 전용 `library_ids`(ADR-0160)는 `catalog.book_search`에 두고, 제목·저자는 `catalog.book`에서 읽는다. AI 검색 대상은 `book_search` 행이고 `collection`이 지금처럼 고른다(추천목록 책 + 보유 많은 책 상위 N − 뺄 책)
- 표지·요약은 AI 호출과 겹쳐 읽는 지금 방식을 유지한다
- 책 프로필은 `catalog.book_profile`(형식 있는 칸)에 두고, 새 넣기 모드 `book-profiles`(`# export_id=`)로 전체를 바꾼다. AI 검색은 서버 시작 때 한 번 메모리에 읽는다(책 벡터와 같은 때)

## 이유 (사용자 발언)
- "지금 더 군데 중복저장되는거는 없었으면해" (2026-10-27)
- "책 프로필도 DB로 / AI 검색이든 뭐든 사용하는데 지장없도록 해" (2026-10-27)
- 대상 위치·프로필 칸·시작 때 읽기: [이유 미확인] (설계 결정 #5·#7 승인)
- dev 24 제약(2026-10-27): 표지·요약 겹쳐 읽기 유지, 프로필은 요청마다 DB를 읽지 않음

## 검토한 대안
### A안: 사본 없앰, 프로필 DB (채택)
### B안: 찾기용 한 줄만 옮기고 사본은 둠
- 채택하지 않은 이유: "지금 더 군데 중복저장되는거는 없었으면해" (2026-10-27)
### C안: 찾기용 한 줄·프로필을 지금 자리에 둠
- 채택하지 않은 이유: 위와 같음
### D안: 프로필 jsonb 한 칸
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 다른 모듈로의 복사가 없어짐, 프로필을 다른 기능도 쓸 수 있음
- 감수하는 점: AI 검색 찾기 글의 제목이 추천목록에 보이는 이름에서 `catalog.book.title`로 바뀜(옮긴 뒤 결과·첫 글 시간 비교), 새 프로필을 넣으면 서버를 다시 켬
