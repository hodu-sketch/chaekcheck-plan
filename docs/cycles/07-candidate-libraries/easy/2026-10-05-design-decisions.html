정해 주세요.

architect가 dev 코드를 읽고 낸 설계안을 쉬운 말로 옮겼습니다. 항목 1~16은 만드는 방법, 17~20은 코드를 읽다 새로 나온 질문입니다. 숫자 중 "추정"은 아직 재지 않은 값이고, dev가 시험 실행으로 잽니다.

1무엇이 어디서 바뀌나

서버 모듈 셋(도서관, 책 목록, 대출 조회)만 바뀝니다. 로그인·내 도서관 저장·지역 모듈과 조회 서버는 그대로입니다. 새 주소(API)는 없습니다.

화살표는 "부른다"는 뜻입니다. 책 목록과 대출 조회가 도서관 모듈의 공개된 기능만 부르고, 서로의 표를 직접 읽지 않습니다(지금 규칙 그대로).

2후보 도서관을 서비스에 넣는 방법

번호는 예시입니다. 등록 도서관은 같은 번호끼리, 후보 도서관은 281번부터 새 번호로 짝을 짓습니다(이미 정한 것).

1짝 표는 "도서관" 모듈이 가집니다 [안]

도서관 번호를 정하는 모듈이 짝도 가집니다. 책 목록 모듈은 가져올 때 도서관 모듈에 "수집 번호 100245는 서비스 몇 번?"을 묻기만 합니다.

다른 선택 책 목록 모듈이 가짐. 가져오기 코드와 가깝지만, 남의 번호를 관리하게 됩니다.

답: "짝 표를 맡는 모듈을 따로 새로 만들면?"

지금은 도서관 모듈에 두고, 갱신 기능 사이클에서 "수집 연결" 모듈로 떼어 내는 것을 추천합니다.

도서관 모듈에 둠 (처음 제안)새 모듈(예: collection)
맡는 일짝 표 하나짝 표 + 앞으로 가져오기 기록·갱신 순서·수집 DB 읽기
좋은 점바뀌는 곳이 가장 적음. 도서관 번호를 정하는 모듈이 짝도 가짐"수집 두 갈래 + 가져오기"와 서비스(검색) 쪽이 코드에서도 갈라짐. 갱신 기능을 만들 자리가 생김
감수할 점나중에 갱신 기능이 커지면 도서관 모듈이 수집 일까지 떠안음지금 가져오기 코드는 책 목록 모듈 안에서 책 표에 바로 씁니다. 새 모듈로 옮기면 책 목록 모듈이 "대량 쓰기" 공개 기능을 새로 내줘야 하고, 모듈 사이 경계·시험이 늘어납니다. 이번 사이클이 커집니다

짝 표 하나만 새 모듈에 두는 것은 득이 적습니다(작은 모듈이 하나 늘 뿐). 새 모듈의 값어치는 가져오기·갱신을 함께 옮길 때 생기므로, 그 일을 다루는 갱신 기능 사이클에서 정하는 것이 맞다고 봅니다. 승인하시면 처음 제안대로, 새 모듈을 원하시면 기타에 적어 주세요.

2후보 도서관 줄과 짝은 사본에서 미리 만든 파일(seed)로 넣습니다.
지금 등록 도서관을 넣는 방식과 같습니다 [안]

dev 스크립트가 사본을 읽어 도서관 목록 파일(CSV)을 만들고, 서버가 처음 뜰 때 DB에 넣습니다. 로컬·시험·운영 어디서나 번호가 같아, 브라우저와 계정에 저장된 도서관 번호가 늘 같은 도서관을 가리킵니다. 나중에 조사된 후보 공공도서관의 가입 규칙도 번호를 미리 알고 넣을 수 있습니다.

명세 R8 "가져올 때 짝 표로 서비스에 이어진다"가 "가져오기 전에 파일로 이어진다"로 바뀝니다. 다음에 새 도서관을 넣을 때는 가져오기 전에 이 파일을 하나 더 만듭니다.

다른 선택 ① 가져올 때 책 목록 모듈이 도서관을 등록: 한 번에 끝나지만 번호가 실행 순서에 따라 달라지고, 가입 규칙 파일이 번호를 모릅니다. ② 도서관 모듈에 따로 가져오기 명령: ①과 같은 단점에 더해 도서관 모듈이 수집 DB(SQLite)를 알아야 합니다.

3파일을 만드는 규칙: 전체 수집이 끝난 후보(약 2,412곳)만, 새 번호는 281부터,
이름이 겹치면 "(북큐브)"·"(교보)"·"(YES24)"·"(알라딘)", 그래도 겹치면 주소를 붙임 [안]

같은 사이트로 표시된 99곳은 들어가지 않습니다(사본에서 99곳 모두 표시된 것을 확인, 2026-10-05). 등록 도서관 이름은 바꾸지 않습니다. 이름은 처음 넣을 때 한 번 정하고 다음 파일에서 바꾸지 않습니다. 교보 구독형 화면도 라벨은 "교보"입니다. 첫 화면 주소는 사이트 주소로, 가입 방법 글은 비워 둡니다.

다른 선택 교보 구독형은 "(교보 구독)"으로 따로. 구분은 더 되지만 소장형 기관도 "구독"으로 보이게 됩니다(질문 19번과 이어짐).

3"가입 정보 미조사" 칸

코드를 읽어 보니 지금도 가입 규칙이 0개인 등록 도서관이 "전체 도서관" 검색에 들어갑니다. 그래서 "규칙이 없으면 직접 넣었을 때만"으로 만들면 등록 도서관 검색이 바뀝니다. 따로 표시하는 칸이 필요합니다.

4도서관 표에 "가입 정보를 조사했나"(join_surveyed) 칸을 둡니다.
아니요이고 직접 넣지 않았으면 검색에서 뺍니다 [안]

등록 도서관 278곳은 모두 "예"라서 지금과 한 글자도 같습니다. 후보 도서관은 "아니요". 같은 칸으로 결과 카드의 "가입 정보를 아직 조사하지 않았어요" 안내도 정합니다. 수집 세션이 후보 공공도서관 조사를 끝내면 그 도서관을 "예"로 바꾸고 가입 규칙 줄만 더하면 됩니다(코드 변경 없음).

다른 선택 "등록/후보" 구분 칸 + "후보이고 규칙 0개면 직접 넣었을 때만". 규칙만 넣으면 보이지만, "등록/후보 구분은 사라지고 가입 조건 유무로"(2026-10-04)와 어긋나고, 학교·회사처럼 규칙이 계속 없을 곳과 아직 조사 안 한 곳을 가르지 못합니다.

5가져오기는 짝 표로 도서관을 찾고, 사이트 주소가 다르면
그 도서관 줄을 세어 알려 줍니다 [안]

지금은 "번호와 주소가 둘 다 같은 도서관"만 가져옵니다. 짝 표로 찾되 주소 확인은 안전장치로 남깁니다. 짝이 없는 곳(받는 중·아직·실패·같은 사이트)은 자동으로 빠집니다.

다른 선택 주소 확인을 뺌. 단순하지만 잘못 짝지어진 것을 알아채지 못합니다.

6북큐브 8자리 날짜는 읽고, 1950년 이전 날짜는 설정에 적은 도서관(명지대학교)만
"없음"으로 [안]

이미 정하신 것(북큐브 날짜 읽기, 명지대 자리 채움 값 없애기)을 만드는 방법입니다. 모든 도서관의 1950년 이전 날짜를 지우면 등록 도서관 10줄이 바뀌므로, 설정에 적은 도서관만 고칩니다.

다른 선택 모든 도서관의 1950년 이전 날짜를 지움. 설정이 없어 단순하지만 등록 도서관 결과가 조금 바뀝니다.

7가져온 뒤 DB 정리(VACUUM ANALYZE)를 한 번 합니다 [안]

정리를 해야 책마다 소장 도서관을 펼칠 때 표 본체를 읽지 않고 색인만 읽습니다(빨라짐). 쓰기 약 10~12분 + 정리 수 분(추정). 배포 전이라 기다림은 괜찮다고 정하셨습니다.

다른 선택 지금처럼 통계만 갱신(ANALYZE). 빠르게 끝나지만 검색이 느릴 수 있습니다.

8가져오기가 메모리를 많이 쓰면(약 11~15GB 추정),
메모리가 큰 PC에서 운영 DB로 가져옵니다 [안]

지금 가져오기는 모든 줄을 메모리에 올립니다. 줄이 약 4.3배라 메모리도 그만큼 듭니다. dev가 시험 실행에서 재고, 모자라면 코드를 고치지 않고 큰 PC에서 돌립니다.

다른 선택 두 번에 나눠 읽게 코드를 고침(메모리 적게). 어디서나 돌지만 일이 늘어납니다.

5DB와 책 검색 속도 (목표: 첫 쪽 1초 안)

9책 목록 표의 모양은 그대로 둡니다 [안]

서비스 DB의 소장 줄에는 표지 주소가 없어, 조사에서 본 "70%가 주소"는 수집 DB 이야기였습니다. 상세 주소 통째로·원문 보존은 이미 정하셨습니다. 예상 크기 약 9~10GB(추정). 쓰이지 않는 색인 하나(약 0.9GB)를 빼는 것은 backlog에 둡니다.

다른 선택 이번에 쓰이지 않는 색인을 뺌. DB가 약 1GB 작아지지만 중복 검사가 사라집니다.

10먼저 지금 방식 그대로 재 보고(정해 둔 검색어 묶음), 하나라도 1초를 넘으면
같은 사이클에서 "책마다 가진 도서관 번호 목록"을 미리 계산해 둡니다 [안]

책이 많아지면 검색이 느려지는 이유: 후보 도서관에만 있는 책도 일단 찾은 뒤 버리고, 책마다 펼칠 소장이 약 4배가 됩니다. "사랑" 224ms가 수백 ms~1초대가 될 것으로 추정합니다. 미리 계산해 두면 책 검색이 소장 표를 읽지 않아도 되어 거의 늘지 않습니다(약 0.2GB 더 씀, 추정).

다른 선택 처음부터 미리 계산. 확실히 빠르지만 같은 사실을 두 곳에 두게 됩니다.

목록 통째로 + 압축 (추천)서버에서 이름으로 찾기
받는 양화면을 열 때 한 번 약 40KB(압축, 추정. 지금 278곳은 약 4KB)칠 때마다 약 2KB
바꿀 것웹 서버 압축 켜기, 화면 정렬·2글자·20곳씩새 주소 2개(이름 찾기, 번호로 이름 조회), 색인

11도서관 목록을 통째로 받고 웹 서버에서 압축합니다.
dev가 실제 크기를 재서 확정합니다 [안]

압축하면 사진 한 장보다 작습니다. 직접 넣은 도서관 목록과 옮기기 창의 이름도 같은 목록으로 보입니다. 사이클 06 결정 기록(ADR-0049)의 "수천 곳이면 서버 찾기로"를 측정으로 정리하는 것입니다.

다른 선택 서버에서 이름으로 찾기. 받는 양이 가장 적지만 새 주소 둘과 화면 변경이 늘어납니다.

답: "어느 쪽이 서버 부담이 적나?"

목록 통째로가 서버 부담이 더 적습니다. 화면을 열 때 한 번만 요청하고, 그 뒤 글자를 칠 때는 브라우저 안에서 거르므로 서버에 요청이 가지 않습니다.

목록 통째로 + 압축서버에서 이름으로 찾기
요청 수내 도서관 화면을 열 때 1번글자를 칠 때마다(잠깐 멈출 때마다) 1번, 한 사람이 도서관 하나 찾는 데 보통 3~5번(추정)
한 번에 서버가 하는 일도서관 약 2,700곳 목록을 만들어 압축(약 40KB, 추정). 도서관 목록은 배포 때만 바뀌어 미리 만들어 둘 수 있음(캐시)DB에서 이름 찾기 + 20곳 만들기(약 2KB)
합친 부담낮음 (요청이 적고, 캐시하면 DB를 거의 안 읽음)요청이 많아 DB 조회가 늘어남

주고받는 양은 서버 찾기가 적지만, 서버 부담은 요청 수와 DB 조회 수가 더 크게 좌우합니다. 목록 응답은 지역에 따라 가입 표시가 달라지는데, 도서관 목록 자체는 미리 만들어 두고 가입 표시만 붙이면 됩니다(설계에서 정함).

7북큐브·알라딘 대출 상태 읽기

12책마다 이미 가진 상세 주소로 읽습니다(북큐브는 같은 사이트의 작은 XML,
알라딘은 상세 화면). "도서관에서 직접 찾기"용 검색도 만듭니다 [안]

교보 일반·YES24와 같은 방식입니다. 카드 링크는 사람이 보는 상세 화면 그대로입니다. 직접 넣은 후보 도서관은 "도서관에서 직접 찾기"에도 들어가므로 그쪽 검색도 만듭니다. 쪽 넘기기를 확인하기 전에는 첫 쪽만 읽습니다. 알라딘 출판사 검색은 확인 전까지 그 도서관만 "실패"로 보입니다.

다른 선택 직접 찾기는 이번에 빼고 바로 보기만. 일이 줄지만 직접 찾기에서 이 도서관들이 실패로 보입니다.

13북큐브 대여형은 응답을 볼 때마다 판정합니다:
보유 0이고 "이용자 수" 칸이 있으면 "구독형 · 바로 대출" [안]

한 사이트 안에 소장형과 대여형 책이 섞여 있어도 맞게 보입니다. 도서관마다 따로 조사할 값이 없습니다.

다른 선택 도서관마다 "대여형" 표시를 두고 요청 없이 판정. 요청이 줄지만 섞인 사이트에서 틀리고 값을 조사해야 합니다.

8로그인 전 직접 추가와 옮기기, 안내

14로그인 직후 옮길 때는 지금 있는 "도서관 하나 추가" 요청을
브라우저 순서대로 하나씩 보냅니다 [안]

20곳이 차서 막히면 멈추고 "20곳까지만 저장했어요", 꺼진 도서관은 건너뜁니다. 새 주소가 필요 없습니다. 로그인 전 직접 추가는 브라우저에 저장하고 검색 때 번호를 넘깁니다(서버 변경 없음).

다른 선택 한 번에 옮기는 새 요청. 중간에 끊기지 않지만 새 주소와 오류 규칙이 늘어납니다.

답: "이미 계정에 설정이 있으면 옮기지 않는 거 아니야? 새 계정이면 20개를 안 넘잖아"

맞습니다. 그래서 "20곳까지만 저장했어요" 처리는 실제로는 일어나지 않습니다. 옮기기 창은 계정에 직접 넣은 도서관이 하나도 없을 때만 뜨고, 브라우저에는 20곳까지만 넣을 수 있으므로 20곳을 넘을 수 없습니다.

이 항목이 정하려던 것은 "옮기는 요청을 어떻게 보내나"입니다: 지금 있는 "도서관 하나 추가" 요청을 브라우저 순서대로 최대 20번 보냄(추천) / 한 번에 옮기는 새 요청을 만듦. 승인하시면 추천대로 하고, 화면 흐름 11번에서 정한 "20곳까지만 저장했어요" 문구는 일어나지 않는 경우라 dev가 안전장치로만 둡니다(화면에 보일 일 없음).

덧붙임: 계정에 지역은 있고 직접 넣은 도서관만 없을 때는, 창에 도서관 줄만 보이고 도서관만 옮깁니다(화면 흐름 10번, 계정에 이미 있는 쪽은 옮기지 않음).

15결과 카드의 "가입 정보를 아직 조사하지 않았어요"는
서버가 보내는 "조사했나" 값 하나로 정합니다 [안]

지금 화면이 쓰는 가입 등급 값은 건드리지 않고 칸 하나만 더합니다. 기존 화면 코드가 덜 바뀝니다.

다른 선택 가입 등급에 "미조사" 값을 새로 더함. 한 칸으로 끝나지만 등급을 쓰는 화면 코드를 모두 고쳐야 합니다.

16DB 구조 변경은 새 파일로만 더합니다(지금 파일은 고치지 않음) [안]

배포 전이라 지금 파일을 고칠 수도 있지만, 사이클 06처럼 새 파일만 더하면 개발 DB를 지우고 다시 만들 필요가 없습니다.

다른 선택 지금 파일을 고침. 파일 수가 적지만 모든 개발 DB를 다시 만들어야 합니다.

9코드를 읽다 새로 나온 질문 넷

17"등록 도서관 결과가 전과 같다"(AC-6)를 "등록 도서관이 가진 책과
그 순서가 같다"로 바꿉니다. 책 대표 제목·묶음은 조금 바뀔 수 있음을 받아들입니다 [안]

책의 대표 제목·저자·출판일은 "그 책을 가진 모든 도서관에서 가장 많이 나온 값"입니다. 후보 도서관 책이 들어오면 등록 도서관 책의 대표값과 같은 책 묶음이 바뀔 수 있습니다. 그래서 완전히 같음은 약속할 수 없습니다.

다른 선택 대표값·묶음을 등록 도서관 소장만으로 계산. 등록 도서관 결과가 그대로지만 후보 도서관을 넣은 사람에게 같은 책이 둘로 갈라져 보일 수 있습니다.

18북큐브 소리·영상 파일(book/wma·vod·wmv)과 교보 "동영상"(약 5,700줄)은
가져오기에서 뺍니다 [안]

명세는 "자료 종류를 모르면 빠진다"고 적었는데, 실제로는 2026-09-30 결정으로 "모름"도 들어옵니다. 이 줄들은 전자책이 아니라 소리·영상이라 빼자는 제안입니다. "모름" 전체를 빼자는 것은 아닙니다.

다른 선택 그대로 둠("모름" 책으로 들어옴).

답: "지금 어떻게 가져오고 있나? 이미 수집된 것들은 어떻게 돼 있지?"

수집은 수집 DB(SQLite)에 모든 도서관 책을 쌓고, 가져오기가 그중 등록 도서관 책만 골라 서비스 DB에 넣습니다.

단계지금
수집 DB등록·후보 모든 도서관의 책 줄이 다 있음(배포용 사본 2,205만 줄). 오디오북·영상 표시 칸(content_type)도 있음
가져오기 (dev, 2026-10-03 한 번)수집 DB를 읽기만 함 → 등록 도서관 줄만 고름(후보 줄 약 410만은 "서비스에 없는 도서관"으로 건너뜀) → 오디오북·동영상북 줄은 뺌, "모름"(UNKNOWN)은 넣음(2026-09-30 결정) → 정리·같은 책 묶기 → 서비스 DB 책 표를 비우고 통째로 채움. 결과: 책 680,689권, 소장 4,954,360줄
이번 사이클 뒤같은 사본으로 다시 가져오면 후보 도서관 줄도 들어옴

18번이 묻는 것: 북큐브 사이트는 소리 파일(book/wma)·영상(book/vod·wmv)을 "오디오북·동영상북"이 아니라 파일 형식으로 적어서, 수집 DB에서 "모름"으로 분류됐습니다. 그래서 지금 규칙대로면 이 줄들이 책으로 들어옵니다(교보 "동영상" 포함 약 5,700줄). 이것만 오디오북·동영상북처럼 빼자는 제안입니다.

19교보 "소장형" 기관이 "구독형 · 바로 대출"로 잘못 보이는 문제는
이번에 고칩니다 [안]

교보 구독형 화면을 쓰는 기관 중 소장형이 후보 1,182곳(등록 5곳)입니다. 지금 코드는 이 화면을 모두 요청 없이 "바로 대출"로 보여, 직접 넣은 소장형 도서관도 틀리게 보입니다. 고치려면 도서관마다 소장형/구독형 표시가 필요하고, 수집 세션의 확인 결과(첫 화면의 소장·혼합·대여 구분)로 채울 수 있습니다(crawl-runbook.md 8-2절). 숫자를 읽는 방법은 dev가 사이트를 시험해 정합니다.

다른 선택 backlog로. 이번 일은 줄지만 직접 넣은 소장형 도서관이 늘 "바로 대출"로 보입니다.

후보 도서관 가입 자격 조사는 이번 범위에서 빼셨습니다. dev 규칙(dev CLAUDE.md)과 부딪치므로 "가입 정보 미조사 표시로 넣어도 됨"을 인계서에 적습니다. plan은 dev 파일을 고치지 않습니다.

답: "가입 조사한 거 곧 넣을 거야, 기다려"
