1ADR-0052: 후보 도서관은 서비스 새 번호로 넣고, 수집 DB 번호와의 짝은 새 모듈 `collection`이 가진다

후보 도서관은 서비스에서 새 번호(지금 최대 다음부터)를 받고, 수집 번호 ↔ 서비스 번호 짝 표 collection.collection_link를 새 모듈 collection이 가진다. 등록 도서관은 같은 번호끼리 짝을 짓는다. 후보 도서관 줄과 짝 줄은 사본에서 만든 Liquibase seed(CSV, 번호 명시)로 넣고, catalog 가져오기는 collection 공개 API로 짝을 받는다.

구체적으로 이렇게 됩니다

예: 수집 DB의 "강동대학교 북큐브 사이트"(수집 번호 100245)가 서비스에 들어오면 서비스 번호 281번을 받습니다. 새 표 collection_link에 "100245 → 281" 한 줄이 생깁니다. 등록 도서관은 "45 → 45"처럼 같은 번호끼리 들어갑니다.

누가 언제 만드나: 배포 전에 dev 스크립트가 사본을 읽어 도서관 약 2,400줄과 짝 줄을 담은 파일(CSV)을 만들고, 서버가 처음 뜰 때 DB에 넣습니다. 그래서 개발 PC·운영 서버 어디서든 281번은 늘 같은 도서관입니다.

새 모듈 collection: 지금은 짝 표 하나만 가지고, "수집 번호 100245는 서비스 몇 번?"에 답하는 기능 하나를 내줍니다. 가져오기(책 목록 모듈)가 이것을 씁니다. 나중에 갱신 기능을 만들 때 수집 연결 일이 이 모듈로 모입니다.

배경

사이클 07에서 수집 DB에만 있던 후보 도서관(웹러브 북스 기관, 수집 번호 100001~)을 서비스 도서관 표에 넣는다. 지금 가져오기는 서비스 번호와 수집 번호가 같은 도서관(등록 도서관 1~280)만 옮긴다. 후보 도서관에 어떤 번호를 줄지, 두 번호를 누가 어떻게 이을지, 도서관 줄을 언제 만들지 정해야 했다. 번호는 브라우저와 계정(mylibrary.account_library)에 저장되므로 모든 환경에서 같고 다시 가져와도 바뀌지 않아야 한다.

이유 (사용자 발언)

  • 새 번호와 짝 표: "서비스에서 새 번호를 주고 짝 맞추는 표를 둠" (2026-10-05)
  • 새 모듈: "따로 모듈로 가고 나중에 수집 연결 모듈이 고치라고 해" (2026-10-05)
  • seed로 넣음: [이유 미확인] (제안 → 승인)

검토한 대안 — "(채택)"이 위에서 말한 할 일이고, 나머지는 하지 않습니다

A안: 새 번호 + collection 모듈의 짝 표 + seed (채택)

  • 장점: 번호가 모든 환경에서 같음, 다시 가져와도 그대로, 가입 규칙 seed가 번호를 미리 앎, 앞으로 가져오기·갱신 같은 수집 연결 일을 맡을 자리가 생김
  • 단점: 모듈 하나가 늘고, 새 도서관마다 가져오기 전에 seed 파일을 하나 더 만듦

B안: 수집 번호(100001~)를 서비스 번호로 그대로

  • 장점: 짝 표가 필요 없음
  • 단점: 서비스 번호가 수집 DB에 묶임
  • 채택하지 않은 이유: 사용자가 "서비스에서 새 번호를 주고 짝 맞추는 표를 둠"을 고름 [이유 미확인]

C안: 짝 표를 library 모듈이 가짐

  • 장점: 모듈이 늘지 않음
  • 단점: 나중에 수집 연결 일이 커지면 도서관 모듈이 떠안음
  • 채택하지 않은 이유: "따로 모듈로 가고 나중에 수집 연결 모듈이 고치라고 해"

D안: 가져오기 때 catalog가 library에 도서관을 등록

  • 장점: 한 번 실행으로 끝남
  • 단점: 번호가 실행 순서에 따라 달라지고, 가입 규칙 seed가 번호를 모름
  • 채택하지 않은 이유: [이유 미확인]

결과

  • 좋아지는 점: 번호가 고정되어 내 도서관 저장이 안전함. 수집 연결 일이 한 모듈에 모임
  • 감수하는 점: 모듈 경계가 하나 늘고, seed를 만드는 절차가 수집 ① 도서관 수집 갈래의 "넣기" 단계에 더해짐
  • 나중에 분리할 때: collection이 "수집 연결" 서비스가 되고, 짝 조회는 그 서비스의 API가 됨

2ADR-0053: 가입 정보를 조사하지 않은 도서관은 직접 추가했을 때만 검색에 넣는다

도서관 표에 "가입 정보를 조사했나" 칸(library.join_surveyed, 기본 true)을 두고, false이면서 이용자가 직접 추가하지 않은 도서관은 검색 계획에서 뺀다. API는 이런 도서관을 가입 등급 eligibility: UNSURVEYED로 내보내고, 화면은 "가입 정보를 아직 조사하지 않았어요" 안내를 보인다. 조사된 후보 공공도서관은 true와 가입 규칙으로 넣는다(규칙을 못 찾은 곳은 ADR-0013의 자격 미확인). ADR-0013·ADR-0050을 보완한다.

구체적으로 이렇게 됩니다

예: 로그인한 사람이 "사랑"을 검색하면, 내 도서관에 넣지 않은 "○○초등학교 전자도서관"(후보, 가입 정보 미조사)은 검색 대상에서 빠지고 그 사이트로 요청도 가지 않습니다. 같은 사람이 그 도서관을 내 도서관에 넣으면 다음 검색부터 결과 맨 앞에 나옵니다.

무엇을 두나: 도서관 표에 칸 하나 "가입 정보를 조사했나"(예/아니요). 등록 도서관 278곳과 조사가 끝난 후보 공공도서관은 "예", 나머지 후보는 "아니요". 화면에는 가입 등급 "미조사"로 전해져, 이름을 누르면 "가입 정보를 아직 조사하지 않았어요" 안내가 나옵니다.

등록 도서관은? 모두 "예"라서 지금 검색과 한 글자도 같습니다.

배경

후보 도서관 대부분(학교·대학·회사·기관 약 2,500곳)은 가입 조건을 조사하지 않았다. 사용자는 이런 도서관을 내 도서관에 넣지 않으면 보이지 않고 요청도 가지 않게 정했다(2026-10-04). 그런데 지금 코드는 가입 규칙이 0개인 등록 도서관도 "자격 미확인"으로 전체 검색에 넣는다(ADR-0013). 그래서 "규칙이 없으면 숨김"으로는 등록 도서관 동작이 바뀐다.

이유 (사용자 발언)

  • "'나'로 하도록 하고 직장/거주 없는 도서관들은 따로 '내 도서관'에서 등록하지 않은 한 기본적으로 안 보였으면 해 요청도 보내지 말고" (2026-10-04)
  • 등급 값으로 내보냄: "가입 등급에 '미조사' 값을 새로 더함 … 이걸로 해줘" (2026-10-05)
  • 칸을 따로 둠: [이유 미확인] (제안 → 승인)

검토한 대안 — "(채택)"이 위에서 말한 할 일이고, 나머지는 하지 않습니다

A안: join_surveyed 칸 + 등급 UNSURVEYED (채택)

  • 장점: 등록 도서관 278곳 동작이 그대로, 조사가 끝나면 데이터만 고침
  • 단점: 등급을 쓰는 웹 분기를 모두 고침

B안: "등록/후보" 구분 칸 + "후보이고 규칙 0개면 직접 추가일 때만"

  • 장점: 규칙만 넣으면 보임
  • 단점: 학교·회사(규칙이 계속 없음)와 미조사를 가르지 못함
  • 채택하지 않은 이유: [이유 미확인]

C안: 칸만 두고 API는 별도 joinSurveyed 값

  • 장점: 기존 웹 분기를 건드리지 않음
  • 단점: 같은 뜻을 두 값으로 봄
  • 채택하지 않은 이유: 사용자가 등급 값을 고름 [이유 미확인]

결과

  • 좋아지는 점: 미조사 도서관에 요청이 가지 않음, 조사 결과를 코드 변경 없이 넣음
  • 감수하는 점: 직접 추가하지 않은 이용자에게는 미조사 도서관이 보이지 않음
  • 나중에 분리할 때: 도서관 서비스의 계획 규칙 하나

답: "회사·대학은 일부러 조사 안 하는 것도 있는데, 진짜 조사해서 안 나온 것과 그냥 조사 안 한 것을 어떻게 가르나?"

"조사했나" 칸을 예/아니요 둘이 아니라 셋으로 나누면 가를 수 있습니다. 수집 세션의 종류 표(candidate-kinds-2026-10-05.tsv)로 어느 쪽인지 정해 넣습니다.

조사함등록 도서관 278곳, 원문이 확인된 후보 공공도서관(약 100곳)지금처럼 지역·직장으로 판정가입 자격·방법

3ADR-0054: 가져오기는 모든 서비스 도서관의 책을, 나눠 읽어서 옮긴다

가져오기는 collection 짝 표에 있는 모든 서비스 도서관의 책을 옮긴다. importer는 수집 DB를 적당한 크기로 나눠 읽도록 고친다(방법·크기는 dev). 북큐브 소리·영상 파일과 교보 "동영상"은 오디오북·동영상북처럼 뺀다. 북큐브 8자리 출판일을 읽고, 설정에 적은 도서관(명지대학교)의 1950년 이전 날짜는 없음으로 둔다. 가져온 뒤 VACUUM (ANALYZE)를 한다. 사이클 04 범위 결정을 바꾼다.

구체적으로 이렇게 됩니다

예: 지금 서비스 DB에는 등록 도서관 책(소장 약 495만 줄)만 있습니다. 바뀐 뒤에는 짝 표에 있는 모든 도서관의 책(약 2,100만 줄)이 들어갑니다.

나눠 읽기: 지금 가져오기는 수집 DB를 한꺼번에 메모리에 올립니다(이번 양이면 11~15GB 추정). 이것을 적당한 묶음씩 읽어 처리하도록 고쳐, 운영 서버 정도의 메모리에서도 돌게 합니다.

빼는 것: 오디오북·동영상북(지금처럼) + 북큐브 소리·영상 파일 + 교보 "동영상" 약 5,700줄. 고치는 것: 북큐브 "20231015" 같은 날짜를 날짜로 읽고, 명지대학교의 1950년 이전 날짜는 "없음"으로.

배경

사이클 04에서 가져오기는 등록 도서관 책만 옮기기로 했다(docs/cycles/04-and-search/spec.md 35행). 후보 도서관이 서비스에 들어오면 그 책도 옮겨야 한다. 양은 소장 약 495만 줄에서 약 2,100만 줄로 는다. 지금 importer는 모든 줄을 메모리에 올려 힙 약 11~15GB(추정)가 든다. 북큐브 소리·영상 파일(book/wma·vod·wmv)과 교보 "동영상"(약 5,700줄)은 "모름"으로 분류돼 지금 규칙대로면 책으로 들어온다.

이유 (사용자 발언)

  • "가져오기는 그러면 이제 서비스 db도서관 표에 있는 도서관의 책만 옮기지 않고 다 옮겨야 하지 않나 어짜피 지금 내 도서관으로 도서관 선택해서 넣을 수 있게 되었는데" (2026-10-04)
  • "적당한 크기로 나눠 읽도록 바꿔줘" (2026-10-05)
  • 소리·영상 제외, 날짜 규칙, VACUUM: [이유 미확인] (제안 → 승인)

검토한 대안 — "(채택)"이 위에서 말한 할 일이고, 나머지는 하지 않습니다

A안: 모든 도서관 + 나눠 읽기 (채택)

  • 장점: 운영 서버에서 바로 돌 수 있음
  • 단점: importer 코드를 고침

B안: 지금 코드 그대로, 메모리가 큰 PC에서 운영 DB로

  • 장점: 코드 변경 없음
  • 단점: 큰 PC가 있어야 함
  • 채택하지 않은 이유: "적당한 크기로 나눠 읽도록 바꿔줘"

C안: 후보 도서관 책은 따로 표에

  • 장점: 등록 도서관 검색이 그대로
  • 단점: 검색이 두 표를 봄
  • 채택하지 않은 이유: [이유 미확인]

결과

  • 좋아지는 점: 후보 도서관 책이 검색됨, 메모리에 덜 묶임
  • 감수하는 점: 가져오는 동안(약 10분 이상, 추정) 책 검색이 기다림(배포 전이라 수용, 사용자 2026-10-05). 등록 도서관 책의 대표 제목·묶음이 조금 바뀔 수 있어 AC-6 기준을 "가진 책과 순서가 같음"으로 바꿈(사용자 승인, 2026-10-05)
  • 나중에 분리할 때: 가져오기는 collection이 맡을 갱신 흐름으로 옮겨 갈 수 있음

3ADR-0054 초안대로 기록합니다(Accepted) [안]

4ADR-0055: 책마다 가진 도서관 번호 목록을 가져올 때 미리 계산한다

가져오기가 책마다 가진 도서관 번호 목록(book.library_ids bigint[])을 채우고, 책 검색은 이 목록과 계획 도서관 번호가 겹치는지로 거른다. 검색은 소장 표를 읽지 않는다.

구체적으로 이렇게 됩니다

예: 책 "아몬드"를 가진 도서관이 45, 281, 1203번이면, 가져올 때 책 줄에 "[45, 281, 1203]"을 적어 둡니다. 검색할 때는 "이 사람의 검색 대상 도서관 번호와 겹치나"만 보고 책을 고릅니다. 2,100만 줄짜리 소장 표를 뒤지지 않아 빠릅니다.

목표: 정해 둔 검색어 묶음에서 첫 쪽 1초 안.

배경

책 검색(GET /books)은 단어로 책을 찾은 뒤 계획 도서관을 가진 책만 남긴다. 소장이 약 4배가 되고 후보 도서관에만 있는 책도 일단 찾아진 뒤 버려져, "사랑" 224ms가 수백 ms~1초대로 늘 것으로 추정했다. 목표는 정해 둔 검색어 묶음에서 첫 쪽 1초 안이다(사용자 승인, 2026-10-05).

이유 (사용자 발언)

  • "처음부터 미리 계산" (2026-10-05, 처음 제안 "먼저 재 보고 넘으면"을 미승인)

검토한 대안 — "(채택)"이 위에서 말한 할 일이고, 나머지는 하지 않습니다

A안: 처음부터 미리 계산 (채택)

  • 장점: 소장 수에 거의 영향을 받지 않음
  • 단점: 같은 사실을 두 곳에 둠(약 0.2GB, 추정)

B안: 지금 쿼리로 재 보고 1초를 넘으면 미리 계산

  • 장점: 넘지 않으면 코드 변경 없음
  • 단점: 넘으면 다시 작업
  • 채택하지 않은 이유: [이유 미확인]

결과

  • 좋아지는 점: 책이 더 늘어도 검색 속도가 덜 흔들림
  • 감수하는 점: 목록은 가져올 때만 맞음(가져오기 사이에는 소장이 바뀌지 않으므로 어긋날 일 없음)
  • 나중에 되돌릴 때: 파생 칸이라 지우면 됨

5ADR-0056: 북큐브·알라딘 대출 상태는 책 상세로 읽고, 북큐브 대여형·교보 소장형은 따로 판정한다

화면 종류 BOOKCUBE_FX, ALADIN_V1을 더하고(ADR-0016·0023), 책마다 가진 상세 주소로 읽는다: 북큐브는 같은 사이트의 XML(/xml/productView/?num=), 알라딘은 상세 화면의 "보유현황". "도서관에서 직접 찾기"용 검색도 만든다. 북큐브 대여형은 응답마다 판정해 "구독형 · 바로 대출"로 보인다. 교보 소장형은 구독형과 구분해 숫자로 보이도록 이번에 고친다(방법은 dev가 사이트 시험으로).

구체적으로 이렇게 됩니다

예: 북큐브 도서관 책 카드에는 "보유 5 · 대출 중 2 · 예약 0"이, 알라딘 도서관 책 카드에는 "보유 1 · 대출 중 1 · 예약 0"이 다른 도서관처럼 보입니다. 북큐브 대여형 도서관은 "구독형 · 바로 대출"로 보입니다.

어떻게 읽나: 책마다 이미 가진 상세 주소로 그 사이트에 요청합니다. 북큐브는 같은 주소의 작은 XML(/xml/productView/?num=)에서, 알라딘은 상세 화면의 "보유현황"에서 숫자를 읽습니다. 같은 사이트에는 한 번에 1건, 1초 간격.

교보 소장형: 교보 구독형 화면을 쓰는 기관 중 소장형(후보 1,182곳, 등록 5곳)은 지금 늘 "바로 대출"로 잘못 보입니다. 도서관마다 소장/구독 구분 칸을 두고 소장형은 숫자를 읽도록 고칩니다.

배경

후보 도서관 중 북큐브(약 450곳)·알라딘(25곳)은 대출 상태를 읽는 코드가 없었다. 2026-10-05 호출 시험에서 둘 다 로그인 없이 보유·대출·예약 수를 읽을 수 있었다(docs/cycles/07-candidate-libraries/research.md 1절). 북큐브 대여형은 보유가 늘 0이다. 교보 구독형 화면(KYOBO_SUBSCRIPTION_V1)을 쓰는 소장형 기관(후보 1,182곳, 등록 5곳)은 지금 코드에서 모두 "구독형 · 바로 대출"로 보인다.

이유 (사용자 발언)

  • "읽는 코드를 이번에 만들었으면 해" (2026-10-05)
  • 상세로 읽기, 대여형 응답 판정, 교보 소장형 고치기: [이유 미확인] (제안 → 승인)

검토한 대안 — "(채택)"이 위에서 말한 할 일이고, 나머지는 하지 않습니다

A안: 상세 기반 + 대여형 응답 판정 (채택)

  • 장점: 이미 가진 상세 주소를 씀, 한 사이트에 섞여도 맞음
  • 단점: 책마다 요청 한 번

B안: 대여형을 도서관별 칸으로 판정

  • 장점: 요청이 줄어듦
  • 단점: 섞인 사이트에서 틀림, 값을 조사해야 함
  • 채택하지 않은 이유: [이유 미확인]

C안: 북큐브·알라딘은 "목록에 있음"까지만

  • 장점: 코드가 없음
  • 단점: 대출 상태가 안 보임
  • 채택하지 않은 이유: "읽는 코드를 이번에 만들었으면 해"

결과

  • 좋아지는 점: 후보 도서관 대부분의 대출 상태가 보임
  • 감수하는 점: 사이트 모양이 바뀌면 고쳐야 할 adapter가 둘 늚. 쪽 넘기기·알라딘 출판사 검색은 시험 전까지 제한
  • 나중에 분리할 때: 조회 서버 쪽 adapter로 그대로 옮김

6ADR-0057: 로그인하지 않아도 도서관을 직접 추가하고, 로그인 때 한 번에 옮긴다

로그인하지 않은 이용자도 내 도서관 화면에서 도서관을 직접 추가할 수 있고, 이 브라우저에 20곳까지 저장해 검색 때 libraryIds로 넘긴다. 로그인 직후 계정에 직접 추가한 도서관이 없고 브라우저에 있으면 지역과 함께 옮길지 묻고, 옮길 때는 한 번에 옮기는 새 요청을 쓴다. ADR-0049의 "도서관 하나씩 저장"에 묶음 옮기기 요청 하나를 더한다.

구체적으로 이렇게 됩니다

예: 로그인하지 않은 사람이 내 도서관 화면에서 "강동대학교 (북큐브)"를 넣으면 이 브라우저에 저장되고, 검색할 때 그 도서관이 들어갑니다. 나중에 로그인하면 "이 브라우저에 저장된 것을 계정에 저장할까요?"가 한 번 뜨고, [계정에 저장]을 누르면 넣어 둔 도서관들이 한 번의 요청으로 계정에 옮겨집니다.

새로 생기는 것: 서버 요청 하나 POST /api/v1/me/library-imports(도서관 번호 목록을 받아 비어 있는 계정에 한꺼번에 넣음).

배경

사이클 06에서 직접 추가는 로그인한 이용자가 서버에 저장하는 것으로 정했다(ADR-0049). 후보 도서관은 직접 추가해야만 보이므로, 이대로면 로그인하지 않은 이용자는 후보 도서관을 쓸 수 없다. 검색은 이미 웹이 도서관 번호(libraryIds)를 넘기는 방식이다(ADR-0037).

이유 (사용자 발언)

  • "로그인 하지 않더라도 직접 넣었으면 하는데... 훔.." (2026-10-05)
  • "한 번에 옮기는 새 요청을 만들어줘" (2026-10-05)

검토한 대안 — "(채택)"이 위에서 말한 할 일이고, 나머지는 하지 않습니다

A안: 브라우저 저장 + 로그인 때 한 번에 옮김 (채택)

  • 장점: 로그인 전후 같은 규칙(지역과 같음), 옮기기가 중간에 끊기지 않음
  • 단점: 새 요청과 오류 규칙

B안: 기존 "도서관 하나 추가" 요청을 하나씩

  • 장점: 새 API 없음
  • 단점: 최대 20번 요청
  • 채택하지 않은 이유: "한 번에 옮기는 새 요청을 만들어줘"

C안: 로그인한 이용자만 직접 추가

  • 장점: 일이 가장 적음
  • 단점: 로그인하지 않은 이용자는 후보 도서관을 못 씀
  • 채택하지 않은 이유: "로그인 하지 않더라도 직접 넣었으면 하는데... 훔.."

결과

  • 좋아지는 점: 누구나 후보 도서관을 씀
  • 감수하는 점: 브라우저 저장은 그 기기에서만, 새 API 하나
  • 나중에 분리할 때: 묶음 옮기기는 "내 도서관" 서비스의 API

7ADR-0058: 내 도서관 화면의 도서관 찾기는 목록을 통째로 받고 응답을 압축한다

목록을 통째로 받는 방식을 유지하고, 웹 서버(nginx)에서 JSON 응답 압축을 켠다. 화면은 앞 글자가 맞는 것 먼저·가나다순, 두 글자 이상, 20곳씩 보인다. dev가 실제 크기를 재서 확인한다. ADR-0049의 전환 조건을 측정으로 정리한다.

구체적으로 이렇게 됩니다

예: 내 도서관 화면을 열면 도서관 약 2,700곳 목록을 한 번 받습니다(압축하면 약 40KB, 추정). 그 뒤 "강동"을 치면 서버에 묻지 않고 화면이 바로 거릅니다(앞 글자가 맞는 것 먼저, 가나다순, 두 글자부터, 20곳씩).

새로 하는 것: 웹 서버가 응답을 압축하도록 설정 한 줄. 새 서버 요청은 없습니다.

배경

ADR-0049는 도서관 공개 목록(GET /api/v1/libraries)을 통째로 받아 화면에서 이름으로 거르고, "도서관이 수천 곳이 되면 서버에서 이름으로 거르는 방식으로 바꿔야 함"을 감수했다. 후보 도서관이 들어오면 약 2,700곳이 된다. 278곳 응답은 48,123바이트(gzip 약 4.2KB)였고, 약 2,700곳이면 약 460KB, gzip 약 40KB로 추정한다.

이유 (사용자 발언)

  • "어느 게 효과적일 것 같아? 서버 부담이 더 족은 방향좀" (2026-10-05) → 요청 수가 적은 목록 통째로가 서버 부담이 적다는 답을 보고 승인

검토한 대안 — "(채택)"이 위에서 말한 할 일이고, 나머지는 하지 않습니다

A안: 목록 통째로 + 압축 (채택)

  • 장점: 화면을 열 때 요청 1번, 캐시 가능, 새 주소 없음
  • 단점: 처음 받는 양이 늚(압축 약 40KB, 추정)

B안: 서버에서 이름으로 찾기

  • 장점: 주고받는 양이 가장 적음
  • 단점: 글자를 칠 때마다 요청과 DB 조회, 새 주소 둘
  • 채택하지 않은 이유: 서버 부담이 더 적은 쪽을 원함 ("서버 부담이 더 족은 방향좀")

결과

  • 좋아지는 점: 서버 요청이 적음
  • 감수하는 점: 도서관이 훨씬 더 늘면 다시 봄
  • 나중에 분리할 때: 도서관 서비스의 공개 목록 API 그대로
