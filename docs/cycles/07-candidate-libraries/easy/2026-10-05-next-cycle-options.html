2다섯 가지 안

A배포(운영에 올리기) 준비 [안]

하는 일. 서버를 어디에 둘지(AWS 서버 한 대 / 먼저 내 PC + Cloudflare 터널), 도메인, 운영 설정(실제 사용자 IP 받기, https 뒤에서 주소 알아보기, 시험용 데이터 빼기), 서비스 DB를 운영으로 옮기는 방법, 카카오 로그인만 켜기, 로고 내림 연락 이메일. 첫 배포 때 "배포 전" 표시를 지웁니다.

왜 지금. 사용자 순서의 ⑥이고 목표가 10월 6일 새벽입니다.

크기. 중간. 코드보다 사용자 결정과 설정이 많습니다.

막는 것. 실제 카카오 로그인 확인(AC-19), 도메인, 이메일 주소, 서버 크기(가져오기 Java 메모리 8GB, DB 약 9.8GB).

보이는 결과. 실제 주소로 서비스가 열립니다.

"운영 설정이 남음" 중 일부(시험 데이터, https 설정)는 (개인 메모)의 진단이고, dev 코드로 다시 확인하지 못했습니다.

B배포 전 다듬기 (사이클 07 남은 작은 수정 + 화면 수정 ⑤) [안]

하는 일.

  • 회고에서 정한 것: 정렬·완전 일치·역할은 기억하지 않음, 가져오기 기록에 사본 수집 기간, 고친 시각이 자동으로 적히게(트리거)
  • dev 남은 질문 페이지에서 정하실 것: 429·503 문구, 도서관 411, 이름이 다른 도서관 등
  • ⑤ 화면 수정: dev가 넘긴 화면 질문(폰 설정 창, 정렬 안내, 글꼴 크기 약 3MB 줄이기, 약관 화면에서 돌아오는 길)과 사용자가 주시기로 한 "이상한 곳" 캡처

왜 지금. 회고에서 "다음 인계서로" 정했고, 사용자 순서의 ⑤이며, "배포 전" 표시가 있을 때 하는 편이 깔끔합니다.

크기. 작음~중간. 하나하나가 작습니다.

보이는 결과. 검색 조건 기억이 바뀌고, 첫 화면이 빨리 뜨고, 도서관 이름이 맞게 나옵니다.

C책 목록 주기 갱신 + DB 메모리 줄이기 [안]

하는 일. 가져오는 동안에도 검색이 멈추지 않게(새 표를 만든 뒤 바꿔 끼우기), 다음 사본으로 아직 수집이 덜 끝난 후보 도서관을 더 넣기, 같은 책의 소장 줄을 붙여 저장(DB 메모리 안 1), PostgreSQL 메모리 설정(안 2), 책 묶기 기준 다시 보기.

왜 지금. 지금 가져오기 쓰기 22~27분 동안 검색이 기다립니다. 교보 대여·혼합형 수집은 10월 11~12일쯤 끝날 것으로 적혀 있습니다(사이클 07 scope.md).

크기. 큼. 가져오기 구조, 수집기 옮기기, 갱신 주기가 얽힙니다.

막는 것. 수집 한 바퀴가 끝나야 합니다. 메모리 설정 값은 서버를 정한 뒤 정합니다. 사용자 말 "다 세팅한다음에 '갱신'기능"으로는 배포 뒤입니다.

보이는 결과. 찾을 수 있는 도서관과 책이 늘고, 갱신 중에도 검색이 됩니다.

D구독형 한도 알리기 [안]

하는 일. 구독형 도서관 줄에 그 도서관의 고정 규칙(한 사람 한 달 몇 권, 매달 1일 다시 열림)과 공지로 본 "이번 달 마감"을 보입니다. 구독 규칙을 도서관 정보와 따로 둘지는 설계에서 정합니다.

왜 지금. "책 번호 유지 다음에 함"으로 정했는데(docs/research/library-limits/research.md), 책 번호 유지가 사이클 07에서 만들어졌습니다. 마감 공지 기록은 쌓이고 있습니다.

크기. 중간. 도서관마다 규칙 값을 사람이 모아야 하고, 월말에 실제로 확인해야 합니다.

보이는 결과. "구독형 · 바로 대출" 줄에 한도와 마감이 보입니다.

E알림 [안]

하는 일. 관심 책 저장, "빌릴 수 있게 됨"을 서버가 확인, 알림 보내기(수단은 조사 필요), 알림 끄기.

왜 지금. 처음 계획에서 회원 다음 순서였습니다("회원 뒤에 함", 2026-10-01).

크기. 큼. 서버가 스스로 도서관을 확인해야 해서 호출 예의 문제가 있고, 보내는 수단은 공식 문서 확인이 필요합니다.

막는 것. 회원이 저장한 책 번호를 다시 가져올 때 고쳐 쓰는 일, 갱신(C)으로 책 번호 합치기·나뉨을 실데이터로 본 뒤가 안전합니다.

보이는 결과. 원하는 책을 빌릴 수 있게 되면 알림을 받습니다.
