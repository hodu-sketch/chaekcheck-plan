dev가 plan에 정해 달라고 한 것 중
남은 여덟 가지입니다.

dev 보고(plan-feedback.md "plan에 넘길 요약" 5절)에서 회고 질문 페이지가 다룬 것(AC-15, AC-6, 로고 문장)을 뺀 나머지입니다. 항목마다 제안과 다른 선택을 적었습니다. 칩에서 승인·미승인·기타를 골라 주세요. 고친 것이 필요한 항목은 다음 dev 인계서에 넣습니다.

1요청이 몰릴 때의 안내

dev가 사용자 요청으로 "요청 수 제한"을 넣었습니다. 지금은 막혔을 때 화면에 일반 오류 문구만 나옵니다.
막는 곳언제지금 숫자 (모두 제안 값)응답
웹 서버(nginx)한 사람(IP)이 도서관을 부르는 검색을 너무 자주 할 때1분에 30번, 한꺼번에 20번까지 더 받음, 동시 연결 6개429 too_many_requests
우리 서버모든 이용자의 검색이 동시에 20개를 넘을 때동시 검색 20개503 server_busy

지금 화면 문구는 둘 다 "검색하지 못했어요. 잠시 뒤 다시 시도해 주세요." (dev 보고 "handoff 밖 추가 작업 C")

1429와 503에 따로 안내 문구를 둠 [안]

예: 429는 "검색을 너무 자주 했어요. 1분쯤 뒤에 다시 해 주세요.", 503은 "지금 찾는 사람이 많아요. 잠시 뒤에 다시 해 주세요." 이용자가 "내가 너무 자주 했다"와 "서버가 바쁘다"를 구별할 수 있습니다. 두 응답 이름을 API 오류표에 더합니다.

다른 선택 지금 일반 문구 그대로: 일이 없지만, 이용자는 왜 안 되는지 모릅니다.

추천: 따로 둠 (문구 두 줄과 오류표 두 줄이라 일이 작음)

2숫자와 "실제 사용자 IP 받는 법"은 배포할 때 정함 [안]

숫자(1분 30번, 동시 20개 등)는 서버 크기와 실제 이용량을 봐야 정할 수 있습니다. 웹 서버 앞에 다른 장치(부하 분산기, Cloudflare 등)가 있으면 모든 사람이 같은 IP로 보여 한 사람처럼 막히므로, 실제 IP를 받는 설정은 배포 구성을 정할 때 함께 정합니다. 그때까지 숫자는 제안 값으로 둡니다.

다른 선택 지금 숫자를 확정: 근거(이용량 측정)가 아직 없습니다.

2주소가 다른 회사로 옮겨 간 도서관

도서관 411은 사이트 주소가 다른 호스트로 넘어가서, 가져오기가 "다른 사이트"로 보고 책 64,461줄을 넣지 않았습니다.

3수집 DB의 주소를 새 주소로 고치고, 다음 수집부터 맞춤 [안]

수집 DB의 411 주소(http://ebook2.ezville.net/FxLibrary)를 넘어가는 곳(https://gsenc.bookcube.biz/FxLibrary)으로 바꾸고 그 도서관 책을 다시 수집합니다. 앞으로 도서관 수집 갈래의 "확인" 단계에서 최종 주소도 함께 확인하게 합니다. 다시 수집하고 가져오기 전까지는 411의 책이 검색에 나오지 않습니다.

다른 선택 (가) 번호 짝 표에 "수집 주소"를 따로 두고 가져오기가 그것과 비교: 다시 수집하지 않아도 되지만 짝 표 구조가 바뀜. (나) 가져오기에 "이 도서관은 주소가 옮겨 갔음" 예외 목록: 빠르지만 예외가 쌓임.

추천: 수집 DB 주소 고치기 (한 곳이고, 원인을 수집 쪽에서 바로잡음)

4그대로 둠 (사이트 문제로 기록만) [안]

이용자가 실제로 빌리러 가는 책 상세 링크는 맞으므로, 대출하는 흐름에는 문제가 없습니다. 문제가 생기는 것은 폰에서 "도서관 첫 화면"이나 "도서관에서 직접 찾기" 결과 링크를 누를 때입니다. dev 문서에 기록해 두고 서비스는 바꾸지 않습니다.

다른 선택 (가) 폰에서 이 13곳의 첫 화면 링크를 숨김: 이상한 화면은 안 보이지만 도서관 표에 표시 칸이 하나 필요. (나) 링크 옆에 "폰에서는 사이트가 다른 화면을 보여요. PC에서 열어 주세요" 안내: 같은 표시 칸 필요. (다) 13곳을 끔: 그 도서관 책이 검색에서 빠짐.

추천: 그대로 둠 (대출 흐름은 맞고, 단순함)

5다른 기관으로 보이는 10곳은 한 곳씩 확인한 뒤 다시 여쭘 [안]

사이트 제목만으로는 "이름이 틀린 것"인지 "사이트가 다른 기관 틀을 빌려 쓴 것"인지 알 수 없습니다(동대문구립도서관이 경동대학교 틀을 쓴 예가 있음). 10곳의 첫 화면과 소개 쪽을 한 번씩 열어(같은 사이트 1건·1초) 표로 정리해, 곳마다 "이름 고침 / 그대로 / 끔"을 다시 여쭙겠습니다.

다른 선택 지금 사이트 제목대로 이름을 바꿈: 빠르지만 틀 빌려 쓰기인 곳은 오히려 틀린 이름이 됨. 10곳을 끔: 확인할 필요는 없지만 맞는 도서관까지 빠질 수 있음.

6기관 이름이 바뀐 곳은 새 이름으로 고칠 수 있게 함 (번호는 유지) [안]

"처음 정한 이름은 바꾸지 않는다"에 예외를 하나 둡니다: 기관 이름이 공식적으로 바뀌었거나 이름이 틀렸을 때는 고칠 수 있고, 번호는 그대로. 이용자 브라우저와 계정에는 번호만 저장되므로, 이름을 고쳐도 내 도서관 목록은 깨지지 않습니다. 어느 곳을 고칠지는 사이트 제목 검사 결과로 목록을 만들어 다시 여쭙니다.

다른 선택 예전 이름 그대로: 이용자가 새 이름으로 찾으면 안 나옴.

5알라딘 "대출하기" 단추

알라딘 3곳(서정대·대구공업대·김해대)은 목록에 보유·대출 수를 보여 주지 않아, 지금은 그 줄을 "확인 필요"로 보입니다. 목록에는 "대출하기" 단추가 있습니다.

7대출 중인 책 화면을 볼 때까지 "확인 필요" 그대로 둠 [안]

대출 중인 책에서도 "대출하기" 단추가 나오는지 아직 못 봤습니다(dev 확인 못 함). 단추만 보고 "지금 빌릴 수 있음"이라고 하면, 대출 중인 책을 빌릴 수 있다고 잘못 보일 수 있습니다. 대출 중인 책을 찾게 되면 그 화면을 보고 다시 정합니다.

다른 선택 단추가 있으면 "지금 빌릴 수 있음": 3곳 결과가 더 쓸모 있어지지만 틀릴 수 있음.

추천: 그대로 둠 (틀린 "빌릴 수 있음"을 피함)

6기록과 다음 일로 넘길 것

아래 셋은 지금 고칠 것은 없고, 언제 무엇을 할지만 정합니다.

8인증 기관 추가의 결정 기록(ADR-0022 갱신)은 사이클 08 범위를 정한 뒤 다른 기록과 함께 씀 [안]

도서관 사이트 연결에만 인증 기관 하나를 더 믿기로 한 결정("이거 신뢰해줘")은 이미 코드에 들어가 있습니다. 결정 기록 초안은 사이클 08에서 무엇을 할지 정한 다음, 사이클 07에서 바뀐 다른 결정들과 함께 한 페이지로 보여 드리겠습니다.

다른 선택 지금 이것만 먼저 기록.

9회원이 책을 저장하는 기능을 만들 때 "옛 책 번호 → 새 책 번호 고쳐 쓰기"를 함께 함 [안]

책 번호 잇기는 이번에 만들어졌습니다(같은 책은 다시 가져와도 같은 번호). 다만 두 책이 하나로 합쳐지면 없어지는 번호가 생깁니다. 2026-10-04에 "회원이 저장한 책 번호는 가져올 때 새 번호로 고쳐 쓴다"고 정했는데, 지금은 책 번호를 저장하는 회원 기능이 없어 할 일이 없습니다. 그 기능(예: 알림, 관심 책)을 만드는 사이클의 할 일로 적어 둡니다.

10가져오기 시간과 메모리는 배포 서버를 정할 때의 입력으로 씀 [안]

가져오기 한 번에 37~41분 걸리고, 그중 쓰기 22~27분 동안 책 검색이 기다립니다(배포 전이라 받아들인 것). 가져오기는 Java 메모리(힙) 8GB 안에서 끝났고, 더 작게는 재 보지 않았습니다. 운영 서버에서 가져오기를 돌린다면 서버 메모리를 이 크기에 맞춰야 합니다. 검색이 기다리지 않게 하는 방법(새 표를 만든 뒤 바꿔 끼우기)과 DB 메모리 줄이기(docs/research/deploy/db-memory.md)는 책 목록 주기 갱신이나 배포를 다루는 사이클에서 함께 정합니다.

다른 선택 지금 바로 가져오기를 빠르게 하는 일을 시작.

정하신 것: 기존 표를 두고 새 표에 쓴 뒤 바꿔 끼우는 간단한 설계를 미리 해 둠

그렇게 적었습니다. 이 방향은 2026-09-30에 정하신 "표 통째로 바꾸기"(catalog-refresh.md 5.1절)와 같습니다. 그때 적어 둔 챙길 점은 셋입니다.

  • 책 번호가 바뀌지 않아야 함 → 사이클 07에서 책 번호 잇기로 해결됨
  • 바꿔 끼우는 방법: 한 번에 이름을 바꾸는 방법 또는 표 묶음 A/B를 번갈아 쓰는 방법. 새 표의 색인·제약을 DB 구조 파일 정의와 같게 유지하는 장치가 필요
  • 바꾸는 순간 진행 중인 대출 조회는 그 줄만 실패로 보일 수 있음

이 설계를 사이클 08에 넣을지는 "다음 사이클 후보" 페이지에서 함께 고르시면 됩니다.
