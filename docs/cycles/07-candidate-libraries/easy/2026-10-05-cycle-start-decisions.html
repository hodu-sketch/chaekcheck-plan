2이번 사이클이 하는 일:
세 덩어리

후보 도서관과 그 책을 서비스에 넣고(A), 늘어난 양에 맞게 DB와 검색을 다듬고(D), 도서관 수집과 책 수집을 두 갈래로 다시 정리합니다(B).

수집은 두 갈래(①②), 그 결과를 서비스로 옮기는 가져오기(③), 서비스 쪽 다듬기로 나뉩니다. 괄호 안 글자는 아래 항목의 덩어리 이름입니다.

한 문장: "후보 도서관과 그 책을 서비스 DB에 넣어 후보 도서관도 이름으로 찾고 그 책도 검색되게 하되, 늘어난 양에 맞게 DB 형식과 검색 방법을 최적화하고, 도서관 수집과 책 수집을 두 갈래로 깔끔하게 다시 정리한다." 사용자가 이번 대화에서 말한 세 가지를 그대로 묶은 것입니다.

3A. 후보 도서관 넣기

후보 도서관 2,738곳 중 등록 도서관과 같은 사이트 99곳을 빼면 2,639곳입니다. 이 중 전체 수집이 한 번이라도 끝난 곳은 지금 2,249곳입니다.
화면 종류후보같은 사이트로 뺌수집 끝난 곳대출 상태 읽는 코드
교보 일반35790266있음
교보 구독형 화면(소장·혼합·대여)1,41421,189있음
YES244840477있음
북큐브4587292없음
알라딘25025없음

교보 대여·혼합 232곳은 아직 받는 중입니다(수집 세션 예상 약 12일). 이미 정한 것: 가입 조건이 없는 도서관은 내 도서관에 넣은 사람에게만 검색에 나오고, 그때만 그 사이트로 요청을 보냅니다 (사용자, 2026-10-04).

3가져올 때 수집이 한 번이라도 끝난 후보 도서관만 넣고,
나머지는 다음 가져오기 때 들어오게 합니다 [안]

예: 오늘 가져오면 2,249곳이 들어갑니다. 대여·혼합 232곳은 다 받은 뒤 다시 가져올 때 들어옵니다. 책이 하나도 없는 도서관이 내 도서관 목록에 보이는 일이 없습니다.

다른 선택 ① 2,639곳을 모두 넣고 책은 받은 만큼만: 고를 수 있는 도서관은 많지만 직접 추가해도 책이 안 나오는 곳이 생깁니다. ② 교보·YES24만 먼저: 대출 상태가 모두 보이지만 북큐브·알라딘 317곳이 빠집니다.

"목록에 있음"과 [도서관에서 보기]만 보입니다 [안]

결과 줄 예시 (위치와 순서만 보이는 그림이며, 실제 모양은 dev 화면을 따릅니다)

북큐브·알라딘 사이트의 대출 상태를 읽는 코드는 지금 없습니다. 그래서 그 도서관은 우리가 받은 책 목록에 있다는 것만 보여 주고, 실제 대출은 링크로 그 사이트에서 확인합니다. 사이트로 실시간 요청을 보내지 않습니다.

다른 선택 ① 읽는 코드를 이번에 만듦: 사이트를 시험해 보고 코드를 짜야 해서 10월 6일 새벽 배포에는 어렵습니다. ② 이번에는 북큐브·알라딘을 아예 넣지 않음.

5서비스로 가져오는 책을 등록 도서관만에서
모든 도서관으로 넓힙니다 [안]

사이클 04에서 정한 "등록 도서관 책만 가져옴"([확정])을 바꾸는 결정이라 결정 기록(ADR)을 새로 남깁니다.

소장 줄이 지금 약 495만에서 약 1,900만으로 늘어납니다(후보 몫 약 1,412만 + 등록 몫 약 499만, 2026-10-04 밤 기준). dev가 실제로 넣기 전에 시험 실행(dry run)으로 크기와 시간을 먼저 잽니다. 지난번에는 쓰는 데 2분 27초였고, 그동안 책 검색이 약 2분 30초 기다렸습니다.

다른 선택 후보 도서관의 책은 따로 표에 넣음. 등록 도서관 검색은 지금 그대로 빠르지만, 검색이 두 표를 봐야 해서 더 복잡합니다.

6후보 도서관의 수집 DB 번호(100001부터)를
서비스 도서관 번호로 그대로 씁니다 [안]

예: 수집 DB에서 100245번인 도서관은 서비스에서도 100245번입니다. 가져오기가 두 DB의 도서관을 번호로 짝짓기 때문에, 번호가 같으면 짝 맞추는 표가 필요 없습니다. 등록 도서관은 지금처럼 1~280번입니다.

다른 선택 서비스에서 새 번호를 주고 짝 맞추는 표를 둠. 번호가 촘촘해지지만 표 하나와 맞추는 일이 늘어납니다.

4D. 데이터 형식 파악 → DB와 검색 다듬기

사용자 말: "그 데이터 형식을 파악해서 db형식을 최적화해서 검색 방법을 최적화해서 후보 도서관도 검색할 수 있고 후보 도서관의 책도 검색이 되게 하는거야" (2026-10-05)

7수집한 값의 모양을 화면 종류별로 먼저 재고,
그 결과로 DB 형식과 검색 방법을 정합니다 [안]

순서는 셋입니다.

단계하는 일누가
재기수집 DB의 칸(책 26칸, 도서관 10칸)마다 비어 있는 비율, 길이, 책 코드 모양, 자료 종류 값, 상세 주소 모양을 화면 종류별로 셈plan이 수집 DB를 읽기만 해서 셈 (수집은 멈추지 않음)
DB 형식소장 약 1,900만 줄에 맞게 책·사람·소장 표와 찾기용 색인(인덱스)을 다시 봄설계(plan) → 구현(dev)
검색 방법책 검색이 늘어난 양에서도 빠르게, 후보 도서관을 이름으로 찾기설계(plan) → 구현·측정(dev)

응답 시간 목표 같은 숫자는 다음 단계(명세)에서 정합니다.

다른 선택 먼저 그대로 넣어 보고 느린 곳만 고침. 빠르지만, 형식을 바꿀 기회가 배포 뒤로 밀립니다.

8내 도서관 화면에서 후보 도서관을 찾는 방법은
재 본 뒤 설계에서 정합니다 [안]

지금은 도서관 278곳 목록을 통째로 받아(약 48KB, 압축하면 약 4KB) 화면에서 이름으로 거릅니다. 약 2,500곳이 되면 약 10배가 됩니다. 두 방법 중 하나를 설계에서 고릅니다.

방법좋은 점감수할 점
지금처럼 통째로바꿀 코드가 거의 없음화면을 열 때 받는 양이 늘어남(압축 약 40KB 예상, 확인 못 함)
서버에서 이름으로 찾기글자를 칠 때 맞는 것만 받음새 검색 주소와 화면 변경

다른 선택 지금 바로 "서버에서 이름으로 찾기"로 정함. ADR-0049가 "도서관이 수천 곳이 되면 바꿔야 함"이라고 미리 적어 둔 길입니다.

5B. 수집 방법 재구성: 두 갈래

사용자 말: "도서관 수집하는거랑(수집하면서 구독형은 마감 여부 확인하는 거랑) 도서관의 책 수집하는 거 그 두가지야" (2026-10-05)

9두 갈래마다 "무엇을 받아 무엇을 내놓나"와 원칙을
한 장씩으로 정리하고, 도서관 목록 원본을 하나로 합니다 [안]

갈래받는 것내놓는 것
① 도서관 수집교보 공식 목록, 웹러브 북스 기관 목록, 공공 목록도서관 목록(이름, 주소, 화면 종류, 켜짐) + 같은 사이트 거르기 + 구독형 마감 여부
② 도서관의 책 수집① 의 도서관 목록도서관마다 책 목록(수집 DB)

지금은 등록 도서관 목록이 dev의 설정 파일(CSV)에, 후보 도서관 목록이 수집 DB에만 있어 목록이 둘입니다. 후보 도서관이 서비스에 들어가면 서비스의 도서관 표 하나를 원본으로 두는 방향입니다. plan 문서는 지금 여섯 장(crawl-method.md, crawl-runbook.md, platforms.md, periodic-tasks.md, collection-areas.md, catalog-refresh.md)에 흩어져 있어, 두 갈래 한 장씩과 진행 기록으로 다시 엮습니다. dev 쪽 절차·코드 정리는 인계서로 요청합니다.

다른 선택 plan 문서만 정리하고 도서관 목록 원본은 지금처럼 둘. 작지만, 후보 도서관을 넣을 때마다 두 곳을 맞춰야 합니다.

10돌고 있는 수집기는 멈추지 않고,
코드 갈아타기와 구조 정리는 수집이 한 바퀴 끝난 뒤에 합니다 [안]

지금 수집은 다른 세션에서 옛 복사본(chaekcheck-data)으로 계속 돕니다. "멈추지 않음"은 이미 정한 것입니다(사용자, 2026-10-04). 이번에는 두 갈래의 규칙과 문서를 정하고, 코드를 실제로 나누고 갈아타는 일은 책 번호 유지·주기 갱신 사이클(다시 가져오기를 다루는 사이클)에서 합니다.

다른 선택 이번에 dev 복사본으로 갈아타고 코드도 나눔. 수집을 잠시 멈춰야 하고 오늘 밤 일정에 들어가기 어렵습니다.
