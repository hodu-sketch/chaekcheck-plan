정하신 규칙을 DB·서버·화면에서
어떻게 만들지 골라 주세요.

설계 제안 에이전트(architect)가 dev 코드(2026-10-11)를 읽고 낸 대안입니다. 고르실 것은 9개이고, 고르신 것은 사이클 08 회고 뒤 설계 문서(design-delta.md)에 그대로 옮깁니다. 회고에서 사이클 08이 다르게 만든 것이 나오면 그 부분만 다시 여쭙니다.

1무엇이 바뀌는지 한 장으로

도서관 표에 칸 둘(업체, 순번)이 생기고, 겹침 확인이 "이름" 하나에서 "이름·업체·대출 방식·순번" 넷으로 바뀝니다. 서버는 이 값을 화면에 보내고, 화면이 "교보 · 소장" 글자를 만듭니다.

주황 글씨가 새로 생기는 칸입니다. 도서관 번호는 그대로라 내 도서관·로그인 계정은 영향이 없습니다.

2업체와 순번을 DB에 어떻게 두나

업체는 화면 종류에서 정해지므로 DB가 직접 계산해 칸에 넣게 하고, 순번은 보통 1인 칸을 하나 둡니다.

업체는 DB가 화면 종류에서 계산해 넣는 칸으로 [안]

도서관 표에 "업체" 칸을 더하되, 사람이나 스크립트가 값을 쓰지 않습니다. 화면 종류가 "교보 일반"이면 DB가 알아서 "교보"를 넣습니다(PostgreSQL의 "생성 칸" 기능: 값을 미리 계산해 저장). 그래서 화면 종류와 업체가 어긋날 수 없습니다.

예: 동대문구립도서관 230번은 화면 종류가 YES24라서 업체 칸에 YES24가 들어갑니다. 누군가 업체만 "교보"로 바꾸려 하면 DB가 거절합니다.

업체 칸(주황)은 화면 종류 칸에서 DB가 계산해 채웁니다. 그래서 둘이 어긋날 수 없습니다.

다른 선택 — 칸 없이 겹침 확인에만 계산식을 씀: 표가 그대로지만, 같은 대응표가 DB·서버·스크립트 세 곳에 생기고, 겹침을 찾아볼 때마다 계산식을 다시 써야 합니다.

다른 선택 — 보통 칸에 스크립트가 값을 씀: 나중에 같은 화면 종류를 다른 업체가 쓰게 되어도 따로 적을 수 있지만, 지금은 그런 곳이 없고 어긋날 위험이 생깁니다.

알아 둘 것: 나중에 실물 도서관(화면 종류가 없는 곳)이 들어오면 업체가 비어 같은 이름끼리 겹칠 수 있습니다. 실물 도서관 사이클에서 다시 봅니다. 근거: PostgreSQL 18 공식 문서 Generated Columns, https://www.postgresql.org/docs/18/ddl-generated-columns.html (확인 2026-10-11).

추천: DB가 계산해 넣는 칸.

질문: 수집 스크립트가 업체를 적는 보통 칸이 낫지 않나? 역할 나누기를 따져 보면

따져 보니 말씀하신 쪽이 역할 나누기에 더 맞습니다. 그래서 추천을 바꿔 새 탭 페이지("업체 칸을 누가 채우나")에 다시 냈습니다.

지금 역할은 이렇게 나뉘어 있습니다(docs/research/collection/1-libraries.md).

누가무엇을 정하나
도서관 수집의 "확인" 단계사이트를 열어 화면 종류, 권수, 교보의 대출 방식(소장·대여·혼합)을 알아냄
seed 생성 스크립트수집 결과를 서비스 DB에 넣을 seed로 옮김
서비스 DB저장하고, 허용된 값인지·겹치는지만 확인
서버의 사이트 읽는 부분화면 종류로 사이트를 어떻게 읽을지 고름

"화면 종류"는 사이트를 어떻게 읽을지를 위한 값이고, "업체"는 누가 운영하나라는 사실입니다. 지금은 둘이 1:1이지만 뜻이 다릅니다. 대출 방식처럼 업체도 도서관 수집이 알아낸 사실로 두면, 처음 제안(DB가 화면 종류에서 계산)보다 새 업체·새 화면이 생겼을 때 덜 묶입니다. 자세한 비교와 그림은 새 페이지에 있습니다. 이 칩은 고르지 않으셔도 됩니다.

순번 칸은 보통 1, 스크립트가 그때그때 셈 [안]

순번 칸은 따로 적지 않으면 1입니다. seed 생성 스크립트는 이름·업체·대출 방식이 같은 묶음 안에서 서비스 번호가 작은 곳부터 1, 2, 3을 셉니다(꺼진 도서관도 셈). 2 이상이 나오면 목록을 보여 주고, dev가 그 곳만 순번을 고칩니다. 지금은 모든 도서관이 1입니다(부여대왕초 겹침이 풀려서).

순번은 스크립트가 셀 때마다 서비스 번호 순서로 다시 셉니다(예시 번호는 그림용). 지금은 모든 도서관이 1입니다.

다른 선택 — 한 번 붙은 순번은 고정하고 새로 온 곳만 다음 번호: "2번째 사이트"가 바뀌지 않지만, 스크립트가 지금 순번을 기억할 파일을 따로 두거나, 이미 넣은 seed를 고쳐 DB를 다시 만들어야 합니다.

추천: 그때그때 셈. 지금은 2 이상이 하나도 없어 가장 단순한 쪽으로 갑니다.

묶음 가운데 도서관 이름을 고치면 뒤 순번이 당겨져도 됨 [안]

위 "그때그때 셈"을 고르면 생기는 일입니다. 예: 같은 묶음에 순번 1·2·3이 있는데 2번째 사이트의 학교 이름을 확인해 고치면, 그 곳은 묶음에서 빠져 1이 되고, 3이던 곳은 다음에 셀 때 2가 됩니다. 화면에서 "3번째 사이트"가 "2번째 사이트"로 바뀝니다.

가운데 사이트가 제 이름(초록)을 찾아 묶음에서 빠지면, 마지막 사이트는 다음에 셀 때 3에서 2가 됩니다.

다른 선택 — 당겨지지 않게: 위 "순번 고정" 안을 골라야 합니다.

추천: 당겨져도 됨. 순번은 이름을 확인하기 전까지 임시로 구분하는 표시이고, 도서관 번호와 내 도서관은 그대로입니다.

3이미 있는 이름과 대출 방식을 어떻게 바꾸나

사이클 08이 이름을 고친 방식(이미 넣은 seed는 그대로 두고, 번호로 고치는 변경 파일을 하나 더함)을 그대로 씁니다.

이름은 번호로 고치는 변경 파일을 하나 더하고, 목록은 사이클 08의 이름 고침 목록에 이어 적음 [안]

DB 변경 파일(Liquibase changeset) 하나에 "230번이 '동대문구립도서관(YES24)'이면 '동대문구립도서관'으로" 같은 줄을 약 285개 적습니다. 옛 이름이 그대로일 때만 바뀌므로 두 번 돌려도 같습니다. 고친 목록은 사이클 08이 만든 name_overrides.tsv에 이어 적어, 다음에 seed를 다시 만들어도 괄호가 다시 붙지 않게 합니다.

사이클 08이 434·456에 붙인 "(북큐브)"도 이때 뗍니다. 같은 학교의 다른 사이트(745 교보, 2239 YES24)와 업체가 달라 괄호 없이도 겹치지 않습니다.

변경 파일 안 순서: 이름 겹침 규칙을 지움 → 이름을 고침 → 대출 방식을 채움 → 업체·순번 칸을 더함 → 새 겹침 규칙을 검. 새 규칙을 마지막에 걸어야 바꾸는 도중에 걸리지 않습니다.

위: 두 방법의 차이. 아래: 추천 방법의 변경 파일 안에서 일어나는 순서. 새 겹침 규칙(주황)을 맨 마지막에 겁니다.

다른 선택 — 이미 넣은 seed 파일을 직접 고침: seed 파일이 그대로 정답이 되지만, 로컬 DB를 지우고 다시 만들어야 하고 책 목록도 다시 가져와야 합니다(지금 가져오기 36~41분). 사이클 08 방식과도 갈립니다.

추천: 변경 파일 하나 더함. DB를 다시 만들지 않습니다.

대출 방식은 정하신 규칙대로 채우고, 통합 포털만 비울 수 있게 DB가 확인 [안]

채우는 값은 앞 페이지에서 정하신 규칙 그대로입니다. 북큐브 구독 4곳의 서비스 번호는 339 부산, 380 제주꿈바당어린이, 386 진천군립, 705 한양대 에리카입니다(이름으로 찾은 번호라 dev가 다시 맞춰 봄).

여기에 DB 규칙을 하나 더합니다: "통합 포털이면 대출 방식이 비어 있어야 하고, 아니면 반드시 있어야 한다." 앞으로 seed가 대출 방식을 빠뜨리면 DB가 거절합니다.

DB가 도서관을 넣거나 고칠 때마다 이 갈림길로 확인합니다. seed가 대출 방식을 빠뜨리면 그 자리에서 멈춥니다.

다른 선택 — DB 규칙 없이 테스트로만 지킴: 규칙이 하나 덜 생기지만, 빠뜨려도 조용히 넘어가 화면에 업체만 보입니다(통합 포털처럼 보임).

추천: DB가 확인.

메모: 나중에 새 도서관 유형이나 대출 방법이 생겨도 유동적이어야 함

승인하신 규칙은 그대로 두고, 바뀔 때 드는 일을 적어 둡니다.

나중에 생기는 일해야 할 일
새 대출 방법(예: 소장·구독 말고 다른 방식)대출 방식 허용 값에 하나 더함(DB 변경 파일 한 줄), 화면 글자 하나 더함. 지금 규칙이 없어도 허용 값 목록은 이미 있어서 같은 일
통합 포털처럼 대출 방식을 하나로 말할 수 없는 새 유형"비어 있어도 되는 곳" 조건에 그 유형을 더함(DB 변경 파일 한 줄)
실물 도서관(화면 종류 없음)지금 규칙은 화면 종류가 없으면 확인하지 않아 그대로 들어감

어느 경우든 DB 변경 파일 하나로 바꿀 수 있고, 이미 있는 도서관 값은 다시 쓰지 않아도 됩니다. 새 탭 페이지에서 업체 칸을 도서관 수집이 채우는 쪽으로 고르시면, 이 규칙도 "화면 종류가 통합 포털"이 아니라 "업체가 통합 포털"을 보게 맞춥니다.

"진천군립도서관 대여형"은 "진천군립도서관"으로 [안]

북큐브 386번 이름에 괄호가 아닌 "대여형"이 들어 있습니다. 정하신 규칙은 "이름 끝의 괄호"만 떼므로 이 이름은 그대로 남고, 화면에 "진천군립도서관 대여형 · 북큐브 · 구독"처럼 보입니다.

제안: "대여형"을 떼고 "진천군립도서관 · 북큐브 · 구독"으로 둡니다. 다른 진천군립도서관 사이트가 있더라도 업체나 대출 방식이 다르면 겹치지 않습니다(dev가 확인).

"대여형"과 분류의 "구독"이 함께 보이는 것을 피합니다.

다른 선택 — 그대로 둠: 사이트가 쓰는 이름 그대로지만, 분류와 같은 말이 이름에도 남습니다.

추천: 뗌.

4서버와 화면

서버는 값(업체·대출 방식·순번)만 보내고, 우리말 글자는 화면이 만듭니다. 지금 가입 조건 같은 다른 값도 이렇게 보냅니다.

서버는 값 세 개를 보내고 화면이 "교보 · 소장" 글자를 만듦 [안]

도서관 목록(GET /api/v1/libraries)과 검색 결과 스트림의 도서관 정보에 칸 세 개를 더합니다. 예:

{"id":230, "name":"동대문구립도서관", "vendor":"YES24", "lendingModel":"OWNED", "orderNo":1}

화면은 "YES24 · 소장"으로 바꿔 보이고, 순번이 2 이상이면 "· 2번째 사이트"를 붙입니다. 값이 없으면(서버와 화면 배포 순서가 어긋남) 이름만 보입니다.

도서관 목록 응답이 커집니다: 지금 약 671KB(압축 뒤 61KB)에서 압축 전 약 130KB 늘어날 것으로 봅니다(추정, dev가 잼). 지금 문서의 "대출 방식은 화면에 보내지 않음" 기록이 바뀝니다.

서버는 영어 값만 보내고, 우리말 글자는 화면이 바꿉니다. 글자를 고칠 때 화면만 고치면 됩니다.

다른 선택 — 서버가 "교보 · 소장" 글자를 만들어 보냄: 화면이 단순해지지만, 화면 문구가 서버에 들어가고 "같은 이름끼리 업체 이름순" 정렬에 값이 따로 필요합니다.

다른 선택 — 화면 종류만 보내고 화면이 업체를 계산: 대응표가 화면에도 생겨, 화면 종류가 늘 때마다 화면을 다시 배포해야 합니다.

추천: 값 세 개를 보냄.

직접 추가 이름 찾기는 화면(웹)에서만 바꿈 [안]

지금도 화면이 도서관 목록 전체를 받아 브라우저 안에서 찾습니다. 그래서 분류 글자도 찾게 하는 것(앞 페이지에서 정하심)은 화면 코드만 고치면 됩니다. 서버에 찾기 기능을 새로 만들지 않습니다.

찾기는 지금도 브라우저 안에서 합니다. 그래서 화면 코드만 고치면 되고, 서버에는 새 기능이 필요 없습니다.

추천: 화면에서만.

질문: 이 항목의 맥락

정하실 것은 "이름 찾기를 고칠 때 서버도 고치나, 화면만 고치나"입니다.

내 도서관 화면의 "직접 도서관 추가" 칸에 "동대문"을 치면 아래에 도서관 줄이 나옵니다. 지금 이 찾기는 이렇게 됩니다.

  1. 화면을 열 때 서버가 도서관 2,663곳 목록을 한 번에 보냄(GET /api/v1/libraries)
  2. 글자를 칠 때마다 서버에 묻지 않고, 브라우저가 받아 둔 목록에서 이름을 찾음

앞 페이지에서 "분류 글자도 찾게"(예: "동대문 yes24")를 정하셨습니다. 6번 제안대로 서버가 목록에 업체·대출 방식을 실어 보내면, 브라우저가 이름과 함께 그 글자도 보면 됩니다. 그래서 서버에 "도서관 찾기" 기능을 새로 만들 필요가 없습니다.

다른 선택 — 서버에 찾기 기능을 만듦: 글자를 칠 때마다 서버에 묻습니다. 목록 전체를 받지 않아도 되지만, 지금 방식(ADR-0058에서 정한 "목록을 한 번 받아 브라우저에서 찾기")을 바꾸게 되고 서버와 화면을 둘 다 고쳐야 합니다.
