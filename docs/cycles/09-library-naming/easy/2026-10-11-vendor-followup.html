업체 칸을 누가 채우나
역할을 나눠 다시 골라 주세요.

앞 페이지 1번(업체는 DB가 화면 종류에서 계산)에 "보통 칸에 수집 스크립트가 값을 쓰는 게 나은 것 같은데, 역할 분리를 잘 따져봐야 할 것 같아"라고 하셨습니다. 따져 본 결과 추천을 바꿉니다. 그리고 "나중에 새로운 도서관 유형이나 대출 방법이 생겨도 유동적이어야 해"라는 메모도 함께 봤습니다.

1지금 누가 무엇을 정하나

도서관에 대한 사실(화면 종류, 대출 방식)은 도서관 수집이 사이트를 열어 알아내고, seed 생성 스크립트가 서비스 DB로 옮깁니다. DB는 저장하고 확인만 합니다.

근거: docs/research/collection/1-libraries.md(도서관 수집의 확인 단계가 화면 종류·권수·교보 대출 방식을 정함). 주황 글씨가 이번에 고를 것입니다.

"화면 종류"는 서버가 사이트를 어떻게 읽을지 고르는 기술 값입니다(예: YES24는 화면이 세 가지라 V1·V2·V3). "업체"는 누가 운영하나라는 사실입니다. 지금은 화면 종류만 알면 업체가 정해지지만, 둘은 뜻이 다릅니다.

2두 안

업체도 대출 방식처럼 도서관 수집이 알아낸 사실로 두는 안(가)을 추천합니다. 새 업체나 새 화면이 생겨도 DB 계산식을 고치지 않아도 됩니다.

나중에 생기는 일(가) 수집이 정해 보통 칸에 씀(나) DB가 화면 종류에서 계산
같은 업체가 새 화면을 냄 (예: YES24_V4)수집이 업체 YES24로 적음. DB는 그대로DB 계산식에 한 줄 더하는 변경 파일
한 화면 종류를 다른 업체도 씀수집이 사이트마다 다르게 적음계산식으로는 나눌 수 없음. 칸을 바꿔야 함
새 업체허용 값에 하나 더함(변경 파일 한 줄)계산식과 화면 종류를 함께 고침
화면 종류와 업체가 어긋날 위험있음 → seed 생성 스크립트 테스트로 막음없음

(가) 업체는 도서관 수집이 정하고, seed 생성 스크립트가 보통 칸에 씀. DB는 허용 값만 확인 [안]

지금 있는 2,663곳은 이번 변경 파일이 화면 종류 대응표(교보 일반·교보 구독형 → 교보 등)로 한 번 채웁니다. 앞으로 새 도서관은 seed 생성 스크립트가 같은 대응표로 채우고, 사이트가 대응표와 다르면(다른 업체가 같은 화면을 씀 등) 도서관 수집이 따로 적은 값을 씁니다. DB는 업체 값이 6개(KYOBO 등) 중 하나인지만 확인합니다.

함께 바뀌는 것:

  • 대응표는 seed 생성 스크립트 한 곳에만 둡니다. DB에는 계산식이 없습니다.
  • 앞 페이지에서 승인하신 "통합 포털만 대출 방식을 비울 수 있음" 규칙은 "화면 종류가 통합 포털"이 아니라 "업체가 통합 포털"을 보게 맞춥니다.
  • spec R2 "업체는 화면 종류에서 정한다"는 "지금은 화면 종류 대응표로 정하고, 사이트가 다르면 도서관 수집이 따로 적는다"로 고칩니다.
  • seed 생성 스크립트 테스트에 "대응표와 다른 업체는 수집이 적은 곳뿐"을 더합니다.

추천: (가). 사용자 말씀대로 역할이 나뉘고(사실은 수집, 확인은 DB), 메모하신 "유동적"에 더 맞습니다. 처음 추천(나)에서 바꾼 이유는 이 두 가지입니다.

(나) 업체는 DB가 화면 종류에서 계산 (처음 제안) [안]

화면 종류와 업체가 절대 어긋나지 않습니다. 대신 새 업체·새 화면마다 DB 계산식을 고치는 변경 파일이 필요하고, 한 화면 종류를 두 업체가 쓰면 칸 방식을 바꿔야 합니다.

둘 중 하나만 승인하고 다른 하나는 미승인으로 보내 주세요.
