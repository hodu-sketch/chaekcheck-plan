## 배경
사용자가 원하는 책을 문장으로 쓰면 우리 DB의 책을 골라 질문에 맞춘 글과 함께 보여 주는 기능을 만든다(사이클 24). 서버가 외부 LLM을 실시간으로 부르는 것은 처음이다. 사이클 23이 같은 때 `picks`를 크게 고치고 있어 같은 코드를 함께 고치면 합칠 때 부딪힌다. 2026-10-17 결정 3번("vast.ai는 일괄로만, 서버가 실시간으로 부르지 않음")은 vast.ai에 대한 것이라 Haiku API 실시간 호출은 그 결정을 바꾸지 않는다.

## 결정
새 모듈 `aisearch`를 두고 `picks`에는 목록 책을 읽는 공개 API `ListedBooks` 하나만 더한다. 질문마다 Claude Haiku 5.5를 두 번 부른다(1차 질문 → 낱말, 2차 후보 → 고르기·글). LLM 호출은 `aisearch` 안 `LlmClient` 한 곳에서 JDK `HttpClient`로 Anthropic Messages API를 직접 부르고, 이번에는 Anthropic 구현만 둔다.

## 이유 (사용자 발언)
- "하이쿠로 일단 먼저 만들어 로컬 llm은 별개야" (2026-10-24)
- "일단 둘 다 되도록 해주고, haiku로 먼저 하고" (2026-10-23) — 부르는 곳 하나로 모으기
- 모듈·직접 요청 선택: "(가) 새 구역 aisearch", "(가) 직접 요청"을 고름 (2026-10-24, 설계 결정 #1·#5) — 이유는 말하지 않음 [이유 미확인]
- 두 번 호출: "(가) 낱말로 30권 (지금 안)" 선택 (2026-10-24, 명세 규칙 2차 #2), 질문 "우리서버에 낮말에 맞게 있어야 하는거네?"

## 검토한 대안
### A안: 새 모듈 `aisearch` (채택)
- 장점: 사이클 23과 겹치는 곳이 새 파일 둘. 찾는 범위를 넓힐 때 책 출처만 바꿈. 나중에 서비스로 나누기 쉬움
- 단점: 모듈 하나, `picks` 공개 API 하나
### B안: `picks` 안에
- 장점: 새 공개 API 없음
- 단점: 23과 같은 패키지를 동시에 고침, `picks`가 외부 LLM·요금까지 맡음
- 채택하지 않은 이유: [이유 미확인]
### C안: Anthropic 공식 Java SDK
- 장점: 스트림·재시도가 있음
- 단점: 의존이 늘고 새 매개변수를 따라오는지 확인 필요, 로컬 LLM은 다른 클라이언트
- 채택하지 않은 이유: [이유 미확인]
### D안: 목록 전체를 Haiku에 한 번에 (한 번 호출)
- 장점: 낱말이 달라도 놓치지 않음
- 단점: 한 번에 약 10배 비용, 목록이 커지면 안 됨
- 채택하지 않은 이유: [이유 미확인] (사용자는 "(가) 낱말로 30권"을 고름)

## 결과
- 좋아지는 점: 23과 따로 개발 가능. Ollama·vLLM(OpenAI 호환)을 나중에 `LlmClient` 구현 하나로 붙임
- 감수하는 점: Anthropic 스트림 해석을 직접 만들고 시험. 질문마다 Haiku 두 번(시간·비용)
- 나중에 되돌리거나 분리할 때: 모듈을 지우고 `aisearch` 스키마를 DROP. 나중에 분리할 때 `ListedBooks`를 REST 읽기로 바꾸고 표 둘을 들고 나감

# ADR-0151: 찾기용 한 줄 — 따로 넣는 명령 `book-texts`, `aisearch` 표의 사본에서 DB 낱말 맞추기

Status: Proposed
Date: 2026-10-24
Cycle: 24-ai-book-search
Supersedes: 없음

## 배경
AI 책 찾기는 지금 있는 추천목록 AI 요약(ADR-0142)과 별개로 책마다 "찾기용 한 줄"을 쓴다(spec R10). 한 줄은 PC에서 Haiku 배치가 원문으로 만들고 운영 DB에는 한 줄만 간다. 낱말을 맞출 글자(제목·저자는 `picks`, 한 줄은 `aisearch`)가 두 모듈에 나뉘어 DB 한 쿼리로 맞추면 모듈 경계를 넘는다. 사이클 23도 책마다 AI 글(탭 추천 글)을 PC에서 만들어 넣는다.

## 결정
`collection`에 따로 넣는 반영 모드 `book-texts`를 두고, TSV에 `kind` 칸을 두어 이번에는 `search_line`만 `aisearch`로 넘긴다(23의 글도 나중에 같은 명령에 실을 수 있게). 넣을 때 `ListedBooks`의 목록 책 전부의 제목·저자 사본과 한 줄을 `aisearch.search_book`에 함께 넣고, 낱말 맞추기는 이 표의 `search_text`(pg_bigm)에서 한다.

## 이유 (사용자 발언)
- "아니 지금 있는거랑 별개로해줘" (2026-10-24, 명세 규칙 #5)
- "따로 하고 나중에 23이랑 같이 되도록 설계" (2026-10-24, 설계 결정 #2)
- "추천도서가 중간에 바뀌기는 어렵고 일단 있는 것으로 해줘" (2026-10-24, 설계 결정 #3, DB에서 맞추기)

## 검토한 대안
### A안: 따로 넣는 명령 + DB 사본 맞추기 (채택)
- 장점: 한 줄만 고쳐도 몇 초에 다시 넣음. 23과 반영 파일 형식 번호가 부딪히지 않음. 메모리를 쓰지 않음
- 단점: 운영에서 명령 하나 더. 제목·저자 사본이 추천도서와 어긋날 수 있고, 새 목록 책은 다음 넣기까지 AI 찾기에 안 나옴
### B안: export/apply 반영 파일에 싣기
- 장점: 운영 할 일이 늘지 않음
- 단점: 무거운 카탈로그 반영 때만 바뀜, 형식 번호 3→4가 23과 부딪힐 수 있음
- 채택하지 않은 이유: [이유 미확인]
### C안: 빌드 리소스 파일
- 장점: 가장 단순
- 단점: 한 줄 바꿀 때마다 다시 배포, "한 줄만 운영 DB로"(R10-3)와 다름
- 채택하지 않은 이유: [이유 미확인]
### D안: 메모리 색인(제목·저자는 `ListedBooks`에서 바로)
- 장점: 사본이 어긋나지 않음, 경계를 지킴
- 단점: 서버 메모리 사용(2~3MB 추정)
- 채택하지 않은 이유: "추천도서가 중간에 바뀌기는 어렵고 일단 있는 것으로 해줘"

## 결과
- 좋아지는 점: 23의 탭 추천 글도 `kind`만 더해 같은 명령으로 넣을 수 있음
- 감수하는 점: 목록 책이 늘면(사서 월 1회, KAIST·노벨 `lists` 모드) 다시 넣어야 AI 찾기에 나옴
- 나중에 되돌리거나 분리할 때: 메모리 색인으로 바꾸려면 `search_book`의 사본 칸만 버림. 분리할 때는 넣는 명령이 `aisearch` 서비스의 가져오기 끝점으로 감

## 배경
질문에는 개인 사정이 섞일 수 있다. 질문을 주소에 넣으면 nginx 접속 기록과 Cloudflare에 남는다. 결과 화면은 ChatGPT처럼 대화로 이어서 묻는다. Haiku 비용과 남용을 막을 상한이 필요한데 서버는 1대다.

## 결정
질문은 `POST /api/v1/ai-searches/stream` 본문으로만 보내고, 서버는 질문 글과 대화를 저장하지 않는다. 대화는 브라우저 탭(sessionStorage)이 들고 다음 요청에 최근 5번(질문 + 보여 준 책 번호)을 보낸다. 같은 IP의 1분 10번·하루 100번은 서버 메모리에서 세고, 하루 $2 상한은 `aisearch.daily_usage`(날짜당 한 줄)에 적는다. 이용 기록 `usagelog.ai_search_event`에는 질문 글·IP·방문 번호·회원 번호 없이 횟수·시간·결과·후보 수·고른 책 번호·몇 번째 질문·토큰 수만 남긴다. 처리방침에는 Anthropic을 위탁 + 국외 이전으로 한 줄 적는다(사이클 16 Cloudflare와 같은 방식).

## 이유 (사용자 발언)
- 질문 글: "(나) 글은 빼고 횟수·시간·책 번호만" 선택 (2026-10-24, 범위 결정 #3) [이유 미확인]
- 주소: "(가) 주소에 넣지 않음" 선택 (명세 규칙 #1) [이유 미확인]
- 대화: "그리고 ai 책 검색칸 결과 ui는 마치 chatgpt처럼하고 질문을 연달아서 하는것이 가능했으면 해" (2026-10-24), "(나) 이 탭 안에서는 남음" 선택 (화면 흐름 #4)
- 값: "1분 10번 하루 100번 하루2달러로 업" (2026-10-24, 명세 규칙 #4)
- 세는 곳·기록 칸: "(가) IP는 메모리, 비용은 DB", "이대로" 선택 (설계 결정 #4·#7) [이유 미확인]
- 처리방침: "Cloudflare처럼 한 줄 적음" 선택 (명세 규칙 #7)

## 검토한 대안
### A안: IP는 메모리, 비용은 DB (채택)
- 장점: IP가 남지 않음, 재시작해도 하루 상한 유지, `usagelog.enabled`가 꺼져도 동작
- 단점: 재시작하면 IP 횟수는 처음부터
### B안: 둘 다 메모리
- 단점: 재시작하면 오늘 비용이 0이 되어 상한을 넘을 수 있음
- 채택하지 않은 이유: [이유 미확인]
### C안: 둘 다 DB
- 단점: IP를 DB에 적어 처리방침 항목이 늘어남
- 채택하지 않은 이유: [이유 미확인]
### D안: 질문을 주소에 넣음 (`?q=`)
- 장점: 새로 고침·공유 가능
- 단점: 접속 기록에 질문 글이 남음
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 질문 글이 우리 서버 어디에도 남지 않음
- 감수하는 점: 주소 공유·다른 기기에서 이어 보기 없음. 질문 글은 Anthropic(미국)으로는 감. 서버가 여러 대가 되면 IP 횟수를 공유 저장소로 옮겨야 함
- 나중에 되돌리거나 분리할 때: 상한을 세는 곳은 인터페이스(`AiSearchQuota`) 뒤라 구현만 바꿈

# ADR-0153: 답을 조금씩 흘리되 책 번호를 먼저 확인, 제목만 넣으면 제목 줄

Status: Proposed
Date: 2026-10-24
Cycle: 24-ai-book-search
Supersedes: 없음

## 배경
사용자는 답이 ChatGPT처럼 써지며 나오기를 바란다. LLM이 후보에 없는 책을 말하면 버려야 하는데, 글을 먼저 흘리면 버릴 책의 글이 잠깐 보일 수 있다. AI 탭에 책 제목만 넣는 사람도 있다.

## 결정
2차 Haiku 답을 구조화 출력(칸 모두 required → 차례 지킴)으로 받아, 책마다 번호가 오면 서버가 후보·중복을 확인하고 통과한 책만 `card` 이벤트를 보낸 뒤 그 책 글을 `card-delta`로 흘린다. 1차가 "제목·저자처럼 보임"을 돌려주면 `title-guess` 이벤트로 "「○○」을(를) 찾으시나요? [직접 찾기에서 보기]" 줄을 먼저 보내고 평소 답도 낸다. 서버는 `catalog`에서 제목을 따로 찾지 않고, 단추를 누르면 웹이 지금 직접 검색을 돌린다. 단추의 제목은 사용자가 쓴 글 안의 말만 쓴다.

## 이유 (사용자 발언)
- 흘리기: "(나) 글이 조금씩" 선택 (2026-10-24, 화면 흐름 #5; 추천 "(가) 한 번에"는 미승인) — 바탕 "결과 ui는 마치 chatgpt처럼"
- 제목: "ai검색인데 책이름을 그냥 넣었을 수 있으니까 그것 대비하고" (2026-10-24), "(가) 제목 줄 + 평소 답" 선택 (설계 결정 #6)

## 검토한 대안
### A안: 번호 먼저 확인 + 흘리기 (채택)
- 장점: ChatGPT처럼 보이면서 버릴 책은 화면에 나가지 않음
- 단점: 2차 JSON을 조각으로 읽는 작은 파서를 직접 만듦, 글 길이(300자)는 흐르는 중에 끊음
### B안: 답을 한 번에
- 장점: 만들기 쉬움
- 단점: 글이 써지는 모습이 없음
- 채택하지 않은 이유: 사용자가 "(나) 글이 조금씩"을 고름 [이유 미확인]
### C안: 제목이면 곧장 직접 검색
- 장점: 2차 비용 없음
- 단점: 제목처럼 보였지만 질문이었으면 AI 답을 못 봄
- 채택하지 않은 이유: [이유 미확인]

## 결과
- 좋아지는 점: 없는 책이 잠깐이라도 보이지 않음. 제목을 넣은 사람도 바로 직접 검색으로 갈 수 있음
- 감수하는 점: 스트림이 끊기면 앞 카드만 남음(`partial`). 단추를 누르면 그 제목은 지금 직접 검색처럼 주소에 들어감(사용자가 누른 것)
- 나중에 되돌리거나 분리할 때: 한 번에 내기로 바꾸려면 서버가 끝까지 모은 뒤 보내면 됨(이벤트 모양 그대로)

[안] #4 ADR-0153 초안을 이대로 씁니다.
