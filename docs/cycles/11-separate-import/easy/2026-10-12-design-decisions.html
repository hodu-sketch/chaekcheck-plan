1A. 파일 하나에 무엇이 들어가나

파일 안에는 새 책 표 네 개와 함께, "이 파일을 만들 때 내 PC 상태가 어땠나"를 적은 작은 표 하나가 들어갑니다. 운영은 표를 넣기 전에 이 작은 표만 먼저 읽어 두 DB가 같은지 봅니다.

1비교 값과 기록은 파일 안의 작은 표 load_manifest에 싣는다 [안]

이미 정하신 "파일 하나"를 지키면서, 운영 DB에 아무것도 넣기 전에 비교할 수 있는 방법입니다. 반영이 끝나면 이 작은 표는 지웁니다.

다른 선택: 덤프 옆에 JSON 파일을 하나 더 둠 — 읽기는 쉽지만 파일이 둘이 되어 "파일 하나" 결정과 어긋나고, 짝이 엇갈릴 수 있습니다.

추천: 파일 안의 작은 표.

질문 "실제 예시로 알려줘"에 대한 답

load_manifest는 줄이 딱 하나인 표입니다. 내 PC가 파일을 만들 때 이렇게 한 줄을 써 넣습니다. 숫자와 글자는 모두 설명용 예시입니다(책 수만 사이클 08 실제 값 1,615,125).

칸예시 값뜻
format_version1파일 형식 판. 나중에 형식이 바뀌면 2
export_id3f2c9a10-…-7b1e이 파일의 번호. 운영 기록과 내 PC 기록을 잇는 값
exported_at2026-10-12 21:40파일을 만든 때
book_count / book_max_id / book_sequence1,615,125 / 1,702,388 / 1,702,388내 PC의 지금(옛) 책 표: 책 수, 가장 큰 책 번호, 번호 시퀀스
holding_count / holding_max_id / holding_sequence17,714,665 / 20,551,020 / 20,551,020같은 것의 소장 표
notes{"library_hash":"9b07e4…","library_count":264, "link_hash":"51ac0d…","link_count":2738, "columns_hash":"e4d1…", "import":{…가져오기 기록…}}도서관 목록·연결표·표 구조 해시, 가져오기 기록

이 예처럼 운영에서 도서관을 하나 켰는데 내 PC는 그대로라면, 기록 줄은 이렇게 남습니다: status=FAILED, failure_reason=mismatch, failure_detail="library: 264≠265 (9b07e4…≠c41f9d…)". 운영 책 표는 그대로이고 검색도 옛 표로 계속됩니다. 운영자는 내 PC에도 같은 도서관 변경을 넣고 다시 가져오면 됩니다. 다섯 값이 모두 같으면 바로 파일을 넣기 시작합니다.

해시는 긴 목록을 짧은 지문 하나로 줄인 값입니다. 목록에서 한 글자만 달라도 완전히 다른 값이 나와서, 두 DB의 목록을 통째로 주고받지 않고도 같은지 알 수 있습니다.

2비교에 "책 표의 칸 구조"도 더한다(스펙에 없던 것) [안]

내 PC와 운영의 앱 판이 달라 책 표의 칸이 서로 다르면, 넣기는 되는데 운영 정의와 다른 표가 조용히 바꿔 끼워질 수 있습니다. 네 표의 (칸 이름, 타입) 목록을 해시로 비교해서 다르면 mismatch(표 구조)로 멈춥니다. 정하신 비교 항목(도서관·연결표·책 표 번호)에 하나를 더하는 것이라 여쭙니다.

다른 선택: 정한 세 가지만 비교. 앱 판을 늘 맞춰 돌린다는 절차에 기댑니다.

추천: 더함.

2A. 명령과 도구

지금 가져오기 명령에 "모드" 설정 하나를 더해, 내보내기·반영·마저 바꿔 끼우기·지우기를 고릅니다. pg_dump·pg_restore는 그 명령 안에서 Java가 불러, 실패와 걸린 시간까지 한 줄 기록에 남깁니다.

모드 (이름은 제안)어디서하는 일
in-place (기본)한 DB지금과 똑같이 가져오고 바로 바꿔 끼움
export내 PC가져오기 → 새 표 남김 → 파일
apply운영비교 → 넣기 → 색인·통계 → 바꿔 끼우기
finish내 PC운영이 성공한 뒤 남겨 둔 새 표로 바꿔 끼움
discard내 PC운영이 실패했을 때 남겨 둔 새 표를 지움

3명령은 지금 가져오기 하나에 모드 설정을 더하고(in-place·export·apply·finish·discard), 지금 방식(in-place)도 남긴다 [안]

예: --chaekcheck.collection.import.mode=apply --chaekcheck.collection.import.file=…. in-place를 남기면 개발 DB 하나로 시험하기 쉽습니다. 반영 명령은 운영 DB에 붙어 시작하므로, 운영 서비스와 같은 앱 판으로 돌려야 한다는 것을 절차 문서에 적습니다.

다른 선택: 프로필을 셋으로 나눔 — 같은 설정 파일이 셋으로 늘어납니다.

추천: 모드 설정 하나, in-place 남김.

질문 "정확히 어떤 명령어인거야?"에 대한 답

지금 가져오기 명령(dev docs/maintenance/3-import.md 32~37행)에 인자 두 개(mode, file)를 더하는 것이 전부입니다. dev backend 폴더에서 돌립니다. 설정 이름과 파일 경로는 제안입니다.

지금 (바뀌지 않음, in-place)

./gradlew bootRun -PbootRunXmx=6g --args='--spring.profiles.active=collection-import
  --chaekcheck.collection.import.sqlite-path=<사본 경로>
  --chaekcheck.collection.import.ttl-path=../data/nlk/ttl'

① 내 PC: 가져와서 파일 만들기

./gradlew bootRun -PbootRunXmx=6g --args='--spring.profiles.active=collection-import
  --chaekcheck.collection.import.sqlite-path=<사본 경로>
  --chaekcheck.collection.import.ttl-path=../data/nlk/ttl
  --chaekcheck.collection.import.mode=export
  --chaekcheck.collection.import.file=../data/export/catalog-2026-10-12.dump'

② 운영 역할 DB(5434)에 반영: 앱이 붙는 DB를 DB_PORT로 바꿉니다(dev application.yml이 ${DB_PORT:5432}를 씀). 묶기를 하지 않으므로 힙이 작아도 됩니다(512MB는 제안).

DB_PORT=5434 ./gradlew bootRun -PbootRunXmx=512m --args='--spring.profiles.active=collection-import
  --chaekcheck.collection.import.mode=apply
  --chaekcheck.collection.import.file=../data/export/catalog-2026-10-12.dump'

③ 내 PC: 운영이 성공했으면 마저 바꿔 끼우기 / ④ 실패했으면 지우기

./gradlew bootRun --args='--spring.profiles.active=collection-import
  --chaekcheck.collection.import.mode=finish
  --chaekcheck.collection.import.file=../data/export/catalog-2026-10-12.dump'

./gradlew bootRun --args='--spring.profiles.active=collection-import
  --chaekcheck.collection.import.mode=discard'

Java가 안에서 부르는 PostgreSQL 도구의 앞부분(4번 항목)은 설정 파일에 한 번 적어 둡니다. 예: chaekcheck.catalog.load.pg-restore-command = wsl -d Ubuntu --exec docker compose exec -T db-ops pg_restore …. 진짜 운영 서버에서는 ./gradlew bootRun 대신 만든 jar를 java -jar로 돌리고, 인자는 같습니다.

4pg_dump·pg_restore는 Java가 DB 컨테이너 안의 18판 프로그램을 불러 돌린다 [안]

DB 이미지가 postgres:18에서 만들어져 있어서 도구 판이 서버와 늘 같습니다. dev는 이미 컨테이너 안 psql을 같은 방식으로 부르고 있습니다. 엉뚱한 DB에 넣지 않도록, 넣은 뒤 파일 번호를 DB에서 다시 읽어 맞대 봅니다.

다른 선택: 운영자가 스크립트로 Java 단계 사이에 직접 돌림 — 명령이 셋으로 쪼개지고, 넣기 실패와 시간을 한 줄 기록에 남기기 어렵습니다. 또는 pg_dump 없이 Java가 자체 파일을 만듦 — 정하신 pg_dump -Fc를 다시 열어야 합니다.

참고: 파일을 표준 입력으로 넣으면 pg_restore -j(나눠 넣기)를 쓸 수 없습니다 — "The input must be a regular file or directory (not, for example, a pipe or standard input)", app-pgrestore.html (확인 2026-10-12). 시간 대부분이 소장 표 하나라 잃는 것은 작다고 봅니다. 시험에서 확인합니다.

추천: Java가 컨테이너 안 도구를 부름.

5catalog의 공개 기능은 지금 CatalogLoad 하나에 더한다(만들기·내보내기·읽기·기준값·반영·마저·지우기) [안]

"남겨 둔 새 표"라는 상태를 다루는 코드가 한 곳에 모입니다. 쓰는 곳은 collection 하나라 나중에 나누기도 쉽습니다.

다른 선택: 옮기기(내보내기·읽기·반영)만 새 기능 묶음으로 떼어 냄 — 나뉘어 보이지만 같은 상태를 두 곳이 다룹니다.

추천: 하나에 더함.

질문 "CatalogLoad는 어디에 있는데?"에 대한 답

CatalogLoad는 dev backend/src/main/java/com/chaekcheck/catalog/CatalogLoad.java에 있는 Java 인터페이스입니다. 인터페이스는 "이런 일을 해 줄 수 있다"는 약속만 적은 파일이고, 실제로 일하는 코드는 따로 있습니다. catalog 모듈의 맨 위 폴더에 있어서 다른 모듈이 불러도 되는 공개 창구입니다(모듈 규칙: 맨 위 폴더 = 공개, internal 폴더 = 바깥에서 못 씀).

지금 이 약속에는 기능이 하나뿐입니다: replaceAll(source, loader) — "책을 다 받아서 새 표에 쓰고 바꿔 끼운다". CatalogImporter가 가져오기 끝에서 이걸 한 번 부릅니다(CatalogImporter.java 120~134행). 제안은 같은 약속에 기능 일곱 개를 더하는 것입니다.

더할 기능 (이름은 제안)쉬운 뜻쓰는 모드
prepare새 표를 만들고 바꿔 끼우지 않고 남김export
export남긴 새 표를 파일로export
readManifest파일 속 작은 표만 읽음(DB는 안 건드림)apply, finish
baseline이 DB 책 표의 기준값(수·가장 큰 번호·시퀀스)apply, finish
apply파일을 넣고 색인·통계·바꿔 끼우기apply
finishPrepared남겨 둔 새 표로 바꿔 끼우기finish
discardPrepared남겨 둔 새 표 지우기discard

"하나에 더한다"는 이 일곱 개를 새 창구로 떼지 않고 지금 CatalogLoad에 같이 둔다는 뜻입니다. 실제 일하는 JdbcCatalogLoad는 지금의 긴 순서를 단계별로 쪼개서 이 기능들이 나눠 씁니다.

3A. 기록과 남겨 둔 새 표 지키기

기록은 "그 DB의 책 표가 바뀌었을 때 한 줄"이라는 지금 뜻을 지킵니다. 그리고 내 PC에 남겨 둔 새 표는 실수로 지워지지 않게 막습니다.

6내 PC에 "기다리는" 새 표가 있으면 다음 가져오기·내보내기는 시작하지 않고 "먼저 finish 또는 discard"를 알린다 [안]

운영에 넣은 파일의 짝을 실수로 지우면, 운영만 새 표가 되어 다음 가져오기가 mismatch로 막힙니다. 이걸 미리 막습니다. 파일 기록이 없는 새 표(지난 실행이 도중에 죽고 남은 것)는 지금처럼 지우고 시작합니다.

다른 선택: 지금처럼 늘 지움. 실수하면 같은 파일을 내 PC에도 반영해서 되살려야 합니다.

추천: 막음.

7기록은 운영에 반영마다 한 줄, 내 PC에는 finish가 끝났을 때 한 줄을 남기고, 두 줄을 파일 번호(export_id)로 잇는다. 내보내기만 했을 때는 줄을 남기지 않는다 [안]

가져오기 기록 표에 칸 두 개(export_id, exported_at)를 더합니다. 성공·실패 값 목록은 그대로이고, 실패 이유 mismatch는 표를 고치지 않고 더할 수 있습니다(지금 값 제한이 없음, dev 코드 확인).

다른 선택: 내보낼 때도 "EXPORTED" 줄을 남김 — 내 PC에서 바로 숫자를 보지만, 상태 값 목록을 바꾸고 "책 표가 안 바뀌었는데 줄이 있음"이라는 새 뜻이 생깁니다.

추천: 이렇게.

4B. 힙 줄이기 세부

세 방식을 하나의 틀(인터페이스)에 꽂아 설정으로 고릅니다. 정할 것은 설정 이름 자리, compact의 묶음 열쇠, sql의 임시 표 자리입니다.

8묶는 방식 설정은 chaekcheck.collection.import.grouping에 둔다 [안]

앞서 "설정 이름은 dev가 chaekcheck.catalog.load.*에 맞춰 정함"으로 정하셨는데, 묶기는 가져오기를 돌리는 collection의 일이고 catalog.load는 책 표 쪽 설정입니다. "같은 꼴로 맞춘다"로 읽고 collection 자리에 두자는 제안입니다.

다른 선택: 글자 그대로 chaekcheck.catalog.load.grouping — collection이 남의 설정 자리를 읽게 됩니다.

추천: collection 자리.

9compact의 묶음 열쇠는 128비트 숫자(해시 두 개)로 바꾼다 [안]

지금은 "SHARED" + 구분문자 + 책 코드 같은 글자 760만 개를 열쇠로 들고 있습니다. 이걸 숫자로 바꾸면 글자가 힙에서 빠집니다. 서로 다른 열쇠가 같은 숫자가 될 확률은 760만 개에서 약 10-25입니다(Claude 계산). 만에 하나 생겨도 결과 비교(다른 책 0권)에서 잡힙니다.

다른 선택: 숫자로만 된 책 코드는 숫자 그대로(겹침 없음), 나머지는 글자로. 정확하지만 코드가 두 갈래이고, 숫자 코드 비율을 몰라 효과를 미리 알 수 없습니다.

추천: 128비트 숫자.

10sql의 임시 표는 가져오기가 연 연결의 임시(TEMPORARY) 표로 둔다 [안]

연결이 끊기면 저절로 지워져서 도중에 죽어도 남지 않고, 다른 모듈 표와 섞이지 않습니다. 줄 약 1,770만 개에 정리값까지 실어 디스크를 수 GB 쓸 것으로 보고, 측정에서 잽니다.

다른 선택: collection 스키마의 로그 없는(UNLOGGED) 표 — 측정 중에 크기를 들여다보기 쉽지만, 죽으면 남아서 다음 실행이 지워야 합니다.

추천: 임시 표.

11결과 비교 도구: dry run이 책 목록·줄 목록 파일을 남기고 스크립트가 비교, 번호는 방식마다 내보내기 → 번호 뽑기 → 지우기로 비교 [안]

EC2 질문 때 찾은 것: 사이클 08은 색인 메모리 1GB로 돌았는데, 운영 DB 상한(1GB)과 같아 그대로 쓰면 안 됩니다. 이 사이클 시험에서 상한을 실제로 걸고 잽니다.

12반영 명령은 maintenance_work_mem=256MB로 돌리고, 운영 역할 DB(5434) 컨테이너에 메모리 상한 1GB를 실제로 건다. 운영 역할 DB는 처음에 지금 DB를 통째로 복사해 시작한다 [안]

병렬 색인 작업자를 늘려도 이 메모리 값은 명령 전체에 한 번만 적용됩니다(PostgreSQL 문서). 지금까지 dev 측정은 컨테이너 상한 없이 한 것이라, 상한을 건 채로 색인 시간이 얼마나 늘어나는지 봅니다. 처음 복사는 2026-10-05에 5434 복사본을 만든 방법과 같습니다.
