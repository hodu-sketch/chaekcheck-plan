사이클 11 스펙: 여쭤볼 것 12가지

dev 코드와 공식 문서를 확인하고 스펙 초안(spec.md)을 썼습니다. 이 페이지는 그 안의 제안을 하나씩 정하는 곳입니다. 새 화면은 없고, "운영자"는 가져오기를 돌리는 사용자 본인입니다. (2026-10-12)

1전체 순서 한눈에

내 PC에서 가져와 파일로 내보내고, 운영 역할 DB가 먼저 두 DB가 같은지 확인한 뒤 넣고 바꿔 끼웁니다. 운영이 성공하면 내 PC도 바꿔 끼웁니다.

④~⑥은 사이클 08의 마지막 단계와 같아서 그 코드를 다시 씁니다. 새로 만드는 것은 ②, ③, ⑦과 명령 두 개(내보내기, 반영)입니다.

2번호를 어디서 매기나

dev 코드를 보니, 책·소장 번호를 잇는 단계가 "지금 그 DB에 있는 책 표"를 직접 읽습니다. 그래서 내 PC에서 번호를 매기면 내 PC의 책 표가 운영과 같아야 합니다.

번호를 잇는 단계는 새로 읽은 소장마다 (도서관, 책 코드)가 같은 옛 소장을 찾아 그 번호와 책 번호를 그대로 씁니다. 없으면 가장 큰 번호 다음부터 줍니다(JdbcCatalogLoad.java Ids.decide, ADR-0062·0070).

1번호 잇기는 내 PC에서 하고, 내 PC 책 표가 운영과 같아야 한다는 조건을 둔다 [안]

운영 서버가 하는 일이 가장 적고(넣기·색인·바꿔 끼우기), 지금 코드를 거의 그대로 씁니다. 조건이 깨지는 경우는 다음 2번과 3번이 막습니다.

다른 선택(2-나): 번호 잇기를 운영으로 옮김. 내 PC 책 표가 달라도 되지만, 운영에서 번호 잇기·쓰기(#2 기준 약 5분, 임시 표 포함)를 해야 하고 가져오기 코드를 둘로 쪼개야 합니다.

추천: 내 PC에서 (2-가).

3내 PC는 언제 바꿔 끼우나

내 PC 책 표가 운영과 계속 같으려면, 내 PC도 운영과 같은 표로 바꿔 끼워야 합니다. 문제는 순서입니다.

2내 PC의 바꿔 끼우기는 운영 반영이 성공한 뒤에 하고, 그때까지 내 PC의 catalog_next를 남겨 둔다 [안]

운영 반영 명령이 성공하면, 운영자가 내 PC에서 "마저 바꿔 끼우기" 명령을 한 번 더 돌립니다. 운영이 실패하면 내 PC의 catalog_next만 지우면 두 DB가 그대로 같습니다.

다른 선택: 내보내기 때 내 PC를 바로 바꿔 끼움. 명령이 하나 줄지만, 운영이 실패하면 내 PC가 앞서 나가 다음 가져오기 전에 되돌려야 합니다(옛 표는 이미 지워져 되돌릴 수 없음).

추천: 운영 성공 뒤.

4두 DB가 같은지 무엇으로 보나

이미 정하신 것: 다르면 반영하지 않고 이유를 기록합니다. 정할 것은 비교하는 값입니다.

비교할 것왜방법 (제안)
도서관 목록 (켜진 곳의 번호·주소·업체 종류)가져오기가 켜진 도서관만 읽고, 주소가 다르면 건너뜀내용 해시 하나
collection_link (서비스 ↔ 수집 도서관 번호)사본의 도서관을 서비스 도서관에 잇는 표내용 해시 하나
책 표 (book, holding)번호 잇기가 읽음(2번 카드)줄 수, 가장 큰 번호, 번호 시퀀스 값

3도서관 목록과 collection_link는 내용 해시로, 책 표는 줄 수·가장 큰 번호·시퀀스 값으로 비교하고, 다르면 실패 이유 mismatch와 다른 항목을 기록한다 [안]

내 PC가 이 값들을 파일에 함께 싣고, 운영이 자기 값과 맞대 봅니다. 책 표를 내용 해시로 하지 않는 것은 소장이 수백만 줄이라 시간이 들기 때문입니다. 운영에서 책 표를 직접 고치지 않는다는 전제에서는 줄 수·번호로 충분합니다.

다른 선택: 책 표도 내용 해시. 가장 확실하지만 반영할 때마다 소장 전체를 읽습니다(시간은 재 봐야 앎). 더 가벼운 선택: Liquibase 변경 기록(databasechangelog)만 비교. 빠르지만 손으로 고친 것은 못 잡습니다.

추천: 위 제안.

5옮기는 방법과 기록

내 PC의 catalog_next 스키마를 통째로 떠서 운영에 넣으면, 운영에서도 그대로 catalog_next에 들어갑니다. 스키마 이름을 바꿀 필요가 없습니다.

근거: pg_restore에는 복원하면서 스키마 이름을 바꾸는 옵션이 없습니다(PostgreSQL 18 문서에 해당 옵션 없음). 그래서 이름을 바꾸지 않아도 되는 이 방법이 맞습니다. postgresql.org/docs/18/app-pgrestore.html (확인 2026-10-12)

4파일은 pg_dump 사용자 지정 형식(-Fc) 하나로 만든다 [안]

파일 하나라 옮기기 쉽고, 기본으로 압축됩니다. 복원도 pg_restore -j로 여러 작업을 나눠 돌릴 수 있습니다.

다른 선택: 디렉터리 형식(-Fd). 내보내기도 나눠 돌릴 수 있어(pg_dump -j는 이 형식만 됨) 빠를 수 있지만, 파일이 폴더째라 옮기기가 번거롭습니다. 측정에서 느리면 그때 바꿉니다.

근거: "custom-format archive … compressed by default", "-j … only use this option with the directory output format" — app-pgdump.html (확인 2026-10-12)

추천: -Fc.

5운영 반영 순서: 남은 catalog_next 지우기 → 파일 넣기 → 색인·제약(운영 정의를 읽어) → 통계 → 바꿔 끼우기 [안]

맨 앞의 지우기는 지난 반영이 도중에 죽어 빈 catalog_next가 남았을 때를 위한 것입니다(사이클 08과 같은 방식). 바꿔 끼우기 잠금 값(2초, 10초, 5번)은 사이클 08 그대로입니다.

추천: 이 순서.

6운영 DB 가져오기 기록은 한 줄: 내 PC 기록(책·소장 수, 수집 기간, 단계 시간)을 파일에 실어 보내고, 운영이 반영 단계 시간(넣기·색인·통계·바꿔 끼우기)과 결과를 더해 남긴다 [안]

예: 운영 기록 한 줄에 "읽기 13분 … 쓰기 2분 27초 | 넣기 ?분, 색인 1분 39초, 통계 43초, 바꿔 끼우기 0.2초, 성공"이 함께 있습니다. 내 PC에도 자기 기록이 남습니다.

다른 선택: 운영에는 반영 결과만 남김. 단순하지만 운영에서 "언제 수집한 것이 들어왔나"를 보려면 내 PC를 봐야 합니다.

추천: 한 줄에 함께.

7운영 역할 DB는 compose 서비스를 하나 더 만든다(같은 이미지, 자기 볼륨, 포트 5434) [안]

dev가 2026-10-05에 포트 5434로 복사본 DB를 쓴 적이 있습니다. 진짜 서버처럼 따로 된 DB라, 메모리 설정도 따로 줄 수 있습니다.

다른 선택: 지금 DB 안에 데이터베이스를 하나 더(CREATE DATABASE). 더 간단하지만 두 DB가 메모리를 같이 써서, 반영할 때 내 PC 가져오기와 섞여 측정이 흐려집니다.

추천: 서비스 하나 더.

6힙 줄이기: SQL 방식을 어디까지 SQL로

글자를 정리하는 Java 코드(제목·출판사 정리, 저자 나누기 등)를 SQL로 다시 쓰면 결과가 달라지기 쉽습니다. 정리는 Java에 두고, 메모리를 많이 먹는 "묶기"만 SQL로 옮기는 것을 제안합니다.

8sql 방식은 글자 정리를 Java가 줄마다 해서 임시 표에 넣고, 묶기·이어 붙이기·대표값 고르기만 SQL로 한다 [안]

Java는 줄을 읽어 정리한 뒤 바로 DB로 보내고 들고 있지 않으므로 힙이 작습니다. 정리 규칙이 한 곳(Java)에만 있어, 세 방식의 결과가 같기 쉽습니다.

다른 선택: 정리까지 모두 SQL. Java가 거의 일을 안 하지만, 저자 나누기(역할어 약 30개, 별칭, "외 N명")를 SQL로 다시 써야 하고 Java와 PostgreSQL의 정규식 차이(공백 문자 범위 등)로 결과가 달라질 위험이 큽니다.

추천: 정리는 Java, 묶기만 SQL.

9가장 많은 값이 동점이면 지금과 같은 값을 고른다: SQL에서는 mode()를 쓰지 않고 개수 큰 순 + 글자 순(C 정렬)으로 고른다 [안]

PostgreSQL의 mode()는 동점일 때 "임의로 첫 번째"를 고른다고 문서에 적혀 있어, 지금 Java(동점이면 작은 값)와 같은 결과를 보장하지 못합니다. 이모지 같은 드문 글자에서 Java와 DB의 글자 순서가 다를 수 있는데, 그건 결과 비교에서 잡습니다.

근거: mode() "arbitrarily choosing the first one if there are multiple equally-frequent values" — functions-aggregate.html; C 정렬은 "byte values" 순 — collation.html; Java String.compareTo는 UTF-16 글자 단위 — String (Java 25) (모두 확인 2026-10-12)

추천: 이렇게.

7결과 비교와 측정에 더할 것

세 방식의 결과 비교와 여섯 관점 측정은 이미 정하셨습니다. 그 세부 두 가지와, 코드 없이 잴 수 있는 Java 옵션 두 개를 제안합니다.

10결과 비교에서 "새로 생긴 책의 번호 순서"는 보지 않는다 [안]

있던 책은 옛 번호를 그대로 받으니 세 방식이 같아야 합니다. 새 책은 가장 큰 번호 다음부터 받는데, 방식마다 새 책을 처리하는 순서가 달라 번호가 서로 바뀔 수 있습니다. 예: current에서 새 책 X가 100번, Y가 101번인데 sql에서는 반대. 책 내용과 묶음이 같으면 통과로 봅니다.

다른 선택: 새 책 번호까지 같아야 통과. sql에서 처리 순서까지 맞추는 일이 더해집니다.

추천: 보지 않음.

질문 "어느 방식마다?"에 대한 답 — 그리고 제안을 바꿉니다

"순서"는 가져오기가 책을 만드는 순서입니다. 방식마다 이렇게 됩니다.

방식책을 만드는 순서
current그 책의 첫 줄을 사본에서 읽은 순서 (BookGrouping이 "첫 줄 순서"로 내놓음)
compact같은 Java 묶기를 쓰므로 current와 같음
sql따로 정하지 않으면 DB가 편한 순서. 줄마다 읽은 순번을 같이 넣고 "첫 줄 순번" 순으로 꺼내면 current와 같아짐

다시 코드를 보니 이 순서는 새 책 번호만이 아니라 있던 책의 번호에도 닿습니다. 옛 책 하나의 소장이 새 책 둘로 똑같이 나뉘면(동점), 먼저 만든 책이 옛 번호를 받습니다(JdbcCatalogLoad.java 546행, 554행). 그래서 순서가 다르면 드물게 "같은 책인데 번호가 다름"이 생깁니다.

책 번호와 숫자는 설명용 예시입니다. 순서가 바뀌면 B가 7번을 받습니다.

바꾼 제안: 세 방식 모두 "첫 줄을 읽은 순서"로 책을 만들고, 결과 비교에서 번호까지 같아야 통과로 봅니다. sql에 순번 하나를 더 싣는 작은 일입니다. 이쪽이 낫다고 봅니다. #10을 미승인으로 보내 주시면 이 바꾼 제안으로 적용하겠습니다(원래 제안대로 하시려면 승인).

11current에 Java 옵션 두 개를 붙인 경우도 함께 재고, GC 기록을 켠다 [안]

옵션하는 일근거
-XX:+UseStringDeduplication같은 글자를 담은 문자열이 글자 배열 하나를 같이 쓰게 함. 기본은 꺼짐JEP 192
-XX:+UseCompactObjectHeaders객체마다 붙는 머리를 96~128비트에서 64비트로. Java 25에서 정식, 기본은 꺼짐. 문서: 객체당 평균 4바이트 줄어듦JEP 519
-Xlog:gcGC 기록을 남겨 힙 사용량을 봄(지금은 꺼져 있음)JEP 158

dev는 Java 25를 쓰므로 명령에 붙이기만 하면 됩니다. 객체 머리 줄이기는 지금 방식처럼 객체가 많을 때(묶음 760만 × 개수표 6개 등) 효과가 있을 수 있습니다. 얼마나 줄지는 재 봐야 압니다. 사이클 08에서는 글자 합치기 옵션을 재지 않았습니다.

다른 선택: 세 방식만 잼. 측정 횟수가 줄지만, 코드를 안 바꾸고 얻을 수 있는 효과를 놓칩니다.

추천: 함께 잼 (방식 셋 + 옵션 두 경우).

12반영하는 동안 운영 검색 기준: 기다린 시간 1초 안, 서버 오류 0 [안]

사이클 08 가져오기에서 기다린 시간은 0.1~0.3초, 서버 오류 0이었습니다. 반영은 그중 마지막 단계와 같으므로 같은 수준을 기대하고, 여유를 두어 1초로 잡습니다.

추천: 1초 안, 오류 0.
