1운영 쪽을 어디서 시험할지 다시 여쭙니다

앞 페이지 #1을 미승인하셨는데, 사유 칸에 추천 문구("같은 PC의 두 번째 DB. 배포 보류 결정을 바꾸지 않습니다")가 그대로 들어와 있어 뜻을 알 수 없었습니다. 둘 중 하나만 승인해 주세요.

파일 내보내기 → 넣기 → 바꿔 끼우기를 모두 시험할 수 있습니다. 진짜 서버로 갈 때는 파일을 보내는 곳만 바뀝니다. 배포 보류(백로그 208행)는 그대로입니다.

못 보는 것: 인터넷으로 파일을 보내는 시간, 운영 서버 사양에서 색인을 만드는 시간.

2묶는 방식을 설정으로 고르기

가져오기를 시작할 때 설정 값 하나로 묶는 방식을 고릅니다. 지금 방식도 남겨 두어, 새 두 방식의 결과가 맞는지 비교하는 기준으로 씁니다.

설정 값 (이름은 제안)방식힙 (dev 예상)
current지금 방식. 비교 기준6GB (4GB는 멈춤)
compact안 2: 겹치는 글자 합치기(안 1) + 개수표를 묶음 안의 칸으로 + 묶음 열쇠를 숫자로3GB 안팎
sql안 3: 줄을 임시 표에 넣고 DB(SQL)에서 묶기몇백 MB

2설정 값은 current·compact·sql 셋, 측정이 끝날 때까지 기본값은 current [안]

예를 들어 가져오기 명령에 --chaekcheck.catalog.import.grouping=sql처럼 붙이면 안 3으로 돌고, 아무것도 안 붙이면 지금 방식으로 돕니다. 설정 이름은 dev가 기존 설정(chaekcheck.catalog.load.*)에 맞춰 정합니다.

다른 선택: 지금 방식은 빼고 compact·sql 둘만. 코드는 줄지만, 새 방식의 결과가 맞는지 비교할 기준과 문제가 생겼을 때 되돌아갈 곳이 사라집니다.

추천: 셋. 기본값은 측정 뒤에 정합니다(아래 5번).

3세 방식의 결과가 같은지 확인하기

방식이 달라도 만들어지는 책은 한 권도 달라지면 안 됩니다. 달라지면 그 책의 번호가 바뀌기 때문입니다(ADR-0062 책 번호 잇기).

3같은 사본으로 세 방식을 돌려 책마다 비교하고, 다른 책이 한 권이라도 있으면 그 방식은 쓰지 않음 [안]

비교하는 것은 어떤 줄들이 한 책이 됐는지, 책마다 고른 제목·저자·출판사·출판일·ISBN·콘텐츠 종류, 그 책을 가진 도서관 목록입니다. 다른 책이 있으면 예시 목록을 남겨 dev가 고칩니다. 책 표에 쓰지 않고 묶기까지만 하는 시험 실행(dry run)이 이미 있어서 그것을 씁니다.

다른 선택: 책 수만 같으면 통과. 빠르지만, 수는 같아도 다른 책끼리 묶였으면 놓칩니다.

추천: 책마다 비교.

4무엇을 잴지 (여러 관점)

메모리만 보면 안 3이 이기지만, 안 3은 DB에 일을 더 시킵니다. 그래서 시간·DB 디스크·검색 영향까지 같이 잽니다.

관점재는 것왜
메모리Java 힙 최고 사용량(GC 기록), 힙을 6→4→3→2→1GB로 줄여 가며 끝까지 되는 가장 작은 값목표 그 자체. "줄였다"를 숫자로
시간전체 시간, 단계별 시간(step_seconds)메모리를 줄이고 느려지면 안 됨. 지금 약 33분(#3c)
DB 디스크DB 크기 최대(pg_database_size), DB가 임시 파일로 쓴 양(temp_bytes)안 3은 메모리 대신 디스크를 씀
CPUJava와 DB 각각의 CPU 시간안 3은 일을 DB로 옮김
검색 영향가져오는 동안 검색 응답 p95·오류(사이클 08 측정 스크립트 probe_during_import.py)같은 PC에서 돌면 DB가 바빠져 검색이 느려질 수 있음. 사이클 08은 p95 560ms
결과3번 카드의 책마다 비교한 권도 달라지면 안 됨

근거: temp_bytes는 PostgreSQL 통계 표 pg_stat_database의 칸으로, 이 DB에서 질의가 임시 파일에 쓴 데이터 총량입니다. postgresql.org/docs/18/monitoring-stats.html (확인 2026-10-11).

4위 여섯 관점을 세 방식 모두 같은 사본·같은 PC에서, 방식마다 두 번씩 잼 [안]

두 번씩 재는 것은 한 번만 재면 우연히 빠르거나 느린 것을 가려낼 수 없어서입니다. 힙을 줄여 가며 재는 것은 끝까지 되는 값을 찾을 때까지만 합니다. 결과는 표 하나(방식 × 관점)로 받습니다.

다른 선택: 한 번씩만. 측정 시간이 반으로 줄지만(가져오기 한 번이 30분 안팎), 차이가 작을 때 판단하기 어렵습니다.

추천: 두 번씩.

5측정 뒤 기본값을 고르는 기준

측정이 끝나면 기본값을 하나로 정합니다. 기준을 미리 정해 두면 결과를 보고 바로 고를 수 있습니다.

5결과 비교를 통과한 방식 중, 전체 시간이 지금보다 10분 넘게 늘지 않고 힙이 가장 작은 것을 기본값으로 [안]

예를 들어 sql이 힙 500MB인데 50분이 걸리면(17분 늘어남) 기본값이 되지 않고, compact가 3GB에 36분이면 compact가 기본값이 됩니다. 숫자는 설명용 예시입니다. 검색 영향(p95)이 사이클 08보다 눈에 띄게 나빠지면 그것도 따로 보고드립니다.

다른 선택: 기준 없이 측정 결과를 보고 그때 정하기. 지금 정할 것은 없지만, 결과가 애매하면 결정 페이지가 한 번 더 필요합니다.

추천: 이 기준. "10분"은 제 제안 값이라 바꾸셔도 됩니다.

질문 "지금은 얼마나 걸려"에 대한 답

지금 방식(current)은 사이클 08 마지막 가져오기(#3c)에서 전체 약 33분이었습니다(dev 최종 요약). 그 전 #2는 약 41분이었고, 국가서지를 원본 파일 대신 DB에 남겨 둔 표에서 읽게 되면서(7분 55초 → 2분 46초) 줄었습니다. 그래서 이 기준대로면 43분 안에 끝나는 방식만 기본값 후보가 됩니다.

#3c의 단계별 시간은 아직 받지 못했습니다. dev docs/plan-feedback.md 최종 요약을 retro 때 읽고 맞춥니다. 10분 대신 비율(예: 지금의 1.3배 이내)로 정해도 됩니다. 원하시면 기타에 적어 주세요.

6사이클이 커졌습니다: 순서

사이클 11에 큰 일이 둘 들어왔습니다. 따로 하기(내보내기·반영)와 힙 줄이기(두 방식, 검증, 측정)입니다. 서로 기다릴 필요는 없습니다.

6한 사이클로 두되, 인계서를 A(따로 하기) → B(힙 줄이기) 두 묶음으로 나눔 [안]

A는 사이클 08의 바꿔 끼우기 코드를 다시 써서 비교적 작고, 끝나면 사이클 목표가 먼저 이루어집니다. B는 측정에 가져오기를 여러 번(방식 셋 × 두 번 + 힙 줄여 가기) 돌려야 해서 오래 걸립니다.

다른 선택: B를 사이클 12로 떼기. 사이클은 작아지지만 "이 사이클에 넣어 달라"는 말씀과 다릅니다. B 먼저: 힙이 먼저 줄지만 사이클 목표(따로 하기)가 늦어집니다.

추천: 한 사이클, A → B.
