사이클 11: 가져오기 따로 하기

무거운 가져오기는 내 PC에서 하고, 다 만든 책 표 네 개만 운영 서버로 옮겨 바꿔 끼웁니다(dev 의견). 그러면 가져오기 41분 중 약 39분과 힙 6GB가 운영 서버에서 빠집니다. 정할 것은 맨 아래 7번 카드의 네 가지입니다. (2026-10-11)

1지금은 PC 한 대가 가져오기와 검색을 다 합니다

지금 가져오기는 검색 서비스가 쓰는 그 DB에서, 처음부터 끝까지 한 번에 돕니다.

"가져오기"는 수집해 둔 전자책 목록 사본과 국가서지 파일을 읽고, 같은 책끼리 묶어서, 서비스가 검색하는 책 표를 새로 만드는 일입니다.

가져오기 프로그램은 새 표를 준비용 자리(catalog_next)에 만들고, 다 되면 옛 표를 지우고 새 표를 제자리(catalog)로 옮깁니다. 이 마지막 순간이 "바꿔 끼우기"입니다. 그동안 검색 서비스는 옛 표를 계속 읽습니다.

옮기는 표는 네 개입니다. book(책), book_contributor(지은이 등), holding(어느 도서관이 어떤 책을 가졌는지), catalog_library_snapshot(가져오기에 들어간 도서관 목록).

41분이 어디에 쓰이나 (가져오기 #2, 2026-10-11)

dev가 잰 단계별 시간(step_seconds)을 묶어 그렸습니다. 시간 대부분이 읽기와 묶기에 쓰입니다. 사이클 08 마지막 가져오기(#3c)는 국가서지를 원본 파일 대신 DB에 남겨 둔 표에서 읽어(7분 55초 → 2분 46초) 전체 약 33분, 검색이 기다린 시간 0.13초였습니다.

바꿔 끼우는 동안 DB 크기

바꿔 끼우기 전까지는 책 표가 두 벌이라 DB가 약 2.2배까지 커집니다.

2힙 6GB는 "묶음" 760만 개 때문입니다 (실제 코드)

가져오기 프로그램은 첫 읽기에서 묶음을 760만 개 만들고, 묶음마다 개수표 6개와 도서관 목록을 끝까지 메모리에 들고 있습니다.

"힙"은 Java 프로그램이 데이터를 들고 있는 메모리입니다. "묶음"은 수집한 줄 가운데 같은 책 코드를 가진 줄끼리 모은 것입니다. 교보·YES24는 도서관이 달라도 코드가 같으면 한 묶음이고, 나머지 업체는 같은 도서관 안에서만 묶습니다.

줄 세 개가 묶음 하나가 되는 모습 (값은 설명용 예시)

줄 세 개를 그대로 들고 있지 않고, 칸마다 "어떤 값이 몇 줄"인지만 셉니다. 나중에 책을 쓸 때 칸마다 가장 많이 나온 값을 고릅니다(위 예에서 저자는 "김"). 줄을 다 들고 있지 않으려고 이렇게 했습니다(ADR-0054, 코드 주석).

dev backend/src/main/java/com/chaekcheck/collection/internal/importer/BookGrouping.java 59~86행 (설명에 필요 없는 줄은 뺌)

Votes가 "개수표" 하나입니다. 묶음 하나에 new Votes가 6번, 곧 따로 된 Java 객체가 6개 생깁니다.

같은 파일 92~117행: 개수표 하나의 생김새

static final class Votes<T> {
    private T first;              // 처음 본 값
    private long firstCount;      // 그 값이 몇 줄
    private Map<T, Long> more;    // 다른 값이 나올 때만 만드는 표

    void add(T value) {
        if (first == null) { first = value; firstCount = 1; }
        else if (first.equals(value)) { firstCount++; }
        else { // 값이 둘 이상일 때만
            if (more == null) more = new HashMap<>(4);
            more.merge(value, 1L, Long::sum);
        }
    }
}

대부분의 묶음은 칸마다 값이 하나라서 first와 firstCount만 씁니다. 위 예의 저자 칸처럼 값이 둘 이상일 때만 more 표가 생깁니다.

같은 파일 140~168행: 줄 하나를 읽을 때마다 하는 일

메모리에 실제로 놓이는 모양: 지금과 안 2

회색 띠는 Java가 객체마다 붙이는 머리 공간입니다. 지금은 묶음 하나에 개수표 객체가 6개 따로 있어서, 760만 × 6 = 약 4,560만 개의 개수표 객체가 생깁니다. 안 2는 "첫 값 + 개수"를 묶음 안에 칸으로 넣고, 값이 둘 이상인 드문 경우에만 따로 표를 만듭니다. 묶음을 찾는 열쇠도 글자 대신 숫자로 바꿉니다. 안 2의 모양은 dev 설명을 따라 그린 것이고, dev가 짠 코드는 아직 없습니다.

힙 크기별로 해 본 결과

36GB를 줄이는 안 셋, 그리고 "DB에서 묶기"의 장단점

안 1·2는 같은 방식을 가볍게 만드는 것이고, 안 3은 묶는 일을 Java에서 DB로 옮기는 것입니다. 안 3은 메모리를 가장 많이 줄이지만, 결과가 한 권이라도 달라지면 책 번호가 바뀝니다.

모두 dev 예상치입니다. 안 1의 옅은 부분은 30%와 40% 사이 폭입니다. 안 1은 겹치는 글자가 많아서 효과가 있습니다. 묶음 760만 개가 책 161만 권이 되므로, 같은 제목·저자·출판사 글자가 평균 4~5번씩 겹쳐 있습니다. dev는 다음 가져오기(#4) 때 Java의 글자 합치기 옵션(-XX:+UseStringDeduplication)이 얼마나 줄이는지 재기로 했습니다.

안 3: DB에서 묶으면 어떻게 바뀌나

근거: PostgreSQL 18 문서 work_mem "정렬이나 해시 표 같은 작업이 임시 디스크 파일에 쓰기 전에 쓸 최대 메모리", postgresql.org/docs/18/runtime-config-resource.html (확인 2026-10-11).

장점

  • 힙이 몇백 MB로 줄어듭니다(dev 예상). 가져오기를 운영 서버에서 돌려도 서버를 작게 잡을 수 있습니다.
  • 책이 늘어도 메모리가 넘치지 않습니다. 지금은 묶음 수만큼 힙이 늘어나서 4GB에서 멈췄습니다. DB는 메모리가 모자라면 디스크로 넘겨 계속 갑니다.
  • 묶은 과정을 표로 들여다볼 수 있습니다. "이 두 책은 왜 한 권이 됐나"를 SQL로 바로 찾아볼 수 있습니다. (Claude 판단)

단점

  • 결과가 한 권이라도 다르면 책 번호가 바뀝니다. 책 번호는 가져올 때마다 이어 주는데(ADR-0062), 묶는 결과가 달라진 책은 번호가 새로 붙거나 사라집니다. 그래서 161만 권을 지금 방식과 한 권씩 맞대 보는 검증이 필요합니다.
  • 묶기 단계 네 개를 SQL로 다시 써야 합니다. ① 같은 코드 ② 교보식 코드로 계산한 ISBN ③ 국가서지 ISBN ④ 같은 제목·첫 저자·출판사. 제목·출판사 정리(CatalogText), 저자 나누기(Contributors.parse), 대표 출판일 고르기(PublishedDates)는 Java 코드라서 SQL로 다시 쓰거나, Java가 줄마다 미리 계산해 임시 표에 넣어야 합니다.
  • 사슬처럼 이어 묶기가 SQL에서는 번거롭습니다. A·B가 ISBN이 같고 B·C가 제목이 같으면 A·B·C가 한 권입니다. Java는 이것을 한 번에 이어 붙이지만(union·find), SQL에는 그런 명령이 하나로 없어서 더 이상 안 바뀔 때까지 여러 번 돌려야 합니다. 시간이 얼마나 걸릴지는 재 봐야 압니다. (Claude 판단)
  • 동점일 때 고르는 값이 달라질 수 있습니다. 지금은 가장 많이 나온 값을 고르고, 동점이면 "작은" 값을 고릅니다. Java와 DB는 글자의 크고 작음을 정하는 기준이 다를 수 있어서 맞춰야 합니다. (Claude 판단)
  • 가져오는 동안 DB 디스크가 더 듭니다. 줄을 임시 표에 한 번 더 넣으니까요. 크기는 재지 않았습니다.

가져오기를 내 PC(32GB)에서 하기로 하면, 안 3의 가장 큰 장점(운영 서버를 작게)이 덜 중요해집니다. 그래서 따로 하기와 함께라면 안 3은 급하지 않다고 봅니다. (Claude 판단)

4내 PC에서 가져오고 운영에 반영하는 순서

내 PC가 표 네 개를 다 만들어 파일로 내보내고, 운영 서버는 그 파일을 받아 넣고 바꿔 끼우기만 합니다.

②는 PostgreSQL의 pg_dump 명령으로 합니다. 표를 파일 하나로 떠내는 명령입니다. ③~⑤는 지금 가져오기의 마지막 단계와 같아서, 바꿔 끼우기 코드는 사이클 08에 만든 것을 그대로 씁니다.

41분이 두 곳으로 나뉩니다

가로 길이는 가져오기 #2의 시간 비율입니다. 내 PC에서 가져오기가 실패해도 운영 서버는 영향이 없습니다.

5이 방식이 맞게 돌려면 지켜야 할 것

내 PC의 DB와 운영 DB가 "책 표와 도서관 목록이 같은 상태"여야 책 번호가 그대로 이어집니다.

가져오기는 이미 있는 책에는 옛 번호를 그대로 주고, 새 책에만 다음 번호를 줍니다. 이 비교를 내 PC의 DB를 보고 하므로, 내 PC의 DB가 운영과 다르면 번호가 어긋납니다.

collection_link는 서비스 도서관 번호와 수집 DB 도서관 번호를 짝지은 표입니다.

운영에서 책 표를 따로 고치면 생기는 일

바꿔 끼우기는 운영의 옛 책 표를 통째로 지우고 새 표로 바꿉니다. 그래서 운영에서는 책 표를 고치지 않고, 고칠 것은 내 PC 쪽 가져오기로 넣어야 합니다.

운영 디스크 여유

dev 예상치입니다. 운영 서버는 파일만 받아 넣으므로 실제 최대값은 이 사이클에서 다시 잽니다. 아직 없는 것: 파일을 받아 넣고 바꿔 끼우는 명령과 절차 문서. 사이클 08에서는 만들지 않았습니다.

6운영 서버 크기가 어떻게 달라지나

가져오기를 내 PC에서 하면, 운영 서버는 검색에 필요한 만큼만 있으면 됩니다.

"가"로 하면 dev 메모대로 가져오기용 8GB급 힙을 전제로 운영 서버 크기를 정해야 합니다. "나"로 하면 가져오기용 메모리는 내 PC(32GB)가 감당합니다.

7사이클 11에서 정할 것

가장 먼저 정할 것: 운영 서버가 아직 따로 없습니다. 반영할 곳을 무엇으로 시험할지 정해야 합니다.

배포는 보류돼 있습니다(백로그 208행). 지금은 내 PC에서 서비스를 돌리고 Cloudflare 빠른 터널로 임시 주소를 엽니다.

1운영 쪽은 같은 PC에 DB를 하나 더 띄워 시험함 [안]

내 PC에서 가져와 파일로 내보내고, 같은 PC의 두 번째 DB(운영 역할)에 넣고 바꿔 끼웁니다. 그 두 번째 DB에 검색 서비스를 붙여, 반영하는 동안 검색이 멈추지 않는지 봅니다. 진짜 서버로 옮길 때는 파일을 보내는 곳만 바뀝니다.

다른 선택: 배포를 이 사이클에 같이 해서 진짜 운영 서버로 시험. 서버 고르기·비용·접속 설정이 더해져 사이클이 커지고, 보류해 둔 배포 결정(백로그 208행)을 당기게 됩니다.

추천: 같은 PC의 두 번째 DB. 배포 보류 결정을 바꾸지 않습니다.

2힙 6GB 줄이기는 이 사이클에 넣지 않음 [안]

가져오기는 내 PC(32GB)에서 돌므로 6GB여도 됩니다. 사이클 08의 #3(6GB로 끝까지 되는지)과 #4(글자 합치기 옵션 효과) 결과는 기록만 해 둡니다. 안 1·2·3은 백로그에 그대로 둡니다.

다른 선택: 안 1(겹치는 글자 합치기, 작은 일)만 같이. 30~40% 줄지만 결과가 바뀌지 않는지 다시 확인해야 합니다. 안 2·3은 일이 커서 이 사이클과 따로 하는 편이 낫습니다.

추천: 넣지 않음. 6GB가 문제 되는 건 가져오기를 운영 서버에서 돌릴 때인데, 이 사이클이 그걸 없앱니다.

3두 DB가 다르면 반영을 시작하지 않고 이유를 기록함 [안]

운영에 넣기 전에 5번 카드의 세 가지(책 표, 도서관 seed, collection_link)가 내 PC가 기준으로 삼은 것과 같은지 봅니다. 하나라도 다르면 운영 표는 그대로 두고, 가져오기 기록에 실패와 이유를 남깁니다. 무엇으로 비교할지(기록 번호, 버전 등)는 설계 단계에서 정합니다.

다른 선택: 비교 없이 절차 문서에 "운영에서 책 표를 고치지 말 것"만 적기. 만들 것은 줄지만, 실수하면 책 번호가 어긋난 채로 반영됩니다.

추천: 반영 전에 확인하고, 다르면 멈춤.

4이 사이클은 손으로 돌리는 절차까지, 자동 갱신은 밖에 둠 [안]

만드는 것은 명령 두 개(내 PC에서 내보내기, 운영에서 넣고 바꿔 끼우기)와 절차 문서입니다. "정해진 때마다 자동 갱신"은 이 사이클 밖에 두고, 백로그에 "가져오기를 내 PC에서 하면 자동 갱신은 내 PC가 켜져 있을 때 돌리고 파일을 올리는 모양이 된다"는 메모만 더합니다.

다른 선택: 자동 갱신 방식까지 이 사이클에서 정하기. 언제 돌릴지, 내 PC가 꺼져 있으면 어떻게 할지까지 정해야 해서 범위가 두 배쯤 됩니다.

추천: 손으로 돌리는 절차까지. 앞서 "자동 갱신과의 관계를 이 사이클에서 정하는 편이 낫다"고 썼던 것을 이렇게 줄였습니다.
