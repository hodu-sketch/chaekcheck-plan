설계 검토에서 나온 것: 정할 것 2개

설계 검토(design-reviewer) 결과 막는 것은 없고, 고칠 것 5개·작은 것 6개였습니다. 표기·번호 같은 것은 바로 고쳤고(7번 카드), 설계를 정해야 하는 두 가지(#1, #2)만 여쭙니다. #2는 승인하셨고 #1이 남았습니다. (2026-10-12)

이 페이지 읽는 순서

  1. 말 정하기: 책 표 A·B, 작은 표
  2. 정상일 때: 내 PC와 운영을 오가는 네 걸음
  3. finish가 하는 일 여섯 단계
  4. finish가 실패하면: 내 PC·운영 나눠 보기 → 결정 #1
  5. 참고: 색인을 만든 채로 옮길 수 없는 이유
  6. 번호 비교는 누가 하나 → 결정 #2 (승인됨)
  7. 바로 고친 것

1말 정하기

책 표 A = 지금 두 DB가 같이 가진 책 표. 책 표 B = 이번에 내 PC에서 새로 만든 책 표. 목표는 끝났을 때 두 DB 모두 B.

  • 작은 표(load_manifest): 파일과 내 PC의 새 표 B에 붙어 있는 한 줄짜리 표입니다. "이 파일을 만들 때 내 PC 책 표는 A였다"가 적혀 있습니다. 내 PC에 이게 남아 있으면 내 PC는 "운영 반영을 기다리는 새 표가 있다"고 압니다(= 기다림 상태).
  • 기다림 상태에서는 다음 export가 시작하지 않고 "먼저 finish 또는 discard"를 알립니다(설계 #6, 승인).
  • 작은 표 없는 새 표는 지난 실행이 죽고 남은 것으로 보고, 다음 실행이 지웁니다(사이클 08 방식).

2정상일 때: 네 걸음

내 PC에서 B를 만들어 파일로 보내고, 운영이 A와 맞는지 확인한 뒤 B로 바꾸고, 마지막에 내 PC도 B로 바꿉니다.

  1. ① 내 PC export: B를 만들고 작은 표에 "내 책 표는 A"를 적어 함께 파일로 뜸. 내 PC 책 표는 아직 A.
  2. ② 파일 옮김: 이 사이클은 같은 PC라 경로만 줌.
  3. ③ 운영 apply: A = A 확인 → 넣기 → 색인 → 바꿔 끼우기. 운영은 B.
  4. ④ 내 PC finish: 남겨 둔 B로 바꿔 끼움. 두 DB 모두 B → 다음 가져오기는 B 기준.

3finish가 하는 일 여섯 단계

finish는 운영 apply에서 "파일 넣기"와 "해시 비교"를 뺀 나머지입니다. B는 이미 내 PC에 있으니 색인을 붙이고, 통계를 만들고, 바꿔 끼웁니다. (아래는 결정 #1 제안대로 한 순서)

단계하는 일시간 (사이클 08)
1. 짝 확인파일 번호(export_id)가 내 PC 작은 표와 같은지, 내 PC 책 표가 아직 A인지(수·가장 큰 번호·시퀀스). 다르면 멈춤짧음
2. 만들다 만 색인 지우기지난 finish가 3단계에서 실패했을 때만. 처음이면 할 일 없음짧음
3. 색인·제약 만들기내 PC 책 표 A의 정의를 읽어 같은 이름으로 B에 붙임. 기본 키 → 유일 제약(ISBN 등) → 검사 제약 → 외래 키(소장 → 책) → 나머지 색인(제목 검색용 pg_bigm 등). 색인 메모리는 내 PC라 1GB약 1분 39초
4. 통계VACUUM (ANALYZE). 검색이 "색인으로 읽을지"를 고를 때 씀. 파일에는 통계가 안 들어감약 43초
5. 바꿔 끼우기짧은 트랜잭션 하나: 작은 표 지우기 → 옛 A 네 표 지우기 → B 네 표를 catalog로 → 빈 catalog_next 지우기 → 확정. 잠금을 2초 안에 못 잡으면 10초 쉬고 다시, 최대 5번0.33초
6. 기록내 PC catalog_import에 한 줄(가져오기 기록 + 색인·통계·바꿔 끼우기 시간, 같은 export_id)짧음

운영 apply는 이 앞에 해시 비교와 파일 넣기(시간 미측정)가 붙고, 색인 메모리가 256MB라 3단계가 더 걸릴 수 있습니다.

4finish가 색인을 만들다 실패하면: 내 PC와 운영 나눠 보기

운영은 이미 B입니다(③ 성공). 문제는 내 PC입니다. 작은 표를 먼저 지우면 내 PC가 "기다리는 중"이라는 걸 잊어서 B를 지워 버리고, 다음 반영이 막힙니다. 작은 표를 바꿔 끼우는 순간에 지우면 실패해도 기다림이 남아 finish를 다시 하면 됩니다.

지금 설계: 작은 표를 먼저 지움

되살리려면 운영에 넣었던 같은 파일을 내 PC에도 apply해야 합니다. 운영자가 이걸 알고 있어야 합니다.

제안: 작은 표는 바꿔 끼우는 순간에 지움

운영은 어느 쪽이든 내내 B이고 검색도 정상입니다. 차이는 내 PC가 "운영과 맞추는 중"이라는 표시(작은 표)를 실패 뒤에도 가지고 있느냐입니다.

1finish는 작은 표를 바꿔 끼우는 순간(같은 짧은 트랜잭션)에 지우고, 그 전에 실패하면 "기다림" 상태로 남겨 finish를 다시 돌릴 수 있게 한다. 다시 돌릴 때는 만들다 만 색인부터 지운다. 수용 기준을 하나 더한다: "finish가 색인 단계에서 실패해도 다시 finish 하면 끝까지 되고, 그동안 export는 막힌다" [안]

다른 선택: 실패하면 새 표를 지우고, 같은 파일을 내 PC에 apply해서 되살림. 코드는 단순하지만 운영자가 이 방법을 알아야 하고, 넣기 시간이 한 번 더 듭니다.

추천: 기다림 유지 + 다시 finish.

5참고: 색인을 만든 채로 운영에 옮길 수 없는 이유

pg_dump 파일에는 색인 내용이 아니라 "색인을 만들어라"라는 명령만 들어갑니다. 받는 쪽이 새로 만듭니다. 색인째 옮기는 길은 DB 전체를 파일째 복사하는 것뿐인데, 운영에는 쓸 수 없습니다.

  • 파일에 든 것: 표를 만드는 명령, 줄 데이터, 시퀀스 값, 그리고 색인·제약의 "정의". 우리 설계는 내 PC에서 색인을 아예 만들지 않고 덤프하고, 운영이 자기 표 정의를 읽어 색인을 만듭니다.
  • DB 파일 통째 복사: 서버를 멈춰야 하고, 표 하나만 골라 옮길 수 없습니다(전체 거래 기록 없이는 표 파일을 쓸 수 없음). 클러스터 전체를 옮기면 운영에만 있는 회원·내 도서관 데이터까지 덮어씁니다.
  • 그래서 색인 시간(사이클 08 1분 39초, 운영은 256MB라 더 걸릴 수 있음)은 운영에서 들고, 이번 사이클에 상한 1GB를 건 운영 역할 DB로 잽니다(AC-14). 그동안 검색은 옛 표로 계속됩니다.

근거(확인 2026-10-12): SQL 덤프는 "generate a file with SQL commands that, when fed back to the server, will recreate the database" — SQL Dump; post-data는 "definitions of indexes, triggers, rules and constraints" — pg_restore; 파일 복사는 "The database server must be shut down", 표 하나만은 "not usable without the commit log files", "only work for complete backup and restoration of an entire database cluster" — File System Level Backup.

6세 방식의 "번호" 비교는 누가 DB를 읽나

세 방식이 번호까지 같은지 보려면 방식마다 export 뒤 catalog_next의 책·소장 번호를 꺼내야 합니다. 이걸 가져오기 코드(collection)가 읽으면 남의 모듈 표를 직접 읽는 셈이라 모듈 규칙에 어긋납니다.

2번호 꺼내기는 앱 밖 비교 스크립트(compare_grouping.py가 psql로)가 한다. 시험용 도구라 앱 코드에 넣지 않는다 [안]

예: 방식마다 export → 스크립트가 catalog_next.book·catalog_next.holding의 번호를 파일로 뽑음 → discard → 세 방식의 파일 비교. dev는 이미 측정 스크립트에서 psql로 DB를 읽고 있습니다.

다른 선택: CatalogLoad에 "번호 내보내기" 기능을 하나 더함(8개로). 시험에만 쓰는 기능이 공개 API에 남고 ADR-0078을 고쳐야 합니다.

추천: 바깥 스크립트. (승인됨, 2026-10-12)
