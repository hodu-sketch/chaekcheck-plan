# 기능 명세: 가져오기 따로 하기 + 가져오기 힙 줄이기 (사이클 11) (초안)

- 상태: **스펙 결정 끝** (2026-10-12). 범위는 `scope.md`의 확정 값. 조사는 `research.md`. 결정 페이지 `easy/2026-10-12-spec-decisions.html`
- 이 사이클에는 새 화면이 없음. "사용자"는 가져오기를 돌리는 운영자(사용자 본인)

## 사용자 이야기

- 운영자는 가져오기를 내 PC에서 끝까지 돌리고, 결과만 운영 DB에 넣고 싶다. 운영 서버에 힙 6GB·사본·국가서지 파일을 두지 않으려고 [확정] (scope)
- 운영자는 두 DB가 어긋났을 때 잘못된 번호로 반영되지 않기를 바란다 [확정] (scope)
- 운영자는 가져오기 힙을 줄이고 싶다. 두 방식(`compact`, `sql`)을 설정으로 골라 돌리고, 결과가 지금과 같은지와 성능을 숫자로 보고 싶다 [확정] (scope)

## A. 따로 하기

### 입력과 출력

| 항목 | 내용 | 규칙 | 상태 태그 |
|---|---|---|---|

| 내보내기 명령 출력 | 파일 하나: `catalog_next` 네 표(구조·데이터·시퀀스 값) + 두 DB 비교용 값 + 가져오기 기록 | `pg_dump` 사용자 지정 형식(`-Fc`) | [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #4) |
| 반영 명령 입력 | 위 파일 경로 | 운영 DB에서 실행 | [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #5) |
| 반영 명령 출력 | 운영 `catalog` 바뀜, 운영 `collection.catalog_import`에 한 줄 | — | [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #6) |

### 동작 규칙

- R-A1 번호 잇기(match)는 내 PC에서 함. 내 PC DB의 책 표가 운영과 같아야 하는 조건은 그대로 [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #1)
- R-A2 내 PC의 바꿔 끼우기는 운영 반영이 성공한 뒤에 함. 그때까지 내 PC의 `catalog_next`를 남겨 둠 [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #2)
- R-A3 반영 명령은 시작할 때 두 DB가 같은지 봄. 비교: 도서관(`library.library`의 enabled 곳 id·base_url·platform_type)과 `collection_link`는 내용 해시, 책 표는 `book`·`holding`의 줄 수·가장 큰 번호·시퀀스 값, **네 표의 칸 구조(칸 이름·타입) 해시** [확정] (사용자 승인, 2026-10-12, 점검 #5; 설계 결정 #2). 비교 값은 파일 속 작은 표 `catalog_next.load_manifest`에 실려 오고, 운영은 복원 전에 그것만 읽어 비교 [확정] (사용자 승인, 2026-10-12, 점검 #5; 설계 결정 #1). 다르면 운영 표에 손대지 않고 기록에 실패 `mismatch` + 무엇이 달랐는지 [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #3)
- R-A4 반영 순서: 남은 `catalog_next` 지움 → 파일 복원(`catalog_next`로) → 색인·제약(운영 `catalog` 정의를 읽어) → `VACUUM (ANALYZE)` → 바꿔 끼우기(사이클 08 그대로, `lock_timeout` 2초·10초·5번) [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #5). 반영 연결은 `maintenance_work_mem` 256MB로 색인을 만듦 [확정] (사용자 승인, 2026-10-12, 점검 #5; 설계 결정 #12)
- R-A5 운영 DB의 가져오기 기록: 내 PC 기록(책·소장 수, 수집 기간, 단계 시간)을 파일에 실어 보내고, 운영이 반영 단계 시간(`restore`, `index`, `analyze`, `swap`)과 결과를 더해 한 줄로 남김 [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #6)
- R-A6 운영 역할 DB는 같은 PC에 compose 서비스 하나 더(같은 이미지, 자기 볼륨, 포트 5434) [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #7) — 운영 쪽 시험은 같은 PC [확정] (scope). 컨테이너 메모리 상한 `mem_limit` 1GB를 걸고, 처음에는 내 PC의 `db`를 통째로 복사해 시작 [확정] (사용자 승인, 2026-10-12, 점검 #5; 설계 결정 #12)
- R-A7 내 PC에 운영 반영을 기다리는 새 표(`load_manifest`가 있는 `catalog_next`)가 있으면 다음 가져오기·내보내기는 시작하지 않고 "먼저 finish 또는 discard"를 알림. `load_manifest`가 없는 `catalog_next`(죽고 남은 것)는 지금처럼 지우고 시작 [확정] (사용자 승인, 2026-10-12, 점검 #5; 설계 결정 #6)
- R-A8 `discard` 모드는 어느 DB(내 PC, 운영 역할 DB, 한 DB 가져오기)에서든 남은 `catalog_next`를 지우는 명령을 겸함. 기다리는 새 표를 지울 때는 "운영 반영이 실패했을 때만" 안내 [확정] (사용자 승인, 2026-10-12, 점검 #1; 사이클 08 회고 45행 결정)
- R-A10 `finish`는 작은 표(`load_manifest`)를 바꿔 끼우는 짧은 트랜잭션 안에서 지움. 그 전(짝 확인·색인·통계)에 실패하면 "기다림" 상태가 남고, 다시 `finish`하면 만들다 만 색인·제약부터 지우고 처음부터 함 [확정] (사용자 승인, 2026-10-12, `easy/2026-10-12-review-decisions.html` #1)
- R-A9 명령은 지금 가져오기 명령에 모드 설정(`in-place`(기본, 지금 동작)·`export`·`apply`·`finish`·`discard`)과 파일 경로를 더함 [확정] (사용자 승인, 2026-10-12, 점검 #5; 설계 결정 #3)

### 상태별 동작

- 두 DB가 다름 → 반영 안 함, `mismatch` 기록, 운영 검색 그대로
- 복원·색인 중 실패 → 운영은 옛 표 그대로, `catalog_next` 지움, `error` 기록
- 바꿔 끼우기 잠금 실패 → 사이클 08과 같음(`lock_not_acquired`)
- 반영 명령이 도중에 죽음 → 빈 `catalog_next`가 남고 다음 반영이 시작할 때 지움(사이클 08 AC-9와 같은 방식) [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #5)

## B. 힙 줄이기

### 동작 규칙

- R-B1 설정 값 `current`·`compact`·`sql`, 측정이 끝날 때까지 기본값 `current` [확정] (scope)
- R-B2 `compact`: 겹치는 글자 하나로 합치기 + 개수표 6개를 묶음 안의 칸으로 + 묶음 열쇠를 숫자로 (dev 안 2) [확정] (scope)
- R-B3 `sql`: 제목·출판사 정리, 첫 저자, 교보식 ISBN, 출판일은 Java가 줄마다 계산해 임시 표에 넣고, 묶기(같은 값끼리, 사슬처럼 잇기, 가장 많은 값 고르기)만 SQL로 [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #8)
- R-B4 가장 많은 값이 동점이면 지금과 같은 값을 고름(SQL은 `mode()` 대신 개수 큰 순 + 값 순, C 정렬). 보조 평면 문자에서 생길 수 있는 차이는 결과 비교로 잡음 [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #9) (근거 `research.md` 9절)
- R-B5 결과 비교: 같은 사본으로 세 방식을 돌려 책마다 비교, 다른 책이 한 권이라도 있으면 그 방식은 쓰지 않음 [확정] (scope). 비교 대상: 어떤 줄들이 한 책이 됐는지, 고른 제목·저자·출판사·출판일·ISBN·콘텐츠 종류, 도서관 목록. **세 방식 모두 "그 책의 첫 줄을 사본에서 읽은 순서"로 책을 만들고, 결과 비교는 책·소장 번호까지 같아야 통과** [확정] (사용자: 미승인 사유로 바꾼 제안을 그대로 고름 "세 방식 모두 \"첫 줄을 읽은 순서\"로 책을 만들고, 결과 비교에서 번호까지 같아야 통과로 봅니다", 2026-10-12, 스펙 결정 #10). 이유: 새 책 번호(`JdbcCatalogLoad.java` L552-555)와 동점일 때 옛 번호를 받는 책(L546)이 책을 만든 순서를 따름. `sql`은 줄마다 읽은 순번을 싣고 첫 줄 순번 순으로 꺼냄
- R-B6 측정: scope의 여섯 관점, 방식마다 두 번 [확정] (scope). 더해서 `current`에 Java 옵션 두 개(글자 합치기 `-XX:+UseStringDeduplication`, 객체 머리 줄이기 `-XX:+UseCompactObjectHeaders`)를 붙인 경우도 잼, GC 로그(`-Xlog:gc`)를 켬 [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #11)
- R-B7 기본값: 결과 비교 통과 + 43분 안 + 힙이 가장 작은 것 [확정] (scope)

## 수용 기준

- AC-1: 내 PC에서 내보내기 명령을 돌리면 파일 하나가 생기고, 내 PC의 `catalog`는 그대로다(검색 결과 같음)
- AC-2: 운영 역할 DB에서 반영 명령을 돌리면, 반영 뒤 운영의 책 수·책 번호·소장 번호가 내 PC `catalog_next`와 같다(`compare_books.py`로 검색 응답 비교, SQL로 번호 비교)
- AC-3: 반영하는 동안 운영 검색이 멈추지 않는다: 기다린 시간 1초 안, 5xx 0 (`probe_during_import.py`) [확정] (사용자 승인, 2026-10-12, 스펙 결정 페이지 #12) (사이클 08 결과 0.1~0.3초 기준)
- AC-4: 운영의 도서관 표나 `collection_link`, 책 표를 일부러 하나 바꾸고 반영하면 시작하지 않고 `mismatch`와 다른 곳이 기록된다
- AC-5: 복원 도중 프로세스를 멈추면 운영 검색은 그대로이고, 다음 반영이 남은 `catalog_next`를 지우고 끝까지 간다
- AC-6: 반영이 성공한 뒤 내 PC를 바꿔 끼우면 두 DB의 비교 값이 같다(다음 가져오기를 바로 할 수 있다)
- AC-7: 운영 `collection.catalog_import`에 내 PC 단계 시간과 반영 단계 시간이 한 줄로 남는다
- AC-8: 설정 값 셋으로 각각 dry run이 끝까지 돈다
- AC-9: 세 방식의 결과 비교에서 다른 책이 0권이고 책·소장 번호도 모두 같다(다르면 예시 목록이 남는다)
- AC-10: 측정 표(방식 × 관점, 두 번씩)가 plan에 넘어온다. 힙은 끝까지 되는 가장 작은 값까지
- AC-11: 두 DB의 책 표 칸 구조가 다르면(예: 운영 역할 DB에만 칸 하나를 더함) 반영이 시작하지 않고 `mismatch`(표 구조)가 기록된다
- AC-12: 내 PC에서 `export` 뒤 `finish`·`discard` 없이 다시 `export`하면 시작하지 않고 "먼저 finish 또는 discard"가 나온다. 내 PC `catalog`와 남겨 둔 새 표는 그대로다
- AC-13: 반영 도중 프로세스를 멈춘 뒤 그 DB에서 `discard`를 돌리면 남은 `catalog_next`가 지워지고 검색 결과는 그대로다
- AC-14: 컨테이너 상한 1GB를 건 운영 역할 DB에서 반영(색인 메모리 256MB)이 끝까지 되고, 색인 시간이 기록에 남는다
- AC-15: 내 PC `finish`를 색인 단계에서 멈추면 내 PC는 "기다림"으로 남아 `export`가 시작하지 않고, 다시 `finish`하면 끝까지 되어 두 DB의 비교 값이 같아진다 [확정] (사용자 승인, 2026-10-12, `easy/2026-10-12-review-decisions.html` #1)
